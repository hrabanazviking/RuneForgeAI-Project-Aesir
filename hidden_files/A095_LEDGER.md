## End-to-end effect (measured, purpleraider, uncontended - ps checked before every NPU run; no seat gate, no other NPU tool live)
Medians; NPU = warm reps (21) with resident context; CPU-opt = 32-thread -O3 -march=native i16->i32 GEMM; oracle = naive single-thread in-program oracle (the A-092/A-094 comparator class).
- 64x64x64: NPU run 99.7 us (A-094 measured 102.6 us - consistent). CPU oracle at this size is ~94-192 us depending on build flags; band-floor win is marginal vs optimized code, as A-094's bracket implies.
- 128x1024x1024 per dispatch: NPU 2262.7 us (run) / 2268.7 us (run+sync); CPU-opt 499.3 us; naive oracle 262,785 us. NPU = 116x vs naive oracle, 0.22x vs CPU-opt.
- End-to-end sequence, 128 consecutive projection dispatches at 128x1024x1024 (32-layer x 4-projection prefill proxy): NPU total 287,400.1 us (2245.3 us/dispatch, final output exact); CPU-opt total 79,022.2 us (617.4 us/dispatch). Single-tile NPU is ~3.6x SLOWER end-to-end than the optimized CPU path at this shape - filed plainly, not rounded away.
- Boundary conversion price (A-094 named it unmeasured; A-095 prices it): Q4->i16 dequant 665-674 us per 1,048,576 weight elements (~0.64 ns/elem in the runner; spike cross-check 0.696 ns/elem, hidden_files/a095/cpu_compare_fresh.log opt 0.548 ms vs WIP 0.527 ms - WIP reproduced). This is weights-side, once per layer load, amortized across prefills - NOT a per-dispatch cost; a production bridge additionally faces f16 activation conversion, not measured here.
- Verdict NEUTRAL-WITH-VALUE: value = the registry + dispatch + resident-context path now exists and is proven on the real device end-to-end (150 consecutive exact dispatches), the op beats the oracle class by two orders of magnitude, and the flag-OFF default means zero production behavior change today.
