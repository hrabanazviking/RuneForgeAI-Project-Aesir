# Task: Project A.E.S.I.R. AI Reality Rules — Part 2

## Authorization

Volmarr requested a massive `AI.rules.part2.md` rule set that prevents fake
code and requires AIs to write real, connected, executable code, then instructed
that it be pushed to the real GitHub `main` branch. This authorizes inspection
of existing repository law, creation of the new rules document, minimal
cross-linking needed to make it an active project authority, verification,
commits, and pushes. It authorizes no runtime implementation, capability
promotion, deletion, Git-configuration change, or fabricated evidence.

## System Statement

Project A.E.S.I.R. already has `RULES.AI.md`, a canonical capability ledger, an
evidence-backed TODO, a reality-first roadmap, fixture provenance policy,
artifact prevention, counted tests, and fail-closed boundaries. The missing
governance layer is a comprehensive code-admission and claim-evidence law that
AI agents can apply mechanically to every function, file, test, integration,
external capability, and completion statement.

## Owning Domain

- `AI.rules.part2.md` — new AI code-reality and evidence law
- `RULES.AI.md` — original project law and authority link
- `CAPABILITY_LEDGER.md` — canonical present-tense capability status
- `TODO.md` — canonical evidence-backed backlog
- `ROADMAP_REALITY_FIRST_COMPLETION.md` — anti-fabrication execution order
- `scripts/check_doc_drift.py` and CI — existing mechanical enforcement

## Desired End State

Create a comprehensive rule set that:

1. defines fake code, fake completion, fake tests, fake integration, fake data,
   fake compatibility, fake hardware, and fake operational evidence;
2. requires every production function to perform its advertised operation or
   fail explicitly before side effects;
3. requires connected vertical slices, ownership, failure contracts, tests,
   documentation, and ledger reconciliation;
4. establishes evidence standards for local logic, persistence, networking,
   formats, models, hardware, concurrency, recovery, security, performance, and
   cross-platform support;
5. defines stop conditions that force an AI to report blocked or unsupported
   behavior instead of inventing success;
6. supplies pre-edit, pre-commit, completion, and review checklists;
7. resolves legacy-rule conflicts in favor of observable truth and the user's
   current instruction to push to real `main`.

## Invariants

- `CAPABILITY_LEDGER.md` remains the present-tense status authority.
- Existing verified CPU and safety behavior remains unchanged.
- A document cannot promote a runtime capability.
- No placeholder implementation file or orphan rule file is admitted.
- No tracked file, function, model, fixture, asset, or history is deleted.
- No machine-local path, secret, generated binary, model weight, fake fixture,
  benchmark, device result, compatibility claim, or CI result is added.
- Existing deletion approval remains limited to temporary model-store-test
  paths and is not exercised by this documentation task.

## Verification Plan

- reconcile Part 2 against current rules, ledger, TODO, roadmap, and CI policy
- link the supplement from the primary rules document
- scan for contradictory branch, status, completion, and capability language
- run documentation consistency, artifact, and fixture-provenance gates
- run master suite, native build, deliberate negative control, and diff checks
- commit and push each documentation boundary to `origin/main`
- observe hosted CI for the final pushed revision

## Completion Boundary

This task establishes enforceable repository law and review gates. It does not
claim that every rule is already mechanically detected by CI. The document must
distinguish rules already enforced by tests/scripts from rules requiring human
or AI review, and it must require future repeat violations to become automated
gates when deterministic detection is feasible.
