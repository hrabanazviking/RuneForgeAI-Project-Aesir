## 0. Protocol (committed first, before any code was built)

This section was committed before the picker extension, the chat wiring, or any test existed. It states the catalogue interface this slice builds on, the exact J-102/J-103 boundary, the fetch/verify decision rule (stated before building, per the slice's commission), and the verdict rule for the slice; everything after §0 is filed under these rules and no others.

### 0.1 The catalogue interface — build on the one that exists, invent no second one

The tree has exactly one durable model catalogue: the `DurableModelStore` catalog (`cli/storage.mojo`, `catalog.v1`) that `pull --name` registers verified bytes into and that the picker already lists through `installed_model_choices`. There is **no** known-models (fetchable) catalogue data anywhere in the tree today — J-099 verified the absence, and this slice does not invent a second catalogue store to put it in. Instead:

- This slice defines the **known-models data interface** in `cli/model_selector.mojo`, beside the picker that consumes it: a `KnownModelEntry` struct carrying exactly the pins the existing pull machinery already demands — display identity (`name`, `tag`), `repository` (owner/name), `filename` (a `.gguf`), `revision` (40 lowercase hex), `sha256` (64 lowercase hex, bare — the form `pull --sha256` and `download_hf_model` take), `size_bytes` (≥ 24, the GGUF-header floor `download_hf_model` enforces), and `quantization` (display only, rendered through the same terminal-safety rule as installed rows).
- The interface's provider is `known_model_catalogue() -> List[KnownModelEntry]`. **In this slice it returns an empty list, honestly:** no curated entries exist in the tree, and seeding invented entries with invented pins would file false catalogue data. The picker must render and decide correctly over the interface with zero entries (today's production behaviour: installed-only, exactly as before) and with fixture entries (the unit suite's proof of the fetchable path).

### 0.2 The J-102 / J-103 boundary, stated exactly

- **J-102 (this slice) owns:** the `KnownModelEntry` shape and its validation; the provider function's contract; the combined picker (installed + fetchable, visually distinguished, stable numbering); the selection → fetch → verify → run decision logic; the fetch integration through the existing pull machinery (§0.3); and the chat call-site wiring that uses them.
- **J-103 owns:** the curated in-repo catalogue **dataset** — the actual entries, kept in the repo as data with their sources and sha256 pins — and the `get` behaviour around it (including refusal-on-mismatch as a standalone command surface). J-103 lands its data **behind `known_model_catalogue()`'s existing shape**; it does not redesign the picker, the entry, or the decision rule. If J-103's data work discovers the shape is wrong, that is a defect against this slice to file, not a silent fork.
- The fetch/verify **engine** is neither slice's to rebuild: it is `pull`'s — `download_hf_model` (pinned, resumable, publishes only after size + header + SHA-256 checks) and `DurableModelStore.ingest_model` (re-measures the source bytes and refuses registration unless the measured digest and size equal the expected pin). This slice reuses both, verbatim, and re-implements neither downloading nor hashing.

### 0.3 The fetch/verify decision rule, stated before building

Every picker selection resolves through one pure decision function, `first_run_decision(entry, fetch_attempted, observed_digest, observed_size)`, with exactly three actions:

- **RUN** — the entry is installed in the durable catalog (its manifest digest starts `sha256:`, the existing `installed_model_choices` rule), **or** the entry was fetchable, a fetch was attempted, and the observed bytes match the catalogue pin exactly: observed digest == `sha256:` + the entry's `sha256` **and** observed size == the entry's `size_bytes`.
- **FETCH** — the entry is fetchable and no fetch has been attempted yet: the picker offers/starts the fetch through the pull machinery before any first run. The fetch is parameterised by `pull_args_for_entry(entry)` — the exact argv `dispatch_pull` parses (`pull <repository> <filename> --revision <rev> --sha256 <sha> --size <n> --name <name:tag>`) — and executed by the same two calls `dispatch_pull` makes after parsing: `download_hf_model(repository, filename, destination, revision, sha256, size, 1)` then, on success, `ingest_model(reference, 'FROM "sha256:<sha>"', destination, "sha256:<sha>", size)`, whose measured record supplies the observed digest/size the decision re-checks.
- **REFUSED** — a fetch was attempted and the observed bytes do not match the pin (digest mismatch, size mismatch, or no verified bytes observed): the model is **not** offered for first run, and the refusal carries the reason (which pin failed). A download that raises (checksum failure inside `download_hf_model`, destination already present, network failure) never reaches registration and never produces a RUN.

No other path to a first run exists for a fetchable entry: unverified is refused, not warned-through.
