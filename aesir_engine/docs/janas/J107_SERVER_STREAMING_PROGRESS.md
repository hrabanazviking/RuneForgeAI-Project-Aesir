## 0. Protocol (committed first, before any code was built)

This section was committed before the streaming layer, the parser/serve wiring, or any test existed. It states what the inspection found, the stream protocol as decision rules, the closures this slice takes, the one leg it consciously does not take, and the verdict rule for the slice; everything after §0 is filed under these rules and no others.

### 0.1 What exists, and the exact delta (re-verified first-hand in this tree at the base tip)

- **The progress account exists and is proven, and nothing consumes it.** `core/prompt_progress.mojo` (J-059) states one read's shape under the pre-registered discipline — watched iff ≥ 1,024 prompt tokens AND ≥ 4 chunks; records only at chunk boundaries; a 10% step throttle (at most 10 records per read); the final 100% record exactly once — and renders two forms: `render_progress_line` (CLI) and `render_progress_event` (one flat JSON object: `{"event":"prefill_progress","tokens_done":…,"prompt_tokens":…,"percent":…,"chunk":…,"chunks":…,"done":…}`, with `elapsed_ms` present only when the caller supplies one). A tree search confirms J-099 T07's finding: the module is imported only by its own test; no live surface consumes it.
- **Every streaming route is silent for the whole read (J-059 §2, re-verified).** In `cli/native_serve.mojo`'s `serve_loaded`, all three generation routes — Ollama (`/api/generate`, `/api/chat`), OpenAI (`/v1/chat/completions`, `/v1/completions`), native (`/v1/generate`) — call the blocking `session.begin_turn(...)` first and send the stream head (`send_stream_head` / `send_native_stream_head`) only after it returns, inside the `if request.stream:` branch that follows. During a long prompt read the client has received nothing at all — not even response headers.
- **Why nothing can interleave tonight (the structural fact W1 names).** `ControlledTextSession.begin_turn` (core/generation_control.mojo) is a blocking call with no sink, callback, or progress parameter; both CUDA sessions run their whole prefill loop inside it (width 1, or width-4 tiles on the one admitted Llama 3 profile). The serve loop is single-threaded and polls its listener only at decode boundaries (`admit_pending` inside the decode loop). There is therefore no program point at which the serve could send a progress event *during* a read without changing the session contract itself — W1 is session work, not serve work.
- **What the serve already knows, exactly.** After `begin_turn` returns, `session.status().prompt_tokens` is the read's exact total; the serve's own `prefill_batch` parameter is the session's read width (the Llama 3 call site passes `session.prefill_batch` ∈ {1, 4}; the Gemma 4 call site takes the default 1, matching its width-1 loop). The native route already times `begin_turn` (`prefill_elapsed_ms` → `timings_ms.prefill`); the Ollama and OpenAI routes do not split the phases. So the J-059 plan for a completed read is computable exactly, after the fact, from caller-observed values — the same honesty basis as `timings_ms`.
- **Streaming usage (K5's ground).** Streamed OpenAI chunks carry no usage object; the parser refuses `stream_options` by name ("Unsupported OpenAI request field: stream_options"), and J-106's audit tables record it REFUSED in both the chat (31) and completions (19) tables. Non-streamed usage is complete (J-106 C3, incl. `prompt_tokens_details.cached_tokens`).

### 0.2 The streaming layer (the pure layer)

A new pure module, **`aesir_engine/core/stream_progress.mojo`**, owns the stream protocol for progress, following the road's established shape (pure logic unit-tested at the lightest target; hosts execute the decisions; no session or socket is faked):

- **Stream kinds:** `STREAM_NATIVE_NDJSON`, `STREAM_OLLAMA_NDJSON`, `STREAM_OPENAI_SSE`, with `stream_kind_name(code)`.
- **Framing:** `progress_frame(kind, record)` — the wire form of one emitted record. The payload is J-059's `render_progress_event(record)` verbatim on every kind; the frame is payload + `"\n"` on the NDJSON kinds, and `"data: " + payload + "\n\n"` on the SSE kind. The payload is an Aesir extension event, **not** a `chat.completion.chunk` — a client distinguishes it by its `event` field (answered-locally, §8).
- **The sequence:** `progress_frames(kind, total_tokens, chunk_width, final_elapsed_ms = -1)` → the read's full framed sequence under the J-059 discipline, in boundary order: exactly `plan.records_expected` frames for a watched read, zero for a silent one. Elapsed honesty (M7's rule, from J-059 §3): non-final records carry **no** `elapsed_ms` (per-boundary times are not measured by any loop tonight, and the layer never invents one); the final record carries `final_elapsed_ms` when the caller supplies its measured whole-read time (≥ 0), and no timestamp otherwise.
- **The usage decision:** `stream_usage_requested(stream, include_usage)` — the one place the K5 rule lives (usage chunk iff the request both streams and asked).

### 0.3 The stream protocol (pre-registered order, all streaming routes)

For a streaming generation request, the wire order is:

1. **Head first.** The stream head is sent **before** `begin_turn` — the client receives `200` + headers at request start, not after the read. On the OpenAI chat route the role chunk (the stream's prologue, no content) follows the head, also before `begin_turn`. `response_started` / `stream_kind` are set before `begin_turn` too, so a read that fails mid-way is answered by the existing streamed-error path, never by a second response head on a started stream.
2. **Progress before decode.** After `begin_turn` returns and before the first decode chunk, the route sends the read's `progress_frames(...)` sequence (width = the serve's `prefill_batch`, clamped to ≥ 1; total = `status().prompt_tokens`; final elapsed = the route's own measured prefill ms). A silent read sends zero frames. No progress frame ever follows a decode chunk.
3. **Decode unchanged.** Chunks, the 1 MiB answer bound, admission polling, and finish handling are exactly as they stood.
4. **Usage chunk (OpenAI routes, K5).** When `stream_usage_requested` holds, one usage chunk follows the final finish chunk and precedes `data: [DONE]`: a chunk object with empty `choices` and the turn's caller-observed `usage` (prompt / completion / total + `prompt_tokens_details.cached_tokens`, validated by the Gate like every usage field).
5. **`[DONE]` last** (OpenAI routes), as today.

Non-streaming requests are untouched: no head games, no progress (there is no stream to carry it), usage in the body as J-106 left it.

**The honesty clause that rides with step 2, stated before any code:** on this wiring the progress frames are emitted **batched after the blocking read completes**, in discipline order, before any generated text. They are the read's true record (exact totals, exact discipline, the final frame's true whole-read elapsed) — the streaming form of the native route's after-the-fact `timings_ms` — but they do **not** arrive spread across the read, and no text in this slice may claim they do. Arrival *during* the read requires W1, the session sink (§0.4). What step 1 does change in real time is the silence itself: headers (and the chat role chunk) now arrive at request start, so a client is never again held in total silence — not even headers — for a whole long read. The deferred leg (§5) grades both halves live.

### 0.4 The one leg consciously not taken here: W1, the session sink

W1 (a progress sink on the CUDA sessions: `begin_turn` handing each emitted record to a host receiver per boundary, with the loop's own monotonic elapsed) is **not** built in this slice, for three recorded reasons: (i) it changes the `ControlledTextSession` contract and both CUDA sessions' prefill loops — engine work whose only honest proof is a live run (ids-first: a watched read must produce the silent read's ids, token for token), and no live run is possible under this slice's bounds (§5); (ii) J-059 §7 already files W1's exact build order (W2 → W1 → W3) and grading recipe for a device-capable worker, and this slice completes W3's serve half against that recipe; (iii) a sink wired but never run would be precisely the faked surface J-059 refused to build blind. W1 is therefore DEFERRED-WITH-REASON with its recipe re-cited in §5/§7, re-cited at the **J-118 Part VII gate**. The CLI host-loop wiring (J-059's W2, G-099-1's unowned chat-side leg) is likewise untouched here: J-107 owns progress through the *server* API (J-099 §3), and W2 stays named for the keeper's disposition, not silently absorbed.

### 0.5 The closures (each closed in scope, wired, and tested)

- **S2 — the progress stream (T07's server leg).** §0.2's layer + §0.3 step 2 wired on all three routes; the Ollama and OpenAI routes gain the native route's prefill timing so the final frame's elapsed is measured on every route (the Ollama/OpenAI whole-request `elapsed` fields keep their current meaning — the split is used only for the final progress frame, and the native route's `timings_ms` is untouched).
