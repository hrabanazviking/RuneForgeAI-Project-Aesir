### 0.1 The question, and the inventory from this tree

J-113 proved the *decision* core of vocabulary restriction as a pure layer and refused the NSM dressing. This slice owns the three things J-113 named as its scope (§0.4 of the J-113 doc): **exact enforcement in the sampler** (a restricted generation can only emit tokens the restrictor admits), **measured cost** (what the restriction's per-token scan costs, honestly, at module level), and the **chat + server surface** (the restriction reachable from chat and from the server/OpenAI surface as tested behaviours, the word list supplied by the user under J-113's bounds).

The tree inspection at the base tip, verified first-hand for this slice:

- **Where the samplers actually live.** There are two. (1) `core/sampler.mojo` — the CPU sampler: `sample_token_from_logits` over an f16 logits pointer (greedy scan with lowest-ID tie, plus a candidate pipeline: threshold filter at max−15, `apply_token_mask` suppression at −1e9, repetition/frequency/presence penalties, temperature, top-k, top-p, min-p, softmax draw from `RuneRNG`); it is the sampler of `core/inference.mojo`'s CPU generation line. (2) `core/cuda_sampling.mojo` — `NativeCUDASampler`, the CUDA sessions' device sampler (partitioned top-k on device; only the chosen token leaves the device), used by `core/llama3_cuda.mojo` / `core/gemma4_cuda.mojo` through `forward()`.
- **How grammar masking is wired today.** `core/grammar.mojo`'s `GBNFGrammar.apply_token_grammar_mask` masks an f16 logits pointer over *candidate token texts* (the layer decides over decoded text; its token-ID-only sibling `apply_grammar_mask` refuses by design). The CUDA sessions carry the `BooleanJSONGrammar` token trie: `forward()` calls `sampler.select_boolean_json(...)` with the trie's next IDs, and `next_chunk()` advances the trie with the emitted token. The engine facade's grammar entry (`generate_tokens_with_grammar`) still raises not-implemented — re-verified at the base tip.
- **No permitted-vocabulary enforcement exists on any generation path** (J-113 §0.1, unchanged at this tip): `PermittedVocab` appears only in J-113's layer and its test.
- **The surfaces' shapes.** Chat: `cli/cuda_chat.mojo`'s two `chat_control` bodies (Gemma 4 and Llama 3 sessions) route slash forms to pure layers (J-112's `/services` is the standing pattern: pure layer answers, host emits; `/services tokenize` executes through the resident tokenizer); the slash-name candidate set lives in `core/chat_manners.mojo` (`chat_command_names`, pinned count 17 after J-112's growth) and the help text in `cli/chat_history.mojo`. ### 0.2 The build: enforcement in the CPU sampler + a candidate layer (new `core/constrained_generation.mojo`)

- **Sampler enforcement (`core/sampler.mojo`, the CPU sampler).** Two additions, in the file's own grain:
  - `apply_vocab_restriction(mut candidates, candidate_texts, restrictor) raises -> Int`: the restriction form of `apply_token_mask` — every candidate whose decoded text the restrictor does not admit gets logit −1e9; admitted candidates are untouched. Raises on a candidate/text count mismatch (a mask applied to the wrong texts is a programming error, never a silent pass). Returns the admitted count.
  - `sample_token_from_logits_restricted(logits_ptr, vocab_size, token_texts, restrictor, temperature, top_k, top_p, repetition_penalty, context_tokens, mut rng, frequency_penalty, presence_penalty, min_p, suppress_tokens) raises -> Int`: `sample_token_from_logits`' exact sibling with the restriction enforced *first and exactly*. Contract: `token_texts` must carry one decoded text per vocabulary ID (count mismatch raises — token IDs alone contain no lexical information, the grammar layer's standing rule). The restrictor is taken by value: **sampling never advances it**; the caller commits the emitted token's text through `advance_state` after emission (validate-then-commit preserved end-to-end; a refused token is never emitted, so there is nothing to roll back). Returns the emitted token's ID, or **−1 when no candidate is admitted** — the restricted sampler never falls back to a disallowed token (the unrestricted function's return-0 fallback does not exist here). Path rules mirror the unrestricted function exactly: greedy (temperature ≤ 0 or top_k == 1) scans admitted-and-unsuppressed IDs only, sanitised logits, lowest ID on ties; the sampled path computes its max−15 threshold over the *admitted* set (the renormalised distribution's own max — answered-locally, §0.6), excludes suppressed IDs by construction, then runs the standing pipeline (penalties, temperature, top-k, top-p, min-p, softmax draw) over the admitted candidates only.
- **The candidate layer (`core/constrained_generation.mojo`, new, pure).** The host-facing form of the same decisions, over `TokenCandidate` lists any host holds:
  - `cg_masked_indices(candidates, candidate_texts, restrictor) raises -> List[Int]` — the positions `apply_vocab_restriction` leaves unmasked. **Agreement claim (the slice's core proof obligation):** for the same candidate order, this equals J-113's `allowed_indices(candidate_texts)` exactly, in every restrictor state — same predicate (`is_token_valid`), same order, no second implementation of the decision.
  - `cg_apply_vocab_mask(...)` — delegates to the sampler's `apply_vocab_restriction`.
  - `cg_greedy_choice(candidates, candidate_texts, restrictor) raises -> Int` — the admitted position with the highest logit (ties: lowest position), or −1 when none is admitted.
  - `cg_scan_account(candidate_texts) -> ScanAccount` — the deterministic cost account: candidates scanned (always the full set — the scan has no early exit), total candidate-text bytes, admitted count under a stated restrictor state is the mask's own return, never estimated.
  - The chat answers (§0.4) and the server validation/refusal text (§0.5) also live here, as pure functions of the command / the supplied list.

### 0.3 Measured cost: the design (pre-registered)

Cost is measured at module level on deterministic synthetic data — no model, no inference, no tok/s anywhere:

- **Exact counts (PROVEN by the unit suite):** the scan examines every candidate (admitted + masked == candidate count, at stated sizes), and `cg_scan_account`'s candidate/byte counts are exact on the filed sets.
- **Wall cost (MEASURED-INDICATIVE, single VM run, machine state filed):** a filed driver (`docs/janas/j114_cost.mojo`) times, per stated candidate-set size (256 / 1024 / 4096 candidate texts over a 6-word permitted list, deterministic rotation of token-like pieces), two scans over the same `TokenCandidate` lists: the *unrestricted baseline* (a greedy max-scan, no validity calls) and the *restricted scan* (`cg_apply_vocab_mask`'s validity scan). Discipline follows the tree's bench shape: one settle round discarded, five measured rounds, the median filed beside min/max; the admitted counts are accumulated and printed so the scan cannot be optimised away. The numbers are per-scan nanoseconds on this VM at the filed memory state — a module-level cost of the decision scan, never a generation speed, and the restricted scan's cost beside the baseline is the restriction's price in the only terms this slice may state.

### 0.4 Chat surface: the `/constrain` door (J-112 pattern)

A new slash family in both `chat_control` bodies, answered by the pure layer (`cg_constrain_response(command) -> String`, which never raises — refusals are text, in the services manner):

- `/constrain list <words>` — a user-supplied word list validated through J-113's parser: the answer is the canonical render + distinct count under the layer's bounds (8192 entries / 64 bytes), or the parser's refusal verbatim in a refusal line. This is a real behaviour: the exact list a restricted generation would enforce, checked and canonicalised.
- `/constrain audit <words> :: <text>` — the list (before the first ` :: `) grades the supplied finished text through `vr_audit_text`: totals, permitted count, first offender. The audit grades a text; it does not pretend to have constrained one (J-113's standing distinction).

Wiring: one branch per `chat_control` body (`/constrain` / `/constrain ...`), placed after the `/services` branch; `/constrain` joins `chat_command_names` (the manners candidate count moves 17 → 18 and its pin is updated in the neighbour suite, the J-112 growth pattern) and the chat help text. ### 0.6 Scope decisions (answered-locally, with precedents)

- **Why the CPU sampler is "the sampler" for enforcement here.** It is one of the tree's two samplers and the only one whose decisions run over host-side logits and decoded texts — the grain J-113's layer decides in. The CUDA device sampler selects over device logits in partitions; a token-text restriction there needs either a host logits copy per step or a device mask upload per step, inside `forward()` — the CUDA generation loop. This road's standing precedent (J-112 §0.4, the T22 disposition) is that generation-loop wiring "cannot be proven by compilation alone" and is not smuggled in as a compile-only claim. The CUDA binding is therefore a named deferred leg (§0.7) with its recipe, not a silent gap and not a faked wiring: both chat bodies and the serve state the binding's status on their own faces where the restriction is offered.
- **Sampled-path threshold over the admitted set.** The unrestricted sampler truncates at max−15 over the whole vocabulary; under restriction the distribution is the renormalised admitted distribution, whose own max is the honest reference — truncating against a disallowed global max could empty the admitted set (every admitted logit more than 15 below a forbidden maximum) and force exactly the fallback this build forbids.
- **Suppression in the restricted sampler is by exclusion.** The unrestricted sampled path masks suppressed candidates to −1e9 yet can still draw one if all are suppressed; a restricted sampler that must never emit a refused token excludes suppressed IDs when building its candidate set, so the "never emitted" claim covers suppression too. The greedy paths agree (both scan-skip suppressed IDs).
- **−1 is the refusal value.** It is outside every vocabulary, it is the pure selection form's own no-candidate value (`first_allowed`), and callers must treat it as "generation stops here" — the loop test files exactly that behaviour.
- **The server field is an extension, named plainly.** `vocab_restriction` (a word-list string in J-113's spec grammar: whitespace/comma/semicolon separated) — the smallest surface that carries the user's list with the parser's standing bounds; no new JSON machinery.

## 3. Measured cost (MEASURED-INDICATIVE; exact counts PROVEN)

Filed in full in `j114_cost_output.txt` (driver `j114_cost.mojo`; §0.3's design executed as pre-registered, two runs, both kept). Deterministic synthetic candidate sets over the list "the cat sat on the mat" (admitted pieces 5/8 of every set — the driver's printed admitted counts 160 / 640 / 2560 per scan confirm the rotation):

| Candidates | Baseline greedy scan (median, 2 runs) | Restricted validity scan (median, 2 runs) | Restricted per candidate |
|---|---|---|---|
| 256 | 1286–1311 ns | 26,784–27,067 ns | ~105 ns |
| 1024 | 5099–5225 ns | 295,392–349,967 ns | ~290–340 ns |
| 4096 | 15,853–17,756 ns | 1,798,563–1,983,042 ns | ~440–485 ns |

Each repetition builds an identical fresh candidate list inside both timings, so the delta is the validity scan's price. **The spread is part of the filing:** at the larger sizes the medians sit well above the same runs' first measured rounds (111,995–114,480 ns at 1024; 495,253–1,637,883 ns at 4096) on a VM running at loadavg ~6–8 on 4 vCPU — the per-candidate growth across sizes is a contention/allocation effect (J-113's walk allocates per byte; that is where the per-candidate price lives), not the algorithm's shape: the scan is one `is_token_valid` call per candidate with no early exit, and its exact counts (full scan; admitted + masked == scanned at 6 and 1024 candidates) are PROVEN in the unit suite. The greedy sampler path pays the scan once per step, the sampled path twice (max scan + collect) — stated in the sampler's own header. A quiet-machine re-measurement rides the J-118 gate's live-leg filing (§5). No tok/s, no generation wall, and no live-cost claim is made anywhere in this slice.

## 8. Answered-locally records (clean-room)

- **Q: Which sampler carries the enforcement — the CPU sampler or the CUDA device sampler?** Answered locally (§0.6): the CPU sampler (`core/sampler.mojo`), the tree's host-logits sampler and the only one whose decisions run over decoded token texts — J-113's grain. The device sampler's binding needs generation-loop surgery this road does not prove by compilation alone (the J-112 T22 precedent); it is a named deferred leg (§5 leg 2), and both doors state the gap on their faces rather than implying a binding that does not exist.
- **Q: How does the sampled path threshold under restriction?** Answered locally (§0.6): at the admitted set's own max−15 (the renormalised distribution's reference). Thresholding against a disallowed global maximum could empty the admitted set and force exactly the disallowed fallback this build forbids.
- **Q: Is suppression a mask or an exclusion in the restricted sampler?** Answered locally (§0.6): exclusion in both paths, so the never-emitted claim covers suppressed IDs too (the unrestricted sampled path's mask can still draw a suppressed token when all are suppressed; a restricted sampler may not).
- **Q: What does "no candidate admitted" return?** Answered locally (§0.6): −1 — outside every vocabulary, the pure selection form's own no-candidate value; callers treat it as "generation stops here", and the loop test files the stop with the restrictor state untouched.
- **Q: Does the server field join the OpenAI audit's tables?** Answered locally (§0.5): no. `vocab_restriction` is an Aesir extension field, not a field of the audited public shape; the audit's canonical lists describe that shape, and filing an extension there would misstate it. The audit module is unchanged and its suite's tallies are unmoved.
- **Q: Why does the serve refuse a valid list instead of ignoring the field or generating anyway?** Answered locally (§0.5): ignoring a stated restriction, or generating unrestricted under it, would silently break the user's stated constraint — the one dishonest option. Validation + a stated refusal (the J-109 embed precedent) is the surface's honest behaviour until the CUDA binding lands (§5 leg 2).
- **Q: Two exact constraints at once — Boolean JSON format + a word list?** Answered locally (§0.5): refused at parse. The Boolean grammar is its own exact constraint with its own session machinery; composing two exact constraints needs an ordering decision and a proof this slice does not owe, so the combination is refused by name rather than silently ordered.
