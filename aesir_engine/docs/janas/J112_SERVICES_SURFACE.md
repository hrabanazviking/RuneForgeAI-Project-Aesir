## 0. Protocol (committed first, before any code was built)

This section was committed before the services layer, the MCP extension, the chat wiring, or any test existed. It states the inventory method, what the inspection found, the per-service expose-or-refuse decisions with reasons, the two doors' shapes, the T22 disposition, the verdict rules, and what is deferred and why; everything after §0 is filed under these rules and no others.

### 0.1 Inventory method

The inventory is taken **from the tree at the base tip**, never from the roadmap's examples alone: for each candidate service, the slice names the exact module/function that would execute it, whether that path needs a loaded model, and which doors already reach it. A service is exposed on a door only where that door can execute it honestly today; where it cannot, the door answers with the stated reason (a tool error on MCP, a plain refusal line in chat) — never with a fabricated result. Anything with no executing path at all is inventoried as ABSENT with its reason.

### 0.3 The two doors, as built shapes

**The pure layer — `aesir_engine/core/services_surface.mojo`** (new), in the road's established grain (pure logic, unit-tested at the lightest target; hosts execute the decisions):

- The registry: `svc_service_names()` / `svc_service(index)` — each entry carries the service name, its MCP tool (or none), its chat form, its availability class (`AVAILABLE` / `MODEL_BOUND` / `REFUSED` / `CLI_ONLY`), and its one-line reason. `svc_inventory_text()` renders the table both doors serve.
- Census: `svc_census_text(facts)` over layer-local `ServiceModelFact` records (the host converts from `KnownModelEntry`, so the layer never imports the CLI layer — the J-109 dependency direction).
- Grade: `svc_grade_step_text(rank, gap_milli, comparator_valid)` and the chat/MCP argument handling around `grade_prefill_cell`'s rule, delegating every number to `core/prefill_grade.mojo` — the service grades by the road's own rule, never a re-implementation (an import, pinned by the tests against the layer's own constants).
- Bench report form: `svc_bench_text(device_describe, model_table_text)` — composition of the host-supplied live inventory description and the filed evidence table, with the sweep's CLI-only reason on its face.
- Chat answers: `services_chat_response(command, facts, device_describe, model_table_text)` — the `saved_config_command_response` pattern (J-104): one pure function the chat host calls; it answers `/services` (inventory), `/services census`, `/services grade …`, `/services bench`, `/services mcp` (the §0.4 disposition, stated in-chat), and refuses any other `/services …` form by name. Tokenize is **not** answered here — it needs the session (below).
- Tokenize formatting: `svc_parse_tokenize(command)` (the text after `/services tokenize `, usage-refused when absent — the chat's standing pattern) and `svc_format_tokenize(text, ids)` (count + the id list, with the tokenizer's identity stated by the host's branch).

**The chat door — `cli/cuda_chat.mojo`, both `chat_control` bodies** (the J-104 wiring pattern, branches placed before `/save-config` so no prefix branch can swallow them):

- `/services tokenize <text>` → `session.tokenizer.encode(text)` through that body's own session type (Llama 3 tokenizer on the Llama body, Gemma 4 tokenizer on the Gemma body) → `svc_format_tokenize`. This is a genuine live service: a chat session exists only with a model loaded, so the tokenizer is really bound.
- `/services` and every other `/services …` form → `services_chat_response(command, facts, device, table)`, where the host converts `known_model_catalogue()` to facts once per call, observes the device inventory (`observe_device_inventory().describe()`), and renders the filed model table (`model_table(filed_model_rows())`).
- The manners candidate set grows by exactly one name: `core/chat_manners.chat_command_names()` gains `/services`, and `cli/chat_history.chat_command_help` names it — a near-miss of it must suggest it like every other slash name (J-105's rule). `test_chat_manners` is updated only for this count.

**The MCP door — `core/mcp_tools.mojo` extended, `cli/mcp_serve.mojo` host**:

- Four new tools join `tools/list` (seven total): `aesir_tokenize` (MODEL_BOUND dispatch, mirroring generate: missing/empty `text` → `-32602`; bound-model mismatch → tool error; unbound → the no-tokenizer tool error naming the reason; bound → `needs_tokenize` verdict carrying the text, completed by the host through `mcp_tokenize_completion` / `mcp_tokenize_failure`, both layer-built and layer-tested), `aesir_grade` (pure: `rank` + `gap_milli` required integers ≥ 0, `comparator_valid` optional boolean defaulting to **false** — a caller who does not state the comparator check gets the COMPARATOR_ARTIFACT verdict, never a free FAITHFUL; inconsistent records → tool error carrying the grading layer's own refusal), `aesir_census` (pure from facts: the census text + the services inventory), and `aesir_bench` (following the bench decision of §0.2: the layer sets `needs_bench` and the **host executes it in this build** — observing the device inventory and rendering the filed table are host acts that need no model — completing through `mcp_bench_completion`). The J-109 host therefore answers `aesir_bench` with a real report, not a deferral.
- `test_mcp_tools` is updated only where J-109's filed counts change by this slice's design (the tool count and the known-tools text), per the J-111 audit-flip precedent; every J-109 group otherwise stands.

### 0.4 T22 disposition (the chat-integrated MCP client door)

**Not built in this slice; dispositioned here so it does not vanish.** The in-chat client door means: a chat session spawning an external MCP server, offering its tools to the model mid-generation, and running a chosen tool only after the user's confirmation (the chat manners' confirm-before-run shape). It does not fit honestly inside this slice's bounds, for reasons of evidence, not effort:

1. Its behaviour lives in the CUDA sessions' generation loop (a tool call is emitted *instead of* text, confirmed, executed, and its result re-entered as context). On this VM that loop cannot be executed at all (no CUDA device; MemAvailable far below the 5,500 MB inference gate), and purplelongship is yielded to the 204 road — so the slice could prove the wiring only by compilation, and a conversational behaviour claimed on compile evidence alone is exactly the fake this road's honesty classes exist to prevent.
2. No named external MCP server exists in the tree or in the road's consumer set to consume against (J-110's real consumer is Aesir-as-server, the opposite direction); a client built against a self-written toy server proves framing, which J-109 §0.5's standalone client already proved against the real host.

**Named future home:** the J-118 Part VII gate re-cites this disposition; the door itself belongs to a dedicated slice once (a) a named external MCP server is a real consumer requirement and (b) a guarded purplelongship window can prove the loop live — ids-first, confirm-before-run, with the standalone client of J-109 §0.5 as its framing reference and this slice's registry as its discovery surface. In this slice, both doors state the disposition where a user would look for it (chat `/services mcp`; the MCP census's service table).

- **Q: Grade grades caller-supplied records — what stops a caller from earning a free FAITHFUL?** Answered locally (§0.3): the comparator statement is the caller's own explicit input and defaults to **false** on the MCP door (and to unstated=invalid in the chat form's `[valid]` argument), so an unstated or failed comparator check grades COMPARATOR_ARTIFACT by the grading layer's own rule; inconsistent records are refused as broken transcriptions, exactly as the layer refuses them.
- **Q: Bench on a conversational/stdio door — the sweep, or the report?** Answered locally (§0.2): the report. A sweep is a minutes-long measurement run that would block a chat session or an MCP host for its whole duration, and `aesir bench` already executes it; the report (live device inventory + filed per-model evidence) is the bench artefact a host consumer can actually use. Both doors state the sweep's CLI-only reason on the answer's face.
