## 0. Protocol (committed first, before any code was built)

This section was committed before the dataset, the `get` surface, or any test existed. It states the dataset's in-repo data form, the pin-provenance rule, the `get` surface, the refusal-on-mismatch rule, and the verdict rule for the slice; everything after §0 is filed under these rules and no others.

### 0.1 The boundary J-102 set, inherited verbatim

J-102's doc (`docs/janas/J102_CHAT_PICKER.md` §0.2) binds this slice: **J-103 owns the curated in-repo catalogue dataset** — the actual entries, kept in the repo as data with their sources and sha256 pins — **and the `get` behaviour around it** (including refusal-on-mismatch as a standalone command surface). The data lands **behind `known_model_catalogue() -> List[KnownModelEntry]`'s existing shape** in `aesir_engine/cli/model_selector.mojo` (entry fields: `name`, `tag`, `repository`, `filename` `.gguf`, `revision` 40-hex, `sha256` 64-hex bare, `size_bytes` ≥ 24, `quantization`). This slice does **not** redesign the picker, the entry shape, or J-102's RUN/FETCH/REFUSED decision rule (`first_run_decision`); if the shape proves wrong for real data, that is filed as a defect against J-102 in §7 instead of silently forking it. The download/verify **engine** remains `pull`'s — `download_hf_model` (pinned, resumable, publishes only after size + GGUF header + SHA-256 checks) and `DurableModelStore.ingest_model` (re-measures the source bytes and refuses registration unless the measured digest and size equal the expected pin) — reused verbatim through J-102's `fetch_known_model`, never re-implemented.

### 0.2 The dataset's in-repo data form — a dedicated data module

The tree has **no runtime data-file loader for catalogue data**: nothing in `cli/` reads a repo data file at runtime to build a list, and a path-relative file read would make the catalogue depend on the caller's working directory — a failure mode no other CLI surface in this tree accepts. The tree's own pattern for curated in-code data is a dedicated module holding a plain data table (the shape the bench/placement tables already take). Therefore:

- The dataset lives in a new dedicated module, **`aesir_engine/cli/known_models.mojo`**, whose one job is data: a `known_models_dataset() -> List[KnownModelEntry]` function that constructs exactly the curated entries, each entry carrying its provenance in an adjacent comment (source record + what it pins — §0.3). The module contains no logic beyond constructing the list.
- **`known_model_catalogue()` delegates to the dataset**: `model_selector.mojo`'s provider returns `known_models_dataset()` and nothing else changes about its contract. The picker, the merge, and the decision rule consume the real entries through the unchanged J-102 shape.
- **Catalogue data is data, models are never committed:** the dataset is five small records of text (names, pins, sizes). No model bytes, no `.gguf`, and no downloaded artefact enter the repo in this slice or any other.

### 0.3 The pin-provenance rule — every pin from a real, citable source

Every entry's `revision`, `sha256`, and `size_bytes` must come from a **real, citable source**, or the entry is **not included** — a pin, a revision, or a size is never invented:

- **Primary source — the road's own filed records:** entries are drawn only from files the road already sha-pinned and measured first-hand: J-015's witnesses (`J015_MOE_ANATOMY.md` §1: OLMoE-1B-7B Q4_K_M and Granite-3.1-3B-A800M Q4_K_M, each downloaded, hashed, and matched against the publisher's HF LFS oid; §7: the Qwen1.5-MoE Q2_K witness and the bartowski OLMoE Q2_K file, same discipline) and the J-022 pin re-verified in J-032 §3 (Qwen3-Next-80B-A3B Q4_K_M, size + full sha256 re-read and matched character-for-character).
- **Revision source — the HF repo's own metadata, read this slice:** the filed records pin sha256 + size but do not state a commit revision, and `KnownModelEntry` requires one. Each entry's `revision` is therefore the repo's HEAD commit as reported by the Hugging Face API (`/api/models/<repo>` `sha`) **at the moment of this slice**, cross-checked in the same pass against the repo tree at that revision (`/api/models/<repo>/tree/main`): the file's LFS `oid` must equal the filed sha256 pin and its LFS size must equal the filed size, or the entry is dropped. The verification date and both sources are recorded per entry in §2.
- **Small and fully verified beats long with gaps:** the dataset is the handful of entries that clear both bars. A candidate whose filed pin or live LFS cross-check fails, or whose revision cannot be verified, is excluded and the exclusion is recorded in §2 — never repaired by guessing.

### 0.4 The `get` surface — a standalone command over the catalogue

`get` is the standalone form of the picker's fetch leg: name a catalogue entry, and it is fetched and checksum-verified before it is usable — the same engine, the same decision rule, no picker in between.

- **Grammar:** `aesir get <name:tag> [--config <path>]`, dispatched in `cli/commands.mojo`'s `dispatch_command` beside `pull` (the tree's CLI pattern: one `dispatch_<name>` per command, parsed without I/O first). The reference is normalised by the existing `normalize_model_reference`; an unknown reference is refused with the catalogue's known references named in the error — `get` never falls back to treating its argument as a repository or a path.
- **Lookup + decision live in `cli/model_selector.mojo`**, beside the catalogue they consume: `find_known_model(reference)` (the catalogue entry for a reference, raising if absent), `get_decision(entry, installed)` (the standalone decision, built on J-102's `first_run_decision` — an already-installed entry resolves RUN with no fetch; a fetchable entry resolves FETCH), and `get_known_model(reference, model_store)` (lookup → decision → on FETCH, J-102's `fetch_known_model` into `model_store + "/" + filename` → the post-fetch decision; on RUN-after-fetch it returns the reference; on REFUSED it raises with the decision's reason).
- **`dispatch_get`** mirrors `dispatch_pull`'s store discipline: the model store root comes from `AesirConfig` (or the `--config` file), the durable store is constructed (validating existing state) before any transfer begins, and success prints the verified reference with its pin. No new store, no new download path, no new hashing.

### 0.5 The refusal-on-mismatch rule — pull's discipline, stated once for `get`

A `get` (or a picker fetch) **publishes and registers only after** the fetched bytes pass all three of `download_hf_model`'s checks — exact byte size, GGUF header, and SHA-256 equal to the catalogue pin — and `ingest_model`'s independent re-measurement agrees. Any mismatch refuses: `download_hf_model` raises before publishing, or the post-fetch `first_run_decision` resolves REFUSED naming the failed pin (digest or size), `get_known_model` raises with that reason, **no model is registered, and nothing is offered for run**. A catalogue reference that does not exist refuses before any network activity. Unverified is refused, not warned-through — J-102 §0.3's rule, inherited unchanged.

### 0.6 Verdict rule for this slice (pre-registered)

The slice **passes** iff all of the following hold, each filed:

(a) **Dataset:** `known_model_catalogue()` returns the curated entries (count stated on the suite's face); **every** entry passes `validate_known_model_entry`; references are unique; and each entry's pins match the provenance constants the suite carries from §0.3's sources (repository, filename, revision, sha256, size, quantization — asserted field-for-field, so a silent data edit fails the suite).
(b) **Picker over real data:** J-102's `test_chat_picker` still PASSes, with its catalogue-interface group updated — as this slice's own change, recorded in §7 — from the honest-zero assertion to asserting the real catalogue (non-empty, every entry valid, the known references present); all other groups unchanged in meaning.
(c) **`get` logic:** a new standalone suite `test_model_get` PASSes at the lightest target: dataset validation + provenance (a); lookup (known reference found with its pins; unknown reference refused); the get decision over the **real** entries (fetchable → FETCH; installed → RUN with no fetch); and the refusal leg over fixtures bound to a real entry's identity (digest mismatch → REFUSED with the digest reason; size mismatch → REFUSED with the size reason; attempted-with-no-bytes → REFUSED) — reusing J-102's `first_run_decision`, never a second rule.
(d) **Neighbours:** the suites in this slice's import graph rebuilt from this tree PASS at their filed counts — `test_chat_picker` (b), `test_model_browser`, `test_model_preferences`, plus the standing `test_machine_report` 6/6, `test_bench_configurations` 8/8, `test_placement_harness` 10/10, `test_thread_topology` 10/10. Any suite not rebuilt is named with its reason, never silently skipped.
(e) **Inspect:** `docs/janas/j103_inspect.py` re-derives every load-bearing claim in this doc from the tree + dataset and PASSes; every FAIL is disposed in the doc, never hidden. The inspect re-reads the dataset's pins from the Mojo data module mechanically and compares them against the provenance table in §2 of this doc.
(f) **The live download leg:** no multi-GB model is downloaded in this slice. A live `get` is attempted **only if** a genuinely tiny already-pinned GGUF is reachable **and** the VM memory gate (MemAvailable > 5,500 MB at the moment of the run) holds; no catalogue entry is tiny (the smallest is ~2.0 GB), so the expected disposition is **DEFERRED-WITH-REASON** with its exact recipe filed in §5, re-cited at the J-118 Part VII gate, and §9 stating plainly what is NOT PROVEN. purplelongship is not used in this slice (the 204 road's S-103 owns that box).

**Honesty classes.** The dataset's pins are **PROVEN as records** — each from a filed first-hand measurement (§0.3) cross-checked against the publisher's live LFS metadata at a named revision on a named date; that is a provenance claim about the data, not a claim that any download ran here. The validation, lookup, decision, and refusal logic are **PROVEN** by the unit suites and the inspect where they pass. The `get` dispatch's composition (which functions, in which order, with which arguments) is **PROVEN (inspection sense)** from the tree. A live download, a live registration from a `get`, and a live refusal of a real corrupted download are **NOT PROVEN** by this slice and are named in §9.
