## 0. Protocol (committed first, before the audit was run)

This section was committed and push-verified before the inspect script was written or run. It states the audit questions, the inventory method, the verdict rules pre-registered for each binding question, the build rule, and what is deferred and why. Everything after §0 is filed under these rules and no others.

### 0.1 The questions

1. **The inventory question.** What can a host program call today, surface by surface — the CLI, the HTTP server (OpenAI shape + the native service shape), the MCP stdio surface, the in-process Mojo-native path — and what can it *not* call: any C ABI / exported-symbol / shared-library surface, any in-process Python binding, any Node/TypeScript module, any FreeBASIC declaration?
2. **The C ABI question (concordance row 65).** Build a C ABI only if a named consumer waits *for a C ABI*. Name the consumer and the exact form it needs, or defer with the exact shape a future C ABI would take and what blocks it today.
3. **The Python/Mojo-native question.** What can a Mojo host already do in-process today, and what can a Python host do today (through which doors), each graded honestly — an in-process binding and a process door are different claims and are never conflated.
4. **The Node/TypeScript question (row 67).** Answered from the evidence, not assumed: does a native Node module need building, or are the language-agnostic doors (HTTP, MCP stdio) already its honest answer today?
5. **The FreeBASIC question (row 68).** The concordance already REFUSED this row; this slice files the audit trail — the tree evidence and the reasons — so the refusal is documented, not silent. A reversal would need the §0.3 rule's conditions, which are checked, not presumed.
6. **The Yggdrasil handoff question (for J-116).** Yggdrasil's adapter is the standing named consumer. Exactly which of this road's surfaces can it consume today, which can it not, and through which door — stated as a record J-116 can re-prove against, not as J-116's work done early.

### 0.3 Verdict rules (pre-registered)

- **Build rule (the road's own, from the roadmap text):** a binding is built in this slice only where the audit proves it missing **and** a named consumer waits for that binding in that form. Otherwise the slice files verdicts + exact recipes. A consumer waiting for a *door* (HTTP/MCP/CLI) is not a consumer waiting for a *binding*; the forms are graded separately.
- **C ABI rule:** BUILD only if a named consumer is shown, from its own record, to require calling Aesir in-process through C. If the standing consumer's own record shows it consuming a process door by design, the verdict is DEFER (not REFUSE — a C ABI is a legitimate future shape), with (a) the exact future shape (handle, error, and reply conventions in Aesir's own terms, informed by — never copied from — the documented Janas conventions), (b) what blocks it today, named from the tree, and (c) the reopen condition: a named consumer requiring the in-process C form.
- **Mojo-native rule:** graded PROVEN for exactly the facade entries and importable modules the inspect enumerates as answering; entries that raise on their faces are filed as named absences inside the surface, not hidden by the surface's existence. Stability is graded separately from existence: a facade with no versioned ABI promise is an in-tree Mojo API, and is called that, not a stable library ABI.
- **Python rule:** process doors (HTTP server, MCP stdio, CLI subprocess) and an in-process Python binding are graded as separate claims. The doors are PROVEN to the extent J-109/J-110/J-112's filed client proofs and this tree's surfaces support; an in-process binding is claimed only if binding machinery exists in the tree.
- **Node/TypeScript rule:** a native `.node` module is built only under the build rule. If no consumer waits for the native form and the language-agnostic doors are open to a Node host today (HTTP is protocol, MCP stdio is protocol — both inspect-verified as surfaces, with any Node-client interop graded NOT PROVEN unless a filed proof exists), the verdict is DEFER-native-form / doors-answer-today, with the recipe for the native form filed.
- **FreeBASIC rule:** the concordance REFUSED verdict stands unless a named consumer in Volmarr's stack is found in the tree evidence. The audit trail must state: the tree evidence (no `.bi`, no C ABI for it to declare even if it were wanted), the consumer evidence (none), and the dependency fact (a FreeBASIC binding is a declaration layer over a C ABI that itself is deferred under its own rule — it cannot be built before its substrate, and its substrate has no waiting consumer either).
- **Honesty classes:** PROVEN / SIMULATED / MEASURED-INDICATIVE / NOT PROVEN, per the road's law. This is an audit slice: its numbers are tree counts re-derived by the inspect, not performance figures; no tok/s, latency, or live-generation claim is made anywhere in it. Live legs (a running server, a live MCP session, a compiled facade call) are graded from the filed proofs of the slices that ran them (J-109/J-110/J-112 for MCP, J-106/J-107 for the server shape), each cited, never re-claimed as this slice's runs.

## 1. Headline — the verdicts

Aesir is embeddable today through **process doors and one in-process Mojo API** — and through no foreign-function binding of any kind. Every number below is re-derived from the tree by `j115_inspect.py` (filed output: **ALL PASS**; tally in §7).

- **C ABI (row 65): DEFERRED, not built** — under §0.3's pre-registered rule. The standing named consumer, Yggdrasil's adapter, consumes the native HTTP door *by its own design* (its record and source agree); no named consumer requires calling Aesir in-process through C. The exact future shape, today's blockers, and the reopen condition are filed in §3. The only C ABIs in the tree face *downward* — the engine calling devices and helpers (the 6-entry Hailo bridge ABI, the 2-entry image shim, the 2-entry thread shim) — none faces upward to a host.
- **Python (answered in two parts, never conflated):** an in-process Python binding **does not exist** (no Python file in the engine outside the filed client proofs, no Python-interop machinery in any engine module — inspect-verified). A Python *host* is nevertheless the best-proven external consumer class in the tree: it can call every process door, and does — Yggdrasil's adapter over HTTP, and this road's own filed stdlib clients over MCP stdio (J-109/J-110/J-112, sessions filed).
- **Mojo-native:** PROVEN as an in-tree Mojo API (§4) — a Mojo host imports the same modules the engine's own CLI, serve, chat, and MCP hosts are built from, because those hosts *are* Mojo hosts of the library modules. It is **not** a stable ABI: the tree carries no versioned library promise (the CLI reports itself "aesir development snapshot (unversioned)"; the workspace version is 0.1.0), and the facade's reserved entries state the surface is still growing.
- **Node/TypeScript (row 67): DEFER the native form; the doors are the answer today** (§5). No `.node` artefact, TypeScript source, or JavaScript exists in the engine tree; no consumer waits for the native form; a Node host can already call the HTTP and MCP stdio doors, which are protocols, not bindings. A native module would in any case stand on the deferred C ABI. Vendor Node-client interop is NOT PROVEN (no Node MCP/HTTP client proof is filed anywhere in the tree).
- **FreeBASIC (row 68): REFUSED — the concordance verdict stands**, with its audit trail filed in §5: no `.bi` file anywhere in the tree, no consumer in Volmarr's stack, and the binding is a declaration layer over a C ABI that is itself deferred for want of a consumer — it cannot precede its substrate.

**Nothing was built in this slice.** Under the pre-registered build rule that is the audit succeeding: every missing binding lacks a named consumer waiting for that form, and every form a named consumer does wait for already exists as a door. The one genuine defect-class finding — a cross-door friction between J-107's progress frames and the Yggdrasil adapter's stream rule — is recorded in §6 as J-116's immediate first item, with evidence from both trees; it is not fixed here because one side is another campaign's repo (read-only for this slice) and the re-proof that owns the reconciliation is J-116 itself.

## 3. The C ABI question (row 65) — DEFERRED, with the shape and the blockers

**Verdict: DEFER (do not build in this slice).** Under §0.3's rule, a C ABI is built only for a named consumer shown to require the in-process C form. The standing consumer's own record is explicit about its form: Yggdrasil Y-024 is "Aesir's NATIVE service API … mapped into the contract shapes over an INJECTED transport" — an HTTP consumer by design, whose source (§6) calls four native routes and nothing in-process. No other consumer named anywhere in this road's records requires a C ABI either. Building one now would be a binding in search of a consumer, against the roadmap's own sentence for this slice.

**The downward ABIs (why "no C ABI" needs its qualifier).** The tree does contain real C ABIs — all facing from the engine toward its devices and helpers, none toward a host: (1) `aesir_hailo10h_*` — 6 entries (`open`, `close`, `describe`, `generate`, `free_text`, `clear_context`) declared in `HAILO10H_INTERFACE.md`, implemented for Hailo machines by `hailo10h_bridge.cpp` against HailoRT and elsewhere by the fail-closed `hailo10h_stub.c` ("the canonical Aesir binary references the aesir_hailo10h_* C ABI") — the *binary consumes* this ABI; the stub is compiled into `libaesir_hailo10h.so` by `scripts/launch.py` so the launcher can link. Hailo itself stays parked; this is inventoried, not touched. (2) `libaesir_image` — 2 entries (`aesir_image_decode`, `aesir_image_free`) in `image_decode.c`, dlopen'd by `loader/image_codecs.mojo` for vision preprocessing. (3) `aesir_par_*` — 2 entries (`aesir_par_for`, `aesir_par_cpu_count`) in `thread_par.c`, the pthread shim for the CPU forward path. These prove the project *can* hold a C boundary where a device demands one; they are not a host library surface and no host can generate through them (the Hailo `generate` entry generates on the Hailo device session for the engine's own CLI, behind the parked gate).

**The future shape (filed so a reopening slice does not start from zero), in Aesir's own terms:** a `libaesir` shared library emitted from a thin Mojo binding module over the facade/session tier, exposing — opaque session handle created from a size-carrying configuration block (model reference, context, placement options in J-036's grammar, sampling defaults); int-style error codes with a last-error string owned by the library; `generate` returning whole UTF-8 reply pieces plus a streaming callback form; `model_info`, `tokenize`, and the J-112 services that are AVAILABLE-class as plain functions; explicit handle close, no library-owned threads visible to the host. (The handle/error/piece conventions rhyme with the documented Janas conventions because those are the shape any C consumer needs; the surface, names, and semantics above are Aesir's own surfaces re-exposed, not Janas's API copied — clean-room record, §8.)

**What blocks it today (named from the tree):** (a) no export mechanism or build target exists (§2.5) — the binding module, its marshalling layer (Mojo owned strings/lists/tensors cannot cross C as-is), and a shared-library build recipe for this codebase are all unbuilt and, for the toolchain path, unproven in-tree; (b) the ABI must first choose its engine tier — the CPU-line facade (whose 5 reserved entries still raise) or the CUDA session structs (the live generation tier) — and that choice is a design decision a consumer's requirements should drive; (c) no ABI-stability/versioning promise exists anywhere in the tree to version the surface against.

**Reopen condition (exact):** a named consumer whose own record requires calling Aesir in-process through C (a C/C++ host, or a language whose only bridge is a C ABI — which is also the FreeBASIC and native-Node prerequisite) — at which point this section's shape + blockers are the slice's starting protocol. J-117's embedding example is the natural first witness when that day comes; until then J-117's example rides the Mojo-native door (§4) and the doors.

## 4. The Python / Mojo-native question

**Mojo host — PROVEN (in-tree API, unversioned).** A Mojo host program today can: import any of the 214 library modules; construct `AesirEngine` over a GGUF model and call its 10 answering entries; drive the CUDA session structs directly, exactly as `cli/native_serve.mojo` and `cli/cuda_chat.mojo` do; and reuse the pure layers this road built (placement, drafts, KV, services, restriction — each with its filed test suite). The honest limits ride with the grade: the facade's 5 reserved entries raise (§2.4); the API is unversioned and in-tree (a host pins a commit, not an ABI); and a host that needs generation *served* rather than linked uses the doors, as the engine's own serve does.

**Python host — doors PROVEN, in-process binding ABSENT.** A Python host today can: call the HTTP server in any of its three shapes (Yggdrasil's adapter is the standing proof of the native shape, §6; the OpenAI shape is the generic one); speak MCP to `aesir mcp` with the standard library alone (filed clients at J-109/J-110/J-112 prove the framing end-to-end); and drive the CLI as a subprocess. It cannot `import` Aesir: there is no Python package, no binding machinery, and no MAX-Python exposure of the engine in the tree (§2.5). Building one would stand on either the deferred C ABI (via ctypes/cffi) or a MAX/Mojo Python-interop layer that does not exist in this codebase — and no named consumer waits for the in-process form: the one standing Python consumer chose HTTP by design. **Verdict: no Python binding built; the doors are the Python answer today, graded PROVEN as doors and ABSENT as a binding.** If a consumer ever needs in-process Python, the C ABI reopen (§3) is its prerequisite and this section is its record.

## 5. Node/TypeScript (row 67) and FreeBASIC (row 68)
