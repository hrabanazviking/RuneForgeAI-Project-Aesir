## 0. Protocol (committed first, before any code was built)

This section was committed before the MCP layer, the stdio host, the client, or any test existed. It states what the inspection found, the server shape as decision rules, the closures this slice takes, the leg it consciously does not take, and the verdict rule for the slice; everything after §0 is filed under these rules and no others.

### 0.1 What exists, and the exact delta (re-verified first-hand in this tree at the base tip)

- **MCP does not exist (T21/T22, re-verified).** A word scan for `mcp` over the engine tree finds the string only inside committed binaries (`aesir_main`, `main`, `test_engine`, `test_server_loop`) as an unrelated byte substring — in `.mojo` sources the only hits are gate-module filenames' substrings in import lists, not the protocol. There is no JSON-RPC server, no stdio tool server, no `mcp` CLI command (`cli/commands.mojo`'s `dispatch_command` has no `mcp` branch; J-099's inspect re-derived the same absence mechanically).
- **The transport shape is decided by the protocol, not invented.** MCP's canonical local transport is JSON-RPC 2.0 over stdio, one JSON object per line. An editor/agent client spawns the server process and speaks newline-delimited JSON-RPC on its stdin/stdout. Aesir therefore serves MCP as a stdio process — `aesir mcp` — and not as another HTTP route: the HTTP surface already exists (J-106–J-108) and is a different door for different clients. (Answered-locally, §8.)
- **The tree's flat JSON parser cannot read a JSON-RPC request.** `server/local_protocol.mojo`'s `FlatJSON.fields()` accepts only string/boolean/number field values by design; a JSON-RPC request carries `params` as a nested object, so the flat parser raises on exactly the field this protocol is made of. The MCP layer therefore carries its own bounded scanner (top-level field extraction with balanced-brace capture for nested values, string-aware), sized and refused in the tree's bounded style. Reusing `FlatJSON` unchanged would have been a fake fit; extending it was out of scope for its other callers. (Recorded as a design decision, §8.)
- **Model info has a real data path that loads no model.** J-103's catalogue is repo data behind `known_model_catalogue()`: name, tag, repository, filename, revision (40-hex), sha256 pin (64-hex), size in bytes, quantization — precisely a model-info tool's honest payload, answerable from the catalogue record alone, plus the standing truth that no model is *loaded* in an MCP host session unless a live engine is bound (§0.3). The tool reports catalogue facts as catalogue facts and never presents them as a loaded model's self-report.
- **Generate has a real surface — and it needs a loaded model.** The facade's `generate_tokens_config` / `generate` are the engine's real generation path (the same coordinator the CLI and serve build on). Constructing `AesirEngine` mmaps and loads a whole model file. On this VM that cannot run: MemAvailable ~3.2–3.9 GB throughout the slice against the road's 5,500 MB inference gate, and no CUDA device exists on the VM; purplelongship is yielded to the 204 road (its S-104 live at dispatch). The generate tool is therefore built complete at the protocol + dispatch layer — argument validation, the dispatch verdict, the success/error response shapes — and its live execution leg is DEFERRED-WITH-REASON with an exact recipe (§5), re-cited at the **J-118 Part VII gate**. In the host this slice ships, no engine is bound, and a generate call is answered with a tool error that says exactly that, in plain words — never with invented text.
- **Embed has no honest surface, so the embed tool refuses.** Per T13 (re-verified in this tree): the live serve has no `/v1/embeddings` route and states `embeddings:false` in `/health`; `format_embeddings` is an error-only stub; J-106's audit records the route REFUSED-501 with the reason "no embedding data path exists in this service". The facade's `extract_query_embedding` is mean-pooled token embeddings from a generation model — not a graded embedding model, never graded as one anywhere on this road. Returning those numbers under the name "embeddings" would be a fake vector with a real-looking shape. The roadmap's own words govern: **embed-where-honest** — and here honesty is a plain refusal, delivered as a proper MCP tool error (`isError: true`) that names the reason and the road that could change it (a graded embedding model kind, J-112/J-115 territory), not a protocol error and never a fabricated vector.
- **No MCP SDK is installed.** `import mcp` fails on this VM's Python 3.12; no Node MCP package is present either. The proving client (§0.5) is therefore a hand-rolled, standard-library-only JSON-RPC-over-stdio client that speaks actual MCP framing (`initialize`, `notifications/initialized`, `tools/list`, `tools/call`, `ping`) against the compiled server process — a real client by the protocol's definition (it is transport- and framing-faithful; nothing calls the server's internals). No package is installed for this: the install's network/cost weight buys nothing the stdlib client cannot prove, and the choice is recorded here in advance.

### 0.2 The layer (the pure layer)

A new pure module, **`aesir_engine/core/mcp_tools.mojo`**, following the road's established shape (pure logic, unit-tested at the lightest target; hosts execute the decisions; no socket, process, or engine lives here):

- **Protocol facts:** `mcp_protocol_version()` → `"2024-11-05"` (the widely-deployed MCP revision; the server answers `initialize` with its own version regardless of the client's ask, per spec); `mcp_server_name()` → `"aesir"`; `mcp_server_version()` → `"1.0.0"` (both answered-locally, §8).
- **A bounded JSON scanner** sized for JSON-RPC lines (64 KiB line bound, field-name bound, string-escape handling): `mcp_scan_field(line, key)` returning found/kind/raw-or-decoded value for top-level fields, with balanced capture for object/array values; `mcp_json_escape(text)` for building payloads. Malformed input is a verdict, never a crash.
- **Method classification:** `mcp_classify_method(method)` → initialize / ping / tools-list / tools-call / notification / unknown; a request with no `id` and a `notifications/` method is a notification (answered with silence, per spec).
- **The request handler:** `mcp_handle_line(line, state, facts, engine_bound)` → a reply struct `{respond: Bool, payload: String, needs_generate: Bool, gen_prompt: String, gen_max_tokens: Int}`. `state` is the session state (initialized flag) the host carries between lines; `facts` is the catalogue as layer-local `McpModelFact` records the host converts from `KnownModelEntry` (so the layer never imports the CLI layer — the tree's dependency direction is kept); `engine_bound` states whether the host has a live engine session bound (§0.3). Verdict rules:
  - Unparseable line → JSON-RPC error `-32700` (parse error), `id: null`.
  - No/empty `method` → `-32600` (invalid request). Unknown method (with an id) → `-32601` (method not found). A request (other than `initialize`/`ping`) arriving before `initialize` → `-32002` (server not initialized — the MCP spec's own code for this case).
  - `initialize` → result `{protocolVersion, capabilities: {tools: {}}, serverInfo: {name, version}}`; sets the session's initialized flag when the host applies the reply.
  - `ping` → result `{}`. `tools/list` → the three tool schemas of §0.4.
  - `tools/call` for an unknown tool name, or with a missing/ill-typed `name`/`arguments`, → `-32602` (invalid params) with the reason. Tool-level failures (unknown model, no engine bound, the embed refusal) are **not** protocol errors: they return a normal result whose content is one text block with `isError: true` — the MCP shape for a tool that ran and failed honestly.
  - `tools/call aesir_generate` with a missing/empty `prompt` → `-32602` naming the field. With a prompt and `engine_bound == false` → the no-engine tool error of §0.1. With a prompt and `engine_bound == true` → `needs_generate` is set and **no payload is final**: the host executes the engine and completes the call through `mcp_generate_completion(id, text)` / `mcp_generate_failure(id, reason)` — the layer builds both envelopes, so the success shape is layer-tested even though the live leg is deferred.
  - `tools/call aesir_embed` → the §0.1 refusal, always, in this slice (there is no `engine_bound` state that makes it honest today).
  - `tools/call aesir_model_info` → §0.4's payload from `facts`: a named model answers its catalogue record; an absent `model` argument answers the whole catalogue as a name/tag listing; an unknown name answers the tool error naming the known references.
- **Response builders:** `mcp_result_response(id_raw, result_json)` and `mcp_error_response(id_raw, code, message)` — the `id` is echoed as the raw JSON value the client sent (number or string), never re-typed.

### 0.3 The host (the stdio server)

A new host module, **`aesir_engine/cli/mcp_serve.mojo`**, in the tree's host shape:

- `run_mcp_stdio()` — the loop: read one line from stdin (a host-local POSIX `getchar` reader, byte-identical in shape to `cli/repl.mojo`'s proven `read_line`; the duplication is deliberate — `cli/repl.mojo` imports the whole engine facade for an 8-line reader, and this host must compile without dragging the facade into its import graph, §0.1's compile bound), convert the catalogue (`known_models_dataset()`) to layer facts once at start, carry the session state, hand each line to `mcp_handle_line` with `engine_bound = false`, print each reply payload as one line on stdout, exit cleanly at EOF. Nothing else is ever printed to stdout (the protocol channel is the product; any diagnostic would corrupt framing); the host writes nothing to disk and never modifies a model file (J-105's manners, applied).
- **The CLI door:** `aesir mcp` — a `dispatch_mcp` in `cli/commands.mojo` beside `dispatch_get`, parsed without I/O first in the tree's pattern: no arguments are accepted in this slice; any argument is refused by name (`mcp takes no arguments in this build; the engine-binding options arrive with the live leg, J-109 doc §5`) rather than silently ignored. `print_general_help` gains the one `mcp` line.
- **The engine binding is a named seam, not a stub pretending to be one.** Binding means: the host's entry constructs an `AesirEngine` over a locally-present catalogue model's file and passes `engine_bound = true`, answering `needs_generate` through the facade. That construction is exactly the deferred live leg (§5): it needs a machine over the memory gate with the model file present. The seam is the layer's `engine_bound` flag + completion builders, both unit-proven; no dead facade code is compiled into this slice's host.

### 0.4 The three tools (exact surface)

| Tool | Arguments | Honest behaviour in this slice |
|---|---|---|
| `aesir_generate` | `prompt` (string, required, non-empty), `model` (string, optional — names the catalogue model the caller believes is bound; a mismatch with the bound session is a tool error in the bound build), `max_tokens` (integer, optional, 1..4096, default 256) | Validated by the layer; in this host build (no engine bound) a tool error states plainly that no live model session is bound and names the deferred leg. In a bound build the host runs the facade and the layer's completion builder returns the generated text as one text content block. |
| `aesir_model_info` | `model` (string, optional — a catalogue `name` or `name:tag`) | From the real J-103 catalogue records: name, tag, repository, filename, revision, sha256 pin, size bytes, quantization; absent argument → the catalogue listing; unknown name → tool error naming the known references. The payload states it is the catalogue record and whether a live session is bound (it is not, in this build). |
| `aesir_embed` | `input` (string, required by the schema) | **Always refuses in this slice** with the §0.1 reason as a tool error (`isError: true`): no embedding data path exists in Aesir today. No vector is ever returned. |

Tool schemas in `tools/list` are the MCP shape (`name`, `description`, `inputSchema` as a JSON Schema object). The embed tool's description states its refusal up front, so a client learns the truth from discovery, not only from calling.
