## 2. The problem as the authors frame it

FlashAttention-2 (see `papers/flashattention-2.md`) fixed the work-partitioning problems of the original on Ampere, but run on the newer **Hopper** generation it reaches only **35% utilisation on H100** — against 80–90% for optimised GEMM kernels on the same chip. The paper's diagnosis is that FA2's *algorithm* still assumes a simplified, synchronous execution model:

- Hopper's tensor cores and its data-movement engine (the Tensor Memory Accelerator, TMA) are **asynchronous** hardware units, separate from the CUDA cores that run scalar logic and floating-point work such as softmax's exponentials. A kernel written as a synchronous sequence — load, matmul, softmax, matmul — never overlaps these units, so each waits on the others in turn.
- Hopper also doubles matmul throughput again at **FP8** precision, but FA2 has no low-precision path, and naive FP8 attention is numerically dangerous: large models have outlier activations, and FP8's e4m3 format (4 exponent bits, 3 mantissa bits) quantises them badly under a single per-tensor scale.

So the problem is restated for the third time in the lineage, each time one level deeper: FA1 — attention moves too many bytes to HBM; FA2 — attention's work is partitioned badly for the SMs; FA3 — **attention's schedule ignores that modern GPUs are asynchronous, multi-unit machines, and ignores the low-precision units entirely.** The goal is a redesign of the same exact-attention computation around asynchrony and FP8, specific to Hopper.

## 3. Core mechanism in our own words

FlashAttention-3 keeps FA2's tiling, online softmax, loop order and IO properties. Everything new is about *when* operations happen and *in what precision*:

**(1) Producer–consumer warp-specialisation.** The warps inside a thread block are split into fixed roles. **Producer** warps do nothing but issue TMA loads, streaming Q, K, V tiles from HBM into a circular multi-stage shared-memory buffer. **Consumer** warpgroups do nothing but compute: WGMMA (the Hopper warpgroup-wide asynchronous matmul instruction) on tiles the producers have staged, plus the softmax work. Because TMA and WGMMA are asynchronous, loads for future tiles proceed while current tiles are being multiplied; register budgets are rebalanced to match the roles (Hopper's dynamic register reallocation gives consumer warps more registers, producers fewer). A **pingpong schedule** coordinates two consumer warpgroups so that while one is in its softmax phase, the other is in its GEMM phase — the paper's worked example lifts FP16 forward throughput at head dimension 128, sequence length 8192 from ~570 to ~620–640 TFLOPs/s on scheduling alone.

**(2) Interleaving block-wise matmul and softmax inside a warpgroup.** Even within one consumer, the naive order serialises: softmax of block *j* needs GEMM-1's output, and GEMM-2 needs softmax's result. FA3 breaks the chain across iterations with a two-stage pipeline: the QKᵀ WGMMA for block *j+1* and the PV WGMMA for block *j* are issued without waiting, and block *j+1*'s softmax executes while those asynchronous matmuls are still in flight. The dependency is honoured per block, but the *units* never idle: exponentials (which the paper quantifies starkly — H100 SXM5 offers 989 TFLOPs/s of FP16 matmul but only ~3.9 TFLOPs/s of special functions such as exp, so softmax's exponentials can consume up to ~50% of the cycles next to matmul at head dimension 128, and relatively more at FP8) are hidden underneath tensor-core work instead of alternating with it.

**(3) FP8 with block quantisation and incoherent processing.** To use Hopper's FP8 tensor cores (2× the FP16 throughput per SM), the kernel must satisfy FP8 WGMMA's stricter layout rules — operands must be k-major, and the FP32 accumulator layout of the first GEMM does not match the operand layout the second GEMM expects. FA3 solves this inside the kernel: V tiles are transposed on chip using load/store-matrix instructions (with a matching row permutation folded into the transpose so byte-permute instructions can re-lay the first GEMM's accumulator into a valid second-GEMM operand, avoiding cross-thread shuffles). Accuracy is defended by two techniques:

- **Block quantisation:** instead of one scale per tensor, each Q/K/V block (the same blocks the tiling already uses) gets its own scale, so a block containing an outlier no longer poisons the precision of every other block. The per-block rescaling folds into the attention computation at no extra cost, and the quantisation itself can be fused into the preceding operation (e.g. rotary embedding).
- **Incoherent processing:** before quantising, Q and K are both multiplied by the same random orthogonal matrix — in practice a sign-flip diagonal times a Hadamard matrix, multipliable in O(d log d) and fusable with rotary embedding. Because the matrix is orthogonal, (QM)(KM)ᵀ = QKᵀ exactly: the attention scores are unchanged, but each entry of QM and KM is a mixture of many original entries, so outlier magnitude is spread across coordinates instead of concentrated where FP8 can least represent it.

The FP16 path validates as numerically identical in error to FA2 (both keep softmax intermediates in FP32, giving 1.7× lower RMSE than a standard implementation in the paper's test); the FP8 path is where the accuracy techniques earn their keep (§4).

## 4. Reported results — as reported, with hardware context

All figures are the paper's own, measured on an **H100 80GB SXM5** GPU. Benchmark shape unless stated: sequence lengths 512–16K, batch sized so total tokens = 16K, hidden dimension 2048, head dimensions 64 / 128 / 256.

- **FP16/BF16 forward:** **1.5–2.0× faster than FlashAttention-2**, reaching up to **740 TFLOPs/s — 75% of the H100's theoretical peak** (989 TFLOPs/s). **Backward:** 1.5–1.75× faster than FA2. Against a standard attention implementation, up to 3–16× faster across the sweep; for sequence lengths ≥ 1K it also beats NVIDIA's H100-optimised cuDNN attention in the paper's comparison, and runs ~1.5× faster than the Triton FA2 implementation that uses Hopper instructions.
- **FP8 forward:** close to **1.2 PFLOPs/s**. The paper is candid about the shape-dependence: at head dimension 64 the FP8 kernel leads; at head dimensions 128 and 256 it is at par with the FP8 cuDNN kernels without causal masking and behind with causal masking — partly, the authors note, because the FP8 kernel lacks the persistent-kernel / load-balancing design the FP16 kernel has.
- **Ablation (fixed shape: batch 4, sequence 8448, 16 heads, head dimension 128, non-causal FP16):** full FA3 — 661 TFLOPs/s (3.538 ms); removing GEMM–softmax pipelining — 582 TFLOPs/s; removing warp-specialisation — 570 TFLOPs/s. Both asynchrony techniques are individually worth roughly 80–90 TFLOPs/s at this shape; neither is decorative.
- **FP8 numerical error (synthetic outlier distribution: Gaussian noise plus a 0.1%-probability, 10σ outlier term; RMSE against an FP64 reference):** baseline FP8 attention with per-tensor scaling — 2.4e-2; **FA3 FP8 with block quantisation + incoherent processing — 9.1e-3, i.e. 2.6× lower error**. The ablation is instructive: removing block quantisation barely hurts (9.3e-3), removing incoherent processing returns the error to the baseline (2.4e-2) — on this distribution, the incoherent rotation does nearly all of the accuracy work. FP16 RMSE for reference: baseline 3.2e-4; FA2 and FA3 both 1.9e-4.

**Hardware-generation caveat — this paper's gains are Hopper-only, stated plainly.** Every mechanism in §3 names a Hopper feature that does not exist on Turing (or on Ampere): TMA, asynchronous warpgroup WGMMA, dynamic register reallocation between warpgroups, thread-block clusters, and FP8 tensor cores. The corpus's target card — RTX 2060 Max-Q, Turing, compute capability 7.5 — has **none** of them. Consequences, stated as implications of the paper rather than as measurements:

- **No FA3 kernel runs on Turing.** This is not a performance caveat but an existence one; serving stacks encode it directly (SGLang auto-selects FA3 only on Hopper and falls back to FlashInfer on Ampere/Ada — corpus: `runners/sglang.md`; mistral.rs likewise gates its FA3 build to Hopper SM 9.0 — corpus: `runners/mistral-rs.md`).
- **What of FA1/FA2 survives on Turing is answered in those dossiers:** the tiling algorithm and FA2's partitioning in full (FlashInfer ships FA2-algorithm kernels for sm75), because they need only SRAM, warps and FP16 tensor cores. FA3 adds nothing to a Turing deployment except ideas (§6).
- **The transferable ideas are precision ideas, not schedule ideas.** Block-wise scaling and outlier-spreading rotations are precision-management techniques that do not depend on FP8 hardware — they apply wherever a narrow format meets outlier-heavy tensors, including INT8/FP8 KV-cache quantisation on lesser hardware (compare the corpus's KIVI/KVQuant dossiers, `papers/kivi.md`, `papers/kvquant.md`, where per-channel structure and outlier isolation do the analogous work for the cache). The warp-specialised producer/consumer pattern transfers only in weakened form: Turing can double-buffer shared memory with ordinary loads, but without asynchronous copy engines the producers spend the same cores the consumers need.

## 5. What it changed in practice

- **FA3 became the Hopper attention standard.** On H100-class hardware it is the kernel the serving world selects: SGLang's auto-selection picks FlashAttention 3 on Hopper (corpus: `runners/sglang.md`), vLLM exposes FlashAttention versions 2/3/4 as forceable backends with FA3 as the Hopper member of the family (corpus: `runners/vllm.md`), and FlashInfer incorporates the FA3 algorithm for Hopper alongside its FA2 templates for older parts (see `papers/flashinfer.md` §3) — the lineage's own library treats FA3 as one generation-specific backend among several, which is the correct mental model.
- **It set the FP8 attention accuracy bar.** Block quantisation + incoherent processing at 2.6× lower error than per-tensor FP8 made FP8 attention a deployable option rather than a demo, and the two techniques have become the standard vocabulary for low-precision attention and KV work since (the corpus's KV-quantisation dossiers argue in the same terms: finer-grained scales, explicit outlier handling).
- **It also demonstrated the lineage's turning point:** from FA3 onward, each generation's kernel is a *different program* written against that generation's asynchronous units — the paper's own limitation list (inference optimisation and persistent-kernel FP8 still to come) and FlashInfer's per-architecture template split both follow from this. Portability stopped being a property of the kernel and became a property of the *library* that holds one kernel per generation. That is the context in which a small runner should read FA3: not as a kernel to adopt, but as evidence about where hardware is going and what it costs to follow.

## 6. Applicability

### (a) Ollama on a 6 GB consumer GPU (RTX 2060 Max-Q, Turing)

- **Direct applicability: none, and the dossier should say so without hedging.** The target card cannot execute FA3's mechanisms. An improved Ollama on this hardware gains nothing by "enabling FlashAttention-3"; any configuration surface that offers it there is mislabelling an FA2-class kernel. The honest local stack is: FA1 tiling + FA2 partitioning (via ggml's flash-attention path or an FA2-class kernel), full stop.
- **Indirect applicability — two precision lessons that do run on Turing.** (i) *Block-granular scales beat tensor-granular scales* wherever quantisation meets outliers: the same principle, applied to KV-cache quantisation (q8_0's per-block scales in ggml are a coarse relative), is part of why block-scaled cache types hold quality better than naive per-tensor INT8 would. (ii) *Rotations spread outliers:* incoherent processing is the attention-side cousin of the Hadamard-rotation trick used in weight/KV quantisation (the corpus's ExLlamaV2 dossier notes Hadamard-rotated Q4 cache modes — `runners/exllamav2.md`). If the improved Ollama ever implements its own low-precision cache path, a fixed Hadamard rotation on keys before quantisation is a cheap, hardware-free accuracy win suggested directly by this paper's ablation — where rotation, not block scaling, did the work.
- **A negative lesson for the roadmap:** do not let Hopper-shaped expectations leak into a Turing product. FA3's headline (75% of peak, 1.2 PFLOPs/s FP8) describes a machine with ~5× the 2060's memory bandwidth and tensor-core generations the card predates. Planning local long-context performance from FA3 numbers would repeat, in miniature, the error the corpus's roofline dossier warns against: quoting a roof measured on different hardware.

### (b) Project Aesir

- **Co-design with the newest hardware — behind a per-generation backend boundary.** FA3 is the proof that the last 2× in attention comes from architecture-specific asynchrony, and simultaneously the proof that chasing it in the portable layer is ruinous. Aesir's structure should mirror the lineage's own resolution: one portable algorithm (tiling + online softmax + FA2 partitioning), and per-target kernel backends free to exploit whatever asynchronous/DMA/low-precision units the target actually has (AMD's async copies and MFMA, NPU DMA engines, ARM SVE pipelines) — each backend an FA3-sized, self-contained optimisation, replaceable per generation.
- **Overlap is a design primitive, not a tuning step.** Producer/consumer separation — some execution resource dedicated to staging the next tile while compute consumes the current one — generalises beyond Hopper: Aesir's targets all have *some* way to move data concurrently with compute (DMA channels, prefetch, double-buffered SRAM), and kernels designed without an explicit staging role leave that concurrency unclaimed. FA3's ablation prices the omission: ~15% of throughput at its test shape.
- **Keep softmax statistics in FP32 even when everything else narrows.** FA3's FP16 path matches FA2's error precisely because intermediates stay in FP32, and its FP8 path survives because scales and rotations are handled in full precision around an FP8 matmul. For Aesir's low-precision ambitions (packed model formats, quantised caches), the rule generalises: narrow the *stored and multiplied* tensors aggressively; keep reductions, statistics and accumulators wide.
- **Grade low-precision claims with an outlier-bearing test.** FA3's error evaluation uses a deliberately outlier-contaminated distribution, because clean Gaussians flatter quantisers. Aesir's compression school should adopt the same discipline: any packed-format or FP8/INT8 attention claim graded only on well-behaved inputs is ungraded where it matters.
