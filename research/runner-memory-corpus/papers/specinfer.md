## 2. The problem as framed

The 2023 speculative-decoding setup (Leviathan et al.; Chen et al. — wave 2, `papers/speculative-decoding.md`) drafts **one linear chain** from one small model and verifies that chain in one parallel target pass. SpecInfer's framing is that this leaves the verifier's parallel capacity mostly idle, for two compounding reasons:

- **The verifier can judge many candidates for the price of one, but is only offered one.** At batch 1, a target forward pass is bound by streaming the model's weights, not by arithmetic: scoring extra positions in the same pass is nearly free while spare GPU compute exists. A single chain spends that pass on a handful of positions arranged in the one configuration most likely to fail early — the first wrong token voids everything after it.
- **A single small model cannot align with the target well enough to exploit even that.** The paper is explicit about the capacity gap: its small speculative models (SSMs) are **100–1000× smaller** than the target LLM. The probability that a single speculated sequence stays aligned decays exponentially with length. Its own measurement (Table 1, LLaMA-7B verified against top-*k* candidates from LLaMA-68M) quantifies the single-candidate ceiling: with only the SSM's top-1 token available, per-token verification succeeds **62–70%** of the time under greedy decoding and only **52–57%** under stochastic decoding, depending on dataset.

The problem, then, is not "draft better" but "verify over a *set* of futures": if the verifier pass is going to happen anyway, present it with a diversity of candidate continuations at once, so that *some* path through them survives each step. SpecInfer also frames the two systems settings where the wasted capacity hurts most — distributed inference (where each decoding step pays inter-GPU communication latency) and offloading-based inference (where each step pays CPU→GPU weight transfers) — because in both, *reducing the number of target passes* is worth more than reducing the work inside a pass.

## 3. Core mechanism in our own words

SpecInfer has three moving parts: a speculator that builds a **token tree**, a verifier that scores the **whole tree in one target pass**, and a sampling rule that keeps the output distribution exact over a tree rather than a chain. It is a *system* paper (built on the FlexFlow distributed runtime), not a drafter-training paper — its SSMs are ordinary pre-trained small models (distilled / quantised / pruned family members, or same-family small variants such as OPT-125M for OPT targets), optionally aligned by the boost-tuning below.

**Token tree.** A tree in which each node is labelled with a token and represents the candidate sequence formed by concatenating the tokens on the path from the root to that node. One tree therefore encodes many candidate sequences at once, with shared prefixes stored (and, crucially, computed) only once.

**Tree construction — two routes.**

- *Expansion-based (single SSM):* at each speculation step, take not just the SSM's top-1 token but its top-*kᵢ* tokens as sibling branches. Because naive top-*k* branching explodes exponentially, the paper uses a **static, preset expansion configuration** ⟨*k*₁, …, *k*ₘ⟩ — how many children each node gets at each depth. The configuration used in the main evaluation is ⟨1,1,3,1,1,1,1,1⟩ (speculation length 8). The motivating measurement: letting the verifier choose among the SSM's top-5 tokens instead of top-1 lifts per-token success from ~70% to **89%** (greedy) and from ~57% to **97%** (stochastic). The paper states plainly that *dynamically* expanding the tree is "an open research problem beyond the scope of this paper, which we leave as future work" — that sentence is, in hindsight, the abstract of EAGLE-2 (see §5 and `papers/eagle-2.md`).
- *Merge-based (multiple SSMs):* run several SSMs, take each one's speculated sequences as its own tree, and **merge** the trees into one (the merge contains exactly the union of the member trees' sequences, prefixes shared). To make a pool of SSMs worth merging, the paper proposes **collective boost-tuning**: an AdaBoost-style unsupervised procedure over a general text corpus (OpenWebText in the evaluation) in which the target LLM generates reference continuations for prompts, the first SSM is fine-tuned to the fullest on all samples, samples it already matches are marked and removed, and the next SSM is fine-tuned on the *remaining* samples — producing a deliberately *diverse* pool whose aggregate coverage of the target's outputs exceeds any member's. In the distributed system the SSMs run data-parallel on different GPUs, so (in the paper's setting) a pool costs no extra speculation latency.

**Tree attention and tree-based parallel decoding — the verifier.** For each node, its attention output must be computed as if its input sequence were exactly its root-to-node path. SpecInfer generalises attention from sequences to trees accordingly (**tree attention**: TreeAttention(*u*) = Attention(*Sᵤ*) for every node *u*), and implements it as *one fused kernel over the whole tree* via two techniques:

- *Shared KV cache with depth-first traversal:* instead of a separate KV cache per candidate sequence (which duplicates every shared prefix), one cache is maintained in tree topology and traversed depth-first, so prefix KV is computed and stored once.
- *Topology-aware causal mask:* flattening the tree into one batch would let a token attend to tokens from *sibling branches* that are not its ancestors — causally wrong. The mask is therefore built from the tree topology: each node attends only to its ancestors (plus the verified prefix). With that mask, the flattened tree computes *exactly* the attention outputs that sequential decoding of each candidate would have produced, in a single kernel launch (the paper's kernel is a customised FasterTransformer-based attention kernel).

**Verification and sampling.** One TreeParallelDecode pass produces, for every node *u*, the target's next-token output 𝒪(*u*). Then:

- *Greedy:* walk from the root — while the current node has a child whose token equals 𝒪(*u*), accept that child and descend; finally append 𝒪(*u*) itself as the one guaranteed new token. Each verifier pass therefore emits the accepted path **plus one** token.
- *Stochastic:* **multi-step speculative sampling (MSS)** — the tree generalisation of Leviathan/Chen's rejection sampling. At each node, children are tried in random order; a child *x* proposed by SSM *s* is accepted with probability min(1, *P*LLM(*x*|*u*) / *P*SSMₛ(*x*|*u*)); on rejection that child's proposal distribution is removed and the target distribution is renormalised over the residual norm(max(0, *P*LLM − *P*SSMₛ)) before trying the next sibling; if all children fail, a token is sampled from the target distribution directly. The paper proves (its Theorem 4.2) that MSS samples from *exactly* the target's distribution, and (Theorem 4.3) that its rejection probability is uniformly ≤ that of the naive alternative (sample from the target, check membership in the tree). **Losslessness is therefore preserved over trees, for both greedy and stochastic decoding** — the property the whole family is defined by.

**System design around it.** Iteration-level scheduling and continuous batching adapted from Orca; SSMs served data-parallel (one GPU each); the LLM served with Megatron-style hybrid parallelism (tensor parallelism within a node, pipeline parallelism across nodes); a request manager that performs tree merge and verification and exchanges only tokens (not activations) with GPU workers — overhead the paper reports as negligible next to LLM execution. The stated overhead accounting (§5.3 of the paper): each SSM adds **<1%** memory (a consequence of the 100–1000× size gap); the tree's extra KV/attention storage is claimed negligible *relative to long-context KV cache* — a claim made in a datacentre serving context, and one §6 below does not import uncritically to a 6 GB card.

## 4. Reported results — as reported, with hardware/model context

All figures are the paper's own; nothing is re-derived. **Platform:** two AWS g5.12xlarge instances, each with **4× NVIDIA A10 24 GB GPUs**, 48 CPU cores, 192 GB DRAM, nodes linked by 100 Gbps Ethernet. **Targets:** LLaMA-7B, OPT-13B, OPT-30B, LLaMA-65B (half precision). **SSMs:** LLaMA-68M, OPT-125M. **Datasets (prompts only, simulating conversation traces):** Alpaca, ChatGPT Prompts (CP), WebQA, Chatbot Instruction Prompts (CIP), PIQA. Main runs generate up to 128 new tokens and report average per-token latency; tree construction in the headline runs is expansion-based with configuration ⟨1,1,3,1,1,1,1,1⟩.

**Headline (abstract):** SpecInfer outperforms existing LLM serving systems by **1.5–2.8× for distributed LLM inference** and by **2.6–3.5× for offloading-based LLM inference**, preserving the same generative performance.

**Distributed inference (§6.2, vs vLLM, HuggingFace TGI, FasterTransformer):**

- **1.5–2.5×** over incremental-decoding systems for single-node multi-GPU serving; **2.4–2.8×** for multi-node serving (LLaMA-65B on 8× A10 across two nodes; vLLM/TGI could not run that configuration at all, lacking pipeline parallelism).
- Control condition: SpecInfer with speculation disabled (empty trees) matches the baselines — i.e. the gain is the mechanism, not the implementation.
- Against its own **sequence-based** speculative variant, the tree approach contributes a further **1.2–1.5×** latency reduction.
- The paper states the caveat itself: the advantage **shrinks as batch size grows**, because larger batches already consume the spare GPU capacity that tree verification exploits. SpecInfer "is most beneficial for low-latency LLM inference."

**Offloading-based inference (§6.3, vs FlexGen):** OPT-13B and OPT-30B served on a **single 24 GB A10** with weights resident in CPU DRAM and streamed to the GPU. SpecInfer reduces per-token latency by **2.6–3.5×**, attributed to fewer decoding steps and therefore fewer CPU→GPU parameter transfers. This is the paper's most consumer-adjacent result — one GPU, weights that do not fit — though still an A10 with a datacentre CPU/DRAM subsystem behind it.

**Mechanism-level numbers:**

- *Per-token verification success (Table 1, LLaMA-7B / LLaMA-68M):* greedy, top-1 → top-5: 68%→85% (Alpaca), 69%→87% (CP), 62%→82% (WebQA), 70%→89% (CIP), 63%→85% (PIQA). Stochastic: 54%→97%, 56%→97%, 52%→96%, 57%→97%, 55%→97%. The paper's introduction rounds the stochastic jump as "from 52–57% to 96–97%".
- *Tokens verified per decoding step (Table 2, speculation length 8) as tree width goes 1 → 5:* greedy 2.95→3.43 (Alpaca), 2.58→3.69 (CP), 2.27→3.07 (WebQA), 2.73→3.91 (CIP), 2.18→3.21 (PIQA); stochastic 1.79→2.38, 1.69→2.28, 1.64→2.21, 1.72→2.29, 1.67→2.21. Note the shape: **width 1→2 is the big step** (e.g. greedy CP 2.58→3.24); widths 4→5 add ~0.1 tokens/step. Diminishing returns are visible inside the paper's own table.
- *Width vs latency (§6.4):* trees reduce decoding steps by 1.2–1.5× (greedy) / 1.3–1.4× (stochastic) vs sequence speculation; at batch sizes 1–2 larger widths keep reducing per-token latency, but at **batch size ≥ 4 the best width is 2 or 3** — wider trees cost more verification time than the extra accepted tokens repay once spare capacity is gone.
- *Tree-based parallel decoding (§6.5):* on par with sequence-based decoding at small batch sizes, up to **1.8× faster** at large batch sizes (shared-prefix reuse + single fused kernel).
- *Multi-step speculative sampling (§6.6, tree width 5, depth 8):* tokens verified per stochastic step 2.21–2.38 with MSS vs 1.73–1.87 with naive sampling — a consistent **1.26–1.28×** improvement at identical speculation/verification cost.

## 5. Position in the family

The speculative-decoding family, as covered across waves 2 and 13, generalises along two independent axes — *what drafts* and *what verification accepts* — and SpecInfer is the paper that opened the second axis:

- **Leviathan et al. / Chen et al. (2023, wave 2)** define the skeleton: a cheap drafter proposes a **linear chain**; the target verifies the chain in one parallel pass; modified rejection sampling makes the result distribution-exact. Everything after them keeps this skeleton.
- **Medusa (2024, wave 2)** changes the *draft source* (parallel heads on the target's own hidden state, no separate model) and, in doing so, is forced to invent tree-shaped candidate sets and tree-attention verification for its Cartesian-product candidates — but its tree is a by-product of head combinatorics, and its default typical-acceptance rule is not distribution-exact (only its rejection-sampling mode is).
- **EAGLE (2024, wave 2)** changes the *draft representation* (autoregression in the target's feature space, shifted-token conditioning) and likewise verifies over a **static** draft tree with tree attention.
- **SpecInfer (2023, ASPLOS '24)** is the **verification-side generalisation**, and chronologically it precedes Medusa/EAGLE: it takes the draft source to be *arbitrary* — one SSM, a top-*k* expansion of one SSM, or a boost-tuned *ensemble* of SSMs merged into one tree — and makes the verifier's contract "score this tree, exactly, in one pass." Tree attention, the topology-aware mask, shared-prefix KV, and a distribution-exact sampling rule *over trees* (MSS) are stated here as general machinery, not as artefacts of one drafter. Medusa and EAGLE both build on precisely this machinery; EAGLE-2's related-work summary describes SpecInfer exactly this way ("integrating multiple small models as the draft model, aggregating their drafts into a tree and using tree attention for parallel verification").
- **EAGLE-2 (2024, this wave)** is then the **draft-side generalisation** of the same tree: SpecInfer's expansion configuration is static and its authors explicitly defer dynamic expansion as future work; EAGLE-2 makes the tree's *shape* a per-step, per-context decision driven by draft confidence (see `papers/eagle-2.md` §5 for the precise division of labour, including what EAGLE-3 later changed instead).
- **Lookahead (wave 2)** is the family's draft-free branch (Jacobi-iteration n-grams verified in-pass) and **Online Speculative Decoding (wave 2)** its draft-*adaptation* branch; both are orthogonal to the tree question — either could in principle propose into a SpecInfer-style tree, and neither requires one.

One-line summary for the compendium: **Leviathan/Chen made verification parallel over a chain; SpecInfer made it parallel over a tree; EAGLE made the drafter predict features; EAGLE-2 made the tree reshape itself.**

## 6. Applicability

### (a) A 6 GB personal runner — where tree width stops paying

*[Engineering judgment, labelled as such; the paper's measurements are A10-datacentre measurements and are not imported as expectations.]*

The corpus's standing rule for this workload applies with full force: at batch 1, decode is **streaming** — each target pass pays the full weight-streaming cost once, and speculation wins by amortising that one stream over several accepted tokens. Tree verification does *not* repeal the budget; it re-spends it. A verifier pass over a tree of *W* nodes still streams the weights once (that is the win), but everything *per-position* scales with *W*: attention against the accumulated context (W × context-length KV reads), KV writes for W new positions, the LM-head matmul and logits for W positions (W × vocab — for a 128k-vocab model this is not small), and the host-side bookkeeping of masks, positions, and rollback. On an A10/A100 serving stack those per-position costs hide under idle FLOPs and abundant bandwidth headroom. On a 6 GB consumer card — lower memory bandwidth, far fewer FLOPs, and a target that already fills most of the card — the crossover where "one more node costs more time than the tokens it buys" arrives much earlier.

The honest reading of the paper's own data points the same way. Its Table 2 shows acceptance gains flattening hard past width 2–3 at every dataset, and its §6.4 finds width 2–3 optimal as soon as batch ≥ 4 eats the spare capacity — a 6 GB card at batch 1 is, in spare-capacity terms, closer to the paper's loaded regime than to its idle one, because the *machine* has less slack even though the *batch* is one. **Verdict (judgment): on a 6 GB card, expect the paying region to be narrow trees — width ≈ 2–3 at the branching levels that branch at all, total verified nodes in the low tens at most (≈ 8–16), depth favoured over breadth — and expect widths of 4–5, or datacentre-sized trees (EAGLE-2's 48–60 draft tokens), to be neutral-to-negative once context is long.** The correct deployment shape is therefore not a fixed width but a *measured* one: expose tokens-per-pass (τ) and wall-clock tokens/s against node budget, and cap the tree where τ stops converting into tokens/s on the user's own card and context length. Two further 6 GB-specific costs the paper's "<1% / negligible" overhead accounting does not cover: (i) every SSM, however small, is resident VRAM competing with the target's KV cache — the corpus's recurring trade (drafter bytes vs context bytes) applies to SpecInfer's ensemble idea most of all, and a *pool* of SSMs is a datacentre answer, not a 6 GB one; (ii) rejected branches' KV must be rolled back or fenced off every step, which is bookkeeping a single-user runner pays in latency-critical code, not in a request manager on a 48-core host.

What *does* transfer intact from SpecInfer to the small runner is the offloading result's logic: where weights are streamed from somewhere slow (CPU DRAM, or a card so full that layers spill), reducing the *number of passes* is worth even more than on a resident model — §6.3's 2.6–3.5× is the paper's own demonstration. A narrow tree on an offloaded 6 GB setup is plausibly the single best use of this paper locally; a wide tree on a resident one is plausibly a slowdown. Both halves are judgment, stated so they can be measured rather than believed.

### (b) Ollama's existing n-gram/draft landscape — what adoption would actually require

As documented in the corpus (`runners/llamacpp-ggml.md` §8.4, `runners/ollama.md` §6.3/§9 D3, IDEA-LEDGER #15/#26/#27/#28), the landscape a personal runner actually ships today is: **n-gram / prompt-lookup speculation as the free floor** (no weights, no training, megabytes of lookup structure — IDEA-LEDGER #15, the default accelerator), then conditional upgrades — a small same-family draft GGUF (`draft-simple`, #26), embedded MTP heads where the model ships them (`draft-mtp`, #28), and an EAGLE-3 head where a checkpoint exists for the exact model (`draft-eagle3`, #27). Ollama itself surfaces only draft-token controls for separate draft models and embedded MTP tensors; the full `--spec-type` menu lives in llama.cpp's server. **All of these verify chains (or chain-like candidate sets), not arbitrary trees.** Nothing in the shipped landscape performs SpecInfer-style tree verification.

Adopting tree verification in a ggml-class backend is engine surgery, and it is worth stating plainly which parts are hard:

1. **The attention path is the blocker.** ggml/llama.cpp attention kernels — above all the FlashAttention fast path (see `papers/flashattention.md`) — assume the standard causal structure: a token attends to a contiguous prefix, with masking expressible as "position ≤ my position." A tree breaks both halves of that assumption: a node's visible set is its *ancestor chain*, which is not a contiguous range of the flattened batch, and two nodes at the same flattened offset range have *different* visible sets. Supporting it requires either (i) a materialised arbitrary mask tensor fed to a mask-capable attention kernel — leaving the fused fast path, paying mask memory and bandwidth per step, per layer, per head-group — or (ii) a purpose-built tree-attention kernel of the kind SpecInfer wrote for itself (customised FasterTransformer kernel, topology-aware mask, tree-topology KV layout). There is no configuration-flag version of this; it is new kernel work in the backend's hottest path, multiplied by every backend (CUDA / Vulkan / Metal / CPU) the runner supports.
2. **Positions stop being indices.** Each tree node needs a position ID equal to its *depth* along its own path (for RoPE), not its slot in the batch — the graph builder, the KV addressing, and the attention kernel must all agree on per-node positions.
3. **KV management becomes tree management.** Nodes occupy KV slots that are shared by descent (a prefix node's KV serves all its descendants) and mostly doomed (every unaccepted branch's KV must be invalidated at step end without disturbing the accepted path's). llama.cpp's KV cells/rollback machinery handles *linear* truncation today; tree verification needs slot allocation over a branching structure with per-step garbage collection of dead branches.
4. **The sampler must walk a tree.** Probabilistic verification over a tree is MSS (§3): per-node proposal distributions from the drafter, sequential sibling trials with residual renormalisation, and correction sampling — a different control flow from chain verification's single left-to-right pass, and one that must stay exactly distribution-preserving (the family's entire claim) under the runner's temperature/top-p/min-p stack.

By contrast, the *draft-side* half of this wave (EAGLE-2's confidence-scored expansion/reranking, `papers/eagle-2.md` §6b) is comparatively cheap host-side logic — *once* a tree verifier exists to feed. The sequencing conclusion for the corpus: tree verification is a prerequisite investment whose payoff is shared by SpecInfer-style ensembles, Medusa-style heads, and EAGLE-family dynamic trees alike; it should be justified (if at all) as that shared substrate, never as a SpecInfer port. For the 6 GB runner specifically, §6a's verdict caps the benefit at narrow trees — which is precisely the regime where the simpler chain verifiers already capture most of the available gain. The gap between "chain + good drafter" and "narrow tree + good drafter" is real but second-order locally; the kernel work to cross it is first-order.
