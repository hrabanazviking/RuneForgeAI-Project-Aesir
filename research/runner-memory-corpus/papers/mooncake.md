## 2. The problem as framed

Mooncake is not a laboratory scheduler looking for a workload; it is the serving platform for **Kimi**, Moonshot AI's production LLM chatbot, and its problem statement is written from inside an overloaded production service. Three strands:

1. **Prefill/decode interference — inherited, then reframed.** Like DistServe and Splitwise (Wave 4b), Mooncake separates prefill from decode because the phases fight when colocated: prefill is compute-heavy and sets time-to-first-token (TTFT); decode is memory-bandwidth-heavy, runs for many steps, and sets time-between-tokens (TBT). But Mooncake's reframing is the paper's identity: in a disaggregated system the thing that actually moves, accumulates, and can be reused is neither compute nor requests — it is the **KV cache**. Every design decision is therefore re-derived with the KV cache, not the request, as the central object: where KV lives, where it is reused, and which instance a request should go to *because of where its KV already is*.

2. **KV as stranded, per-instance state under production traffic mixes.** In a conventional deployment each instance's prefix cache is local: a reusable prefix that happens to sit on another node might as well not exist, and the fleet's aggregate CPU DRAM and SSD — which sit largely idle on GPU servers — hold nothing useful. Kimi's traffic makes this waste large and measurable: long-context, chat-heavy workloads with substantial shared prefixes (system prompts, documents, multi-turn history). The paper reports prefix-cache hit ratios in the published production traces in the region of **40–66%** — i.e. a large fraction of prefill compute is, in principle, re-doable work that a global cache could eliminate. The paper formalises when reuse pays: fetching a cached prefix beats recomputing it when the available transfer bandwidth clears a threshold derived from the model's KV bytes per token and its prefill compute cost — for the paper's worked example (LLaMA3-70B-class, 8×A800 node) the break-even is on the order of **6 GB/s**, rising to roughly **19 GB/s** on H800 — comfortably inside RDMA fabric bandwidth, which is why the pool is buildable at all. The slogan of the published title is the thesis: *trade more storage for less computation*.

3. **Overload is the normal case, not the exception.** The paper is explicit that, unlike prior serving studies, it does **not** assume all arriving requests will be served. At peak, Kimi's offered load exceeds capacity; a scheduler that admits everything degrades everyone — queues build, prefill work is spent on requests that will find no decode slot, and SLOs collapse fleet-wide. Scheduling under overload — including the decision to refuse work *early and cheaply* — is therefore a first-class part of the problem, not an operational afterthought (§3, admission).

The SLO framing follows the disaggregation generation: requests are judged on **TTFT and TBT** simultaneously, and the system's objective is maximum *effective* throughput — requests served *within* SLO — not raw tokens per second.

## 3. Core mechanism in our own words

**Three pools, one centre.** Mooncake splits the fleet into a **prefill cluster**, a **decode cluster**, and beneath both a **disaggregated KV cache pool (Mooncake Store)**, coordinated by a global scheduler named **Conductor**.

- **Prefill instances** run the prompt phase. Their objective is maximum KV reuse: before computing, they pull every reusable prefix block the Store holds for this request, and compute only the suffix that is genuinely new.
- **Decode instances** run continuous batching for generation. They receive the request's KV from the prefill side and never do prefill work.
- **Mooncake Store** is a distributed cache built from the GPU cluster's otherwise underutilised **CPU, DRAM, SSD and NIC** capacity. It stores KV blocks (256 tokens per block in the evaluation configuration) keyed by prefix-aware hashes, so any block is addressable by the prefix that produced it, from any node. Hot blocks are **replicated** across nodes to avoid fetch congestion; cold blocks are evicted under an LRU-style policy and can be demoted toward SSD. Conductor additionally predicts future block usage and drives swapping/replication accordingly, with a heuristic hot-spot migration scheme that replicates hot blocks without requiring precise usage predictions. The Store turns prefix caching from a per-instance accident into a fleet resource: the paper reports the global cache achieving substantially higher hit rates than node-local caching (a secondary analysis of the paper puts the figure at up to ~136% higher hit rate and up to ~48% less prefill GPU time; the dossier treats those as analysis-reported, with the primary claims in §4).

**The request workflow.** For each request Conductor selects a *pair* — a prefill instance (or group) and a decode instance — then: (1) transfer as much reusable KV as possible from the Store to the chosen prefill instance; (2) run prefill in chunks/layers, **streaming the produced KV continuously to the decode instance** rather than shipping it in one blocking handoff at the end; (3) the decode instance loads the KV and admits the request to its continuous batch. For very long contexts, prefill itself is spread across nodes with **chunked pipeline parallelism (CPP)**, so a single long prompt's TTFT is not bounded by one node's prefill speed.

**The transfer layer.** Moving KV at this volume is a storage-systems problem, and Mooncake builds it like one: a dedicated **Transfer Engine** over RDMA (with TCP and other transports as fallbacks) that moves KV blocks GPU↔DRAM↔remote node without involving the compute path. Project-published figures for the open-sourced engine are ~87 GB/s on 4×200 Gbps RoCE and ~190 GB/s on 8×400 Gbps RoCE, roughly 2.4× and 4.6× faster than the TCP path in the same tests. The engine is the component that escaped the paper: it is now a standard KV-connector backend in vLLM and SGLang (§6).

**KV-centric scheduling.** Conductor's placement rule is the paper's namesake idea. A naive disaggregated scheduler balances load; a KV-centric scheduler balances load *and* cache locality together, because sending a request to the instance where its prefix already lives can be worth more than sending it to the emptiest instance — the saved prefill compute dwarfs small load imbalances. Conductor scores candidate prefill/decode placements by a combination of expected cache hit (how much of this request's KV is already resident, and where) and current instance load, subject to TTFT/TBT SLO feasibility, and it must also respect a local constraint the disaggregation creates: prefill nodes reserve much of their DRAM for the global cache pool, so prefill scheduling is constrained by cache-pool space as well as GPU load.

**Overload-oriented admission: prediction-based early rejection.** When predicted near-future load exceeds what the decode cluster can serve within SLO, Conductor **rejects selected requests at admission — before any prefill compute is spent on them**. The paper reports that a naive version of this (reject when currently full) oscillates badly: rejection frees load, admission surges, overload returns. The shipped policy therefore *predicts*: it estimates individual requests' generation lengths and the short-term aggregate load, and rejects against the forecast rather than the instantaneous state. A rejected request costs the system almost nothing and costs the user a fast, explicit refusal instead of a long queue followed by an SLO-violating answer; the capacity that would have been wasted prefilling doomed requests is spent on requests the system can actually finish well. The paper names this whole stance **overload-oriented scheduling** and presents it as a preliminary but production-necessary study — an honesty marker worth keeping (§7).

## 4. Reported results — as reported, with hardware and scale context

All figures are the paper's or the project's own, on datacentre fleets, under TTFT/TBT SLOs. **Nothing below is a single-machine or consumer-hardware number.** The recurring caveat of this dossier applies throughout: these are *fleet* results; §5 separates the mechanism truth from the magnitude truth.

**Production deployment (FAST '25 abstract, as reported):**

- Mooncake is operational across **thousands of nodes**, processing **over 100 billion tokens daily** for Kimi.
- In practical deployment it enables Kimi to handle **115% more requests on NVIDIA A800 clusters and 107% more on H800 clusters** than the previous (vLLM-based) system it replaced.
- In tests replaying **real traces**, effective request capacity rises by **59%–498%** versus baseline methods while complying with SLOs — the range spans workloads; the high end is the long-context, high-prefix-reuse end, which is exactly the regime the architecture is built for.

**Preprint evaluation (arXiv abstract and body, as reported):**

- Up to a **525% increase in throughput in certain simulated scenarios** while adhering to SLOs, versus the baseline method — a simulated, best-case, long-context figure, labelled as such by the source.
- Under real workloads, **75% more requests** handled — the preprint-era production figure, superseded in print by the 115%/107% per-cluster figures above.
- The trace-replay evaluation behind these numbers uses a LLaMA3-70B-class stand-in model across a multi-node GPU testbed (16 nodes of 8 GPUs in the configuration discussed in secondary analyses of the paper) against vLLM-family baselines (plain, prefix-caching, and chunked-prefill variants). The reproducible numbers are thus *replayed production traces on a proxy model*, while the production numbers are *historical statistics against the operator's own previous system* — two different kinds of evidence, and §7 weighs them differently.
- The mechanism-level findings that support the headlines: global (disaggregated) prefix caching materially raises hit rates over node-local caching on Kimi-like traffic (published traces: ~40–66% prefix hit ratios), and the benefit of the whole architecture **scales with context length and prefix reuse** — short-context, low-reuse traffic is not where Mooncake wins, and the paper does not claim otherwise.

**Scale caveat, stated plainly.** Every multiplier above is conditioned on (a) many nodes, (b) an RDMA fabric fast enough to clear the reuse break-even of §2, (c) a workload with long contexts and heavy prefix sharing, and (d) an overloaded production service where admission control has something to protect. Remove any one of these and the magnitude does not survive — which is precisely why §5 extracts mechanisms, not multipliers.

## 5. What transfers DOWN to a single machine

The corpus's standing question: what survives the collapse from thousands of nodes to one box — for Ollama-class serving on a 6 GB consumer GPU, and for Project Aesir's single-machine serve?

**The pool survives — as memory tiering.** Mooncake's deepest idea is not disaggregation; it is that *KV is a poolable asset with a residence independent of any one compute instance*, stored in whatever memory the system has, addressed by prefix, and fetched when fetching beats recomputing. Remove the network and that sentence describes, exactly, the tiered-KV design this corpus already argues for on one machine (`memory/kv-cache-design.md`): KV blocks resident in **VRAM** when hot, demoted to **system RAM**, then to **SSD**, keyed by prefix hash, restored on demand — SGLang's HiCache is the same thought inside one process. Mooncake contributes three things to that local design that the local literature states less sharply:

1. **The break-even inequality as a design tool.** Mooncake prices reuse in bandwidth: cache a prefix iff fetch bandwidth beats recompute cost for that model. On one machine the same arithmetic runs with local numbers — VRAM↔RAM over PCIe, RAM↔SSD over NVMe — and the corpus's own measured case (a 7.3K-token session restoring in ~2.14 s versus ~160.7 s of cold prefill on a CPU-only box; IDEA-LEDGER #10) is Mooncake's inequality evaluated at laptop scale, with the same verdict. The discipline transfers even where the constants invert: *measure the fetch path, price the recompute, then decide what to keep* — never keep or discard KV by intuition.
2. **Cache-aware placement becomes cache-aware session scheduling.** Conductor sends the request to where its KV lives. A single-machine runner has one GPU, but it still chooses *which session to resume, which prefix to keep resident, and which to evict* — and Mooncake's rule applies verbatim: the value of a resident prefix is the prefill it saves, weighted by how likely it is to be asked for again; hot prefixes deserve replication's local analogue (pinning in VRAM), cold ones demotion, not deletion, while cheaper tiers have room.
3. **Streaming handoff, miniaturised.** Mooncake streams KV from prefill to decode *during* prefill instead of blocking at the boundary. The single-machine echo is overlap: restore/spill of session KV overlapped with the work that does not depend on it, so tier movement is hidden behind compute rather than serialised in front of the user's first token.

**The admission lesson survives intact — it never needed a fleet.** Early, cheap, predicted rejection is the one Mooncake mechanism whose value *increases* as resources shrink. A 6 GB runner asked to do more than it can — a second model load, a context that cannot fit, a background task during a live decode — has the same choice Kimi has: degrade every in-flight interaction, or refuse the new work immediately, explicitly, and before spending scarce compute on it. The corpus's robustness line (IDEA-LEDGER #31, one residency arbiter with ordered pressure shedding: failure becomes "prefix evicted", not "machine died") is this lesson in local dress. What does *not* transfer is the prediction machinery's sophistication — a single-user runner's "forecast" can be a simple budget check (will this fit alongside the resident session, yes/no) — but the *posture* transfers whole: **an honest fast refusal is a feature; a slow collective collapse is the bug.**

**What does not survive.** The prefill/decode pool split itself (one GPU has no pools — the DistServe dossier's §6 verdict governs), RDMA transfer engineering (the local "fabric" is PCIe/NVMe and needs no engine of this class), CPP across nodes, and every magnitude in §4. Anyone quoting "525%" in a single-machine design document has confused the mechanism truth with the magnitude truth.

**For Aesir specifically:** Aesir's serve already treats session state as a movable, storable asset (bounded bit-exact snapshots for hybrid models; IDEA-LEDGER #23). Mooncake is the fleet-scale proof that this posture is correct and worth building the scheduler around: state first, compute second. Aesir's snapshot store is a Mooncake Store of four entries; the design questions are the same (what to keep, at which tier, keyed how, evicted when) at a scale where they can be answered by measurement on the bench instead of prediction in production.

## 7. Risks and limits of the source itself

- **It is the operator's paper about the operator's system.** Mooncake's authors are Moonshot AI and its academic partners; the production claims (115%/107%, 100B tokens/day, thousands of nodes) are Moonshot's own statistics against Moonshot's own previous system, with no independent replication and no public access to the production deployment. This does not make them false — the FAST '25 Best Paper award and the open-sourced engine/store give the work unusual substance for a production paper — but the production numbers are *testimony*, while the trace-replay numbers are *evidence*, and the dossier weights them accordingly.
- **Workload selection is the result.** The gains scale with long contexts and 40–66% prefix hit ratios — Kimi's chat-heavy traffic. A workload of short, unrelated, single-turn prompts would show a fraction of the benefit, and the paper's framing (a chatbot platform) should not be silently generalised to "LLM serving" as a whole. The 525% figure in particular is a *simulated, certain-scenario* maximum from the preprint abstract; quoting it without its qualifiers misquotes the source.
- **Version drift.** arXiv (75% real-workload figure) and FAST '25 (115%/107% production figures; 59%–498% trace range) report different numbers from different evaluation rounds, and the author list grew between them. Any citation of "Mooncake's results" that does not name its version is under-specified (§1 records both deliberately, following this corpus's DistServe precedent).
- **The baseline is a moving, self-chosen target.** "Previous system" comparisons measure Mooncake against what Moonshot replaced, tuned by the same team that built the replacement. The vLLM-family baselines in the replay evaluation are fairer, but still configured by the proponents.
- **Overload-oriented scheduling is explicitly preliminary.** The paper presents early rejection as a studied necessity, not a solved problem — the prediction policy's failure modes (mispredicted generation lengths, fairness between rejected and admitted users) are production concerns the paper opens rather than closes. A reader should bank the *posture* (§5), not a finished algorithm.
- **KV-size dependence.** The reuse economics depend on the model's KV bytes per token; architectures that shrink KV state (MLA-class latent attention; see the corpus's DeepSeek-V2/MLA dossier) change the exchange rate between storage and computation that the whole design trades on. Mooncake's arithmetic is honest about this; its conclusions are not architecture-universal.
