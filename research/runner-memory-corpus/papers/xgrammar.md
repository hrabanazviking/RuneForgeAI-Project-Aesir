## 2. The problem as framed

Structured generation is the requirement that an LLM's output *conforms* — that it parses as JSON against a schema, as a function call with typed arguments, as SQL, as code, or as an embodied agent command — because a downstream program, not a human, is the reader. The paper opens on the agent-driven demand for exactly that: outputs "that can be parsed into code, structured function calls, and embodied agent commands."

Constrained decoding is the guarantee mechanism: at each step, identify every token that would make the prefix unextendable to a valid completion, set its logit to $-\infty$ (equivalently, its probability to zero), and sample only from what remains. Context-free grammar (CFG) is the specification language the paper chooses, because regular expressions cannot express the recursive nesting that JSON, SQL and domain-specific languages require — an arbitrarily nested array or object is not a regular language.

The paper frames three compounding costs in doing that naively, and they are the whole problem:

- **Vocabulary scan per step.** Each decoding step "needs to interpret CFG for every possible token in the vocabulary, which can be as large as 128k in Llama 3.1." A per-step $O(|V|)$ grammar interpretation, on CPU, sits on the decode critical path. If mask construction takes longer than the forward pass it is supposed to serve, constrained generation — not the model — becomes the bottleneck, and the tax grows with batch size because the CPU grammar work scales with requests while the GPU forward pass amortises.
- **The stack makes precomputation combinatorial.** A CFG is recognised by a pushdown automaton (PDA): a finite-state machine per rule plus a stack for recursive rule expansion. Whether a token is valid can depend on the *entire* stack, and the stack is unbounded, so "it [is] impossible to precompute and cache all combinatorial combinations of stack patterns ahead of time." This is the precise point where the regular-language solution (see the companion dossier: precompute an index once, look up in $O(1)$) breaks — there is no finite index over all PDA configurations.
- **Token boundaries do not respect grammar boundaries.** An LLM token is a byte string that may end in the middle of a grammar element, complete one rule and start the next, or pop several stack frames at once. Any engine that pretends tokens and grammar terminals align will misjudge validity at exactly those boundaries — the paper criticises a predecessor on precisely this ground (§3, §5 below).

Behind the speed problem sits the fidelity problem, which this corpus states as a requirement even where the paper states it as a mechanism (§5): masking must produce the model's *conditional* distribution over valid continuations — invalid logits to $-\infty$, relative probabilities among valid tokens preserved, renormalisation over the valid set only. A mask that is merely *fast* but wrong — that rejects a valid token because it mis-tracked the stack, or accepts an invalid one — either distorts the distribution silently or breaks the guarantee the whole apparatus exists to provide. And a mask computed against a stale or misaligned state can empty the valid set or force the sampler down a corridor of individually-valid, jointly degenerate tokens. Speed and faithfulness are therefore not two desiderata; a wrong mask is not a faster mask, it is a different sampler.

## 3. Core mechanism in our own words

**The PDA, and why JSON needs a stack.** XGrammar compiles the CFG into a *byte-level* pushdown automaton. Each grammar rule becomes a finite-state automaton; a rule-reference edge, taken when one rule invokes another, pushes the return position onto a stack, and completing a rule pops it. Byte-level (rather than character- or token-level) edges let a single LLM token be walked byte by byte through whatever rule transitions it spans, including tokens that split a multi-byte character. Non-determinism — several possible expansions for the same input — is handled by maintaining multiple parallel stacks, one per live parse path, and unioning their accepted-token sets into the final mask. A finite-state machine alone cannot do this job: an FSM has no memory of *how deeply* it is nested or *which* object it must close, so `{"a": [1, {"b": …` is beyond it. The stack is that memory. This PDA-vs-FSM distinction is the architectural fork between this dossier and its companion: Outlines' index is complete for regular constraints; XGrammar pays for a stack because its target class — full CFGs — requires one.

**The split: context-independent vs. context-dependent tokens.** This is the paper's central insight. Walk a candidate token through the PDA from the current configuration and watch what the walk needs:

1. the walk *pushes* into a child rule, or
2. the walk *advances within* the current rule, moving only the stack-top node, or
3. the walk *finishes* the current rule and must *pop* to a parent rule to decide the token's remainder.

In cases 1 and 2, validity depends only on the node at the top of the stack — the position inside the current rule. The paper calls such tokens **context-independent**: for each PDA node, the set of context-independent tokens accepted/rejected when that node is on top can be decided *before runtime*, once, and cached. In case 3, validity depends on what lies below the top — the whole stack — so the token is **context-dependent** and must be interpreted at runtime against the live stack.

The measured asymmetry is what makes the design work: for Llama-3.1 with JSON grammar, context-dependent tokens are **fewer than 1% of the vocabulary — 1,134 of 128k** — before further optimisation. The engine therefore precomputes ~99% of every mask and interprets ~1% live.

**The adaptive token mask cache.** Precomputed results are stored keyed by stack-top node, in a storage format chosen per node by which case is cheaper:

- *Accept-heavy* nodes (e.g. inside a string, where a wildcard accepts almost everything): store only the short **rejected** list plus the context-dependent list.
- *Reject-heavy* nodes (e.g. where only a few specific characters may follow): store only the short **accepted** list plus the context-dependent list.
- *Balanced* nodes (rare): store a full vocabulary-sized bitset.

Storing the two smaller of the three partitions (accepted / rejected / context-dependent) cuts the cache for Llama-3.1 + JSON grammar, as reported, **to 0.2% of the naive size — from 160 MB to 0.46 MB**. Merging masks across parallel stacks is likewise performed on the small stored lists (intersect rejected sets, union accepted sets) rather than on full bitsets.

**Context expansion — shrinking the runtime remainder further.** A context-dependent token is only undecided because its remainder, after finishing the current rule, must be checked against the parent. XGrammar precomputes, for each rule, an *expanded suffix* automaton: the set of strings that can legally follow that rule in its parents (extracted by a bounded search that follows character edges only, stopping at further rule references). At preprocessing time, any context-dependent token whose remainder is neither a prefix of an expanded suffix nor an extension of one is rejected *in advance* and leaves the runtime set. As reported for the same Llama-3.1 / JSON case, this cuts context-dependent tokens **by 90%, from 1,134 to 120**. Two supporting PDA optimisations feed it: *rule inlining* (small fragment rules are inlined into their parents, within size limits, which both removes stack excursions and enlarges what context expansion can see) and *node merging* (merging same-label successors and ε-edge endpoints, reducing non-determinism and therefore the number of parallel stacks whose masks must be merged).

**The persistent execution stack — branching and rollback.** The remaining runtime checks, and the preprocessing walks themselves, need many stacks that share almost all of their contents. XGrammar stores them as one tree — a persistent (functional) stack in which each stack is a root-to-node path and its top is a pointer. Branching a stack is allocating a new tree node, not copying a stack; **rollback to any earlier state is changing a pointer — constant time**. The paper puts this to three uses: (i) checking the vocabulary in lexicographic order during preprocessing, rolling back to the longest common prefix with the previous token instead of re-walking shared prefixes (as reported, reducing characters checked across the vocabulary to 30%); (ii) jump-forward / retokenisation schemes that retract already-emitted tokens — the automaton state retracts with them; and (iii) tree-structured generation — speculative decoding in the SpecInfer line, tree-of-thought, SGLang-style branching — where each branch carries its own automaton state as its own pointer into the same tree (§5).

**Co-design with the inference engine — overlap.** Finally, the engine hides what latency remains by scheduling: mask generation is CPU work depending only on *already generated* tokens; the forward pass is GPU work depending on the same tokens. The two run concurrently and synchronise only at sampling, where the GPU applies the finished mask. Preprocessing likewise overlaps prompt prefill. If mask generation is faster than the forward pass — the regime the cache is designed to produce — its *exposed* cost is, in the paper's phrase, near zero.

## 4. Reported results — as reported, with context

All figures below are the paper's own (v3 / MLSys 2025 text, read 2026-11-15), in the paper's frame. Nothing here is a local measurement.

**Mask-generation latency (§4.1 of the paper).** Setup: Llama-3.1-8B-Instruct vocabulary; AMD Ryzen 9 7950X CPU, NVIDIA RTX 4090 GPU. Baselines: Outlines v1.0, the llama.cpp grammar engine (build b3998), and lm-format-enforcer v0.10.9 (regex-based; no CFG support). Tasks: JSON Schema and unconstrained JSON (CFG) from the JSON-mode-eval dataset; XML and a Python DSL on synthetic data. As reported: XGrammar has the lowest latency on every task — **under 40 µs per token for JSON Schema and CFG (JSON), under 200 µs for XML and Python DSL** — delivering **up to 3× speedup on JSON Schema and over 100× on CFG** against the best baseline in each case. The abstract's headline — "up to 100× speedup over existing solutions" — is this CFG mask-generation figure, not an end-to-end figure.

**End-to-end serving (§4.2).** Setup: online serving, fixed batch sizes, AMD EPYC 7R13 CPU + NVIDIA H100 GPU, Llama-3.1-8B-Instruct, mean input 139 tokens / output 53 tokens; engines compared include vLLM v0.6.3 with Outlines and llama.cpp with its built-in grammar engine, against MLC-LLM and SGLang integrated with XGrammar. As reported: XGrammar gives the best time per output token (TPOT) on both JSON Schema and CFG tasks, and "up to **80×** output token rate compared to existing solutions" in the configurations where baselines degrade most — the paper attributes the baselines' degradation at larger batch sizes to CPU grammar processing becoming the bottleneck. On the same engine (SGLang), swapping Outlines for XGrammar improves TPOT on the JSON Schema task from 44.2 ms to 6.8 ms (Llama-3.1 8B) and from 15.8 ms to 4.8 ms (DeepSeek-V2-Lite 16B MoE) in the paper's Table 1.

**Overhead when enabled (§4.2, Table 2).** MLC-LLM, Llama-3.1 8B, TPOT with vs. without XGrammar: JSON Schema, batch 1: 6.2 ms → 6.3 ms; batch 16: 9.0 ms → 9.2 ms. CFG (JSON), batch 1: 6.3 ms → 6.3 ms; batch 16: 9.0 ms → 9.1 ms. This is the evidence behind the "near-zero overhead" claim: in the low-latency, single-/small-batch regime with the overlap scheduling in place, the constraint is not measurable in TPOT at one decimal place.

**Ablation (§4.3, Table 3).** Mean mask-generation latency on CFG (unconstrained JSON), built up from an unoptimised PDA baseline: baseline 65.776 ms → + node merging 38.280 ms (1.7×) → + adaptive token mask cache 0.154 ms (248.6×) → + rule inlining 0.035 ms (4.4×) → + context expansion 0.018 ms (1.9×). The cache is, by an order of magnitude, the load-bearing optimisation; everything else is refinement around it.

**Downstream correctness (§4.4, Table 4).** Llama-3.1 8B syntactic correctness, without → with XGrammar: function calling (JSON-mode-eval) **62% → 100%**; XML code generation (synthetic) **80% → 100%**. Read precisely: 100% is *syntactic* conformance to the grammar — the guarantee working as designed — not semantic correctness of the values inside the structure.

## 5. Position in the runner stack

Constraint is a **mask on logits**, and its position in the decode step is fixed by what a mask is:

```
forward pass → logits → [GRAMMAR MASK: invalid logits := −∞] → sampler chain
              (temperature, penalties as implemented, truncation — top-k / top-p / min-p …)
              → renormalise over survivors → sample → advance automaton with the sampled token
```

The interaction rules, stated precisely:

- **Mask before sampling, never after.** Masking is a restriction of the distribution's *support*. If sampling happens first and the sampled token is then rejected and resampled (or worse, repaired), the result is not a draw from any well-defined conditional distribution, the retry loop has no termination guarantee, and the cost model collapses. Both papers in this wave define guided generation as mask-then-sample; there is no legitimate mask-after-sample design.
- **Masking renormalises over valid tokens only, preserving their relative probabilities.** Setting invalid logits to $-\infty$ before softmax (the paper's own description, §2.1) leaves the ratios among valid tokens exactly as the model produced them; softmax then renormalises over the valid set. The sampled distribution is therefore $P(\cdot \mid \text{prefix}, \text{valid})$, the model's conditional distribution over valid continuations — not a distorted or re-weighted one. This is the fidelity standard: any engine whose mask changes the *relative* odds of two valid tokens has introduced a second, undocumented sampler.
- **Relative to the Wave 9 sampler chain (`papers/min-p-sampling.md`, `papers/mirostat.md`; IDEA-LEDGER #37): the mask is a validity filter applied before truncation and temperature scaling of the surviving set.** Penalties and repetition controls shape scores; truncation (top-k / top-p / min-p) then selects a plausible subset *of the valid set*; temperature scales what survives. The ordering constraint that matters is support-before-shape: a truncator must never be allowed to spend its budget on tokens the grammar forbids, and temperature must never be able to resurrect a masked token ($-\infty$ survives any finite temperature). In implementations where temperature is folded into the logits before the mask is applied, the invariant to test is the same: masked-out means zero probability in the final categorical, and valid-token ratios are the model's. Mirostat, as a stateful controller that *replaces* the chain (IDEA-LEDGER #37's compose-or-substitute law), composes with constraint only by having its surprise target computed over the masked distribution — a combination neither paper in this wave evaluates, and one a stack should treat as untested until its own conformance vectors say otherwise.
- **The automaton state is per-sequence decode state, on a par with the KV cache.** It advances with each accepted token, it is distinct per request in a batch (XGrammar merges *parallel-parse* stacks within one sequence; it does not share state across sequences), and any mechanism that rewinds or forks the token stream must rewind or fork it too.

**The speculation interaction.** Speculative decoding (Waves 2/13: `papers/speculative-decoding.md`, `papers/specinfer.md`, `papers/eagle-2.md`) drafts several tokens, verifies them in one target pass, and on rejection *rolls back* to the last accepted token. Under constraint, verification has two judges: the target model's distribution *and* the grammar. A drafted token that the target would accept but the automaton forbids must be rejected; a drafted continuation must be checked against the automaton state *as of its position in the draft tree*, not the trunk state; and when verification truncates the draft, the automaton state must roll back to the state corresponding to the accepted prefix — no further, no less. XGrammar is, of the two designs in this wave, the one built for this: the persistent stack (§3) makes each draft branch's automaton state a pointer, branching a branch a new pointer, and rollback a pointer reset in constant time, and the paper names the speculative-decoding / SpecInfer setting explicitly as a motivating application of exactly that property. The design rule for any stack combining the two lines: *draft, mask and automaton state are one transactional unit — a token is committed only when model, sampler and automaton have all accepted it, and rollback restores all three together.*

## 6. Applicability

### (a) Ollama / llama.cpp world

*Judgment in this subsection is labelled as such; the factual baseline is the corpus's runner dossiers and the paper's own baseline choices.*

What already exists: llama.cpp ships a grammar engine (GBNF grammars, JSON-Schema-to-grammar conversion) and Ollama exposes structured output through the `format` parameter of `/api/generate` and `/api/chat` — `format: "json"` or a full JSON schema (see `runners/ollama.md`: structured outputs, December 2024). So the *feature* is present in the Go/llama.cpp-class stack. It is telling that the paper chose that built-in engine (b3998) as a baseline and beat it by the margins in §4: what the papers add to a stack that already "has grammars" is not the feature but (i) a **performance architecture** and (ii) a **correctness standard**.

Requirements language a Go/llama.cpp-class stack should adopt (judgment, argued from §§3–5):

- **R1 — Precompute the mask; do not interpret the grammar over the vocabulary per step.** The adaptive-cache principle is portable even where the full PDA design is not adopted: validity for the overwhelming majority of (state, token) pairs must be decided at grammar-compile time and stored in a compact, state-keyed structure, with per-step work proportional to the small undecided remainder, not to $|V|$. A per-step full-vocabulary grammar walk should be treated as a defect with a number attached (mask µs/token, reported beside TPOT), not as an implementation detail.
- **R2 — Compile once per (grammar, vocabulary), cache across requests.** Grammar compilation and mask-cache construction are request-independent given the model; they belong at load/first-use, keyed and reused — the same "grammar compiled once" interface IDEA-LEDGER #36 already specifies for this programme (§7).
- **R3 — Mask work lives off the decode critical path.** Overlap mask preparation for step $t+1$ with the forward pass for step $t$ (in Go: a goroutine per resident sequence, synchronising only at sampling), per the ledger's off-critical-path discipline (#25 in the ledger's numbering as cited by #36). Constraint that only fires occasionally must not tax every unconstrained token.
- **R4 — Distribution fidelity is a conformance property, not a hope.** Test vectors must pin: masked tokens have exactly zero probability; relative probabilities of valid tokens are unchanged pre-renormalisation; EOS is available exactly in accept states; tokens spanning rule boundaries (the case the paper uses against lexer-based predecessors) are judged against the full stack. A grammar engine that fails the boundary vectors is incorrect even if its JSON demos parse.
- **R5 — Automaton state is session state.** It must branch and roll back with speculative verification, jump-forward and session resume, or those features must refuse to run under constraint rather than run with a desynchronised automaton. Silent desynchronisation is the worst failure mode available here: output that *looks* constrained and is not.

### (b) The persona-chat case: constraint as the reliability floor under agent memory

Free-form persona chat should stay unconstrained — forcing a character's dialogue through a JSON grammar would be a category error, and §4's correctness table is about machine-read output, not conversation. The persona stack's *other* generations are a different matter. Every agent harness around the chat — tool calls, function arguments, and above all **memory extraction** — emits text whose next reader is a parser.

The link to the agent-memory dossier (`memory/agent-memory-architectures.md`) is direct. That dossier's central finding is that persistent-memory failures are overwhelmingly *write-side*: bad extractions, invented details, records that cannot be acted on. Its write step — "decide what, from a raw episode, becomes a persistent record, and in what form" — is in deployed systems a model call whose output is parsed into fields (fact, subject, predicate, provenance, timestamps). **A memory write that must parse is a constrained-generation problem.** Run unconstrained, the extractor occasionally emits prose around the JSON, a wrong type, a missing provenance field — and the pipeline's choices are to drop the write (memory loss), retry it (latency, cost, and a second draw from the same distribution that just failed), or parse leniently and store a degraded record (the seed of exactly the rot that dossier catalogues). Run under a schema constraint of the XGrammar class, the write is syntactically valid by construction, every required field is present and typed, and the editorial questions that *should* occupy the memory system — is this fact true, does it supersede an older one, what is its provenance — are the only questions left. Constraint does not make an extraction *true*; it makes it *well-formed*, which is the floor the editor layer stands on.

The same argument covers tool calls in a persona-agent stack (a malformed call is a failed action, not a stylistic flaw) and structured sidecar generations generally — summarisation-to-schema, classification, routing. Design rule (judgment): in an agent stack, *every generation whose consumer is code runs constrained, with the schema versioned beside the prompt that produced it; every generation whose consumer is the user runs free.* XGrammar's contribution to that rule is that it prices the constrained half at near-zero marginal cost, removing the performance excuse for leaving it unconstrained.
