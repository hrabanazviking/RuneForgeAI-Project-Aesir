## 2. The problem as framed

Serving systems are optimised against workloads that do not exist in production. The paper's framing (§§1–2 of the v3 text):

- **The evaluation gap.** Because no open LLM serving workload existed, systems were evaluated on synthetic concurrency models or on traces borrowed from *non-LLM* services — principally Microsoft Azure Functions (MAF). Those stand-ins fail in both directions at once: MAF's mean rate is far higher (1.64 RPS on average, against 0.019 RPS for BurstGPT conversation service and 0.21 RPS for API service with ChatGPT, as reported) because function calls are lightweight and non-autoregressive, while its *burstiness* is far milder. A system tuned and validated on MAF is therefore tuned for the wrong load level *and* the wrong load shape.
- **Why LLM load is its own species.** Each request's cost is set by two lengths, not one: prefill cost grows quadratically in prompt length and decode cost linearly per generated token (the paper's §2.2 statement of the $O(s^2)$ / $O(s)$ split), and the second length — the response — is unknown at arrival and decided by the model at run time. No fixed-size-job assumption survives that. Arrival behaviour compounds it: real users and automated API clients do not arrive as a smooth Poisson stream (see §4).
- **The consequence the paper demonstrates, not just asserts:** optimisations validated on unrealistic workloads do not reliably generalise — KV-cache management and request scheduling that look sound on a uniform workload degrade in efficiency, stability, or reliability under the real trace, and (§4) an optimisation that wins on one *real* service type can lose on another. The problem is therefore not "benchmarks are slightly off" but "the field's evidence base measures a different system than the one it deploys."

In one sentence: **before BurstGPT there was no public, request-level record of what LLM serving traffic actually looks like — its arrivals, its lengths, and its failures — so every serving claim in the corpus's scheduling line was, knowingly or not, conditioned on an invented workload.**

## 3. Core mechanism / method in our own words

BurstGPT is a measurement artefact, not a serving system. Its "mechanism" is a collection method, a characterisation, and a replay method.

**Collection scope (v3 text, §1).** A logging engine deployed at one regional Azure OpenAI GPT service provider — a provider serving enterprises/campuses, with over 3,000 users — recorded privacy-independent per-request metrics only: request start time, request token length, response token length, service type (API vs conversational), and model type (ChatGPT vs GPT-4). No prompt or response content is recorded. The v3 population: 4.81M ChatGPT + 0.24M GPT-4 traces via API services, and 0.16M ChatGPT + 0.08M GPT-4 via conversational services, over 121 days, including failed requests (recorded with response length zero). The v5 expansion (§1) roughly doubles this to 10.31M traces over 213 days.

**What is characterised (v3 §3; v5 abstract).** Four families of features:

1. **Concurrency / burstiness.** Long-term: conversational traffic is *periodic* (weekday and working-hours peaks, weekend and night troughs, for both models); API traffic is *aperiodic* and markedly more variable day to day — the paper's inference is that much of it is automated. Short-term: burstiness is quantified two ways — how often request volume *doubles* from one five-minute window to the next, and a Gamma-process model of arrivals refit every 20 minutes, whose shape parameter $\alpha$ (with coefficient of variation $CV = 1/\sqrt{\alpha}$; smaller $\alpha$ = burstier) *itself varies sharply within the day*, differently for conversation and API services. Burstiness is therefore not a constant of the workload; it is a time-varying property of it.
2. **Request / response length distributions and their correlation.** Request lengths follow a Zipf-like distribution (a peak of short requests, a long tail) for both ChatGPT and a Llama-2-13b-chat comparison run. Response distributions differ by model: ChatGPT's is described as bimodal / shifted-Gaussian peaking at shorter lengths with spread growing with request length; Llama-2-13b-chat's is Zipf-like with relatively more long responses. The request→response relation also differs by model: ChatGPT shows a roughly linear correlation between request and response length, while Llama-2-13b-chat's response length *decreases* and grows more variable as request length increases (the paper attributes this in part to context limits). There is no model-independent length law to design against.
3. **Conversation patterns (v5 addition).** Counts and intervals *within* conversations — the session structure above the single request — characterised for service optimisation. (Named in the v5 abstract; the v3 text read for this dossier predates this section, so no finer v5 statistic is claimed here.)
4. **Failures.** Per-service, per-model failure rates over time (§4) — a first-class part of the workload, not noise to be cleaned away (though the cleaned release does exclude failure logs; the raw release keeps them).

**Replay / use method (v3 §4).** The paper ships a benchmark suite shape: a prompt pool indexed by token length (built from a dialogue dataset such as ShareGPT), a prompt sampler drawing lengths from the trace's Zipf model, and a concurrency generator emitting arrivals either by *RPS scaling* (time-warp the vanilla trace by a factor $c$ to a target mean rate) or by *modelled scaling* (drive arrivals from the fitted Gamma parameters — $\alpha$, $\beta$ refit per 20-minute interval — and the Zipf length parameter). Metrics are reported in average *and* instantaneous forms: failure rate, token latency, latency jitter (standard deviation), and throughput. That average/instantaneous pairing is part of the method: under bursty load, averages are precisely where the damage hides.

## 4. Reported results — as reported, with context

All figures are the paper's own. Demo evaluations were run on **vLLM serving Llama-2-13b-chat on a single A800 GPU server** (64-core Intel Xeon Platinum 8358P, 1 TB host memory), unless stated otherwise. **Nothing below was measured on consumer hardware or a single-user workload.**

**Headline statistics (v3 population unless marked v5):**

- **Scale:** 5.29M traces / 121 days (v3); **10.31M traces / 213 days (v5, current)** — regional Azure OpenAI GPT services, 3,000+ users at the provider.
- **Mean rates:** conversation service ≈ **0.019 RPS**, API service ≈ **0.21 RPS** (ChatGPT) — against MAF's 1.64 RPS. Real LLM load at this provider is *sparse on average and violent in bursts*; the mean rate is the least informative number in the dataset.
- **Burstiness is time-varying:** the Gamma shape parameter $\alpha$ varies sharply during working hours in conversation service, and both $\alpha$ and $\beta$ vary sharply through the day in API service. Any single-$CV$ arrival model is a snapshot mislabelled as a law.
- **Failures are not rare:** the average failure rate of the *conversation* service is **consistently above 5% for ChatGPT** — explicitly noted as significantly higher than regular cloud services. GPT-4 shows a lower average failure rate but worse stability (more outliers) than ChatGPT in the paper's comparison; read precisely: ChatGPT fails more often on average but more steadily, GPT-4 less often but less predictably.
- **Lengths:** request lengths Zipf-distributed; ChatGPT responses shorter-peaking and request-correlated; Llama-2-13b-chat responses longer-tailed and anti-correlated at long requests (see §3). The transferable fact is the *divergence between models on identical prompts*, not either curve alone.

**Demo-evaluation findings (v3 §4.5–§4.6):**

- **Same mean rate, different system.** With BurstGPT and MAF2 scaled to the *same* 0.326 RPS (both runs completing in 6,126 s over the first 2,000 queries), BurstGPT's burstier concurrency produced higher average latency and throughput demand — i.e. higher resource occupation — and specifically stressed KV-cache management, where MAF2's uniform arrivals did not. Mean-RPS equivalence does not imply workload equivalence; this is the paper's single most quotable experiment.
- **Scheduling does not generalise across real workloads.** Comparing FCFS, short-request-first (SRF), and long-request-first (LRF) on vLLM under modelled BurstGPT: FCFS's failure rate is low on the conversation trace but turns high under the API trace's extreme burstiness; and LRF's latency/jitter advantage over FCFS on conversation service *does not hold* on API service. Even *within* real traces, an optimisation proven on one service type is unproven on the other.
- **Stated limitations (v3 §5, the paper's own):** traces come from a *single* service provider; universality across providers is not demonstrated. The trace lacks session IDs, per-session conversation counts, and response times (the v5 conversation-pattern work partially answers the session gap). Both caveats travel with every citation of the headline statistics.

## 5. Position in the corpus

**The workload-side sibling of Wave 10's methodology.** The corpus's measurement line — `papers/vidur.md` (simulation) and `papers/mlperf-inference.md` (benchmark discipline) — argues from the system side that a number is only as honest as its disclosed conditions (IDEA-LEDGER #44). BurstGPT makes the same argument from the *input* side: a scheduler, a KV policy, or a simulator evaluated on an invented arrival process has measured its own assumptions. The two halves compose:

- **Vidur needs BurstGPT-shaped inputs.** Vidur's central finding (banked in its dossier) is that the optimal serving configuration is a property of the *(model, trace) pair* — the same model's best batch size was 256 on one trace and 64 on another, with up to a 2× penalty for crossing configurations. A simulator fed Poisson arrivals and fixed lengths will faithfully optimise for a workload nobody has. BurstGPT (and traces like it) is what makes Vidur's search — and #44's rule that tuning records are keyed by workload shape — an empirical exercise rather than a parametric one. Conversely, BurstGPT's own Gamma/Zipf *modelled scaling* is a small simulator of exactly Vidur's kind: useful for sweeping scale, honest only while its fitted parameters are named.
- **MLPerf's Poisson is a disclosed convention, not a finding.** MLPerf Inference's Server scenario *defines* Poisson arrivals as its load model (see `papers/mlperf-inference.md`). BurstGPT does not refute MLPerf — a standardised synthetic load is a legitimate yardstick — but it prices the convention: conclusions drawn under Poisson (including FastServe's own evaluation, §5 of the sibling dossier) inherit the gap BurstGPT measured between Poisson/uniform load and real load at equal mean rate. #44's disclosure set already requires naming the workload profile; BurstGPT is the evidence for why that line is load-bearing rather than bureaucratic.
- **It retroactively conditions the whole scheduling line.** Orca, Sarathi-Serve, DistServe, Llumnix, and the Dynamo/llm-d routing dossiers all report gains under stated synthetic or dataset-derived loads (Poisson arrivals over ShareGPT/arxiv-style length distributions, in the main). BurstGPT does not invalidate their mechanisms — head-of-line blocking, stalls, and interference are real at any arrival process — but it demotes their *magnitudes* to workload-conditional claims, and its scheduling-non-generalisation result (§4) is the direct warning: FCFS-vs-SRF-vs-LRF rankings flipped between two real service types from the *same provider*.
- **Its FastServe connection is literal.** BurstGPT's Table 1 uses FastServe's synthetic workload as a comparison column (request/response lengths present, real concurrency and failures absent), and its related-work framing names FastServe's MLFQ as an optimisation "not yet evaluated on real-world workloads." Wave 28's pairing is therefore the papers' own: FastServe proposed a queueing discipline for a workload shape it had to invent; BurstGPT, a year later, published the shape.

## 6. Applicability

### (a) A personal runner: one user, queueing mostly evaporates — the *shape* knowledge survives

With one user there is no arrival process to characterise and no concurrency to provision for; BurstGPT's fleet statistics (RPS, failure rates, Gamma parameters) do not transfer and must not be quoted locally. What transfers is the *shape* of the load a single user actually generates when the runner does more than one thing — and a personal chat runner does: the visible turn, plus app-generated sidecars (memory extraction, summarisation, title generation, embedding calls), plus multi-persona scenes, plus the user's own rapid-fire follow-ups and regenerations. That composite load is bursty and heavy-tailed in miniature: long silences, then three requests inside a second; mostly short turns, occasionally a 14,712-token paste (the corpus's recorded baseline event). Testing that behaviour with uniform prompts at uniform intervals — the local equivalent of MAF — will certify a system that production-shaped local load then surprises.

Concretely, as a testing discipline (labelled **proposal**, not a paper result):

- **Local multi-session benchmarks should use bursty, heavy-tailed synthetic loads**: arrivals clustered (a burst model, not a metronome), prompt lengths drawn from a Zipf-like mix dominated by short turns with a real long tail, and output lengths allowed to vary by an order of magnitude — because the properties under test (admission, fairness, KV pressure, failure behaviour) only exist when the load has variance.
- **Report average *and* instantaneous behaviour**, following the paper's metric pairing: a local runner that holds its mean latency while its worst burst collapses (KV exhaustion, a shed sidecar, a stalled stream) is BurstGPT's demo finding reproduced at desk scale.
- **Include failures in the test, not just the trace:** the paper's >5% conversation failure rate is a fleet number, but its *mechanism* — burst-driven KV pressure converting directly into failed requests — is scale-free. A local load test that never drives the card into KV pressure has not tested the failure path at all.

This ties directly to **IDEA-LEDGER #44's disclosure set** (checked in the banked ledger, §7): a local capacity or latency claim must name its *workload profile* (prompt/output split) and *machine state* — BurstGPT adds the missing half of that line: the *arrival shape* belongs in the profile too. A claim measured under uniform arrivals should say so, in the same way #44 requires a single run to be labelled a single run.

### (b) Trace-driven honesty as a standing rule

**Proposal, labelled as such:** any future local capacity claim — "the runner sustains N concurrent sessions", "persona B's turn never waits more than X" — should name its workload shape in one breath with the number: arrival pattern (bursty/uniform), length mix (median and tail), and which sidecars were running. BurstGPT's contribution to the corpus is ultimately this norm, with data behind it: the mean rate is not the workload, the workload is the distribution — of arrivals, of lengths, and of their variation over time. The cheapest version of the norm costs nothing: never publish a local serving number whose load was a single repeated prompt at a fixed interval without labelling it exactly that.
