## 2. The problem as framed

Offloading solves the capacity problem and creates a latency problem. If the KV cache lives in CPU memory, a model can generate contexts far beyond GPU memory — but in a naive offloading system, *every layer of every generated token* needs the keys and values of all previous tokens, so the full cache (or the full per-layer slice of it) must cross PCIe before attention can run. Transfer stops being an occasional cost and becomes the serial bottleneck of decode itself: the paper's latency breakdown (§6.2) measures data transfer at **96.9% of a Transformer block's execution time** for the FlexGen baseline and 91.8% even for H2O-on-FlexGen. The GPU is idle waiting on the bus; adding capacity via offloading has been paid for with throughput.

The obvious escapes each fail in a characteristic way, and the paper uses them as its baselines: fetch everything in lower precision (INT4 quantisation) — the bytes shrink by a fixed factor but still grow linearly with sequence length and batch, so speedups saturate; or permanently prune the cache to a fixed budget of "important" tokens (H2O) — the fetched set stops growing, but importance is judged once and tokens discarded early can become important again later (the paper demonstrates attention-weight spikes for tokens that were negligible for thousands of iterations, §6.3), so accuracy diverges as generation proceeds. InfiniGen's framing: the fetch set should be **re-decided per layer, per token, from a prediction of the attention pattern that layer is about to compute** — and the prediction is cheap enough to make one layer ahead, while there is still time to move the data.

## 3. Core mechanism in our own words

InfiniGen keeps the *entire* KV cache in a CPU-memory pool — nothing is permanently discarded by the prefetch path — and, for each layer during decode, speculatively computes which entries that layer will actually need, then prefetches only those to the GPU. Four pieces make that work:

**The signal — cross-layer input similarity, weaponised by outliers.** Consecutive Transformer blocks receive highly similar inputs: because of residual connections, block *i*'s input is dominated by block *i−1*'s input (measured cosine similarity 0.89–0.97 across OPT-6.7B/13B/30B and Llama-2-7B/13B, vs ~0.3 for the attention/FFN outputs), an effect the paper attributes to fixed outlier channels surviving LayerNorm while the per-layer increments stay small. Therefore the attention input already available at layer *i−1* is a good proxy for the query layer *i* is about to form — good enough to *rehearse* layer *i*'s attention cheaply and read off its pattern before layer *i* runs.

**Making the rehearsal cheap — offline skewing + partial matrices.** A full rehearsal would cost as much as the layer itself, so InfiniGen rehearses with a *partial* computation over ~30% of the dimensions — and makes 30% sufficient by restructuring the model offline. Query and key weight matrices are multiplied by a shared orthogonal matrix *A* (per layer, derived from an SVD of a sample forward pass's query matrix: *A* = **V**). Because *A·Aᵀ = I*, the true attention scores are *mathematically unchanged* — skewing is exact, not an approximation — but the skewed Q/K concentrate their magnitude into a few columns, so the top columns carry a representative share of every dot product. During prefill, InfiniGen selects those top-*k* columns (30% in the paper, chosen by summed absolute column magnitude over skewed Q and K jointly) and materialises a **partial query weight** and a **partial key cache** for each layer, held on the GPU (reported overhead at ratio 0.3: partial weights ≈2.5% of model parameters, partial key cache ≈15% of the full KV cache).

**The fetch set — thresholded speculation, dynamically sized.** At layer *i−1* of decode, the rehearsal multiplies layer *i−1*'s attention input by layer *i*'s partial query weight and partial key cache, producing *speculated* attention scores for layer *i*. The fetch set is every token whose speculated score exceeds **max_score − α** (α = 4 for OPT, 5 for Llama-2 in the evaluation; after softmax, a token α=5 below the max carries <1/148 of the top token's weight, which is the paper's justification for the cut). Head counts are averaged across heads so all heads fetch the same number. The set is therefore *not a budget*: it grows or shrinks with the actual attention distribution — measured important-token counts of 37 / 60 / 66 / 73 at sequence lengths 512 / 1024 / 1536 / 2048 (OPT-13B), sub-linear in length, versus H2O's fixed 20% (= 409 tokens at 2048). A safety cap allows at most 20% of the cache per layer. On average **under 10% of the KV cache is fetched per layer**. Speculation starts at Layer 1 (outliers emerge in Layer 0). The prefetched entries are used for the real attention at layer *i* and then *ephemerally pruned* — dropped from the GPU, not from the CPU pool.

**Overlap and fallback.** The rehearsal at layer *i−1* runs while layer *i−1*'s own computation proceeds, and the selected entries are transferred so that they arrive for layer *i* — prediction and transfer are folded into the previous layer's compute window rather than serialised before layer *i* (the paper's block breakdown shows FFN time fully overlapped with transfer in the non-baseline schemes). **On a prediction miss there is no corrective re-fetch described**: a token the rehearsal underrates is simply absent from that layer's attention for that token — the design's answer is statistical, not transactional: α is tuned so missed tokens carry negligible softmax weight, the full entry remains in the CPU pool and can be selected at the next token or layer, and the accuracy evaluation (§4) is the evidence that the residual error is small. This is the honest structural fact a runner engineer must hold: InfiniGen trades a bounded-by-tuning approximation inside attention for transfer volume; it is not exact inference with better scheduling. Separately, the CPU pool itself is capacity-managed: under a user-set memory limit, a **counter-based eviction** (increment on each prefetch; evict the least-fetched; halve all counters on saturation) removes entries permanently — reported at parity with LRU on perplexity and far better than FIFO — but that is pool pressure management, not the prefetch path.

## 4. Reported results — as reported, with hardware context

All figures are the paper's own; nothing below is re-derived.

- **Testbed:** single **NVIDIA RTX A6000 (48 GB)**, Intel Xeon Gold 6136 CPU, **96 GB DDR4-2666**, **PCIe 3.0 ×16** CPU↔GPU interconnect — a deliberately ordinary bus, which is the point. Implemented on FlexGen; baselines are CUDA UVM (implicit paging), UVM+H2O, FlexGen full-FP16 fetch, FlexGen+INT4 (4-bit group-wise asymmetric quantisation), and FlexGen+H2O (20% budget). Models: **OPT-6.7B / 13B / 30B, Llama-2-7B / 13B** (plus Llama-2-7B-32K and a Llama-3-8B-1048K analysis in §6.3). Settings: partial ratio 0.3, α = 4 (OPT) / 5 (Llama-2), <10% of KV fetched on average, 20% per-layer cap.
- **Headline (abstract / introduction):** up to **3.00× speedup over prior KV cache management methods** on a modern offloading system, with up to a **32.6 percentage-point accuracy increase** over those methods at comparable cache usage.
- **Latency detail (§5.3):** on OPT-13B, 1920 input + 128 output tokens, batch 20, InfiniGen achieves **1.63×–32.93× speedups over the baselines** in end-to-end latency (the wide range spans the very slow UVM baselines at the top end). Across batch sizes 1–20 the range is **1.28×–34.64×**, with the gap *widening* in batch; throughput from batch 4→20 rises 27.36→41.99 tok/s for InfiniGen vs 12.22→14.02 (INT4) and 21.31→25.70 (H2O).
- **Scaling vs FlexGen (§5.3):** speedup grows with sequence length to **5.28×** (OPT-13B, batch 8, total lengths 512→2048) while INT4 saturates at 1.92× and H2O at 3.40×; grows with model size from 6.7B→13B, and at OPT-30B — where 30% of *parameters* are also offloaded, 1.7× larger than the KV cache — InfiniGen still leads at 1.34× vs FlexGen (INT4 1.18×, H2O 1.28×).
- **Distance from ideal (§6.2):** InfiniGen runs at **1.52× the latency of an "Ideal" all-on-GPU no-transfer oracle**; the baselines sit at 3.90×–18.55×.
- **Accuracy:** on five 5-shot lm-evaluation-harness tasks (COPA, OpenBookQA, WinoGrande, PIQA, RTE), at relative KV usage <10% InfiniGen holds accuracy where INT4 and H2O drop noticeably; above 10% it matches the full-cache baseline and occasionally exceeds it slightly. Perplexity on WikiText-2 / PTB (OPT-13B, Llama-2-13B, 256-token chunks) stays at the full-cache level as generation proceeds, while H2O at the same fetched volume diverges chunk over chunk. With the CPU pool capped at 80%, counter-based and LRU eviction reproduce the uncapped perplexities exactly in the reported table (e.g. OPT-13B WikiText-2 10.55 in all three rows); FIFO collapses (30.99).
- **Skewing ablation:** with a fixed 20% budget on OPT-6.7B, removing the SVD skewing causes a large accuracy drop on the harness tasks; with skewing, accuracy is at the full-cache level. (Llama-2 models are reported as less sensitive to its removal.)
- **Long-context (§6.3):** on Llama-2-7B-32K / WikiText-2, InfiniGen's perplexity stays near the full-cache baseline even as the relative fetched size shrinks, where quantisation and H2O diverge; the 1M-token analysis (Llama-3-8B-1048K) shows the fraction of queries attending to <1% of keys *grows* with length — the trend InfiniGen's dynamic sizing exploits and fixed budgets cannot.

## 5. Position vs Wave 3 — selection and scheduling of movement, not compression

InfiniGen contains no codec. Nothing is quantised, delta-coded, or entropy-coded; every byte that crosses PCIe is a full-precision KV entry, and every byte that stays behind stays at full precision in the CPU pool. What InfiniGen optimises is **which bytes move, and when**: a per-layer, per-token selection (the rehearsal's fetch set) plus a schedule (decide at layer *i−1*, transfer into layer *i*'s window). It belongs on the movement axis of the corpus's KV map, orthogonal to Wave 3's storage axis:

- **Versus KIVI/KVQuant (Wave 3, compression in place):** those shrink *every retained entry* so more fits at rest; InfiniGen shrinks *the working set per layer* so less travels. The objective functions differ (capacity vs transfer volume per token-step), and they compose: nothing in InfiniGen forbids the CPU pool holding KIVI-format entries and dequantising on arrival — the paper instead compares against INT4 as a rival, and INT4's saturating speedup is its evidence that shrinking bytes alone loses to shrinking *trips* once sequences lengthen. A corpus reader should not generalise that into "selection beats compression" universally: INT4-on-FlexGen still fetches *all* tokens every layer; a compressed *and* selected scheme was not evaluated.
- **Versus SnapKV/PyramidKV (Wave 3, selection in place):** this is the true kinship, and the difference is precise. SnapKV also reads an attention pattern to decide which tokens matter — but it decides *once, at prefill, from an observation window*, and the decision is a permanent eviction from a cache that lives and dies in VRAM. InfiniGen decides *repeatedly, during decode, one layer ahead of use*, from a rehearsal of the very layer being predicted, and the decision is **ephemeral**: unselected entries are not evicted, merely not fetched this time; they remain in the CPU pool and the paper's spike analysis (§6.3) is precisely the demonstration that this reversibility is worth accuracy that permanent pruning cannot recover. PyramidKV's layer-varying budgets are the static cousin of InfiniGen's dynamic per-layer fetch counts. One sentence for the map: **SnapKV selects what the cache *is*; InfiniGen selects what the cache *sends* — selection within a cache versus selection across a bus.**
- **Versus H2O specifically:** H2O appears in this paper as a baseline, not a relative — same heavy-hitter intuition, opposite permanence. InfiniGen's measured perplexity stability over long generations, against H2O's divergence at equal fetched volume, is the corpus's cleanest evidence for ephemeral-over-permanent selection when a backing tier exists to be reversible *into*.

## 6. Applicability

### (a) Single machine — tiered KV on a 6 GB card + system RAM

InfiniGen is *already* a single-machine paper: its "network" is PCIe 3.0 ×16 between one CPU and one GPU, its pool is ordinary system RAM. Collapsing the fleet to one box changes nothing structural — which makes it, of the movement papers, the one whose setting most literally matches the corpus's target hardware (a 6 GB consumer card backed by system RAM, with NVMe below that). The tiered-KV design in `memory/kv-cache-design.md` needs a promote policy for RAM→VRAM; InfiniGen is a complete, evaluated candidate for that policy: keep the full cache in RAM, promote per layer only the rehearsal-selected entries, demote by simply dropping the GPU copies.

The implementability judgement must nonetheless be split, and labelled as judgement:

- **The policy is portable; the machinery is not free.** A ggml-class backend today computes attention layer-by-layer with the cache resident wherever the graph placed it. InfiniGen requires: (i) the cache's canonical home moved to CPU memory with fine-grained per-token gather over PCIe; (ii) a rehearsal pass interleaved into decode — an extra partial QK product per layer per token, plus the bookkeeping to launch async transfers a layer ahead; (iii) offline SVD skewing of Q/K weights per layer and per-prefill partial-matrix construction; (iv) attention kernels that consume a *gathered subset* whose membership changes every token. Items (ii)–(iv) are real kernel and scheduler work — not "heroics" in the research sense (the paper's own implementation is a FlexGen modification, and the rehearsal arithmetic is small: a 30%-width QK product), but well beyond a configuration change, and the subset-attention path fights the paged/block-contiguous layouts ggml-class backends rely on for speed. **Labelled judgement: CacheGen (companion dossier) is the realistic first implementation for a ggml-class backend — batch codec at tier boundaries, no attention changes. InfiniGen is the realistic *second* step, and only for the specific regime where its paper shows it winning: long contexts and large batches under offloading, where transfer is measured at >90% of block time.** On a 6 GB card running one chat at moderate length, transfer volume is far smaller, batches are 1, and the rehearsal + gather overhead can plausibly eat the win — the paper offers no batch-1, short-context evidence to the contrary, and its own speedups grow with exactly the dimensions a single-user runner lacks.
- **What to steal immediately, without the machinery:** the *reversibility principle* (§5) — never permanently evict what a cheaper tier can hold; eviction decisions in a tiered runner should be demotions, with promotion re-decided per use. And the *measurement*: before building any of this, instrument the local runner for transfer share of block time; InfiniGen's 96.9% FlexGen figure is the threshold logic — prefetch machinery is justified only when the local number is anywhere near that regime.

### (b) Aesir's snapshot work — KV in motion across time

Snapshots move KV across *time* (write now, restore later) rather than across a bus during decode, so InfiniGen's mechanism has no direct snapshot analogue: there is no "next layer" to rehearse against at restore time, and a restore wants the *whole* state, not a predicted subset — the corpus's bit-exact position for session snapshots is untouched by anything in this paper, and InfiniGen itself never alters the stored bytes it manages (its pool is full-precision; only its *fetches* are selective).

The transferable idea is one step removed, at *restore scheduling*: a bit-exact snapshot need not be restored *atomically*. A session restored from RAM/SSD could be made live progressively — restore the layers/state the first generated tokens will touch first, stream the remainder in behind ongoing decode, rehearsal-style — converting restore latency from a single blocking transfer into overlapped background motion, with zero change to the stored format or its exactness. That is a scheduling property, fully compatible with the bit-exact contract, and it is the honest extent of InfiniGen's relevance here: **it teaches Aesir how to *schedule* a snapshot's return, not how to *represent* it.** (For the representation question — whether lossy compression may touch snapshots — see the CacheGen dossier §6(b): the corpus position stands; loss belongs, if anywhere, in labelled derived artefacts at the pool layer.)
