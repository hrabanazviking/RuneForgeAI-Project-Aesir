## 2. The problem as framed

EAGLE (wave 2) already drafts as a **tree** and verifies the tree in one target pass with tree attention. But the tree's *shape* is fixed in advance: at drafting step *i*, a preset number *k* of candidates is added at every position, in every context, for every prompt. Medusa's sparse tree has the same property, and Sequoia (Chen et al., 2024, cited in the paper) makes the underlying assumption explicit: that a draft token's acceptance rate depends **only on its position in the tree**.

EAGLE-2's opening move is to measure that assumption and show it is half true. On the Alpaca dataset with Vicuna 7B (the paper's §3.1), acceptance rate *is* position-dependent on average — highest at the shallow/early positions of the static tree, lowest at the deep/late ones, which retroactively justifies the static tree's taper. But at **any single position, acceptance varies widely across contexts**: the same slot that is nearly always accepted after one prefix is nearly always rejected after another. Position is a prior; context is the evidence; a static tree can only ever spend its verification budget according to the prior.

The cost of that blindness is concrete, and the paper's Figure 4 example is the crisp statement of it: after "10+2=", the next token is almost certainly "1" — a static tree nevertheless spends a second candidate slot on an implausible alternative ("3"), verification budget burned on a branch that will essentially never be taken. After "10+2" (no equals sign), the next token is genuinely uncertain, and there two candidates are worth their slots. A static tree gives both contexts the same shape. It therefore **wastes verification budget on low-confidence branches in easy contexts and starves high-confidence continuations in hard ones** — and because the total number of draft tokens per verification pass is capped (each one costs verifier work), every wasted slot is a slot a productive branch did not get. The problem EAGLE-2 sets itself: reshape the tree *per step, per context*, spending the fixed verification budget where acceptance is actually likely — without querying the target model to find out where that is, since querying the target is the cost the whole scheme exists to avoid.

## 3. Core mechanism in our own words

EAGLE-2 changes **only how the draft tree is constructed**. The drafter (EAGLE's single trained Autoregression Head, autoregressing in feature space with shifted-token conditioning — `papers/eagle.md` §3), the verification pass (tree attention over the tree in one target forward), and the acceptance rule (speculative sampling's min(1, *p*/p̂) with residual resampling) are all inherited **unchanged**. The paper states this scope itself: EAGLE-2 "does not alter the training and inference of the draft model, nor does it affect the verification stage. Its improvements focus on two aspects: how to expand the draft tree and how to rerank draft tokens." No additional training of any kind is required — an existing EAGLE checkpoint becomes an EAGLE-2 drafter by changing the tree-construction code around it.

The mechanism rests on one empirical finding (§3.2 of the paper): **EAGLE's draft model is well-calibrated — its confidence score is a good approximation of a draft token's acceptance rate.** Measured on Alpaca with Vicuna 7B: draft tokens with confidence below 0.05 are accepted at a rate of ≈ 0.04; tokens with confidence above 0.95 at ≈ 0.98; the curve tracks the diagonal closely in between. Confidence is free — the draft model emits it as a by-product of drafting — so acceptance probability can be *estimated per node, per context, at zero target-model cost*. That estimate is the signal the static tree lacked.

**Value.** A node deep in the tree is accepted only if *every* ancestor is accepted first (rejection discards the whole subtree below it). So the quantity that should rank nodes is not local confidence but the **global acceptance probability of the whole path**: the paper defines a node's *value* Vᵢ as the product of the acceptance rates along the path from the root to that node, approximated by the product of the draft confidences along the same path:

> Vᵢ = ∏ pⱼ ≈ ∏ cⱼ  over tⱼ ∈ Path(root, tᵢ)

Value is monotonically non-increasing down any path (each factor ≤ 1), which turns out to matter for the reranking step's correctness.

**Expansion phase — grow where value is high.** Drafting proceeds layer by layer. Naively expanding every node in the current layer makes layer sizes grow exponentially and slows the draft model's own forward passes. Instead: score every node in the latest layer by value, take the **top-*k* highest-value nodes**, and feed only those into the draft model for the next layer. Tree attention lets the draft model process those selected nodes in a single forward pass and emit their candidate children, which are attached to the tree. Easy contexts concentrate expansion on the one confident continuation (deep, narrow growth); hard contexts spread it across genuinely competing branches (shallower, wider growth). The tree's shape is now an output of the context, recomputed at every drafting step.

**Reranking phase — spend the verification budget on the globally best nodes.** Expansion optimises for *depth*, but its by-product is a tree whose nodes are not globally ranked: a shallow node that was never selected for expansion can still hold a higher value than a deep node that was. So before verification, EAGLE-2 pools **all** nodes in the grown tree, reranks them by value, and keeps only the **top-*m*** — *m* being the verification budget (total draft tokens per pass; see §4 for the paper's settings). Two details make this sound: because a child's value never exceeds its parent's, the top-*m* set is automatically ancestor-closed — it is still a connected tree containing the root, never a set of orphaned deep nodes whose prefixes were cut; and ties in value are broken in favour of *shallower* nodes, reinforcing the same property. The selected nodes are then flattened into a one-dimensional sequence, an **ancestor-only attention mask** is built from the tree structure (each token sees exactly its ancestors plus the verified prefix — the same tree-attention contract as Medusa/EAGLE/SpecInfer), positional indices follow depth in the tree, and the flattened tree goes to the target for the single verification pass.

**Losslessness.** Because neither the acceptance rule nor the target model is touched — no relaxed acceptance, no fine-tuning of the target, no change to the sampling distribution — EAGLE-2 inherits speculative sampling's exactness guarantee in full: the generated text distribution is provably identical to vanilla autoregressive decoding, at temperature 0 and temperature 1 alike. The paper is careful to compare, in its headline figures, only against methods that preserve the distribution on the same terms (noting that Medusa's non-greedy mode relaxes acceptance and is therefore excluded from the lossless comparison).

## 4. Reported results — as reported, with hardware/model context

All figures are the paper's own; nothing is re-derived. **Targets:** Vicuna 7B / 13B; LLaMA2-Chat 7B / 13B / 70B; LLaMA3-Instruct 8B / 70B. **Tasks (six):** MT-bench (multi-turn conversation), HumanEval (code generation), GSM8K (mathematical reasoning), Alpaca (instruction following), CNN/Daily Mail (summarisation), Natural Questions (question answering). **Baselines:** vanilla autoregressive decoding (= 1.00×), standard speculative sampling (SpS; Vicuna-68M draft for the Vicuna series), PLD, Medusa, Lookahead, Hydra, EAGLE. Comparisons run through **Spec-Bench**; the paper states that speedup ratio is hardware-dependent and that all methods were therefore tested **on the same devices** — the GPU model for the main tables is **not named in the paper text** (an honest gap in the record; the numbers should be cited as same-device relative speedups, not as tied to a specific card). **Metrics:** speedup ratio vs vanilla, and average acceptance length τ (tokens generated per drafting–verification cycle; hardware-independent, but blind to draft overhead — the paper says both things itself). **EAGLE-2 tree settings (Appendix A):** total draft tokens per verification pass **60** (7B/8B targets), **50** (13B), **48** (70B); draft tree depth **6**; **10** nodes selected per expansion step.

**Headline (abstract):** speedup ratios **3.05×–4.26×**, which is **20%–40% faster than EAGLE-1**, with the output distribution unchanged. The introduction widens the range across all experiments to **2.5×–5×**, and notes that on MT-bench EAGLE-2 is approximately **2× faster than Medusa** and **2.3× faster than Lookahead**.

- **MT-bench spot values** (the comparison the paper's figures headline): Vicuna 7B at temp 0 — EAGLE-2 **3.62× / τ 4.98** vs EAGLE 2.90× / 3.94; at temp 1 — **3.05× / 4.28** vs 2.13× / 3.17. The dynamic tree's τ advantage (~+1.0 token/cycle on this cell) is the mechanism working as designed: same drafter, same per-token acceptance rate (the paper notes the acceptance *rate* is unchanged — EAGLE-2 does not modify the draft model), more of the verification budget landing on acceptable nodes.
- **Large / newer targets (Table 2, MT-bench, temp 0):** LLaMA2-Chat 70B — EAGLE-2 **3.51× / 4.48** vs EAGLE 3.01× / 3.81; LLaMA3-Instruct 70B — **3.29× / 4.16** vs 2.83× / 3.62; LLaMA3-Instruct 8B — **3.46× / 4.53** vs 2.72× / 3.65.
- **Task pattern:** code generation (HumanEval) is the peak, as everywhere in this family — up to **5.00× / τ 5.52** (LLaMA2-Chat 13B, temp 0) and 4.96× / 5.41 (Vicuna 13B, temp 0). Summarisation and QA are the weakest tasks for all head-based methods (EAGLE-2 included), which the paper attributes to draft training data: EAGLE-family drafters are trained on SFT data only, while SpS's draft also saw pretraining data — world-knowledge QA and summarisation live disproportionately in the pretraining distribution. Even there, EAGLE-2 remains ahead of SpS.
- **Per-cycle yield:** across datasets and targets, one EAGLE-2 drafting–verification cycle generates **≈ 4–5.5 tokens**, roughly twice standard speculative sampling and Medusa (paper §5.1).

**Ablation (Table 3; Vicuna 7B, temp 0; MT-bench / GSM8K):**

| Variant | MT-bench | GSM8K |
|---|---|---|
| Without value *and* without reranking (≈ static behaviour) | 2.81× / 3.92 | 2.85× / 3.93 |
| Without value (expand by raw confidence) | 3.21× / 4.39 | 2.93× / 3.96 |
| Without reranking | 3.48× / 4.86 | 3.50× / 4.85 |
| **Full EAGLE-2** | **3.62× / 4.98** | **3.63× / 4.97** |

Both components pay, and they pay differently: the *value* (path-product) ranking is worth more than reranking on GSM8K (3.63× vs 2.93× without it — ranking by local confidence alone badly misprices deep nodes, whose true acceptance requires all ancestors to survive), while on MT-bench reranking is the smaller but still real term (3.62× vs 3.48×). The "without both" row is the honest control: strip the dynamics and you are back at EAGLE's static-tree numbers, confirming the entire EAGLE→EAGLE-2 delta is tree *construction*, not a better drafter.

## 5. Position in the family

EAGLE-2 is the **draft-side generalisation** of the tree idea, and its lineage is best stated as a sequence of single, separable moves:

- **Leviathan et al. / Chen et al. (2023, wave 2)** — draft a **chain**, verify in one pass, rejection-sample for exactness. No tree anywhere.
- **SpecInfer (2023, this wave's companion)** — generalise the *verifier*: organise candidates from one or several small models into a **token tree**, verify the whole tree in one pass with tree attention and a topology-aware mask, and extend the exactness proof to trees (multi-step speculative sampling). Its expansion configuration, however, is a **static preset** ⟨k₁,…,kₘ⟩, and the paper explicitly leaves dynamic expansion as future work. SpecInfer generalises *what verification can accept*; it does not decide, per context, *what is worth proposing*.
- **Medusa (2024, wave 2)** — draft from parallel heads; candidate set is a tree by combinatorics, pruned to a **static sparse tree** whose shape is fixed from calibration-set accuracies (position statistics, averaged over a dataset — exactly the prior-only information EAGLE-2 shows to be insufficient).
- **EAGLE (2024, wave 2)** — draft by autoregressing the target's **features** with a single trained head and shifted-token conditioning; verify over a **static tree** (fixed candidates per step). EAGLE changes *what the drafter predicts*; the tree it predicts into is still one-size-fits-all-contexts.
- **EAGLE-2 (2024, this dossier)** — keep EAGLE's drafter, verifier, and acceptance rule **exactly**; make the **tree itself dynamic**: confidence-calibrated, value-ranked expansion and reranking rebuild the tree's shape at every step from the current context. It is the direct fulfilment of SpecInfer's deferred problem, solved on the draft side rather than the verifier side.
- **EAGLE-3 (2025, wave 2)** — adopts EAGLE-2's dynamic tree **wholesale and unchanged**, and changes the *other* components instead (below).

**Precisely what EAGLE-2 does and does not change:**

- *Relative to EAGLE:* it changes **tree construction only** — expansion becomes value-guided top-*k* selection instead of fixed-shape filling, and a reranking pass imposes a global top-*m* budget by value. It does **not** change the draft model (same Autoregression Head, same weights — no retraining, no extra model), does **not** change feature-level autoregression or shifted-token conditioning, does **not** change training data or objectives, and does **not** change verification (same tree-attention pass, same speculative-sampling acceptance, same losslessness). An EAGLE deployment upgrades to EAGLE-2 in software alone.
- *Relative to EAGLE-3:* EAGLE-3's contributions are disjoint from EAGLE-2's. EAGLE-3 **removes** the feature-prediction constraint (the drafter predicts tokens directly; the regression loss is deleted), **fuses low/mid/high target features** as drafter input instead of the top-layer feature alone, and adds **training-time test** (unrolled training on the drafter's own outputs) — none of which exists in, or is anticipated by, EAGLE-2. Conversely, EAGLE-3 introduces **no** tree-construction idea of its own: the dynamic tree it verifies over *is* EAGLE-2's. The clean statement for the compendium: **EAGLE-2 = EAGLE's drafter + dynamic tree; EAGLE-3 = EAGLE-2's dynamic tree + a new drafter.** (Chronology confirms the dependency direction: EMNLP 2024 precedes EAGLE-3's March 2025 arXiv submission.)
- *Relative to SpecInfer:* complementary halves. SpecInfer's tree is built from *independent small models* (with an ensemble/boost-tuning story) and verified by machinery SpecInfer designed; EAGLE-2's tree is built from *one feature-level head* and verified by the same tree-attention contract. Nothing in EAGLE-2's value ranking is specific to EAGLE's drafter in principle — any drafter emitting calibrated confidences could drive it — but the paper demonstrates it only on EAGLE, and its calibration evidence (§3.2) is an EAGLE-drafter measurement, not a general theorem about draft models.

## 6. Applicability

### (a) A 6 GB personal runner — dynamic shape helps, datacentre budgets do not transfer

*[Engineering judgment, labelled as such; the paper's speedups are same-device relative numbers on unnamed hardware and are not imported as expectations.]*

Two halves of EAGLE-2 pull in opposite directions on a small card, and they should be judged separately.

**The dynamic shape itself is *more* valuable at 6 GB, not less.** The corpus's rule for this workload — decode is streaming, and verification width spends the same bandwidth budget — means the scarce resource a tree consumes is precisely what EAGLE-2 rations. A static tree spends its fixed node budget identically on the "10+2=" steps (where one branch suffices) and the genuinely uncertain steps (where branching pays). A value-ranked tree automatically runs *narrow and deep* through predictable stretches — which, in single-user chat, is most stretches: names, forms of address, formulaic transitions, quoted structure — and only widens where the draft model itself reports uncertainty. That is the correct shape for a bandwidth-bound card: the average verified-node count per accepted token falls, so the same τ costs less verifier work. If tree verification is ever adopted locally (see §6b on what that costs), EAGLE-2-style construction is the only version worth adopting; a static 60-node tree on a 6 GB card would be a datacentre habit transplanted to hardware that cannot afford it.

**The paper's budgets are datacentre budgets.** EAGLE-2 verifies **48–60 draft tokens per pass** at depth 6. On the paper's serving-class hardware that pass is still dominated by one weight-streaming, so 60 positions ride nearly free. On a 6 GB consumer card the per-position costs — attention over a long accumulated chat context for every tree node, KV writes for every node, a 60-wide LM-head/logits computation — stop being rounding errors well before node 60, and each widening step is paid from the same bandwidth that makes speculation worthwhile at all. The companion dossier's verdict (`papers/specinfer.md` §6a) applies unchanged: **the paying region locally is narrow trees — total verified nodes in the low tens at most, breadth 2–3 where breadth exists — with EAGLE-2's value ranking used to *choose* those few nodes well, rather than to fill a 60-node budget dynamically.** Depth is the cheap direction on small hardware (deep nodes reuse one path's KV and mostly ride the confident stretches); breadth is the expensive one. A sensible local configuration inverts the paper's proportions: depth ~5–6 as published, total nodes ~10–20, expansion top-*k* small — with the node budget treated as a measured knob (tokens/s vs budget on the user's card and context length), exactly as the SpecInfer dossier prescribes. The drafter side, by contrast, transfers cleanly: EAGLE-2 adds **zero** resident weights over EAGLE (no extra model, no retraining), so the residency arithmetic of `papers/eagle.md` §7a (~0.24B trained parameters for a 7B target) is EAGLE-2's arithmetic too — the constraint is purely the verifier's per-step width, never the tree logic's memory.

One honesty note on calibration: the confidence≈acceptance evidence is measured on EAGLE's head, on Alpaca, against Vicuna 7B. A local deployment on a different target/drafter pair (or a GGUF-quantised backbone shifting the feature distribution the head was trained against) should re-measure the calibration curve before trusting value ranking — if confidence is miscalibrated for *this* pair, the dynamic tree will confidently misallocate its budget, and a static tree (or a chain) can beat it. The failure is graceful (output stays exact; only speed suffers), but it is a real precondition, not a detail.

### (b) Ollama's existing n-gram/draft landscape — what adoption would actually require

As documented in the corpus (`runners/llamacpp-ggml.md` §8.4; `runners/ollama.md` §6.3/§9 D3; IDEA-LEDGER #15/#26/#27/#28), today's shipped landscape is chain-shaped throughout: the **n-gram/prompt-lookup free floor** (#15 — no weights, no training, the default accelerator), **draft-simple** (small same-family GGUF, #26), **draft-mtp** (embedded heads, #28), and **draft-eagle3** (a trained EAGLE-3 head per target family, #27) — with Ollama itself exposing only the draft-model and MTP controls. Two facts about that landscape frame EAGLE-2's adoption cost:

1. **The tree substrate is the price; EAGLE-2's own logic is nearly free.** Everything EAGLE-2 adds over EAGLE is host-side bookkeeping: confidence products along paths, top-*k*/top-*m* selection, mask construction from a tree. That is hundreds of lines of ordinary code with negligible runtime cost. What it *presumes* — and what no chain verifier provides — is the SpecInfer/Medusa/EAGLE tree-attention substrate in the runner's attention path: per-node ancestor-only masks instead of the causal triangle, depth-based position IDs, tree-structured KV allocation with per-step rollback of unaccepted branches, and a tree-walking sampler. In a ggml-class backend that substrate is kernel-and-graph surgery, for the reasons stated plainly in `papers/specinfer.md` §6b: the FlashAttention fast path cannot express an arbitrary ancestor mask, so the backend either materialises masks and leaves the fused path or grows a dedicated tree-attention kernel — per backend (CUDA/Vulkan/Metal/CPU). **EAGLE-2 cannot be adopted as a feature; it can only be adopted as a rider on a tree-verification investment made for other reasons.**
2. **The realistic local path already runs through EAGLE-3.** The one trained-head route the GGUF world actually ships is `draft-eagle3` — and EAGLE-3's verifier *is* EAGLE-2's dynamic tree (§5). So the practical question for a personal runner is not "implement EAGLE-2" but "does the shipped EAGLE-3 path expose its tree budget, and can that budget be tuned down to 6 GB proportions (§6a)?" Where it can, the user gets EAGLE-2's contribution — confidence-shaped trees — as a by-product of the EAGLE-3 checkpoint ecosystem, with no new kernel work of their own. Where it cannot (arbitrary community models with no EAGLE-3 checkpoint — the common case), the landscape's honest ranking stands: n-gram floor first, draft-simple where headroom survives, and EAGLE-2 remains a paper to learn the *principle* from — spend verification width by estimated acceptance, never by position alone — a principle that transfers even to chain drafting, where it argues for confidence-gated draft length (abort the chain early when draft confidence collapses) over fixed-γ drafting. That gated-chain form captures a real fraction of EAGLE-2's insight with none of the tree substrate, and it is the form in which this paper is most likely to pay rent on a 6 GB machine.
