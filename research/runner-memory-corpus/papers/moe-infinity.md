## 2. The problem it attacks

`papers/mixtral.md` §6 states the gap: an MoE model *computes* like its active parameter count but must be *stored* like its total parameter count. The standard bridge is **offloading** — keep the full model in host (CPU) memory and fetch each token's selected experts into GPU memory on demand. In principle only a few experts cross the bus per token. In practice, the paper argues, offloading systems are slow for a *caching* reason, not a bandwidth reason:

- Existing systems manage the GPU-side expert buffer with policies imported from dense-model serving: dependency-based prefetching (fetch the next layer's experts while computing this one), recency (LRU), or global activation statistics. All three assume something MoE violates — that the needed set is predictable from the computation graph's order, from recency alone, or from population-wide frequencies.
- The measured consequence (v3 Table 1, §5): on a single 24 GB card, baseline systems spend **254–2,073 ms per token with the GPU idle waiting on expert transfers**, and inaccurate prefetch makes it *worse* than honest on-demand fetching, because wrongly prefetched experts consume the same PCIe bandwidth the genuinely needed expert is queued behind. Prefetch traffic and miss traffic contend; a bad predictor is a bandwidth tax, not a free option.

The problem is therefore precise: **design an expert cache — what to keep, what to prefetch, what to evict — that is aware of how MoE activation is actually structured at the granularity at which it is actually predictable.** The paper's answer rests on measuring where that granularity is (§3).

## 3. Core idea in our own words

**The setting is the insight.** On a personal machine, inference is single-user and effectively **batch size 1**: one request decodes at a time. In that regime the paper's trace studies find MoE activation is *deeply* skewed — but only at the right level of analysis:

- **Per token:** a token activates a tiny slice (Mixtral: 2 of 8 experts per layer; many-expert models: far less).
- **Per request:** the slice stays small and *stable*. Across the models studied, **fewer than 5% of experts are repeatedly activated during one request's decode** for models with ~100+ experts per layer (DeepSeek, Qwen-MoE, NLLB, Switch class), and **≈25% for Mixtral** — the coarse, few-expert worst case. One worked illustration from the paper's figures: in Mixtral's last layer, one sampled request reuses a single expert over 15 times — 7× more than any other expert in that layer for that request — while a second request's hot experts in the same layer are entirely different ones.
- **Across requests:** the skew *evaporates*. Aggregated over 1,000 sequences, reuse counts even out toward uniform — experts are specialised *per request context*, not globally popular. Any cache policy built on global frequencies (the paper names BrainStorm-style statistical counting) is therefore averaging away exactly the signal it needs.

So the working set of a single request comfortably fits a consumer GPU's spare memory, but *which* working set it is can only be learned from the request itself, matched against how similar requests behaved before. MoE-Infinity builds the cache around that:

1. **Trace at request level.** Every routing decision is recorded into an **Expert Activation Matrix (EAM)** — an L×E count matrix (layers × experts per layer) of how many tokens each expert has processed. An iteration-level EAM (iEAM) captures one forward pass (prefill: the whole prompt; decode: one token); a request-level EAM (rEAM) accumulates them over the request so far.
2. **Remember traces, match new requests to them.** Completed and in-progress rEAMs are kept in an **EAM Collection (EAMC)**. Clustering analysis in the paper shows rEAMs fall into a small number of *group activation patterns* (K-means elbow analysis: roughly 10–30 groups per model/dataset over 1,000 samples), while transitions *between* groups across requests are essentially unpredictable (transition probabilities mostly <0.12, max ≈0.3). Conclusion the design follows strictly: do not try to learn a cross-request predictor; **match** the current request's partial trace to the most similar stored traces (cosine distance over flattened EAMs — chosen because it compares relative activation frequencies and weights high-frequency experts most), and let the matched traces vote on what happens next.
3. **Predict an EAM, then cache and prefetch from it.** Matching produces a predicted EAM (pEAM): per-expert activation/reuse likelihoods for the rest of the request, aggregated from matched traces and **decayed by layer proximity** — likelihood is weighted by (1 − (i − l)/L) so experts in layers about to execute count more for prefetching than distant ones.
4. **Evict by predicted irrelevance, not recency.** On a miss with a full cache, the victim is the cached expert with the *lowest pEAM-derived priority*, with one structural correction: experts in **early layers get a caching-priority bonus**, because early in each forward pass (and early in a request) the group match is least certain, prefetch is least reliable there, and a miss in layer 0 cannot be hidden behind earlier compute — while later layers' experts have the whole preceding pass to be prefetched in.

The result is a GPU expert cache whose contents track the *current request's* expert working set, warmed by pattern-matching rather than by global popularity, with prefetching that is issued only where the matched pattern actually predicts activation — the direct answer to §2's contention problem.

## 4. Key design details a runner engineer needs

- **What is resident where (the paper's Figure 1 design):** the **full model lives in host memory**; **dense/shared parameters — attention weights and the KV cache — are pinned in GPU memory and never evicted**; only **experts** live in the managed GPU cache and move over PCIe. This split is the same one `papers/mixtral.md` §4 derives from Mixtral's structure, here made into a system invariant. Its long-context consequence is measured, not asserted (§5): because KV never shares the bus with expert traffic, MoE-Infinity's latency degrades more gently with context than systems that offload KV too.
- **Expert granularity and sizes differ wildly by model — the cache must be expert-shaped, not byte-shaped.** The paper's own examples: a Mixtral expert is ≈0.15B parameters / **340 MB** (in the paper's serving precision) — few, huge cache units, 8 per layer, top-2 — while Switch-128's experts are ≈33 MB, 128 per layer, top-1. A cache policy tuned on one shape (hit value per eviction, prefetch cost per unit) does not transfer numerically to the other; what transfers is the tracing/matching machinery.
- **Prefetch is integrated with the cache, not bolted on:** the pEAM drives both. Prefetch targets are the predicted experts of *upcoming layers* in execution order, issued so the transfer overlaps attention and current-layer expert compute; the worked example in the paper (§4.7) shows the joint policy beating LRU+dependency-prefetch and statistical counting on the same trace, in both directions — retaining a soon-to-be-reused expert the baselines evict, and not wasting a fetch slot on an expert the pattern says will not fire.
- **The EAMC is small and bounded.** Sweeping its capacity, the paper finds the lowest latency at capacities around **120 traces — roughly 3% of the number of requests** in its mixed 290-task workload — and the behaviour generalises across models. Trace memory is therefore a minor line item; the data structure is a history buffer, not a second model. (Implementation detail a reimplementer needs: matching is over flattened L×E matrices — for Mixtral that is a 256-entry vector; for many-expert models it is larger but extremely sparse.)
- **Worst case is honest:** when the pattern match fails or the cache cannot hold the working set, the system degrades to on-demand fetching — the vLLM-style floor — rather than below it, *provided* prefetch is throttled to predicted activations. The paper's long-context results (§5) show exactly this degradation path as KV growth squeezes the expert buffer.
- **Adaptation to workload change is measured:** after a task shift within a dataset, low latency returns after ≈50 requests worst-case (≈5% of a 1,000-sequence task set); after a dataset shift, ≈30 requests on average (<0.1% of the sampled inputs) — because matched patterns are reused across similar tasks. A personal-machine deployment, where the "workload" is one user's habits, should adapt faster than either figure; that is **[our inference from the paper's mechanism, not a paper measurement]**.
- **Relationship to the incumbent local stack:** the baselines include **Ollama (via llama.cpp)** explicitly, characterised as storing parameters CPU-side and computing/offloading from there — and llama.cpp's own current MoE machinery (`--cpu-moe`, `--moe-cache-mib`; corpus `runners/llamacpp-ggml.md` §5.2) is best read as the *static* version of this design space: a fixed placement plus a size knob, with no activation tracing. MoE-Infinity is what that cache becomes when its policy is learned online from routing traces.

## 5. Reported results — as reported, with context

All figures are the paper's own (v3). **Testbed:** a **single NVIDIA RTX A5000 (24 GB)** connected over **PCIe 4.0** (the evaluation section states 32 GB/s; the Table 1 caption states 24 GB/s — the paper is internally inconsistent on this number, recorded here rather than resolved). Host memory is sized to hold each full model (32 GB for DeepSeek up to 1 TB for Arctic). **Models:** DeepSeek-V2-Lite (31 GB, "DeepSeek-64×2.4B" configuration), Mixtral-8×7B (120 GB in the paper's accounting), Switch-128×0.2B (30–100 GB by configuration), NLLB-MoE 128×0.4B (220 GB), Snowflake Arctic 128×4B (900 GB). **Workloads:** 290 tasks from BIG-bench (166), FLAN (66) and MMLU (58); headline decoding runs use 512-token prompts and 32 generated tokens; latency is time-per-output-token (TPOT) in decode.

- **Headline (abstract): 3.1–16.7× per-token latency improvement** over vLLM, Ollama, DeepSpeed-Inference and BrainStorm across the DeepSeek and Mixtral models and task sets. The conclusion restates the range as **2.7–13.7×** over "strong baselines" — the two ranges coexist in the paper (different baseline sets/aggregations); neither should be quoted without its comparison set.
- **The cleanest single table (Table 1) — DeepSeek-V2-Lite, TPOT:** MoE-Infinity **155 ms average / 169 ms tail, with 51 ms GPU idle** — vs vLLM 485 / 493 ms (254 ms idle), DeepSpeed 737 / 803 ms (513 ms idle), Mixtral-Offloading 1,250 / 1,530 ms (754 ms idle), **Ollama 2,590 / 2,599 ms (2,073 ms idle)**, BrainStorm ≈934 ms average (in text). Read the idle column as the paper's argument in one number: the baselines' GPUs are mostly *waiting for experts*; MoE-Infinity's mostly is not.
- **End-to-end by model (§5.1):** for the many-expert models the system reaches latency "comparable to the model running fully in GPU" — Switch 155 ms, DeepSeek 155 ms, NLLB 531 ms TPOT — while using **one GPU where the non-offloading alternative needs 4 (Switch) to 8 (NLLB)**. For **Mixtral — explicitly the authors' worst case**, because its experts are few, large, and its per-request activation ratio is the highest studied — TPOT is **836 ms**, a **1.4× improvement** over BrainStorm/Mixtral-Offloading-class baselines (vLLM and DeepSpeed are worse, for cache-hit-rate reasons). For Arctic (900 GB), MoE-Infinity is reported as the only system offering competitive single-GPU inference at all. **The honest shape of the result: the sparser and finer-grained the MoE, the larger the win; coarse Mixtral-class models gain least** — a point §7 prices for our exact target model class.
- **Long context (DeepSeek-V2-Lite, generation lengths 2¹² → 2¹⁷):** total per-token time rises 50 → 160 ms across the range for the field generally. The mechanism the paper isolates: KV growth shrinks the expert buffer — DeepSeek-V2-Lite activates ≈3 GB of experts per decode iteration, and the buffer stays above that until ≈2¹⁵ tokens, then falls to ≈2 GB at 2¹⁶ and ≈1 GB at 2¹⁷, at which point MoE-Infinity falls back toward on-demand fetching (+137 ms, still less than vLLM/Mixtral-Offloading, whose KV itself also crosses the bus and contends with expert fetches). All systems OOM by 2¹⁷ in this setup.
- **What is *not* in the evaluation:** no consumer 6–8 GB card, no GGUF/quantised models (the model sizes above are full-precision serving footprints), no batch>1 serving, and no power or CPU-utilisation accounting for the host side. The A5000's 24 GB expert buffer is 4–8× what §7 budgets; the *policy* is what transfers, not the latencies.

## 6. Limitations / what it does not solve

- **Batch 1 is a premise, not a setting.** The entire sparsity argument — small per-request working set, stable within a request — is a batch-1, single-user property. Under continuous batching, the union of concurrent requests' experts densifies toward the full pool (compare `runners/powerinfer.md` §5 on batch densification), the per-request trace stops describing the aggregate, and the cache advantage shrinks. The paper does not evaluate batched serving and its design should not be quoted there.
- **Prefill is not the subject.** Decode is where the cache earns; a 512-token prompt's tokens scatter across far more experts than one decode token, so prompt processing pays close to on-demand costs. Workloads dominated by long prompts and short answers gain least — the same boundary every sparsity system in this corpus hits.
- **Cold start and pattern novelty are real costs.** A new request begins with an empty match; the EAMC needs history, and §5's recovery measurements (≈30–50 requests after a shift) are the price list. For a personal runner this is mostly a first-run tax, but a workload of *one-shot, all-different* requests (bulk heterogeneous batch jobs) sits permanently in the cold regime.
- **The Mixtral worst case bounds the headline.** On the model class this corpus most cares about (coarse 8-expert models), the measured gain over the strongest offloading baselines is 1.4×, not 16.7× — the large multipliers belong to many-expert models whose tiny experts make caching easy. Quoting the abstract range for a Mixtral deployment would be a misrepresentation of the paper's own results.
- **Systems cost is unpriced in the paper:** the tracer, matcher and cache manager run on the host CPU on every layer of every token; their overhead is inside the reported TPOTs on the authors' host but is not broken out, and a weaker host (the fleet's laptops vs a workstation serving 1 TB of Arctic) may feel it differently. **[Engineering judgement]** — flagged as a measurement to take in any reimplementation, not as a known defect.
- **No quality risk — and that is worth stating.** Unlike sparsity-*inside*-the-model systems (PowerInfer-style neuron skipping, thresholded activations), expert caching is **lossless**: a miss costs time, never correctness; the same experts compute the same outputs. The entire risk surface is latency variance (miss storms on pattern shifts), which is the safest failure shape a serving optimisation can have.

## 7. Applicability

### (a) Ollama on a 6 GB consumer GPU — expert caching is the MoE feature

Context: Mixtral-class model, Q4_K_M-class GGUF (≈26–29 GB total, ≈100 MB per expert — `papers/mixtral.md` §7 arithmetic), 6 GB card with ≈0.5–1.0 GiB already taken by context/display (corpus `memory/gpu-memory-internals.md` §2.3), leaving roughly **3–4 GB of expert cache** after shared weights (≈1 GB at Q4), KV cache for a chat-length context (≈0.5–1 GB), and compute buffers. That cache holds **≈30–40 experts — about 12–15% of Mixtral's 256**.

- **Why that can still work — the locality stack, in order of reliability:**
  1. *Per-request skew (MoE-Infinity §4.1):* ≈25% of Mixtral's experts (≈64) are repeatedly activated within one request. A 30–40-expert cache cannot hold all 64 — but reuse is itself skewed *within* the working set (the paper's 15×-reuse illustration), so the hottest half of the working set serves a large majority of token-layer visits. **[SPECULATION — quantitative split not measured in the paper for a cache this small; the direction is the paper's, the fraction is ours to measure.]**
  2. *Temporal locality (Mixtral §5):* consecutive tokens repeat the same expert ≈62–67% of the time (either slot) at middle layers. Even a tiny cache — or a one-token-delayed prefetch — harvests this: the expert needed at layer l for token t+1 is, better than even odds at mid-depth, the one just used.
  3. *Syntax/domain coherence:* routing tracks token type and local syntax more than topic, so a single conversation — one character, one scenario, one language — is close to the paper's "one request" ideal even across turn boundaries, *provided the cache is not flushed between turns* (see (b) for the session version of this point).
- **What an Ollama-class runner can realistically implement, in ascending order of ambition — all three are Go-feasible without kernel work, riding the existing ggml placement machinery:**
  1. **Static hot-set placement (load-time, zero runtime risk):** ship or build a per-model activation profile (the PowerInfer dossier's sidecar idea, at expert rather than neuron granularity — profiling an MoE's routing over a general corpus is a routing-counter pass, far cheaper than neuron profiling), and pin the globally hottest experts in VRAM at load. This captures cross-request popularity only — MoE-Infinity shows that signal is weak — so treat it as the *floor*, worth having because it is free.
  2. **Request-level tracing + LFU-within-request eviction (the cheap 80% of MoE-Infinity):** count routing decisions per request (the runner already knows them — it dispatched the experts), evict by *this request's* frequency rather than global LRU, reset or decay counts at request boundaries, and prefetch the next layer's predicted experts from the current request's rEAM while the current layer computes. No EAMC, no clustering, no cosine matching — just "the trace is per-request" — which is the paper's central finding, implementable as a cache-policy change behind `--moe-cache-mib`-style sizing.
  3. **Full EAMC matching (the paper's design):** persist rEAMs across requests (they are small — a 256-float vector for Mixtral), match new requests by cosine distance, drive prefetch and eviction from the pEAM with layer-proximity decay and the early-layer priority bonus. This is the version that survives workload diversity (many different users/tasks); for a single-user personal runner, step 2 likely captures most of the value — **[engineering judgement]** — and step 3 should be justified by a measured miss-rate gap, not adopted on the paper's authority alone.
- **The miss-traffic budget, priced** (corpus PCIe arithmetic, `memory/gpu-memory-internals.md` §4.4; expert ≈100 MB at Q4): each miss costs ≈8 ms of pure transfer at Gen3 ×16 typical (12.1 GB/s) or ≈4 ms at Gen4 ×16 typical (26.2 GB/s), *if* the bus is otherwise idle — which is why wrong prefetches are so damaging: they spend the same milliseconds. A token touches 64 expert slots; at a 90% hit rate that is ≈6 misses ≈50 ms/token of bus time on Gen3 (a ≈20 tok/s ceiling from misses alone, overlappable in part with compute); at 75%, ≈16 misses ≈130 ms (≈7–8 tok/s ceiling). **The runner should expose expert-cache hit rate as a first-class metric** — it predicts MoE decode speed on small cards better than any FLOP figure, and it is the number that tells the user whether a bigger cache allocation (trading KV context for experts) would actually help.
- **The CPU-compute alternative, honestly bounded:** for a missed expert, computing it *in place in RAM* (llama.cpp's `--cpu-moe` mode; the PowerInfer pattern) avoids the transfer and the cache slot, at host-bandwidth cost. On a strong host CPU this can beat a miss-then-compute for *cold* experts while the GPU handles hot ones — a two-tier policy (cache the hot, CPU-compute the cold, never fetch-and-evict speculatively) is a legitimate design point the paper does not evaluate, and a natural A/B experiment for the Go runner. **[Engineering judgement]**

### (b) The fleet case — the 39 GB RAM host is the interesting machine

The commissioning brief names the fleet's G14-class host (39 GB RAM) as the interesting target, and the arithmetic supports it: a Q4_K_M Mixtral (≈26–29 GB) **fits entirely in 39 GB of RAM** alongside the OS and the runner, with the 6 GB card acting purely as cache + dense-compute tier. That is exactly MoE-Infinity's reference topology (full model in host memory; attention + KV pinned on GPU; experts cached on GPU) at personal scale — no NVMe tier is needed in steady state, and the disk only participates at load. On smaller-RAM hosts the same design still works at lower quants (IQ3-class totals ≈15–17 GB), trading model quality for residency; below that, an NVMe expert tier becomes necessary and the design inherits PowerInfer-2's flash-tier problems (`runners/powerinfer.md` §5) — out of scope for a first implementation. **[Our arithmetic throughout this paragraph, from `papers/mixtral.md` §6's quant ladder.]**

### (c) Project Aesir (Mojo runner — sessions, prefix memory, hybrid SSM models)

- **Expert cache and KV cache are siblings, and should share a manager.** Both are per-session working sets with skewed reuse, both compete for the same device memory, and MoE-Infinity's long-context result (§5) is precisely the two fighting: KV growth evicts experts, expert misses stall decode. Aesir should budget them from one arena with an explicit, logged split policy (and a user-visible trade: context length vs expert-cache size), rather than letting two independent allocators discover the conflict at OOM.
- **Session restore should restore the expert working set.** Aesir's prefix-memory/session design already persists KV state; the rEAM of a session is a few hundred floats that *predict* its expert working set. Persisting the rEAM (or the cache contents' identities) with the session lets a restored session pre-warm its experts during the KV restore transfer — hiding expert misses behind an I/O the system is already paying. This is the MoE analogue of RadixAttention's cache-aware scheduling (`papers/radixattention-sglang.md`), applied to weights instead of KV.
- **Fine-grained MoE is where Aesir should aim the design.** MoE-Infinity's gains grow as experts get smaller and more numerous (DeepSeek-class: <5% per-request working set, 3.1–16.7× range) — and Aesir's hybrid/SSM ambitions already assume small, pluggable per-layer state. An expert cache designed around Mixtral's 100 MB units will be wrong-shaped for 3–30 MB units (eviction granularity, prefetch batching, and transfer setup costs all change); design the cache interface around *expert identity + byte size*, not around a fixed block size, from the start.
- **Do not import the batch-1 premise into Aesir's server-shaped features.** If Aesir ever serves concurrent sessions from one device, the expert cache must be partitioned or shared with per-session traces kept separate (the cross-request uniformity result means a shared naive cache serves the *average* session, i.e. none of them). Per-session EAMs with a shared physical cache and pEAM-weighted eviction is the paper-faithful extension; it is untested in the paper and should be labelled as Aesir's own experiment. **[SPECULATION as a design proposal, marked as such.]**
