# Splitwise — Efficient Generative LLM Inference Using Phase Splitting

## 1. Full citation

- **Title:** Splitwise: Efficient Generative LLM Inference Using Phase Splitting
- **Authors:** Pratyush Patel, Esha Choukse, Chaojie Zhang, Aashaka Shah, Íñigo Goiri, Saeed Maleki, Ricardo Bianchini
- **Affiliations (as listed in the paper):** University of Washington (Patel — work partly done as an intern at Microsoft); Microsoft (Choukse, Zhang, Shah, Goiri, Maleki, Bianchini)
- **Venue / year:** 2024 ACM/IEEE 51st Annual International Symposium on Computer Architecture (ISCA 2024), Buenos Aires, Argentina, 29 June – 3 July 2024, pp. 118–132. DOI: 10.1109/ISCA59077.2024.00019
- **arXiv:** arXiv:2311.18677 [cs.AR] — submitted 30 November 2023; v2 (the version read for this dossier) 20 May 2024 — https://arxiv.org/abs/2311.18677
- **Position in the wave:** Splitwise is the earliest of the three disaggregation-era papers in this wave — submitted about six weeks before DistServe (arXiv:2401.09670) — and the only one framed as a *hardware/provisioning* paper rather than a scheduler or serving-system paper. That framing is its identity: it starts from a characterisation study and ends at cluster designs priced in dollars and watts.

## 2. The problem as framed

Splitwise's problem statement is a measurement, not a scheduling pathology. The authors characterise production LLM inference (Azure production traces; BLOOM-176B and Llama2-70B on DGX-A100 and DGX-H100 machines) and find that a request's two phases are effectively two different applications sharing a binary:

- **Prompt computation (prefill)** is compute-intensive: throughput saturates early (past ~2,048 prompt tokens in a batch, adding more *reduces* throughput), latency (TTFT) grows ~linearly with prompt size, power draw rises with batch size, and latency is highly sensitive to power caps.
- **Token generation (decode)** is memory-intensive: throughput keeps climbing with batch size until the machine runs out of KV-cache memory (batch 64 in their setup, with TBT less than 2× worse than at batch 1), most end-to-end time is spent here even for prompt-heavy workloads (a 1,500-token prompt phase on BLOOM-176B takes the same time as generating **6** output tokens), power draw is flat in batch size, and capping power by over 50% (700 W → 350 W on H100) costs it **almost no latency**.

The two workloads the traces represent underline that "the workload" is not one thing: the **coding** service has median prompt 1,500 tokens but median output **13** tokens; the **conversation** service has median prompt 1,020 and median output **129**. Any single provisioning must serve both shapes.

The economic sting is in the hardware trend (paper Table I). From A100 to H100: compute **3.43×** (19.5 → 66.9 TFLOPs), power **1.75×** (400 → 700 W), machine cost **2.16×** ($17.6/hr → $38/hr) — but HBM capacity **1.00×** (80 GB both) and HBM bandwidth only **1.64×** (2,039 → 3,352 GB/s). New silicon sells FLOPs at a steepening price; decode cannot spend FLOPs — it spends bandwidth and capacity, which barely improved. Measured head-to-head without batching on Llama2-70B (paper Table IV, P50): moving A100 → H100 roughly halves TTFT (coding 185 → 95 ms; conversation 155 → 84 ms) but only multiplies TBT by ~0.70× (52 → 31 ms; 40 → 28 ms), and the A100 is **equal or better on cost and energy per request overall**. The paper's Insight VII follows: *token generation can be run on less compute-capable hardware for better performance-per-dollar and performance-per-watt.*

So the problem, as framed: **state-of-the-art batching still leaves the token phase under-utilising compute, because both phases are pinned to the same machines — machines that must be bought for the prompt phase's appetite and then mostly idle, in compute terms, through the token phase's long tail.** Services over-provision flagship GPUs to meet interactive SLOs, and the over-provisioning is structural, not operational.

## 3. Core mechanism in our own words

**Phase splitting.** Splitwise runs the two phases on separate *machine pools*. All machines are pre-loaded with the model. A request is assigned, at arrival, a prompt machine and a token machine as a pair: the prompt machine runs the prompt phase, produces the first token and the KV cache, transfers the KV cache to its paired token machine, and is free; the token machine generates the remaining tokens under continuous batching. Three pools exist, not two:

- **Prompt pool** and **token pool** — the specialists, run the way each phase wants (below).
- **Mixed pool** — the shock absorber. Machines retain a home identity but can be borrowed into mixed duty (both phases, mixed batching, like a conventional server) when load fragments the specialist pools, and return home when the borrowed queue drains. Coarse re-purposing between the specialist pools happens only if a machine lives in the mixed pool persistently. This elasticity is easy to underrate: it is the paper's answer to the obvious objection that fixed pools shatter whenever the workload's prompt/output ratio drifts — and its evaluation (§4) shows heterogeneous designs losing only ~7% when run on the *wrong* trace, with the mixed pool doing the absorbing.

**Two-level scheduling.** A cluster-level scheduler (CLS) owns pool membership and routing: it assigns each request its prompt+token pair by **Join-the-Shortest-Queue** (queues measured in pending tokens), assigning *both* machines at arrival specifically so the KV transfer can be overlapped with prompt computation. A machine-level scheduler (MLS) owns batching per machine, with phase-specific policies that encode the characterisation: prompt machines schedule FCFS and **cap total batched prompt tokens at 2,048** (the saturation point — configurable per model/hardware); token machines schedule FCFS and **batch as much as memory allows**, queueing only near KV exhaustion; mixed machines prioritise prompts for TTFT, preempting token work if necessary, with ageing and a per-request preemption cap to prevent token starvation.

**KV handoff, overlapped.** The transfer is the design's only new cost, and the paper engineers it down rather than waving at bandwidth. The naive version — serialise the whole KV cache after prefill, then send — measurably hurts: up to 3% of end-to-end latency at large prompts and **+64% on the latency of the second token** (the one gap a streaming user actually sees). Splitwise instead transfers **layer-wise**: as each layer's KV is produced on the prompt machine, it is sent asynchronously (MSCCL++ zero-copy one-sided puts over InfiniBand — 200 Gbps on their A100 setup, 400 Gbps on H100) while the next layer computes. Small prompts don't need the trick and don't pay its synchronisation cost: below a threshold (**512 tokens on H100**) Splitwise uses the simple serialised transfer; above it, the layer-wise path. Result (§4): visible transfer overhead **< 7% of prompt computation time**, **0.8% of end-to-end latency**, **+16.5% on the second token** instead of +64%, with a small constant non-overlapped remainder (~8 ms A100, ~5 ms H100). The transfer is lossless — Splitwise changes where state lives, never what the model computes, so there is no accuracy impact by construction.

**Provisioning as a search.** Splitwise is also a cluster-design method. An event-driven simulator (performance model from hardware profiles, mean absolute percentage error **< 3%**; validated end-to-end over 50K+ iterations) searches pool sizes for a target design under SLOs expressed as allowed slowdowns vs an uncontended A100 (paper Table VI — all nine must hold: TTFT P50/P90/P99 = 2×/3×/6×; TBT and E2E = 1.25×/1.5×/5×), optimising throughput, cost, or power. Four designs are evaluated (paper Table V): **Splitwise-AA** (A100 prompt, A100 token), **Splitwise-HH** (H100/H100), **Splitwise-HA** (H100 prompt, A100 token — the heterogeneity the characterisation argues for), and **Splitwise-HHcap** (H100/H100 with token machines power-capped — token pool at 70% of rated cluster power, each GPU capped to 50%). Pool ratios follow the trace, as they must: for the coding trace under Splitwise-HH, 35 prompt + 5 token machines; for conversation, 25 + 15. One worked sizing (iso-throughput, cost-optimised, coding, 70 RPS target): **27 prompt + 3 token machines**.

## 4. Reported results — as reported, with hardware and model context

All figures are the paper's own. **Read the evaluation's shape before its numbers:** the transfer mechanism was measured on real hardware (a modified vLLM on two DGX-A100 and two DGX-H100 Azure VMs, MSCCL++ over InfiniBand); the *cluster* results come from the validated simulator (§3) replaying the production traces, because nobody evaluates 70-machine clusters on a bench. Models throughout: **BLOOM-176B and Llama2-70B**, tensor-parallel across 8 GPUs per machine. Baselines: homogeneous all-A100 (Baseline-A100) and all-H100 (Baseline-H100) clusters running mixed continuous batching.

**Headline (abstract):** Splitwise clusters achieve **up to 1.4× higher throughput at 20% lower cost** than current designs; alternatively **2.35× more throughput under the same cost and power budgets**.

**Cluster results in detail (§VI-B/C of the paper)** — the abstract's two numbers are the envelope of these operating points, not a single configuration:

- **Iso-power, throughput-optimised** (budget = power of 40 DGX-H100 machines, which also fits 70 DGX-A100): **Splitwise-AA delivers 2.15× the throughput of Baseline-A100** at the same power and cost; **Splitwise-HA delivers 1.18×** at **10% lower cost**, same power. (Coding provisioning under AA: 55 prompt + 15 token machines.) For conversation, Splitwise-HHcap leads on latency as well as throughput — long token phases are exactly what capped token machines are for.
- **Iso-cost, throughput-optimised:** Splitwise-AA gives the best throughput for the money — **1.4× Baseline-H100** — at 25% more power and 2× the space. The paper is candid that this point flatters the customer (throughput per dollar, on readily available older GPUs) more than the provider (power, space).
- **Iso-throughput, power-optimised:** **Splitwise-HHcap matches Baseline-H100's throughput at 25% lower power**, same cost and space — the provider's favourite point, bought entirely with the power-cap insight.
- **Iso-throughput, cost-optimised:** Splitwise-AA matches Baseline-H100 throughput at **25% lower cost** in the body text (§VI-C) — the abstract's "20% lower cost" is the more conservative envelope figure; both are the paper's, at different operating points, and this dossier reports both rather than picking one silently.
- **Transfer overhead (real hardware, §VI-A):** as in §3 — < 7% of prompt computation, 0.8% of E2E (vs up to 3% serialised), second-token +16.5% (vs +64% serialised); H100 transfers run ~2× faster than A100, tracking the 400 vs 200 Gbps fabrics.
- **Robustness (§VI-D):** running the conversation trace on a coding-provisioned cluster (and Llama2-70B on a BLOOM-provisioned one) costs the heterogeneous designs (HA, HHcap) ~**7%** throughput vs their matched designs; all Splitwise designs still beat both baselines. The homogeneous Splitwise designs morph via the mixed pool with no measured impact.
- **The honest boundary (§VI-E):** under batch-job stress (no latency SLOs, maximum load), Splitwise **devolves to the baselines** — every machine ends up in the mixed pool doing mixed batching, and throughput-per-dollar equalises (0.89 RPS/$ for AA and Baseline-A100; 0.75 for HH and Baseline-H100). Phase splitting is a latency-regime technique; saturate the system and there is nothing left for it to protect. The paper also flags its own deployment caveats: Splitwise-HA assumes an InfiniBand path between *different* GPU generations that clouds may not actually sell, and fragmenting a fleet into GPU types has operational costs a simulator does not price.

## 5. What it changed in practice

Splitwise as a named system was not productised — there is no "Splitwise mode" in a shipping server. What shipped is its worldview, in three layers:

- **The characterisation became the field's shared premise.** "Prefill is compute-bound, decode is memory-bound, and the newest GPU's FLOPs are wasted on decode" is now the opening paragraph of essentially every serving design — DistServe (this wave) builds its goodput argument on it, Sarathi-Serve's arithmetic-intensity slack is the same observation from inside one GPU, and Mooncake/Dynamo documentation repeats it as settled fact. Of the three papers in this wave, Splitwise is the one whose *measurements* (phase saturation points, power-cap asymmetry, A100-vs-H100 per-phase economics) are still quoted as design inputs.
- **Phase-split pools with heterogeneous hardware are a real deployment pattern.** NVIDIA Dynamo's disaggregated serving explicitly supports sizing and placing prefill and decode pools independently, and its deployment guidance and ecosystem write-ups treat **H100-class prefill + A100-class decode** — Splitwise-HA, verbatim — as a legitimate production cost strategy, with the Planner dynamically rebalancing pool ratios (Splitwise's pool-ratio search, turned into a control loop; its mixed pool, turned into elastic rescaling). SGLang's zero-downtime prefill/decode role switching is the same elasticity from the engine side. Power-capped decode pools appear in operator practice for the reason Splitwise measured: decode latency barely notices a 50% cap, so the watts are free to reclaim.
- **The KV-handoff engineering pattern stuck.** Layer-wise, overlapped KV transfer — start moving each layer's cache while later layers still compute, and don't bother for small prompts — is the shape production transfer layers (Mooncake Transfer Engine, NIXL-based connectors) implement, and the "second token" framing (the handoff's cost lands on exactly one user-visible gap) is how those systems budget it.

Where Splitwise's idea does *not* live: nobody provisions static, simulator-searched fleets per workload trace the way the paper's §IV-D prescribes — autoscaling and role-switching replaced the offline search, because real traces drift faster than clusters can be re-bought. The paper's own robustness section anticipated this; the mixed pool was the seed of the elastic answer.

## 6. Applicability, honestly scaled

### (a) Ollama on a 6 GB consumer GPU, single-user chat

Nothing in Splitwise's mechanism transfers literally: there is one machine, one GPU, no second pool, no InfiniBand, and a single user whose requests arrive minutes apart, not at 70–130 RPS. The 1.4× / 2.35× figures are cluster-provisioning results from a simulator fed production traces; they have no single-user meaning and must not be quoted in the 6 GB context. Four things do transfer — three measurements and one warning:

1. **Characterise the two phases separately on the target card before tuning anything.** Splitwise's method — measure prefill and decode as different workloads (saturation point, power/thermal sensitivity, batch behaviour) — is cheap and directly actionable on the 2060: the improved Ollama's own numbers should state the prompt-token count at which prefill saturates the card, and the decode step's sensitivity to the laptop's power/thermal envelope. On a thermally constrained laptop the paper's power finding has a local echo: prefill bursts are what push a small GPU into its power/thermal limits; decode is the phase that must stay smooth *while the card is hot from prefill*. That argues for the same remedies as elsewhere in this wave (chunked ingestion, residency so re-prefill is rare), but Splitwise is where the phase-asymmetry evidence is strongest.
2. **Character chat is conversation-shaped — decode dominates the user's clock.** In Splitwise's traces, conversation (median 129 output tokens) spends most of end-to-end time in the token phase, and even the prompt-heavy coding trace does (1,500 prompt tokens ≈ 6 output tokens of time). Volmarr's workload is more extreme than either: very long prompts *and* long replies, turn after turn. The provisioning conclusion miniaturises to a tuning priority: **protect TPOT first** — decode smoothness is where the user's hours go — and treat prefill cost as the thing to eliminate by reuse (IDEA-LEDGER #1/#5) rather than to accelerate raw, because per-turn it is amortised over hundreds of decode steps. A runner tuned by a single blended tok/s number will mis-serve this workload in exactly the way Splitwise's baselines mis-served theirs.
3. **Within one box, "heterogeneous pools" reads as: match the phase to the resource you actually have.** Ollama's world already contains a two-tier machine — GPU plus CPU with system RAM — and llama.cpp-style layer splitting already assigns work across it. Splitwise's discipline says to make that assignment *by phase and by measurement*, not by a single fit heuristic: the compute-bound phase wants the fastest arithmetic available; the bandwidth-bound phase wants the fastest memory path for its working set (weights stream + KV read). On a 6 GB card where some layers spill to CPU, the spill's cost lands overwhelmingly on decode (every step re-reads everything), which is the corpus's standing rule in another vocabulary (IDEA-LEDGER #12: buy VRAM back with cache precision, then weight quant, before accepting layer spill). Splitwise adds the *why* at cluster scale: decode is the phase that cannot be given slow resources without the user feeling every step of it.
4. **The warning: rigid phase splits lose to one flexible pool at low load.** Splitwise needs its mixed pool precisely because fixed pools fragment; at saturation for batch work it devolves to the baseline entirely. At single-user scale the "mixed pool" is the whole machine, permanently — which is the structural reason this wave's colocated paper (Sarathi-Serve), not its disaggregated ones, supplies the 6 GB runner's scheduling mechanism. Splitwise's role in the local design is diagnostic: it proves the phases differ, prices the difference, and then honestly steps aside.

### (b) Project Aesir

- **Splitwise is the wave's closest analogue to Aesir's hardware problem.** Aesir targets a heterogeneous SoC (Strix Halo: CPU, integrated GPU, NPU on unified memory, one shared power envelope) — a Splitwise cluster shrunk onto a die. Its phase-to-resource assignment question is Splitwise's, with devices instead of machine pools: which device runs prefill, which runs decode, and what does each phase actually need from the shared bandwidth and power budget? Aesir should adopt Splitwise's *method* wholesale: characterise each phase per device (saturation, bandwidth, power sensitivity) before fixing the assignment in the serve design, and record the characterisation as campaign evidence the way Splitwise's §III anchors its §IV.
- **The power-cap result is a design input for unified-power hardware.** On Strix Halo the GPU, CPU and NPU draw from one package budget; Splitwise's finding — decode latency ~flat under a 50% power cap while prefill latency is cap-sensitive — suggests an explicit Aesir policy: during a resident session's decode, cap the decode device's power share and reserve headroom for the next turn's prefill burst (and for the user's other work on the machine). This is also the polite-neighbour property a personal machine needs and a datacentre paper would never motivate: Aesir's serve must not cook the laptop it lives on.
- **The mixed pool becomes elastic device roles.** Aesir's devices, like Splitwise's machines, should not be hard-assigned: a device idle in its specialist role should absorb the other phase's work (its "mixed pool" behaviour) rather than sit out a burst, and role assignment should be revisable at runtime as the session mix changes — with Splitwise's caveat carried over: at full saturation the specialisation stops mattering, so the fallback path (every device on the urgent phase) must be a designed mode, not an accident.
- **The handoff discipline applies to snapshots.** Aesir's cross-phase/cross-session state movement is the hybrid-state snapshot (Q35-5), and Splitwise's transfer lessons translate one-for-one: overlap the movement with compute where possible (layer-wise → state-component-wise), use the cheap path below a size threshold and the overlapped path above it, and budget the cost against the *one user-visible gap it lands on* (the first decode step after a restore — Splitwise's "second token"). A snapshot restore that stalls the first generated token by an unbudgeted amount is Splitwise's naive serialised transfer, rediscovered.
- **What Aesir should not import:** simulator-searched static provisioning. Aesir serves one user's drifting workload on fixed silicon; its equivalent of pool sizing is the measured-fit/residency gate, re-run per model and per session — a control loop, not a cluster plan.
