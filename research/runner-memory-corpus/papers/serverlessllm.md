## 2. The problem as framed

Serverless inference is an economic proposition before it is a technical one. A provider multiplexes many developers' models onto a shared GPU fleet and charges only for the duration of each request; a developer avoids reserving expensive GPUs for a workload that may be idle most of the day. That proposition only works if models can be **scaled to zero** between bursts and brought back fast enough that the user does not pay the resurrection in latency.

For LLMs, they cannot — not with incumbent loaders. The paper frames the cold start as three stacked costs, and is explicit that the first two dominate:

1. **Checkpoints are enormous.** Sizes run from gigabytes to, in the paper's examples, hundreds of gigabytes (Grok-1 over 600 GB, DBRX 250 GB, Mixtral-8×22B about 280 GB, all in FP16 terms as stated). Even a 130 GB LLaMA-2-70B checkpoint takes a minimum of 26 seconds to download from S3/blob storage over a fast 5 GB/s commodity network, as the paper calculates it.
2. **Loading is slow even when the bytes are already local.** Loading is not a copy: it is model initialisation, GPU memory allocation, tensor creation, shape parsing, deserialisation, and tensor-by-tensor transfer. The paper's anchor figures: loading OPT-30B into 4 GPUs takes **34 seconds** with PyTorch, and LLaMA-2-70B into 8 GPUs takes **84 seconds** — against a per-token generation time usually under 100 ms. First-token latency is therefore not degraded by cold start; it is *constituted* by it.
3. **Cold starts are not rare.** Citing the public Azure serverless trace, the paper notes that over 40% of functions exhibit a cold-start rate exceeding 25%, and about 25% experience a cold-start rate greater than 60%, within a 5-minute keep-alive interval. A slow cold start multiplied by a high cold-start rate is the system's normal operating point, not its tail.

The incumbent mitigations are each priced and found wanting in the paper's framing: keeping warmed, over-subscribed GPU instances defeats the economics for models this large; caching checkpoints in host memory alone cannot hold a zoo of hundred-gigabyte checkpoints, so misses and remote downloads return; adding dedicated storage servers plus 100–200 Gbps networking can cost as much as the GPU servers themselves (the paper's example: network-optimised cache servers to support a 70B model can double costs).

The observation the whole design stands on: a GPU inference server already contains a **large, fast, and mostly idle storage hierarchy** — host DRAM, NVMe SSDs, SATA SSDs, multiple PCIe links to multiple GPUs — that existing serverless systems (KServe, Ray Serve are the named examples) barely use. An 8-GPU server can carry up to 4 TB of main memory, 64 TB of NVMe, and 192 TB of SATA storage in the paper's contemporary example, with aggregate host-to-GPU bandwidth of 512 GB/s on PCIe 5.0 and about 60 GB/s from RAID-0 NVMe to host memory. The problem, restated: **treat that hierarchy as the checkpoint store, and make loading a bandwidth-saturation problem instead of a download-and-deserialise problem.**

## 3. Core mechanism in our own words

ServerlessLLM is three mechanisms that only make sense together: a loader fast enough that locality is worth having, a migration primitive that makes locality usable without punishing running work, and a scheduler that prices both.

**a) The loading-optimised checkpoint format.** A checkpoint uploaded once and loaded many times should be stored in the shape loading wants, not the shape training wrote. Conversion therefore does two things. First, **sequential chunk-based reading**: tensors destined for each GPU are grouped into per-GPU partitions containing only binary parameter data — no interleaved metadata, no per-tensor file structure — so the loader reads large sequential chunks (the evaluation uses a 16 MB chunk size for bulk reading) instead of chasing thousands of small tensors, a third of which are under 1 MB in the models measured. Second, **direct tensor addressing**: a separate tensor index file maps each tensor name to (GPU id, offset, size), with tensors aligned to memory-word sizes, so a tensor's GPU address is arithmetic — base address plus offset — not a search. Loading and inference are also decoupled as processes: a *model manager* allocates GPU memory and streams the bytes in, while the inference process initialises the model object and simply sets each tensor's data pointer from the base addresses (obtained via CUDA IPC handles) plus the index offsets, synchronising once at the end. Because the manager owns the transfer, loading can be pre-scheduled and overlapped with inference-process initialisation.

**b) The multi-tier loading pipeline.** The manager moves chunks through whichever tiers hold them — remote object storage, SATA, NVMe, DRAM — into GPU memory, as a staged pipeline of I/O threads handing chunk indices (offset, size) down a task queue, so tiers work concurrently rather than in lock-step. Three data-path decisions do most of the work, each aimed at removing a copy or a stall:

- **Chunk-based data management over parallel PCIe links.** Checkpoints for multi-GPU models load over the parallel DRAM-to-GPU PCIe links concurrently, instead of serialising through one link; a fixed-size chunk pool in memory avoids fragmentation and gives the application explicit allocate/evict control over cached chunks, which a plain page cache does not.
- **Direct I/O, deliberately not mmap.** The loader reads with `O_DIRECT`-style direct file access into user space, bypassing the kernel page cache. The paper is explicit about why it rejects the mmap route used by Safetensors-class loaders: mmap performance is hostage to page faults and cache state and so lacks the *predictable* performance a startup-time scheduler needs to estimate against (the evaluation counts 112K page faults for Safetensors loading LLaMA-2-7B cold — see §4). Predictability is a feature here, not a side effect.
- **Pinned memory.** Staging through pinned (page-locked) host memory lets DMA move data to the GPU with minimal CPU involvement, saturating PCIe bandwidth with a single thread; the paper reports maximum bandwidth utilisation with only 4 CPU cores allotted to the loader.

Intra-tier concurrency (multiple I/O threads per tier, to drive modern SSDs' parallel channels) and per-interface access methods (local NVMe/SATA, remote S3-style stores, in-memory pinned pool) complete the pipeline. The design goal is stated plainly and then measured: **saturate whatever bandwidth the tier actually offers** (see §4).

**c) Token-level live migration of inference.** Locality-driven scheduling has a classic trap, which the paper works through a two-server/two-model example: send the new request to the idle GPU and it pays a slow load; send it to the GPU that holds its checkpoint locally and it queues behind a long, unpredictable running inference; preempt that inference and the preempted work pays reload plus recompute. ServerlessLLM's answer is to **migrate the running inference away** to free the locality-rich GPU, and to make that migration cheap by exploiting what an LLM inference's state actually is.

The migrated state is **the tokens, not the KV cache** — typically 10s–100s of KB of token ids against 1–10s of GB of KV. The destination recomputes the KV cache from the tokens. That trade wins because recomputation is fast relative to generation: the paper cites recomputing KV for 1,000 tokens as taking about the time to generate 100 new tokens, an order-of-magnitude gap. Migration is **multi-round**, in the shape of VM live migration adapted to this asymmetry: the destination loads the model (if not already resident), receives the source's tokens so far, and recomputes KV while the source *keeps generating*; further rounds ship only the tokens generated since the last round, a shrinking residue; when the gap is close enough the source stops, the final token set travels via the request router, the router flips its route table to the destination, and the source's copy of the model is unloaded so the waiting model can start where its checkpoint is local. User-visible interruption is confined to the final hand-off. Failure cases (source or destination failing during load or during resume) abort or cancel the migration with defined clean-up rather than leaving half-moved state — a protocol shape the corpus has already banked independently from Llumnix (IDEA-LEDGER #48).

**d) Startup-time-optimised scheduling.** The controller's scheduler chooses the server that minimises *estimated startup time*, not the first idle GPU. It maintains two estimators. Loading time is estimated as **q + n/b** — queuing time in that server's (deliberately sequential, per-server) loading queue, plus model (partition) size over the bandwidth of the slowest tier involved in the pipelined path — with bandwidth figures continuously corrected from the loading latencies servers actually report. Migration (resume) time is estimated as **a·(t_in + t_out) + b** with per-model parameters, the output-token count inferred from inference duration and average per-token time via the request router rather than by polling servers. A dynamic-programming step selects among load-here / load-there / migrate-to-free combinations. Server and storage-locality state (which checkpoint sits in which tier on which server) is kept in a reliable key-value store (etcd/ZooKeeper class), updated on assignment and on completion, so the scheduler can recover from its own failure; the paper reports the asynchronous implementation handling thousands of loading tasks per second. If no GPU is free even after considering migration, the task waits and retries on release.

## 4. Reported results — as reported, with hardware context

All figures are the paper's own, as reported; nothing here is re-measured or extrapolated. **Fleet results on datacentre GPUs; §5 separates mechanism from magnitude.**

**Setup (§7.1).** Two testbeds: (i) a single GPU server with **8× NVIDIA A5000**, 1 TB DDR4, 2× AMD EPYC 7453, two PCIe 4.0 NVMe 4 TB SSDs in RAID 0 (12 GB/s read throughput in the loader tests) and two SATA 4 TB SSDs in RAID 0, connected at 1 Gbps to a storage server running MinIO (S3-compatible) object storage; (ii) a cluster of **4 servers** on 10 Gbps Ethernet, each with **4× NVIDIA A40**, 512 GB DDR4, 2× Intel Xeon Silver 4314, and one PCIe 4.0 NVMe 2 TB SSD. Models: OPT, LLaMA-2, and Falcon families at multiple sizes, FP16 checkpoints; LoRA adapters in PEFT format for the adapter test. Datasets GSM8K and ShareGPT (inputs truncated to 2,048 tokens, the models' context limit in this setup); cluster workloads synthesised from the Azure serverless trace with bursty arrivals (Gamma distribution, CV = 8, following AlpaServe's method). Loader microbenchmarks clear page and inode caches and read randomly among 20 copies of each checkpoint to simulate cold, real-world access.

**Checkpoint loading (§7.2):**

- Headline (abstract/introduction): loading is **3.6–8.2× faster** than the existing systems compared, across the models tested.
- Smallest model, OPT-2.7B: **6× faster than PyTorch, 3.6× faster than Safetensors**. Largest model, LLaMA-2-70B: **8.2× faster than PyTorch, 4.7× faster than Safetensors**. Loading time depends on checkpoint size, not model family (OPT-13B and LLaMA-2-13B load alike).
- Why the mmap baseline loses, as measured: Safetensors incurred **112K page faults** on a cold LLaMA-2-7B load; PyTorch is about 2× slower than Safetensors in their setup because it copies data into host memory and then again into GPU memory.
- LoRA: a 1 GB rank-32 adapter for LLaMA-70B loads in **83.5 ms vs Safetensors' 370 ms — 4.4×**.
- Bandwidth: against FIO/MinIO optimal-throughput baselines per medium, the model manager **saturates the full bandwidth of each storage medium tested**, and is *better* suited to faster media (RAID-0 NVMe) than the baselines, which do not adapt to newer, faster storage.
- Ablation (throughput multipliers as each optimisation is added over a read-by-tensor base, RAID-0 NVMe, OPT models): bulk reading **1.2×** (small-tensor reads are the tax), direct I/O **2.1×**, multi-threading **2.3×**, pinned memory **1.4×**, pipelining a final **1.5×**. Maximum bandwidth is reached with **4 CPU cores** and a 16 MB bulk-read chunk size.

**Scheduler and migration in the cluster (§7.3):**

- Against a locality-agnostic serverless scheduler and a preemption-based Shepherd variant (Shepherd*, strengthened with ServerlessLLM's own loading-time estimator so placement quality is equal and only the eviction primitive differs): at 1.4 requests/s on GSM8K with OPT-6.7B, ServerlessLLM's P99 latency is **1.27× better than Shepherd* and 1.95× better than the serverless scheduler** (53 migrations vs 9 preemptions over 925 requests). On ShareGPT at the same rate, Shepherd*'s P99 is up to **2× worse** than ServerlessLLM's under locality contention, and Shepherd* reads checkpoints from SSD **2× as often**.
- Largest stress case (OPT-30B, ShareGPT; the 66 GB model leaves room for only two models in main memory, minimising locality's advantage): ServerlessLLM still achieves **35% lower P99 than the serverless scheduler and 45% lower than Shepherd***.
- Estimator accuracy, as reported: GPU-time estimation error bounded at 5 ms, SSD loading error at 40 ms, with a noted instability — CUDA state clean-up (`torch.cuda.empty_cache()`) during migration caused an average 25.78 ms underestimation, and a maximum 623 ms underestimation in 1 of 119 migrations.

**Whole system (§7.4):**

- Headline (abstract): **10–200× latency reduction** across various LLM inference workloads versus state-of-the-art serverless systems (KServe 0.10.2; Ray Serve 2.7.0, and a Ray Serve variant the authors extended with a local SSD LRU checkpoint cache — both Ray variants given local-SSD checkpoints and an exclusively-occupied 10 Gbps network for download estimates, i.e. strengthened baselines).
- Worked example (OPT-6.7B, GSM8K): average model startup **0.8 s (ServerlessLLM) vs 12.1 s (Ray Serve) vs 8.2 s (Ray Serve with Cache)** — over 10×; even granting Ray Serve a 100 Gbps network, its average falls only to 3.8 s, still **4.7× slower** than ServerlessLLM. The loader's advantage grows with model size because large models load partitioned across GPUs over parallel PCIe links.

## 5. Position in the corpus

The corpus's resident-session doctrine (IDEA-LEDGER **#1**: the resident session object with token-level residency, rank 1) says, in effect: *keep the session hot; never pay re-entry.* ServerlessLLM prices the opposite regime with equal rigour: *assume nothing is hot; make re-entry so cheap that hotness stops mattering.* These are not rival claims about the same workload — they are optima for different workload shapes, and the dossier's job is to state the boundary honestly.

**Where residency wins, and it is most of Volmarr's world.** A personal, single-user runner has one dominant conversation, a small zoo actually in rotation, and a user who experiences every switch personally. Keeping the active session resident costs memory that is otherwise idle; evicting it to save that memory buys nothing anyone can spend, and every cold start is paid by the one user, in full, in the middle of a conversation. The corpus's arithmetic (IDEA-LEDGER #10/#11: spill idle sessions, never the running one; restore beats recompute for long prefixes) already encodes this. At personal scale, ServerlessLLM's scheduler, migration machinery, and multi-server locality logic have no substrate: there is no second server, no queue of tenants, no multiplexing gain to harvest.

**Where cold-start optimisation is the right spend.** The regime flips when three conditions hold together: (i) the zoo is large relative to memory, so most models are cold most of the time by arithmetic, not by policy; (ii) demand per model is bursty and unpredictable, so pre-warming everything is waste and pre-warming the wrong thing is the common case; (iii) many independent users/tenants share the fleet, so cold-start latency is amortised infrastructure cost rather than one person's interrupted evening. That is the cloud serverless market the paper addresses, and — at much smaller scale — any future multi-persona, multi-model local deployment in which a dozen specialists share one card and each is invoked rarely. The boundary is therefore not "cloud vs local" but **duty cycle per model**: high duty cycle → residency; low duty cycle across a large zoo → priced, optimised cold starts.

**What transfers regardless of regime — the two pieces this wave exists to bank.**

1. **The loading pipeline.** Every runner, resident-doctrine or not, loads models, and load time is user-visible on *every switch* — the first launch of the day, the persona change, the sidecar invocation, the return to the main model after a summariser ran. Residency reduces how *often* loads happen; it does nothing to how *long* each surviving load takes. ServerlessLLM's loader is a complete, ablated, measured answer to "what does a load path cost when it is built naively, and what is each fix worth" — and its fixes (bulk sequential reads, direct I/O over fault-driven mapping for the bulk transfer, parallel staging, overlap with initialisation) are properties of a single machine's storage hierarchy as much as of a cluster's. This is the dossier's primary transfer; §6a develops it.
2. **The profiling-matrix discipline, in estimator form.** ServerlessLLM's scheduler is only as good as its per-(model, tier, server) startup-time estimates, continuously corrected by measured load latencies. That is the same discipline the corpus demands of benchmarks — IDEA-LEDGER **#44**, the measurement law (a number is real only with its scenario, model, workload, and machine state disclosed) and its sibling #33 (measure per (model, workload), never quote a context-free figure) — applied *inside* the system, at runtime, as an operational record rather than a publication rule. Mélange (sibling dossier, this wave) makes the same move for allocation. The shared lesson: **a zoo you cannot price per (model, device, tier) from measurements is a zoo you are scheduling by folklore.**

## 6. Applicability

### (a) Ollama model switching on the fleet — the load-path lesson *(labelled judgement)*

*The following is this dossier's judgement, applying the paper's measured mechanism to Ollama/llama.cpp-class Go/C++ runners on Volmarr's fleet. It is not a claim the paper makes.*

An Ollama model switch today pays, in sequence: evict/unload the old model, open the new GGUF, establish its memory mapping, allocate GPU/CPU buffers, and then — the hidden phase — **fault the weights in** as execution first touches each page. The corpus's virtual-memory dossier (`memory/virtual-memory-and-caches.md`) prices exactly this: with mmap-based loading, first-touch page faults are not an implementation detail, they are a *phase of the load*, paid lazily, unpredictably, and partly inside what looks like first-token latency. ServerlessLLM's measurement makes the same point from the other side: its mmap baseline's cold-load penalty is legible as a fault count (112K faults for a 7B), and its direct-I/O loader's advantage is partly that it converts that lazy, fault-driven population into an explicit, parallel, saturating transfer whose cost is known *before* inference starts.

The transferable lessons for a Go runner's own load path, in the paper's ablation order (multipliers as reported in §4, on its hardware — the *ordering and the anatomy* transfer, the numbers do not):

1. **Read in bulk, sequentially, in large chunks.** Per-tensor/per-layer small reads tax throughput before any device limit is reached (bulk reading alone: 1.2× in the ablation, and the tax grows with tensor count). A GGUF's layout is already largely sequential; the load path should exploit that with large buffered reads rather than many small `pread`s through the mapping layer.
2. **For the bulk transfer, prefer explicit reads over fault-driven mmap population — or prefault deliberately.** The honest local menu has three entries: keep mmap but prefault/populate the mapping in parallel before first inference (the weight-arena discipline of IDEA-LEDGER #41: alignment, huge pages, deliberate prefaulting); stage through pinned/locked host buffers with DMA-style transfer to the GPU; or read directly with direct-I/O semantics where the platform offers them. What ServerlessLLM rules out is the fourth entry — *do nothing and let faults happen during generation* — because it makes load time unmeasurable, and an unmeasurable load cannot be scheduled, budgeted, or honestly reported (IDEA-LEDGER #6's disclosure duty applies to load events too).
3. **Parallelise across the hierarchy you actually have.** Multi-threading the read (2.3× in the ablation) and pipelining tier-to-tier movement (1.5×) are not datacentre luxuries: a laptop NVMe SSD likewise needs queue depth to reach its bandwidth, and a load that reads-then-copies-then-uploads serially leaves each stage idle two-thirds of the time. On the fleet this means: parallel readers over the GGUF, staged host buffers, GPU upload overlapped with the next read — and, on the Strix Halo APU, see §7 on why the "upload" stage changes shape under unified memory.
4. **Overlap loading with everything that does not need the weights.** ServerlessLLM's manager/inference split — bytes stream in while the process initialises and sets pointers — maps locally to: tokeniser/template setup, KV-arena sizing (IDEA-LEDGER #12's measured placement), sampler and session restoration should proceed *concurrently* with weight streaming, not after it. A switch whose phases are serial is paying sum-of-parts for what could cost max-of-parts.
5. **Keep the second model warm in the cheap tiers, and say what "warm" means.** Page-cache warmth is the local, accidental version of ServerlessLLM's deliberate DRAM-tier caching: a model loaded once this boot reloads faster, and the difference is real, user-visible, and currently unrecorded. The disciplined version is small: record per-model load times split by cache state (cold / page-cache-warm / resident), per device — which is precisely the estimator habit of §5, and precisely what #44's disclosure law would demand of any published switch-time figure.

None of this argues for adopting ServerlessLLM's format or system. GGUF is the fleet's format and its mmap path has real virtues (instant start for small models, shared pages across processes). The argument is narrower: **measure the load as a pipeline with named stages and a fault count, then spend on the stage that is actually slow** — the paper demonstrates that, on its hardware, the naive path left roughly an order of magnitude on the table in exactly those stages.

### (b) Fleet-scale note

ServerlessLLM's cluster machinery (locality store, migration, DP scheduling) is recorded here as *priced prior art*, not as a build proposal for a three-machine fleet. Its local echo is §6a's estimator habit and IDEA-LEDGER #48's handoff protocol shape, both already in the ledger. If a future local router ever fronts several machines, this dossier — not the llama-swap/router incumbents of §7 — is the corpus's reference for what startup-time-optimal placement costs and requires.
