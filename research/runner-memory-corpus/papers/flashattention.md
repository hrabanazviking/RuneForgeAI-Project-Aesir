# FlashAttention — Fast and Memory-Efficient Exact Attention with IO-Awareness

## 2. The problem as the authors frame it

Self-attention costs time and memory quadratic in sequence length N, which is what blocks Transformers from using long context. The paper's distinctive move is its diagnosis of *why* the standard implementation is slow, and it is a memory-traffic diagnosis, not a FLOP diagnosis:

- The standard implementation computes attention in separate steps — form the score matrix S = QKᵀ, apply softmax to get P, multiply P by V — and **materialises the N×N matrices S and P in high-bandwidth memory (HBM)** between steps. That is O(N²) memory, and each step re-reads and re-writes large intermediates through the slowest level of the GPU memory hierarchy.
- Most of the operations involved (softmax, masking, dropout, elementwise work) are **memory-bound**: their runtime is set by how many bytes move between HBM and the chip, not by arithmetic. The paper's hardware anchor, stated in its background section: an A100 carries 40–80 GB of HBM at 1.5–2.0 TB/s, against 192 KB of on-chip SRAM per streaming multiprocessor at an estimated ~19 TB/s — SRAM is roughly an order of magnitude faster and many orders of magnitude smaller.
- The large literature of *approximate* attention methods (sparse, low-rank, and combinations) attacked the FLOP count, often to linear complexity, yet frequently failed to beat standard attention in wall-clock time and saw little adoption. The authors' explanation: those methods optimised the wrong quantity. They reduced arithmetic while ignoring IO — the reads and writes between memory levels — which is what actually sets the runtime of a memory-bound operation.

The problem, in the paper's own framing, is therefore: **compute *exact* attention while accounting for reads and writes between levels of GPU memory** — "IO-awareness" — instead of approximating attention to save FLOPs. This is the kernel-level statement of the claim the corpus's memory-wall dossier (`memory/memory-wall-and-roofline.md`) makes at system level: for this class of work, bytes moved, not operations counted, are the scarce resource.

## 3. Core mechanism in our own words

FlashAttention computes exactly the same attention as the standard implementation — no approximation, no dropped interactions — but never lets the N×N score or probability matrix exist in HBM. Three established techniques are combined to make that possible inside a single fused CUDA kernel:

**Tiling.** Q, K, V are cut into blocks sized to fit in on-chip SRAM. The kernel loads one block of K and V into SRAM, then streams blocks of Q past it (in the published Algorithm 1 the outer loop runs over K/V blocks and the inner loop over Q blocks), computing each block's partial scores, softmax contribution, and output contribution entirely on chip. The only things written back to HBM are the output block and two small per-row statistics. Because S and P blocks live and die in SRAM, HBM traffic and memory footprint stop being quadratic: extra memory beyond inputs and output is O(N) — one running maximum and one running sum per row — instead of O(N²).

**Online softmax.** Tiling is only possible because softmax can be computed incrementally. A row's softmax needs the row maximum (for numerical stability) and the sum of exponentials over the *whole* row, which a tiled kernel has not seen yet. The online-softmax construction keeps, per row, a running maximum m and a running sum ℓ of exponentials relative to that maximum. When a new block raises the maximum, the previously accumulated output and sum are rescaled by a correction factor (an exponential of the difference of the old and new maxima) before the new block's contribution is added. Each block is therefore processed with purely local statistics, and a final division by the accumulated ℓ produces the exact result. The pair (m, ℓ) — later compressed into a single logsumexp value by FlashAttention-2 — is the entire state the tiling needs.

**Recomputation in the backward pass.** Training's backward pass normally needs S and P, which is why standard implementations store them. FlashAttention stores only the output O and the per-row statistics (m, ℓ) from the forward pass, then **recomputes S and P block by block in SRAM during the backward pass** from the still-resident Q, K, V. This deliberately spends extra FLOPs to save HBM traffic. The paper's Figure 2 makes the trade concrete (GPT-2 medium, sequence length 1024, head dimension 64, 16 heads, batch 64, on an A100): standard attention performs 66.6 GFLOPs with 40.3 GB of HBM reads/writes in 41.7 ms; FlashAttention performs *more* arithmetic — 75.2 GFLOPs — but moves only 4.4 GB through HBM and finishes in 7.3 ms. More compute, ~9× less traffic, ~5.7× faster on that measurement: the paper's thesis in one table.

**IO complexity (the paper's Theorem 2).** With N the sequence length, d the head dimension, and M the SRAM size, standard attention needs Θ(Nd + N²) HBM accesses, while FlashAttention needs Θ(N²d²/M). For typical values the paper cites (d of 64–128, M around 100 KB), d² is much smaller than M, so FlashAttention's traffic is many times smaller; the paper further proves a matching lower bound — no exact-attention algorithm can asymptotically beat this access count across all SRAM sizes in the stated range — and extends the construction to **block-sparse attention**, whose IO cost improves by a factor proportional to the sparsity, as a proof that the primitive can carry approximate methods too.

## 4. Reported results — as reported, with hardware context

All figures below are the paper's own measurements, on **NVIDIA A100** hardware (attention microbenchmarks on a single A100 with 40 GB HBM; end-to-end training runs on 8× A100), unless a line says otherwise. Nothing here was measured on consumer hardware.

- **Attention kernel (forward + backward):** up to **3× faster** than the standard PyTorch implementation across common sequence lengths 128–2K in the paper's benchmark sweep, scaling to 64K; the GPT-2 attention computation shown in Figure 1 is **7.6× faster** than the PyTorch implementation. Runtime still grows quadratically with N (the FLOPs are unchanged in order) — it is the constant, set by HBM traffic, that collapses.
- **Memory footprint:** linear in sequence length; up to **20× more memory-efficient** than exact-attention baselines, and more memory-efficient than the approximate baselines tested; every baseline except Linformer ran out of memory before 64K on the A100, and FlashAttention used 2× less memory than Linformer there. (The follow-up paper restates the saving as 10–20× depending on sequence length.)
- **BERT-large (sequence length 512):** training time 17.4 ± 1.4 minutes vs 20.0 ± 1.5 for NVIDIA's MLPerf 1.1 record implementation — a **15% end-to-end speedup** over the standing speed record, averaged over 10 runs on 8× A100.
- **GPT-2 (sequence length 1K, OpenWebText, 8× A100):** up to **3× end-to-end speedup** over the HuggingFace implementation and up to **1.7–1.8×** over Megatron-LM at identical perplexity (e.g. GPT-2 medium: 6.9 days vs 21.0 days HuggingFace and 11.5 days Megatron-LM). Trained at 4K context, FlashAttention GPT-2 was still ~30% faster than Megatron-LM at 1K while scoring **0.7 perplexity better**.
- **Long-Range Arena (sequence lengths 1K–4K):** **2.4× speedup** over standard-attention baselines at comparable accuracy; block-sparse FlashAttention reached 2.8× and was faster than every approximate method tested.
- **New capabilities from longer context:** first Transformer to beat chance on Path-X (sequence length 16K, **61.4% accuracy**); block-sparse variant first to beat chance on Path-256 (sequence length 64K, **63.1%**); long-document classification gains reported as **6.4 points of lift** in the abstract (per-dataset: MIMIC-III micro-F1 52.8 → 57.1 from 512 → 16K tokens; ECtHR 72.2 → 80.7 at 8K).

**Hardware-generation caveat — what survives on Turing (RTX 2060 Max-Q, compute capability 7.5).** The paper itself is written against A100 (Ampere), and every number above is an A100 number. But the *algorithm* is stated parametrically in SRAM size M, and that is what transfers:

- **What survives in full:** exactness, the O(N) extra-memory property, and the qualitative win — never materialising S/P removes the quadratic HBM term on any GPU with an SRAM/HBM hierarchy, which is every GPU in the corpus. The IO bound Θ(N²d²/M) is a theorem about the algorithm, not about Ampere.
- **What shrinks:** the constant. Turing's per-SM shared memory is substantially smaller than the A100's 192 KB per SM the paper quotes, and its HBM (here GDDR6) bandwidth is far lower, so M in the bound is smaller and the traffic advantage over standard attention, while still large, is smaller than on A100. Block sizes must be retuned to the smaller SRAM; the paper's own Figure 2 (middle) shows runtime improving with block size only until other factors bind — on a small-SRAM part that ceiling arrives earlier.
- **What does not transfer at all:** the absolute speedups. A 2060-class card has a fraction of an A100's tensor-core throughput and memory bandwidth; quoting 3× or 7.6× for it would be inventing a measurement. The honest statement the paper supports is directional: on memory-bound attention, cutting HBM accesses by ~9× at the cost of ~13% more FLOPs is the right trade wherever compute is cheaper than bandwidth — and that condition holds *more* strongly, not less, as one moves down the hardware range (see §6a).

## 5. What it changed in practice

FlashAttention reset the default expectation for what an attention implementation is: a single fused, tiled kernel that treats HBM traffic as the cost function. Concretely, in the systems the corpus covers:

- **It became the reference attention path in training and inference stacks.** PyTorch's scaled-dot-product attention, Hugging Face integrations, and the major serving engines all route to FlashAttention-family kernels where hardware allows; FlashAttention-2 (§ sibling dossier) is the version most widely deployed, and the FlashInfer dossier shows the serving world rebuilding around its tiling template.
- **In ggml / llama.cpp** — the substrate under Ollama — the same design appears as the engine's Flash Attention implementation: tiled attention that never materialises the full N×N score matrix, with attention memory linear rather than quadratic in sequence length, implemented on the **CUDA, Metal and Vulkan** backends (SYCL has received sparse Flash Attention work), controlled by `-fa, --flash-attn [on|off|auto]` and defaulting to `auto` — on where the backend supports it (corpus: `runners/llamacpp-ggml.md` §6). In that stack Flash Attention is also the **gateway feature for quantised KV cache**: the quantised cache types are tied to Flash Attention being active, per the llama.cpp/Ollama documentation as read for the corpus.
- **In Ollama itself**, Flash Attention moved from an opt-in flag to automatic use where backend and device support it during late 2025, with `OLLAMA_FLASH_ATTENTION=1/0` as the force on/off override (corpus: `runners/ollama.md` §4.5). For the improved-Ollama work this matters doubly: it is both a speed feature and the precondition for the KV-cache quantisation that stretches a 6 GB card's context.
- **Conceptually**, it retired "approximate attention for speed" as the field's default direction: after this paper, the burden of proof sits on any approximation to beat an exact kernel that is already IO-aware — a shift visible across the corpus's later paper dossiers (e.g. speculative and eviction methods are routinely benchmarked *with FlashAttention on*, as in `papers/lookahead-decoding.md`).

## 6. Applicability

### (a) Ollama on a 6 GB consumer GPU (RTX 2060 Max-Q, Turing)

Reason from the paper's own IO analysis, separating the two inference phases:

- **Prefill is where FlashAttention pays, and on 6 GB it pays twice.** Processing a prompt is attention over N_q = N_kv = prompt length: the standard implementation's S/P materialisation is quadratic in exactly the quantity a long character card + history makes large. Tiling removes both the quadratic *traffic* (speed: time-to-first-token) and the quadratic *activation memory* (capacity: at long prompts the S/P buffers of a naive implementation can rival the KV cache itself — memory a 6 GB card does not have). For long-context chat, FlashAttention-style prefill is not an optimisation but an enabler.
- **Batch-1 short-context decode is where it does not pay.** In decode, each step's query is a single token: the score "matrix" is a 1×T vector, there is no N² intermediate to avoid materialising, and the step's cost is the compulsory streaming of the weights plus the KV cache read — a GEMV bandwidth problem that tiling cannot reduce, because every KV byte must be read exactly once regardless of order. The corpus's roofline analysis (`memory/memory-wall-and-roofline.md` §3.2) puts batch-1 decode at ~1 FLOP/byte, orders of magnitude left of any ridge point: the binding resource is bytes, and FlashAttention's contribution — avoiding *redundant* bytes — has almost nothing to act on when the query length is 1. Expecting a Flash Attention toggle to speed up single-stream short-context generation is a category error; its decode-side value appears only as context grows long (the KV read dominates and kernel quality on that read starts to matter), under batching, or in speculative/multi-token verification steps where the query length is again > 1.
- **The capacity corollary for 6 GB:** because quantised KV in the ggml/Ollama stack is gated on Flash Attention (§5), enabling it is what unlocks q8_0/q4_0 cache types — roughly halving / quartering cache bytes (corpus: `runners/ollama.md` §4.5). On the target card that coupling is worth more context headroom than the kernel's direct speedup.
- **Turing note:** the target card predates Ampere. The algorithm needs only SRAM tiling and FP16/BF16 tensor-core matmuls, both of which Turing has; block sizes must be chosen for its smaller shared memory. Nothing in the paper's analysis requires Ampere-or-later features — that requirement only enters with FlashAttention-3 (see its dossier).

### (b) Project Aesir

- **Adopt HBM-access counting as a first-class kernel metric.** Aesir's kernels should be specified and graded the way this paper grades attention: bytes moved between each pair of memory levels, stated alongside FLOPs, with the roofline dossier's discipline (measured sustained bandwidth as the roof). A kernel review that reports only FLOPs is, after this paper, an incomplete review.
- **Never materialise the score matrix — at any layer, on any backend.** The tiling + online-softmax pattern (running max, running sum, rescale-on-update; logsumexp as the saved statistic) is architecture-independent mathematics. It applies to Aesir's AMD, NPU and ARM targets exactly as to CUDA, with tile sizes re-derived from each target's on-chip memory. The saved (m, ℓ) pair is also the composable partial state that FlashInfer later builds its whole scheduling model on — designing Aesir's attention around that state from the start keeps split-K, chunked prefill and prefix composition available later.
- **Recomputation is a legitimate memory strategy, not a fallback.** Where Aesir is bandwidth-bound (its decode regime, per the accelerator-first law's own measurements), spending FLOPs to avoid storing or re-reading intermediates is the winning direction of trade. The same logic grades Aesir's compression school: a packed form that costs extra arithmetic to decode but moves fewer bytes is FlashAttention's Figure 2 trade restated.
- **Exactness is a feature to keep.** FlashAttention beat approximations without approximating. Aesir's attention should hold the same line — exact by default, with any lossy variant (eviction, quantised cache) layered explicitly and graded separately, as the corpus's KV dossiers do.
