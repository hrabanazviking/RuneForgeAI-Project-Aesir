## 2. The problem as framed

The paper's problem statement is the cleanest in this wave, because it is stated as a complexity claim. Guided generation — producing token sequences that conform to a regular expression or a context-free grammar — is, in most implementations, done by *biasing scores*: at each step, evaluate **the entire vocabulary** against the constraint and the prefix sampled so far, set the probabilities of invalid tokens to zero, and sample from the rest. The paper prices that directly: "This approach entails a fixed $O(N)$ cost for each token generated, where $N$ is the size of the LLM's vocabulary" — with $N$ "often on the order of $10^4$ or larger" in the paper's 2023 frame (the companion dossier's 128k vocabularies make the same point louder). Worse, for anything beyond a trivial pattern the per-token check is not a table lookup but *matching or parsing an incomplete string*: partial matching re-run from the start of the sequence each step has a cost that also grows with sequence length. The paper's motivating comparison (§4) is against a contemporary implementation doing exactly that, whose runtime it shows growing steeply with output length while its own stays near-flat.

The stakes the paper attaches to the cost are not raw speed for its own sake. Guided generation is how an LLM's output becomes *usable by a program* — "to make LLM model output usable under rigid formatting requirements that are either hard or costly to capture through fine-tuning alone" — and it is the mechanism for "the construction of reliable interfaces by guaranteeing the structure of the generated text." If guidance costs $O(N)$ work plus a re-parse per token, reliable interfaces are taxed on every token of every call, and the tax is worst exactly where the interface matters most: long structured outputs. The paper's question, verbatim in substance: *how can we efficiently match or parse incomplete strings according to a regular expression or CFG and determine the masks at each iteration?*

The fidelity half of the problem, as this corpus frames it (§5): the mask defines a conditional distribution — the model's distribution restricted to valid continuations and renormalised. The paper formalises exactly that object (§3): masking is multiplication of the model's categorical by a boolean mask, i.e. an *un-normalised conditional distribution* whose support is the valid set. A guidance method is therefore faithful by construction *if and only if* its valid set is exactly right at every step — which is why the paper spends its second half on the genuinely hard part, partial tokens that straddle grammar-symbol boundaries, where a valid set computed naively is wrong (§3). A fast mask over the wrong set is not an approximation of guided generation; it is a different, unguaranteed sampler that can both forbid valid text (distorting the conditional, potentially to the point of emptying it — deadlock, where no token may legally follow) and permit invalid text (breaking the guarantee the caller paid for).

## 3. Core mechanism in our own words

**Reformulation: generation as FSM transitions.** The paper's move is to stop thinking of guided generation as *checking strings* and start thinking of it as *walking a machine*. A regular expression is a finite-state machine $(Q, \Sigma, \delta, q_0, F)$: states, alphabet, transition function, start state, accept states. Generation maintains the FSM's current state alongside the token sequence. After each sampled token, the FSM advances by consuming that token's characters; the set of legal next tokens is exactly the set of vocabulary strings the FSM can consume *starting from the current state*. Because the state is carried forward incrementally, matching never restarts from the beginning of the sequence — the machine can be "arbitrarily started and stopped" between sampling steps, which is what makes guidance composable with an autoregressive loop at all.

**The index: pay $O(N)$ once, $O(1)$ per step.** The decisive construction is a map

$$\sigma : Q \;\to\; \mathcal{P}(V)$$

from each FSM state to the subset of the vocabulary accepted starting from that state. It is built once, before generation, by running every vocabulary string $v \in V$ through the FSM *from every state that could consume its first character* and recording, for each complete walk, the start state and the states traversed (the paper's Algorithms 3–4: `find_sub_sequences` enumerates the state sequences accepting $v$; `map_states_to_vocab` files $v$ under each walk's start state). Multi-character tokens are the reason for the "every start state" care: a token like `".2"` or `"42"` consumes several characters and crosses several FSM states, and the same token must be findable from whichever state generation happens to be in when it is considered.

At runtime the mask step collapses to: look up $\sigma(\text{current state})$, zero the logits of everything not in it, sample, advance the FSM by the sampled token's recorded state sequence. With $\sigma$ as a hash map, the paper's claim is that the mask step costs **$O(1)$ on average** — independent of vocabulary size and of sequence length. The $O(N)$ vocabulary work has not vanished; it has been *moved*, from per-token runtime to a one-time index construction whose cost is amortised over every generation that reuses the constraint, and whose memory cost the paper argues is modest in practice: not every vocabulary string is accepted from any state, and not every state is reached by any string, so the stored index is far sparser than the $|Q| \times |V|$ worst case suggests.

**Worked shape of the idea (the paper's own example, retold).** For the float pattern `([0-9]*)?\.?[0-9]*` and a toy vocabulary {`"A"`, `"."`, `"42"`, `".2"`, `"1"`}: in the start state, `"A"` is masked and the rest are legal. Sample `".2"` and the FSM lands in a state where only `"42"` and `"1"` remain legal; sample `"1"` instead and a different state leaves `"."`, `".42"`-class continuations and `"1"` legal with the mask effectively unchanged. Every one of those per-state legal sets is a row of $\sigma$, computed before the first token was sampled.

**From regex to CFG: the parser extension.** Regular expressions are the paper's complete, implemented-in-detail case. The extension to context-free grammars (§4 of the paper) is presented as a construction, and this dossier reports it as such — a design with worked reasoning, at a different maturity level from the regex algorithm:

- Grammars are handled by a **pushdown automaton / LALR(1) parser** rather than a bare FSM, because CFG symbols (terminals) are themselves recognised by lexing: each terminal has its own regex, hence its own FSM.
- The difficulty is *partial lexing*: having sampled tokens that concatenate to `"def f"`, a naive lexer reports `DEF NAME` — but the `f` is not a finished `NAME`; it may continue into `foo(`. The paper's resolution reuses the FSM machinery per terminal: a partially matched terminal corresponds to being *mid-FSM* in that terminal's machine, and the next legal vocabulary strings are those that either continue the partial terminal or, if the current FSM position is also an accept state, close it and begin a terminal the grammar allows next.
- For each parser state, the FSMs of all terminals readable in that state are combined, Algorithm 3 is applied against the combined machines, and the resulting parser configurations (PDA state, FSM state, candidate terminal set, and — for LALR reduce actions — the relevant stack prefixes) are entered into an index that, unlike the flat regex map, must be a **trie keyed by stack values**, because CFG validity can depend on more than the top of the stack.

That last dependence is the honest boundary of the design, and the companion dossier is what lies past it: XGrammar's context-independent/context-dependent split exists precisely because a CFG index cannot, in general, be completed in advance — the stack is unbounded. Outlines' paper shows the index idea at full strength where it is exact (regular constraints) and sketches its parser generalisation; XGrammar shows how to keep most of the precomputation benefit where exact completion is impossible.

**What the paper claims about scope.** The approach is **model-agnostic** — it needs only next-token logits — and applies to any autoregressive sampler in its Algorithm-1 form (the paper discusses greedy, beam and sequential-Monte-Carlo sampling as hosts). Guidance can start and stop mid-sequence, so constrained and unconstrained spans can be interleaved in one generation.

**Project evolution — kept separate from the paper, and dated.** The following is the state of the Outlines *project* as documented at the time of writing (accessed 2026-11-15), not claims of the 2023 paper: Outlines is now maintained by **.txt (dottxt-ai)** — Rémi Louf is its CEO/technical founder — having originated at Normal Computing. The current documented surface accepts **JSON Schema (including via Pydantic models), regular expressions, and context-free grammars (EBNF/Lark-style)**, plus choice/function-signature constraints, across integrations including Transformers, llama.cpp, vLLM and API models. Architecturally, the project has become a front end over **pluggable constraint backends** — its own `outlines_core` engine (the FSM-index lineage of this paper, reimplemented), **XGrammar**, and **llguidance** — selectable per deployment; the current documentation's own performance framing ("microseconds of overhead… compilation happens once, not every request") is the 2023 paper's thesis restated as product copy. Two consequences for a reader of this corpus: (i) when §4 of the XGrammar dossier reports "Outlines v1.0" as a baseline, that is a specific, dated version of a moving target, not the library's permanent speed; (ii) the modern fact that Outlines can *delegate to* XGrammar is the field's own verdict on §3 above — the index design won the interface, and the PDA design won the hardest grammars, and a production stack may well run both.

## 4. Reported results — as reported, with context

This paper is deliberately light on benchmark tables — its evidence is a complexity argument, worked examples, and one head-to-head timing comparison — and this section reports exactly that, without inflating it into a benchmark suite it does not contain.

**The complexity claim (the paper's central quantitative result).** Naive guided generation: $O(N)$ per generated token ($N = |V|$), plus partial-match/parse work that grows with sequence length. The index approach: the mask step is **$O(1)$ on average** per token (hash-map lookup of the precomputed state→token-set map), with index construction paid once, outside the sampling loop. The abstract's performance sentence is correspondingly qualitative: the approach "adds little overhead to the token sequence generation process and **significantly outperforms existing solutions**."

**The Guidance comparison (§3.2 of the paper).** Setup as reported: GPT-2 (vocabulary $N = 50{,}257$); the Guidance library as contemporary baseline, which the paper characterises as using partial regex matching re-applied from the start of the sampled sequence at each step and iterating over the vocabulary per step; the task is regex-guided generation of a Python variable name (`[^\W\d]\w*`) at temperature 0.1, timing a single generation call with `timeit` (one loop, one repeat — the paper is explicit that each point is a single sample) while varying `max_tokens` from 20 to 100. As reported in the paper's Figure (§3.2): Guidance's runtime grows steeply — roughly linearly-to-worse in generated tokens, reaching the ~100 s scale at 100 tokens — while Outlines' runtime stays near-flat, on the order of seconds across the same range. The paper itself adds the honest caveat, retained here verbatim in substance: "Barring any configuration oversights that might be creating a large runtime discrepancy, the observed scaling … is striking." The result should be read as evidence for the *scaling law* (flat vs. growing), not as a precise speed ratio between two libraries at their current versions.

**Index memory (§5 of the paper).** In the authors' tests with a slightly augmented Python grammar, "even naively constructed indices … are still only around **50 MB**", built with un-reduced DFAs — i.e. with redundant states the authors note could be reduced. This is the paper's only memory figure, and it is offered as evidence that the time/space trade (spend memory once, save time per token) is cheap at grammar scale.

**Illustrative correctness examples (§3.1).** With GPT-2-medium (355M): an unguided continuation rambles, while the regex-guided run answers the paper's prompts in-form — "Is 1+1=2? **Always**" under `\s*([Yy]es|[Nn]o|[Nn]ever|[Aa]lways)`; a year prompt constrained to `\s*19[0-9]{2}` yields a well-formed (if factually wrong — the paper's point is form, not truth) year; an IP-address regex yields a syntactically valid address. These are demonstrations that the guarantee binds, not accuracy evaluations.

**What the paper does not report.** No per-token microsecond latencies, no end-to-end serving throughput, no comparison against grammar engines of the llama.cpp class, and no distribution-quality evaluation (e.g. perplexity of guided vs. unguided text). Those gaps are exactly what the companion paper measures five years later — including against Outlines itself (§4 of `papers/xgrammar.md`) — and a reader should not back-fill them into this paper's record.

## 5. Position in the runner stack

Constraint is a **mask on logits**, and this paper is the source of the corpus's canonical formalisation of that fact: guided sampling is ordinary sampling with the categorical replaced by $\tilde{\alpha} = m(\tilde{S}_t) \odot \alpha$ — the model's distribution multiplied by a boolean mask and renormalised, i.e. sampling from the model's **conditional distribution over the valid set**. Everything about its stack position follows:

```
forward pass → logits → [GUIDANCE MASK: invalid logits := −∞ / probability := 0]
              → sampler chain (temperature, penalties as implemented, truncation — top-k / top-p / min-p …)
              → renormalise over survivors → sample → advance FSM / parser state with the sampled token
```

- **Mask before sampling, never after.** The paper's Algorithm 2 *is* mask-then-sample; there is no post-hoc variant in the design. Sampling first and rejecting invalid draws afterwards would not sample from the conditional distribution the mask defines, would waste forward passes, and — since a forward pass is the expensive step guidance exists to cheapen — would invert the paper's whole cost argument.
- **Masking renormalises over valid tokens only, and preserves relative probabilities within the valid set.** Zeroing invalid entries and renormalising is conditioning, not re-weighting: two valid tokens keep the odds ratio the model gave them. This is the fidelity standard for the whole wave. Its failure modes are worth naming because both are *mask-set* errors, not sampler errors: a mask that wrongly excludes a valid token silently conditions on a smaller event than the grammar specifies (in the limit, an empty set — deadlock, where the sampler has nothing legal to draw and an implementation must either crash, emit EOS illegally, or break its own guarantee); a mask that wrongly includes an invalid token breaks the structural guarantee downstream, where it will be discovered by a parser at the worst possible time. The paper's §4 partial-lexing analysis exists because mid-token, mid-terminal states are where wrong sets actually happen in practice.
- **Relative to the Wave 9 sampler chain (`papers/min-p-sampling.md`, `papers/mirostat.md`; IDEA-LEDGER #37): the mask is the chain's entry condition — a validity filter applied before truncation and temperature.** Truncation methods (top-k, top-p, min-p) answer "which of these tokens are plausible enough to consider?"; the mask has already answered "which of these tokens may exist at all?". Applying truncation first would let implausible-but-valid and plausible-but-invalid tokens compete for the same budget, and applying temperature before the mask is harmless to validity only because $-\infty$ (or 0 probability) is absorbing — the invariant an implementation must guarantee is that no later stage can resurrect a masked token or alter the relative odds of two valid ones except by its own documented rule. Mirostat's case is the sharp one: as a stateful controller that replaces the chain (IDEA-LEDGER #37's compose-or-substitute law), it must compute its surprise statistics over the *masked* distribution when guidance is active, or its feedback loop will chase probability mass the grammar has already deleted. Neither paper in this wave evaluates that combination; treat it as an open conformance item, not a composition that comes free.
- **Guidance state is decode state.** The FSM/parser state advances once per sampled token, is per-sequence, and must be checkpointed and restored with anything that checkpoints or restores the sequence (session resume, branching, speculation rollback — §5 of the companion dossier). The paper's start/stop property cuts the other way as well: because the machine can start and stop arbitrarily, a stack may constrain *spans* of a generation (a tool-call block inside free prose) — but the span boundaries then become part of the state discipline, and a mask left on past its span is a distribution distortion with no error message.

**The speculation interaction, from this design's side.** Outlines' 2023 text does not address speculative decoding — it predates the corpus's speculation line's maturity, and this dossier does not attribute a position to it. What can be said from the mechanism (labelled as inference, not paper claim): a flat FSM index is *rollback-friendly almost for free*, because FSM state is a single integer — verifying a draft token means looking up $\sigma$ at successive states, and rejecting a draft means restoring the integer saved before the draft, with no stack to unwind. The CFG/trie case inherits the general problem the companion dossier solves with its persistent stack. The stack rule (§5 of `papers/xgrammar.md`) is stated there and applies to both designs: tokens, sampler state and automaton state commit or roll back as one unit.

## 6. Applicability

### (a) Ollama / llama.cpp world

*Judgment in this subsection is labelled as such; the factual baseline is the corpus's runner dossiers.*

The llama.cpp world already embodies half of this paper's lesson and illustrates the other half by its absence. GBNF grammars in llama.cpp and Ollama's `format` parameter (a JSON schema or `"json"`, per `runners/ollama.md`) give the Go/llama.cpp-class stack a working constraint *feature*; the XGrammar paper's baseline results (§4 of the companion dossier) show that a grammar engine which interprets the constraint against the vocabulary at runtime pays heavily for it at CFG complexity and at batch. What this paper adds, as requirements language a stack should adopt (judgment):

- **R1 — The mask is a lookup, not a computation.** Whatever the constraint class, per-step mask cost must be independent of $|V|$ in the common case: precompute state→allowed-set once at grammar compile time (this paper's $\sigma$ for regular constraints; the companion's adaptive cache for CFGs), and make the per-step operation a retrieval plus application of a stored set. A design whose per-step cost scales with vocabulary size fails this paper's test regardless of its constant factor — vocabularies only grow.
- **R2 — Compile once, keyed by (grammar, vocabulary), reused across requests and sessions.** Index construction is the one $O(N)$ pass the design permits itself; it must therefore be cached, shared, and invalidated only when its keys change. This is the same interface IDEA-LEDGER #36 specifies ("grammar compiled once") — this paper is its earliest published justification in the corpus.
- **R3 — Correctness of the valid set at token boundaries is the conformance bar.** Test vectors must include tokens that split terminals, tokens that complete one terminal and start the next, and partial-terminal continuations of the `"def f" → "foo("` kind. A mask engine that is exact only when tokens align with grammar symbols is exact nowhere that matters.
- **R4 — Fidelity language belongs in the API contract.** A `format`/grammar option should promise, in writing: output is a draw from the model's distribution conditioned on the constraint; invalid tokens have probability exactly zero; relative probabilities of valid tokens are the model's. Without that sentence, "structured output" is a hope with a parser at the end of it, and silent distortions (a mask applied after temperature in a way that interacts with penalties, a truncated valid set) have no spec to be bugs against.
- **R5 — Start/stop guidance is a product surface, not an accident.** The ability to constrain a span — free prose, then a constrained block, then free prose — is what agent harnesses actually need (§6(b)); a stack should expose it deliberately, with the mask's on/off state visible in response metadata, rather than leaving whole-response grammars as the only mode.

### (b) The persona-chat case: constraint as the reliability floor under agent memory

Persona dialogue itself stays free — no grammar should be shaping what a character says to the user. But a persona *agent* is a program wrapped around that dialogue, and its internal generations are machine-read: tool and function calls, routing decisions, classifications — and, load-bearing for this programme, **memory extraction**.

The connection to `memory/agent-memory-architectures.md` is structural. That dossier shows persistent memory is a database with an editor, and that its failures concentrate at the *write*: extractions that invent, drop qualifiers, or arrive in a form the store cannot use. The write is a generation. If it runs unconstrained, its failure modes are syntactic before they are semantic — prose wrapped around the record, a field of the wrong type, a missing provenance slot — and each syntactic failure forces a bad choice: discard the write (the memory is lost), retry it (another draw, another chance to fail, latency on the memory path), or store a leniently-parsed fragment (a corrupt record the retrieval layer will later serve faithfully — the exact rot mechanism that dossier documents). **A memory write that must parse is a constrained-generation problem**, and this paper is why solving it is cheap: compile the memory-record schema into an index once, and every extraction thereafter is guaranteed-parseable at $O(1)$ mask cost per token. The editor's real work — truth, supersession, provenance, contradiction — then happens on records that at least *arrived whole*.

The same floor applies to tool calls in the persona stack (a malformed call is not a charming improvisation; it is a failed action) and to any structured sidecar — summarise-to-schema, safety classification, lorebook-key extraction. Design rule (judgment, shared with the companion dossier): *generations whose consumer is code run constrained, with versioned schemas; generations whose consumer is the user run free; and the boundary between the two is explicit in the harness, because start/stop guidance makes it technically easy to blur.* Outlines' historical contribution to that rule is that it made the constrained side a library call rather than a research project — which is why, of the two papers in this wave, this is the one whose *interface* (schema/regex/grammar in, guaranteed text out, any model) a Go stack should copy first, even where it adopts the companion's engine underneath.
