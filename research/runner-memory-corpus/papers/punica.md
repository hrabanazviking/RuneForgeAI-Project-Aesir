## 2. The problem as framed

Punica starts from the provider's side of the LoRA economy: machine-learning providers must serve a large number of specialised LoRA models *simultaneously* for different tenants. Each LoRA model is a base model plus a small trained delta — two matrices $A \in \mathbb{R}^{h_1 \times r}$, $B \in \mathbb{R}^{r \times h_2}$ per dense projection, with $r$ typically ~16 against dimensions in the thousands, adding, in the paper's figure, only **0.1%–1% of the base model's weight** per fine-tuned model (its §5.2 figure for the loading path is ~1%). Serving each such model “as if it were independently trained from scratch” therefore wastes the one resource that matters:

1. **Duplicated base weights.** If serving one model takes $k$ GPUs, the naive reading says $n$ LoRA models take $k \times n$ GPUs — although all $n$ share almost all of their weights. Even short of whole GPUs, the per-adapter-system answer of the day (a separate serving instance per merged model, as in S-LoRA's baselines) multiplies base-weight residency by the adapter count and strands each instance's memory and batch capacity behind its own adapter.
2. **Batching breaks by adapter.** Batching is, in the paper's guideline G2, the most effective consolidation lever in LLM serving — decode steps are so memory-bound that raising batch size from 1 to 32 barely moves step latency (its Figure 1 measurement: 11 ms → 13 ms at short sequence lengths on its setup). But conventional batching only works for requests *for the exact same model*. The moment a batch must mix adapters, the standard machinery has no batched operator for “same base projection, different small delta per request”: the fallbacks are a per-model loop (each sub-batch degenerates toward batch 1) or gathering/padding weights into a batched matmul (paying large extra memory I/O to materialise the gathered weights — quantified in §4). So a multi-tenant GPU either serialises by adapter or wastes its decode capacity on tiny per-adapter batches — the *kernel launch shape* is the failure, not the scheduler's intentions.
3. **KV and scheduling accounting follow the wrong unit.** Each request still owns a growing KV cache, and a cluster scheduler that places requests by *model* (affinity to wherever that merged model lives) cannot consolidate: GPUs sit partly idle holding different tenants' models while other GPUs saturate. The paper's reframing is that placement should follow *load and KV space*, not adapter identity — which is only possible once (2) is solved, because only a mixed-adapter batch makes a request placeable anywhere its base model runs.

The paper states its three design guidelines explicitly, and they are worth recording because the third one scopes the whole system: **(G1)** consolidate multi-tenant LoRA workloads onto a small number of GPUs; **(G2)** enable batching for *different* LoRA models, not just identical ones; **(G3)** *the decode stage predominates in serving cost, so only decode performance needs optimising* — everything else (including loading an adapter on demand) can use straightforward techniques. Punica is, by its own framing, a decode kernel plus the consolidation scheduler that kernel makes possible.

## 3. Core mechanism in our own words

**The decomposition (shared with the whole multi-LoRA line).** The base model's dense projections run once, batched, with ordinary matrix multiplication over one resident copy of the pre-trained weights. The LoRA addon — per request, $xAB$ for that request's adapter — is *not* merged and *not* looped per adapter; it is computed by one new kernel over the whole mixed batch. A GPU therefore holds exactly **one copy of the backbone**, however many LoRA models it serves in that batch.

**SGMV — Segmented Gather Matrix-Vector Multiplication.** The kernel is the paper. Its semantics:

- Sort/group the batch so requests sharing a LoRA model are *consecutive*. The batch is then a list of **segments**, one per distinct adapter present, described by segment indices (the cumulative boundaries $s_i$; $s_n$ = batch size). Each request's LoRA computation is a matrix-vector product against *its segment's* adapter matrices — a “gather” because the kernel must fetch, per request, the adapter slice its segment names, rather than reading one shared weight matrix.
- The LoRA addon is two SGMV launches per adapted projection: **SGMV-shrink** computes $xA$, contracting the hidden dimension down to the rank-$r$ bottleneck; **SGMV-expand** computes $vB$ (where $v$ is the shrink output), expanding back to the hidden dimension. No gathered weight copies are materialised — contrast Gather-BMM (§4), which stacks the needed weights into a temporary batched matrix and pays, by the paper's accounting, $s_n \times h_i \times h_o \times 2$ more elements of memory I/O than SGMV.
- **Two schedules for two regimes**, chosen by segment size. The LoRA index is bound to the CUDA grid's `blockIdx.y`, so each block works on one adapter's segment. When a segment is large (many requests share one adapter), the operation approaches a matrix-matrix product with real arithmetic intensity: the schedule splits the weight along the output-feature dimension and uses **Tensor Cores**. When every request has a distinct adapter (segment size 1), the operation degenerates to pure matrix-vector multiplication — totally I/O-bound — and a dedicated schedule maximises memory-bandwidth utilisation and deliberately *does not* use Tensor Cores, because there is no intensity for them to exploit. This regime-sensitivity is the kernel's real design content: “batching different adapters costs the same as batching the same adapter” (the paper's surprising headline observation, §4) is true only because the kernel changes strategy as sharing disappears, instead of padding everything into the shared case.
- **Batch bookkeeping is hoisted out of the layers.** Prefill and decode requests are mixed in a single model invocation (prefill capped at 1 request per batch to bound its latency effect; attention itself runs as separate BatchPrefill/BatchDecode kernels via FlashInfer, while dense projections and the LoRA addon treat all tokens as one batch). Requests are ordered prefill-first, decode after, same-adapter requests consecutive across that boundary where possible; the `BatchLen` structure and the SGMV segment indices are constructed *once per model invocation* and held constant across all layers — the paper notes this avoids recomputing them $L$ and $7L$ times respectively for an $L$-layer model.

**The system around the kernel.**

- **Consolidating scheduler.** Punica's cluster scheduler keeps, per GPU, the working set (current batch) and the free KV space. A new request goes to the GPU with the *largest* current working set that still satisfies two constraints — below the maximum batch size (profiled at **32** on A100, the paper's throughput/latency sweet spot) and enough KV memory for the new request — i.e. it deliberately packs busy GPUs busier, so lightly loaded GPUs drain to idle and can be released, and new GPUs are allocated only when none has room. Queued requests are served first-come-first-served as space opens.
- **On-demand adapter loading.** Because an adapter is ~1% of the base, loading one is an asynchronous host-to-device copy overlapped with running computation: the paper measures ~50 µs per layer and **~2 ms for an entire model** over PCIe Gen4 ×16, against a ~30 ms decode step — a newly arrived request's adapter is resident before the current invocation finishes, and the request joins the batch naturally. Adapter residency is therefore not a scheduling constraint at all in Punica's design; this is G3's “straightforward techniques suffice” made concrete.
- **Request migration by recompute.** When a GPU runs out of KV space, the scheduler evicts its *newest* request (preserving FCFS semantics) and re-adds it elsewhere as a new request: the destination re-runs prefill over the original prompt plus all tokens generated so far, rebuilding the KV there. Punica explicitly chooses recomputation over transferring KV, citing PagedAttention's costing that recompute is equal or better in most cases. Migration is also the consolidation tool: periodically moving requests off draining GPUs is what lets the cluster shrink.
- **KV layout.** A paged KV cache (PagedAttention lineage, via FlashInfer) with the batch dimension outermost and per-sequence pages — the paper contrasts this with the HuggingFace Transformers layout, whose inseparable batch forces every request in a batch to run decode steps until the *longest* finishes, wasting compute on completed requests. Continuous batching falls out of the layout, not out of extra machinery.
- **Implementation shape.** A Python/PyTorch library per GPU (Llama implementation adapted from HuggingFace Transformers; FlashInfer for attention; SGMV exposed as a PyTorch extension), with scheduler, frontend and runner written in Rust, runners spawning one Python subprocess per GPU. Deliberately the inverse of S-LoRA's shape: a kernel and a cluster scheduler, with the per-GPU library comparatively thin.

## 4. Reported results — as reported, with hardware and scale context

All figures are the paper's own. **Nothing below is a consumer-hardware or single-user number.**

**Setup.** Testbed #1: one server, one **NVIDIA A100 80 GB**. Testbed #2: two HGX A100 servers, **8× A100 40 GB each** (NVSwitch), used for tensor parallelism and the cluster experiment. Models: **Llama-2 7B, 13B, 70B**, LoRA applied to all dense projections, **rank 16 for all end-to-end experiments** (random adapter weights — the paper notes weights do not affect latency performance). Workloads: prompt/response lengths drawn from the ShareGPT distribution; four adapter-popularity distributions over requests — **Distinct** (every request a different LoRA model), **Uniform** ($\lceil\sqrt{n}\rceil$ models for $n$ requests, equally popular), **Skewed** (Zipf, $\alpha = 1.5$), **Identical** (all requests the same model). Baselines: HuggingFace Transformers + PEFT, DeepSpeed, FasterTransformer and vLLM — with the paper's explicit, baseline-favouring relaxations: FasterTransformer and vLLM did not support LoRA, so they are run **backbone-only** (no LoRA computation at all), and **model-switching costs are omitted for all baselines**. Maximum batch size 32 throughout the text-generation experiments.

**Headline claim (abstract, as reported):** with a fixed-size GPU cluster, **12× higher throughput** serving multiple LoRA models than state-of-the-art LLM serving systems, **while only adding 2 ms latency per token**.

**SGMV microbenchmarks (Testbed #1, as reported).** The LoRA operator is two SGMV launches, compared against a per-model loop and against Gather-BMM:

- *Distinct* (no sharing): SGMV latency rises 37 µs → 116 µs as batch grows 1 → 64 — batching cannot raise arithmetic intensity when no weights are shared, only parallelism. The loop baseline “behaves terribly”; Gather-BMM degrades fast on its gather step.
- *Uniform / Skewed* (partial sharing): SGMV rises only marginally, 37 µs → 46 µs over the same batch range.
- *Identical* (full sharing): SGMV is essentially flat, 37 µs → 40 µs, and beats `torch.bmm()` at its own semantics — the paper's inference is that SGMV implements the batched matmul more efficiently than the library BMM for LoRA shapes.
- *Rank sweep* (microbenchmark only, ranks 8/16/32/64): a batch of 1 costs ~42 µs at every rank; at batch 64 in the Distinct case, latency is 72 / 75 / 89 / 118 µs for ranks 8 / 16 / 32 / 64 respectively; under any sharing (Uniform/Skewed/Identical) latency stays ~42–45 µs across batch 1–64 at all four ranks.
- *Transformer-layer level:* with the LoRA operator integrated, raising batch 1 → 32 raises layer latency by only **72%** at sequence length 512 (the batching effect weakens at 2048, where attention dominates). Layer latency is “roughly the same across different workloads” — the property the paper calls **LoRA-model-agnostic performance**, and the premise its scheduler is built on: if layer cost does not depend on *which* adapters are in the batch, placement can optimise load alone.

**Text generation (as reported).**

- *Single GPU (Testbed #1), 1,000 requests (~101k tokens), FCFS, max batch 32:* Punica delivers **1,044 tok/s (7B)** and **693 tok/s (13B)** *consistently across all four popularity distributions*. Baselines match that class of throughput only in the Identical case and collapse as adapters multiply: in Distinct they are forced to batch size 1; in Uniform/Skewed their effective batch sizes are 1–3. In the Identical case **vLLM is slightly higher than Punica — 1,140 tok/s (7B) and 789 tok/s (13B)** — because, per the baseline relaxation above, vLLM ran backbone-only with no LoRA work at all. That inversion is the honest centre of the evaluation: Punica's claim is not “fastest single-model serving” but “multi-model serving at single-model speed”.
- *70B with tensor parallelism (8 GPUs, Testbed #2):* Punica holds **441–446 tok/s regardless of popularity distribution**; vLLM manages **21–25 tok/s** in the multi-LoRA cases against **457 tok/s** backbone-only — i.e. on this configuration the multi-adapter penalty for the baseline is roughly twentyfold, and Punica's is within a few percent.
- *Cluster deployment (16 GPUs, Testbed #2, 7B, one hour, Zipf-1.5 popularity, Poisson arrivals with a rising-then-falling rate):* the consolidating scheduler keeps active GPUs at or near maximum batch, migrates requests out when KV space runs out, and leaves drained GPUs idle (batch 0, releasable) — presented as a qualitative trace figure rather than a single summary number; the 12× headline is the paper's aggregate over its serving comparisons, not a figure read off this trace.

**Scale caveat, stated plainly.** The evaluation is A100 datacentre hardware, rank fixed at 16 end-to-end, adapters with random weights, and baselines that were *helped* (backbone-only, switching costs waived) and still lose on multi-adapter workloads — which strengthens the multi-adapter claim while meaning the Identical-case numbers, where the helped baselines win narrowly, are the correct calibration for what Punica does *not* claim. The “2 ms per token” is the paper's own summary of LoRA's added latency in its serving configuration, not a per-kernel figure.

## 5. Position relative to S-LoRA

Contemporaneous, independent, and — unusually — connected by a stated code lineage in one direction:

- **Same decomposition, different centre of gravity.** Both systems split $xW$ (batched, shared) from $xAB$ (per-request, unmerged) and refuse per-adapter model copies. Punica's contribution is concentrated in *the kernel*: SGMV is analysed in depth (roofline, two schedules, I/O accounting against Gather-BMM) and the surrounding system is a cluster consolidator built on the kernel's model-agnostic-cost property. S-LoRA's contribution is concentrated in *the memory system*: Unified Paging and tensor parallelism, with kernel performance explicitly deferred — its related work says kernel analysis “is not the focus of this paper, but it is discussed in Punica” (see `papers/s-lora.md` §5).
- **The citation/derivation, as the texts support it.** S-LoRA (arXiv November 2023) cites Punica (arXiv October 2023, and Chen's earlier blog post) as concurrent work, and states that some of its CUDA kernels “were developed based on the implementation presented in a previous blog post of Punica”, and that its decode kernel as used in experiments is a modification of an earlier Punica kernel version — extended for *non-contiguous memory, multiple ranks in one batch, and finer-grained gathering*. Punica, submitted earlier, does not cite S-LoRA. So the accurate statement is: **Punica is the kernel ancestor; S-LoRA is a descendant in kernel implementation and a sibling in system design.** Any account that presents them as wholly independent duplicates, or S-LoRA's kernels as from-scratch, misstates the record.
- **Scope differences that follow from the centres of gravity.** Punica serves a *cluster* and consolidates tenants onto fewer GPUs (its scheduler's packing and migration are cluster operations; its end-to-end evaluation fixes rank 16 and treats adapters as interchangeable in cost). S-LoRA serves *one machine* (one GPU or one node's GPUs), registers *thousands* of adapters in host memory, and makes *heterogeneous ranks in one batch* and *adapter/KV co-residency in one pool* first-class — problems Punica's design does not take up: Punica loads adapters on demand in ~2 ms and gives them no paged residency of their own, and its KV is paged separately (via FlashInfer) rather than pooled with adapter weights. Conversely, Punica's cluster consolidation and its SGMV roofline analysis have no counterpart in S-LoRA.
- **No head-to-head exists.** Neither paper evaluates against the other system. The corpus therefore records no performance ranking between them, and their headline numbers (Punica 12×; S-LoRA up to 4× vs its vLLM construction) are against *different baselines on different hardware* and must never be compared as if commensurable.

In the lineage this corpus tracks: PagedAttention made KV pageable; Punica made the adapter side of a mixed batch *computable in one kernel*; S-LoRA made the adapter weights *resident in the same paged pool as the KV*. The three compose, and modern multi-LoRA serving is recognisably their union.

## 6. Applicability

### (a) The persona case at personal scale — a handful of personas, not thousands

*Labelled judgement — the corpus's translation, not the paper's claim.*

Punica's cluster machinery inverts at personal scale even more completely than S-LoRA's catalogue machinery: there is no cluster to consolidate, no tenants to pack, no GPUs to drain and release, and migration-by-recompute between GPUs has no destination. None of §3's scheduler survives, and none of §4's throughput ratios should be quoted in a personal-scale design document.

What survives is narrower and, for one specific future, decisive:

1. **The model-agnostic-cost property, as a design target.** Punica's deepest finding for the persona case is not SGMV's speed but its *flatness*: a batch mixing adapters costs what a batch of one adapter costs, at the layer level. At personal scale with one active persona, that property is worth nothing — a single-adapter batch is the degenerate case every system already handles. It becomes worth everything in the one personal-scale scenario where several personas generate *at the same time*: a group scene, or a background persona (summariser, memory extractor) decoding alongside the foreground conversation. In that scenario the choice is Punica's shape — one base pass, per-persona side terms in the same batch — or serialised per-persona passes that multiply decode cost by the cast size. SGMV is the proof that the first shape has no intrinsic penalty.
2. **On-demand loading priced in milliseconds.** Punica's ~2 ms whole-adapter load (PCIe Gen4, A100-class host) is the fleet paper's measurement, not a local promise — but the *ratio* it establishes (adapter load ≈ a small fraction of one ~30 ms decode step, overlappable with running work) is the reason “hot-loadable” in IDEA-LEDGER #39 can mean *hot*: an adapter does not need a residency ceremony, a model reload, or a session restart. At personal scale the same arithmetic holds in kind (adapters are tens of MB; the base reload they replace is gigabytes), so a persona switch can be a per-request field, not an event — *provided* the runner keeps the base resident and the per-persona KV/anchor separation is maintained by the session layer (IDEA-LEDGER #1, #2, #7), which no kernel provides.
3. **What does not survive, honestly:** the SGMV kernel itself, as an artefact to port. A ggml-class personal runner would need its own gather-matvec for its own layouts and backends (including non-CUDA ones Punica never addresses); what transfers is the *operator contract* — grouped-by-adapter segments, no materialised gathered weights, a bandwidth-first schedule for the distinct-adapter case — not code, and not the A100 numbers. And if concurrent multi-persona generation never ships in the personal product, Punica's local contribution reduces to (2): a pricing proof for hot-loading, with S-LoRA (§ sibling dossier) carrying the residency design.

**Honest verdict (labelled):** for a handful of personas served one at a time, Punica changes nothing locally except proving persona switches can be millisecond-cheap; its kernel becomes load-bearing only the day two personas must decode in the same batch — at which point it is the *only* design in the corpus that makes that batch free.

### (b) Ollama's documented adapter support — the gap this paper names

As the corpus records it (`runners/ollama.md` §6.2–§6.3): an adapter enters Ollama at *package* time, via the Modelfile `ADAPTER` instruction (safetensors against a matching base, non-quantised recommended; or GGUF converted with llama.cpp's LoRA converter), and `ollama create` bakes base + adapter into **a separate named model entry**. Serving then has no concept of an adapter at all: no per-request adapter selection, one runner per model entry, slots partitioned per model, and — decisive against Punica's premise — *no batch that mixes adapters*, because two personas are two models and two models never share a forward pass.

Punica names the cost of exactly that arrangement from the provider's side: duplicated base residency per persona and batching that collapses to per-model fragments. Ollama's arrangement is the single-user version of the baseline Punica beats — with the fairness note that at batch 1, single-persona-at-a-time, the cost Punica removes is mostly *not being paid yet* (see (a)): what Ollama's users actually pay today is the *switch* cost (unload/reload, KV destroyed) rather than a batching penalty, and that half of the gap is S-LoRA's framing more than Punica's. The joint gap both papers name, in Ollama's terms: adapters as runtime, per-request, separately-resident objects over one shared base (IDEA-LEDGER #39) — a serving concept, not a packaging one.
