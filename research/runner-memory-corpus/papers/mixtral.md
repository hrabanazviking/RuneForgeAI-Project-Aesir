# Mixtral of Experts — Mixtral 8×7B, a Sparse Mixture-of-Experts Language Model

## 1. Full citation

- **Title:** Mixtral of Experts
- **Authors:** Albert Q. - **arXiv:** arXiv:2401.04088 [cs.LG] — v1 8 January 2024 — https://arxiv.org/abs/2401.04088
- **Code / checkpoints (as reported in the paper):** https://github.com/mistralai/mistral-src ; release page https://mistral.ai/news/mixtral-of-experts/ . Both the base model, Mixtral 8×7B, and the instruction-tuned Mixtral 8×7B – Instruct are released under the **Apache 2.0** licence.
- **Scope note for this dossier:** Mixtral is the corpus's open sparse-MoE reference point — the deliberately simple, coarse-grained design (few, large experts; top-2 routing) against which the fine-grained DeepSeekMoE design in `papers/deepseek-v2-mla.md` §4 is the contrast. Its second role here is as the worked example for the total-vs-active memory split that governs all MoE serving on small cards (§7).

## 2. The problem it attacks

A dense transformer pays for every parameter on every token: doubling the model's stored knowledge roughly doubles both its memory footprint *and* the compute and bandwidth cost of each generated token. By 2023 the open-weights frontier was therefore a single, expensive point — Llama 2 70B-class quality meant 70B parameters read per token. Mixture-of-Experts (MoE) architectures had long promised to break that coupling in principle — hold many parameters, use few per token — but the prominent MoE systems (GShard, Switch Transformer) were training-side demonstrations, not released, servable, frontier-quality open models.

The paper's problem, stated in its own frame, is: **release an open-weights sparse MoE that matches or beats Llama 2 70B and GPT-3.5 on standard benchmarks while activating only about one fifth as many parameters per token as Llama 2 70B** — and do it with the smallest possible architectural delta from a known-good dense model (Mistral 7B), so the result is easy to adopt, convert, and serve. It is a model paper, not a serving-systems paper; the serving problem its design creates (§6, §7) is named in one honest paragraph and otherwise left to its readers — which is why this corpus pairs it with `papers/moe-infinity.md`.

## 3. Core idea in our own words

Take Mistral 7B's decoder-only transformer unchanged, except for one substitution: **in every layer, replace the single feed-forward (FFN) block with eight parallel FFN blocks — the experts — plus a small router.**

- For each token, at each layer independently, the router scores all eight experts and selects the **top 2**. Only those two experts process the token; their outputs are combined as a weighted sum, the weights being the softmax over the two selected router logits. The other six experts do no work and — the serving-critical point — need not be read for that token at that layer.
- Each expert is an ordinary SwiGLU FFN with the same shapes as Mistral 7B's single FFN. There are no shared experts, no fine-grained expert splitting, and no per-expert specialisation mechanism beyond what routing learns.
- Because the choice is per token *and per layer*, different tokens in one sequence, and the same token at different depths, use different expert pairs. A token therefore has *access* to the full parameter pool across the network while *paying* for only two experts per layer.

That is the whole mechanism, and its consequence is the distinction the paper itself (§2.1) insists on:

| Quantity | Value | What it prices |
|---|---|---|
| **Total ("sparse") parameters** | **47B as reported in the paper** (46.7B in the precise model accounting used by model cards and converters — the difference is rounding and how shared/non-expert parameters are counted) | **Storage and residency:** every byte that must live *somewhere* the runner can reach — file size, RAM/VRAM footprint |
| **Active parameters per token** | **13B as reported in the paper** (12.9B precise accounting) | **Compute and, in a fully resident deployment, per-token bandwidth:** what one token's forward pass actually touches |

Increasing the expert count n at fixed top-k raises the first number while holding the second roughly constant. Every MoE serving difficulty in this wave is that sentence, operationalised.

**Architecture constants (paper Table 1):** hidden dimension 4,096; **32 layers**; attention head dimension 128; FFN hidden dimension 14,336; 32 attention heads; **8 KV heads (grouped-query attention — see `papers/gqa.md`)**; context length 32,768; vocabulary 32,000; **8 experts per layer, top-2 routing**. Sanity arithmetic (ours): one expert is 3 × 4,096 × 14,336 ≈ 176M parameters; 8 experts × 32 layers ≈ 45.1B expert parameters, plus ≈1.6B of attention, embedding and norm parameters shared by all tokens — which is where 46.7B total comes from, and why the active count is 2/8 of the expert pool (≈11.3B) plus the shared ≈1.6B ≈ 12.9B.

## 4. Key design details a runner engineer needs

- **The router, exactly as described.** The gating function is G(x) = Softmax(TopK(x · W_g)) with K = 2: a single learned linear projection from the token's hidden state to 8 logits, all but the top two set to −∞ before the softmax, so the two surviving weights are positive and sum to 1. The layer output is Σᵢ G(x)ᵢ · SwiGLUᵢ(x) over the selected experts. There is no token dropping, capacity factor, or expert-choice routing described in the paper.
- **Load balancing, as described — which is to say, barely.** This dossier records the absence deliberately, because secondary summaries routinely import machinery the paper does not contain. The Mixtral report specifies **no auxiliary load-balancing loss, no balancing coefficient, and no capacity limit**. Load balancing appears exactly once, as a systems warning: under Expert Parallelism (below), tokens routed to an expert must travel to the GPU holding it, so uneven routing overloads individual devices. The paper's evidence that routing does not collapse is empirical and post-hoc — its §5 routing analysis (§5 below) — not a described training mechanism. Any load-balancing loss used in training is **[not in the paper — unverified from this source]** and must not be attributed to it.
- **Attention is not sparse; only the FFN is.** Attention, embeddings and the LM head are dense and shared: they are touched by every token, they are comparatively small (≈1.6B parameters), and in any split-residency design they belong permanently in the fastest tier alongside the KV cache — the same placement MoE-Infinity adopts (`papers/moe-infinity.md` §4).
- **Execution notes the paper does give:** MoE layers run efficiently as large sparse matrix multiplications (it cites MegaBlocks kernels, integrated via the authors' contributions to vLLM); at scale, layers can be sharded by **Expert Parallelism** — experts placed on different GPUs, tokens dispatched to the expert's device and results returned — with the load-balancing caveat above. The paper also warns, in its size-and-efficiency discussion, that SMoE layers add routing overhead and extra memory loads when more than one expert runs per device, and are "more suitable for batched workloads" where arithmetic intensity can be raised. At batch 1 — the personal-machine regime — that caveat is load-bearing (§6).
- **Context behaviour is dense-priced, not expert-priced.** The model supports a fully dense 32k context; its KV cache is an ordinary GQA cache (8 KV heads), priced by the GQA dossier's arithmetic, entirely unaffected by the MoE structure. MoE sparsity saves weight bandwidth, never cache bytes.
- **Practice — the open-MoE wave, and GGUF reality (per corpus dossiers).** Mixtral was the first frontier-class open MoE, and it normalised the form: the fine-grained DeepSeekMoE line, Mixtral 8×22B, and the now-routine "total / active" labelling of MoE releases (e.g. "26B-A4B") all follow it. In the local stack this corpus covers, Mixtral is a first-class GGUF architecture: llama.cpp builds its graph with per-layer expert tensors, and — the decisive serving fact — current llama.cpp exposes MoE-specific placement rather than only whole-layer offload: `--cpu-moe` / `--n-cpu-moe N` keeps expert weights (all layers / the first N) in system RAM while attention and shared weights stay on the GPU, and `--moe-cache-mib` adds a GPU-side cache for host-resident experts (corpus: `runners/llamacpp-ggml.md` §5.2). Ollama inherits that machinery through its ggml/llama.cpp path and lists Mistral/Mixtral among its directly importable safetensors families (corpus: `runners/ollama.md`). In other words, the ecosystem's answer to Mixtral's residency problem already exists in primitive form; `papers/moe-infinity.md` is about how much better the *policy* inside it can get.

## 5. Reported results — as reported, with context

All figures are the paper's own. Two evaluation protocols appear and must not be merged: **Table 2** re-runs every model (Llama family included) through the authors' own pipeline; **Table 3** compares against externally reported Llama 2 70B / GPT-3.5 figures under those benchmarks' customary shot counts — which is why, e.g., GSM8K appears as 74.4 in one table and 58.4 in the other (8-shot with maj@8 vs 5-shot).

- **Headline (Table 2, authors' pipeline; active parameters in brackets).** Mixtral 8×7B [13B active] vs Llama 2 70B [70B]: **MMLU 70.6% vs 69.9%**; HellaSwag 84.4% vs 85.4%; WinoGrande 77.2% vs 80.4%; PIQA 83.6% vs 82.6%; ARC-Easy 83.1% vs 79.9%; ARC-Challenge 59.7% vs 56.5%; NaturalQuestions 30.6% vs 25.4%; TriviaQA 71.5% vs 73.0%; **HumanEval 40.2% vs 29.3%; MBPP 60.7% vs 49.8%; MATH 28.4% vs 13.8%; GSM8K 74.4% vs 69.6%**. The paper's summary — "outperforms or matches Llama 2 70B on almost all benchmarks while using 5× fewer active parameters" — is accurate in its own frame, with the honest texture visible in the row: the large wins are mathematics, code and knowledge recall; a few commonsense/reading measures (HellaSwag, WinoGrande, TriviaQA) run the other way, and the paper's own category chart concedes reading comprehension as the exception class.
- **Against GPT-3.5 (Table 3, customary protocols).** MMLU: Mixtral 70.6%, GPT-3.5 70.0%, Llama 2 70B 69.9%. MBPP 60.7% vs 52.2% / 49.8%; GSM8K (5-shot) 58.4% vs 57.1% / 53.6%. HellaSwag and WinoGrande again slightly favour one of the baselines. MT-Bench for the *instruct* models: Mixtral – Instruct 8.30, GPT-3.5 Turbo 8.32, Llama 2 70B – Chat 6.86.
- **Instruct model, human evaluation.** Mixtral 8×7B – Instruct (supervised fine-tuning + Direct Preference Optimization) reached a **LMSys Chatbot Arena Elo of 1121** in the 22 December 2023 leaderboard screenshot the paper reproduces — above Claude-2.1 (1117), GPT-3.5 Turbo (1117), Gemini Pro (1111) and Llama-2-70B-Chat (1077) *at that date*. Treat as a dated snapshot of a moving leaderboard, not a standing ranking.
- **Multilingual (Table 4).** On ARC-Challenge, HellaSwag and MMLU in French, German, Spanish and Italian, Mixtral beats Llama 2 70B in every listed cell — e.g. French MMLU 70.9% vs 64.3%, German ARC-Challenge 54.3% vs 47.3% — which the paper attributes to upsampled multilingual pre-training data plus the capacity headroom sparsity provides.
- **Long context.** Passkey retrieval: **100% accuracy regardless of context length (to 32k) or passkey position**. Perplexity on a proof-pile subset decreases monotonically as context grows. No long-context *serving* cost analysis is offered (see §6).
- **Routing analysis (paper §5) — the result this wave most depends on.** Measuring expert assignment over Pile validation subsets (layers 0, 15, 31 reported):
  - **No obvious domain specialisation.** The expert distribution is strikingly similar for arXiv papers, PubMed abstracts, PhilPapers, Gutenberg, Wikipedia and the rest; only the synthetic DM Mathematics set diverges marginally. The authors' reading: routing tracks **syntax and token type more than topic** — e.g. the Python token `self`, the English word "Question", and code indentation tokens are consistently routed to the same experts, especially at the first and last layers.
  - **Temporal locality is real and layer-dependent.** The share of consecutive token pairs assigned the *same first-choice expert*: ≈14% at layer 0 (near the 12.5% random baseline for 8 experts), rising to ≈24–28% at layers 15 and 31. Counting a repeat in *either* slot (first-or-second choice): ≈45–50% at layer 0, **≈62–67% at layer 15**, ≈45–54% at layer 31, against a ≈46% random baseline the paper derives. The paper itself draws the serving conclusion: this locality "can be leveraged for caching" — and, in the other direction, causes expert over-subscription under Expert Parallelism. `papers/moe-infinity.md` is, in large part, the systematic exploitation of this paragraph.

## 6. Limitations / what it does not solve

- **The paper's own caveat is the wave's thesis.** Its efficiency analysis "focuses on the active parameter count, which is directly proportional to the inference compute cost, but does not consider the memory costs" — memory cost is proportional to the **total** 47B. Mixtral therefore does not, by itself, make a 70B-class model fit anywhere a 13B model fits; it makes it *compute* like a 13B model in a place that can already *store* 47B. Closing the storage gap is a serving-system problem (offloading, caching) that the paper explicitly leaves open.
- **No serving measurements.** There are no tokens/second, latency, or memory-footprint experiments in the report — no hardware testbed is even named for inference. Claims like "6× faster inference" belong to the release blog's framing against Llama 2 70B under its conditions; the paper supports only the active-parameter arithmetic behind them. Any speed figure for Mixtral on a given card must come from a runner dossier or a measurement, never from this paper.
- **Batch-1 arithmetic intensity.** With one token, each selected expert performs a matrix–*vector* product: the expert's full weight bytes are read to produce one token's contribution. Sparsity reduces which bytes are read, but the bytes-per-FLOP ratio of what remains is the worst in the system — the paper's "more suitable for batched workloads" note (§4) is the polite form of this. Prefill has the opposite shape: a long prompt's tokens scatter across most or all experts, so prefill touches close to the total parameter set and gains little from sparsity.
- **Underspecified training/serving details.** Beyond §4's load-balancing absence: no training compute, data mixture proportions, or routing-regularisation details are given at a level that would let anyone reproduce the model or predict a *new* MoE's routing locality. The locality numbers in §5 are measurements of *this* checkpoint on *The Pile*; a differently trained MoE's locality is an empirical question per model (the MoE-Infinity trace studies are the broader evidence).
- **Scale of the artefact.** Even the "small" reference MoE is 46.7B parameters: ≈93 GB at FP16, and — **[our arithmetic, from the corpus's GGUF quantisation ladder in `runners/llamacpp-ggml.md` §2.2]** ≈26–29 GB at Q4_K_M-class quantisation (≈4.9 bits/weight effective), ≈15 GB at IQ2-class (≈2.1 bpw), ≈9 GB even at IQ1_S-class (≈1.56 bpw). No GGUF quantisation in the corpus's ladder brings the *total* inside a 6 GB card. That is not a defect of the model; it is the fact that defines §7.

## 7. Applicability

### (a) Ollama on a 6 GB consumer GPU — the total-vs-active split is THE fact

State it as a residency law for any MoE, with Mixtral as the worked example:

> **Compute follows the active count; residency follows the total count. A runner gets the active count's speed only for the experts it can keep resident or fetch cheaply — every non-resident expert a token selects is a bus transfer or a CPU computation, priced per token, forever.**

- **Full GPU residency is impossible for Mixtral on 6 GB — at any quant.** §6's ladder: total weights are ≈9 GB even at the most aggressive GGUF quantisation, ≈26–29 GB at the Q4_K_M quality point the ecosystem actually ships. Add the corpus's planning reserve for driver context + display (≈0.5–1.0 GiB on a card also driving a screen; `memory/gpu-memory-internals.md` §2.3) and a GQA KV cache, and there is no configuration to find. An Ollama-class runner that tries "load it all on the GPU" will fail at allocation; the only honest modes are split residency (below) or a smaller model.
- **The active set nearly fits — and that "nearly" is quant-dependent.** **[Our arithmetic]** Active weights per token ≈12.9B parameters: ≈7–8 GB of weight bytes at Q4-class precision — just *over* a 6 GB budget once shared weights, cache and buffers are counted — falling to ≈5–6 GB at Q3/IQ3-class precision, i.e. just *inside* it. This is the precise sense in which the commissioning brief's framing holds: a 47B-class MoE's active working set is 6 GB-adjacent in a way a dense 47B model's never could be. But "active per token" is not a fixed resident set: across a whole generation the union of selected experts grows well beyond one token's 64 experts (2 × 32 layers), so a cache sized for exactly one token's active set will thrash. Sizing must follow the *per-request working set* — MoE-Infinity measures ≈25% of experts repeatedly activated per request for Mixtral (`papers/moe-infinity.md` §4) — not the per-token active count.
- **The expert-miss price, in the corpus's PCIe arithmetic** (`memory/gpu-memory-internals.md` §4.4: PCIe 3.0 ×16 ≈12.1 GB/s typical per direction; PCIe 4.0 ×16 ≈26.2 GB/s typical; halve for ×8). **[Our arithmetic]** One Mixtral expert at Q4-class precision is ≈176M × ≈0.56 B ≈ **100 MB**. A token selecting 64 experts with *zero* cache hits would need ≈6.4 GB of expert traffic — ≈0.53 s/token over Gen3 ×16 (≈1.9 tok/s as an absolute bus ceiling, before compute) or ≈0.24 s/token over Gen4 ×16 (≈4 tok/s). Every cache hit removes ≈100 MB from that bill: at a 75% hit rate the Gen3 ceiling rises to ≈7–8 tok/s; at 90%, to ≈19 tok/s. **Cache hit rate, not FLOPs, is the product** — which is why the routing locality of §5 is worth more to this runner than any kernel optimisation.
- **The realistic 6 GB configuration is therefore the llama.cpp shape, policy-upgraded:** shared/attention weights + KV cache + a *bounded expert cache* in VRAM; the full expert pool resident in system RAM (the Q4_K_M file is ≈26–29 GB — it fits a 32 GB+ host, and see (b) for the fleet host where it fits comfortably); experts computed on the GPU when cached, fetched over PCIe on a miss, with prefetch driven by routing locality. The existing `--cpu-moe` + `--moe-cache-mib` knobs (§4) are the substrate; what they lack — request-level activation tracing and sparsity-aware eviction instead of naive recency — is exactly MoE-Infinity's contribution. The alternative split, computing missed experts *in place on the CPU* (the PowerInfer pattern, `runners/powerinfer.md`), avoids the transfer but pays host CPU bandwidth and a per-layer synchronisation; for SwiGLU experts at batch 1 it is a legitimate fallback for cold experts, not the primary path. **[Engineering judgement]**
- **User-facing honesty requirements:** (i) label MoE models by *both* numbers everywhere ("46.7B total / 12.9B active — needs ≈28 GB RAM + expert cache in VRAM"), never by the active count alone; (ii) price context from the GQA cache arithmetic as usual — MoE does not discount KV; (iii) when the expert cache is too small for the request working set, say so in the load log with the ledger style of `memory/gpu-memory-internals.md` §7.1 (cache size vs measured working set), because the resulting slowness otherwise looks like a broken model rather than a predictable miss storm.

### (b) Project Aesir (Mojo runner — sessions, prefix memory, hybrid SSM models)

- **MoE support is a placement problem before it is a kernel problem.** Aesir's tensor-placement abstraction must be able to express, per tensor class: *resident* (attention, shared FFN, norms), *cacheable* (experts — resident in host RAM, cached in device memory under an eviction policy), and *streamed* — with the expert cache as a first-class allocator arena beside the KV arena, not as an afterthought inside layer offload. Mixtral's clean structure (experts are independent, identically shaped SwiGLU blocks) makes it the right first MoE target: one expert kernel, one cache unit size class per layer, no shared-expert special cases. DeepSeekMoE's fine-grained experts (160 routed + shared; corpus `papers/deepseek-v2-mla.md` §4) are the stress case to design the *interface* against, even if Mixtral is the first implementation.
- **Routing locality is session state.** The §5 finding — syntax-driven, temporally local, request-coherent routing — means an Aesir *session* has a predictable expert working set that warms up over its first tokens and stays warm. Aesir's prefix/session memory design should therefore treat the expert-cache contents as part of a session's warm state: restoring a session should restore (or pre-warm) its expert working set alongside its KV prefix, and evicting a session's experts on every turn boundary would re-pay the miss storm per turn. This composes with, and is priced separately from, KV prefix reuse (`papers/radixattention-sglang.md`).
- **Speculative decoding interacts badly with MoE sparsity — budget for it.** The corpus's EAGLE dossier records the mechanism: verifying several drafted tokens touches more experts than one decode token, weakening the "verification is almost free" premise (Mixtral speedup 1.50× there, the lowest in its table). Aesir should measure speculation gains *per architecture class* and not promise dense-model speedups on MoE targets.
- **For Aesir's model ambitions:** Mixtral is the existence proof that the *simplest* MoE — coarse experts, top-2, no described balancing machinery — reaches frontier quality, which lowers the design risk of a house MoE considerably. The open variable its paper leaves — how routing locality behaves under *our* training choices — should be measured on any house checkpoint with the Mixtral §5 method (per-domain assignment distributions + consecutive-token repetition rates) before serving policies are tuned around it.
