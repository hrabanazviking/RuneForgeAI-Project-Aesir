## 2. The problem as framed

The starting observation is the shape of the “pretrain-then-finetune” economy: one base model, fine-tuned by Low-Rank Adaptation (LoRA) into a multitude of task- or user-specific variants. A LoRA adapter is two small matrices per adapted projection — for a weight $W$, the update is $AB$ with rank $r \ll \min(h,d)$, so $h = xW + xAB$ — typically applied to the query, key, value and output projections. Adapters are therefore *small but numerous*: cheap to train, cheap to store, and, in the paper's framing, potentially thousands or millions of personalised variants of one base (the paper's motivating example is personalised assistants at that scale). The serving question the paper says was unexplored is: how do you *serve* that collection, concurrently, on one machine?

The paper names the naive answers and why each breaks:

1. **Merge each adapter into the base and serve copies.** Merging ($W' = W + AB$) is the original LoRA paper's inference recipe: zero added latency for *one* adapter. For many adapters it means many full copies of the base model — GPU memory holds a handful at most — and every copy is a separate serving instance, so the batching opportunity across adapters is destroyed by construction.
2. **Swap adapters by adding/subtracting on the fly.** Also from the original LoRA paper: one base, adapters merged in and out serially. This serves adapters *one at a time*; concurrent requests for different adapters cannot share a forward pass, so throughput and latency both degrade exactly when concurrency arrives.
3. **Per-adapter serving stacks (the baselines as built).** HuggingFace PEFT batches requests for a single adapter and switches adapter weights between batches — no heterogeneous batching, no serious memory management. A “packed” vLLM construction (the paper's own baseline, §4) merges adapters and runs one vLLM worker per merged model under NVIDIA MPS, statically partitioning GPU memory by average request rate.

Underneath those three failures sit three systems problems, which the paper separates cleanly and which structure the whole design:

- **Weights paging.** Only the adapters in the *current* batch need to be on the GPU; the full collection can live in host (main) memory, bounded by host RAM rather than VRAM. But dynamically loading and unloading adapters *of different ranks and therefore different sizes*, alongside KV cache tensors *of different and growing sequence lengths*, fragments GPU memory and adds I/O overhead — the two dynamic populations fight over the same pool with incompatible allocation shapes.
- **KV-per-adapter accounting.** There is no separate “per-adapter KV” object, but that is precisely the accounting trap: every request carries *both* a variable-size adapter residency cost (its rank, across every adapted layer) *and* a variable, growing KV cost (its sequence length), and a scheduler that budgets only one of the two will over- or under-admit. Serving capacity is a joint function of which adapters are active and how long their requests run.
- **Kernel launch shapes.** Separating the computation — one batched base-model GEMM for $xW$, then the per-adapter $xAB$ side computation — is the obvious decomposition, but off-the-shelf batched GEMM forces padding to a common shape. Requests in one batch have different sequence lengths *and* different ranks, and their adapter weights, under any sane paging scheme, are non-contiguous. Padding wastes exactly the compute and bandwidth the decomposition was meant to save; per-adapter kernel launches serialise it instead.

## 3. Core mechanism in our own words

**The decomposition.** S-LoRA never merges. It computes $xW$ once, batched across *all* requests in the batch regardless of adapter (the base model is common, so this is an ordinary GEMM), and computes each request's $xAB$ side term on the fly with custom kernels (§ below). The extra compute of the unmerged form is real but small — $xAB$ is far cheaper than $xW$ because $r \ll h$ — and the paper's ablation (§4) shows it is repaid by batching as soon as more than about two adapters are active.

**Residency: all adapters in host memory, active adapters fetched.** Every adapter the system serves lives in main memory; only the adapters needed by the currently running batch are fetched to the GPU. The maximum number of servable adapters is therefore bounded by *host* memory, not VRAM — the paper's host configurations run from 64 GB to 670 GB (§4). While the current batch decodes, S-LoRA *prefetches* the adapters the next batch will need, predicted from the waiting queue, overlapping the host→GPU transfer with computation so the swap cost is mostly hidden.

**Unified Paging — the paper's centre of gravity.** The key observation is an analogy: an adapter weight tensor for one layer has shape $(R, H)$ — rank by hidden size — and a KV cache tensor for one layer has shape $(S, H)$ — sequence length by hidden size. Both are variable in their first dimension, both are allocated on request arrival and freed on completion, and both share the $H$ dimension. S-LoRA therefore generalises PagedAttention (see `papers/pagedattention-vllm.md`) from “page the KV cache” to “page everything dynamic”: **one unified memory pool** — a single large buffer taking all GPU space not held by base weights and temporary activations — holds *both* KV cache and adapter weights, interleaved and non-contiguous, in pages of one $H$-sized vector each. A KV tensor of length $S$ occupies $S$ pages; an adapter tensor of rank $R$ occupies $R$ pages. Because every allocation is in the same uniform page unit from the same pool, there is no external fragmentation between the two populations, and the pool *balances itself dynamically*: a batch with many distinct adapters spends more pages on weights and fewer on KV; a batch with long sequences does the reverse — without any static partition being chosen in advance. That dynamic balance is the idea's real content, beyond the paging mechanics it inherits.

**Heterogeneous batching kernels.** Because pooled weights are non-contiguous and ranks vary within a batch, S-LoRA writes kernels that gather directly from the pool without padding:

- **MBGMM** (Multi-size Batched Gather Matrix-Matrix Multiplication) for **prefill**: a batch of sequences, each token gathering its own request's adapter slice. Implemented in Triton with tiling.
- **MBGMV** (Multi-size Batched Gather Matrix-Vector Multiplication) for **decode**: one token per request, same gather semantics. Two implementations were built — one in Triton, and one by *modifying an earlier version of Punica's kernels* to add non-contiguous memory, multiple ranks in one batch, and finer-grained gathering. The paper states the Punica-derived version was faster and is the one used in the experiments (the relationship is examined in §5).

**Scheduling around the batch.** The serving loop is iteration-level (continuous) batching in the Orca lineage: new requests join the running batch at token granularity when space allows. Two adapter-aware policies sit on top, both presented with their trade-offs rather than as free wins:

- **Adapter clustering** (optional strategy, ablated in the paper's appendix): preferentially batch requests that share an adapter, reducing the number of *distinct* active adapters in a batch, which frees pool pages for KV and permits larger batches — at a stated cost to average latency and fairness across adapters.
- **Early abort (admission control):** under overload, estimate the latest-arriving set of requests that can still meet the SLO (defined as first token within 6 seconds) and serve in arrival order within that set, aborting the rest *before* spending compute on them — the paper compares it against first-come-first-served and last-come-first-served in ablation (§4).

**Tensor parallelism for LoRA (S-LoRA TP).** For models too large for one GPU, the base model uses Megatron-LM tensor parallelism, and S-LoRA partitions the added LoRA matrices to align with the base partition (column/row splits matched per projection), so that communication happens on the small intermediate tensors (size $\propto r$) and fuses with the base model's collectives where possible. The paper's cost analysis puts the added LoRA communication at $5(N-1)Br/N$ against the base's $2(N-1)Bh/N$ for $N$ devices, batch $B$, hidden size $h$ — negligible precisely because $r \ll h$ — and notes no weight matrix is replicated.

**Implementation shape.** Built on LightLLM, a PyTorch/Triton single-model serving system — i.e. S-LoRA is a full serving stack (scheduler, memory manager, kernels, parallelism) built around the multi-adapter problem, not a kernel library with a scheduler attached.

## 4. Reported results — as reported, with hardware and scale context

All figures are the paper's own. **Nothing below is a consumer-hardware or single-user number.**

**Setup.** Models: Llama 7B / 13B / 30B / 70B in five configurations — 7B at rank {8} and at mixed ranks {64, 32, 16, 8}; 13B at {64, 32, 16}; 30B at {32}; 70B at {64} (with a footnoted caveat: the 70B configuration used different architecture parameters than the official model and did not use grouped-query attention). Hardware: a single NVIDIA A10G (24 GB), a single A100 (40 GB), a single A100 (80 GB), and multiple A100s (40/80 GB); host main memory 64 GB to 670 GB depending on configuration. Workloads: synthetic Gamma-arrival traces (5 minutes; per-adapter rates power-law distributed; input/output lengths uniform in [8, 512] by default) and a real-workload trace downsampled from LMSYS Chatbot Arena logs (average input 85 tokens, average output 165 tokens, ~26 adapters — with the paper's own caveat that the Arena log records different *base models*, whose distribution it reinterprets as a distribution over adapters of one base). Baselines: HuggingFace PEFT (single-adapter batching, adapter switching between batches) and “vLLM-packed” (the paper's construction: adapters merged, one vLLM worker per merged model under MPS, GPU memory statically split by average request rate — necessary because, as the paper puts it, vLLM at the time did not support LoRA serving). SLO attainment = percentage of requests returning a first token within 6 seconds.

**Headline claims (abstract / introduction, as reported):**

- Throughput **up to 4×** higher than vLLM-packed and **up to 30×** higher than HuggingFace PEFT, while increasing the number of served adapters **by several orders of magnitude**.
- S-LoRA serves **up to 2,000 adapters simultaneously** (the largest configuration tested) with throughput that, in the paper's Table 3 (single A100 80 GB), barely moves as the adapter count grows:

| Configuration | Adapters $n$ | S-LoRA (req/s) | vLLM-packed (req/s) | PEFT (req/s) |
|---|---|---|---|---|
| 7B, rank {8} | 5 | 8.05 | 2.04 | 0.88 |
| 7B, rank {8} | 100 | 7.99 | OOM | 0.25 |
| 7B, rank {8} | 1,000 | 7.64 | OOM | — (not evaluated) |
| 7B, rank {8} | 2,000 | 7.61 | OOM | — |
| 7B, mixed ranks {64,32,16,8} | 5 | 7.48 | 2.04 | 0.74 |
| 7B, mixed ranks | 2,000 | 6.71 | OOM | — |
| 13B, ranks {64,32,16} | 2 | 4.49 | 3.83 | 0.54 |
| 13B, ranks {64,32,16} | 1,000 | 3.96 | OOM | — |

The paper's explanation for the flatness is structural and is the result's real content: once the adapter count passes a threshold (~100 in most of its experiments), throughput stops declining, because the number of adapters *active in the running batch* is bounded by the batch, not by the catalogue — the marginal cost of the 2,000th *registered* adapter is host memory only. Conversely, vLLM-packed “can only serve fewer than 5 adapters” under the GPU memory constraint, because each merged adapter is a full model copy.

**Multi-GPU (as reported).** Llama-30B on 2 and 4× A100 (40 GB) with 10–100 adapters, and Llama-70B on 2 and 4× A100 (80 GB) with 10 adapters: the throughput difference with vs without the added LoRA communication is small (communication overhead below the LoRA compute overhead), and moving from 2 to 4 GPUs more than doubles throughput — which the paper attributes to the workload being predominantly memory-bound, so added GPUs relieve the binding constraint (its word is “superlinear” scaling in that transition; recorded here as the paper's claim, on its testbed).

**Ablations (as reported).**

- *Merge vs compute on the fly:* the merging design wins with exactly **one** adapter (one-time merge cost, no per-step side compute) and declines beyond **2** adapters, as adapter switching leaves the GPU under-utilised. This is the paper honestly bounding its own design: unmerged serving is a *multi*-adapter technique.
- *Own variants:* removing Unified Paging (S-LoRA-no-unify-mem) and removing both paging and custom kernels in favour of copying weights to contiguous memory with padded batched matmul (S-LoRA-bmm) both cost substantial throughput and latency — the paper's evidence that the pool and the gather kernels each carry part of the headline.
- *Early abort:* S-LoRA-Abort beats both FCFS and LCFS on user satisfaction / SLO attainment, especially as arrival burstiness (coefficient of variation) grows; FCFS is worst, spending capacity on requests that have already missed the SLO.

**Scale caveat, stated plainly.** The “thousands” are thousands of *registered* adapters behind a bounded active batch, on datacentre GPUs with up to 670 GB of host RAM, under synthetic or reinterpreted traces, against a PEFT baseline with no heterogeneous batching and a vLLM baseline the authors had to construct because the upstream system lacked LoRA support. The durable claim is the flatness — catalogue size decouples from serving cost — not any particular req/s figure.

## 5. Position relative to Punica

Contemporaneous and explicitly acknowledged as such. Punica (arXiv October 2023) appeared while S-LoRA (arXiv November 2023) was in preparation, and S-LoRA's related-work section (§8 of the paper) handles the relationship in its own words, which this dossier follows:

- Punica “explored the concept of decomposed computation for the base model and adapters” — the same $xW$ + $xAB$ split. S-LoRA does **not** claim the decomposition, or heterogeneous batching as an idea, as its novelty against Punica.
- The kernel debt is direct and stated: “Some of our CUDA kernels were developed based on the implementation presented in a previous blog post of Punica, with additional support for batching different ranks and non-contiguous memory” (§8; §5.3 says the decode kernel actually used in the experiments is the one built by modifying an earlier Punica kernel version, extended for non-contiguous memory, multiple ranks per batch, and finer-grained gathering). “Analyzing kernel performance is not the focus of this paper, but it is discussed in Punica.”
- S-LoRA locates its own difference exactly: “Our work differs from Punica in our novel memory management and tensor parallelism techniques, which have not been covered in any previous work.” I.e. **Unified Paging (one pool for adapter weights and KV) and S-LoRA TP are the claims; the kernel lineage is shared.**

The centres of gravity are therefore complementary rather than competing: Punica is a *kernel-first* system for a GPU *cluster* (one rank regime in its end-to-end evaluation, adapters as tenants to be consolidated onto fewer GPUs — see `papers/punica.md`); S-LoRA is a *memory-system-first* full stack for *one machine* (single GPU or one node's several GPUs), whose headline problem — thousands of adapters of *varying* ranks coexisting with dynamic KV in one fragmented-prone pool — Punica does not address. Neither paper's evaluation compares against the other system (each compares against PEFT/vLLM-family baselines), so no cross-system performance ranking exists in either text, and none should be manufactured here. In the lineage this corpus tracks: PagedAttention paged the KV cache; Punica made the adapter side batchable; S-LoRA paged the adapters *into the same pool as the KV* and built the serving stack around that pool.

## 6. Applicability

### (a) The persona case at personal scale — a handful of personas, not thousands

*Labelled judgement — the corpus's translation, not the paper's claim.*

At personal scale the paper's headline problem **inverts**. A handful of persona adapters — say three to a dozen characters over one resident base — fit in GPU memory outright at adapter sizes; there is no catalogue to page in from host RAM, no fragmentation crisis among thousands of variable-rank tensors, and no batch of strangers to heterogeneously gather. Anyone importing S-LoRA's machinery wholesale to serve five personas has brought a fleet system to a problem that does not exist.

What survives the scale collapse is, in order:

1. **The unmerged, one-resident-base discipline itself.** The personal-scale disease S-LoRA cures is not fragmentation — it is the *base-model swap*: today's personal stacks represent each persona as a separate merged model entry (see (b)), so changing character means unloading and reloading gigabytes of near-identical weights, destroying the resident session's KV in the process (the corpus's IDEA-LEDGER #17 failure mode, at model granularity). S-LoRA's ablation is the honest boundary: merging wins for exactly one adapter; the moment a *cast* exists — the persona-chat case by definition — computing $xAB$ on the fly over one resident base beats maintaining merged copies. The win at this scale is *not swapping base models*, plus keeping each persona's KV and anchor separation intact across a character switch (the session object, IDEA-LEDGER #1, selects an adapter per conversation; its KV is keyed by model + adapter, per `memory/kv-cache-design.md` §3's sharing invariant).
2. **The unified-pool idea — one paged budget, two tenants.** This is the paper's deepest transferable claim, and it survives intact because it was never really about thousands: adapter weights and KV cache are both dynamic, variable-size, per-request residents of the same scarce GPU memory, and budgeting them from *one* pool with *one* page unit lets the balance shift per batch instead of being frozen by a static partition. On a 6 GB card that trade is not an optimisation detail, it is the whole arithmetic: pages spent holding a second persona's adapter are pages not spent on the first persona's context, and only a unified accounting (IDEA-LEDGER #4's arena, extended to adapters) can make that trade explicitly and per request. Link: `memory/kv-cache-design.md` — S-LoRA is that dossier's “one addressing scheme, several residents” principle with a second resident class added.
3. **The batching shape, conditionally.** If multiple personas ever generate *concurrently* on the personal machine — the user chatting with one character while a second persona runs a summarisation or memory-extraction sidecar, or a group scene with several characters taking turns in one forward stream — then heterogeneous batching (one base GEMM, per-request adapter side terms) is the shape that makes it one pass instead of serialised per-persona passes. If generation is strictly one persona at a time, this part of S-LoRA contributes nothing locally, and the dossier says so plainly.

**Honest verdict (labelled):** at personal scale S-LoRA is not a performance system to port but a *residency architecture* to copy — one base, unmerged adapters, one paged pool budgeting adapters against KV — whose fleet-scale throughput numbers do not transfer at all.

### (b) Ollama's documented adapter support — the gap this paper names

As the corpus records it (`runners/ollama.md` §6.2–§6.3): Ollama imports a LoRA adapter through the Modelfile `ADAPTER` instruction — safetensors against a matching base (non-quantised adapters recommended, since quantisation schemes differ across training frameworks) or GGUF form converted with llama.cpp's LoRA converter against the same base it was trained on — with architecture coverage narrower than for fused models. Crucially, `ollama create` then builds **a separate named model entry**: base + adapter become one package in the blob store, indistinguishable at serving time from any other model. There is no per-request adapter field, no adapter residency separate from model residency, and no batching across adapters — a second persona is a second model, with a second runner, a second weight residency (the merged-or-parallel cost S-LoRA's §2 analysis prices), and a model swap between characters.

That is exactly the pre-S-LoRA world the paper's problem statement describes — adapters handled by *packaging* rather than by *serving*. The gap the paper names, in Ollama's terms: the adapter needs to become a first-class, separately resident, per-request-selectable object over one shared base (IDEA-LEDGER #39), with its memory budgeted in the same pool as KV — not a build-time ingredient of a model entry. Nothing in Ollama's documented surface, as read for this corpus on 2026-11-15, provides that today.
