## 2. The problem as framed

Capacity planning for LLM serving, done the obvious way, is an experiment you cannot afford to run. A deployment decision bundles a parallelisation strategy (tensor/pipeline degrees, replica count), a scheduler (Orca, vLLM, Sarathi-Serve, FasterTransformer-class systems), scheduler parameters (max batch size, batching wait, chunk size, KV watermark), and a GPU SKU — hundreds of configurations per model. Each configuration must be tested against a *workload*, because the paper's motivating measurement shows the optimum is a function of the **model–trace pair**, not the model alone:

- The optimal configuration differs across the 12 model–trace pairs the paper examines (its Figure 1a) — different batch sizes, different parallelism, sometimes a different GPU SKU.
- Reusing one trace's optimal configuration on another trace costs up to **2×** (LLaMA2-70B, Figure 1b).
- A single point in that figure cost as much as **$97K** to obtain by deployment; the paper's running cost context is an estimated $694K/day to serve ChatGPT (Patel & Ahmed 2023, as cited).

Production traces make it worse: they cannot be replayed at will against hardware you do not yet own, arrival processes cannot be re-run identically after a config change, and every new model or workload restarts the search — the search space grows as O(|models| × |traces|). The paper's research question, stated plainly: *is it possible to find a performant configuration without access to expensive experimental resources, at a fraction of the cost?*

Simulation is the obvious candidate and the paper is honest about why existing simulators do not transfer: DNN *training* simulators (Daydream, Habitat, Proteus) assume iterations of hundreds of milliseconds with fixed batch composition. LLM inference violates all of it — iterations of a few milliseconds (predictions must be accurate at far finer granularity), wildly varying iteration times (prefill vs decode phases, varying sequence lengths, dynamically changing batch composition mixing both phases), and **cascading errors**: a mispredicted batch time changes the next batch's composition, so small per-step errors compound into large end-to-end error, worst exactly where it matters — near capacity, where queueing delay explodes.

## 3. Core mechanism in our own words

Vidur's wager: LLMs are architecturally monotonous, so their *performance* can be factorised. Almost all of them are the same small set of operators (attention, MLP linears, norms, activations, collectives) with different dimensions. Profile those operators once, learn to predict the unprofiled sizes, and simulate everything above the operator level — scheduling, batching, KV-cache management, routing — as discrete events.

### 3.1 Operator triage — three buckets, three prediction strategies

The profiler classifies every operator by what its runtime actually depends on:

- **Token-level operators** (linears, activations, norms): runtime depends only on the *total tokens in the batch* (prefill + decode). Profiled with standard PyTorch kernels via CUPTI, for every tensor-parallel sharding the model spec implies — on a **single GPU**, because the sharding arithmetic tells the profiler what each device would compute.
- **Sequence-level operators** (attention): runtime depends on each request's context length, so the input space explodes combinatorially. Two reductions make it tractable. *Prefill* attention is quadratic per request, so a batch of prefills of lengths p₁…p_P is priced as one equivalent prefill of length √(Σpᵢ²). *Decode* attention is memory-bound, so it is priced by **total KV-cache bytes fetched**, not by the per-request split — the paper notes modern kernels (PagedAttention v2, FlashDecoding) handle context-length skew well enough for this to hold.
- **Communication operators** (all-reduce, all-gather for tensor parallelism; send/recv for pipeline parallelism): runtime depends only on bytes transferred and topology; profiled once, model-agnostically.

### 3.2 The runtime estimator — random forests over a sparse profile

Profiling every input combination is infeasible, so Vidur profiles a minimal set and interpolates with **random-forest regression** per operator. The paper's reasoning is methodological and worth keeping: MLPs (the training-simulator choice) need too much data; polynomial regression cannot capture CUDA kernels' tile/wave-quantisation non-linearities; random forests hit the data-frugality/fidelity balance. The estimator emits per-operator runtime lookup tables over the input ranges the simulator will encounter. *This is the load-bearing assumption of the whole system*: every downstream number inherits the estimator's error, which is why the validation methodology (§3.4) is not decoration.

### 3.3 The simulator — a hierarchical, event-driven serving stack

Above the estimator sits a discrete-event simulator with a three-tier scheduler mirroring real serving systems:

- **Global scheduler:** request routing across replicas (round-robin, least-outstanding, and stateful/deferred routing for bursty loads).
- **Replica scheduler:** batching policy plus memory planning/management — a memory planner computes KV-cache capacity from model spec + parallelism config; the memory manager exposes the APIs batching policies are written against. Five policies ship in the paper (FasterTransformer, Orca, Sarathi-Serve, vLLM, LightLLM), each implemented in **<150 lines of Python** — the extensibility claim is quantified, not asserted.
- **Replica stage scheduler:** microbatch scheduling within a pipeline stage (synchronous pipeline parallelism in the paper's version).

Outputs are request-level (scheduling delay, TTFT, time-between-tokens, normalised latency) and cluster-level (MFU, KV-cache utilisation, memory utilisation). **Vidur-Bench** supplies the workload side: traces curated from LMSys-Chat-1M (chat; median prefill:decode ratio 2.3), Arxiv-Summarization (long prompts; P:D 35.4 untruncated, 15.7 in the 4K-capped variant) and Bilingual-Web-Book (decode-heavy; P:D 0.66) — three deliberately different P:D regimes, because §2's whole point is that the workload is half the answer. **Vidur-Search** wraps the simulator in a constrained search: enumerate configurations, binary-search each one's maximum sustainable QPS (defined by a P99 scheduling-delay bound of 5 s), divide by hourly GPU cost, return the best QPS-per-dollar configuration meeting TTFT/TBT SLOs, parallelised across CPU cores.

### 3.4 Validation methodology — against real vLLM, at the hard operating point

The fidelity claims rest on a specific, disclosed protocol: a fork of vLLM extended with the other scheduling policies, chunked prefill and extensive telemetry serves as ground truth. Four models (LLaMA2-7B, LLaMA2-70B, InternLM-20B, Qwen-72B), Azure VMs with 4× A100-80GB (NVLink) and 4× H100-80GB configurations, tensor parallelism matched to model size (TP2 for InternLM-20B, TP4 for the 70B-class models). Two workload regimes: **static** (all requests present at t=0; execution time only, scheduling delay excluded to isolate prediction quality) and **dynamic** (Poisson arrivals at **85% of measured system capacity** — chosen deliberately near the tipping point where errors cascade, and stated as representative of production provisioning headroom). The dynamic metric is percentage error in *normalised* end-to-end latency (latency ÷ output length). Every error figure in §4 carries this protocol with it; detached from it, the figures are uninterpretable — which is precisely the paper's implicit lesson for everyone else's simulators.

## 4. Reported results — as reported, with context

All figures are the paper's own, on the §3.4 setup (A100/H100 datacentre GPUs, vLLM-fork ground truth, the three Vidur-Bench traces capped at 4,096 total tokens). **No figure below is a consumer-hardware figure, a single-user figure, or a claim about any system other than the ones simulated.**

- **Headline fidelity:** inference latency estimated with **<9% error "across the range"** (abstract). The body is more precise, and the body's numbers govern: **static** workloads — P95 (tail) request latency predicted with **up to 3.33% error** across the four models and three traces, with slightly higher error on the 7B model, attributed to its higher relative CPU overhead. **Dynamic** workloads at 85% of capacity — **<5% error in almost all scenarios** (median and P95 normalised latency).
- **Where fidelity degrades — reported by the paper itself:** at **95% of capacity**, larger models retain high fidelity, but LLaMA2-7B's error reaches **12.65% maximum** — small-model CPU overheads mispredicted, then cascaded by queueing near the tipping point. The <9% headline and the 12.65% appendix figure are both the paper's; quoting only the first is misquoting it.
- **Vidur-Search cost contrast (the paper's flagship example):** best LLaMA2-70B configuration found in **~1 hour on a 96-core CPU machine** (Azure rate $9.93/hour as reported) vs a deployment-based exploration estimated at **42K GPU hours ≈ $218K**.
- **The full what-if sweep:** 35,565 simulated runs covering 4 models × 3 workloads; total simulated cost **~$125 (~12.5 hours on the 96-core CPU machine)** vs **$1,139,865** projected for real execution (paper Table 2 / Appendix A.2) — roughly four orders of magnitude, stated by the paper as a cost *of the search*, not a performance gain of any configuration.
- **What the search found (the substantive results):** optimal batch size for LLaMA2-70B is 256 on Chat-1M but 64 on BWB (BWB's long decodes load the KV cache); the optimal SKU flips from H100 (Chat-1M) to A100 (BWB) for the same model. Qwen-72B (multi-head attention) carries ~8× the KV load of LLaMA2-70B (grouped-query attention) and is **almost 2× more costly to serve**, needing a different configuration — architecture details, not parameter count, set serving cost. Misconfiguration cost confirmed in simulation: running Chat-1M under Arxiv-4K's optimal configuration incurs a **2× overhead**.
- **SLO sensitivity:** on LLaMA2-70B/Chat-1M, relaxing the TBT SLO from 120 ms to 140 ms moves the Pareto-optimal cost from ~$0.13 to ~$0.07 per unit capacity — a **~1.85× cost reduction for 20 ms** — and some configurations Pareto-optimal on TTFT violate the TBT SLO outright. Latency promises are priced, discontinuously, and one-metric optimisation silently breaks the other metric's promise.

## 5. What it changed in practice

**Simulation became a citable method for serving questions.** Before Vidur, "what happens if we change the scheduler / SKU / parallelism for this workload?" was answered by buying the experiment or by intuition. Vidur established the template — operator-level profiling + learned interpolation + discrete-event simulation of scheduler and KV system, *validated against a real engine with errors published* — and the template, more than the tool, is what propagated:

- **A simulator lineage followed, each extending Vidur's envelope and citing its limits** (public record as of 2026-11-15): **LLMServingSim** (and its 2.0 revision) coupled simulation to ASTRA-sim-style infrastructure modelling and later to heterogeneous/disaggregated deployments, noting Vidur's aggregated batching and single-hardware-type assumptions; **Splitwise-sim** and **APEX / TokenSim** explored phase-split and serving-dynamics corners; NVIDIA's **AIConfigurator** productised the Vidur-Search idea (recommend parallelism/pool configuration from model, hardware and SLO inputs) inside the Dynamo ecosystem. Later comparative work (e.g. BLIS and subsequent serving-simulator papers) treats Vidur as the baseline discrete-event design — and criticises it on exactly methodological grounds: its runtime estimator is a random forest fit *per (model, GPU, TP) configuration*, its replica scheduler follows a Sarathi-Serve-era vLLM fork, and it does not model admission control or prefill/decode disaggregation. That criticism is Vidur's success measured honestly: the field now argues about simulators' *assumptions and validation regimes*, which is the conversation Vidur started.
- **Vidur-Bench's traces became shared workload vocabulary** — the P:D-ratio framing (chat ≈2.3, summarisation ≫1, translation <1) is now the standard shorthand for "which serving regime is this?", used well beyond Vidur itself.
- **Capacity planning practice shifted at the margin that matters:** configuration search *before* hardware commitment — SKU selection, replica counts, SLO pricing (§4's 20 ms ≈ 1.85× result is the kind of number procurement actually uses) — is now a simulation-first workflow in the large-serving world, with real-hardware runs reserved for validation of the chosen point rather than exploration of the space.

**Limits, stated fairly.** Vidur models *one* engine family's behaviour (its ground truth is a vLLM fork; a llama.cpp or Ollama deployment is outside the validated envelope until re-profiled and re-validated). Its profiles are per-hardware artefacts — a new GPU means a new profiling pass, and an unprofiled configuration is an extrapolation, not a prediction. It does not model correctness at all: a simulated configuration is a performance hypothesis, and §3.4's discipline — validate against the real system at the operating point you care about — remains the user's job. None of this diminishes the paper; all of it is the paper's own methodology applied to the paper.

## 6. Applicability

### (a) Our own programme — prediction held to the same standard as measurement

*[Our synthesis — programme rules drawn from this paper and the MLPerf dossier; not quotations from Vidur.]*

This programme makes capacity claims constantly, in miniature: will this quant fit beside this KV at this context on 6 GB? Does a second resident session fit on the APU? What does a 14,712-token prompt cost before the first token? Vidur's discipline, scaled down, gives those claims a method:

1. **Profile the atoms, simulate the composition — and say which you did.** Aesir already owns the atoms (per-operator timings from its wave-era profiling; the MimirAlloc campaigns' measured host facts). A claim about a *composition* (a new scheduler policy, a residency plan, a snapshot budget) that was derived by reasoning from atom measurements is a **simulation claim** and must be labelled with its validation state: validated against a real run at the stated operating point, or unvalidated. Vidur's <5% dynamic error was earned at 85% of capacity against a real engine; an unvalidated local estimate has no error figure and must not borrow one.
2. **Error grows at the tipping point — measure there.** Vidur is most wrong exactly where queues saturate (the 7B/95%-capacity case). The local analogue: memory and latency claims are most fragile at the residency edge (KV nearly full, spill beginning, second session prefilling). Validation runs for our serve belong at the edge — full context, concurrent prefill — not in the comfortable middle where everything predicts well.
3. **The optimum is a (model, workload) pair — never a model property.** Vidur's 2× misconfiguration penalty and SKU flip kill the phrase "the best settings for this model" in our own tuning notes too. Local tuning records should be keyed by workload shape (prompt/decode lengths, session count) — the P:D vocabulary of Vidur-Bench is directly adoptable for a personal runner's trace diary: chat, summarisation-of-long-document, and persona-sidecar workloads are different regimes with different optima.
4. **Price the latency promise before relaxing it.** The 20 ms ≈ 1.85× SLO result generalises as a habit: when a local target (TTFT budget, max inter-token gap) is loosened to make a design "work," record what the loosening bought. A stall budget silently widened is a benchmark quietly redefined — MLPerf's constitution (§ sibling dossier) forbids it in submissions; Vidur shows its price tag in search.

### (b) What a personal-runner benchmark should report — the simulation annex

*[Engineering judgement, labelled as such; companion to the MLPerf dossier's §6b disclosure set, which covers measured runs. This annex covers predicted/simulated numbers, which a personal programme produces whenever it sizes a feature before building it.]*

Any predicted number in a dossier, plan or commit message should carry:

1. **What was profiled vs what was interpolated:** which operator/kernel timings are measured on the target machine, and which are estimated (and by what — roofline arithmetic, a sibling model's profile, a vendor figure).
2. **The ground-truth anchor:** the real run(s) the prediction is validated against, with the error at that anchor — or the explicit label **unvalidated**.
3. **The operating point:** load/context/session count at which the prediction is claimed, with a note on behaviour at the edge (spill onset, KV-full, capacity) if the point is near one.
4. **The workload shape:** P:D character and length distribution of the assumed trace, since the prediction is void for other shapes (Vidur §2).
5. **The search cost honesty line:** what the prediction cost to produce vs what measuring would have cost — the Vidur-Search contrast ($125 vs $1.14M at fleet scale; locally: an afternoon of reasoning vs an evening of benchmarking) — so a reader can judge whether skipping the measurement was economy or evasion. Where measuring is cheap (it usually is, at personal scale), the annex's verdict is Vidur inverted: *simulate to choose what to measure; never simulate instead of measuring what you could have measured.*

- `aesir/aesir-ideas-for-ollama.md` — raw-oracle grading is the correctness half that Vidur deliberately does not attempt: Vidur predicts how fast a configuration runs, never whether its outputs are faithful. Aesir's serve design needs both instruments — Vidur-style what-if search over residency/scheduling configurations, graded for faithfulness by the raw-prompt oracle before any predicted winner is adopted. A simulator that cannot see divergence will happily optimise a divergent engine.
- `memory/MEMORY-COMPENDIUM.md`, Chapter 9 (Measurement Discipline) — Ch. 9 covers measured claims (§9.2 sustained-vs-peak, §9.3 identical-legs protocol, §9.4 oracle grading). Ch. 9's law "never report a speed without its bytes, its phase, its machine state, and its distance from a measured roof" extends to simulation as: never report a prediction without its profiled-vs-interpolated split, its ground-truth anchor and error, and its operating point.
