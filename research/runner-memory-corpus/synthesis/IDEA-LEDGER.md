## 1. Method note — how ideas were scored

Each idea was scored on four axes, for the target workload above and no other:

1. **Expected gain for the 6 GB single-user long-chat workload.** Prefill avoided, context bought, decode multiplied, or a failure mode removed — in that workload's units (tokens of usable context, seconds of prefill per turn, tok/s at batch 1), never in the source's native units (fleet throughput, batch-64 rates) without translation. Where the corpus's own worked case exists (kv-cache-design §7.2), it governs over any paper headline.
2. **Cost.** Engineering depth (policy flag vs allocator surgery vs new kernels), resident-memory cost on a card that has none to spare, and operational cost (calibration artefacts, per-model validation, training pipelines).
3. **Risk.** Correctness risk first (silent quality loss outranks a crash — a crash is at least honest), then portability risk across arbitrary community GGUFs, then maintenance risk.
4. **Evidence strength**, graded per entry:
   - **A** — measured in a peer-reviewed paper's own evaluation, or in our own campaign records (Aesir gates, MimirAlloc gates), with hardware and workload stated.
   - **B** — reported by a project (docs, release notes, project benchmarks) without independent paper-grade evaluation in the corpus.
   - **C** — reasoned inference: our translation of a measured mechanism to this workload, a dossier's labelled judgement estimate, or an adaptation the source does not itself make. **C is marked honestly wherever the gain — not just the mechanism — is unmeasured on anything like our target.** Several high ranks are C-gain/A-mechanism; the entry says which.

Two corpus disciplines were applied to every number: no number travels without its context (machine, model, precision, workload), and a claim is never stated stronger than its source states it. Where two dossiers give the same idea in different strengths (e.g. prefix reuse in Ollama §9 A2, vLLM §9.2, SGLang §9.1), the ledger carries one entry at the strongest well-evidenced form and names the others as lineage.

**Ranking principle:** correctness and residency foundations first (a fast runner that beheads the persona is worth nothing), then the memory arithmetic that decides what fits, then decode speed, then refinements whose value is real but conditional. Dependencies break ties: an idea that unblocks three others outranks a slightly larger standalone win.

## 3. The ledger — entries

### #1 — Resident session object with token-level residency
- **Rank movement (v2):** rank 1 — unchanged from v1.
- **Source:** `runners/ollama.md` §9 A1; `aesir/aesir-ideas-for-ollama.md` §2.1–§2.2, §3.1 (HS-6, HS-3); `runners/llamacpp-ggml.md` §8.6 lineage.
- **Mechanism:** The conversation becomes a server-side session object that owns its token stream and KV across turns; clients send only the new turn. The session tracks exactly which tokens have KV committed, token by token — generated tokens are committed the moment they are produced — and each request reuses the longest exact token prefix, with the final committed token always re-evaluated as the price of exactness.
- **Expected gain:** Per-turn prefill falls from O(history) to O(new tokens) *guaranteed*, not conditionally on slot luck. Aesir's recorded baseline disease is Ollama-via-Voxta re-evaluating 14,712 tokens in 52.1 s per turn; Aesir's own small proof (HS-3) reused 46 tokens, turn 2 at 610 ms vs 825 ms. The large-chat magnitude on our card is inference, not measurement — hence the split grade.
- **Cost/risk:** The deepest product change in the ledger: session expiry, ownership, crash recovery. Mitigation from the Ollama dossier: sessions are an optimisation layer *over* the stateless API — the client still owns the message log and can replay to rebuild.
- **Evidence: A** for the mechanism and the seam-loss elimination (Aesir gates, bit-exact records); **C** for the size of the win on purplelongship.
- **Home:** anchor/residency — the foundation slice group; #5, #7, #10, #14 all presuppose it.

- **V5 note — construction, not refactor (2026-11-15):** `runners/ollama-internals.md` §7 settles the premise this entry was written on, against the optimistic reading: Ollama proper holds **no session state** — no session object, no conversation identifier, no server-side history; each request carries its full message list, and the one legacy mechanism that gestures at sessions, the `/api/generate` `context` array, is a **deprecated text round-trip** (detokenise the array, prepend it as text, re-tokenise prompt-plus-generation on return) whose handlers log a removal warning per use. There is therefore nothing in the base to refactor this entry *from*: the session object, its token-level residency watermark, and its composition layer are **greenfield construction inside the fork**, and the build campaign should budget them as such (the dossier's own §9 verdict: "the memory work is a reform; the session work is a construction"). The `context` array is a removal candidate, never a foundation. This note changes the entry's cost class, not its rank: the same finding raises the entry's value — no upstream session layer is coming — and §4's dependency argument (everything else attaches to this object) is untouched. The same construction framing applies to #7, #10 and #11, each of which carries the cross-reference in its own v5 note.

- **V6 note — the floor is now priced; the construction case stands (2026-11-15):** two further engines banked this wave decline to build a session object, and their position is recorded here at full strength. ExLlamaV3 has no session type anywhere in its generator/cache structure (`runners/exllamav3-session-pass.md` Q4, verified from structure): the caller owns the conversation as text, re-renders and re-tokenises it whole every turn, trims it from the head when it outgrows the cache, and recovers reuse purely through the content-hash cache. TokenSpeed takes the same position one layer up (`runners/tokenspeed.md` §4.6): the engine should make re-deriving state cheap enough that nobody needs to tell it what a session is; history storage lives in its gateway. This entry is therefore re-argued on its guarantees, not on prefill alone: a stateless engine plus #5's hash cache captures much of the per-turn prefill win *while the cache survives* — and the session pass's own comparison states the price when it does not (evicted pages → replay prefill from the last surviving boundary). What the floor cannot provide is this programme's founding laws: no pinning (the V3 example caller performs #2's failure mode itself, trimming the head), no composed anchor (#7), no validity-enveloped persistence (#10), no disclosure (#6). Disposition: rank and construction framing unchanged; sequencing gains a legitimate interim milestone — #5 stateless first is a shippable floor, and this entry is then justified slice by slice by the guarantees only it adds. The substitute form ("no session layer is needed at all") is rejected as R29.

### #2 — Pinned, non-truncatable anchor segment
- **Rank movement (v2):** rank 2 — unchanged from v1.
- **Source:** `runners/ollama.md` §9 B1 (and §4.3, the two-layer truncation finding); `runners/llamacpp-ggml.md` §8.2; `papers/streamingllm.md` §7a; `memory/kv-cache-design.md` Rule 5.
- **Mechanism:** A request is `[anchor][history][new]`, with the anchor (persona/system) declared as a distinct pinned segment. Truncation and shifting apply to history only, oldest-first; `num_keep` becomes "the whole anchor", not 4 tokens. Stock Ollama's layer-2 shift preserves 4–5 head tokens and frees ~half the window on first shift — at `num_ctx` 4096 a 12,000-token prompt reaches the model as ~5 + ~2,046 tokens — which is the failure this entry abolishes.
- **Expected gain:** Not a speed number: the catastrophic, silent failure mode — a long conversation amputating the persona to 5 tokens — becomes structurally impossible. The corpus's clearest demonstrated harm, removed by policy.
- **Cost/risk:** A pinned anchor permanently consumes window; cap it (the Ollama dossier suggests ≤25% of window) and reject oversize anchors loudly at session creation.
- **Evidence: A** — the failure is source-verified in Ollama's own code at named tags; StreamingLLM's sink measurements (below, #9) independently show why head eviction collapses quality. **Corroborated as shipped canon in v2:** an always-injected head block (Memory) is a first-class object in both persona-chat products now documented — `runners/koboldcpp.md` §9.1 and `runners/aphrodite.md` §9.1 — so the pinned head is two-product practice, not only our law.
- **Home:** anchor/residency — ship with #6; it is cheap (policy, not kernels) and is Volmarr's law, not an optimisation.

- **V5 note — scope widened to the four-behaviour truncation matrix (2026-11-15):** `runners/ollama-internals.md` §5 (Ollama v0.40.16, source-read) settles what this entry must defend against, and it is four behaviours, not one. **Layer 1 exists twice:** native chat (`server/routes.go`) and rendered chat (`server/prompt.go`) each drop whole messages from the front, re-collect system messages from the dropped prefix, keep the last message even if it alone overflows, add a flat 768 tokens per image, and record the event only at debug level — and the twins diverge, down to their log fields counting different quantities (messages dropped vs messages remaining). **Layer 2 exists once:** the Go wrapper's token shift (`llm/llama_server.go`, completion path only) preserves `num_keep` tokens (default **4**) and frees roughly half the remainder, warning-log only, HTTP 400 when shift is off. **The native chat path has no Layer 2 in Ollama at all** — it delegates to llama-server's own shift-or-reject (paired dossier §7: reject before processing, shift only under `--context-shift`, off by default upstream). And the **shift default is family-dependent**: resolved on for every GGUF family except `deepseek2`, so the same over-long history is silently shifted for one model and a loud 400 for another. This entry's anchor must therefore be declared **once, above all four behaviours** — a segment none of the twins may drop, the wrapper may not count inside its keep-4, and the subprocess may not shift — with the family-dependent default abolished in the fork: shift is a per-session declared property (#6 discloses which is in force), never a family accident. The v1–v4 text above stands; this note widens its scope line from "Ollama's two-layer truncation" to the matrix the code actually implements.

### #3 — q8_0 KV by default on small cards, K/V separate, per-model
- **Rank movement (v2):** rank 3 — unchanged from v1.
- **Source:** `runners/ollama.md` §9 C1 (§4.5, §5.5); `runners/llamacpp-ggml.md` §8.3; `memory/kv-cache-design.md` §7.1 Step 3, §7.2 worked case, Rule 4; `memory/gpu-memory-internals.md` §7.3 (the reserve decomposition, new in v2).
- **Mechanism:** Below a VRAM threshold, default the KV cache to q8_0 instead of f16, with K and V types set independently (K is empirically the more sensitive) and a per-model escape hatch to f16. Pure policy over cache types Ollama already ships; requires Flash Attention on the backend, and the *effective* type in force must be reported, including any coupling surprise.
- **Expected gain (restated in v2 — the reserve is now split, and the v1 headline was the headless case):** The corpus's worked case is Llama-3.1-8B class, Q4_K_M weights 5,018 MiB on the 6,144 MiB card. `memory/gpu-memory-internals.md` §7.3 decomposes v1's single 512 MiB planning reserve into its consumers (CUDA context ~300 MiB; display/compositor 200–400 MiB when the card drives a screen, 0 headless; backend scratch, capped ~256 MiB; fragmentation headroom ~10% of the KV arena) and shows the 512 MiB figure is exactly the *optimistic, headless* end of a 0.5–1.0 GiB planning range. **Headless** (reserve ~512 MiB → 614 MiB KV budget), the v1 numbers stand: f16 affords **4,912 tokens** — failing even an 8K minimum — while q8_0 affords **9,246**, so the build ships 8,192 with ~13% headroom; at 32K the saving is 4 GiB → ~2.1 GiB; q4_0 (~17,465 tokens) is an explicitly labelled experiment only, its long-context quality cost documented as noticeable. **Display-attached** — purplelongship's normal state, a laptop driving its own panel — the reserve is **0.9–1.1 GiB**, leaving **≈0–250 MiB** for KV: f16 affords at most ~2,000 tokens and possibly nothing at all; q8_0 at most ~3,800; even q4_0 at most ~7,100. On the desk configuration the 8K minimum is therefore unreachable for this model at *any* cache precision, and the honest levers become a smaller weight quant chosen by lineage (#42), the sub-8-bit tiers (#19/#20), or headless running — chosen by the budget (#12), never discovered by an OOM. The decomposition strengthens this entry rather than moving it: on the machine as actually used, q8_0-by-default is the difference between a product and an allocation failure.
- **Cost/risk:** Quality risk grows with grouped-query-head count and context length; validate per model family (#34) and label each precision with its validated context range. Changing cache type invalidates saved sessions (#10's envelope must record it).
- **Evidence: A** — arithmetic from verified formulas plus the project's own characterisation of q8_0's cost as usually unnoticeable; the worked case is the corpus's own derivation, not a vendor claim.
- **Home:** KV/memory — the cheapest large win in the ledger; do before any eviction scoring (#9), because scoring operates on the cache this entry sizes.

### #4 — Block (paged) KV allocation in one pre-sized arena
- **Rank movement (v2):** rank 4 — unchanged from v1.
- **Source:** `papers/pagedattention-vllm.md`; `runners/vllm.md` §9.1; `runners/ollama.md` §9 C2; `memory/kv-cache-design.md` §2, §4.1, Rule 2; `memory/mimiralloc-our-own-proven-work.md` §5 (the negative allocator evidence).
- **Mechanism:** Pre-size one KV pool at load; inside it, hand out fixed-size blocks (default 16 tokens per kv-cache-design; the vLLM dossier argues 32–64 wastes negligibly at single-sequence scale and cuts table work — a build-time constant to sweep, see Open Questions) through a per-sequence block table with reference counts and a free list. A session grows one block at a time instead of reserving window × slots up front. No per-block host allocation, ever: our own MimirAlloc record is the standing proof that a general allocator is the wrong tool for this shape (it lost all three KV-shaped probes, Z-115). Where the backend offers it, prefer a VMM-backed *expandable* arena — reserve address space once, map physical pages on demand — over fixed segments (`memory/gpu-memory-internals.md` §7.1 item 4); that dossier's §5.2 allocation sequence is the conformance test: an arena whose reserved total doubles under the sequence is behaving like unexpandable segments, whatever its documentation says. The arena's host-side geometry follows #41 (alignment, huge pages, prefaulting).
- **Expected gain:** Memory honesty rather than throughput: prior systems used only 20.4%–38.2% of allocated KV for actual token states (PagedAttention paper's profiling, datacentre traces). The Ollama dossier's judgement estimate for our shape is 2–4× effective context capacity at low concurrency — one real 12–16K session instead of four reserved 4K slots. A cheaper approximation (start small, grow the runner preserving KV via #10) captures much of it if full surgery must wait.
- **Cost/risk:** The deepest runner surgery in the top five; every attention path must read through the table. Kernel complexity is the risk, mitigated by a build-time-constant block size and a plain slice-of-ints table. **Backend-abstraction caution (new in v2 — the Cortex lesson, `runners/jan.md` §6.3, §7.3):** the arena is a contract with the one backend we ship, stated as behaviour (one mergeable arena per lifetime class, growable without copying live data where the backend allows). Menlo spent roughly a year building Cortex — an engine *platform* with its own API and release train — between Jan and llama.cpp, then removed it and went direct, because the abstraction's cost bought engine-swappability the product did not need; the second engine, when it finally came, arrived as a sibling extension, not through the abstraction. Do not generalise this contract into a multi-engine abstraction layer until a second engine is real, shipped and maintained — until then the abstraction is a tax on every release.
- **Evidence: A** for the mechanism (SOSP '23, exact — no accuracy change); **C** for the 2–4× capacity estimate on our workload.
- **Home:** KV/memory — foundation; #5, #9, #10, #11, #23 all build on it.

- **V5 note — the incumbent's alternative, and the defragmentation deletion (2026-11-15):** `runners/llamacpp-kv-internals.md` §§3–4 (llama.cpp v1.0.0) records a sharing design materially different from this entry's block table, and the ledger now carries it as the priced alternative rather than leaving the block design looking inevitable. Upstream shares by a **per-cell sequence bitset**: a cell lists the sequences it is visible to, a shared prefix is stored once with several bits set, same-stream copies are metadata-only, placement is a non-contiguous ring search that tolerates holes, and attention consumes scattered cells through an explicit row list. There is **no block table and no reference counting**, and at v1.0.0 the project **removed defragmentation entirely** (setting and `--defrag-thold` flag deleted, PR #30565; the cell-move operation survives only as commented-out code) — the design bet being that non-contiguous placement makes compaction unnecessary. Two consequences for this entry and #5. First, the fork's choice between block-table-with-refcounts (this entry) and cell-with-bitset is now a *choice*, to be made on the single-user sharing shape (one trunk, swipes, a handful of sequences — the regime where the bitset design is radically simpler) and recorded with its reason; the acceptance test (memory honesty, teardown to baseline) is unchanged either way. Second, **no defragmenter is to be designed, deferred, or assumed**: the incumbent deleted its own once placement tolerated holes, and any fork plan that budgets compaction work is spending on a mechanism its authors abandoned as unnecessary. The VMM precedent in this entry's v2 text is also narrowed by the ggml dossier (`runners/ggml-backend-internals.md` §5.3): upstream's VMM pool is a **scratch-only, stack-discipline** pool (one reservation, bump allocation, backing never unmapped during its life) — it confirms reserve-once/map-on-growth for scratch, and does not by itself prove the shape for the KV arena, which upstream serves with direct buffer allocations. The expandable-arena preference stands as the fork's design position; its upstream evidence is now stated at its true strength.

- **V6 note — the defragmentation verdict is substrate-dependent; two incumbents now disagree (2026-11-15):** this entry's v5 note recorded llama.cpp's deletion of defragmentation and concluded no defragmenter is to be designed. `runners/exllamav3-session-pass.md` Q3 (verified from structure) records the opposite settlement in V3: a real physical compaction exists — idle-only (no job holding any page reference), gated on allocation activity since the last run, disabled if it would move ≤ a tenth of the cache — laying cached chains out as contiguous runs across every cache sharing the page table. The two verdicts do not contradict each other's facts; they price different substrates (llama.cpp's non-contiguous cell placement tolerates holes by design; V3's uniform 256-token pages gain sequential layout). The v5 sentence is therefore narrowed, not reversed: **no compaction of live state, and no defragmenter as load-bearing machinery** — but idle, gated, no-reference layout compaction of the unreferenced cache is a shipped pattern the fork may adopt at its true (small) price. Separately: the arena's ownership discipline is now ranked as #58; this entry's block table is where its states live.

### #5 — Hash-chained / radix prefix cache: persona trunk + branches
- **Rank movement (v2):** rank 5 — unchanged from v1.
- **Source:** `runners/sglang.md` §9.1; `papers/radixattention-sglang.md`; `runners/vllm.md` §9.2; `runners/ollama.md` §9 A2; `runners/mlx.md` S-2.
- **Mechanism:** Finished prefixes stay resident, indexed either as hash-chained blocks (parent hash + tokens + model/quant/precision + scope) or as a token-keyed radix tree — the tree form additionally captures partial overlap (same character, different scenario). The persona/system trunk is inserted once and shared by reference count across sessions and branches; a swipe or regenerate forks at a node and pays only for its suffix (copy-on-write on the boundary block); eviction is LRU over unreferenced leaves only, with the live session's trunk and tip pinned.
- **Expected gain:** In the independent consumer-hardware measurement cited by the SGLang dossier, a 94%-cached prompt cut TTFT ~13× on a laptop-class chip and ~5× on an RTX 3090; an MLX field case shows a cached turn at ~1.4 s vs ~29.5 s uncached. Fleet hit rates of 50%–99% are paper-reported on datacentre workloads and are *not* the expectation here; the local expectation is the shape — later-turn TTFT falls by roughly the cached fraction. Memory saving is equally real: N branches share one trunk instead of N copies.
- **Cost/risk:** The largest single engineering item after #4: node splitting, reference counts, leaf eviction, and ruthless invalidation on model/quant/template change (stale KV is wrong KV). Subtle corruption, not crashes, is the failure mode — budget parity tests.
- **Evidence: A** for the mechanism (NeurIPS '24 paper + production reports); **B** for the consumer-hardware TTFT figures (one independent author's measurements).
- **V4 note — the indexer, collapsed to one process (2026-11-15):** `runners/llm-d.md` §§4.2, 8.2 confirms this entry's data structure from production fleet design and adds three refinements, adopted here. (1) **Longest-consecutive-prefix is the scoring primitive:** the index maps chained block-hash keys → the set of locations holding each block, maintained by create/evict events, and a match counts only as an *unbroken chain* from the root — scattered partial hits are worth zero, which is the correct semantics for causal attention and easy to get subtly wrong with a naive hit-count. (2) **Tier-weighted matches:** llm-d's documented defaults price a CPU-tier block at 0.8 of a GPU-tier block; the local version prices a RAM/SSD-resident block against a VRAM-resident one by *measured restore cost*, per #43/Mooncake's break-even discipline — the weight is a measurement, not a constant. (3) **Speculative indexing:** after choosing a placement, tentatively record the prefix as resident under a short TTL so the next decision sees the in-flight state — locally, the session's next turn is scored against the prefix its own previous turn is still committing. Remove the fleet and the indexer *is* this entry, with pod+GPU/CPU tier renamed VRAM/RAM/SSD tier and the event stream renamed the block allocator's own stored/removed notifications, in-process.
- **Home:** anchor/residency, on top of #4. Prefix caching before tiering (#10/#11): there is nothing to tier until prefixes are retained objects.

- **V6 note — publication is a policy: turn-boundary shaping, and identity is tier-scoped (2026-11-15):** three dated additions from this wave's pair of cache dossiers. **(1) Which boundaries exist is a design variable** (`runners/tokenspeed.md` §§4.2, 4.4, 9.4): a reuse boundary is any token count at which a request *published* its state — page multiples **plus a tail** wherever it stopped (prompt end, junction, finish, retraction) — so the next turn's hit covers the whole previous turn, not all-but-a-partial-page of it. The junction cut (ending the first chunk after a checkpoint exactly at the hit boundary, so KV and recurrent groups resume at one boundary), the in-forward checkpoint (snapshot state at the boundary the *next* turn's re-render will actually resume from — for chat, the end of the re-rendered history, not the raw generation end), dead-checkpoint suppression (checkpoints no future re-render can resume from are kept out of the cache), and superseded-turn eviction (a conversation's two-turns-back checkpoint is evicted early once a newer one publishes past it, unless another request resumed from it) are adopted as this entry's publication policy: small mechanisms, each attacking misses that occur at *every* turn boundary. **(2) The hash-chained form gains its second production instance, with tiers** (`runners/exllamav3-session-pass.md` Q1–Q2): V3 keys each complete 256-token page by a 128-bit hash chained on its parent — the same construction as this entry's hash form — shared across concurrent jobs by reference, retained after finish with no TTL, evicted tree-at-a-time (orphaned chains first, then least-recently-used root, pruned leaf-first so the longest prefix survives partial eviction), and spilled through pinned-RAM and disk tiers under the same key. The radix form remains the partial-overlap variant; the chained form is no longer the less-proven of the two. **(3) Identity is tier-scoped — the tier-dependence disposition.** V3's in-process tiers key on tokens alone, and that is safe there because the configuration domain is singular (one process, one loaded model, one cache configuration: no other configuration exists in that domain for a page to be served under). Its **disk tier is partitioned by a full fingerprint** — model including sampled weight contents, cache configuration and per-layer bit-widths, page size, format version, engine version (session pass Q5) — which is #10's envelope wearing a directory's clothes. The rule this entry now carries: **the chained hash is the identity within a configuration domain; the domain must be explicit, and wherever multiple effective configurations can coexist inside one domain (adapter sets and scales are the proven case — Q32), configuration enters the key or the domain is partitioned.** The slogan form ("the prefix hash is the only identity state ever needs") is rejected as R28. **Flagged divergence, not harmonised:** TokenSpeed publishes partial-page *tails* as matchable; V3 shares only *complete* pages (a tail page carries a placeholder identity until it fills). Both cannot be the fork's granularity rule; the choice interacts with page size (Q11) and is recorded here as an open design fork inside this entry, to be settled with the page-size sweep — the ledger does not pretend the two dossiers agree.

### #7 — Post-history anchor slot (composed, never stored)
- **Rank movement (v2):** rank 7 — unchanged from v1.
- **Source:** `aesir/aesir-ideas-for-ollama.md` §2.3 (HS-5, banked `8f98b2a5`); the same pattern set in Voxta, 2026-11-14 (our records).
- **Mechanism:** A serve-level anchor block (config default + per-request override) is rendered *after* the history at prompt-assembly time, every turn, and is never written into stored history or the committed token stream. Because it is composed rather than stored, history growth cannot push it out, and prefix reuse (#5) still covers the whole history in front of it.

- **Evidence: A** — banked and proven in our own Aesir serve line (HS-5), with the unpushable property as its recorded design intent. **Corroborated as shipped canon in v2:** KoboldCpp's Author's Note is this pattern as a product feature — a near-tail steering note with user-settable injection depth (`runners/koboldcpp.md` §9.1) — and Aphrodite ships the same canon (`runners/aphrodite.md` §9.1); the composed anchor slot now has two independent products behind it as well as our own records.
- **Home:** anchor/residency — after #1 (it needs the session's composition layer), alongside #2.

- **V5 note — construction framing (2026-11-15):** per #1's v5 note: the composed anchor slot presupposes a composition layer the base does not have (`runners/ollama-internals.md` §7 — no session object exists to compose into). ### #8 — Whole-turn summarise-then-evict middle management
- **Rank movement (v2):** rank 8 — unchanged from v1.
- **Source:** `runners/ollama.md` §9 B3; `runners/llamacpp-ggml.md` §8.2 (d); `memory/kv-cache-design.md` §4.2 composition judgement.
- **Mechanism:** When history must shrink, drop or compress *whole turns* (user/assistant pairs), never partial turns and never tokens from inside a turn or adjacent to the anchor. Preferred form: summarise the dropped span into a short recap segment inserted after the anchor (itself pinned, second tier), accepting one summarisation pass as the price of coherence. Token-level middle excision (llama.cpp shift style) is reserved for raw completion mode, where it was born.
- **Expected gain:** Degradation becomes graceful and semantically coherent — older turns fade; persona and current exchange remain intact. No corpus measurement quantifies chat quality under this policy vs raw discard; the gain is a correctness-of-degradation claim.
- **Cost/risk:** Whole-turn units lose information in larger chunks than token eviction, and summarisation costs a generation pass plus a recap-prefill. The recap can itself drift from the dropped facts — it is a memory aid, not a record (see #9's honesty requirement). **Supersession discipline (new in v2, `memory/agent-memory-architectures.md` §6.4):** the recap is a *derived* record — typed as such, citing the span it summarises — and it is itself superseded when the facts under it change; it is never silently promoted to the standing of a record. A recap store that cannot supersede becomes exactly the stale-fact reservoir that dossier's §6.1 proves an append-only store must become.
- **Evidence: C** — reasoned composition of two dossiers' prescriptions; neither measures it.
- **V3 note (2026-11-15):** the summarisation this entry performs is a consolidation, and v3's ancestor evidence prices its failure mode. `memory/generative-agents.md` §§3.3, 5.2: reflection **survives flattened** — one level of consolidation (episodes → summary), off the critical path, outputs **typed as derived and citing their evidence**; the multi-level reflection tree died because each level multiplies fabrication (R22). The production name for that fabrication is **summary drift**: a summary drawn partly from since-superseded material is not itself superseded when the source is corrected, absent dependency tracking — so this entry's summaries carry provenance and are invalidated when their sources are (the open design question is Q25). The importance-accumulation trigger (reflect when enough has happened, not on a wall-clock timer) is the one scheduling mechanism in the paper no descendant appears to have kept — adopted here as this entry's trigger, labelled judgement in the dossier.
- **Home:** accuracy — the policy layer above #9's mechanism; the two must be designed together so scoring never splits a turn.

### #9 — Eviction composition: pinned head + scored middle + recent window
- **Rank movement (v2):** rank 9 — unchanged from v1.
- **Source:** `papers/streamingllm.md`; `papers/h2o.md`; `memory/kv-cache-design.md` §4.2, §7.1 Step 6, Rule 5.
- **Mechanism:** Three pools, three rules, one declared composition. (i) Pinned head: the persona block plus the first few tokens forever — StreamingLLM's ablation found 4 sink tokens reach essentially full quality on Llama-2-7B, and evicting the head collapses perplexity (Llama-2-13B window attention 5158 vs 5.40 sink+window on PG-19). (ii) Scored middle: heavy-hitter retention by accumulated attention (H2O), evicting the lowest-scored non-recent token at block granularity. (iii) Recent window: never evicted, protecting tokens that have not yet had the chance to prove themselves. Every eviction is reported (#6).
- **Expected gain:** H2O at a 20% cache budget stayed within ~2% perplexity of full cache on its reported suites where recency-only policies degraded sharply on recall tasks (paper's measurements, A100/FlexGen implementation, OPT/LLaMA/GPT-NeoX). For our workload the honest translation is: a much longer *usable* conversation at the resident cache #3 sizes — not a longer *remembered* one. Evicted detail is gone permanently and the model will confabulate rather than admit it; pair with #8's recap/external memory for facts.
- **Cost/risk:** The integration cost is attention-score accumulation: fused attention kernels deliberately do not materialise attention weights. A per-step reduction over the newest query's weights is O(context) and small; if the runner cannot do even that, a sampled-steps degraded variant must be labelled as such and quality-tested. Irreversibility is intrinsic.
- **Evidence: A** for both component policies (ICLR '24; NeurIPS '23); **C** for the three-pool composition as a chat policy (the composition is the corpus's synthesis, kv-cache-design §4.2).
- **Home:** KV/memory — after #3 (precision first: scoring a cache you are about to halve re-scores everything) and after #4 (eviction is at block granularity).

### #10 — Session persistence to disk/RAM with a validity envelope
- **Rank movement (v2):** rank 10 — unchanged from v1.
- **Source:** `runners/llamacpp-ggml.md` §8.1 (§3.4); `runners/ollama.md` §9 A3; `memory/kv-cache-design.md` §4.4, §7.1 Step 7; `runners/sglang.md` §9.1 (HiCache tiering, miniaturised).
- **Mechanism:** Serialise a named session's stable-prefix KV to fast local storage at unload, on idle-timeout, and at branch points; reload instead of re-evaluating on reopen. The file carries its own validity envelope — model identity (GGUF hash + quant + build), context size, cache precision, tokeniser/template version, token count, checksum — and refuses loudly and distinctly on mismatch, where upstream returns one generic 400. Store quantised (q8_0 halves the file). A session file *is* the conversation in recoverable form and inherits the conversation's privacy handling.
- **Expected gain:** Measured on a CPU-only VM (Qwen3-1.7B, 7,289-token prompt): restore **2.14 s vs 160.7 s** cold prefill; a second measurement put a 5K-token chat at ~7× (9.9 s → 1.4 s). On GPU hardware the absolutes shrink but file-read vs compute still favours restore for long prefixes; returning-conversation TTFT becomes near-constant.
- **Cost/risk:** Disk: the measured 7.3K-token session was 836 MB for one small model; a 32K-context 8B session at f16 is ~4 GiB by the §5.5 arithmetic. Needs an eviction policy and the discipline not to save short chats whose cold prefill is already fast.
- **Evidence: A** — community measurements reported and dissected in two dossiers; the envelope design is ours (C for that part).
- **V3 note (2026-11-15):** #43 (new in v3) supplies this entry's demote/promote transform at its tier boundaries — the CacheGen codec is how a session's KV crosses VRAM→RAM→SSD cheaply. The boundary of that licence is R20: **this entry's snapshots stay bit-exact**; lossy encoding is lawful only for labelled derived artefacts at the pool layer (shared prefix caches, cold archives), never inside the session record itself. InfiniGen's restore-scheduling steal also lands here (`papers/infinigen.md` §6b): a bit-exact snapshot need not be restored atomically — restore what the first generated tokens touch first, stream the remainder behind ongoing decode; scheduling, not representation.
- **Home:** anchor/residency — the persistence tier of #5; sequence strictly after prefix caching exists.

- **V5 note — persistence is construction, and the envelope is fork work (2026-11-15):** two source-read corrections to this entry's assumptions. (1) Per #1's v5 note, there is no upstream session layer to persist *from* — this entry builds its store against #1's new object, not against any inherited state. (2) The nearest upstream analogue, llama-server's RAM prompt cache (`runners/llamacpp-kv-internals.md` §5.3, v1.0.0), keys its entries on **tokens + checkpoints only** — no adapter set or scales, no template or sampler identity — with FIFO eviction and destructive single-use restore; an external report at an earlier build demonstrated KV computed under one LoRA scale being silently reused under another, and the v1.0.0 entry structure still contains no configuration identity, so the gap is treated as **plausibly open, unverified by execution** (Q32). This entry's validity envelope is therefore not a property the fork inherits from its base — it is precisely the work that distinguishes the fork's store from the upstream cache, and it must key on the **full effective configuration** (tokens, adapter set + scales, template identity, cache precision, model hash) from the first slice. The envelope list in the v1 text above stands and is extended by that sentence.

- **V6 note — persistence splits by reuse horizon, and the envelope takes its production form (2026-11-15):** `runners/deepinfer.md` §§5.1, 5.3, 11.1 is the production evidence for a partition this entry previously left monolithic, and batch-13 ingestion's treatment of it as a refinement of this entry is confirmed at ledger level: **persisted state has two populations with opposite reuse shapes, and they get different media and different lifetimes.** DeepInfer's split — global KV on SSD for days (TTL 3 days agent / 7 days chatbot, set from measured reuse intervals and priced in hit-rate points), sliding-window state in host DRAM for minutes, and window state at resume rebuilt by bounded replay rather than stored — miniaturises to: **the trunk** (persona/system prefix + completed turns; long-tail, reused across days) persists to disk under this entry's envelope; **the live window's transient state** stays in RAM only; and the runner *counts* trunk-hit age distribution (#6 applied to its own cache policy) so the local TTLs are set from measurement, as DeepSeek's were, not by habit. **The validity tuple is adopted as the envelope's production form** (DeepInfer §5.3): reuse is keyed by (deployment configuration, weights, user group), and *any* framework change that alters KV values invalidates — with DeepSeek's operational rule attached: **no migration path; a mismatch discards, never converts.** The local tuple drops the user-group term (one user) and adds the axes Q32 proved load-bearing (adapter set + scales, template identity, cache precision, runner KV-affecting version). The rebuildable third class is **not** adopted for session resume: bounded replay on untrained local models is deferred as R27 — DeepInfer's model was trained to tolerate replay error and still flags resumption boundaries as uncharacterised; a local resume that approximates window state silently breaks this entry's bit-exact contract (R20).

- **Rank movement (v2):** rank 11 — unchanged from v1.

- **Mechanism:** Hold session KV in system RAM (or in #10's store) independently of weight residency, so evicting a model for a second model does not destroy the first model's sessions. Preemption policy, laptop form: never preempt the *running* sequence; spill *idle* sessions to RAM (llama.cpp's bounded RAM-cache shape), then to disk at checkpoints; keep recompute as the always-working fallback for short spans only, and make any preemption of the live conversation visible ("context was compacted"), never silent.

### #50 — The four-number context rule: budget and report against the usable number
- **Rank movement (v4):** new in v4 — enters at rank 13, directly after #12 (the budget it completes).
- **Source:** `papers/ruler.md` §§3–5; `papers/infbench.md` §§3, 5–6.
- **Mechanism:** Every context figure in the build carries **four numbers, never one**: **trained** (the length the model was trained at), **scaled** (the length its positional scheme claims after RoPE scaling / extension), **allocated** (the window the runner actually reserves and pays KV for), and **usable** (the *effective* length, measured by a RULER-shaped probe at deployment precision — retrieval *plus* tracing, aggregation and QA-shaped tasks, since vanilla needle retrieval saturates while the harder categories collapse). The rules: any published context figure **names which number it is**; the KV budget (#12) is set against the **usable** number where one is known; anything allocated above usable is labelled **reach**, priced in full by the KV arithmetic, and never presented as capability.
- **Expected gain:** Not speed — honesty with a budget consequence. **Effective ≪ claimed, as-reported:** GPT-4's 128K claim measured **64K effective** under RULER's threshold (and Llama2-7B scored 85.6% at its own 4K); Yi-34B's 200K claim measured **32K**; LWM's 1M claim measured **<4K** (RULER v1/v3 figures as-reported — cite the version a claim comes from, never blend them: v1, April 2024, seven authors, ten models, "only four models" at 32K; v3/COLM, August 2024, eight authors, 17 models, "only half"). Locally: every allocated token past usable is charged in full and fails quietly — on a 6 GB card, allocating to the *claimed* number instead of the usable one spends the scarcest resource on context the model cannot actually use, and #3's arithmetic makes that spend visible per model.
- **Cost/risk:** The probe itself (Q26): prefill-dominated, run per (model, quant, workload shape) at deployment precision — neither context paper ablates quantisation (RULER ran BF16 via vLLM; ∞Bench contains no precision study), so "quantisation shrinks the usable number" is corpus synthesis, testable only locally, and this entry claims it as a hypothesis the probe settles, not a finding. The reporting half costs nothing but discipline.
- **Evidence: A** for the effective≪claimed measurements on the stated testbeds; **C** for any local usable number — none exists yet, and this entry asserts none.
- **Home:** KV/memory — the reporting/budgeting companion to #12; its measurement is Q26, its disclosure rides on #44.

- **V5 note — the scaled number names its recipe (2026-11-15):** `papers/position-interpolation.md` and `papers/ntk-aware-scaling.md` (the family's two roots, banked this wave; the descendants YaRN/LongRoPE were banked in wave 7) complete this entry's vocabulary. The **scaled** number is manufactured by a *recipe*, and the recipe is part of the number: **PI** (Chen et al., June 2023) is uniform position compression plus a ≤1,000-step fine-tune, its effective-window evidence a passkey probe with a ≥20%-over-10-attempts criterion — a lenient single-needle standard by RULER's measure, and its own tables show the price (original-window degradation growing with scale factor *s*; BoolQ 76.1 → 64.7 at 16×). **NTK-aware scaling** (bloc97, June 2023 — a community post, **no paper exists**; formalised in YaRN §3.1/App. A.2) mints the scaled number with **no training run at all**: one RoPE base change, high frequencies effectively extrapolated, low frequencies interpolated, its base set empirically (Code Llama hand-set 1,000,000 and ignored the formula). The rule this entry now carries: **every scaled figure names its recipe, its fine-tune (or its absence), and its pricing evidence; the cheaper the recipe, the more of the evidentiary burden shifts to Q26's probe** — a number minted by a config line is a claim, and the probe is its only possible backing. The runner-side duty is unchanged detect-and-honour, sharpened by NTK-aware's shape: honour the **shipped** base/factor exactly, never recompute it from the formula (practitioners set it higher than nominal), and never apply a copied scaling setting to a checkpoint that was not extended with it — both errors are silent at short lengths and appear only in the long sessions the setting was for.

### #13 — Byte-stable prompt rendering as a caching requirement
- **Rank movement (v2):** rank 13 — unchanged from v1.
- **Source:** `runners/llamacpp-ggml.md` §8.6; `runners/sglang.md` §9.1 (prompt-assembly discipline); `runners/ollama.md` §9 D1; `papers/radixattention-sglang.md` §7a.

- **Cost/risk:** Template rigidity: any feature wanting per-turn prompt variation must live after the stable prefix or it silently destroys the cache — and without the telemetry check, nothing will say so.
- **Evidence: A/C** — the mechanism is exact (A); the per-turn token counts are arithmetic from stated sizes (derived, labelled as such in the source dossier).

- **V6 note — byte-stability presupposes tokeniser purity (2026-11-15):** `runners/exllamav3-session-pass.md` Q5 closes the mechanism behind V3's v1.6.5 prompt-caching regression, and its lesson generalises past that engine: the cache faithfully keyed whatever token identifiers it was given; what broke was that a chunked long-input encoding path produced *different identifiers for the same text* (a split inside a multi-character line-ending token; a correctness probe that failed to restore the tokeniser's special-token mode). **Tokenisation of a given text must be a pure function of the text — independent of length, chunking, and call history** — or every hash downstream misses silently and #5/#1 pay for a cache that exists but never hits. The settling question for the fork's own path is Q34.

### #14 — Stable-order, whole-block memory injection under a token budget
- **Rank movement (v2):** rank 14 — unchanged from v1.
- **Source:** `aesir/aesir-ideas-for-ollama.md` §3.3 (HS-7, banked `fd53cc8c`).
- **Mechanism:** Memory injected into a prompt (recall, lore, world-info) arrives in the same order every turn — sorted by a fixed key (priority, then stable id; never by recency or retrieval score, which change turn to turn) — admitted in whole blocks or not at all, against a %-of-context budget, dropping the lowest-priority whole block when over budget rather than truncating mid-block. Per-turn reuse counters are logged so churn is visible. **Store-side requirement (new in v2, `memory/agent-memory-architectures.md` §§6–7.1):** the injected set must be drawn from a store with supersession semantics — versioned facts with bi-temporal validity, tombstones consulted at read time, provenance on every record — because append-only storage plus retrieval guarantees eventual contradiction (that dossier's §6.1), and a stable-order injection of *stale* facts is worse than churn: it is consistently, reproducibly wrong. The store itself lives in a memory service beside the runner, not in runner state (§7.1's boundary argument: the runner is the cache, and caches do not own databases); the runner's half is the stable, budgeted, logged injection specified here. An explicit "no relevant memory found" state must be distinguishable from "memory was not consulted" (§6.3, abstention).
- **Expected gain:** Protects #5/#13: any reordering or partial admission changes the token prefix and destroys the reuse the session exists to provide. The gain is the preservation of the prefix-cache win in exactly the workload (retrieval-augmented character chat) most likely to lose it.
- **Cost/risk:** Whole-block admission wastes the partial space a truncated block could have used; the budget discipline is the product decision. Retrieval quality may prefer score order — the contract deliberately subordinates it to stability.
- **Evidence: A** — banked in our own Aesir serve line with its contract recorded (fixed order, budgeted whole-block admission, reuse counters); the Ollama-side magnitude is unmeasured. **Corroborated in v2:** the keyword-triggered, budget-capped lorebook (World Info) is shipped canon in two independent products (`runners/koboldcpp.md` §9.1; `runners/aphrodite.md` §9.1) — B-grade product evidence for the budgeted-injection half; the supersession requirement rests on the agent-memory dossier's published-practice survey (Mem0 / Letta / Graphiti patterns, §6.2).
- **V3 note (2026-11-15):** #47 (new in v3) is this entry's store-side existence law, stated there in full: decay may rank this entry's injected candidates (currently-valid, episodic tier only), and may never decide what the store keeps; the anchor is never scored at all. The ancestor pair is the evidence: Generative Agents' scored stream has no supersession operation at all (`memory/generative-agents.md` §5.3 — the corpus's append-only theorem in its purest early form, priced at R17), and MemoryBank's decay updater is the limiting case of a store whose read path *cannot* filter, because its write path recorded nothing to filter by (`memory/memorybank.md` §7) — which is Q18's sharpened form in v3.
- **Home:** accuracy — design with #8; both are "how memory enters and leaves without lying about it".

### #37 — Sampler pipeline as a first-class, ordered, per-request surface
- **Rank movement (v2):** new in v2 — enters at rank 15.

- **Source:** `runners/koboldcpp.md` §9.2 (§§4.2–4.3); `runners/aphrodite.md` §9.4 (§4).

- **Expected gain:** No speed claim — this is persona quality. For long-form character chat the sampler stack is the difference between a persona that stays in voice for 200 turns and one that loops by turn 30 (Aphrodite dossier's phrasing); KoboldCpp's dossier calls sampler depth the clearest documented differentiator against Ollama's standard API and, for fiction users, *the product*. Implement from the published concepts (DRY/XTC/mirostat have their own public literature) — never from either product's code; Aphrodite is AGPL and is a study source, never a code source.
- **Evidence: B** — documented behaviour of two shipping products; no paper-grade evaluation in the corpus, and the 200-turn figure is a dossier's qualitative judgement, marked as such.
- **V3 refinement — samplers compose or substitute, never both (2026-11-15):** `papers/min-p-sampling.md` §§3, 5–6 and `papers/mirostat.md` §§3, 5–6 give this entry its two paper-backed members, and they are different *kinds* of thing. **Min-p is a stateless filter that composes late in the chain:** keep tokens with probability ≥ p_base × p_max (p_max post-temperature in the reference implementations), p_base 0.05–0.1 as published; ship it as the primary truncation sampler, enabled by default (persona preset min_p 0.05–0.1, top_p/top_k off), in the shipped chain order penalties → DRY → truncators (min-p last among them) → XTC → temperature last, renormalising once at the end, with preset validation rejecting stacks of multiple aggressive truncators. Ship Mirostat 2 first (one float of state, no Zipf fit), scoped to long persona sessions as a named anti-drift preset; defaults follow runner practice (τ=5.0, η=0.1), not the paper's GPT-2 optimum. **μ is per-generation state:** μ starts at 2τ, updates μ ← μ − η·e every token, resets each generation, never leaks across requests sharing a resident runner, is restored with a resumed prefix (it belongs in the session snapshot state beside the KV material), and is logged beside τ, η and the seed — without them a mirostat run is not reproducible under this entry's own conformance habit.
- **Home:** accuracy — the cheapest high-value feature entry in the ledger; it has no dependency on the memory machinery and can ship in parallel with the top five.

(1) The guided-generation dossiers name constraint as this entry's **missing sibling**: the grammar mask is not a sampler and does not belong inside this chain at all — it restricts the distribution's *support* before the chain shapes it. That discipline is formalised as **#49**, with its home at #36's interface; this entry's chain order (penalties → DRY → truncators → XTC → temperature) is unchanged, and #49's mask sits strictly before all of it. (2) `papers/contrastive-decoding.md` §§5–7 and `papers/dola.md` §§5–7 add a third and fourth member to the class mirostat opened: **contrast transforms are not chain-shaped.** CD and DoLa are distributions→distribution transforms needing a *second logits input* this chain does not carry (a second model's logits for CD; per-layer logits for DoLa), so they cannot be modelled as chain stages; their ordering against grammar masks and truncators is **open — not settled — in the literature**, and no published acceptance rule preserves a contrasted distribution under speculation. ### #19 — Asymmetric KV quantisation: K per-channel, V per-token, FP16 residual
- **Rank movement (v2):** rank 17 — ↑ from #19 in v1.
- **Source:** `papers/kivi.md`; `memory/kv-cache-design.md` §5.2.
- **Mechanism:** Keys and values have opposite outlier geometry, so quantise them along opposite axes: keys per-channel (grouped along the token axis, so outlier channels get their own scale), values per-token (so each token's error stays its own). New K/V land in a full-precision residual window (paper defaults: group 32, residual 128); when it fills, its oldest block is quantised into the grouped body. Attention runs in two tiles — fused dequantise-in-matmul over the grouped part, ordinary path over the residual — concatenated before softmax. The residual is load-bearing, not overhead: fake-quantising everything drops Llama-2-7B GSM8K from 13.50 to 5.76, vs 12.74 for KIVI-2 with its residual.
- **Expected gain:** Paper-measured (A100-80GB, HuggingFace implementation): KIVI-2 at 2.6× less peak memory including weights and near-baseline quality on its suites (Llama-2-7B LongBench average 44.52 FP16 vs 44.27 KIVI-2). Corpus arithmetic for our shape: an 8K context's ~1 GiB FP16 cache (7B GQA worked example) falls to roughly 150–200 MB including residual and scales. This is the tier *beyond* #3 — q8_0 first, this when 8K is not enough. **Restated in v2:** on the display-attached card (#3's split reserve: ≈0–250 MiB of KV budget for the flagship 8B), this tier is no longer only "beyond 8K" — it is among the few ways a mid-length context exists at all at that operating point, which is why the entry is promoted two places. The promotion does not relax its gate: the paper's evaluation ceiling (≤4K for most models) is now the binding risk, and R7's per-model, longest-context grading requirement is unchanged.
- **Cost/risk:** A llama.cpp-class kernel project, not a flag flip — Ollama's existing uniform cache types are not this scheme. Evaluation ceiling: LongBench capped at 4,096 tokens for most models in the paper; nothing validates 2-bit at 32K+. Falcon/MQA is the warning label: already head-compressed caches have less headroom, and the paper's own fix is 4-bit. Default per model by KV-head structure, gated by #34.
- **Evidence: A** — ICML '24, with the axis ablation stated brutally (any V-per-channel configuration collapses to ~2.8 / ~0.3–0.7 on its CoQA/TruthfulQA fake-quant tests).
- **V4 note — SmoothAttention, a converter-side KV4 candidate (2026-11-15):** `papers/qserve.md` §§3–4, 6 adds a member to this entry's family that costs no kernel: SmoothAttention is a RoPE-commuting diagonal rescaling folded **offline into W_Q/W_K** at conversion time, recovering **0.05 of KV4's 0.14 perplexity cost** in QServe's ablation (Llama-class, as-reported) — zero runtime work, which is precisely why it is a candidate here while QServe's KV4 *kernels* are not (its A100 naive-KV4 baseline ran 1.1–1.2× *slower* than KV8 before optimisation, as-reported: any local KV4 claim is graded on measured decode tok/s at long context, not bytes saved). - **V5 note — head-policy composes with this tier (2026-11-15):** #54 (new in v5) is this entry's capacity sibling on a different axis: asymmetric precision shrinks the bytes **per token kept**; head-policy shrinks the **tokens kept per head**. The dossier's arithmetic composes them (614 MiB budget: ≈9,500 tokens at f16 under a 50%-retrieval GQA policy, ≈17,900 composed with q8_0) — labelled arithmetic in the dossier, not a measurement, and gated by Q29 exactly as this entry is gated by R7. Neither tier relaxes the other's gate.

### #42 — Weight-quant provisioning by lineage, not by bit count
- **Rank movement (v2):** new in v2 — enters at rank 18.
- **Source:** `papers/gptq.md` §6a; `papers/awq.md` §6a; `papers/smoothquant.md` §6a; `papers/quip-sharp.md` §6a.
- **Mechanism:** Choose, recommend and ship weight artefacts by quantisation *method lineage* per bit-width — with true-bitrate accounting (group scales and zero-points are real bits) and a mature-kernel requirement — instead of by the bit count on the label. The canon's rules: at **4 bits**, GPTQ/AWQ/GGUF-Q4-class artefacts are all sound and kernel maturity decides. At **3 bits**, method is worth more than a bit-width step: AWQ-class > GPTQ > RTN (AWQ's LLaMA-7B INT3 row, perplexity: FP16 5.68, AWQ 6.35, GPTQ-with-reorder 6.53, GPTQ 8.81, RTN 7.01). At **2 bits**, only the incoherence/codebook lineage is credible (QuIP#/AQLM-class; GGUF IQ-class with activation-derived importance data); scalar RTN/GPTQ-style quantisation pushed below its regime is not a provisioning option. Solve the (model, bits) choice jointly: a larger model at fewer bits can beat a smaller model at 4 bits *only* from that lineage. W8A8 (SmoothQuant lineage) is a quality reference point, not a 6 GB deployment target: it halves weight memory where W4A16 quarters it, and its INT8-arithmetic prize belongs to compute-bound serving, not bandwidth-bound single-user decode.
- **Expected gain:** This entry is the rule that makes #3's and #12's "buy VRAM back with a smaller weight quant" lever safe to pull — and on the display-attached card (#3, restated) that lever is now routinely load-bearing for the flagship model. It also prevents the two classic provisioning errors: shrinking a small model to 3 bits to make it fit (small models degrade disproportionately at low bits — GPTQ's own numbers), and trusting a label over the method that produced the artefact.
- **Cost/risk:** Per-artefact grading through #34 (with its calibration-integrity rules) is the price of admission; availability rules practice, so grade the specific artefact, never the surname. Kernel cost is part of the format: a codebook artefact whose dequantisation path is slow can lose its entire bandwidth saving (the AQLM cautionary tale — more accurate on paper, slower than FP16 in practice, purely from codebook cache behaviour).
- **Evidence: A/C** — the method comparisons are paper-measured (A); the provisioning rule assembled from them is the corpus's synthesis (C).
- **Home:** KV/memory — the weights half of the budgeting pair with #3; applied at model onboarding alongside #12.

- **V6 note — the trellis lineage re-scopes the floor, conditionally (2026-11-15):** `runners/exllamav3.md` §§3, 6 (EXL3, a streamlined QTIP trellis-coded format with Hadamard incoherence processing and LDLQ error feedback) extends this entry's lineage table at exactly the bit-widths where it matters. The entry's existing rule — at 2 bits only the incoherence/codebook lineage is credible — gains its strongest shipped member: EXL3 publishes coherent artefacts at ~1.6 bpw on large models and release-tests MoE quants at 2.05 bpw, and independent measurement in the dossier (30B MoE: EXL3 at 3.0 bpw within 0.14 perplexity of a ~4.86 bpw GGUF K-quant; 12B at 4.00 bpw with lower mean KLD than Q4_K_M at fewer *weight* bytes, RTX 5090 stack comparison, all as-reported) supports the dossier's summary: **the usable floor moved down by roughly a bit per weight at equal quality versus scalar allocation.** The re-scope is conditional in three stated ways. (1) **Per artefact family, graded:** the floor is a trellis-artefact property, established per family through #34 like every tier in this entry — it does not lower the floor for scalar GGUF tiers by association. (2) **Provision on total bytes, never the bpw label:** EXL3's headline excludes its embedding table (default 16-bit; quantisable to 1–8 with RAM/disk-streamed decode) — in the 12B comparison, embedding-inclusive totals were near-identical to a GGUF Q5_K_M. A fork-side trellis *quantiser* is deliberately **not ranked**: it is a format programme whose own dossier gate is a decode-kernel prototype on the target card class (dossier §9.1) — if trellis decode at 2.5 bpw does not beat scalar at 3.5 bpw on the same card, the programme drops and only this provisioning note survives. Rotation + error-feedback rounding without the trellis (dossier §9.2) is recorded as the stepping-stone form if that gate is ever run.

### #18 — Chunked prefill with progress and cancellation
- **Rank movement (v2):** rank 21 — ↓ from #18 in v1.
- **Source:** `papers/sarathi-serve.md` (the mechanism's paper, new in v2); `runners/vllm.md` §9.3; `runners/mlx.md` S-5; `papers/orca.md` §7a (step-loop shape).
- **Mechanism:** Cap new tokens per engine step (512–2048 as the local starting range; auto-size the chunk to current headroom on tight budgets); a long prefill is split across steps, yielding to the event loop and a cancel check between slices, with streamed progress ("prefilling… 12,400 / 96,000 tokens"). The attention implementation must support attending over a partially prefilled prefix with correct position offsets — the same machinery #5's suffix prefill needs. Only the *uncached suffix* is ever chunked: chunking makes re-evaluation polite; #1/#5 make most of it not happen.
- **Expected gain:** Zero for raw speed and stated as such in the source: chunked prefill does not shorten the request's own TTFT. The gain is that a long paste or document ingest converts from "the app hung" into a cancellable progress bar — on a laptop, often the difference between a kept user and a lost one. **Priced in v2 by `papers/sarathi-serve.md` §6a:** at budget τ=512 the corpus's own 14,712-token disease case is 29 chunks, so the worst-case delay imposed on anything else in the loop is ~3.5% of the prompt instead of 100%; the paper's ablation prices the politeness — prefill up to ~25% slower at τ=512, negligible at τ=2,048 (Yi-34B; direction and shape transfer, percentages do not) — so the local τ belongs at the large end, exposed to the user as *maximum inter-token gap during ingestion*, not an abstract token count. The stop-word consequence is a correctness property, not a nicety: a runner that regains control only at step boundaries can only honour a stop, an interrupt, or a new message at step boundaries — for any voice/controller surface, the boundary must be one step away, not 52 s.
- **Cost/risk:** Low; the risk is a subtle position/attention-mask bug across chunk boundaries. Acceptance test from the dossier: a long prompt computed chunked vs whole must produce identical logits.
- **Evidence: A/C** — the mechanism and its price are paper-measured (OSDI '24, fleet setting); the single-user sizing and the stop-word framing are our translation.
- **V3 refinement — the fuse half completes this entry (2026-11-15):** `runners/deepspeed-fastgen.md` §§2, 7 is the second source, and SplitFuse generalises the fill. Sarathi's formulation spends the budget on one prefill chunk plus decodes (the *split* half, already in this entry); the *fuse* half composes **any mixture** — several short prompts, parts of prompts, and all pending decodes — to hit the budget **exactly**, including splitting a short prompt solely for alignment. The law, in INGEST-006's words: **a token budget is a target to compose to, not a cap to fit under** — under-filled passes waste the weight read as surely as over-long passes stall decodes. **Choose the budget at the knee:** profile throughput vs tokens-per-pass per (model, device) and set the budget at the smallest pass size reaching near-peak throughput, further bounded by the inter-token latency the product promises; FastGen publishes the method and **no numeric budget**, so there is no SplitFuse number to copy — Sarathi's 512–2,048 remains the starting bracket, localised by the knee profile (re-profiled on model load, under representative concurrency). Two honest limits, both from the dossier: exact-fill buys nothing when the queue is empty — apply it only when a queue exists, which on this single-user target is the exception, and is why this refinement does not move the rank; and FastGen's headline gains (up to 2.3× "effective throughput" vs the vLLM of late 2023, as-reported) live in long-prompt/short-output traffic on the claimant's own SLA-defined metric, against a vLLM that did not yet ship chunked prefill, with a contemporaneous vLLM rebuttal (14 Nov 2023) finding the advantage absent or reversed in other regimes — steal the composition rule and the knee method, not the multiplier. Priority, recorded without a winner declared: Sarathi's August 2023 preprint is the first full public description of chunked prefill; FastGen (November 2023) shipped it first in a supported library and cites Sarathi. The chunked-vs-whole logits acceptance test above governs fused passes unchanged.
- **Home:** robustness — cheap; schedule any time after the step loop exists.

- **V6 note — the budgeting variable changes: tokens → time (2026-11-15):** `runners/deepinfer.md` §§4.2, 11.4 supplies this entry's third form. DeepInfer's prefill scheduler does not fix a chunk size: each step is given a **time budget** (a nanosecond compute quota), and a fitted **quadratic cost model** — cost as a function of chunk tokens *and* the prefix length already computed — is solved for the largest chunk fitting both the time budget and the token ceiling. The transfer is direct and cheap: on this target the user-visible quantity was never tokens — it is the **worst-case pause before the next token**, i.e. time. The local form: fit the two-parameter cost model at model load (a handful of timed chunks at two prefix lengths — #51's records are its home), then size each chunk to a stated inter-token latency budget, chunks shrinking as the resident prefix grows. This subsumes the knee method of the v3 fuse note (the budget becomes a latency promise; the token count becomes an output) without changing this entry's rank or its queue-empty caveat. Evidence note: DeepInfer's chunk-solving is described for its production system in the deployment Q&A; the shipped engine's visible half is the batched-token cap — the budgeting *rule* is adopted, its production magnitudes are not claimed.

### #54 — Per-head cache policy: retrieval heads keep full KV, streaming heads keep sinks + recent window
- **Rank movement (v5):** new in v5 — enters at rank 23, directly after #18 (the step-loop politeness it composes with at prefill) and before #20 (the cheaper precision steals it out-gains). Ranked below #19/#16 deliberately: its mechanism is paper-proven, but no locally derived mask has yet passed its gate (Q29), and an unproven mask is a silent-quality risk of exactly the class #34 exists to catch.
- **Source:** `papers/duoattention.md` §§3–6 (DuoAttention, Xiao et al., ICLR 2025, arXiv:2410.10819).
- **Mechanism:** Heads are not uniform, so their caches should not be. A minority of heads retrieve from distant context; the majority attend almost only to sinks + recent window. DuoAttention classifies each KV head **once, per model, offline**: a trainable scalar gate per KV head blends full attention against streaming (sinks + recent) attention, trained by L2 distillation against the model's *own* full-attention outputs on synthetic passkey data (loss on answer tokens only) under an L1 sparsity penalty, base weights frozen throughout — a head whose gate stays high under sparsity pressure *is*, by definition, a retrieval head. Binarised at a target ratio, the artefact is a **binary mask over (layer, KV-head) plus two integers** (sink count, window size). At serve time the layer holds two caches: retrieval heads grow without bound; streaming heads hold a **constant** sinks + recent cache (deployment: 64 sinks / 256 recent for long context, as-reported; the paper's own ablation plateaus at 16/64 on Mistral-7B) — O(1) memory in context length, and streaming-head prefill prunes per chunk, so prefill cost falls too. Reported operating ratios: 25% retrieval heads (Llama-2-7B, MHA), 50% (Llama-3-8B, GQA).
- **Expected gain:** Paper-measured on a single A100 (BF16, FlashInfer kernels): memory reduction up to **2.55× (MHA) / 1.67× (GQA)**, decode speedup up to 2.18× / 1.50×, prefill up to 1.73× / 1.63×, with NIAH comparable to full attention up to 1,048K at those ratios where uniform compressors at the same budget fail (all as-reported; the abstract/body maxima differ slightly by operating point, recorded in the dossier, savings scaling ~linearly as the retrieval ratio is lowered). **Local arithmetic (the dossier's §6b, labelled arithmetic, not a measurement):** at the GQA 50% point against #3's worked case (614 MiB KV budget, f16 `kv_rate` 131,072 B/token), retrieval heads cost 65,536 B/token and the streaming half costs a fixed ~20 MiB — **≈9,500 tokens at full f16 precision** vs 4,912 unmodified, i.e. past the 8K minimum *without* spending the q8_0 step; composed with q8_0, ≈**17,900 tokens**. The local win is **fit, not speed**: at ~9.5K tokens the cache is still a minority of per-token traffic beside 4.9 GiB of weights, so the A100 decode figures are not inherited.
- **Cost/risk:** The serving change is a cache-policy change (two cache shapes per layer, a per-head cache-length table — the paper's head reorder is an optimisation, not a semantic requirement) over machinery the runner already has (StreamingLLM's mask is #9's incumbent policy, here applied per head instead of uniformly). The real cost is the **mask**: derived with a full PyTorch/FlashInfer stack over 2,000 steps at lengths up to each model's maximum, and a mask derived differently (shorter calibration, different sink/window during optimisation, a quantised reference) is a *different* mask — and a wrong mask fails silently, the model still talking while it can no longer find things. Hence the gate, which is part of this entry, not a caveat under it: **no mask ships beside a model until (i) raw-oracle mask agreement — local gate values / final masks graded against the paper's published masks where they exist (Llama-2-7B, Llama-3-8B, Mistral-7B are the checkable set), rank agreement reported per layer — and (ii) per-policy needle sweeps (RULER-shaped, depth × length, against the unmodified model; any collapsed depth band invalidates the mask, not the benchmark), plus a long-document QA spot-check against passkey-only overfitting (Q29).** For masks the *authors* publish, honouring the shipped artefact is detect-and-honour work, graded once per family the same way. The classification is per-model-fixed and input-independent — it cannot adapt to a conversation that pivots (SnapKV's per-prompt axis, #22, is its mirror image; the two compose in principle inside retrieval heads, untested in either paper, recorded as synthesis).
- **Evidence: A** for the mechanism and its A100 measurements; **C** for the local fit arithmetic and for any locally derived mask, until Q29 lands.
- **Home:** KV/memory — the head-granularity member of the capacity family: #16 prices layers, #19/#20 price bytes per token, this entry prices tokens per head. Its capacity vector is (layer, head-class) per #16's v5 note.

### #20 — Precision follows importance: sink/head FP16, 1% outlier sparing
- **Rank movement (v2):** rank 22 — ↓ from #20 in v1.
- **Source:** `papers/kvquant.md`; `runners/mlx.md` S-10 ("quantize the cache late, and the sink never").
- **Mechanism:** Two cheap steals from the KVQuant stack without the stack: (i) keep token 0 — in chat terms, protect the head of the system/character prompt — in FP16 and out of calibration statistics, because the attention sink is disproportionately quantisation-sensitive; (ii) at 3–4 bits, hold out a tiny sparse fraction (~1% of elements) in full precision — reported to buy more quality than an extra uniform bit. The outlier geometry both steals exploit is the same phenomenon the quantisation canon measures from the weight side — persistent per-channel activation outliers (AWQ, SmoothQuant) — and the corpus now names three structural answers to it: *rescale* the channels (SmoothQuant/AWQ), *mix* them away (QuIP#'s incoherence processing), or *choose the quantisation axis* so the outliers harm only themselves (KIVI, and this entry's companions in #19). A designer who holds all three can pick per artifact instead of by habit. Generalised by the MLX pattern: early tokens stay full-precision and the cache converts to quantised form only past a token threshold, with group size recorded as part of the cache's identity.
- **Expected gain:** KVQuant's headline quality chain (paper-measured, WikiText-2/C4, LLaMA/Llama-2/Llama-3/Mistral): 4-bit <0.02 perplexity degradation at 3.7× cache saving; 3-bit-1% <0.1 at 4.8×; 2-bit-1% <0.5 at 6.9× — with the paper's own correction that retrieval degrades far more than perplexity suggests (RULER average 56.40 FP16 → 53.65 at 3-bit-1%, but 36.54 at 2-bit-1%). The honest operating point this evidence supports: **3-bit-class is the near-lossless floor; 2-bit is a capacity mode with named costs.** A persona fact stated once, early, is exactly a passkey — test for precisely that failure (#34).
- **Cost/risk:** The full KVQuant stack (non-uniform datatypes, pre-RoPE key caching, calibration artefacts per model) is rejected as a default — see Rejected §R6. These two steals are the parts that cost almost nothing. Pre-RoPE caching, if ever wanted, is a day-one format decision, not a retrofit.
- **Evidence: A** for the measured chain; the chat mapping of the sink rule is the dossier's stated inference.
- **Home:** KV/memory — companions to #19; the sink half can ship with #3.

### #21 — Per-layer pyramidal budgets over scored selection
- **Rank movement (v2):** rank 23 — ↓ from #21 in v1.
- **Source:** `papers/pyramidkv.md`; `papers/snapkv.md` (the scoring it allocates).
- **Mechanism:** Uniform per-layer cache budgets waste the resource being saved: lower layers attend broadly, upper layers collapse onto a few tokens ("pyramidal information funneling"). Keep the total budget identical but distribute it as a pyramid — bottom layer at 2·k_total/m, top set by a shape parameter (paper's β = 20), arithmetic sequence between — with token selection inside each layer by SnapKV-style voting. In a paged allocator this is a per-layer block quota, not a global one: the cache manager must support a capacity *vector* from the start, even if the first policy shipped is uniform.
- **Expected gain:** Paper-measured (LongBench, 17 datasets): at comfortable budgets the win is within noise (LLaMA-3-8B average 41.49 PyramidKV vs 41.35 SnapKV at avg 2048/layer) — and at starved budgets, exactly where a 6 GB card lives, it is not: at avg 64/layer, **34.76 vs 33.05 (SnapKV), 33.89 (H2O), 30.43 (StreamingLLM)**, full cache 41.46, with TREC at 58.00 vs 38.50 for SnapKV. Do not import β = 20 blindly: it was set once, for three models, on LongBench — sweep steepness per model family on a recall-sensitive chat test first.
- **Cost/risk:** Inherits SnapKV's one-shot irreversibility; the funnel is demonstrated on LLaMA-family multi-document QA and untested on hybrids/MLA/heavily-GQA'd small models. No systems evaluation in the paper — per-layer capacities complicate tiling, unmeasured.
- **Evidence: A** for the allocation effect at equal total budget (a clean experimental design worth copying); **C** for any specific steepness on our models.
- **Home:** KV/memory — an allocation layer over #22's scoring; cheap once per-layer budgets exist.

### #22 — Per-turn re-snap: SnapKV voting as history compaction
- **Rank movement (v2):** rank 24 — ↓ from #22 in v1.
- **Source:** `papers/snapkv.md` §7a (the adaptation is explicitly the dossier's, not the paper's).
- **Mechanism:** SnapKV proper is one-shot: at end of prefill, the last window of the prompt (the observation window) votes by attention over the prefix; keep the pooled top-k per head plus the whole window, discard the rest before generation. The chat adaptation: re-vote *per turn* over the accumulated history, using the latest user message as the observation window, with the persona/system block pinned outside the vote — SnapKV as a between-turns compaction step inside #9's composition, not a one-time gate at prefill.
- **Expected gain:** In the paper's home ground (long static prompt, single question): a ~13K-token prompt served from a 1–2K cache at small quality delta on most LongBench tasks (Mistral-7B HotpotQA 42.77 full → 40.94 at 1024, 42.32 at 4096), decode latency flat as input grows (~3.6× generation speedup and 8.2× memory efficiency vs its HuggingFace baseline at 16K input, batch 2, A100-80GB). Summarisation of long single documents is the weak spot (GovReport 27.97 → 19.79 at 1024). None of these numbers describes multi-turn chat.
- **Cost/risk:** The vote needs the observation window's attention over the prefix — the same fused-kernel exposure problem as #9. A frozen snap judges the whole future conversation by the opening exchange; the per-turn form mitigates but is untested. Selection is instruction-sensitive by design: a prompt tail that does not express the eventual task votes for the wrong prefix.
- **Evidence: A** for SnapKV as published (NeurIPS '24); **C** for the per-turn chat adaptation — flagged as ours in the source dossier and here.
- **Home:** accuracy — a compaction policy inside #9, gated by #34 on chat-shaped recall tests before it touches a live session.

### #23 — Hybrid models: per-component budgets + bounded bit-exact snapshots
- **Rank movement (v2):** rank 25 — ↓ from #23 in v1.
- **Source:** `aesir/aesir-ideas-for-ollama.md` §3.2 (Q35-5, banked `88c71564`); `memory/kv-cache-design.md` §6; `runners/sglang.md` §5.4–§5.5 (unified tree, voting resume).
- **Mechanism:** A hybrid's inter-token memory is two things: paged KV for its attention layers, and a fixed-size recurrent (SSM/conv) state that summarises the whole prefix and cannot be prefix-reused token-wise. Budget the components separately (state bytes and snapshot counts are first-class lines, or the fit-checker lies), and make prefix reuse work by *snapshotting* the whole state at stable boundaries (end of system prompt, character card, long lore), keyed by the exact token prefix, restored bit-exact or not at all. SGLang's generalisation — one tree, a slot per component, resume from the deepest boundary every component accepts — is the policy shape to grow into.
- **Expected gain:** Our own records: snapshot restores bit-exact (state/conv/KV diffs 0.0); a stateless resend reused **72 of 90 tokens** via snapshots after residency was destroyed. Cost per snapshot for the 27B-class hybrid: ~158.9 MB SSM+conv, plus boundary KV — which is why the store is bounded (4 per session in Aesir) with a named eviction rule (keep longest prefix + most recent).
- **Cost/risk:** Snapshot placement is a policy problem, not a mechanism problem: snapshotting every token costs more than it saves. Branch costs measured on dense models must never be promised for hybrids. Applies only when hybrid GGUFs are in scope — but the budget-line discipline (#12) should land before the first hybrid arrives, not after.
- **Evidence: A** — our own campaign records with gate numbers; SGLang's productised form is project-reported (B for that part).
- **Home:** KV/memory — a branch of #5/#10 for hybrid sessions; declare `trimmable` / `prefix-rollback-able` / `quantizable-after-N` per model at load (MLX S-7) so speculation and reuse enable only where the declaration supports them.

- **V6 note — checkpoint placement is turn-shaped (2026-11-15):** the hybrid half of #5's v6 publication policy lands here: TokenSpeed's junction cut and in-forward checkpoint (`runners/tokenspeed.md` §4.4) and V3's checkpoint discipline (`runners/exllamav3-session-pass.md` Q6 — checkpoints stashed under the boundary page's hash at page-aligned intervals, stranded checkpoints pruned first, a private rolling checkpoint committed under the final page's hash at job end) agree on the rule this entry now carries: **snapshots are placed where a future re-render can resume from them, not where the current job happened to stop** — for chat, the end of the re-rendered history is the resume boundary that matters, and checkpoints no re-render can reach are dead weight in a bounded store (this entry's per-session bound makes the waste concrete). V3's spacing asymmetry (coarse during ingestion, fine near the prompt's end) is adopted as the local starting shape.

### #43 — Tier-boundary transit codec: compression to move, not to keep
- **Rank movement (v3):** new in v3 — enters at rank 26.
- **Source:** `papers/cachegen.md` §§3–6; `papers/mooncake.md` §§2–3, 5 (the pool it serves); `papers/infinigen.md` §6a (the implementability comparison).
- **Mechanism:** At each KV tier boundary (VRAM→RAM, RAM→SSD, and back), encode the cache *for the trip*: delta-against-anchor within 10-token groups (anchor at 8-bit), three-band layer-wise quantisation (error growing from early to late layers, because early-layer error propagates), and arithmetic coding with per-(layer, channel) distributions — decoded back into ordinary tensors on arrival. One fixed, well-chosen level per tier pair locally (the paper's bandwidth-adaptive streamer matters less on a local bus with stable, known bandwidth); the fetch-vs-recompute escape hatch is kept — for a short chunk, re-prefilling from stored text can beat decoding + transferring a cold cache, priced per chunk by the tier manager. This is **compression to move**: Wave 3's schemes (#19/#20) decide the bytes' shape *at rest* (capacity); this codec decides their shape *on the wire* (transfer time) — the paper states the two compose multiplicatively, they do not compete.
- **Expected gain:** As-reported on the paper's testbed (4× A40, vLLM; Mistral-7B / Llama-34B / Llama-70B, 662 contexts of 1.4K–16K tokens, headline TTFT at 3 Gbps): **3.5–4.3× smaller than the uniform-quantisation baseline** at ≤2% accuracy cost (<0.1 F1, <0.1 perplexity vs the quantisation baseline at matched settings), **1.67–1.81× beyond 8-bit quantisation alone**, TTFT 3.2–3.7× faster than the quantisation baseline. Locally the win is proportional to how much cache actually crosses a tier boundary: long contexts, multiple resident sessions, SSD-backed cold caches — exactly #10/#11's regime. For a single short chat that never leaves VRAM it buys nothing and the encode cost is pure tax; the entry says so.
- **Cost/risk:** Offline/batch tensor code plus an entropy coder at the demote/promote seam — no attention changes, no weight surgery (the dossier's labelled judgement: of the two Wave 15 movement papers, this is the realistic one for a ggml-class backend; InfiniGen's machinery is R19). The correctness risk is silent divergence if the codec ever touches session state: fenced by R20 — snapshots stay bit-exact; the codec's lawful home is the pool layer and labelled derived artefacts. No formal error bound exists in the paper; its quality claims are per-workload measurements, graded per model through #34 before a level is labelled for a tier pair (Q22).
- **Evidence: A** for the mechanism and its measured ratios on the stated testbed; **C** for the size of the win on purplelongship's PCIe/NVMe tiers.
- **Home:** KV/memory — the transform inside #10/#11's tiering; presupposes #4's blocks and #5's prefix keys.

### #24 — Cache-aware ordering of pending generations
- **Rank movement (v2):** rank 26 — ↓ from #24 in v1.
- **Source:** `runners/sglang.md` §9.2; `papers/radixattention-sglang.md` (cache-aware scheduling, 96% of optimal hit rate as reported).
- **Mechanism:** Whenever more than one generation is pending, sort by matched prefix length descending, arrival order as tie-break: the reply (longest resident prefix) runs first and extends the tree; sidecars (summary update, memory extraction, second candidate) run against the warmed tree; all swipes of one turn run consecutively before another character's turn interleaves and thrashes a pool that holds roughly one long conversation. Engage only when queue depth exceeds one; FCFS remains the fallback default.
- **Expected gain:** Modest in steady state (a lone user rarely queues), large at the burst moments that dominate perceived quality — multi-candidate turns, app-generated sidecars, rapid chat-switching. Costs no memory and no model quality; it purely avoids evicting a prefix milliseconds before its next use.
- **Cost/risk:** Small: a matched-length tree walk per pending request (already performed at admission) plus a sort. Starvation is the fleet failure mode in miniature — hence the tie-break and a cap on how long a user-visible request may be overtaken; a cancelled high-hit request must release its pins promptly.
- **Evidence: B** — SGLang's policies and hit-rate behaviour are project/paper-reported for fleets; the single-user burst translation is the dossier's reasoning.
- **Home:** speed — a scheduler policy slice once #5 exists to be ordered against.

- **V5 note — a second ordering key: demotion by attained service (2026-11-15):** `papers/fastserve.md` §§3, 5–6 and `papers/burstgpt.md` §§4–6 (wave 28) supply the case this entry's prefix-length key cannot price. Prefix length orders work by *cache value*; it says nothing about *fairness between live generations*, because the contended resource in a multi-persona burst is decode steps, not cache hits: a persona mid-way through a 2,000-token generation holds its step-share under FCFS while a 30-token interactive turn waits behind it. FastServe's skip-join MLFQ is the fleet answer — priority **demoted by attained service** (each quantum consumed without finishing sinks the job; short jobs finish in the high queues), arrivals **skip-joined** at the priority their *known* cost earns (prefill priced from input length, the half of job size that is known at arrival), and a **starvation guard** (periodic promotion; 300 ms default in the paper, locally a human-scale bound) without which demotion is merely a different unfairness. The local adoption is the discipline, miniaturised: when pending generations contend, order by prefix value **and** decay by attained service within the contention episode, with the starvation cap this entry already carries now named as the same mechanism as FastServe's promotion. Two fences, both from the dossiers: FastServe's multipliers are throughput-at-SLO under Poisson load on A100 clusters and transfer not at all (and BurstGPT prices the Poisson assumption itself — §6a of its dossier); and its **proactive KV swapping is not imported** — its own peak-KV measurement is 7× FCFS's, and on this card KV pressure is answered by #31's shedding, not by a swap tier kept for scheduling elegance. What shipped in practice also argues the ranking: chunked prefill (#18) won the fleet; MLFQ survives as instincts inside other schedulers — which is exactly the form this note adopts it in.

### #52 — Placement decisions as a scorer pipeline (the EPP pattern, miniaturised)
- **Rank movement (v4):** new in v4 — enters at rank 29, directly after #24 (the single-queue ordering it generalises).
- **Source:** `runners/llm-d.md` §§3, 8.1; `runners/nvidia-dynamo.md` §8.1 (the same shape priced against load, fleet side).
- **Mechanism:** Every placement decision the runner makes — which session runs next, which prefix stays resident, which tier a block demotes to, which model a request lands on when more than one is resident — is made by **one pipeline shape: producers → filter → score → pick.** Producers emit candidate facts (prefix-overlap length per #5's indexer, current load, residency state, latency sensitivity declared at admission); filters remove ineligible candidates (cannot fit, wrong model, pinned elsewhere); scorers attach inspectable numeric scores (overlap priced against load — Dynamo's KV-aware routing is this trade at fleet scale); the picker takes the best score and **the decision record keeps the scores**. No placement logic lives as ad-hoc conditionals scattered through the scheduler: a decision that cannot show its scores cannot be debugged, tuned, or honestly reported (#6).
- **Expected gain:** No tok/s claim. The gain is that #24's ordering, #31's admission and #5's retention stop being three separate policies that can silently disagree, and become one auditable decision surface whose weights are tunable per workload (#44's rule: the optimum is a (model, workload) pair — the scorer weights are where that truth lives). llm-d's contribution is the *shape*, proven as a production router architecture; its Kubernetes machinery, its multi-pod scorers and its autoscaling signals do not transfer and are not imported.
- **Cost/risk:** A design discipline, priced as one scheduler refactor plus a decision log. The risk is ceremony: at one process and one GPU the pipeline must stay a function call, not a service — the Dynamo dossier's four-condition line (§8.5, carried in #31's v4 note) is the fence.
- **Evidence: B** for the pattern as production architecture (project-documented); **C** for its miniaturised form, which is the dossier's labelled steal (§8.1) and this ledger's adoption of it.
- **Home:** speed — the decision layer above #24/#31; its index is #5's, its budget is #31's.

### #59 — Single-flight shared prefill: join the computation already running
- Rank movement (v6): new in v6 — enters at rank 31, directly after #52 (the decision pipeline that must know a prefill is in flight) and before #25.
- Source: `runners/magnitude.md` §§4, 10.5 (release 0.2.16, primary release notes).
- Mechanism: prefix identity is computed at admission (token-level, post-template — #5/#13's identity). If another in-flight request is already prefilling a prefix this request matches, the new request waits and reuses that computation instead of starting a duplicate prefill of the same tokens; the shared prefix remains cached after the batch that computed it finishes. Cancellation semantics are part of the entry: if the computing request is cancelled mid-prefill, joined requests fall back to computing the remainder themselves — a join is an optimisation, never a dependency that can strand a queue.
- Expected gain: the burst shape Q30 names — parallel subagents/sidecars of one parent sharing one large system prompt — stops paying the shared prefill N times, in latency and in duplicated KV. The vendor figures are the pathological best case (8 concurrent requests sharing a 15K prompt: 226 s → 3.5 s each on an NVIDIA A10G, with draft model, as-reported in release notes; post-batch repetition 12 s → 0.7 s at 4 concurrent on 13.6K) and are not a local expectation; the mechanism's value does not depend on the multiple.
- Cost/risk: in-flight prefill becomes a shareable, reference-counted object in the scheduler (it joins #58's ownership states: in-flight is a state with joiners); prompt identity must be exact, or joins are wrong-result bugs. Scheduler work only; no kernel work.
- Evidence: B — primary release notes with hardware and workload stated; C for local magnitude.
- Home: speed — the in-flight complement to #5 (finished prefixes) and #24 (ordering of pending work).

### #25 — Get CPU work off the decode path; profile the gap, not the average
- **Rank movement (v2):** rank 27 — ↓ from #25 in v1.
- **Source:** `runners/sglang.md` §9.3; `memory/memory-wall-and-roofline.md` §4.3.
- **Mechanism:** Enumerate every piece of CPU work between two GPU steps — sampling bookkeeping, stop checks, detokenisation and streaming, grammar-mask preparation, KV bookkeeping, next-turn lore lookups — and get all of it off that path: run it concurrently with the in-flight forward pass (Go goroutines are a better tool for this than the Python machinery it replaces), precompute it before the loop (templates rendered, prompts tokenised while the user is still typing — idle human time is the cheapest overlap window a single-user system has), or make it cheaper. Acceptance test, copied from SGLang's method: timestamp the gaps between forward passes in a long generation; if bookkeeping gaps exceed a small fraction of step time, the loop — not the kernel — is the next target.
- **Expected gain:** At batch 1 with small-to-mid models, inter-token latency is GPU step time plus every CPU cost in the loop; shaving the CPU term is worth proportionally more the smaller the model (the same reason SGLang's overlap gain was largest on its smallest benchmark model). No number is asserted for our stack — the entry *is* the measurement discipline that produces one.
- **Cost/risk:** Pipelining hazards: a stop condition discovered in post-processing must reliably abort a prepared-but-not-yet-run step; speculative preparation must never mutate shared cache state before its step is confirmed. Goroutine-per-stage applied dogmatically to a millisecond loop can add channel hand-off latency — measure the gap, then hide what the measurement indicts; do not overlap everything.
- **Evidence: B/C** — SGLang's zero-overhead claim is project-verified by GPU trace on its stack; the Go translation is reasoned.
- **Home:** speed — a profiling-first slice; also the natural home of Aesir's dequant-placement rule (dequantise outside the per-token loop, at most once per layer per forward pass — the QS-0 cautionary tale, whose ~35× prompt-path figure is carried as briefed-but-unverified, see Open Questions).

### #26 — Small same-family draft model, only where headroom survives #3

### #38 — Request-level expert caching for MoE models (the MoE-Infinity pattern)
- **Rank movement (v2):** new in v2 — enters at rank 31.
- **Source:** `papers/moe-infinity.md` §§4–7; `papers/mixtral.md` §5, §7a; `runners/llamacpp-ggml.md` §5.2 (the incumbent `--cpu-moe` / `--moe-cache-mib` knobs this upgrades).
- **Mechanism:** Three tiers, ascending ambition, all Go-feasible over existing placement machinery. (1) *Static hot-set:* pin the globally hottest experts in VRAM at load, from a routing-counter profile — #29's sidecar idea at expert granularity, and the floor, worth having because it is free. (2) *Request-level tracing + frequency eviction:* count routing decisions per request/session, evict by *this* request's frequency rather than global LRU, decay counts at turn boundaries but never flush between turns of one conversation, and prefetch the next layer's predicted experts while the current layer computes. (3) *Full EAMC matching across requests:* deferred until a measured miss-rate gap justifies it (Open Questions). The expert cache is a first-class arena beside the KV arena, budgeted from one pool with the split logged (#31's vocabulary; `memory/gpu-memory-internals.md` §7.1), and **expert-cache hit rate is exposed as a first-class metric** — it predicts MoE decode speed on small cards better than any FLOP figure. Session restore (#10) pre-warms the expert working set from the session's persisted activation trace during the KV restore transfer.
- **Expected gain:** This is the only path by which a 47B-class MoE runs on the target at all: residency follows the *total* count (Mixtral Q4_K_M ≈26–29 GB — inside the fleet host's 39 GB RAM, never inside 6 GB of VRAM at any quant), compute follows the *active* count (~12.9B parameters). On the card, ≈3–4 GB of expert cache (after shared weights, KV and buffers, and the §7.3-class reserve) holds ≈30–40 of Mixtral's 256 experts (~100 MB each at Q4) — 12–15% of the pool against a measured per-request working set of ~25% (≈64 experts), with reuse skewed inside the set and consecutive-token expert repetition at ≈62–67% at middle layers (either slot, Mixtral §5). The miss price list, in corpus PCIe arithmetic: ≈8 ms per expert at Gen3 ×16 (≈4 ms at Gen4); at a 90% hit rate ≈50 ms/token of bus time (≈20 tok/s ceiling from misses alone, partly overlappable with compute), at 75% ≈130 ms (≈7–8 tok/s). Paper context, honestly bounded: MoE-Infinity's headline 3.1–16.7× belongs to many-expert models on an A5000 with a 24 GB buffer; for coarse Mixtral-class models the measured gain over the strongest offloading baselines is **1.4×** — the policy transfers, the latencies do not. The mechanism is *lossless*: a miss costs time, never correctness — the safest failure shape a serving optimisation can have.
- **Cost/risk:** Prefill gains little (a long prompt's tokens scatter across most experts); cold start pays a working-set warm-up (the paper's serving setting needs ≈30–50 requests to recover after a distribution shift; a single conversation is one "request" in the paper's sense and warms within its first tokens). The hit-rate split at a 30–40-expert cache is unmeasured anywhere — the dossier marks its own fraction as speculation (Open Questions). Computing cold experts in place on the CPU (`--cpu-moe` pattern) is a legitimate A/B alternative tier for the cold tail, not a default.
- **Evidence: A/C** — mechanism and routing locality are paper-measured (A); the small-cache fractions and the chat-session transfer are the dossiers' labelled speculation (C).
- **Home:** KV/memory — the MoE sibling of #29; sequenced after #4 (it needs the arena discipline), arbitrated against KV by #31's budget vocabulary.

### #29 — Tiered weight residency: hot-first placement policy
- **Rank movement (v2):** rank 32 — ↓ from #29 in v1.
- **Source:** `runners/powerinfer.md` §8.1–§8.2.
- **Mechanism:** When a model does not fit, stop splitting *between* layers (llama.cpp `-ngl` style: some layers wholly resident, the rest wholly on CPU) and split *within* the FFN instead: fill VRAM by activation-frequency impact-per-byte — hot neuron blocks of every layer on the GPU, cold blocks computed on CPU in place — subject to a minimum-chunk rule so merge/sync cost does not eat the win. Attention and norms stay wholly on GPU (small, dense, latency-critical). The placement is computed at load from a per-model activation-frequency profile shipped as sidecar metadata, falling back to layer offload when no profile exists; hot sets are measured to be stable across tasks, so stale-profile risk is low.
- **Expected gain:** In PowerInfer's ablation, policy-over-random placement was worth ~1.5× on Falcon-40B on top of an already-hybrid engine. The dossier's speculation for 6 GB — labelled as such — is that the practical effect shows up less as peak tok/s and more as *the size of model that stays interactive* (a 13B INT4 behaving like a resident model instead of a swapped one). The full-system ceilings (up to 11.69× FP16, up to 8× INT4 on an 11 GB card) are ReLU-family numbers and must never be quoted for SwiGLU models; the SwiGLU control outcome is ~1.5× (see #30, Rejected §R1/§R9).
- **Cost/risk:** The placement policy itself is low-risk (a load-time greedy/knapsack pass, a few hundred lines). The within-FFN split is not: it needs neuron-granular kernels on both sides and a split-merge per layer per token, with a per-layer synchronisation tax that is unforgiving on slow PCIe. Prototype on one model before generalising. Profile data must be produced per model once.
- **Evidence: B/C** — SOSP '24 paper measurements for the mechanism family; the simplified-policy translation and the 6 GB expectation are the dossier's speculation.
- **V4 note (2026-11-15):** #53 (new in v4) is this entry's generalisation: FlexGen searches placement fractions over **three** tensor kinds (weights, KV, activations), where this entry searches the weight kind by activation frequency. The two compose — #53's solver is the frame, this entry's hot-first policy is the weight-kind objective inside it — and a build that ships the frame without this policy has searched fractions with nothing to optimise.
- **Home:** KV/memory (residency policy) — relevant only for models that do not fit; irrelevant, correctly, for the resident 7–8B case #3 serves. For MoE models the sibling policy is #38 (the same placement logic at expert granularity — its tier 1 *is* this entry's hot-set idea with routing counters instead of neuron profiles); the two compose and compete for the same host resources, and a build that ships both must arbitrate them as one residency policy.

### #53 — Placement-as-optimisation over three tensor kinds (FlexGen's fraction search)
- **Rank movement (v4):** new in v4 — enters at rank 36, directly after #29 (the weight-kind policy it generalises).
- **Source:** `papers/flexgen.md` §§3, 5–6.
- **Mechanism:** When a model does not fit, placement is **solved, not set**: search the fractions of **three tensor kinds — weights, KV, activations —** assigned to each tier (VRAM / RAM / disk), independently, against **measured** tier bandwidths and capacities (the LP's inputs are four bandwidths and three capacities, all measurable on the actual machine in minutes), with computation delegated to where data sits where the arithmetic favours it (FlexGen's s× attention argument: at long context with CPU-resident KV, computing attention where the cache lives can beat shipping the cache). A single "offload amount" knob conflates three decisions with different size curves — weights fixed, KV growing with context × batch, activations with batch — and this entry forbids the conflation inside the runner even where the UI keeps a simple face. Even a greedy/knapsack solver over per-layer fractions, driven by measured bandwidths, satisfies the entry; the LP itself is not required.
- **Expected gain:** The evidence that the policy layer is where the performance lives is the paper's own ablation, as-reported: the same runtime with a hand-inherited DeepSpeed policy scored **0.01 vs 0.69 tok/s** (OPT-175B, FlexGen's throughput regime) — un-searched placement cost ~69× *inside the regime where placement dominates*. No part of that magnitude is a local expectation: FlexGen's regime is throughput at effective batch in the hundreds, its numbers do not transfer to batch-1 chat at all, and its honest local use for a far-too-big model is an explicitly-labelled **batch mode** (overnight summarisation, bulk extraction, evaluation sweeps), priced per use case and never blended into one tok/s figure with interactive serving. What transfers unconditionally is the method: measure the tiers, then solve.
- **Cost/risk:** A load-time solver pass plus the tier measurements (#51's records supply them). The disk tier as a *live* tier for interactive decode is explicitly out: a model that needs live disk reads per token is a batch-mode model, and the runner says so rather than streaming it hopefully. FlexGen's 4-bit transport format is likewise not imported — the fleet's GGUF formats are compute-side formats with their own dossiers (#42).
- **Evidence: A** for the placement-search mechanism and its ablation on the stated testbed; **C** for the local solver's gains, unmeasured until a too-big model is actually placed by it.
- **Home:** KV/memory — the frame around #29 (weights), #38 (experts) and #10/#11 (KV tiers); arbitrated by #31, priced by #51's records.

### #30 — Gate-first threshold sparsity for SwiGLU models (CATS)
- **Rank movement (v2):** rank 33 — ↓ from #30 in v1.
- **Source:** `runners/powerinfer.md` §8.3 (§2.6 follow-up line).
- **Mechanism:** For SwiGLU models there are no exact zeros to exploit — but the gate projection must be computed anyway, so use it as its own predictor: calibrate a per-layer magnitude threshold offline, zero sub-threshold gate outputs, and skip the matching up/down work. No predictor weights, no training pipeline, no extra parameters. Combined with #29, the skip also halves cold-side traffic, because skipped cold neurons are precisely the ones that would have consumed host bandwidth.
- **Expected gain:** CATS reports ~50% MLP sparsity at ~1.5% quality cost with no fine-tuning, ~40% MLP-layer efficiency and ~15% end-to-end latency improvement with custom kernels in their (in-VRAM) setup. The dossier's speculation — labelled — is that the end-to-end effect should be larger in an offload setting, for the traffic reason above. Keep two execution modes and switch by phase: dense for prefill and any batched work, sparse for batch-1 decode, with a runtime fallback to dense if observed sparsity drops below threshold (PowerInfer-2's dynamic-ratio idea in policy form).
- **Cost/risk:** Threshold choice is a per-model, per-layer quality/speed dial and must be validated per model release (#34), with a conservative default. Custom-kernel work is the real cost; without kernels there is no win to collect.
- **Evidence: A/B** — CATS figures are the project's reported results as read in the dossier (paper + project summary); the offload amplification is speculation.
- **V4 refinement — match the sparsity grain to the accelerator's grain (2026-11-15):** `papers/powerinfer-2.md` §§3, 5–6 supplies this entry's missing design variable. PowerInfer-2's core move is the **neuron cluster**: hot neurons re-grained into dense blocks sized by both activation statistics and the target compute unit, because a single neuron is a sparse object an NPU cannot execute and a whole matrix is an I/O object flash cannot feed — **the sparsity grain is matched to the accelerator's grain**, and a scheme designed at the wrong grain is not a slower version of the right scheme; on the NPU it is a non-scheme (the paper's sparse-on-NPU primitives lose to the CPU outright). This entry already carried PowerInfer-2's dynamic-ratio idea in policy form (dense for prefill/batched work, sparse for batch-1 decode); the grain law is the same paper's other half, and it binds locally as a *choice rule*: the unit of skipping (neuron, block, cluster, expert) is chosen by what the target executes natively, per phase — and **batch size is a sparsity variable** (the paper's hot set densifies toward ~75% by batch 32, as-reported), so any threshold calibrated at batch 1 is silently a batch-1 policy and must be labelled one where verification spans or parallel sampling batch the decode. The local grain per accelerator is unmeasured — Q28. This is a refinement, not a new entry: the dossier itself records the grain principle as a candidate principle for future accelerator work rather than a runner feature, and #30 is its runner-side home.
- **Home:** speed — pairs with #29; pointless without the split it accelerates, which is why it ranks below it.

### #31 — One residency arbiter + ordered pressure shedding
- **Rank movement (v2):** rank 34 — ↓ from #31 in v1.
- **Source:** `runners/mlx.md` S-1, S-4, S-11 (UMA evidence, translated).
- **Mechanism:** Route weights, per-session KV and the prefix cache through one arbiter that knows the pool budget as four separate numbers (system cap, residency request, allocation budget, reusable-buffer cap) instead of one "memory used" figure. Admission may shrink the prefix cache, never the reverse by accident. On OS memory-pressure signals, shed in a fixed order: reusable buffer caches and shallow prefix snapshots at warning; the prefix cache at critical; never weights or active generations.
- **Expected gain:** The failure mode changes from "machine died under combined load" to "request queued / prefix evicted" — in the MLX field reference, warning-level shedding bought back ~1.7 GB on a 27B exactly when it mattered. On purplelongship's discrete 6 GB the arbiter's value is narrower (VRAM admission is #12's job); the transferable half is the four-number budget vocabulary and the shedding order for the host-RAM tiers (#10/#11), where model files, spill and page cache genuinely compete.
- **Cost/risk:** The largest policy-layer item on this list if built whole — deadlock and fairness questions included. Build the vocabulary and the shedding order first; the full arbiter only if measurements show independent allocators actually colliding.
- **Evidence: C** for our target — the evidence base is unified-memory systems; the dossier itself marks the full arbiter as judgement, and this ledger ranks it accordingly (real, late, and scoped).
- **V3 refinement — the admission half: refuse early and cheaply (2026-11-15):** `papers/mooncake.md` §§3, 5 prices the half of this entry v2 left implicit. When predicted load exceeds what can be served within SLO, **reject at admission — before prefill compute is spent** — against a *forecast* rather than instantaneous fullness (Mooncake's naive reject-when-full oscillates: rejection frees load, admission surges, overload returns — as-reported). The posture transfers whole and strengthens as resources shrink; the prediction machinery does not — locally the "forecast" is this entry's budget check (will this fit alongside the resident session, yes/no). The failure vocabulary therefore gains a third honest outcome beside "prefix evicted" and "machine died": **"refused at admission, fast, with the reason stated"** — an honest fast refusal is a feature; a slow collective collapse is the bug. Fleet magnitudes do not transfer (Mooncake's 115%/107% more requests in production and 525% simulated best case are fleet/RDMA/long-context numbers, as-reported) — the mechanism truth transfers, the magnitude truth does not.
- **V4 note — the Dynamo Planner convergence (2026-11-15):** `runners/nvidia-dynamo.md` §8.3 reaches this entry from the fleet side and agrees with it: Dynamo's Planner (GPU-driven, SLA-first autoscaling over profiled engines) has, at one-machine scale, nothing to actuate — no replicas to create, no second worker to route to — and **degenerates honestly to this entry's budget check**: will this fit, at the promised latency, alongside what is resident — yes or no, with the reason stated. The convergence is evidence for the entry's shape, not a new mechanism: two independent lines (MLX's UMA arbiter in v1; NVIDIA's datacentre planner in v4) collapse to the same local object. The dossier's four-condition line (§8.5) is the boundary, adopted here: build the *accounting* (scores, budgets, profiles, validity envelopes) at any scale; build *orchestration machinery* only when there is something to orchestrate — multiple interchangeable workers, variable capacity, state mobile at fabric speeds, and a layer cost small against what it optimises. The personal runner satisfies none of the four.
- **Home:** robustness.

- **V5 note — degradation is decided at fit time, in the open; there is no run-time fallback to improvise (2026-11-15):** `runners/ggml-backend-internals.md` §7 (ggml at v1.0.0) settles the failure contract this entry's arbiter must be designed against. **No automatic CPU fallback exists inside ggml's allocators:** a graph node runs on CPU because the scheduler *assigned* it there before allocation — a planning decision — never because a GPU allocation failed at run time and the node was re-homed. Model loading converts a null buffer into a thrown error and aborts the load (no retry with fewer layers, no partial-load state); the graph allocator's reserve returns false and the context layer throws; inside the CUDA scratch pools, failure after one flush-and-retry is a **checked-fatal** driver error, and the static bump allocator **aborts the process** on overflow. The one designed retry in the whole stack is the shape to copy: if the prompt-processing reserve fails under pipeline parallelism, the context disables pipeline parallelism, rebuilds its scheduler, and retries **once** — a named, logged, single-step degradation. This entry's arbiter therefore gains its degradation clause: **the spill/degradation decision (fewer GPU layers, smaller context, named layers to CPU) is made by the fit loop before load — priced by #56's dry run, disclosed in #51's load record — and is never improvised after a failed reserve.** The improvised form is rejected as R25. Ollama's own layered OOM response (`runners/ollama-internals.md` §4.7 — one automatic context step-down for unpinned contexts only, evict-all-and-retry-once, runtime OOM expiring *all* resident runners) is the incumbent behaviour the fork reforms: keep its lifecycle skeleton (drain-before-evict, recovery waiting), replace its triggers with the fit-time decision above, and note that a *pinned* context disables its step-down entirely — one more reason pinning must be a session property, not an accident of how a value was set.

- **V6 note — the arbiter gains its mechanism (2026-11-15):** this entry's pressure response is now a ranked mechanism, **#57** (suspend-by-image, directly after this entry): the shedding order above decides *what* yields; #57 decides *how* — imaged byte-for-byte, frontier published, restored exactly, aborted visibly if the image cannot be kept. TokenSpeed's victim ranking (no forward in flight; incomplete prefills preferred; a request blocked on its own next page preferred overall) is adopted as this entry's victim rule.

### #57 — Suspend-by-image: the designed pressure tier for live sessions
- Rank movement (v6): new in v6 — enters at rank 41, directly after #31 (the arbiter whose pressure decision it executes).
- Source: `runners/tokenspeed.md` §§3.5, 9.3.
- Mechanism: when the KV pool cannot fund an admission, the arbiter (#31) selects a victim among resident requests with no forward in flight (incomplete prefills preferred; a request blocked on its own next page preferred overall — TokenSpeed's ranking) and images it to pinned host memory byte-for-byte: (1) publish its computed frontier into the prefix index exactly as a finish would, so the suspended session's prefix stays matchable — including by its own next turn; (2) published pages become ordinary host-tier entries, pinned for this request until restore; everything else (unpublished state, recurrent slots, sampler/RNG state, speculative readiness) goes to a request-private snapshot pool — unindexed, unevictable, bounded; (3) freed pages are granted to the specific blocked admission that triggered the suspension, retried in the same scheduling pass. Restore copies the image into fresh pages and resumes at the exact position — mid-prefill chunk or next decode step. If no victim's image fits the pool, the newest resident is aborted visibly (client-facing error), never silently recomputed. The pool is provisioned at fit time as a deliberate fraction of the device pool (TokenSpeed's default 0.1× of device KV capacity for whole images is the starting ratio, locally unmeasured) and is a named line in #12's budget.
- Expected gain: chat-switching and second-session pressure on 6 GB cost a host copy instead of a full re-prefill of tens of thousands of tokens; TokenSpeed §9.3's framing ("the 6 GB pressure valve") is the dossier's own. No local number exists; TokenSpeed's figures are fleet figures.
- Cost/risk: the image must capture everything exact resume needs (KV + sampler/RNG + recurrent + speculative state) and carry #10's validity stamp — an image restored under different weights or template is stale and invalidates, never converts. Atomicity against model/template change mid-suspension. Pool bytes are host RAM held against the spill tiers (#10/#11 share the host budget; the arbiter accounts jointly).
- Evidence: B for the mechanism as a shipped/documented production design (TokenSpeed design documents, project-reported); C for local gain.
- Home: KV/memory — #31's mechanism arm; presupposes #4's blocks, #5's publication, #10's envelope.
- Relation: this is the lawful sibling of R25 — the tier is designed and provisioned before pressure arrives; nothing is improvised after a failed reserve. Distinct from #11 (idle spill: the victim is not under pressure and may be recomputed cheaply) and from #48 (the movability protocol shape, which this entry instantiates for the pressure case).

### #47 — The sort-key / delete-key law for the memory store
- **Rank movement (v3):** new in v3 — enters at rank 36.
- **Source:** `memory/memorybank.md` §§3.3, 5–6; `memory/generative-agents.md` §§5–6; the supersession standard in `memory/agent-memory-architectures.md` §§6.2–6.4 (already carried by #14/#8 in v2).
- **Mechanism:** One sentence, in INGEST-006's words: **Ebbinghaus belongs in the sort key, never in the delete key.** Decay (recency/rehearsal weighting) may *rank* currently-valid episodic records for injection; **existence is decided only by invalidation and witnessed acts** — bi-temporal supersession, user demand, legal erasure, editorial decision — each tombstoned and auditable. The scopes are part of the law: ranking applies to the **valid view only** (records with no closing validity and no tombstone; superseded records are excluded by semantics *before* ranking begins), to the **episodic tier only** (it is **forbidden for semantic facts** — an allergy does not become less true with age — and **never touches the anchor**, which is never scored at all), and rehearsal survives only as a **capped, inspectable ranking boost** (the injected set and its scores are part of the turn's provenance log, per #6). Genuine deletion is a deliberate, tombstoned operation, never a curve crossing a threshold in the night; storage cost is not a counter-argument at personal scale (a lifetime of extracted facts is megabytes).
- **Expected gain:** Not a speed number: the failure mode removed is the *quietly vanished fact* — undiscoverable because nothing is left to inspect. MemoryBank's updater (retention R = e^(−t/S), strength +1 and clock reset on recall, probabilistic forgetting as R falls) is content-blind, rehearses only on recall (topics the user avoids — often the sensitive ones — decay fastest), and actively *strengthens* a stale, often-rehearsed fact while its quiet once-stated correction decays: decay does not merely fail to resolve contradiction, it can entrench the wrong side of one. The field's verdict, as banked: **no modern system surveyed keeps Ebbinghaus-style decay as a memory-management mechanism** — Letta removes only by witnessed edit or sleep-time pass, Mem0's vocabulary is add/update/delete/no-op as model decisions, Graphiti invalidates and never deletes, ChatGPT's management is editorial; what survives is recency as one ranking signal among several. (The ancestor's own evidence caveat travels too: MemoryBank never ablated its forgetting mechanism.)
- **Cost/risk:** The ranking half is a sort key — days. The existence half is already priced in #14's store-side requirement and R17; this entry names it as a law so no future design re-litigates it piecemeal. The rejection form is R21. Decay-as-deletion remains defensible only where a store is explicitly *not* a record (a scratchpad, a simulation's ambience, a cache whose misses cost nothing) — each store's side of that line is decided in writing before its updater is chosen.
- **Evidence: A** for the field audit (banked dossier A5's system-by-system record) and the ancestor mechanism as specified; **C** for the ranking scopes as our design position (labelled judgement in the dossier).

### #55 — Surprise as a write gate for the agent-memory store, with an unconditional floor for witnessed acts
- **Rank movement (v5):** new in v5 — enters at rank 41, directly after #47 (the law it applies) and before #32. Ranked as a policy entry, not a mechanism: the gate is days of work over #14's store; what is expensive is getting its fences right, and the fences are this entry.
- **Source:** `papers/titans.md` §§3, 5–6 (Titans, Behrouz et al., arXiv:2501.00663 — submitted 31 Dec 2024; its results graded author-reported and independently contested in part, per the dossier §4 — which does not touch this entry, since the steal is the write *rule's shape*, not the architecture's benchmark claims).
- **Mechanism:** Titans' long-term memory writes by **surprise**: the gradient of its associative loss *is* the write strength — what memory already predicts writes almost nothing; what violates expectation writes strongly. Translated to the record layer as a **write gate** over the external store (#14's service, beside the runner): an incoming episode that contradicts or extends what the store already holds about the user (a changed preference, a new commitment, a corrected fact) is a high-priority write; an episode that merely repeats the known earns no new record. The gate's two fences are constitutive, and an implementation missing either is not this entry. **(1) The floor is unconditional for witnessed acts:** a fact the user states about themselves, a commitment they make, a correction they issue — these write **regardless of surprise score**. The gate ranks the *ambient* stream (inferred preferences, episode summaries, extraction candidates) where a missed write costs little; it never sits between a witnessed act and the record. **(2) The gate is never a delete rule:** low surprise removes nothing, fades nothing, and demotes nothing out of existence. Once written, a record lives under the ordinary rules — pinned if it is an anchor, superseded only by a witnessed correction, tombstoned on deletion (#47). Titans' own forgetting term (the learned $(1-\alpha_t)$ fade) is explicitly refused at this layer: it is R21's defect with a learned coefficient, and its rejection form here is R26. A third, smaller steal rides along, labelled analogy in the dossier: **momentum as an episode-boundary hint** — significance extends over a neighbourhood, so extraction operates on episodes, not utterances; the correction is often in the sentence after the surprising one.
- **Expected gain:** Not a speed number: the failure mode priced is the *drowned record* — a store that writes everything the stream contains fills with the predictable bulk, and extraction cost, injection contention (#14's budget) and contradiction surface all grow with volume that carried no information. The gate spends the store's write and review budget where prediction error says the information is. The honest cost is also stated in the dossier and carried here: **a surprise gate inherits the model's miscalibrations** — facts stated quietly, in familiar words (a changed medication, a moved house, phrased like small talk) can score low-surprise, which is precisely why the floor in fence (1) is unconditional rather than a threshold: the gate may miss an *inference*; it is never permitted to miss a *statement*.
- **Cost/risk:** A scoring pass over extraction candidates plus the provenance discipline to log gate decisions (score, floor invoked or not) in the turn's record (#6) — a gate whose rejections cannot be inspected is an unauditable filter on the user's own history, the same defect class as decay-as-deletion in quieter dress. The scorer itself is a model judgement and inherits #34-style grading for its calibration on chat-shaped material before it ranks anything load-bearing.
- **Evidence: C** — the write rule is the dossier's labelled steal (corpus synthesis from a paper mechanism); the fences are corpus policy continuous with #47/R21 (A for the field audit beneath those). No measurement in the corpus prices a surprise gate on a personal store; the entry claims the shape, not a magnitude.
- **Home:** accuracy — the memory service beside the runner; the write-side companion to #47's existence law and #14's injection discipline. Cross-reference: MEMORY-COMPENDIUM amendment (fifth cut), where the gate is stated as memory doctrine.

### #33 — Roofline benchmarking law for the build itself
- **Rank movement (v2):** rank 36 — ↓ from #33 in v1.
- **Source:** `memory/memory-wall-and-roofline.md` §4; `memory/mimiralloc-our-own-proven-work.md` §5.1 (measurement protocol).

### #44 — The measurement law as a build requirement: disclose, or the number is not real
- **Rank movement (v3):** new in v3 — enters at rank 39, paired with #33 (method) and #34 (faithfulness grading).
- **Source:** `papers/mlperf-inference.md` §§3, 6; `papers/vidur.md` §§3.4, 4, 6; `runners/deepspeed-fastgen.md` §7.4 (effective throughput).
- **Mechanism:** Not a feature — the constitution every number the build publishes must satisfy, adopted as a *build requirement* (a benchmark result missing a line is incomplete in a named way, and is not cited until the line is supplied or the gap is labelled). The minimal disclosure set: **scenario** (a blended tok/s is a scenario error — prefill and decode are different metrics), **phase**, **model + quant in bytes** (file size *and* active bytes under the run's residency state), **workload profile** (prompt/output split, sampling settings), **machine state** (hardware, clocks/governor if known, co-tenants, warm vs cold, measured sustained roof or the label "roof unmeasured"), **n and spread** (median + range; single runs labelled single runs), and **faithfulness grade** (raw-oracle rank/gap per #34, or the label "correctness not re-graded"). Three standing rules ride on it. **No percentile without its n:** MLPerf derives query counts from the percentile claimed — 270,336 inferences for a 99th-percentile claim at 99% confidence, as-reported; state n, or report a mean and call it one. **No summary score:** per-phase, per-scenario, per-quality-band results, or nothing. **Predictions carry their validation error or the label "unvalidated":** a simulated/modelled number names what was profiled vs interpolated and its ground-truth anchor — Vidur's fidelity (P95 up to 3.33% static; <5% dynamic at 85% of capacity; 12.65% worst at 95%, all as-reported) was earned against a real engine at a stated operating point, and error grows at the tipping point, so validation runs belong at the edge. FastGen's ethic is the local benchmark form: count only SLA-meeting requests (stated TTFT/generation-rate pair, fixed and versioned in the test suite, never tuned to a result).
- **Expected gain:** The same class as #33's, one level up: #33 stops the build deceiving itself about *speed*; this entry stops every downstream reader — dossier, commit message, release note — inheriting a number stripped of the conditions that make it real. It also prices a phrase out of the programme's vocabulary: **the optimum is a (model, workload) pair, never a model property** (Vidur, as-reported: the same model's best batch was 256 on one trace and 64 on another, with a 2× penalty for crossing them) — tuning records are keyed by workload shape from this cut.
- **Cost/risk:** Disclosure discipline on every claim, and the willingness to label our own numbers incomplete. No product risk.
- **Evidence: A** — consortium rules and a peer-reviewed simulator validated against a real engine, both with their numbers as-reported above.
- **Home:** robustness — stands from slice one beside #33; #45's energy line is its eighth disclosure line.

- **V5 note — arrival shape joins the workload profile (2026-11-15):** `papers/burstgpt.md` §§3–4, 6 (real traces from one regional Azure OpenAI provider; v3 population 5.29M traces / 121 days, v5 population 10.31M / 213 days — **never mix the two populations in one citation**) prices a line this entry's disclosure set previously left implicit. At **equal mean rate** (0.326 RPS, both runs 6,126 s over the first 2,000 queries, as-reported), BurstGPT's bursty arrivals produced higher latency and resource occupation than the uniform-arrival comparison trace and specifically stressed KV-cache management; and scheduling rankings **flipped between the conversation and API service types of the same provider** (FCFS's failure rate low on one, high on the other; LRF's advantage not holding across both). The fleet statistics themselves (mean rates, Gamma parameters, the >5% conversation failure rate) do not transfer to one user and are not quoted locally; what transfers is the norm — **the mean rate is not the workload; the workload is the distribution** — and its local test form: bursty, heavy-tailed synthetic loads (clustered arrivals, Zipf-like length mix with a real long tail, failures driven into the test, average *and* instantaneous behaviour reported), specified in Q30. - **V6 note — attribution joins disclosure: a comparison is not a measurement of a mechanism (2026-11-15):** `runners/magnitude.md` §8 is this entry's worked cautionary case, supplied by a vendor more candid than most. Its headline — over 2× decode vs Ollama — is a **defaults-versus-defaults, drafter-included, two-flagship-machines** figure; the controlled independent comparison on identical GGUF with the drafter isolated attributes ~1.12–1.20× to the tuned base engine, ~2× *additional* to the drafter on predictable code, and a drafter *penalty* (0.90–0.93×) on long-context work — three different mechanisms wearing one headline. ### #41 — Weight-arena VM discipline: alignment, huge pages, deliberate prefaulting
- **Rank movement (v2):** new in v2 — enters at rank 39.
- **Source:** `memory/virtual-memory-and-caches.md` §7.1 (§§3.4–3.5, 5.2–5.3).
- **Mechanism:** Treat model load as a fault-scheduling problem with a stated budget. Weight arenas are requested 2 MiB-aligned and sized in 2 MiB multiples, with `MADV_HUGEPAGE` applied under a system THP mode of `madvise` — the runner opts its known-dense ranges in; it does not set `always` for the machine — and the result is *verified* per arena via `AnonHugePages` in `/proc/<pid>/smaps`: THP is a request the kernel may decline, and a runner that cannot state whether its weights are actually huge-page-backed has a hope, not a policy. Prefault deliberately — `MADV_WILLNEED` over the weight ranges (or `MAP_POPULATE` at map time), issued ahead of first compute from enough threads to overlap storage latency — instead of letting prefill discover pages serially; never `MADV_SEQUENTIAL` on weights (its free-behind half is actively harmful to a per-token re-read set). Report cold and warm TTFT as separate metrics, with major/minor fault counts beside them. RAM budgets carry a named page-cache line, read from `smaps_rollup` (PSS) and `MemAvailable`, not from RSS arithmetic — a model that has ever been loaded is resident in page cache until evicted, and two "alternating" models compete for cache residency as well as arena space.
- **Expected gain:** Priced by our own campaign, not the literature's: MimirAlloc Z-049 measured 2 MiB huge pages **ADOPT** (the win bimodal on PMD alignment — an unaligned request silently gets base pages, which is why alignment is in the mechanism and not a footnote), 20 MiB **ADOPT**, 200 MiB **ADOPT on fault behaviour with bandwidth TIE**. The expected signature is faults and translation, not warm bandwidth: a team that benchmarks this by tok/s alone can honestly measure "no difference" and wrongly conclude huge pages do nothing. Cold-start TTFT is where the user feels it — the first token of a freshly loaded model is a paging event before it is a compute event.
- **Cost/risk:** A sparsely-touched 2 MiB region pins 2 MiB where 4 KiB would do — apply to known-dense weight arenas, never to sparse caches or mostly-empty reservations (the textbook counter-case). Fault-time compaction under aggressive defrag settings can stall the touching thread; `madvise` mode plus explicit opt-in contains it. On 16 KiB-page Pi-class targets the quanta differ and the policy is re-derived, not transplanted.
- **Evidence: A/C** — the huge-page verdicts are our own measurements on fleet-class hardware (A); the transfer from allocator-path measurements to runner weight arenas is the dossier's stated engineering judgement (C).
- **Home:** KV/memory (host-side residency) — companion to #4 (the device arena) and #12 (budgets); cheap, and it disciplines every load the build ever does.

### #51 — A load is a pipeline, stage-priced — with per-(model, workload, device) records
- **Rank movement (v4):** new in v4 — enters at rank 47, directly after #41 (the fault discipline it prices and extends from weights to the whole load).
- **Source:** `papers/serverlessllm.md` §§3–6; `papers/melange.md` §§3, 5–6 (the record-keeping half).
- **Mechanism:** A model load is treated as a **pipeline with named stages, each priced**: file open/read (bulk, direct I/O where it wins), page-fault population, pinned staging where used, device transfer, kernel/arena initialisation, session/sampler/template setup — the last group proceeding **concurrently** with weight streaming, not after it (a serial switch pays sum-of-parts for what could cost max-of-parts). Population is an allocator decision (#41): keep mmap where it earns its keep, but prefault deliberately in parallel and stage through pinned buffers — **never let first-touch faults land inside generation**, where they are unmeasurable, unschedulable, and charged to the one user at the worst moment. Every load writes a **record keyed by (model, workload, device)**, split by cache state (**cold / page-cache-warm / resident**), carrying engine version and date and expiring when its conditions change — Mélange's profiling matrix as a discipline, with its solver and cloud savings explicitly not imported (owned hardware has no rentable menu). "Warm" is a defined, recorded state, never an anecdote.
- **Expected gain:** Priced by the paper's anatomy, as-reported on its testbeds (the anatomy transfers, the numbers do not): ServerlessLLM's mmap baseline incurred **112K page faults** on a cold LLaMA-2-7B load, and its ablation prices the fixes **in order** — bulk reading 1.2×, direct I/O 2.1×, multi-threading 2.3×, pinned memory 1.4×, pipelining 1.5×. The local claim is only the method: measure the load as a pipeline with a fault count, then spend on the stage that is actually slow — on its hardware the naive path left roughly an order of magnitude in exactly those stages. Model *switching* is where the target feels it: a switch whose cost is known per stage, and whose warm state is recorded, stops being the multi-second mystery stall #17 exists to remove.
- **Cost/risk:** Instrumentation per stage plus the record store — days, not slices. ServerlessLLM's own format and cluster machinery are not adopted (GGUF and its mmap path have real virtues: instant start for small models, shared pages across processes); the entry is a measurement-and-staging discipline over the existing path, sequenced by what the fault counts indict.
- **Evidence: A** for the stage anatomy and ablation order on the stated testbeds; **C** for local stage prices, which the records exist to replace with measurements.
- **Home:** robustness — companion to #41 (device-side arena discipline) and #17 (no reload thrash); its records feed #53's solver and #12's placement cache.

### #56 — Dry-run fit: measured estimation through the real allocator
- **Rank movement (v5):** new in v5 — enters at rank 50, directly after #51 (the load records it feeds) and before #39. Ranked by dependency, not by elegance: it presupposes #12's budget policy to consume its numbers and #4's allocator shape to run against, and it replaces the input both currently assume.
- **Source:** `runners/ggml-backend-internals.md` §§4–6 (ggml / llama.cpp at tag v1.0.0, source-read 2026-11-15); the contrast in `runners/ollama-internals.md` §6 (Ollama v0.40.16).
- **Mechanism:** Price a load by **running the real machinery with allocation disabled**, exactly as ggml's `common/fit.cpp` does at v1.0.0. (1) Load the model with allocation turned off: tensor metadata, shapes and buffer-type assignments are real; weight buffers are zero-sized dummies. (2) Create a real context on the phantom model; context creation reserves the **worst-case compute graphs** (prompt-processing, then token-generation, then prompt-processing again, so resident buffers fit the larger of the two) — in no-allocation mode the reserve runs in its **size-only form**: the scheduler splits the graph, the graph allocator runs its full liveness simulation, and reports the per-backend buffer sizes it *would* materialise. (3) Read out the **memory breakdown** and sum per device. The breakdown's shape is adopted verbatim as the fork's ledger format: **model / context / compute**, per device, with host memory as an explicit bucket — where *context* is the KV buffers' structural size for the configured length, sequences and cache types (priced through each buffer type's own allocation-size function, so backend padding — e.g. CUDA's quantised-row expansion — is *included*, where element-count arithmetic under-reports it), and a GPU-class device reporting 0 free / 0 total is treated as **unusable for fitting, never as infinite**. The fit loop then adjusts only its declared knobs (GPU layer count and its fractional refinement, context size when automatic) against measured free memory with stated margins, re-running the full phantom measurement per iteration — the measurement is an expensive, real execution of the loading path, and the entry budgets it as one. Two companion disciplines are part of the entry: **expected-vs-actual verification** (reserve-time expected sizes are recorded; drift at teardown is logged as a defect, per #51's v5 note) and the **named blind spot** (scratch-pool retention is not a breakdown bucket upstream — the fork's breakdown carries it as #6's sixth number, or the estimate understates a long-lived server's residency by construction).
- **Expected gain:** The elimination of a bug *class*, priced by the contrast the wave-32 dossiers read from both codebases. The incumbent alternative (Ollama v0.40.16's `PredictServerVRAM`, #12's v5 note) is wrong **structurally**: KV priced at f16 regardless of the configured type, head geometry from a minimum and a division, and no buffer/context/display terms at all — errors a percentage margin cannot correct. The dry run cannot diverge from the allocator in that way, because it *is* the allocator: its exactness is the graph allocator's own guarantee (for the exact graph simulated, peak compute usage is known before execution, per buffer type, through the backend's real allocation-size functions). What it does not know is equally definite and is stated in the entry so no later text overclaims it: pool retention, captured graphs, driver context and other processes sit outside the breakdown and are handled only as shrinkage of measured free memory — which is why the fork's six-number ledger (#6) and the dry run are companions, not substitutes.
- **Cost/risk:** A phantom-load path through the fork's own loader and allocator (the upstream implementation is the proof of shape; the fork's is real work, sequenced after #4's arena exists to be simulated), plus the per-iteration cost of full phantom context creation inside the fit loop. The failure contract must be the fork's, not upstream's seams blindly copied: upstream converts a null buffer into a thrown load error with **no in-load negotiation** (fitting must happen *before* loading — which is this entry's whole point), while some ggml allocator paths abort the process outright (the bump allocator; checked-fatal scratch errors) — the fork wraps every allocation path its server can reach in an error its scheduler can act on (#31's v5 degradation clause is the policy this entry's numbers feed).
- **Evidence: A** for the mechanism as implemented and read at the pinned tag (the estimate's exactness is a construction property of the allocator, §4.5 of the dossier); **C** for the fork's implementation cost and for local fit quality until the fork's own dry run is graded against its parsed actuals per #44.
- **Home:** KV/memory — the instrument under #12's budget policy and #51's load records; its degradation decisions are #31's, made at fit time on its numbers.

### #49 — Guided-generation constraint discipline: mask before the chain, precomputed, transactional
- **Rank movement (v4):** new in v4 — enters at rank 51, directly after #36 (its interface home). Ranked by its consumer, not its correctness: free-form persona chat needs no constraint, and the entry says so — its rank rises the day a structured consumer (tool calls, memory-extraction sidecars) becomes load-bearing.
- **Source:** `papers/xgrammar.md` §§3, 5; `papers/outlines-guided-generation.md` §§3, 5; the chain it precedes is #37's (v3 refinement).
- **Mechanism:** Three laws, stated as one entry because each is void without the others. **(1) The mask goes before the chain:** forward → logits → **mask (invalid := −∞)** → penalties / truncation / temperature → renormalise **over valid tokens only** → sample → advance the automaton. Masking restricts the distribution's *support*; sampling first and rejecting after is not a draw from any well-defined conditional distribution, has no termination guarantee, and collapses the cost model — there is no legitimate mask-after-sample design, in either dossier. Masked-out means zero probability in the final categorical under any finite temperature, and the relative odds of two valid tokens are the model's, untouched — an engine whose mask re-weights valid tokens has introduced a second, undocumented sampler. **(2) Precompute the mask; per-step cost must not scale with |V|:** Outlines pays the vocabulary walk once into a state→token-set index (O(1) lookup per step); XGrammar's context-independent/context-dependent split keeps the live remainder under 1% of the vocabulary (1,134 of 128K tokens, cut to 120 by context expansion; mask <40 µs/token for JSON Schema/CFG, all as-reported) — mask preparation lives off the decode path (#25) by construction, not by hope. **(3) Constrained speculation is one transactional unit:** tokens + KV + automaton state commit or roll back **together** — a draft token is judged against the automaton state *at its position in the draft tree*, and rollback restores all three to the accepted prefix, no further, no less; anything that rewinds the token stream rewinds the automaton or refuses to run under constraint. The automaton state is per-sequence decode state, on a par with the KV cache (#48's movability applies to it: it belongs in the session snapshot beside the KV material and mirostat's μ).
- **Expected gain:** Guaranteed-*shape* output for the workloads that need it — and the honesty boundary travels with it: **100% conformance means syntactic, never semantic.** For the persona case the dossiers make the stronger claim (§6b of both): constraint is the **reliability floor under agent memory** — structured extraction sidecars (#8/#14's write path) that cannot emit malformed records do not need repair loops, and a malformed memory write is a store-corruption event, not a formatting bug. No speed claim for free-form chat; XGrammar/Outlines throughput figures are fleet figures and stay in their dossiers.
- **Cost/risk:** An automaton + mask-index layer behind #36's interface — build when a consumer lands, per #36's own scheduling. The mirostat combination is explicitly untested in both dossiers (surprise target computed over the masked distribution): treat as untested until #37's conformance vectors say otherwise (Q24/Q27 territory). Grammar compilation is once per grammar, cached as an artefact (#35).
- **Evidence: A** for the mask semantics and precomputation costs as-reported in the two dossiers; **C** for the local sidecar-reliability magnitude, which is the dossiers' labelled applicability judgement.
- **Home:** accuracy — the discipline half of #36's interface; sibling to #37's chain, never a stage inside it.

### #48 — State-movability: sessions built movable, handoffs by the Llumnix protocol shape
- **Rank movement (v3):** new in v3 — enters at rank 47. The *principle* is adopted immediately as a design constraint on #1/#10/#11 (it costs nothing at design time and everything if retrofitted); the rank prices the incremental *protocol work*, which is later.
- **Source:** `papers/llumnix.md` §§3, 5; `papers/mooncake.md` §5 (the sibling: pool the state); `papers/infinigen.md` §6b (progressive restore).
- **Mechanism:** **Placement is revisable, so build state movable:** state designed as a serialisable, restorable object can be re-placed; state smeared through a heap can only be recomputed. Llumnix could revise placements only because request state was designed transferable (paged blocks, a handshake, commit/abort) — and its protocol exploits the KV cache's append-only shape: copy the immutable bulk while decoding continues, pause only for the final iteration's residue. The local handoff shape is copied literally, with the network replaced by memcpy and the destination's pre-allocation handshake replaced by a fit check: **reserve → overlapped bulk copy → final-increment pause → commit/abort**. Local destinations are real: session between models (chat model ↔ summariser sidecar), between backends, between GPU residency and RAM/disk tiers, and — at turn boundaries on unified memory — between devices. Two miniaturisations ride along: *fragmentation as a first-class metric* (free memory that could satisfy the blocked head-of-line request if unfragmented — a better local health number than raw free bytes; #6's VRAM ledger should carry it), and *virtual usage as policy language* (the active persona session carries headroom in the accounting, so ordinary allocation spills background work first — #31's shedding order expressed as weights, not special cases).
- **Expected gain:** As-reported at fleet scale (Llumnix, 16× A10 testbed): migration downtime **~20–30 ms**, near-constant in sequence length and shorter than a single decode step, with per-step interference up to ~1% during migration — the *shape* is the steal, not a local promise. Locally the gain is that #11's spill/restore and any future backend/device handoff abort cleanly instead of landing half-moved, and that session transfers stay invisible when they happen mid-conversation: the user-visible pause is proportional to the last increment, not the whole history. The fleet machinery itself does not transfer — on one GPU there is no destination instance, and the P99 multipliers stay in the paper (see §5 of the dossier).
- **Cost/risk:** The protocol is short and proven; the cost is the discipline of keeping session state a defined object (which #1 already mandates) plus a fit-check/commit path per handoff kind. Risk is over-building: one handoff kind at a time, driven by a real move the product needs.
- **Evidence: A** for the protocol and its measured downtime on the stated testbed; **C** for local magnitudes.
- **Home:** anchor/residency — the movement discipline for #1's object, #10's persistence and #11's spill.

### #58 — Typed ownership for cache resources: the scheduler's state machine
- Rank movement (v6): new in v6 — enters at rank 58, directly after #48. The principle is adopted immediately as a design constraint on #4/#5/#57 (it costs nothing at design time and everything if retrofitted — #48's own argument); the rank prices the incremental work: the state-machine core itself.
- Source: `runners/tokenspeed.md` §§2.1, 3.4, 9.2.
- Mechanism: every KV page/block and recurrent-state slot is a value with an explicit state (free / owned / published / pinned-by-image-or-transfer / in-flight), transitions only through named operations (allocate, publish, copy-on-write, pin, release, evict); any "must not free while X" condition is *derived from state*, never stored as a flag beside it (TokenSpeed's prefill–decode pin is a function of scheduler state — "no event handler can forget to clear it"). ### #46 — Narrow-tree speculation, value-ranked, as a rider — never a default
- **Rank movement (v3):** new in v3 — enters at rank 48, last among the ranked: it is the most conditional entry in the ledger, gated on a substrate the build does not yet have.
- **Source:** `papers/specinfer.md` §§4, 6; `papers/eagle-2.md` §§3–4, 6.
- **Mechanism:** The small-card verdict, restated as an entry so it cannot be quoted away: **tree verification pays at width ≈2–3 and low-tens total nodes, depth over breadth, budget measured locally.** SpecInfer's own table shows acceptance gains flattening hard past width 2–3 at every dataset, and width 2–3 optimal once batch ≥4 consumes the spare capacity — a 6 GB card at batch 1 is, in spare-capacity terms, closer to that loaded regime than to the idle one. The local paying region (the dossiers' labelled judgement): width ≈2–3 where branching happens at all, total verified nodes ≈8–16, depth ~5–6, with the node budget treated as a *measured* knob (tokens-per-pass vs wall-clock tok/s on the user's own card and context length — Q21). **Width is spent by value, never by position alone:** EAGLE-2's transferable principle — rank nodes by the path-product of draft confidences from the root, expand the highest-value nodes, rerank globally, keep the top-m under budget — so the tree runs narrow and deep through predictable stretches and widens only where the drafter itself reports uncertainty. The same principle in chain form (confidence-gated draft length) captures a real fraction of the gain with no tree substrate.
- **Expected gain:** No datacentre number is imported. EAGLE-2's **48–60 draft tokens per pass at depth 6 are datacentre budgets** (R18 rejects transplanting them): on a 6 GB card the per-position costs — attention over a long accumulated context per node, KV writes per node, a wide LM-head/logits pass — stop being rounding errors well before node 60, paid from the same bandwidth that makes speculation worthwhile at all. What is claimed locally is only the shape: a value-ranked narrow tree costs less verifier work per accepted token than a static tree of the same budget, and on an *offloaded* setup (weights streamed from somewhere slow) reducing the number of passes is worth even more (SpecInfer's offloading result, 2.6–3.5× as-reported on its testbed, is the logic's demonstration, not a local expectation).
- **Cost/risk:** **Tree verification is kernel work, not a flag:** a tree node's visible set is its ancestor chain — not a contiguous prefix, and different for nodes at the same flattened offset — which ggml's FlashAttention path cannot express. Adoption means a materialised mask off the fused path or a purpose-built tree-attention kernel, **per backend**, plus per-node RoPE positions (depth on its own path), tree-structured KV with per-step rollback of dead branches, and a tree-walking sampler. Priced as that shared substrate — justifiable, if at all, by the tree family together — never as a single-paper port. The realistic local path runs through #27: EAGLE-3's verifier *is* EAGLE-2's dynamic tree, so the practical question is whether the shipped path exposes its tree budget to tune down (Q21). Confidence calibration is a precondition, not a detail: re-measure it per (target, drafter) pair, or value ranking misallocates silently (output stays exact; only speed suffers).
- **Evidence: A** for the width-flattening and the value-ranking mechanism on the papers' testbeds; **C** for the local paying region, which is the dossiers' labelled judgement awaiting Q21.
- **Home:** speed — a rider on #27's shipped path and on any future tree substrate; the default accelerator remains #15.
- **V4 refinement — Sequoia generalises the method, TriForce bounds the regime (2026-11-15):** wave 26 banked during this cut (`papers/sequoia.md` — NeurIPS 2024, *Scalable, Robust, and Hardware-aware Speculative Decoding*; `papers/triforce.md` — COLM 2024), and both dossiers address this entry directly (§5 of each). **Sequoia generalises this entry's reasoning; it does not overturn its conclusion inside its regime.** This entry says "the budget must be measured locally"; Sequoia supplies the formalism for what to measure and how the budget follows: **Speedup(n, d) = G(n, d) / ( t(n) + d·c )** — G the DP-computed expected yield of the best tree of size n and depth d, **t(n) the measured, hardware-dependent time to verify n tokens** (normalised to verifying 1), c the measured draft-token cost — then grid-search (n, d). Because G grows only (sub-)logarithmically while t(n) grows at least linearly, the optimum is finite and interior, set by where the measured t(n) curve bends: on hardware where t(n) rises steeply — this card, whose per-node costs are paid from the same narrow bandwidth that makes speculation pay — the formula's optimum *is* a narrow tree. **The scope bound is equally explicit:** the same formula on the L40 offloading curve (one target pass at 5.6 s/token, as-reported) returns a **768-node, depth-17–23 tree** and the paper's largest speedup (9.96×, Llama2-70B, as-reported) — so this entry must never be quoted as "wide trees don't pay" without its regime qualifiers (small card, on-chip weights, short/medium context, batch 1); quoted *with* them it stands untouched, and Sequoia's own on-chip optima (64–128 nodes on A100/L40-class cards, shrinking as the target grows, as-reported) already slope in this entry's direction. **TriForce bounds the entry by context regime:** its speculation is **chain-shaped at both levels** (γ₁, γ₂ are lengths, not widths) and it contains **no tree-width experiment** — it neither confirms nor refutes this entry's numbers. What it prices is the premise underneath them: #46 assumes drafting is nearly free and verification width is the scarce spend; by **122K context** the draft's own KV load is first-order, cheap drafting's acceptance collapses (naive policy 0.465 at T=0, as-reported), and the winning spend is a second speculation level plus a retrieval-selected draft cache (4K budget, plateauing thereafter, as-reported). **This entry governs width *within* a level; TriForce governs how many levels there are and what each level reads** — the two compose (a narrow value-ranked tree, sized by Sequoia's cost model, verified at TriForce's outer level), and a runner carrying this entry's tuning unchanged into a 100K-context workload has optimised the smaller term. **What does not change:** this entry's specific numbers (width ≈2–3, ≈8–16 nodes) remain **unmeasured local judgement, evidence C** — neither dossier measures a 6 GB card, batch 1 with a resident chat context, or a quantised GGUF target; Sequoia's evaluation is short-context (128-token prompts/generations) and TriForce's is A100/RTX 4090 at 122K. Q21 is now precisely Sequoia's prescribed measurement localised (measure t(n) and the acceptance vector on the 2060; let the DP compute the budget). Both dossiers also carry the corpus's raw-oracle rule for "lossless" claims (§6b of each): TriForce's losslessness argument confines all approximation to the proposal side of a full-cache verifier — a claim about an *implementation* is graded, never inherited from the argument's shape.


- **V6 note — confidence budgeting gains a production instance and its bound (2026-11-15):** DeepInfer's DSpark scheduler (confidence head + profiled throughput curve → per-request verify length; `runners/deepinfer.md` §§3.3, 9) is this entry's chain-form principle — confidence-gated draft length — running in production, and it prices the family honestly: +4–7% at its operating point, −1.5% at its lowest measured concurrency. The budgeting rule is adopted on #32 (acceptance history as the confidence signal a general runner actually has); this entry's numbers and regime qualifiers are unchanged, and DeepInfer's table is one more reason the rider stays a rider at batch 1.

## 4. Top five — scheduling reasoning for the coordinator

The top five are not simply the five largest wins. They are the five that make the rest of the ledger possible, in dependency order. A coordinator should read the sequence, not just the set.

**V2 re-derivation — the top five stand, and the new evidence mostly widened their lead.** Each new dossier was checked as a potential challenger. The persona-chat canon (KoboldCpp, Aphrodite) corroborates the top five's workload premise — the persona trunk *is* the canon's Memory block, the post-history slot *is* its Author's Note — and its one genuinely new surface (samplers, #37) enters at rank 15: valuable and cheap, but a sampler multiplies nothing until sessions, residency and an intact persona exist to sample for; a looping persona is a bad product, a beheaded one is no product. The reserve decomposition (gpu-memory-internals §7.3) strengthens #3 specifically: display-attached, f16 KV affords at most ~2,000 tokens and possibly no budget at all, so the q8_0 default is now the difference between shipping and not shipping on the machine as actually used. TensorRT-LLM's retreat validates #4/#12's shared framing — planning at load time, inside the runner, over a portable artefact — by removing its only serious rival: NVIDIA deleted the build-time alternative itself. The strongest genuinely new candidate, MoE expert caching (#38), enters at rank 31, not the five: it serves a model class outside the target's primary catalogue and presupposes the arena and residency machinery the five build. Nothing banked since v1 reduces any top-five entry's gain, cost or risk by enough to reorder them; the honest change is in #3's numbers (below), not in the set or its order.

**V3 re-derivation — the top five stand again, and batch 4 mostly widened the moat rather than challenging the set.** Each new dossier was checked as a challenger, as in v2. Mooncake is the strongest: its pool *is* #5/#10's design at fleet scale (KV as a poolable asset, priced by fetch-vs-recompute break-even), and its admission lesson strengthens #31 — corroboration, not competition; nothing in it moves a session, an anchor, or a byte of KV arithmetic earlier than the five. Llumnix argues for the five's shared premise from the far side: placements rot, so state must be built movable — which is what #1's session object *is*; its protocol enters as #48, ranked by its incremental work, not its principle. CacheGen (#43) presupposes the tiers #10/#11 build and the blocks #4 allocates. The measurement law (#44) and the energy metric (#45) are constitutions, not features: they grade the five, they do not replace them — the same reason #33/#34 have always ranked as disciplines rather than contenders. The sampler law sharpens #37 at rank 15 without touching the argument that a sampler multiplies nothing until sessions, residency and an intact persona exist. Narrow trees (#46) enter last, deliberately: the batch's clearest negative result is that the datacentre's speculation budgets do not survive contact with this card. The honest v3 change to this section is therefore not the set or its order — it is that #3's display-attached warning now has a priced companion: when the KV budget collapses toward ≈0–250 MiB, #43's transit codec and #45's efficiency mode are part of how the shipped configuration stays honest about what it can hold and what it costs to run.

**#2 Pinned anchor + #6 Loud disclosure — schedule first, together, as policy.** Neither needs new kernels, an allocator, or a cache. Together they convert the build's founding law (the anchor cannot be pushed out) from an intention into a tested property, and they install the observability (reuse counts, eviction reports, effective-precision reporting) that every later slice will be graded through. Shipping anything lossy before #6 exists means shipping it unmeasured in production. Cost: days, not slices. This pair is also the only top-five work that is pure win with no quality trade-off to validate.

**#1 Resident sessions — the object everything else attaches to.** Prefix caching (#5), persistence (#10), stable-order injection (#14), the post-history anchor (#7) and per-persona drafters (#32) are all, structurally, properties of a session object. Building any of them against the stateless API first means building it twice. HS-6's lesson generalises: token-level residency (the committed-token watermark) must be in the session's first design, because the generation-seam loss it eliminates is invisible until real resends hit it. Sequence: session object with watermark first, composition (anchor segments, injection) second, retention third.

**#3 q8_0 KV default — the arithmetic that decides what the sessions can hold.** This is a policy change over existing cache types, so it can land in parallel with #1/#2 — but it must land *before* #9 (eviction scoring) and before #10's persistence format freezes, because both inherit the cache precision: scoring operates on the cache this entry sizes, and a saved session is only valid for the precision it was saved at (hence the envelope). Its worked case is the build's founding arithmetic, restated in v2 with the split reserve: *headless*, f16 does not meet even the 8K minimum for an 8B chat (4,912 tokens) and q8_0 does (9,246); *display-attached* — the laptop as actually used — the KV budget falls to ≈0–250 MiB and no cache precision reaches 8K for this model, so the coordinator should expect the shipped configuration to pair this entry with #42 (a smaller, lineage-chosen weight quant) or #19/#20 (sub-8-bit KV), decided by #12's budget, per model. Validate per model family through #34 as it lands, not after.

**#4 Block allocation — the substrate.** Radix/hash prefix retention (#5), block-granular eviction (#9), spill and persistence (#10/#11), per-layer quotas (#16/#21) and hybrid snapshots (#23) are all operations *on blocks*. Without the arena + block table + reference counts, each would invent its own allocation shape and the campaign would pay five integrations instead of one. This is the deepest surgery in the five and the one to staff most carefully; its acceptance test is memory honesty (exact KV accounting, teardown returning provably to baseline — the MimirAlloc L-006 lifecycle shape), not speed.

**#5 Prefix cache (trunk + branches) — the retention layer, last of the five by dependency, first by felt impact.** It needs #4's blocks to share, #1's sessions to own the sharing, #13's rendering discipline to hit, and #3's precision to afford keeping prefixes resident at all. Once it lands, the workload's economics invert: later turns cost the new turn only, swipes cost a suffix, and #10's tiering has something worth tiering. The dependency the brief names — *prefix caching before tiering* — is exactly this: tiering (#10/#11) is a policy over retained prefix objects, and scheduling it earlier produces a persistence format with nothing stable to persist. The second named dependency — *q8_0 KV before eviction scoring* — is #3 before #9, for the same reason: do not tune a scoring policy against a cache whose size is about to halve.

**V4 re-derivation — the top five stand a third time; batch 5–6 corroborated them from the fleet side.** Dynamo and llm-d are the strongest challengers by pedigree, and both collapse *into* the five rather than against them: llm-d's precise indexer, collapsed to one process, *is* #5 with its locations renamed (§8.2 of its dossier, carried in #5's v4 note); Dynamo's Planner degenerates to #31's budget check (#31's v4 note); both fleet systems put their intelligence in placement, capacity and cache policy and leave token generation to the engines — the five's own division of labour, at the opposite end of the scale axis. The four-number rule (#50, rank 13) is the cut's highest new entry and still does not challenge the five: it prices the windows the five build, and a usable-length measurement for a session that does not yet exist measures nothing. The load pipeline (#51) and fraction search (#53) likewise presuppose #4's arena and #12's budget. Nothing banked since v3 reduces any top-five entry's gain, cost or risk; the honest v4 change is corroboration depth, not order.

**V5 re-derivation — the top five stand a fourth time; this wave's strongest evidence was about the base, not about rivals.** The three deep-dive dossiers (llama.cpp KV internals, ggml backend internals, Ollama internals — all source-read at pinned tags) were checked as challengers first, because they describe the ground the five must be built on. They corroborate the five's premises from inside the incumbent code: the base has **no session layer at all** (#1 is construction, and nothing upstream is coming to substitute for it), its anchor protection is a 4-token `num_keep` inside a four-behaviour silent-truncation matrix (#2/#6 are not hardening an existing property — they are creating one), and its pre-load memory number is a heuristic whose KV term is priced at the wrong type and geometry (#3's arithmetic and #12's budget are the fork's to build, with #56 now naming the instrument). The wave's one genuine capacity challenger, DuoAttention (#54, rank 23), presupposes the five rather than rivalling them: its two cache shapes live inside #4's arena, its fit arithmetic is #3's budget spent differently, and its mask gate is #34's discipline — a head-policy multiplies the value of resident, honestly-sized KV; it does not create any. Titans' steal (#55) presupposes #14's store and #47's law. Nothing banked since v4 reduces any top-five entry's gain; the honest v5 change is to #1's **cost class** (construction, not refactor — its v5 note), which if anything strengthens the scheduling conclusion: the object everything attaches to is also the largest single build in the programme, and starting it late is now measurably the expensive option.

**V6 re-derivation — the top five stand a fifth time; this wave priced #1's floor and strengthened #5's evidence without moving either.** The five new dossiers were checked as challengers in the usual way. ## 5. Rejected / deferred — priced by the corpus, do not re-litigate

Each entry names the idea, where the corpus priced it, and the reason it is wrong *for this target*. "Rejected" means do not build it for the 6 GB single-user build; "deferred" means a named condition would reopen it.

**R1. Learned activation predictors (DejaVu-style) for SwiGLU sparsity — REJECTED.**
Priced in `runners/powerinfer.md` §8.4: a per-layer MLP predictor at the paper's ~7% parameter ratio is ~0.5B parameters for a 7B-class model — ~0.5 GB at INT8, ~1 GB at FP16, resident in a 6 GB budget — plus two small matmuls per layer per token on the critical path, plus a per-model training pipeline (hours per model) that a Go project does not otherwise need. Modern chat models are SwiGLU: there are no exact zeros, and the learned predictor is the part of PowerInfer that does not survive contact with a small-VRAM, no-training-pipeline product. The free alternative exists and is ranked instead: gate-first thresholding (#30). A narrow low-rank gate approximator is the only form that could reopen this, and only after #30 is exhausted.

**R2. Datacentre preemption-by-recompute as the *sole* overflow policy — REJECTED (as a sole policy).**
vLLM V1 recomputes because, in a datacentre, recompute is cheaper than many small PCIe swap transfers. For a single long chat the victim is the user's whole conversation: re-prefilling 32K tokens on a laptop GPU is minutes, paid by the person waiting on exactly that conversation. `runners/vllm.md` §9.4 and `memory/kv-cache-design.md` §4.3 both invert the policy locally: spill idle sessions to RAM/disk, recompute only short spans, keep recompute as the always-working fallback. Recompute as *fallback* is in the ledger (#11); recompute as *doctrine* is rejected.

**R3. Draft-GGUF speculation as the *default* speculation — REJECTED as default (kept as #26, conditional).**
The draft model spends the scarcest resource on the card — VRAM — to buy speed, and on 6 GB it competes byte-for-byte with the KV cache a long chat needs. Meanwhile the zero-weight member of the same family (n-gram/prompt-lookup, #15) captures the repetitive-chat win for megabytes, losslessly, today. A default that evicts context to fund a drafter is the wrong trade for this workload; a per-pair, telemetry-gated option is the right one. Do not re-litigate the default; litigate individual (target, draft) pairs with acceptance data.

**R4. Medusa-style bolt-on heads for arbitrary GGUFs — DEFERRED (blocked on artefacts that do not exist).**
Medusa's residency is the best in the trained family (no draft model; a few hundred MB of heads for a 7B-class target) — and irrelevant in practice: heads must be trained per target model on the unquantised backbone's hidden states, community GGUFs ship without them, and llama.cpp's shipped speculation is draft-model and n-gram based. Two further cautions from `papers/medusa.md`: its default *typical acceptance* rule does **not** preserve the output distribution (only rejection sampling is lossless — any deployment promising "same output, faster" must use it and accept the lower speedup), and Medusa-2 changes the backbone, i.e. it is a fine-tune with a fine-tune's regression burden. Reopens only if the build campaign ships its own model releases, where Medusa-1-style heads baked in at fine-tune time are the cheapest integrated drafter available.

**R5. Full Jacobi Lookahead decoding — REJECTED as an implementation target (idea already captured by #15).**
Lookahead spends the scarcest thing on small hardware — FLOPs: its tuned A100 configurations imply 56–120× extra FLOPs per step, absorbed only while decoding is bandwidth-bound with compute to spare. The paper's own RTX 3090 result (~1.3× on MT-Bench) is the realistic reference class for consumer cards, its acceptance length (τ ≈ 1.5–2.0) is the lowest in the speculation wave, and its fused lookahead+verification step needs a bespoke attention mask per backend. llama.cpp's n-gram modes are mechanically its pool-and-verify idea with table-lookup drafting instead of extra model FLOPs, and they dominate it on 6 GB. Trajectory-mined n-grams (harvesting discarded-but-computed continuations into the pool) is the one refinement worth remembering — as a #15 extension, not a project.

**R6. Full KVQuant as the default KV scheme — REJECTED as default (two steals extracted as #20).**
Five interacting mechanisms, per-model calibration artefacts (Fisher-weighted codebooks, key scales, thresholds) that arbitrary community GGUFs do not ship, CPU-offloaded threshold computation, and pre-RoPE key caching that is incompatible with every existing engine's cache format and with any persisted prefix store built on post-RoPE keys. Each mechanism's individual gain in the paper's own chain is modest (0.19–0.82 perplexity); the stack pays off only whole, and whole is a research project. The near-free parts — sink/head FP16 protection and 1% outlier sparing — are in the ledger. Reopens only for a small set of first-class models the campaign itself calibrates and ships.

**R7. KIVI-2 (2-bit) as an unvalidated default — DEFERRED behind a per-model gate.**
The asymmetric scheme is ranked (#19); the 2-bit *default* is not. The paper's own evidence bounds it: LongBench capped at 4,096 tokens for most models (nothing validates 2-bit at 32K+), and Falcon/MQA — the already-head-compressed architectures — needed 4-bit to hold accuracy. On a card whose entire purpose is long context, shipping the least-validated-at-long-context precision as the default inverts the evidence. 2-bit is a labelled capacity mode per model, after #34 grading at the longest supported context.

**R8. Non-prefix modular reuse (Prompt Cache splicing, CacheBlend fusion) as early work — DEFERRED behind a quality gate.**
Both solve a real chat problem (lore chunks assembled in varying order never form a clean prefix) and both are approximate in ways prefix reuse is not: Prompt Cache rests on empirical tolerance of discontinuous position IDs, with per-dataset accuracy movement in both directions in its own table; CacheBlend's ~15% selective-recompute figure comes from FP/8-bit datacentre models on QA/summarisation and must be re-measured for roleplay models and quantised weights, and its HKVD fusion needs layer-wise partial-prefill hooks inside the engine — real work, not a flag. The cheap intermediate (chunk-level KV persistence + plain prefix reuse) is already #10. Reopens when measurements show lore re-prefill dominating TTFT *after* #5/#10 land.

**R9. PowerInfer's full sparse-hybrid engine, and ReLUfied model catalogues — REJECTED for this build.**
The headline numbers (up to 11.69× FP16, up to 8× INT4, 11 GB card) belong to ReLU-family models. The SwiGLU control outcome in the same dossier is ~1.5×. Building neuron-granular hybrid kernels to chase the ReLU ceiling on a SwiGLU catalogue misprices the work by an order of magnitude; shipping converted/ReLUfied model variants to manufacture the ceiling makes the runner own a model-quality liability (the conversions carry multi-billion-token fine-tunes and their own quality caveats). What survives — placement policy (#29), gate-first sparsity (#30), the LRU neuron cache and cluster-pipeline shapes if a flash/RAM weight tier ever exists — is already extracted.

**R10. A custom general allocator (MimirAlloc included) for the KV pool or for decode speed — REJECTED, on our own measurements.**
This is the rejection our own records argue loudest. MimirAlloc — correct, fuzzed, soaked, 117/117 on two campaigns — lost to glibc on every general workload on the Pi (5.4×–65.2× in the K-002 baseline) and on most core shapes on the Z13, including **all three KV-cache-shaped probes (Z-115, no adoption)**. Decode is bandwidth-bound, not malloc-bound. The pool is an arena with a free list (#4); a general allocator is for the structures around it. Where allocator work could still pay is footprint/longevity (retention: back to within 128 KiB of baseline after free, where glibc retained 1,232 KiB, Pi K-008) — a server-hygiene property to *measure* (#33), not a reason to adopt an allocator. Any future proposal carries the burden of a K-002-style A/B on the target machine.

**R11. Fleet serving machinery: continuous batching as a throughput project, multi-process engine cores, CUDA graphs, disaggregated prefill/decode, tensor/pipeline parallelism — REJECTED for this target.**
Orca's 36.9× is a static-batching comparison on GPT-3 175B; with one user and usually one active generation there is no batch to continuously refill, and the PagedAttention paper's 2–4× scales with the concurrency we do not have. What transfers from that world is already extracted: the iteration-level step loop (#18/#25), the token-budget scheduler shape, block allocation (#4). The rest solves Python contention, multi-GPU communication and fleet fairness problems a single-user Go binary does not have. (`runners/vllm.md` §9.5 states the same list as its own "what not to steal".)

**R12. Forking ggml/libllama; exposing llama-server directly; the fixed-slot scheduler as a concurrency story — REJECTED.**
`runners/llamacpp-ggml.md` §8.7, with Ollama's 2025–2026 engine detour as the controlled experiment: subprocess + pinned upstream build + compatibility translation is the proven pattern; a fork inherits the whole maintenance surface for no workload-relevant gain. Exposing llama-server beyond loopback imports its unauthenticated, unnamespaced session surface into our product. And if multi-user serving ever becomes a goal, it should be entered deliberately with paged-KV/prefix-tree designs (#4/#5), not by stretching slots. **Extended in v2 with a second natural experiment (`runners/jan.md` §6.3, §7.3):** Menlo built the abstraction variant of this same mistake — Cortex, a separate engine *platform* (own name, CLI, API, site, swappable-engine roadmap) between Jan and llama.cpp — kept it roughly a year, then deprecated it in favour of direct llama.cpp integration and migrated every user; the second engine Jan eventually added (MLX) arrived as a sibling extension, not through the platform. The priced lesson, carried into #4's risk note: an engine abstraction earns its keep only when a second engine is real, shipped and maintained — until then it is a tax on every release. (Lemonade's router-over-engines is the apparent counter-example and is not one for us: it is a *vendor's* orchestration over subprocesses it does not maintain, entered with the fragmentation costs documented in its dossier — subprocess isolation, yes; an abstraction layer of our own, no.)

**R13. "Infinite memory" readings of StreamingLLM — REJECTED as a claim (the policy is #9).**
Sink+window gives stable, constant-cost generation over unbounded *input*; it provides no recall of anything evicted, and the paper says so. Any build or UI copy that lets "infinite chat" imply "remembers everything" is a dishonesty defect: the character has forgotten whatever scrolled out, and the product must pair the policy with an explicit memory mechanism (#8) and say which is in force. Recorded here so the marketing version is never re-litigated as if it were the technique.

**R14. UMA retention breadth imported wholesale to a discrete card — REJECTED (translation, not transfer).**
MLX's lesson that "keeping a cache is cheaper than recomputing it" (S-9) is priced in unified memory, where a dormant cache costs only its bytes and never left the pool. On a 6 GB discrete card, resident KV is priced against the weights themselves; retention breadth must scale with the pool, and #3's arithmetic — not UMA instinct — sets it. The parts of the MLX dossier that *do* transfer (budget vocabulary, shedding order, capability declarations) are in #23/#31.

**R15. Per-configuration compiled engine artefacts (classic TensorRT-LLM shape) — REJECTED, on the vendor's own retreat (new in v2).**
Priced in `runners/tensorrt-llm.md` §§2.3–2.4: serialised engines keyed to (model, precision, GPU, shape envelope), with 3–10 minute builds for an 8B-class model (30–60 for 70B-class), shape ceilings that *refuse* rather than slow down, a combinatorial artefact store, and version coupling that can invalidate the store on a library upgrade. The decisive evidence is NVIDIA's own: the PyTorch backend became the stable default in the 1.0 line, and the current migration guide states the TensorRT engine backend **has been removed** — no build step, no conversion scripts, serving is "point the server at a checkpoint" (version caveat in the dossier: pinned stable installs may still ship the deprecated tooling; the documented direction is unambiguous). The personal runner's unit stays the portable model file. What survives of compile-first is already extracted: load-time memory planning (#4/#12) and bounded autotune as a *deletable cache* (#40) — a request larger than the tuned profile runs slower, never fails for being unplanned.

**R16. An NPU compiled-blob path as a product dependency — DEFERRED (new in v2).**
Priced in `runners/lemonade.md` §3, §7.2: on current AMD hardware there are exactly two NPU paths, and both are compiled-blob regimes. FastFlowLM runs whole models on the XDNA2 NPU from Q4NX packages whose kernel binaries (xclbins) are closed, shipped only for officially supported models, and hold an *exclusive NPU lock* while loaded; the Ryzen AI/ONNX path is Windows-only, version-locked to the Ryzen AI release, with historically 2K–4K contexts. The target card (RTX 2060) has no NPU at all, so this is fleet-future work, not build work. The measured value proposition is real but narrow — the only end-to-end comparison on Z13-class hardware (§6.3) shows the NPU ~2.4× *slower* at sustained decode, ~2.3× faster to first token, and nearly contention-free alongside the GPU: a second worker for background-class tasks (summarisation, extraction, transcription), not a faster engine. Reopens when three conditions hold together: the FastFlowLM kernel licence conflict (Open Questions Q16) is resolved from primary text; a fleet machine with an NPU is in the build's scope; and a background-class workload exists that the GPU path serves badly. The bounded form, if it ever reopens, is Lemonade §8.4's: a curated fast path for a small set of small models, GPU path remaining the product.

**R17. Append-only memory stores with retrieval-only honesty — REJECTED (new in v2).**
Priced in `memory/agent-memory-architectures.md` §6.1, §6.6: append-only writing plus similarity retrieval *guarantees* eventual contradiction — truth has a time dimension and similarity does not, so a changed fact's old and new values remain equally eligible for injection forever, and no embedding model, reranker or larger budget fixes a defect that lives in the store's semantics. The honest store is storage semantics purchased at write time: versioned facts with validity intervals, invalidation-not-deletion, tombstones (including a read-time filter, Open Questions Q18), provenance on every record, and approval tiers for writes — assembled in #14's store-side requirement and #8's supersession discipline, in a memory service beside the runner (§7.1 of that dossier). Any design that proposes "just store everything and retrieve better" is re-litigating a proved result.

**R18. Datacentre-width trees as a local default (EAGLE-2's 48–60 draft tokens per pass; SpecInfer widths of 4–5) — REJECTED for this target (new in v3).**
Priced in `papers/specinfer.md` §6a and `papers/eagle-2.md` §6a: acceptance gains flatten hard past width 2–3 (SpecInfer's own table), per-position costs (attention over the accumulated context, KV writes, LM-head/logits per node) are paid from the same bandwidth that makes speculation pay at all, and a 6 GB card at batch 1 sits in spare-capacity terms closer to the papers' loaded regime than their idle one. The narrow, value-ranked form is ranked as #46; the wide form is a datacentre habit transplanted to hardware that cannot afford it. Do not re-litigate widths without Q21's local measurement.

**R19. InfiniGen's rehearsal-prefetch machinery as a first step — DEFERRED behind a transfer-share measurement (new in v3).**
Priced in `papers/infinigen.md` §§5–6: the policy (keep the full cache in RAM; promote per layer only the rehearsal-selected entries; demotion = dropping the GPU copies; selection *ephemeral*, never eviction) is portable, but the machinery is not free — canonical cache home moved to CPU memory with per-token gather over PCIe, a rehearsal pass interleaved into decode, offline SVD skewing of Q/K weights, and attention kernels consuming a gathered subset whose membership changes every token, fighting the paged/block-contiguous layouts the backend relies on. The paper's wins live where transfer is >90% of block time (its FlexGen figure is 96.9%), in long contexts and large batches; a single chat at moderate length on this card is none of those, and the paper offers no batch-1, short-context evidence. What is stolen immediately is the **reversibility principle** — never permanently evict what a cheaper tier can hold; eviction in a tiered runner is demotion, promotion re-decided per use — carried by #43/#48. Reopens when Q23's local transfer-share measurement shows the runner anywhere near the paper's regime; the dossier's own ordering then applies (CacheGen first, InfiniGen second).

**R20. Lossy KV compression inside session snapshots — REJECTED (new in v3).**
Priced in `papers/cachegen.md` §6b: a snapshot is a *resume contract* — the user returns expecting the same session — and CacheGen offers no error bound, only workload-level validation, so a lossy step makes restoration a silent model change whose divergence cannot be detected or bounded after the fact; snapshots are also the substrate for debugging, replay and the corpus's own parity grading, which a lossy snapshot poisons. The pressure that justifies loss in CacheGen (an interactive TTFT deadline on a fluctuating channel) is absent when a restore can take the time the bytes take. The corpus position stands: **bit-exact, no exception argued by anything in the paper.** CacheGen's legitimate role is the pool layer (#43) and, at most, an explicitly separate, labelled lossy fast-restore artefact *derived from* the bit-exact record, so exactness remains recoverable.

**R21. Ebbinghaus decay as a deletion/update rule for personal memory — REJECTED (new in v3).**
Priced in `memory/memorybank.md` §§3.3, 5–6: decay as specified (R = e^(−t/S); S +1 and clock reset on recall; probabilistic forgetting) is destructive and un-auditable by design (no tombstone, no validity interval, no decision to inspect), content-blind (a once-stated standing fact has exactly the survival profile of small talk), and orthogonal to the honesty problem — it acts on age and rehearsal, which are uncorrelated with truth, and can entrench a stale rehearsed fact against its quiet correction. No modern system surveyed keeps it (§5.2 of the dossier), and its authors never ablated it. The ranking form survives as #47; the deletion form does not reopen for any store the user is entitled to rely on. (Distinct from R17: R17 rejects append-only *store semantics*; R21 rejects the *decay updater* — either alone is sufficient to lose facts dishonestly; together they are MemoryBank's whole update story.)

**R22. Multi-level reflection trees as retrievable memory — REJECTED (new in v3).**
Priced in `memory/generative-agents.md` §§3.3, 5.2: reflections retrieved as evidence for further reflections compound fabrication at each level while the citation trail grows too long for any read-time check — the production name for the failure is **summary drift**. No modern system kept the tree as a retrievable object. What survives — and is adopted in #8's v3 note — is reflection **flattened**: one level of consolidation, off the critical path, outputs typed as derived and citing their evidence, invalidated when their sources are (Q25). Do not re-litigate depth without a dependency-tracking design that answers the drift mechanism directly.

**R23. Early-exit retrofits for untrained checkpoints (LayerSkip/SkipDecode-style exits applied to stock models) — REJECTED (new in v4).**
Priced in `papers/layerskip.md` §6 and `papers/skipdecode.md` §§3, 6: LayerSkip's mechanism *is* its training (layer dropout + shared-head early-exit loss); the paper states plainly it "requires finetuning a model or pretraining it with our recipe", and its own baseline columns price the retrofit — untrained mid-depth exit collapses generation quality to near zero. SkipDecode is the policy-side member and its results are likewise **all on models fine-tuned under its schedule**; its 2×–5× figures are average-active-layer compute targets, not wall-clock timings. A runner option that truncates an untrained model at layer E and calls it "early exit" is selling the baseline column as a feature. What is **not** rejected — it is prescribed by both dossiers — is the detect-and-honour posture: record per checkpoint whether it declares early-exit training (exit-competent prefixes, shared head, its E/d dials), honour it faithfully where present, and refuse loudly where absent. Confidence-based *stopping* is a different axis entirely (whole tokens saved by ending a sequence vs layers saved per token) and confers no early-exit credit. LayerSkip's self-speculative form (1.34×–2.16×, full-model quality restored, as-reported) belongs to checkpoints that ship the training, when they arrive — a capability flag at load, beside #23/#28's declarations.


**V5 extension — Mixture-of-Depths joins this rejection (2026-11-15).** Priced in `papers/mixture-of-depths.md` §§3, 5–6: MoD's routers, capacities (12.5% at the winning configuration, routed every other block) and interleaving are **pre-training architecture** — learned jointly with the weights, with no post-hoc conversion of a vanilla checkpoint offered or possible. Bolting a router onto a trained GGUF and skipping ~87.5% of tokens at alternate blocks is structured layer-dropping with a learned-looking gate, and the paper's own stochastic-routing control (drastically worse than both MoD and the vanilla baseline) is the nearest published evidence for what unlearned routing does. The detect-and-honour half is identical in form to this entry's: a checkpoint that *declares* MoD structure (router weights, per-block capacity/interleaving metadata) is served faithfully — expert-choice routing at prefill, the causal predictor/threshold routing at decode (the paper's ~97–99% decision fidelity, as-reported), capacities honoured rather than "improved" — and a runner that runs such a checkpoint densely is not running the model that was evaluated. MoD's one transferable shape is recorded for the from-scratch line, not this build: fixed per-block token budgets with fluid token identity is the conditional-compute formulation whose training-time cost is knowable before the batch is seen.

**R24. An "NSA mode" for dense checkpoints (Native Sparse Attention as a runner retrofit) — REJECTED (new in v4).**
Priced in `papers/native-sparse-attention.md` §§3, 5–6: NSA is an **architecture a model ships with** — compression + selection + window branches with trained MLPs — not a runner feature. Serving an NSA checkpoint through a dense path silently changes its computation; offering an "NSA mode" for a dense GGUF is an untested method wearing its name. The detect-and-honour half stands as in R23: recognise the property from the checkpoint, implement its serving path faithfully, refuse the name where the property is absent. Its headline discipline also enters the corpus's citation law: NSA's **11.6× decode figure is an *expected* speedup** (volume-derived: KV load 65,536 → 5,632 token-equivalents at 64K, its Table 4 headed "Expected Speedup"); its *measured* figures are 9.0× forward / 6.0× backward vs Triton FlashAttention-2 on A100 at 64K, all as-reported — expected figures are quoted only with the word, the derivation, and the measured figures beside them. (Distinct from MInference, which *is* retrofittable by design — prefill-only, zero decode benefit by its own statement; see the companion note at Q28.)

**R25. Run-time OOM→CPU fallback improvised inside the allocator — REJECTED (new in v5).**
Priced in `runners/ggml-backend-internals.md` §7: at v1.0.0 no such fallback exists to inherit. A node runs on CPU because the scheduler assigned it there **before** allocation; a failed device allocation surfaces as a null buffer (converted by the model layer into a thrown, load-aborting error), a false reserve return (converted into a thrown context error), or — in the static bump allocator and the CUDA scratch pools after their one flush-and-retry — a **process abort**. A fork design that plans to "spill to CPU when VRAM runs out mid-load or mid-generation" is planning on a contract the layer below explicitly does not offer, and its first real OOM will discover the abort paths instead. The lawful form is not rejected — it is ranked, as #31's v5 degradation clause fed by #56's dry run: degradation (fewer GPU layers, smaller context, named layers to CPU) decided **at fit time, before load, named and logged as a single-step degradation** in #51's load record, on the model of the one graceful retry the incumbent stack does have (disabling pipeline parallelism and re-reserving once). What is rejected is the improvisation: any code path whose response to a failed reserve is to invent a new placement in the moment.

**R26. Weight-space learned memory as the record substrate for facts about a person — REJECTED (new in v5).**
Priced in `papers/infini-attention.md` §5 and `papers/titans.md` §5, against the standard in `memory/agent-memory-architectures.md`: a superimposed associative matrix (Infini-attention) or a small network whose weights *are* the memory (Titans) fails every clause a record substrate must satisfy, by construction rather than by sloppiness. **Not inspectable** (no operation lists its contents; a binding can only be probed as a blend), **not addressable or pinnable** (no entry exists to exempt — the character anchor has no possible representation inside a state where everything is subject to the same interference and the same learned fade), **not invalidatable** (the delta rule overwrites only when the stream happens to re-present the same key; a correction in different words binds under a different key and *competes* instead of superseding; Titans adds the sharper hazard that the memory is **writable by the input stream itself** — surprising content, adversarial or merely mistaken, is gradient-written with the same authority as the user's own corrections, with no authentication, no review, and no undo), and **not auditable or bi-temporal** (no timestamps, no provenance, no validity intervals, no replay that excludes one episode). The boundary is stated once, for both papers and for any successor of the same shape: **learned compressive memory is a capability substrate — gist, style, skills, the statistical shape of a long document — and is not a record substrate; the moment a fact about a person must be correctable, the memory holding it must be an explicit record, because a superimposed state can be overwritten by accident but can never be corrected on purpose.** What is *not* rejected: serving such architectures faithfully if checkpoints ever ship (detect-and-honour, per R23/R24's posture — Titans additionally requires the runner to specify the learned state's reset/snapshot semantics, since the checkpoint format cannot), and the record-layer steals the wave produced, which are ranked where they belong (#55's write gate; #8's compaction discipline already carries the folded-summary form with its records retained beneath it). Distinct from R17 (append-only *store semantics*) and R21 (the *decay updater*): either of those corrupts an explicit store; this rejection is about stores that were never explicit at all.

**R27. Bounded replay as a session-resume default — DEFERRED behind per-model grading (new in v6).**
Priced in `runners/deepinfer.md` §§5.3, 11.2: replaying a bounded suffix (128 tokens in DeepInfer's design, constant in context and layer count) rebuilds sliding-window state *approximately* at resume. DeepInfer can do this because its model was **trained to tolerate replay error** — the same replay is simulated in post-training — and its technical report still names resumption boundaries an uncharacterised robustness risk. Local models received no such training; on them the approximation's quality cost is unmeasured in any source read. An approximate resume also breaks #10's bit-exact contract (R20) if applied to a session record. Reopens only per model, after #34 raw-oracle grading of resumed-vs-exact sessions at the longest supported context, and even then only as an explicitly disclosed opt-in fast-resume mode (#6 names the reconstruction and the replayed token count in the response) — never as a default.

**R28. "The prefix hash is the only identity state ever needs" as a universal law — REJECTED as stated (new in v6).**
The slogan is the `runners/exllamav3-session-pass.md` headline conclusion, and its own pass refutes the universal form: V3's disk tier is partitioned by a full configuration fingerprint (Q5 of that pass), because a token-only key is safe only inside a singular configuration domain. The second counterexample is already in this ledger: llama.cpp's RAM cache keying on tokens alone can serve KV computed under a different LoRA scale (Q32). The tier-scoped form is adopted instead (#5's v6 note, #10's v6 note): hash within a domain, fingerprint at the disk tier, configuration in the key wherever configurations can coexist. Do not re-litigate the slogan; litigate domain boundaries.

**R29. Caller-side re-render as a substitute for the session layer — REJECTED as a substitute; adopted as the floor (new in v6).**
Priced in `runners/exllamav3-session-pass.md` Q4/Q6 and `runners/tokenspeed.md` §4.6: two production engines hold no session object; the caller re-renders the whole conversation and the hash cache does the remembering. As a *floor* this is sound and is now #1's interim milestone. As a substitute it fails on the programme's founding laws: the caller in V3's own example trims history from the head when it outgrows the cache — the persona-beheading failure (#2) performed by the client, outside the runner's disclosure (#6) entirely; nothing is pinned, nothing is composed after history (#7), nothing persists under a validity envelope (#10); and reuse lasts exactly as long as eviction leaves it (the session pass's own comparison: a returning conversation whose pages were evicted pays replay prefill from the last surviving boundary). A design that adopts the floor *as* the product has re-created stock Ollama's session posture with a better cache. Do not re-litigate without a design that provides pinning, composition, envelope and disclosure from the caller side.

29. **DuoAttention mask agreement and per-policy needle sweeps (new in v5; #54's gate).** No locally derived (layer, KV-head) mask exists for any fleet model, and the paper's derivation conditions (full PyTorch/FlashInfer stack, 2,000 gate-optimisation steps, calibration lengths sampled up to each model's maximum, 128 sinks / 256 recent during optimisation) are not the conditions a GGUF-side derivation would naturally run under — a mask derived under weaker conditions is a different mask, and a wrong one fails silently. *Settle by:* for each candidate family, in order — (i) raw-oracle agreement between the locally derived gates/mask and the paper's published masks where they exist (Llama-2-7B, Llama-3-8B, Mistral-7B), rank agreement reported per layer under #34; (ii) RULER-shaped needle sweeps (depth × length) with the derived policy applied, against the unmodified model — any collapsed depth band invalidates the mask; (iii) a long-document QA spot-check, because passkey-only calibration is exactly the distribution the mask was fitted on. Until a family passes all three, its #54 policy does not ship, and the ≈9,500 / ≈17,900-token figures in #54 remain labelled arithmetic.
30. **The local burst shape: multi-persona and sidecar contention, measured (new in v5; #24/#44's test form).** BurstGPT prices fleet burstiness; FastServe prices fleet queueing; neither measures the desk-scale composite this runner actually serves — a visible turn plus memory-extraction/summarisation sidecars plus a second persona plus rapid regenerations, arriving clustered after long silences, with lengths drawn from a short-turn-dominated mix with a real long tail (the corpus's recorded 14,712-token paste is the tail's local exemplar). *Settle by:* a local load harness in BurstGPT's discipline — clustered (not metronome) arrivals, Zipf-like length mix, failures driven into the test (KV pressure reached, not avoided) — reporting average **and** instantaneous behaviour (worst inter-token gap per session during a burst; shed/refused counts under #31), run against #24's two ordering keys (prefix value alone vs prefix value + attained-service demotion) so the fairness rule is chosen on measurement, not on the fleet papers' authority. Fleet statistics (RPS, Gamma parameters, failure rates) are explicitly not the settling data.
31. **Scratch-pool retention on the fleet's cards, and which pool the RTX 2060 exercises (new in v5; #6's sixth number, priced).** ggml at v1.0.0 selects per device between a legacy pool (best-fit free list, 5% look-ahead, freed blocks retained up to 256 slots, flush-on-OOM) and a VMM pool (one reservation up to 32 GiB, bump allocation, backing never unmapped) — different reuse geometry, different fragmentation behaviour, chosen by a device capability the operator may not know they are exercising (`runners/ggml-backend-internals.md` §5). Neither pool ever returns scratch memory to the driver while the process lives, and the retention is invisible to upstream's own breakdown. *Settle by:* on purplelongship's card, under the pinned backend — which pool is selected; the retained bytes after a representative long generation vs after load; and whether the retention measurably moves #3's shipped configuration (it enters the reserve through Q17's differencing, run post-generation per Q17's v5 note). Until measured, the sixth ledger number is reported as "unmeasured" rather than zero — zero is the one value it is known not to be.

33. **Configuration variation inside a token-only-keyed cache domain (new in v6; #5/#10's tier rule, fork side).** V3's token-only in-process key is safe because its domain is singular; the fork's domain may not be — per-job adapter sets/scales, template variants and cache-precision changes are all configuration axes that could vary inside one process. *Settle by:* enumerating every axis that can vary per job in the fork's design; for each, either prove it cannot coexist with a shared cache domain, partition the domain, or fold it into the key — with a Q32-style two-configuration reproduction (same tokens, two configurations, cache on vs off, graded under #34) for every axis folded in. Until the enumeration exists, the fork keys its own store on the full effective configuration (#10) regardless of tier.
34. **Tokeniser purity under chunked/streamed encoding in the fork's own path (new in v6; #13's v6 note).** V3's v1.6.5 regression proves the failure class exists in a shipped engine: same text, different identifiers, cache silently useless. *Settle by:* a property test over the fork's tokenisation paths — chunked/streamed vs whole-text encoding must agree bit-for-bit over a corpus including CRLF runs, special-token spellings in user text, and length-threshold crossings — run in CI beside #13's rendering checks. If the fork's path never chunks, the test is one line and the question closes cheaply; the question exists because "never chunks" is exactly the kind of assumption the upstream regression falsified for its own authors.
