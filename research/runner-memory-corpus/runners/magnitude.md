## 2. Architecture

### 2.1 Shape of the system

In our own summary of the primary material and the generated codebase summaries (DeepWiki, treated throughout as secondary and cross-checked where possible):

1. **A desktop/CLI product on top.** A desktop app (Electron shell), a web app served by the service itself, and the `magnitude` CLI. The user-facing flow is: assess hardware → browse a catalog whose entries already carry a fit verdict and a speed estimate for *this* machine → download → one-time optimization → load on demand → connect an agent.
2. **A TypeScript control plane.** The ACN owns sessions, configuration and agent state; the ICN owns model catalog, download, residency (which model is loaded), hardware probing, telemetry and the serving endpoints. The two talk over local transports (standard I/O pipes and loopback, per the generated summaries).
3. **A Rust inference engine under `inference/`.** Model-family code, a generation layer (token streaming, draft control, prefix caching), a scheduler, an executor, and the Seismic native runtime. Legacy and experimental trees from the project's short history (earlier Python/MLX and TileLang prototypes and an older Rust stack) are preserved in the monorepo alongside the current engine — a reminder of how young and fast-moving this codebase is.
4. **The Seismic runtime.** Seismic is the native execution layer: device discovery and a validated snapshot of device capabilities, per-backend compilers/executors, memory pools/heaps, and a checked-program pipeline. Kernel operations are declared in a small domain-specific language (files with a `.seismic` extension) that states the mathematics, tensor shapes and scalar types of an operation independently of hardware; backend implementations then bind those declarations to Metal, CUDA, Vulkan or CPU code. The kernel library's declarations, as listed in the generated summaries, cover attention (project / prefill / decode / output, plus the KV history codec below), dense feed-forward rows, recurrent gated-delta blocks, routed mixture-of-experts blocks, and logit readout.

### 2.2 Backends and platforms — verified matrix

From the project's own hardware documentation (updated 2026-11-02, read 2026-11-15) and README:

| Platform | Backends |
|---|---|
| Apple Silicon Mac | Metal GPU acceleration |
| Intel Mac | CPU only |
| Windows x64 | CPU, supported NVIDIA CUDA GPUs, or supported Vulkan GPUs |
| Linux x64 or ARM64 | CPU, supported NVIDIA CUDA GPUs, or supported Vulkan GPUs |

Qualifications that matter, all from the project's own documentation or release notes:

- **CUDA is Ampere-class and newer.** The hardware docs state current CUDA builds target Ampere and newer; older CUDA-capable cards are not automatically supported. No CUDA toolkit install is required — the project acquires the runtime components itself; a supported NVIDIA driver is required. (On macOS there is no NVIDIA path at all in the table above.)
- **AMD and Intel GPUs go through Vulkan only. There is no ROCm backend** — the hardware docs say so explicitly. Vulkan 1.1 or later is the stated floor, with the honest caveat that the version alone does not guarantee a given GPU can run every model; per-model compatibility is a catalog verdict. The generated runtime summary adds that device discovery filters out hardware failing capability floors such as Vulkan subgroup and fused-multiply-add requirements. One generated summary elsewhere says "Vulkan 1.3+" — where the project's own docs and its generated wiki disagree, this dossier follows the docs (1.1) and flags the discrepancy in §11.
- **Integrated GPUs are handled as a real case, not an edge case.** Release 0.2.10 fixed memory planning so integrated GPUs such as AMD Strix Halo use their shared memory as well as the dedicated carve-out; release 0.2.8 made machines whose integrated GPU does not meet requirements (an Intel UHD 770 is the named example) fall back to CPU instead of failing to load; release 0.2.11 made the engine serve on the discrete GPU when a machine has both.
- **CPU is a supported backend, not a fallback error** — x86-64 and ARM64, with per-architecture kernel work still landing (0.2.14: faster quantized GGUF decode on CPU; 0.2.17: new ARM dot-product kernels, §8.4). Whether it is a *competitive* backend is a different question, answered badly by the one independent CPU test in §8.4.
- **Operating-system floors exist.** The installer states macOS 15 or later is required (0.2.12 release notes); a secondary directory's claim that the app needs macOS 26.2 or later could not be verified against a primary source and is not relied on.
- A Docker image is also published (0.2.16) for x64 and ARM64 Linux, reaching NVIDIA GPUs through the NVIDIA Container Toolkit and AMD/Intel GPUs through Vulkan; on a Mac the container cannot reach the Apple GPU. This dossier records that as a distribution fact only.

### 2.3 Design posture: narrow families, deep kernels

Magnitude is explicit that it does **not** try to run everything. The site and launch post both give the same reason in different words: generalist engines pay for breadth with generic kernels, so Magnitude instead writes tunable, highly optimized kernels for the most popular open-weight families and accepts a narrow catalog as the price. The founders' launch post frames the market as three existing trade-offs — datacentre batch engines that sacrifice single-session performance, broad-compatibility engines that sacrifice per-hardware optimization, and hardware/model specialists that lack engine completeness — and positions Magnitude as an attempt to get specialist performance with engine completeness, *for agents on desktops specifically*.

That posture has a concrete consequence for everything below: almost every performance claim is conditional on the model being one the project has written kernels for. A model outside the supported families is not "slower" — it does not run, and since 0.2.11 the product says so in advance, listing models that cannot run with the reason (an architecture without kernels yet, or an unsupported weight type).

## 3. The download-time tuning mechanism — in depth

This is the campaign question for this dossier, so it gets the fullest treatment, with an explicit statement of what each layer of evidence is.

### 3.1 What the project says to users (primary, verified)

The user-facing description is consistent across the README, the site and the FAQ, and is short enough to state completely in paraphrase:

- Kernels are tuned **for each model, when you download it**.
- The tuning spends **up to a minute on the actual chip**.
- What is varied is how the mathematics is split up for the hardware: **how many GPU threads team up on a piece of work, how big a chunk each one takes, and how far ahead data is loaded**.
- The engine **keeps the fastest combination that does not change the model's output**.

The founders' launch post adds the two most important qualifiers, in their own framing:

- Kernels are *written with flexible parameters* and those parameters are tuned on the device before the model runs — the claim is hardware-specific performance without hardware-specific code.
- The current system **tunes a few parameters**. A *full kernel compiler* that automatically chooses how to fuse kernels and which implementations to use is listed as **future work**, alongside expert streaming and multi-device utilization. Any account describing Magnitude as compiling or fusing arbitrary kernels per machine today is describing the roadmap, not the product.

### 3.2 What is actually tuned (mechanism, from the repository's design material as summarized)

The public user documentation does not go deeper than §3.1. The deeper account below comes from the repository's own design documents and tuning code *as summarized by DeepWiki's generated documentation of the repo* (crawled 2026-10-15 to 2026-10-30), which names its source files throughout — principally `design/inference/seismic-compilation.md`, `design/inference/engine/execution-plan.md`, `inference/docs/tuning.md`, `inference/engine/executor/src/native/tuning/mod.rs` and its per-kernel siblings, and `inference/seismic/runtime/src/native/search.rs` / `tune.rs`. This dossier did not read those source files directly; the mechanism is therefore graded **corroborated secondary, consistent with all primary behaviour observed in release notes**, not primary-verified line by line. Where release notes (primary) confirm a piece, that is noted.

Reconstructed mechanism:

1. **An execution plan is resolved before memory is allocated.** When a model is prepared, the engine first builds an immutable numerical execution plan: the enabled components, the exact weight representations, tied storage, the ordered program slots, and service policies. Tuning is part of preparation, before persistent device memory is committed — which is why a model can be *assessed* and *optimized* as distinct steps from being *loaded*.
2. **Operations are backend-neutral entries with declared tuning parameters.** Each native operation is a Seismic declaration bound to a device-specific implementation. A *specialization* carries compile-time constants — the generated summary names block dimensions, tile sizes and vectorization parameters. Entries that declare tuning parameters are candidates for search; entries that do not simply use their canonical defaults.
3. **The search is per tuning point, and the tuning points are per kernel family.** The tuning code is organized by operation family — attention, dense rows, routed (MoE) operations, recurrent blocks, readout, post-norm, short convolution, state-space, allocation and precision each have their own tuning module, with a further per-layer tuning module. In plain terms: the engine does not pick one global "configuration"; it picks configurations for the individual kernel families (and apparently per layer where that pays), for the specific shapes the model will actually serve.
4. **The objective is expected service time, not a single microbenchmark.** The search's cost model, as summarized, sums over all tuning points: each point's *invocation demand* (how often the model will actually call it) multiplied by the candidate's measured execution time, relative to the canonical default. Release 0.2.9 (primary) confirms the prioritization half of this in user language: the one-time optimization "spends its time on the kernels that account for the most measured work, within the existing time budget".
5. **A challenger must win statistically, not just once.** Candidate promotion requires a statistically significant lead over the incumbent across matched rounds, governed by an error-rate parameter (the summary gives α = 0.05 as the example). Timing is described as sustained-clock timing — i.e. measurements taken in a way intended to survive laptop clock behaviour rather than a single cold burst. This matters: naive first-run autotuning on a thermally throttling laptop is measuring the fan curve as much as the kernel, and the design at least names the problem.
6. **Candidates must pass a numerical gate.** A validator compares a candidate's outputs against a reference execution point by point. Floating-point results may deviate only within an allowed number of rounding steps; non-floating-point state must match bit-for-bit. A candidate that is fast but changes the answer beyond the tolerance is rejected. This is the mechanism behind the user-facing promise "keeps the fastest combination that doesn't change the model's output" — with the honest refinement that for floating point, "doesn't change" means "within a declared rounding tolerance", not bit-identical.
7. **The whole search shares one hard budget.** Formation, measurement and selection together share a strict first-load budget, typically **60 seconds of served effort** (see §3.3 for the history that produced that number). Work that does not finish inside the budget keeps its default settings rather than extending the wait.

### 3.3 How long it takes, and what it cost before the cap (primary release history)

The "up to a minute" figure is a *learned* limit, not the original behaviour, and the release record is unusually candid about it:

- **Before 0.2.4**, tuning time scaled inversely with device speed — the slower the machine, the longer it searched. An independent tester running 0.2.3 on a 3-core ARM CPU server (Neoverse N1, no GPU) measured kernel compilation and tuning taking **33–48 minutes on each of three loads** (§8.4). Secondary summaries of the project's own 0.2.4 release notes describe the same failure mode in the project's words: initial loading could take roughly 20–50 minutes on CPU-only machines and appeared to hang.
- **0.2.4 (2026-10-02)** capped initial tuning at about one minute on all devices, with a progress display, and consolidated test-data preparation for large models into a single step; kernels that do not finish within the minute retain defaults. The same secondary summary gives the project's example: initial tuning for Qwen3.5-4B on an M4 Max fell to about 50 seconds. (The summary's "formerly 149 seconds on GPU and 279 seconds on CPU" figures are reported here as reported; the exact comparison basis was not in the primary text read.)
- **Current behaviour is asynchronous and interruptible by design — after a bug taught them why.** Release 0.2.11 notes that a catalog model's one-time optimization waits until the GPU is free, and that loading a model the user actually wants takes priority over it. Release 0.2.16 fixes the failure mode where *using* a model while its optimization was running stopped the optimization partway and left the model permanently on untuned settings: the optimization now finishes, either during that load or later when the device is free, and the UI distinguishes "Optimizing" from "Optimization pending". The same release warns plainly that after that update **each downloaded model optimizes once more**, adding about a minute to its next optimization or first load — i.e. engine updates can and do invalidate previous tuning results.
- The benchmark harness exposes the same lifecycle: the vendor's own reproduction command for its benchmarks passes a `--fresh-tuning` flag, i.e. tuning state is a thing that can be deliberately discarded and redone.

**Cost to the user, stated plainly:** roughly up to a minute of full-tilt local compute per model, per device, per tuning-version — paid once, at download/first-preparation time, in exchange for every later run. For a user who downloads the full 23-model catalog that is on the order of twenty-plus minutes of aggregate tuning spread across downloads, plus a re-tune when an engine update invalidates the cache. There is no monetary cost and, per the privacy position in §3.4, no data leaves the machine to do it. The cost that cannot be capped away is the one 0.2.3 demonstrated: on hardware where a single measurement round is slow, a fixed *wall-clock* budget buys a much *shallower* search — the cap protects the user's time by silently reducing how much tuning a slow machine actually gets.

### 3.4 How results are cached — and whether they are shared

**Caching (corroborated secondary, as in §3.2).** Once tuning completes, the chosen configurations and compiled artifacts are serialized into a persistent **Kernel Cache**. The lookup key, as summarized from the tuning code, is composed of:

- the model manifest's content digest and a tuning version,
- a **device tuning identity** established when the device is opened,
- the implementation digest, the shapes that will be served, and the active comparison strategies.

A later load that hits the cache bypasses the search entirely and instantiates the previously verified ("attested") program groups. This explains three primary-observed behaviours at once: why tuning is described as one-time, why an engine update can force exactly one re-optimization per model (the tuning version / implementation digest in the key changes), and why the benchmark harness needs an explicit fresh-tuning flag to measure the cold path.

**Sharing (negative finding).** No public source read — README, site, documentation, release notes, launch post — describes tuned results being uploaded, shared between users, or downloaded pre-tuned for a popular chip. The project's privacy position points the other way: prompts, files and models stay on the machine, and no internet is needed once a model is downloaded. The honest statement is therefore: **tuning results are a local, per-device cache as far as any public source shows; a cross-user sharing mechanism is unverified — specifically, no evidence for one was found, and the design (a cache key that includes a per-device identity) would make naive sharing of results between machines meaningless anyway**, since the whole point of the key is that the result is only valid for that device identity, that implementation digest and those shapes. The on-disk location and format of the Kernel Cache were likewise not established from primary sources read (§11).

### 3.5 How this compares — ship-time heuristics and runtime autotuning

Three different places to put the search, in our own analysis:

| Approach | When the search happens | Who pays | What it can know | Representative shape |
|---|---|---|---|---|
| **Ship-time heuristics** (llama.cpp / Ollama's ggml kernels, most vendor libraries) | In the vendor's lab, before release | The vendor, once | Generic hardware profiles; must be safe on every machine the binary will ever meet | One binary, hand-tuned defaults and per-architecture code paths chosen by the maintainers; the user's exact chip, driver, memory speed and thermals are invisible to it |
| **Runtime / first-call autotuning** (the pattern used by kernel libraries and compilers that benchmark variants at first use for a given shape) | Lazily, at first invocation of each shape, inside a running process | The user, in latency spikes during real work | The real device and the real shape, but usually one operation at a time and with the process's own lifetime as the cache horizon | Per-operation, per-shape selection; often cached only in memory or in a local compiler cache; no whole-model view of which operations actually dominate |
| **Magnitude: download-time, whole-model tuning** | Once per model, at download / first preparation, before serving | The user, as a bounded (~60 s) up-front wait | The real device, the real model geometry, and — through the invocation-demand cost model — which kernels will dominate *this model's* service time | A bounded, statistically gated, numerically validated search over declared parameters of hand-written kernels, persisted in a device-keyed cache and reused by every later load |

Two honest limits follow from the design itself, and the founders state the first one themselves:

1. **The search space is small by construction.** Today's system tunes parameters of kernels a human already wrote — thread team sizes, chunk/tile sizes, prefetch distance and their per-backend equivalents. It does not invent kernels, choose fusions, or restructure the computation; the founders list exactly that ("a fully custom compiler that automatically chooses how to fuse kernels") as future work. The ceiling of download-time tuning is therefore the ceiling of the hand-written kernel family it parameterizes. This is also why the catalog is narrow: a family without hand-written kernels has nothing to tune.
2. **It is a one-time calibration, not an adaptation.** Except for one runtime-adaptive component (the speculative draft controller, §5.3, which continuously re-decides draft width from measured step times), nothing in the public material describes the tuned configuration being revisited as workloads, drivers or thermal behaviour change. A configuration chosen on a cool, idle, plugged-in laptop is the configuration used on a hot, busy, battery-powered one, until an engine update invalidates the cache. Ship-time heuristics are dumber but workload-independent; runtime autotuners are narrower but can in principle re-decide. Magnitude trades adaptivity for a whole-model view and zero steady-state overhead.

A further comparison the campaign asked for explicitly: **this is not mistral.rs-style load-time quantization, and it is not TVM-style offline compilation either.** Magnitude does not transform the model's weights at download (§6: it downloads a pinned, pre-quantized GGUF variant) and it does not compile a model-specific binary ahead of time on a build farm. What is compiled/tuned on the device is the *execution configuration of a fixed kernel library*, specialized to the device and the model's shapes, then cached. That is a much smaller — and much more shippable — idea than either, which is precisely why §10 finds a reduced form of it stealable.

## 4. Scheduling and batching

Magnitude's workload assumption is stated in the launch post: agent sessions are long, several often run at once, and the user still wants to use the computer. The scheduler is designed for that shape rather than for datacentre throughput.

What could be established:

- **Continuous batching with time-shared prefill and decode.** The generated scheduler summary describes a continuous-batching scheduler coordinating token-bounded, time-shared prefill and decode operations, serialized over a single executor resource domain per engine instance. A strict split is maintained between an event pump / worker (thread confinement, mailboxes, sleeping — no scheduling decisions) and a schedule owner (the unique schedule, request states, round formulation, pipeline phases). This dossier found **no public maximum-concurrency, token-budget or chunk-size defaults** comparable to mistral.rs's published knobs; those numbers are unverified (§11).
- **Requests are durable records, not fire-and-forget calls.** An admitted request's record survives preemption, parking and state migration, and carries its admission time, current timing phase, an accumulated *preemption debt* (priority penalties accrued under load), its prefix-branch divergence points, and its publication stream for token output. Preemption therefore exists as a designed mechanism with a fairness accounting device (the debt), even though no public document read describes the preemption policy in user terms.
- **State changes are transactional.** Modifications to logical KV-cache state and tensor bindings are synchronized with in-flight execution completions through a bindings layer, and a state store manages active, in-flight and retained banks across layouts. In plain terms: the engine is careful, at the design-document level, about not letting a session observe a half-updated cache — the kind of correctness work that only matters once prefix sharing and preemption coexist.
- **Single-flight shared prefill (primary, release notes).** Release 0.2.16 fixed concurrent chats sharing a prompt prefix (the fix names parallel subagents of one agent as the motivating case) in two steps: a request now *waits for another request that is already computing their shared prefix and reuses its result* instead of computing the prefix again, and a shared prefix *stays cached after a batch finishes* so a repetition is fast. The vendor's numbers, as reported in the release notes, with hardware: with a draft model, 8 concurrent requests sharing a 15K-token prompt went from 226 s each to 3.5 s on an NVIDIA A10G; after a batch, 4 concurrent requests on a 13.6K-token prompt went from 12 s to 0.7 s and 8 from 24 s to 1.2 s. These are release-note figures for a pathological duplicate-prefill case, not general concurrency throughput — but the *mechanism* (deduplicating identical in-flight prefill work) is real, named, and independently interesting (§10.5).
- **Independent concurrency picture.** In the independent M1 Max comparison (§8.3), Magnitude's aggregate generation throughput across 2 / 4 / 8 concurrent identical code-generation requests was 56.8 / 72.2 / 133.0 tok/s with median time-to-first-token 0.69 / 1.26 / 3.66 s — aggregate throughput that genuinely scales with concurrency (llama.cpp on the same rig scaled similarly, 42.4 / 78.0 / 122.0 tok/s; Ollama's MLX configuration stayed flat at ~54 tok/s aggregate with time-to-first-token growing by roughly 8–9 s per added stream, indicating largely sequential processing *in that configuration*). Magnitude is therefore a real continuous-batching engine at desktop concurrency levels, not a single-session engine with a queue — while remaining, by design and by evidence, a single-machine, single-device engine: multi-device use is on the founders' roadmap, not in the product.

## 5. KV cache, prefix/session handling, and speculative decoding

### 5.1 Quantized KV: the K8/V4 history codec

- The site states the user-level fact: **quantized KV halves memory per agent**. The launch benchmarks quantify the older form of the same claim as 28% less per-agent memory on Metal and 27% less on CUDA versus llama.cpp at 64K context (§8.1) — a smaller number than "halves", because per-agent memory includes more than the KV cache.
- The kernel library gives the mechanism a name. Its attention declarations include an **affine K8/V4 history codec** (encode/decode operations for the cached history), and the CUDA kernel tree includes a dedicated K8V4 attention-decode kernel file. Read plainly: cached **keys are stored at 8 bits and values at 4 bits**, under an affine (scale/offset) encoding, and the decode attention kernel consumes that representation directly. Against a 16-bit cache that is 12 bits stored per key/value pair instead of 32 — rather better than halving the cache itself, before scales and metadata.
- Secondary reporting of the founders' launch-thread answers adds that the scheme is TurboQuant-inspired and that the team evaluated long-context retrieval (a RULER-based evaluation is named) as not degraded. **This dossier could not verify the TurboQuant/RULER claim from primary text it retrieved** — the launch post itself does not contain it, and the comment thread was not fully retrievable — so it is recorded as *reported, unverified in this pass* (§11). The K8/V4 structure itself rests on the kernel-library source listing, a stronger footing.
- A fairness caveat the founders themselves disclosed (via secondary summaries of the launch thread): in the launch comparison, llama.cpp was run with a 16-bit KV cache because its compressed cache slowed its decode, while Magnitude used its compressed cache. The launch memory and speed comparisons are therefore **not like-for-like in cache precision**, by the vendor's own admission.

### 5.2 Prefix caching: resume states, not just blocks

The founders describe the design as **hybrid paged attention**: ideas borrowed from SGLang-style radix/prefix sharing, with placement optimized for memory adjacency so that single-session performance does not suffer from the sharing machinery. The design-document summary (secondary, as before) fills in the model:

- The prefix cache stores **immutable resume states at the ends of token paths**. A new request resumes from the *deepest* cached state on its own token path. A resume state is more than KV blocks: it includes the numerical sequence-lane states, the encoded features of any media spans straddling the resume position, and the target features a speculative drafter will need for its next rows. That last item is a telling detail — prefix reuse and speculative decoding were designed together, so a resumed session does not lose its drafter warm start.
- Lifecycle: a request's inputs are installed once at admission and released only at request closure; on a residency transition the engine looks up the deepest cached prefix below the resume bound, forks the numerical state, adopts the cached features and sets the generation position; on eviction it releases the numerical states and encoded features **while retaining the inputs**, so a later re-entry can re-condition exactly rather than approximately.
- Hybrid and recurrent architectures are first-class in this design: the kernel and state machinery includes gated-delta / recurrent state (the catalog's Qwen3.5/3.6, Nemotron and Liquid families are hybrid or MoE designs), so a "prefix state" can include recurrent state, not only attention KV. How complete that support is per family could not be verified beyond the design documents' existence (§11).
- Observed behaviour matches the design: in the independent multi-turn test (§8.3), by turn 10 Magnitude served 1,318 of 1,473 input tokens from its prompt cache, with a median time-to-first-token of 0.575 s across the conversation.

### 5.3 Speculative decoding: a drafter paired per model, adapted at runtime

Speculative decoding is not an option in Magnitude; it is part of the catalog contract. The site states each model ships with the fastest speculative decoding drafter, and the catalog tags every model with its method:

- **MTP** — the model's own multi-token-prediction heads (Gemma 4 family, Qwen3.8 Flash Next, others).
- **DFlash / DFlash2** — block-drafting heads (most Qwen3.5/3.6 models, Muse Glimmer, Nemotron Lightning).
- **DSpark** — separate/chained drafters (MiniCPM family, Liquid LFM2.5 8B-A1B / 2.6B).
- **LiLiCorr** — the newest method in the catalog (Nemotron 3.5 Super VL and Bolt; release 0.2.11 describes it as a new drafting method ranked above DFlash2, with a vendor figure for Bolt on a GB10).

Download sizes in the catalog explicitly include the draft model and any vision projector alongside the weights. For custom models (0.2.11), the engine assigns the best drafter known to work with the model — from its own repository or folder, from the matching catalog model, or its built-in MTP heads — and the user can choose a different drafter or none.

The runtime half is **adaptive draft control**: a draft controller decides, per generation round, how many tokens to propose and how many to verify, by evaluating historical acceptance curves against measured launch costs to maximize tokens committed per second; verification rows are aggregated across concurrent requests sharing a physical launch. Release 0.2.11 (primary) confirms the adaptive behaviour in user terms: drafting decides from the time recent steps actually took, so one slow step no longer disables it, and it resumes once it pays off again. §8.3 shows why this adaptivity matters: the same DFlash setup that doubled code generation throughput *reduced* long-context throughput by 7–10% — a fixed draft width would have kept the loss; an adaptive controller at least has the signal to back off.

### 5.4 Session handling

Sessions are the product's centre of gravity: models load on demand when an agent actually needs them and shut down after inactivity (launch post); memory is freed when agents stop (site); short follow-up turns resume from the cached conversation rather than re-rendering/re-processing it (0.2.11 notes a fix for chat templates that scanned the whole conversation per message, after which short follow-ups resume from cache). The built-in chat surface keeps per-model default settings (sampling, system prompt, thinking level, seed, stop sequences) across restarts (0.2.16). None of this is datacentre session management — there is no public multi-tenancy, fairness-between-users or isolation story, because the threat model is one user and their own agents on one machine. Network exposure is treated in §7.

## 6. Memory management and quantization support

### 6.1 Memory: reserve the weights, grow the rest

The launch post states the core policy in one move: Magnitude **reserves only enough memory up front to hold the model weights**; as agent sessions grow, the memory heap dynamically increases, and it frees itself when agents stop — explicitly so the machine remains usable for other work while agents run. The generated design summaries add the machinery underneath:

- A loaded engine owns a **single heap** in the physical memory domain of its device; the runtime measures pool capacities, tracks live usage, charges every allocation before instantiation, and enforces headroom boundaries.
- Two reserve tiers are defined per memory domain (figures from the generated summary of the project's memory design document; not read directly in the design document itself, §11): a *planning reserve* of `max(capacity/10, 2 GiB)` for host RAM and `max(capacity/20, 512 MiB)` for dedicated device memory, and a smaller *emergency reserve* of `max(capacity/20, 1 GiB)` / `max(capacity/40, 256 MiB)` respectively. Residency planning reserves headroom for state *growth*, not just for caches that already exist.
- A platform memory policy watches for **host distress** — sustained swapping, compressed-memory thrashing, or kernel-reported critical pressure — and responds with compaction or eviction. Release 0.2.9 (primary) shows the same policy from the user side: large loads are no longer rejected because of *brief* memory pressure caused by the load itself; protection responds to *sustained* thrashing or swapping. Release 0.2.8 fixes the corresponding failure on 8 GB NVIDIA and AMD GPUs, where several requests after a long prompt could unload the model.
- **Fit is a served-context decision, not a yes/no gate.** Release 0.2.17 (primary): each model is now served at the largest context that fits in memory, from 32K up to its full length, instead of being refused when its full context does not fit; Discover recommends the highest-quality variant that reaches 64K, falling back to 32K; the served context is what chat, the API's model listing and connected agents are told, and an over-long prompt is refused with a `context_length_exceeded` error rather than failing mid-load. The same release line has repeatedly tightened estimate accuracy (counting driver-reserved kernel memory on CUDA; counting only memory the allocator cannot reuse — with the concrete result that models on an 8 GB card previously limited to 32K now get up to their full 128K context). A memory *breakdown* (weights / context / overhead) is exposed in the app and in CLI JSON output.
- The cost of getting this wrong early is also on the record: release 0.2.4 (via its secondary summary) cut the non-weight working memory for Qwen3.5-4B from 3.7 GB to 120 MB and its reserved execution memory from 10.0 GB to 5.9 GB; and the independent CPU test of 0.2.3 (§8.4) found a load plan that demanded 9.9 GB for a 4B model at its fixed maximum context and refused to load under 12 GB and 14 GB limits. Memory planning has visibly been the project's hardest engineering problem — which is itself a finding for §10.

### 6.2 Quantization: selection, not conversion

Magnitude's quantization story is the opposite of mistral.rs's in-situ quantization. **Magnitude does not quantize weights at download.** The catalog pins exact pre-quantized artifacts (the models page states download sizes are the exact files pinned by the catalog's locked Hugging Face commits, weights plus vision projector plus draft model), and the user's choice is *which pinned variant to download*:

- **Catalog variants** are labelled Q4, Q5, Q6, Q8 (with QAT — quantization-aware-trained — variants where the publisher provides them, e.g. Gemma 4 Q4 QAT), plus NVFP4 and NVFP4 QAT for models/hardware that support them, and one 2-bit special (Nemotron 3.5 Bolt's IQ2 QAT, described as 2-bit expert weights sized for 24 GB machines). The models page's own guidance is to take the highest-fidelity variant that fits memory with room for context. The underlying files are GGUF — the benchmark reproduction command names a model as `qwen3.6-35b-a3b:gguf:q4`, and the independent tests confirm catalog downloads are the same GGUF files other engines can read.
- **Loadable GGUF weight types have broadened release by release**, which cuts both ways as evidence (breadth now, immaturity then). Release 0.2.16 (primary): Q1_0, IQ1_S, IQ1_M, IQ2_S and TQ1_0 newly load and run; Q2_K, Q3_K, Q4_1, IQ3_S, IQ4_XS, IQ4_NL and TQ2_0 stopped being expanded at load and stay at their own size (the release gives Q3_K falling from 6.56 to 3.44 bits per weight as stored), with decode speedups for many formats on CUDA and Metal. Release 0.2.10 added IQ2_XXS on every backend. In other words, the aggressive IQ/TQ formats that mistral.rs refuses outright are a supported — if recently supported — part of Magnitude's world, *provided the model family has kernels*.
- **Custom models (0.2.11)** extend the same contract beyond the catalog: any GGUF of a supported family — other quantizations, finetunes, merges, uncensored versions — found on Hugging Face or already on the machine (the Hugging Face cache, LM Studio, the llama.cpp cache, Ollama's store and user-added folders are all searched and used in place, without copying).
- **The KV cache quantization (§5.1) is the only quantization the engine itself performs**, and it is a runtime representation choice, not a weight transformation. There is no public evidence of a user-facing KV-precision knob; K8/V4 appears to be the design, not an option.

## 7. Serving surface

Design-level summary; not an API reference.

- **Forms.** Desktop app, bundled CLI (`magnitude serve` runs the service in the foreground without the desktop window; `magnitude server setup` registers it as a boot service — a systemd unit under a dedicated `magnitude` account on Linux, a LaunchDaemon on macOS; on Windows there is no server-setup mode and the docs direct users to wrap `magnitude serve` with a service wrapper), a web app served by the service itself, and an official Docker image. Only one desktop or foreground instance can run per user account.
- **APIs.** An OpenAI-compatible API at `http://<host>:10100/inference/v1` and an Anthropic-compatible API under `/inference/anthropic` (messages and token-counting endpoints; since 0.2.15 these accept any `anthropic-version` header value or none). Port **10100** is the service port for both the app and the APIs. Default sampling was unified across both APIs in 0.2.11 (temperature 1.0, top_p 0.95, top_k 20, as reported in the release notes).
- **Agent connections.** One-click configuration for Pi, OpenCode, Hermes, OpenClaw, Codex, Claude Code, Oh My Pi and Cline (CLI harness IDs are listed in the CLI reference). Two caveats are documented by the project itself and deserve recording: connecting Codex and Claude Code routes their *hosted* models through Magnitude's local gateway on that computer (so the local service becomes a dependency of cloud requests too, and a remote server's local models are the only ones available to them from another device); and the Claude Code connection rewrites the user's Claude settings to do so (secondary review reporting; the gateway behaviour itself is confirmed in the project's network-access documentation).
- **Network posture.** By default the API is loopback-only with no key required on the same machine. Enabling network access generates an API key, which other devices must send with every request; the connection is **plain HTTP**, and the project's own documentation directs users to a trusted/private network such as Tailscale, an SSH tunnel (documented, with the tunnel bypassing the key requirement), or an HTTPS reverse proxy. A remote-server setup turns network access on itself, creates the key, and opens the firewall port where the platform supports it.
- **Structured output.** Grammar-constrained generation exists: release 0.2.9 improves grammar preparation for structured output and parallel tool calls, and the generation layer's design includes a constraint mechanism (fork / stage / forced-token / vocabulary-mask operations, per the generated summary). Depth of JSON-schema support versus dedicated grammar engines was not established (§11).


## 8. Performance character

All numbers carry their hardware and source. As with mistral.rs, there are two evidence families — the vendor's own benchmarks and independent tests — and here they diverge more than usual, in both directions.

### 8.1 Vendor numbers, launch form: against llama.cpp, no speculative decoding

From the founders' launch post (2026-09-30), the cleanest vendor comparison because speculative decoding is **off** on both sides: Qwen 3.6 35B A3B at 4-bit, 64K context, a prose-repetition workload.

| Hardware | Metric | llama.cpp | Magnitude | Gain |
|---|---|---:|---:|---:|
| Mac M4 Pro, 48 GB (Metal) | Decode | 30 tok/s | 57 tok/s | +92% |
|  | Prefill | 466 tok/s | 507 tok/s | +9% |
|  | Per-agent memory | — | — | 28% less |
| NVIDIA DGX Spark (CUDA) | Decode | 49 tok/s | 58 tok/s | +19% |
|  | Prefill | 2,033 tok/s | 2,507 tok/s | +23% |
|  | Per-agent memory | — | — | 27% less |

Caveats, all from §5.1 and the founders' own disclosures: llama.cpp ran a 16-bit KV cache while Magnitude ran its compressed cache, so neither the memory nor (to an unknown degree) the decode comparison is like-for-like; and the model is the project's showcase MoE, chosen by the vendor.

### 8.2 Vendor numbers, current form: against Ollama, speculative decoding on

The current benchmark page (read 2026-11-15) compares against **Ollama v0.35.1, each engine at its defaults**, averaged over 11 catalog models at about 4-bit, 64K context, **with speculative decoding on for both** (Ollama using the drafter shipped with each tag, Magnitude its catalog drafter):

| Hardware | Prefill speedup (mean) | Decode speedup (mean) |
|---|---:|---:|
| Mac mini, M4 Pro 48 GB, macOS 15.7 — Ollama on its MLX runner (NVFP4 tags) | 1.32× | 2.19× |
| NVIDIA DGX Spark (GB10), 128 GB — Ollama on llama.cpp (GGUF Q4_K_M tags) | 1.34× | 2.17× |

Methodology as the vendor states it: one chat request with about 64K tokens of context (Moby-Dick passages, model asked to repeat the latest) and 256 output tokens, greedy sampling, thinking off, identical prompt for both engines, a fresh engine process and empty prompt cache per request, an idle machine that passed a thermal check, rates from each engine's own timing counters, each result the median of two requests (except some Ollama results that are single requests from an earlier run of the same harness), and averages computed as the arithmetic mean of per-model speedups. The harness is open source in the repository's `inference/` tree.

The vendor's own notes section deserves quoting in paraphrase because it discloses the comparison's weaknesses itself: the engines do not run identical weights, templates or numerics, so outputs differ and answer quality is not scored; on Mac, Ollama's MLX runner drafted very few tokens for three Gemma 4 models at 64K even with its drafter loaded, so those decode gains partly compare speculative decoding against almost none; and the losses are included in the averages — Nemotron 3.5 decode on DGX Spark is **0.76×** (Magnitude slower), Gemma 4 E2B prefill on Mac 0.91×, Gemma 4 26B prefill on DGX Spark 0.96×. Per-model decode extremes (Qwen3.5 4B at 4.84× on DGX Spark, Gemma 4 31B at 3.51× on Mac) are predominantly *drafter* comparisons (DFlash/MTP pairings differ per side), not kernel comparisons. Read correctly, this page supports a claim of roughly **1.3× prefill and 2.2× decode over Ollama's defaults on two high-end machines, under a long-context agent-like workload, with a substantial and undisclosed-in-the-headline fraction of the decode gain coming from speculative-decoding pairing rather than from tuned kernels**. It does not support "2× faster" as a property of the tuning mechanism alone. §8.3 is the control experiment for that.

### 8.3 Independent numbers: M1 Max, identical GGUF, speculation isolated

An independent, fully documented comparison (lilting channel, published 2026-10-27, runs updated 2026-10-28) ran five engines on a MacBook Pro with M1 Max (32-core GPU, 64 GB unified memory, macOS 27.0), all on Qwen3.5-9B at 4-bit, temperature 0, thinking off. Crucially, llama.cpp and Magnitude ran the **identical GGUF file** (UD-Q4_K_XL, the file from Magnitude's own catalog), and the tester isolated Magnitude's base engine by disabling its DFlash drafter (via a renamed clone of the file, recognized as a custom model — itself a small confirmation of the 0.2.11 custom-model path). Magnitude version: **0.2.12**.

**Base engine, no speculative decoding (medians of 5 runs):**

| Workload | llama.cpp prompt / gen (tok/s) | Magnitude prompt / gen (tok/s) | Reading |
|---|---:|---:|---|
| Short Q&A (~140 in) | 348.6 / 36.6 | 333.1 / 41.6 | Prompt slightly slower; generation ~1.14× |
| Code generation (~121 in) | 355.6 / 37.1 | 340.2 / 41.6 | Prompt slightly slower; generation ~1.12× |
| ~8K context summary | 452.3 / 34.0 | 541.3 / 40.3 | Prompt ~1.20×; generation ~1.19× |
| ~27K context summary | 403.2 / 31.4 | 382.4 / 37.5 | Prompt slightly slower; generation ~1.20× |

**With DFlash enabled (Magnitude's default catalog setup), generation versus its own no-drafter base:** code generation 41.6 → 82.6 tok/s (**1.99×**); short Q&A 0.99× (no change); ~8K summary 0.93×; ~27K summary 0.90× — speculative decoding *cost* throughput on both long-context workloads while roughly doubling it on predictable code. llama.cpp's own MTP on the same file showed the same shape (1.62× on code, 1.04× at 27K).

Other results from the same rig: multi-turn chat (§5.2) and concurrency (§4) as already cited; output quality — all engines except one distilled-checkpoint entrant produced syntactically valid code passing the required assertions, Magnitude included.

**Reading:** on hardware one generation older than the vendor's showcase, with weights and drafter controlled, Magnitude's tuned base engine is **about 12–20% faster at generation than llama.cpp and roughly at parity (mixed) at prompt processing**. That is a real, worthwhile lead for a five-month-old engine — and it is an order of magnitude smaller than the headline claim, the difference being drafter pairing, Ollama-default comparisons, and hardware generation. Anyone citing the 2× figure for the *tuning mechanism* is misattributing the drafter's work to the tuner.

### 8.4 Independent numbers: CPU-only, the failure case

The second independent test (Local Model Watch, 2026-10-01) ran Magnitude **0.2.3** against llama.cpp b11223 on a CPU-only ARM server (Neoverse N1, 3 cores, no GPU), both reading the identical catalog file (Qwen3.5-4B UD-Q4_K_XL), five fixed questions, temperature 0, thinking off, streaming:

- Generation: Magnitude **0.24–0.41 tok/s** versus llama.cpp 4.92–6.19 tok/s — about **21× slower** (median); prompt processing 16–38× slower.
- Preparation: every load first compiled and tuned kernels for the CPU, taking **33–48 minutes per load** (the pre-cap behaviour of §3.3).
- Memory/context: Magnitude's context was fixed at the model's maximum (262,144 tokens) and its load plan asked for 9.9 GB; loads under 12 GB and 14 GB memory limits were refused after preparation finished; at 16 GB it loaded with a 12.2 GB peak. llama.cpp ran at a 4,096-token context in this test — an asymmetry the tester states openly, which explains part of the memory gap but not a 21× speed gap.
- Streaming: despite streaming being requested, text arrived all at once at the end of each answer (first text after 9–33 minutes, versus 2–39 seconds for llama.cpp).
- The tester does not recommend Magnitude for CPU-only machines, and notes the results say nothing about Metal or CUDA performance.

Two later vendor data points bear on this without overturning it: 0.2.4 capped the tuning time (§3.3), and 0.2.17's release notes claim new ARM dot-product kernels make Q8_0 prompt processing 4–13× faster and generation 1.4–5× faster than 0.2.16 on ARM CPUs such as Graviton and Ampere (example given: Qwen3.5 4B Q4 on Graviton4, prompts 3.8 → 45 tok/s, generation 3.0 → 14.7 tok/s). **No independent retest of the CPU path after 0.2.3 was found**; the honest status is "CPU was catastrophically slow in the only independent test, the vendor has since shipped targeted CPU kernel work and a tuning-time cap, and the current CPU standing is unverified" (§11).

### 8.5 Credibility assessment — our honest reading

- The vendor is *better than average* at disclosing its own comparison weaknesses (the benchmark page's notes section, the KV-precision disclosure, the release notes' plain-language bug admissions, the "each model optimizes once more" warning). That candour raises the credibility of the numbers it does publish — within their stated conditions.
- The headline "over 2× faster than Ollama" is nevertheless a **defaults-versus-defaults, drafter-included, two-flagship-machines** figure. The controlled independent evidence supports ~1.1–1.2× for the tuned base engine on an M1 Max, a ~2× *additional* drafter effect on predictable code, a drafter *penalty* on long-context work, and a catastrophic CPU result at 0.2.3. Secondary launch coverage also reported testers finding Magnitude slower than alternatives on M5-generation Macs (the founders attribute this to kernels not yet using Metal 4 matrix operations on M5 and newer — reported, and consistent with a hand-written-kernel strategy's known weakness: new silicon features arrive only when a human writes for them) and on at least one RTX 5070 Ti / Gemma configuration. Treat all vendor speed claims as *best-case, per-family, per-chip-generation* claims.
- Release velocity is itself performance evidence of a kind: between 0.2.9 and 0.2.17 (roughly five weeks) the release notes claim, among many fixes, generation improvements from "better kernel tuning and token packing", 13–23% CUDA decode gains for several GGUF formats, a 2.5× gain for one IQ format, and the ARM CPU gains above. An engine improving this fast is an engine whose current numbers — good or bad — have a short half-life. This dossier's performance section should be considered stale within one or two release cycles.

## 9. Strengths and weaknesses

### Strengths

1. **The tuning idea is real, bounded and correctly scoped.** A per-model, per-device, time-capped, statistically gated, numerically validated parameter search with a persistent device-keyed cache (§3) is a coherent mechanism, described consistently from the user FAQ down to the design documents, and its observable side-effects (the one-time optimization step, the re-optimization after updates, the fresh-tuning benchmark flag, the interrupted-optimization bug and its fix) all appear in the primary release record where the design predicts they would.
2. **Agent-workload fit is designed, not marketed into existence.** Single-flight shared prefill, prefix resume states that include drafter state, dynamic heap growth from a weights-only reservation, on-demand load / idle unload, and served-context fitting (§4–§6) are each direct answers to the stated workload: long sessions, parallel subagents, a machine with other jobs.
3. **Speculative decoding as a catalog contract.** Pairing every model with its best-known drafter at download time, sizing downloads to include it, and adapting draft width at runtime from measured step times (§5.3) removes the single largest configuration burden in local inference — and §8.3 shows the drafter, when it fits the workload, is worth more than the kernel tuning.
4. **Quantized KV as a default, not an option.** The K8/V4 cache (§5.1) attacks the resource that actually grows during agent sessions, and it is simply how the engine works rather than a flag users must discover.
5. **Format breadth within the family fence.** GGUF variants from Q1_0/IQ1 through Q8 and NVFP4 load, low-bit formats stay at their own size instead of being expanded, and custom GGUFs of supported families run (§6.2) — broader *weight-type* coverage than several older engines, inside a narrower *architecture* fence.
6. **Documentation and release-note candour.** Hardware floors, the absence of ROCm, the plain-HTTP warning, the benchmark notes section, and bug admissions in release notes are all stated by the project itself. This dossier relied on that candour repeatedly, as it did with mistral.rs.
7. **Hardware assessment before download.** Profiling the machine, estimating per-model speed from measurements of the user's own hardware (0.2.11: replacing a generic bandwidth figure with a one-time background measurement, never run while a model is in use), and giving a fit verdict at a *served* context (§6.1) attack the download-then-discover-it-doesn't-fit loop that defines the Ollama-class experience.

### Weaknesses

1. **The headline number misattributes its own cause.** Most of the marketed 2× decode gain over Ollama is drafter pairing and defaults comparison, not download-time tuning; the controlled base-engine lead is ~1.1–1.2× (§8.3). A user who adopts Magnitude *for the tuning* and runs a workload where the drafter does not pay (long-context summarization, §8.3) can end up slower than the engine they left.
2. **The family fence is absolute.** No kernels, no model — regardless of how popular the GGUF is elsewhere. The catalog is 23 models; entire major families present at launch coverage time are absent from the current catalog, and a custom model is only possible inside a supported family. This is the deliberate price of the kernel strategy (§2.3), but it makes Magnitude a complement to a generalist runner, not a replacement for one.
3. **CPU-only use was, on the only independent evidence, unusable** at 0.2.3 — 21× slower generation, half-hour tuning, refusal to load a 4B model under a 14 GB limit (§8.4). Later vendor CPU work is unretested independently. The README's "or just a CPU" should be read as "runs", not "runs well", until new evidence lands.
4. **Backend holes and generation lag.** No ROCm (AMD on Linux/Windows is Vulkan-only), no pre-Ampere CUDA, no Metal path for NVIDIA-era Macs, and — by the founders' reported own admission — a kernel generation lag on Apple's newest silicon (M5 / Metal 4 matrix operations). Hand-written kernels win per-chip and lose per-chip-*generation*: every new architecture feature is a human's work item.
5. **Memory planning has been the recurring defect class.** The release record is a litany of fit-estimate, over-reservation, unload-under-pressure and optimization-memory bugs (0.2.4, 0.2.8, 0.2.9, 0.2.10, 0.2.11, 0.2.16, 0.2.17 all touch it). The direction is consistently improving and the fixes are candid, but a user on a small-memory machine — exactly the user the fit machinery exists for — is the user most exposed to the remaining defects.
6. **Extreme youth and key-person concentration.** The repository is five months old at dossier date; the current engine is six weeks old; 86 releases in that span means the surface a user installs changes weekly. Release notes are dominated by two author handles. None of this is a criticism of the individuals — it is the standard risk profile of a two-person company at 0.2.x, and any adoption decision should price it in.
7. **Scope beyond inference.** Like mistral.rs's agentic runtime, Magnitude's product includes agent-connection machinery that *rewrites other tools' configuration* and a gateway that hosted-model traffic transits (§7). That is a larger trust and breakage surface than a pure runner carries, and the 0.2.9 release record shows it breaking in practice (a zstd Codex request expanding past a routing limit is the colourful example).
8. **Tuning is a per-model tax that multiplies and expires.** Up to a minute per model per device, again after invalidating updates, and shallower exactly on the slow hardware that needs help most (§3.3). For a one-model agent machine this is nothing; for a user evaluating ten models it is a real friction the generalist engines do not charge.

## 10. Ideas to steal for a Go runner

Written for an improved Ollama-class runner in Go, targeting — as the campaign brief specifies — a **6 GB graphics card**. Each idea states the expected gain and the honest cost/risk. None of this requires copying Magnitude code or text; these are behaviours and contracts, re-implementable from first principles. The section ends with what *not* to steal, because the limits are the most valuable part of this dossier for our fork.

### 10.1 First-run calibration of the knobs we actually have — the stealable core of download-time tuning

**Steal:** the *contract*, shrunk to fit a ggml-based Go runner. Magnitude tunes kernel internals because it owns its kernels; an Ollama fork does not — but it owns a different, smaller set of high-value parameters that are currently either fixed, heuristically defaulted, or left for the user to discover: thread count, prefill batch and micro-batch sizes, flash-attention on/off, KV cache type (per K and V where the backend allows), GPU layer-offload split for models that do not quite fit, memory-map/lock choices, and speculative draft length where a drafter exists. Run a **bounded first-run calibration** per (model digest, quantization, device identity, engine version, context bucket): serve the model with defaults immediately, then — in the background, when the device is free, exactly as Magnitude learned to do — measure a short synthetic prefill+decode workload under a handful of candidate configurations, keep the best under the admission rules of §10.2, and persist the result (§10.3) so every later load starts tuned.

**Expected gain — stated honestly:** not 2×. The knobs available above a compiled kernel library are worth, realistically, **single-digit to ~20%** on decode or prefill for a given model/device pairing, plus occasional large wins where a default is simply wrong for the hardware (a bad offload split on a 6 GB card, or flash attention off on a long-context workload, can each cost far more than 20%). The larger prize is not peak speed but *the elimination of per-user configuration folklore*: "what settings for a 6 GB card?" becomes a measurement the runner makes, not a forum answer the user finds.

**Cost/risk:** each candidate configuration needs memory headroom to test — on a 6 GB card, testing an offload split that does not fit is an out-of-memory event, so candidates must be ordered safest-first and the search must be able to fail a candidate without killing the serving process (a subprocess probe is the obvious shape). Thermal noise on a laptop GPU can pick a worse configuration with confidence unless §10.2 is implemented with it. And the calibration must never block first use: Magnitude's own history (a half-hour tuning hang at 0.2.3; models left silently untuned when optimization was interrupted at 0.2.16) is the cautionary tale, shipped by the inventors of the idea.

### 10.2 Statistical admission and a numerical gate for any autotuned choice

**Steal:** Magnitude's two guardrails verbatim in spirit. (a) A challenger configuration must beat the incumbent by a statistically significant margin across matched rounds — not by winning one timed run — with timing taken under sustained-clock conditions. (b) A configuration that changes outputs beyond a declared tolerance is rejected regardless of speed: run a fixed probe prompt under default and candidate, compare the produced tokens/logits within tolerance, and keep the default on any mismatch.

**Expected gain:** autotuning that cannot silently make users slower or change their model's answers. Without (a), a laptop fan curve becomes a configuration file; without (b), a "faster" KV-cache or attention setting that perturbs numerics ships as a quality regression nobody can reproduce. These two rules are most of why Magnitude's tuning is trustworthy enough to run unattended at download time, and they cost days, not months.

**Cost/risk:** matched-round measurement multiplies calibration time (budget it, §10.1); a token-exactness probe is only valid for configurations expected to be numerically neutral — for genuinely approximate choices (a more aggressive KV quantization), the gate must be a *quality* check with a labelled tolerance, and the UI must say the choice was approximate, as Magnitude's own KV design is a fixed, disclosed approximation rather than a tuned one.

### 10.3 The cache key is the design

**Steal:** the composition of Magnitude's Kernel Cache key (§3.4) for our calibration cache: model manifest digest + tuning/calibration version + **device identity** + implementation (engine build) digest + served shapes/context bucket. Subsequent loads bypass the search; an engine update invalidates exactly the results it should, once, visibly.

**Expected gain:** calibration becomes a durable per-machine asset instead of a per-process ritual, and the invalidation behaviour is predictable enough to document in one sentence ("after an update, each model recalibrates once"). It also prevents the classic autotuning bug — applying a configuration measured on one GPU/driver to another — by construction.

**Cost/risk:** device identity must be stable across reboots but sensitive to driver changes; getting that definition right is the whole job. Cache entries must be small, inspectable and deletable by the user, or the cache becomes undebuggable state.

### 10.4 Spend the budget where the measured work is

**Steal:** the invocation-demand cost model (§3.2, point 4) and its 0.2.9 refinement: order calibration candidates by *(how often this configuration point is exercised) × (its measured time)*, and stop when the budget ends, leaving defaults elsewhere. On a 6 GB card the budget should be much smaller than Magnitude's minute — tens of seconds, backgrounded — which makes prioritization the difference between tuning the one knob that matters and tuning nothing well.

**Expected gain:** most of the achievable calibration win inside a budget a small-machine user will tolerate. **Cost/risk:** requires demand accounting (which knobs dominate *this* model's runtime) before the search — a short profiling pass over the default configuration, which is itself part of the budget.

### 10.5 Single-flight shared prefill for parallel agents

**Steal:** release 0.2.16's mechanism, which needs no kernel work at all and is implementable in the Go scheduler: when a request arrives whose prompt prefix is *currently being prefilled* by another in-flight request, it waits and reuses that computation instead of starting a duplicate; and a shared prefix remains cached after the batch that computed it finishes. Magnitude's vendor figures for the pathological case (8 parallel subagents sharing a 15K prompt: 226 s → 3.5 s per request on an A10G) are vendor figures for a best case — but the mechanism's value for our actual target workload (several subagents of one parent agent, sharing one large system prompt, on one 6 GB card where duplicate prefill also duplicates KV memory) does not depend on the exact multiple.

**Expected gain:** for multi-agent local use, plausibly the largest single win in this dossier — larger than kernel tuning — in both latency and memory. **Cost/risk:** requires prefix identity to be defined exactly (token-level, after templating), in-flight prefill to be a shareable, reference-counted object, and careful behaviour when the first request is cancelled mid-prefill. All scheduler work, no GPU work — which is why it is stealable by a Go runner and the kernel DSL is not.

### 10.6 Serve at the largest context that fits, and show the memory breakdown

**Steal:** 0.2.17's contract (§6.1): never refuse a model because its *maximum* context does not fit; serve it at the largest context that does (with a floor), tell the API and connected agents the served context, refuse over-long prompts with a clear `context_length_exceeded`-style error, and expose a weights / context / overhead memory breakdown in status output. On a 6 GB card this is the difference between "7B at 128K: no" and "7B at 32K: yes, and here is exactly where the 6 GB went".

**Expected gain:** a whole class of small-card failures becomes graceful degradation with a legible reason. **Cost/risk:** fit estimates must count what the driver/allocator actually reserves — Magnitude's release record (§9, weakness 5) shows this estimation is easy to get wrong repeatedly; budget real testing on the smallest supported card, and treat an estimate that says "fits" as a promise the loader must keep.

### 10.7 Smaller thefts worth naming

- **Quantized KV by default, asymmetrically** (K at 8-bit, V at 4-bit, §5.1): on a 6 GB card, per-session KV is the binding constraint on both context and concurrency; an asymmetric cache is the cheapest memory in the whole design. In a ggml runner this maps to existing asymmetric cache-type support where present — verify per backend before promising it.
- **Weights-only reservation with a growing heap** (§6.1): reserve the weights up front, grow session memory as sessions actually grow, free it when they stop, and plan against *sustained* host memory pressure rather than instantaneous pressure. Directly serves "the user is also using this computer".
- **Per-model drafter pairing with runtime-adaptive draft width** (§5.3): pair drafters at download time, then let measured step times — not a fixed draft length — decide how much drafting to attempt, resuming when it pays. §8.3's shape (2× on code, 0.9× on long context) is exactly the signal an adaptive controller exists to exploit.
- **Speed estimates measured on the user's own hardware, once, in the background** (§9, strength 7): a one-time background measurement replacing generic bandwidth arithmetic makes the model browser's estimates — and therefore the user's download decisions — honest.

### 10.8 What not to steal — the honest limits

- **Do not steal the kernel DSL.** Seismic — a checked kernel language, four backend code generators, a hand-written kernel family per model architecture — is a multi-person-year substrate, and it is the reason Magnitude's tuning has something deep to tune. A Go runner that wants Magnitude's *results* must get them from §10.1's shallow knobs, §10.5's scheduler and §10.6's memory contract, and accept the ~1.1–1.2×-class ceiling those imply, not the drafter-assisted 2× headline.
- **Per-device tuning cannot rescue a weak backend.** The CPU evidence (§8.4) is the proof: the same tuning system, on a backend whose base kernels are uncompetitive, produced a result 21× slower than the generalist it claims to beat. Tuning multiplies a base; it does not create one. For our fork, backend/kernel quality (the ggml layer) remains the first-order term.
- **Tuning assumes a stable, dedicated device.** A configuration measured on an idle, cool, plugged-in machine is served on a hot, shared, throttled one. Magnitude mitigates measurement noise (§10.2) but does not re-tune as conditions change; on a 6 GB laptop card shared with a desktop compositor, expect calibration gains to be at the low end of the range in §10.1, and design the admission gate to prefer the default whenever the measurement is ambiguous.
- **The family fence does not transfer.** Magnitude can afford hand-written kernels per family because it *refuses* the long tail. An Ollama-class runner's core promise is the opposite — any GGUF runs. Stealing the fence would break the product; stealing the *honesty* of the fence (saying in advance, per model, what is optimized, what merely runs, and what cannot run, with the reason) costs nothing and is worth taking wholesale.
