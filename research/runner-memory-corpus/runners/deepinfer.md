## Essence

DeepInfer is the opposite experiment from every general runner in this corpus. vLLM, SGLang and Ollama all begin from *any model, any user* and pay for that generality in abstraction: a model registry, a generic KV layout, kernels chosen at runtime for an architecture they met at load time. DeepInfer begins from **one model, one operator, one traffic shape** — DeepSeek serving its own DeepSeek-V4.1-Flash to its own users, in its own datacentres — and removes every layer of generality that does not pay for itself at that scale. The model and the runner were designed together: the model's attention shares KV cache entries *across layers* so the cache is small enough to persist on SSD for days; its sliding-window state is deliberately *not* persisted, because the runner can rebuild an approximation of it by replaying a bounded suffix; its experts are stored in a 4-bit format the training run was quantisation-aware-trained to tolerate; its speculative drafter carries a confidence head whose only job is to tell the *scheduler* how much verification compute each draft token deserves. None of those are runner features that happen to suit a model, or model features that happen to suit a runner. They are one design, cut in half at the API boundary for publication.

That is also why the open release must be read as **two objects, not one**, and this dossier keeps them separate throughout:

1. **The shipped engine** — an offline (batch, in-process Python `LLM`-class) inference engine for exactly one checkpoint, on exactly two accelerator families (NVIDIA SM100, Huawei Ascend 950), carrying the kernels, the parallelism, the speculative decoder, the asynchronous scheduler and the structured-output machinery. There is no HTTP server in the release; the public surface is a script you run.
2. **The production system it was extracted from** — a disaggregated vision-encoder / prefill / decode fleet with dedicated KV-storage nodes, four load balancers and a ~100 PiB SSD cache tier, described in unusual detail in the repo's deployment Q&A and the model's technical report, but **explicitly not included**: the README lists a KV cache system, VE/prefill/decode disaggregation and cross-replica load balancing as "required for a complete inference service (not included in this release)", and the Q&A adds that those components are tightly coupled to DeepSeek's internal infrastructure and not yet fully open-sourced.

DeepSeek's own summary numbers for object 2, reported as reported in §9, are a single cluster serving 155 trillion tokens a day. The honest summary of object 1 is narrower and more interesting: it is the first time a frontier lab has published the actual engine room of its flagship serving stack — with the factory walls, conveyor belts and warehouse left behind, and a candid map of where they stood.

## 2. Architecture in our own words

### 2.1 The shipped engine (object 1)

The repository's shape follows its vLLM ancestry (the README's acknowledgements state DeepInfer was originally built primarily on vLLM, with additional inspiration from SGLang and TensorRT-LLM), specialised hard in one direction:

- **One model implementation.** The engine package (`deepinfer/`) is organised as a recognisable modern serving engine — `engine`, `model_executor`, `worker`, `distributed`, `entrypoints`, `structure_output`, a vision-encoder package (`ve/`), platform abstraction (`platform.py`, `npu_ops/`) — but the model surface is a single architecture class, `DeepseekV41ForCausalLM`. There is no model registry to speak of; configuration flows from the checkpoint's own `config.json`.
- **Offline entry point only.** The documented use is a Python program that constructs the engine (the examples pass expert-parallel size, data-parallel size, context-parallel size, a batched-token budget of 32,768, a sequence cap, and a GPU-memory-utilisation fraction of 0.85) and calls a generate method over a batch of prompts, with optional multimodal inputs and structured-output checks. Evaluation harnesses in `eval/` (AIME, HLE, GPQA) are built on the same batch API in two stages — generate everything to disk, then score — which tells you who the release is *for*: operators benchmarking a deployment, not application developers embedding a chatbot.
- **The tokeniser is not in this repo.** Prompt construction for the real API protocols lives in the companion **deepseek-recipe** project (Rust libraries with Python bindings, MIT): it converts Chat Completions, Responses and Messages requests into one internal conversation form, renders the V4/V4.1 prompt, encodes it, and parses streamed output back into each protocol. DeepInfer's own checkpoint ships a self-contained Python reference encoder, and the Q&A describes recipe's two load-bearing tricks: encoding is segmented at known special-token boundaries so the segments can be encoded in parallel (a long-context latency cut), and user-supplied text that merely *spells* a special token is encoded as ordinary tokens — special-token injection is prevented by construction, not by filtering. The two repos are released side by side and, notably, not wired together: recipe explicitly leaves inference, tool execution and HTTP transport to the caller.
- **Two hardware backends, one engine.** The build is selected by an accelerator environment switch (`nvidia` / `ascend`); prerequisites are Linux, GCC ≥ 13, Python 3.12, and CUDA 13 or CANN 9.2 respectively. Feature parity is not total: batch-invariant inference and deterministic sampling are documented as NVIDIA-only (§4.3).

### 2.2 The model the engine is cut around (from the checkpoint config + technical report)

Everything in §3 follows from these facts, all verified against the checkpoint's `config.json` and the technical report:

- **Causal Encoder-Decoder (CED), 40 layers.** The stack is split into a 20-layer causal *encoder* and a 20-layer *decoder*. For global attention, the decoder does not build its own per-layer KV from its own hidden states: its global KV is *projected from the final encoder layer's hidden states*, with per-decoder-layer projection weights. Prefill therefore runs only the encoder half for global-attention purposes — the report's accounting is that prefill complexity falls from roughly O(N·L) to O(N·L/2) plus a bounded sliding-window term, and the model **activates ~8B parameters per token in prefill against ~16B in decode**. The design target is stated plainly: agentic workloads are input-heavy, tool calls keep triggering fresh prefill, so reading must be cheaper than writing.
- **Compressed Sparse Attention 2 (CSA2).** Every layer except the first two (sliding-window only) combines a local sliding-window branch (window 128) with a global sparse branch. Global KV is produced by compressing the sequence (encoder layers compress 2-to-1; decoder layers use ratio 1, i.e. uncompressed entries, per the report's setup section and the config's per-layer ratio list), scored by a lightweight indexer (32 indexer heads, head dimension 128) that selects **Top-512** entries per query. The V4.1 change — the one the report's title is about — is *cross-layer* reuse, with each layer statically assigned one of three modes: **Full** (compute own global KV, project indexer keys from it, run the indexer), **Reindex** (reuse a preceding layer's global KV and indexer keys, but rescore with its own indexer query and pick fresh Top-K), **Reuse** (reuse both the KV and the Top-K selection; no indexer work at all). The config names only four KV-source layers and eight index-source layers across the whole 40-layer stack — the sharing is aggressive, not decorative. In the decoder, a **Hierarchical Sparse Indexer** further bounds cost: the first Full-mode decoder layer also scores blocks (8 positions each), keeps the best **2,048 blocks** as a candidate pool (up to 16,384 positions), and every later indexer searches only inside that pool — per-query indexing cost for deeper layers becomes constant in context length instead of linear.
- **Scale.** 552B backbone parameters plus 196B Engram parameters (see §6.3); hidden size 5,120; 64 query heads sharing **1 KV head** of dimension 512; native context **1,048,576 tokens** (YaRN-extended RoPE in the config). MoE in every block: **1 shared + 384 routed experts**, intermediate size 2,304, **6 routed experts active per token**, auxiliary-loss-free routing with separate correction biases per modality (text vs image tokens route-balance separately).
- **The cache number.** Global KV is held in a 4-bit format (§7.3). Combined with cross-layer sharing, the report puts the global KV footprint at **890 bytes per token in HBM** — about a quarter of V4-Flash's 3,514, and the report's generational chart claims ~437× below the original DeepSeek-V1 design. A full million-token context's global cache is therefore under a gigabyte; the report further notes decode FLOPs per token stay nearly flat with context (a 256× context growth, 4K→1M, raises single-token decode FLOPs by only about a quarter).
- **Vision.** A 32-layer vision encoder (hidden 1,024, patch 14) with 3×3 pixel-unshuffle downsampling, feeding embeddings into the language backbone at image-token positions; the model is multimodal from pre-training, not bolted on.

### 2.3 The production system (object 2, described, not shipped)

The Q&A's reference architecture is a three-stage disaggregation plus storage: **vision-encoder instances** (one GPU each; cheaper GPUs recommended), **prefill instances** on ordinary 8-GPU machines, **decode instances** on 64–128-GPU supernodes, and **dedicated KV-storage nodes** (§5), with a load balancer per stage plus a fourth for expert parallelism (§4.4), an entrypoint that performs cache matching, and recipe in front for protocol conversion. Attention runs data-parallel with the DP degree equal to the EP degree, as in DeepSeek's earlier V3/R1 system. §4–§6 detail the three stages' very different parallelism doctrines; the point here is structural: *the shipped engine is the code that runs inside each of those instance types*, and the Q&A says most of the engine functionality disaggregation needs is already implemented in it — what stayed home is the coordination and storage layer around it.

## 3. The design centre: what a single-model production framework does differently

This section is the dossier's reason to exist. A general runner and DeepInfer solve the same equation — tokens out per dollar — with opposite unknowns. The general runner fixes the *runner* and treats the model as data. DeepInfer fixes *one model, one operator and one workload*, and treats everything else — including the model's own architecture — as a variable. Five consequences follow, each visible in the sources.

### 3.1 The model's architecture is a serving decision

CED (§2.2) exists because DeepSeek's production traffic is input-heavy agent work. A general lab ships a decoder-only model and lets a thousand runners cope; DeepSeek reshaped the model so that the expensive half of the network is skipped during the phase its traffic performs most. The same logic runs through CSA2: cross-layer KV sharing is not an inference trick a runner can apply to an arbitrary checkpoint — the layers were *trained* to read each other's cache entries and selections, the hierarchical candidate restriction is applied identically in training and inference, and the approximate state reconstruction of §5.3 is *simulated during post-training* so the model learns to tolerate it. **The transferable observation is about where the boundary sits:** in a co-designed stack, "model quality vs cache size" is one trade made once, by one team, with training in the loop. In a general runner the same trade reappears as quantisation and eviction heuristics applied to a model that never consented to them — which is why our corpus grades every lossy cache idea against a raw oracle (IDEA-LEDGER #34) while DeepSeek can simply train through its approximations and report the result as the model's quality.

### 3.2 Quantisation choices are baked in at training, not negotiated at load

The checkpoint's quantisation config is part of the model, not a serving flag: dense weights in FP8 (dynamic activation scheme, 32×32 weight blocks, ue8m0 scales), routed-expert weights in FP4, the main KV cache itself in an FP4 variant (E2M1 values, one E4M3 scale per 16 channels, NVFP4-like but with the second-level global scale deliberately omitted — the report argues the cache's magnitude bound makes the global scale dead weight), indexer keys in MXFP4. Crucially, the report states the FP4 main-KV format was enabled by **quantisation-aware training during post-training**: the model was taught to live with a 4-bit cache. A general runner choosing KV precision at load time (#3 in our ledger, q8_0-by-default) is making a unilateral approximation; DeepInfer's precision *is* the model's native precision. The runner-side corollary is narrow but real (§10.4): per-model, per-tensor precision belongs in the model's own metadata, carried with the checkpoint, not in a runner-wide default the user must tune.

### 3.3 The scheduler and the drafter were designed as one mechanism

Speculative decoding in general runners is a bolt-on: a fixed draft length, a generic acceptance test. DeepInfer's DSpark drafter (three Transformer blocks, sliding window 128, a Markov head modelling dependencies among draft positions, block size 5) carries a **confidence head** whose output — a predicted per-position acceptance probability — is consumed by the *scheduler*, which combines it with a profiled throughput curve of the actual hardware to choose, per request, how many of the 5 draft tokens are worth verifying (§8.2). Drafting, confidence estimation and verification budgeting are one design spanning the model file and the engine loop. No general runner can retrofit the confidence head onto a model that does not have one; what transfers is the *budgeting rule* (§10.3).

### 3.4 Parallelism doctrine is per-phase, per-model, and empirical

§4.4 gives the details; the principle belongs here. Prefill uses the *smallest* expert/data-parallel group that fits in HBM (EP2–8); decode uses the *largest* the hardware allows (EP64–128, "Wide-EP"); tensor parallelism is not used at all in production, and context parallelism — though the shipped engine supports a balanced-CP mode and the examples expose it — is *not used* in the production deployment, on measured grounds the Q&A states (up to ~5% slower end-to-end in their measurements, worse expert-load balance, extra overhead; tail latency is acceptable without it because the model is fast enough on a full cache miss). A general runner offers TP/PP/EP as user knobs because it cannot know; DeepInfer's operators *measured their one model on their two node shapes* and deleted the knobs that lost. The doctrine is: parallelism is a benchmark result, not a configuration surface.

### 3.5 Determinism is a feature, because there is exactly one operator to please

The engine offers batch-invariant inference (results identical regardless of batch composition) and, combined with a fixed per-sequence seed and variable-length speculative verification disabled, deterministic sampling — both NVIDIA-only. In a general runner, batch-dependent floating-point variation is accepted as weather. For a single operator running evaluations, regression baselines and RL rollouts on the same engine that serves production, reproducibility is worth real throughput, and the repo's own test suite leans on it: offline runs are validated by comparing decode perplexity *exactly*, sample by sample, against stored baselines per platform and workload. §10.5 takes the local version of this lesson.

## 4. Scheduling & batching

### 4.1 Asynchronous (zero-overhead) scheduling — shipped

The engine's scheduler overlaps its own CPU work with device execution, enabled by default. The Q&A's account, in our words: a naive decode step serialises as *schedule → forward → sample → post-process*, with a host/device synchronisation before post-processing, so the accelerator idles through post-processing of step N and scheduling of step N+1. DeepInfer pipelines it in the manner it credits to SGLang and NanoFlow: while the device runs step N's forward and sampling, the host concurrently schedules step N+1, launches its forward, post-processes step N−1, and launches step N+1's sampling — the device is never waiting on Python. This is the same overlap principle as SGLang's zero-overhead scheduler arriving in a second production codebase, which matters for §10: it is now a convergent, twice-shipped design, not one project's idiosyncrasy.

### 4.2 Prefill scheduling inside one engine: a time budget, solved per step

The most distinctive scheduler detail in the Q&A is on the prefill side (described for the production system; the engine-side chunk budget it operates is visible in the examples as a 32,768-token batched-token cap):

- Requests are dequeued FIFO on each GPU, but the *chunk size is not fixed*. Each prefill step is given a **time budget** (a nanosecond compute quota), and a fitted **quadratic cost model** — cost as a function of the chunk's token count and of the prefix length already computed for that sequence — is *solved* for the largest chunk that fits both the time budget and the 32,768-token ceiling. The budget is then tightened by a minimum-reduction across the data-parallel group so all ranks step together.
- One level up, prefill capacity is managed in **compute quotas**: requests are bucketed into four context-length tiers (<16K, 16–64K, 64–256K, ≥256K), the number of engines serving each tier is redistributed dynamically by each tier's share of quota demand in the previous round, and each tier carries its own per-batch quota cap. Within a data-parallel group, an arriving batch's requests go to the rank with the lowest current quota load.
- Prefill engines **pull** work rather than being pushed it: an engine fetches its next batch when the remaining time in its current step is just enough to prepare that batch, so fetching and preparation hide under computation and the next step starts the moment the current one ends.

The contrast with the corpus's chunked-prefill canon (Sarathi / FastGen, IDEA-LEDGER #18) is instructive: there the budget is a *token count*, chosen at the saturation knee. DeepInfer budgets *time*, and derives the token count per step from a measured cost model that knows a token at prefix-length 200K costs more than a token at 2K. §10.2 grades the transfer.

### 4.3 Batch invariance and deterministic sampling — shipped, NVIDIA-only

Two related guarantees, both gated behind the same environment switch in the README's configuration notes, both documented as NVIDIA-only: **batch-invariant inference** (a request's results do not depend on which other requests share its batch) and **deterministic sampling** (identical inputs and sampling parameters reproduce identical outputs, given a fixed per-sequence seed and variable-length verification turned off). Their cost is not stated in the sources read; their existence is the finding (§3.5).

### 4.4 Load balancing and autoscaling — production system only, not shipped

Because the balancers are among the withheld components, everything here is DeepSeek's *description* of its internal system, from the Q&A — valuable as design record, unusable as code, and labelled accordingly wherever §10 draws on it.

- **Expert-parallel load balancing (EPLB).** Each GPU additionally hosts replicas of hot experts ("redundant experts"). Expert loads are collected over a statistics window; periodically, experts are reassigned across GPUs from those statistics, with weights shuffled inside the group over NVLink symmetric memory. Reported settings differ by phase: prefill starts from 4 redundant experts per GPU, a 100-step window and reassignment every 1,000 steps (reported imbalance ratio, slowest rank over mean: 1.074 at EP4/DP4, 1.045 at EP2/DP2); decode starts from 1 redundant expert per GPU (which rounds out to 7 experts per GPU at EP64, excluding the shared expert), a 1,000-step window and reassignment every 10,000 steps (reported ratio 1.090).
- **Decode load balancing.** Requests are dispatched (pushed, not pulled — a request, once placed, stays on its decode engine until it finishes, so placement needs the global view prefill can do without). The balancer tracks two quantities per engine — live request count (which sets per-step batch size) and total resident KV length (which sets attention cost) — and routes to pull both toward their fleet averages, with the stated heuristic of sending short requests toward engines with low concurrency but large total KV, and long requests toward engines with small total KV.
- **Vision-encoder load balancing.** Coarsest of the three: a prefill machine picks a vision-encoder machine at random; within it, the image goes to the GPU processing the fewest image patches, counted directly from image dimensions.
- **Net effect, as reported:** the balanced system reaches roughly **80% of a perfectly balanced offline benchmark** — a vendor-reported figure, and a usefully un-round one.
- **Autoscaling & failure.** Prefill capacity is driven by non-cached token volume; decode capacity by running-request count; adjustments are rate-limited and clamped. Headroom is policy, not accident: spare ready machines are held in the pool, and scale-in is forbidden while quota utilisation exceeds 0.8. A decode engine told to shut down gets a one-minute grace period, after which unfinished requests *and their KV* are forwarded in one shot to other decode engines to continue. Engine restarts take minutes; resilience comes from quota redundancy plus request-level rerouting, not from fast restarts. In a wide-EP instance all GPUs form one communication domain, so one failed GPU kills the instance; on restart the platform simply re-derives the EP size from however many healthy GPUs it is actually given.

### 4.5 What the shipped engine does not schedule

There is no online request queue in the release at all: the offline API submits a batch and drains it. Continuous batching across arriving online requests, admission control and SLO management live in the withheld layer. Anyone evaluating DeepInfer as a "vLLM replacement" is comparing an engine core against a serving system — the README's scope statement says as much, and §9's production numbers must not be read as properties of the downloadable code.

## 5. KV-cache design — and what "not included" actually means

### 5.1 Three different caches, three different homes

The production design separates KV state by *reuse horizon*, and the separation is the design. From the Q&A's storage table and the technical report's inference-system section:

| State | Where it lives | Lifetime / policy | Managed by |
|---|---|---|---|
| In-flight block KV + sequence state KV | Accelerator HBM | Life of the request | Prefill / decode instances |
| Sliding-window (SWA) KV | **Local host memory** of the producing machine (a distributed pool carved from ~10% of each machine's DRAM, per the report) | Minutes; single copy; nothing on the storage cluster | Prefill / decode instances; cross-machine hits pull over a 400G VLAN via an in-memory directory partitioned across entrypoint machines |
| Paged block KV (main KV + indexer keys) | **Dedicated 3FS storage cluster** (SSD) | Days: TTL 3 days for agent traffic, 7 days for chatbot traffic; LRU reclamation by the filesystem's GC workers under a disk watermark | A `kvcache-store` component (not shipped) |

Sizing, as reported: roughly **100 PiB** of SSD serves as the cache store; a standard storage server carries 20 × 30.73 TB SSDs with at least 40 GB/s read and 5 GB/s write throughput and enough capacity to retain 24 hours of data; logical cache capacity works out to about **14.4 TB per online GPU**. The storage system (DeepSeek's 3FS) uses 10+2 erasure coding — a read fans out to all storage nodes in the group and completes from any 10 responses — so the cache tier carries no application-level replication of its own.

### 5.2 Why a dedicated store, and not tiered local disks

The Q&A gives the reasoning explicitly, and it inverts the fleet-orchestration corpus's default assumption (Dynamo-style tiering demotes blocks through each node's own RAM and SSD):

- **Any prefill machine can hit any prefix.** Because the block cache is centralised, routing does not need prefix affinity: the prefill load balancer (§4.2) is free to balance purely on compute quota, since a cache hit costs the same fetch regardless of which engine serves the request. Local tiering would couple the routing policy to cache placement; the dedicated store decouples them.
- **Storage scales independently of compute**, and survives it: compute nodes fail at more than an order of magnitude higher rate than storage nodes, and a node's death does not take its share of the fleet's cached prefixes with it.
- **The hit economics justify the hardware.** Retention is set from measured reuse intervals: the report and Q&A agree that ~72 hours captures almost all reusable agent-traffic cache (and conveniently spans a weekend), while chatbot traffic's heavier long tail justifies 7 days — costed honestly: shortening chatbot TTL to ~3 days would cost an estimated 0.5–1% of hit rate. SSD capacity is cheap; recompute is not. (A CXL-based memory-semantic L2 was considered and set aside in the Q&A: with V4.1's cache this small, reads already overlap queueing and compute, so latency gains would be limited; the one open benefit would be reduced SSD write wear.)

### 5.3 The hit path, and bounded replay — the mechanism that makes the split affordable

A cache hit is not free, and the Q&A prices its stages: **matching** runs at the entrypoint against a local store replica, as a hash-chain prefix match over metadata only — but the hit length must be known *before* routing, so this step cannot be hidden. **Fetching** runs asynchronously in a separate process, moving blocks from the storage cluster into host shared memory. **Swap-in** from shared memory to HBM runs on a thread inside the engine, overlapping per-layer host-to-device transfer with forward computation; because the CUDA copy engine performs poorly on fine-grained block copies, swap-in is done with GPU-direct RDMA — the NIC saturates PCIe bandwidth without consuming streaming multiprocessors.

The subtle part is what a hit *means* when the SWA state is not in the persistent store at all:

- **The block cache alone determines hit length.** The maximum reusable prefix for an input of length L is capped at L − 134 (the 128-token window plus 6 tokens of speculative backtracking headroom). The block lookup yields a hit length L1 at 128-token block granularity; the SWA directory is then consulted, and if no SWA state exists near the boundary, the hit backs off by exactly one block (128 tokens) and that block is recomputed.
- **Bounded replay rebuilds the missing window state at constant cost.** Exactly reconstructing L layers of sliding-window state would require replaying L × 128 tokens (for the decoder under CED, 2,560 tokens through 20 layers). Instead the engine replays only the **last 128 tokens**, with attention truncated to the replayed segment, producing an *approximate* SWA state whose cost is constant in both context length and layer count. Two uses: *encoder* replay, when a block-cache hit arrives without its SWA state (the replayed tokens regenerate only SWA state; the cached global KV is reused untouched); and *decoder* replay at every prefill (decoder SWA state is never cached; replaying 128 tokens instead of 2,560 nearly halves total prefill compute in the Q&A's accounting, and the reconstructed state is used for decoding only, never written into the prefix cache).
- **The approximation is trained for, and its limits are stated.** The technical report is explicit that replayed state is not mathematically identical to exact state, that suffix computation therefore depends slightly on where the cache hit landed, and that the same replay is simulated in post-training so the model adapts to it; the report's limitations section names CSA2 selection errors and SWA reconstruction at cache-resumption boundaries as robustness boundaries not yet fully characterised. This honesty is part of the design record: bounded replay is a *model* feature with a known failure surface, not a runner hack.
- **Persistence details.** SWA state that *is* kept in host memory is stored per sequence in a fixed-size slot, only at positions that are multiples of 128 tokens, covering the first 20 layers — the Q&A's arithmetic is 20 layers × 134 tokens × 528 bytes (the MXFP8 SWA format) ≈ **1.42 MB per sequence**. Block KV written during decode uses a write-back policy; write failures are silent to the engine, and correctness is instead enforced by strict validation on read. Cache reuse is keyed by a **validity tuple** — deployment configuration, model weights, user group — and changes to weights, block byte layout, tokeniser, or any framework change that alters KV values all invalidate reuse; DeepSeek reports it has never performed a cache-format migration in production.

### 5.4 So what does "not included" mean, precisely?

The open release ships **no** persistent KV system: no 3FS store, no `kvcache-store`, no entrypoint matcher, no SWA directory, no swap-in path to a remote tier. What the engine has is the in-HBM block/state management needed to run a batch, plus — per the README's parenthetical — most of the engine-side functionality disaggregation requires. The practical consequences:

- **You cannot reproduce the production hit rates, TTFT, or economics from the release.** The 72-hour prefix reuse that the whole model architecture (CED, CSA2, FP4 cache, bounded replay) was shaped to exploit lives in the withheld tier. The downloadable engine running a multi-turn workload recomputes what production would have fetched.
- **What DeepInfer assumes from its surrounding stack** is therefore the real specification, and the Q&A states it: a prefix-addressable block store with hash-chain matching, asynchronous fetch into host shared memory, RDMA swap-in overlapped per layer, a host-memory SWA pool with a cross-machine directory, and validity keyed to deployment configuration. A third party re-implementing the service must build all of that — the release is the engine *inside* the prefill/decode/vision services in the reference diagram, not the diagram.
- For this corpus the gap is itself the datum (§10.6): the part DeepSeek kept is the part whose value is *operational* (a decade of traffic statistics, failure behaviour and infrastructure coupling), while the part it gave away is the part whose value is *reproducible* (kernels, scheduling, model-serving mechanics).

## 6. Memory management

### 6.1 Inside one engine instance

The offline examples expose the conventional knobs — a GPU-memory-utilisation fraction (0.85 in the sample), a batched-token budget, a sequence cap — over a paged block cache (the Q&A confirms the prefill side also uses paged KV). Beyond that, the shipped engine's memory story is dominated by the model's own footprint decisions (§2.2, §7.3): with global KV at 890 B/token, HBM pressure at production context lengths comes from *weights and experts*, not cache — which is precisely why decode doctrine (§4.4) spends its effort on expert placement rather than cache eviction, and why the Q&A can state that decode is not bound by cache capacity and does not offload KV during decode (decode still *writes* KV to the store, purely to raise future hit rates).

### 6.2 Host memory as a first-class tier

Two production mechanisms treat host DRAM as engineered memory rather than swap: the SWA pool (§5.1, ~10% of each machine's DRAM, minute-scale TTL, high turnover serving most concurrent sessions) and the Engram placement (§6.3). Swap-in (§5.3) adds a third: host shared memory as the staging area between the storage cluster and HBM, with RDMA doing the fine-grained movement the copy engine does badly.

### 6.3 Engram: model memory that lives on the host by design

V4.1-Flash carries a conditional-memory module, Engram, whose tables total **196B parameters** across two modules (at layers 1 and 14), addressed deterministically from n-gram hashes of the input tokens (orders 2–4, 8 hash heads, ~16M-entry tables, FP8 storage). Because addressing depends only on the token sequence, embeddings can be **prefetched**: in production serving the vocabulary-sharded tables live in *host memory* — a separate parallel group (ENP: 8-way in prefill, equal to the DP/EP degree in decode) holds one shard per rank, registered for RDMA, and at the start of the forward pass a kernel issues one-sided RDMA reads so the NIC moves the needed rows into GPU memory in the background while compute proceeds; only the small scale factors travel over NVLink. On Ascend, host offload for Engram is not yet supported and the tables stay in device memory — a documented platform asymmetry. Engram is the clearest example in the dossier of a memory hierarchy designed *into the model*: a fifth of the model's parameter mass is, by construction, cold, lookup-addressed, and prefetched from host RAM.

### 6.4 Failure-shaped memory

Memory behaviour under failure is specified, not emergent (§4.4): a dying decode engine forwards live requests with their KV to peers after a grace period; an EP instance restarts at whatever size the healthy hardware supports; the persistent cache is unaffected by compute-node loss because it never lived there (§5.2). The through-line is the same as Dynamo's (§2.5 of that dossier) reached independently: at fleet scale, *state placement is the fault-tolerance design*.

## 7. Kernel strategy

### 7.1 Assemble the published kernel libraries; fuse what's left

DeepInfer's kernel story is mostly *integration*: the README credits six named components — **FlashMLA** (attention over the compressed latent / CSA2 structures, including a fused RoPE–attention–RoPE–cast kernel per the technical report), **DeepGEMM** (the GEMM library, home of the fused Mega-Gate, Mega-mHC and **Mega-MoE** kernels), **DeepEP** (expert-parallel communication), **TileKernels**, **DeepSelect** (TopK selection), and custom **TileLang** kernels — all previously open-sourced DeepSeek libraries, now wired into one engine, with platform counterparts for Ascend. The technical report's framing is that the inference flow is deliberately *concise*: a CSA2 Reuse-mode layer executes with only 15 kernels in prefill and 11 in decode. The report's Single-Pass mHC redesign exists purely to make fusion possible — by shifting the residual-mixing coefficients one block, the residual update, input mixing, coefficient prediction, pre-norm and FP8 conversion collapse into one Mega-mHC kernel that reads and writes the residual once, halving activation memory traffic against the original multi-kernel form. **The pattern to note:** where a general engine accumulates kernels per model feature, DeepInfer *redesigned a model component* (mHC) to reduce the kernel count — co-design again, at the lowest level.

### 7.2 Mega-MoE and the wide-EP bet

The Q&A names Mega-MoE as the general solution inside a scale-up domain: regardless of EP size or batch size it is reported significantly faster than an unfused MoE path, because fusing dispatch, expert GEMMs and combine lets communication hide under compute. The same Q&A explains where the bet stops paying: as decode EP grows past ~32, arithmetic intensity rises until memory bandwidth is no longer the bottleneck, after which further width buys only communication and synchronisation overhead — and jobs sharing NVLink inside a supernode interfere, which is why a whole supernode is given to a single EP group. Wide-EP decode (§4.4) is thus a *measured* optimum on SM100 supernodes, not a principle.

### 7.3 Precision as kernel contract

The low-precision map, from the Q&A and checkpoint config together: main KV in FP4 (per-16 E4M3 scales, no global scale); indexer KV in MXFP4 (per-32 ue8m0 scales); routed-expert weights in MXFP4 (per-32 ue8m0); dense weights in FP8 with 32×32 blocks; SWA KV retained in FP8 (MXFP8 in the Q&A's storage arithmetic) because it proved sensitive to heavier quantisation; Engram tables and projections in FP8. Two details matter for a runner engineer: FP4 for the main cache is a *storage* format — values are dequantised before attention, so no native FP4 matmul support is required of the hardware, which is what keeps the format portable across the two supported platforms; and the internal-vs-released kernel gap is disclosed — the Q&A states the released libraries are broadly the same as internal ones, except the indexer and Mega series differ somewhat and the released FlashMLA lacks one hand-tuned SASS optimisation, making its decode kernel an estimated 5–10% slower, with end-to-end performance within ~5% overall. Vendor-reported, and unusually specific.

## 8. Prefix & session handling

DeepInfer has no sessions in the personal-runner sense — no conversational state object, no per-user residency — because its "session" is a *prefix in a shared store*, and its user is a fleet. The handling that exists, all production-side (§5):

- **Identity of a reusable prefix** is a hash chain over 128-token blocks of main + indexer KV, matched at the entrypoint over metadata before routing (§5.3). Reuse is whole-prefix: the block cache stores global KV in its entirety and a hit reuses the complete matched prefix.
- **Validity** is the tuple of §5.3 (deployment configuration, weights, user group). There is no per-entry versioning and no migration path; invalidation is total and by construction.
- **Multi-turn behaviour** falls out of the TTL split: a returning conversation's global KV is likely still on SSD days later, while its SWA state — minute-scale, host-resident — is almost certainly gone, and bounded replay (§5.3) is the bridge that makes the second fact cheap. The design *expects* partial hits and prices them, rather than treating cache state as all-or-nothing.
- **Isolation** between users in the shared store is represented in the sources only by that user-group term in the validity tuple; the matching, eviction and accounting machinery that would make a multi-tenant store safe is in the withheld layer and is **not described** in the material read. Recorded as a gap, not filled by inference.
- **The shipped engine's** prefix handling is correspondingly minimal: prompts arrive whole, the offline harness constructs cached-prefix workloads synthetically for benchmarking (a shared prefix is computed once and forked into many requests, with image inputs kept whole on either side of the cache boundary), and nothing persists between runs.

For contrast with this corpus's centre of gravity: Ollama-class runners treat the session as the precious object and the prefix cache as an optimisation. DeepInfer treats the *prefix store* as the precious object — a hundred petabytes of other people's conversations, retained for days — and the session as a routing event. §10.1 is about the one place those two views genuinely meet.

Interconnect budgeting for cross-datacentre experiments: roughly **400 Gbps per 8 GPUs**.

These are DeepSeek's own estimates from its benchmark data, in its own frame.

**Engine benchmark claims (README):** the README publishes two Pareto charts — prefill non-cached-input throughput against latency, measured on **4 SM100 GPUs**, and decode output throughput against per-user speed, measured on **64 SM100 GPUs**, each within one scale-up domain — with a sweep script provided for reproduction. **The charts are images; no numeric values appear in the text of the README as read, and this dossier does not quote numbers it could not read.** The claim that survives honestly is the *shape*: DeepSeek chose to publish operating curves, not point maxima, for its own engine.

**Model-quality reference points (eval README, vendor-reported):** the release's offline evaluation harness reports reference Pass@1 of 99.9% (AIME 2026), 93.4% (GPQA Diamond) and 42.6% (HLE-Full) for the V4.1 model under its default configuration, explicitly as sanity-check figures that repeated runs will vary around. The 1017 checkpoint's model card reports its benchmark improvements over the original V4.1-Flash checkpoint in DeepSeek's own harnesses (e.g. Terminal-Bench 4.0 from 31.2 to 42.3, in the Claude Code harness; DeepSWE v1.1 77.0, in the Mini-SWE-V2 harness) — recorded as model-card claims, with harness dependence noted on the card itself.

**The honest summary of §9:** DeepInfer's public evidence base is *architecturally rich and numerically thin*. The design documents quantify mechanisms (bytes per token, replay windows, imbalance ratios, verification-token savings) far more precisely than outcomes (tokens per second), and the one outcome number everyone will quote — 155T tokens/day — describes a system whose defining components are not in the repo. Budget accordingly.

## 10. Strengths / weaknesses

### Strengths

- **Co-design, demonstrated end-to-end.** CED, CSA2, FP4-with-QAT, bounded replay, DSpark's confidence head, Single-Pass mHC: each is a place where model and runner were changed *together* to move a serving metric, with the trade stated. As a reference for what the model/runner boundary costs general systems, nothing else in the corpus is as instructive — including the parts (§3.1) that cannot be copied.
- **The cache economics are worked, not gestured at.** Retention TTLs derived from measured reuse intervals and priced in hit-rate points; a storage tier sized in TB-per-GPU; a hit path whose three stages are individually assigned overlap strategies; a validity tuple; an explicit rejection of CXL tiering with reasons. §5 is the most complete production KV-store design record in this corpus after Mooncake's paper — and it describes a *different* answer (centralised store, no prefix affinity) reached from production evidence.
- **Candour about scope and gaps.** The README's "not included" list, the Q&A's "not yet fully open-sourced", the kernel-parity disclosure, the ~80%-of-ideal load-balancing figure, the technical report's limitations section naming its own approximation risks: the release consistently labels its own boundaries. That is rarer than it should be, and it is what makes the dossier writable from primary sources at all.
- **Determinism as a shipped feature** (§4.3), with the test suite built on exact-baseline comparison — an operator-grade reproducibility story no general runner in the corpus matches.
- **Two-platform reality.** SM100 and Ascend 950 support from one engine, with platform asymmetries (Engram offload, batch invariance) documented rather than hidden — a genuine, if narrow, portability proof.

### Weaknesses

- **The release is an engine core in search of its system.** Offline-only, no server, no persistent cache, no balancers: as shipped, DeepInfer cannot serve traffic. Its practical audience today is operators with SM100/Ascend-950 fleets willing to rebuild the withheld layer, and researchers. Everyone else gets a document, not a deployment.
- **The hardware floor is absolute.** SM100 or Ascend 950, CUDA 13 / CANN 9.2, GCC 13, Python 3.12 — no Hopper, no consumer cards, no CPU path, and a checkpoint whose parameter mass (552B backbone + 196B Engram) puts even *storage* of the model beyond a workstation. There is no small configuration to learn on; the examples assume 8 accelerators on a node.
- **One model, by design, forever-ish.** The README promises future DeepSeek models' inference code will land in DeepInfer, but the architecture surface is a single model class per release. Every co-design strength in §3 is purchased with this: the engine cannot generalise, because generalising is what it declined to do.
- **Evidence thinness (§9).** No independent benchmarks found; headline production figures unauditable by construction; README performance data locked in chart images; Ascend performance entirely unquantified in the material read.
- **Youth and churn risk.** Six commits and no tagged releases at crawl; a Q&A that "will be updated continuously" as the main design document; a Zhihu architecture post referenced as the fuller account of the withheld components (not read for this dossier — see Unverifiables). Pinning anything to this repo today is pinning to a moving drop.
- **Approximation risk is real and admitted.** Bounded replay and CSA2 sparse selection carry the technical report's own warning about uncharacterised boundary behaviour (§5.3). In production DeepSeek mitigates by training through the approximations and monitoring; a third party reusing the *ideas* on an untrained model inherits the risk without the mitigation.

## 11. What our Ollama work should steal as IDEAS

Graded honestly for the corpus's target — a single-machine personal runner (Ollama-class, one GPU with ~6 GB, one user, character-chat and agent workloads on arbitrary community models). The through-line, stated first: **almost nothing in DeepInfer *runs* at our scale, but DeepInfer is the corpus's best evidence for *why* several of our existing ledger entries are shaped correctly, and it contributes three genuinely new refinements.** DeepSeek spent a model-generation proving that the cache — its size, its precision, its retention, its reconstruction cost — is the product. A 6 GB runner lives under the same law with the signs flipped: our cache is tiny, our models are strangers, and our user is one person. The accounting transfers; the machinery does not.

### 11.1 Split persisted state by reuse horizon — the §5.1 split, miniaturised (refines #10)

DeepInfer's deepest transferable idea is not the 100 PiB store; it is the discovery that **one cache contains two populations with opposite reuse shapes** — global KV with a days-long long tail, SWA state with a minutes-long, session-bound life — and that giving them the same medium and the same TTL wastes both. The production answer (SSD for one, host DRAM for the other, nothing for what replay can rebuild) miniaturises cleanly into IDEA-LEDGER **#10**'s session persistence: persist the *trunk* (the persona/system prefix and completed turns — long-tail, reused across days) to disk with #10's validity envelope, keep only the *live window's* transient state in RAM, and let everything between be recomputed on resume. Our corpus already persists monolithically; DeepInfer argues for a two-class store with two TTLs and two media, sized from measured reuse — for a personal runner, "measured" means the runner should *count* trunk-hit age distribution, which is #6 disclosure applied to our own cache policy. **Grade: real refinement of an existing entry. Buildable now, no model cooperation needed.**

### 11.2 Bounded replay as a *disclosed* resume mode (new, with a hard caveat)

The local form of §5.3: when a session is resumed from a persisted trunk, the runner currently faces an exact-or-nothing choice — recompute the whole uncached suffix exactly, or store every layer's full state. Models with sliding-window layers admit a third option: recompute only a bounded suffix (window-sized) to rebuild window state approximately, and proceed. DeepInfer's numbers (128 tokens regardless of context; ~half of prefill saved in its decoder case) will not reproduce locally — its saving comes from CED's structure — but the *shape* transfers to hybrid models in our fleet: resume cost bounded by the window, not by history length. **The caveat is load-bearing:** DeepSeek *trained* its model to tolerate replay error and still flags resumption boundaries as an open robustness risk (§5.3). Our models were not trained for it. So: bounded replay may ship only as an explicitly disclosed, opt-in fast-resume mode (#6: the response discloses that state was approximately reconstructed, and how many tokens were replayed), graded per model by the #34 raw-oracle harness before it is allowed near a default. **Grade: steal the mechanism, refuse the default. [Assessment, marked: on untrained models the quality cost is unmeasured in any source read; treat as an experiment, not a feature.]**

### 11.3 Confidence-scheduled verification → variable draft budgets (refines #15 / #26 / #28)

DSpark's budgeting rule (§3.3, §9) generalises beyond its confidence head: *verification compute should be allocated per draft position by predicted acceptance, against a profiled throughput curve, not spent uniformly on a fixed draft length.* A general runner has no confidence head, but it has acceptance *history* — per-session, per-position acceptance statistics from previous steps are a usable predictor, and our ledger already carries session-granularity draft adaptation (#32) and embedded-MTP drafting (#28). DeepInfer contributes the scheduling form: maintain the profiled curve (draft length → net tokens/sec on this hardware, which is #33 roofline discipline applied to speculation), and let the *budget* float per step. Its measured effect (+4–7% at its operating point, −1.5% where concurrency was low) also honestly bounds the prize: this is a single-digit refinement, worth having after the draft path itself is right, not before. **Grade: small, real, late. The fixed-draft-length default in current runners is the thing to unlearn.**

### 11.4 Time-budgeted prefill chunks from a fitted cost model (refines #18)

§4.2's scheduler solves for chunk size from a *time* budget and a quadratic cost model over (chunk tokens, already-computed prefix length). Our #18 (chunked prefill) budgets tokens. On a 6 GB card running one user, the user-visible quantity is neither — it is *worst-case pause before the next token*, i.e. time. DeepInfer's form transfers directly and cheaply: fit the two-parameter cost model at model load (a handful of timed chunks at two prefix lengths), then size each prefill chunk to a stated inter-token latency budget, shrinking chunks as the resident prefix grows. This also subsumes the knee-profiling method from the FastGen dossier (§7.2 there): the budget becomes a *latency promise*, the token count an output. **Grade: the best small steal in this dossier. Low risk, measurable, user-felt.**

### 11.5 Determinism as a mode, not a property (supports #34)

Batch-invariant inference is unaffordable as a default on consumer hardware, and unnecessary — one user means batch composition is usually trivial anyway. What transfers from §4.3 is the *stance*: DeepInfer ships a named reproducibility mode and builds its regression suite on exact comparison against stored baselines. Our runner's equivalent is a deterministic grading mode (fixed seed, speculation off, cache state pinned) under which #34's raw-oracle comparisons and perplexity baselines run — the mode's slowness is irrelevant because it exists for measurement, and its existence is what makes every lossy optimisation in the ledger honestly gradeable. **Grade: discipline, already half-banked in #34/#44; DeepInfer is corroboration from production that the mode earns its keep.**

### 11.6 Smaller steals, briefly

- **Validity tuple, verbatim in spirit (#10).** DeepInfer keys cache reuse to (deployment configuration, weights, user group) and invalidates on *any* framework change that alters KV values. Our envelope should be equally explicit and equally total: (weights hash, quantisation/layout version, tokeniser identity, runner KV-affecting version) — and, following DeepSeek's practice, *no migration path*: an envelope mismatch discards, never converts. Simplicity here is a correctness feature.
- **Pull-based admission (#31).** Prefill engines pull work when their remaining step time can hide the preparation (§4.2). Local form: the runner should admit the next turn's prefill preparation (tokenisation, cache lookup, prompt rendering — #13's byte-stable rendering) *during* the current generation, sized to finish as generation ends. CPU work hidden under GPU work, again — the same law as §4.1's overlap scheduler and our #25, stated from the admission side.
- **Special-token injection prevention (supports #13).** deepseek-recipe's construction — user text that spells a control token is encoded as ordinary tokens, because encoding is segmented at *known* boundaries rather than scanned for matches — is the correct general rule for any runner that renders chat templates: control tokens enter a prompt only from the template, never from user content. One line in #13's acceptance tests.
- **Per-model precision metadata (#3, #42).** §3.2's lesson: where a checkpoint declares its own cache/weight precision expectations, the runner should honour them as the default instead of imposing a global policy. For GGUF-class models this is a metadata-reading discipline, not new machinery.
- **Publish curves, not points (#44).** DeepSeek's README benchmarks are Pareto curves with hardware and configuration stated. Our bench mode should do the same at our scale (throughput vs context length on the named card), for the same reason §9 of the Dynamo dossier gave: a point number without its operating conditions is marketing, including when we market to ourselves.

### 11.7 What does NOT transfer — the negative list, priced

- **CED, CSA2, cross-layer KV sharing, hierarchical indexing.** Model architecture, trained in. A general runner cannot retrofit cache sharing onto a checkpoint whose layers never learned to read each other's entries. The 890 B/token figure is not a target our runner can approach for arbitrary models; our equivalent lever remains per-layer real-cost allocation (#16) and KV quantisation (#3/#19), an order of magnitude less powerful and honestly labelled as such.
- **FP4 KV as a default.** DeepInfer's FP4 cache is safe *because QAT taught the model to live in it*. Applying FP4 (or any sub-8-bit scheme) to an arbitrary local model is an unconsented approximation of exactly the kind #34 exists to catch. The format engineering (per-16 scales, no global scale, dequantise-before-attention) is interesting prior art if a *specific* local model family ever ships QAT'd for it — and not before.
- **Wide-EP, DeepEP, Mega-MoE, EPLB.** All of it presumes many accelerators, NVLink domains and a hot-expert problem created by batch sizes in the thousands of sequences. A single 6 GB card running one user's MoE has the opposite problem (all experts cold, residency-bound — #29/#38 territory), and importing fleet expert-balancing machinery would be theatre.
- **The 3FS store, disaggregation, the balancers.** Not shipped, not buildable at our scale, and not needed: §5's *policy* transfers (§11.1), its *infrastructure* is a datacentre. Likewise the 155T-tokens/day economics: our cost function is one user's latency and one card's memory, and §9's numbers have no local meaning.
- **Engram-style host offload.** The prefetch-from-host-RAM pattern is real, but it serves a 196B-parameter lookup table addressed by hash — a model component no local checkpoint has. The nearest local relative (host-resident cold experts, prefetched by predicted routing) is already #38, and DeepInfer adds nothing to it beyond scale envy.
- **The single-model fast path itself — with one conditional exception.** DeepInfer's core bet (delete generality, hard-code one model's shapes) is unavailable to a general fork *as a default*. The conditional exception, stated as speculation and marked as such: **[Speculation]** if this fork ever ships *one* bundled house model (a persona-tuned checkpoint distributed with the runner), a DeepInfer-style specialised path for exactly that checkpoint — fixed KV layout, baked precision, profiled chunk budgets, a trained-in drafter — becomes legitimate, and this dossier is its design brief. Until that day, the bet stays DeepSeek's.
