## Essence

TokenSpeed is what you get if you start from the workload instead of from the engine. The workload it names — coding agents such as Claude Code, Codex and Cursor — has a very specific shape: contexts routinely past 50K tokens, conversations spanning dozens of turns, each turn appending a comparatively small increment (a tool result, a file edit, a short instruction) to an enormous shared history, and a human (or an agent loop) waiting on each reply at interactive speed. TokenSpeed's founding move is to state the objective for that shape explicitly and unusually: **maximise tokens-per-minute per GPU subject to a per-user tokens-per-second floor** — typically 70 TPS per user, sometimes 200+. Throughput is the thing being maximised, but latency is a hard constraint, not a by-product. Almost every other engine in this corpus maximises aggregate throughput and lets per-user latency fall out; TokenSpeed inverts the priority on paper and then builds for it.

The building has five named pillars (launch blog): a compiler-backed modelling layer for parallelism (local SPMD with placement annotations; a static compiler inserts the collectives), a high-performance scheduler whose control plane is a C++ finite-state machine that uses the type system to make unsafe KV reuse a compile-time error, a "safe KV resource reuse restriction" (that FSM/ownership discipline applied to cache state), a pluggable layered kernel system for heterogeneous accelerators, and SMG integration so the request entrypoint costs almost no CPU. Its most famous artefact is not the engine but a kernel: the TokenSpeed MLA (multi-head latent attention) decode/prefill pair for NVIDIA Blackwell, which LightSeek states — and a vLLM release-notes dependency pin independently corroborates (§6.4) — was adopted by vLLM.

The design target is the opposite end of the world from a 6 GB laptop: frontier mixture-of-experts models (Kimi K2.5/K3, Qwen3.5-397B, DeepSeek V4) on B200/GB300 clusters, served to fleets of agents. Nothing in the software transfers to our Ollama fork. Several of its *decisions* transfer unusually well, because a single-user persona chat is, structurally, an agentic workload with a fleet size of one: one huge shared prefix, tiny increments per turn, long idle gaps, and a user who feels every millisecond of latency. §8 and §9 grade that honestly, including the large parts — the MLA kernel above all — that do not transfer at all.

## 2. Architecture

### 2.1 The control plane / execution plane split

TokenSpeed's central architectural claim — repeated by the PyTorch Foundation's ecosystem welcome, quoted in the README — is that it is the first open engine to separate the **control plane** from the **execution plane** as distinct implementations in distinct languages:

- **Control plane (C++, `tokenspeed-scheduler/`).** A finite-state machine owns the request lifecycle, KV-cache ownership, and overlap timing. States and transitions are explicit; ownership of cache resources is encoded in the type system so that a class of reuse bugs — using a page after it was freed, publishing a checkpoint before it is complete, freeing a page a transfer still addresses — is meant to be unrepresentable rather than merely tested against. The scheduler design doc shows this discipline in production form: for example, the prefill/decode-disaggregation transfer pin is not a flag a handler must remember to clear, it is a function of the request's FSM state, so "no event handler can forget to clear it" (design doc's reasoning, paraphrased). The scheduler decides, once per round, what every engine role does next, and emits a plan; §3 covers the plan's contents.
- **Execution plane (Python).** Model definition, forward execution, tensor ownership, sampling, and the physical side of the cache (GPU KV pages, recurrent-state tensors, copies, zeroing, snapshots). Python is kept deliberately, for iteration speed and researcher ergonomics — the split is a bet that the *decisions* need compiled-language rigour and the *doing* needs Python velocity.
- **The bridge.** The two sides meet over typed structures: the C++ side works purely in logical, token-denominated quantities (prefix granularity, per-group block granularity — §4.1) and is forbidden, by an explicit naming law in the cache-concepts doc, from knowing physical geometry (kernel page sizes, byte layouts, LCM packing live on the Python/storage side). Python recipes size pools by asking the C++ capacity model (§5.1) before any arena exists, so both sides plan against one arithmetic.

**Why this matters beyond TokenSpeed:** every other engine in this wave (vLLM V1, SGLang) arrived at process separation to keep Python off the GPU's critical path. TokenSpeed's version is stronger and more opinionated: not just process isolation but *semantic* isolation — the scheduler cannot express a physically impossible cache operation. For a Go fork this is the most quotable idea in the dossier (§9.2), because Go's type system can carry the same discipline without a second language.

### 2.2 The modelling layer: local SPMD with a static compiler

Models are written once, in a local SPMD (single program, multiple data) style. A developer annotates I/O placement at module boundaries; a lightweight static compiler then generates the collective communication (all-reduces, all-gathers, scatters) needed by the chosen parallelism at model-construction time, instead of the model author hand-writing communication per layer. The parallelism vocabulary the compiler targets is broad and, characteristically, *split* rather than monolithic:

- **Tensor parallelism, split by layer family** — separate sizes for attention (`--attn-tp-size`), dense and MoE parts, so a deployment can run, e.g., Attention TP4 + MoE TP4 (the launch benchmark's best coding-agent configuration) or Attention TP8 + MoE EP8.
- **Expert parallelism** for MoE layers.
- **Data parallelism for attention (DP attention)** — whole attention replicas with separate KV, the standard answer for MLA models whose per-token latent KV cannot be sharded by heads (the parallelism doc describes an MLA decode engine running attention at TP1 with DP across the world, optionally re-sharding just the head projections — "head TP" — over contiguous ranks).
- **KV parallelism (KVP), decode-context parallelism (DCP) and query-context parallelism (QCP)** — sharding the *history itself*: full-history KV pages are distributed cyclically over a subgroup of attention ranks, so per-GPU KV capacity grows by the sharding factor; decode attends its shards in place (DCP), prefill shards query rows against gathered history (QCP). This is a genuinely unusual axis — most engines shard weights and replicate or partition requests; TokenSpeed also shards one request's context across GPUs.
- **Pipeline parallelism** exists in the rank naming and config surface but is not the celebrated axis.

### 2.3 Entrypoint: SMG and Dynamo, no Python on the request path

The README's third core component is the entrypoint: **SMG (Shepherd Model Gateway) and NVIDIA Dynamo drive the engine from Rust over its msgpack wire, with no Python on the request path.** Concretely, from the docs and the SMG material:

- `tokenspeed serve <model>` starts an OpenAI-compatible HTTP server for a single (aggregated) engine; the chat template is handled by the SMG gateway layer, not the engine.
- For disaggregated topologies (§2.4), each role runs headless (`ts serve --headless`) and an `smg launch` gateway fronts them; the gateway binds each worker's ZMQ sockets and the roles dial its handshake. The gateway/engine wire is msgpack-encoded structs over ZMQ; a published Rust crate mirrors the schema exactly (golden fixtures generated by the Python encoder keep the two sides byte-identical — a conformance discipline worth noting in itself).
- SMG is a separate LightSeek project (Rust, cache-aware routing across engines, tokenisation in the gateway) — TokenSpeed consumes it as its front door rather than growing its own HTTP/tokenisation stack inside the engine. Dynamo support existed at day 0 (NVIDIA's own Dynamo docs carry a TokenSpeed backend recipe, `python -m dynamo.tokenspeed`).

The transferable observation is the same one vLLM V1 and SGLang both reached, taken one step further: not only is tokenisation exiled from the engine process, the entire request surface lives in a different, compiled-language program that the engine treats as a peer.

### 2.4 Deployment shapes: aggregated, PD, EPD

- **Aggregated (fused).** One engine does prefill and decode locally; the launch blog's benchmarks are all this shape. The scheduler doc calls this role "fused" and gives it the richest local policy set (§3).
- **Prefill/decode disaggregation (PD).** Separate prefill (P) and decode (D) engines behind SMG; KV and embeddings move between them over **Mooncake** (RDMA where present). At launch (May 2026) PD was explicitly still being cleaned up and excluded from benchmarks; by the November docs it is a fully specified topology with its own scheduler roles, a layer-wise transfer pipeline, and CI launchers for Qwen3.5 and DeepSeek V4.1 PD deployments. §3.4 and §4.5 cover the transfer mechanics.
- **Encode/prefill/decode (EPD).** A third role runs only the vision tower for multimodal models; image embeddings travel to the prefill engine over Mooncake.

### 2.5 Lineage and ecosystem position

The launch blog states plainly that parts of the runtime reflect upstream lineage from FluentLLM, with the scheduler, modelling layer, kernel stack and MLA work as the original contributions. The project joined the PyTorch Ecosystem Landscape in August 2026. Its repo topics and news feed read as a day-0 enablement business: new frontier models (Kimi K3 at 2.8T parameters, Qwen3.8 at 2.4T, Inkling, Muse Spark, Beam) announced with TokenSpeed support on NVIDIA *and* AMD flagship parts within days of the model's own announcement. That cadence — not any single benchmark — is the best evidence of where the engineering effort goes: breadth across frontier MoE/hybrid architectures, at the top of the hardware range.

## 3. Scheduling & batching

### 3.1 The round, and what a plan contains

The C++ scheduler works in **rounds**: once per round it builds a plan for its engine role — which prefills advance by a chunk, which decodes step, what gets published to the prefix cache, what gets retracted or restored, which transfers start — and the Python execution plane carries the plan out. Publication of completed cache pages *rides with admission*: the progress a request made since its last admission (completed prefix pages, computed-token count) is hashed and published inside the same admission operation that grants its next chunk, so a page becomes matchable by later admissions at exactly the moment its owner is known to have finished writing it. With prefix caching disabled, nothing is hashed, published or written to the host tier at all — the machinery fully collapses, a detail that signals how central the cache is to the design.

### 3.2 Admission is per chunk, never per prompt

The scheduler's first law (its design doc's §1, in our paraphrase): a prompt's prefill is scheduled in chunks bounded by `--chunked-prefill-size` (default 8,192 tokens; `-1` disables chunking), and capacity is admitted **for the chunk being scheduled, never for the whole prompt**. Each cache group (§4.1) gets a demand sized by this chunk's tokens; the coordinator grants the pages or the request stays put. Two refinements sit on top of the raw chunk size:

- **The junction cut.** For hybrid models, when a prefix hit extends past the longest reusable recurrent-state checkpoint, the first chunk after the checkpoint is cut to end exactly at the hit boundary, so the checkpoint that chunk naturally leaves behind coincides with already-cached KV — the next request sharing that prefix can then resume at the boundary in *every* group at once (§4.4).
- **The reserve.** Every admission also states what it holds beyond the chunk: principally the *decode slot* — the chunk that completes a prompt reserves room for the first decode step (and, on a prefill-only node with speculation, for the drafter's first candidate block, which is written behind the prompt before being shipped to the decode peer). Intermediate chunks reserve nothing. Sliding-window groups reserve only the growth that recycling slid-out pages cannot fund. State groups reserve nothing — their table is two slots at any prompt length. The design intent is visible: admission is a contract that a request, once started, can always take its next step.

### 3.3 Ordering: head-of-line, decode protection, and two opt-in policies

- **Head-of-line rule for prefills.** Once a round schedules a chunk of a prefill that remains incomplete, nothing behind it is scheduled that round. The reasoning is stated in the design doc: per-chunk admission gives an in-progress prefill no claim on the capacity its remaining chunks need, so admitting a newcomer behind it risks stranding the half-prefilled request holding pages it can never complete with — a retraction waiting to happen. The cost is one round of queue latency; one full chunk already saturates the GPU, so nothing is lost. A chunk that *completes* its prompt releases the line within the same round, so a round's shape is: all decodes, plus any number of completing prefills, plus at most one truncated prefill, last.
- **Decodes are never behind the line.** In mixed mode (`enable_mixed_prefill_decode`) the decode batch is built first and takes its token budget first — a streaming client must not be starved by a long prefill chunk. Outside mixed mode, prefill and decode never share a round at all.
- **Prefill/decode interval.** An optional knob makes a round that ran a prefill chunk owe the running decodes N decode-only rounds before the next prefill round — with a hard fairness cap: no prompt may be held back more than N rounds in total across its whole life, so the knob adds at most N decode steps to any prompt's time-to-first-token, whatever its chunk count. Counters survive retraction and restore.
- **Yielding chunks (prefill role, opt-in).** `--prefill-chunk-yield-tokens` lets a chunk that cannot finish its prompt give up a bounded slice of its forward (fewer than N+1 pages, N at most half the chunk budget) to waiting prompts that fit *whole* in that slice — small prompts complete in the same forward instead of waiting for a 100K prompt's chunk to pass, while the long prompt is guaranteed to keep roughly half or more of every round.
- **Short-prefill-first (opt-in).** New prompts may be ordered by *remaining work after prefix reuse* (prompt tokens minus Device/Host hits, plus replay work) instead of submission order — with an anti-starvation guard: after eight successful bypasses, the oldest waiting prompt gains selection priority. Resident (already-started) chunks always keep priority. Off by default; submission order is the default policy.

**[Assessment]:** this is the most operationally honest scheduler documentation in the corpus. Every policy names its own failure mode and ships its guard (starvation counters, bounded yield, head-of-line as a deliberate trade). Compare SGLang, where cache-aware ordering's starvation risk is a documented caveat the operator must manage; TokenSpeed builds the guard into the policy itself.

### 3.4 Roles: fused, prefill, decode — three different schedulers in one

The scheduler's phase order differs by role, and the differences are instructive:

- **Fused:** restore first (it resumes a streaming client and takes no budget), then decodes, then local prefill phases spend what remains, then capacity retraction if needed.
- **Prefill (P):** no local decode ever runs; a completed prompt's pages stay *pinned* until the decode peer acknowledges the transfer, then release wholesale. **Retraction does not exist on this role** — the transfer itself is the pressure valve, and retracting a prompt whose KV is mid-transfer would strand the decode side. The transfer ACK publishes the prompt into the cache exactly like a finish.
- **Decode (D):** a round routinely carries three things at once — the decode batch, one restore (§3.5), and at most one *remote admission* (a whole new prompt, prefilled by the peer) — the restore and the remote admission ride *beside* the batch as cache operations, consuming no token budget and no batch slot. Remote admissions are capped at one per round because each reserves an entire prompt's pages. The D-side probe checks its own Device cache first so the peer transfers only what is missing.

### 3.5 Retraction: suspend and restore, never recompute

This is TokenSpeed's sharpest divergence from both vLLM V1 and SGLang, which both chose recompute as the in-engine pressure response. TokenSpeed's rule, stated flatly in the server-parameter docs: **a retracted request loses no work.**

- When admission fails for capacity and no prefill made progress in the round, `maybeRetractForCapacity` picks victims among *resident requests the current round has dispatched no work for* (a request with a forward in flight cannot quiesce in time). Incomplete prefills are preferred victims on the fused role; a resident blocked on its own next page is the preferred victim overall.
- The victim is **imaged to host memory byte-for-byte**: first its computed frontier is published into the Device prefix index exactly as a finish would publish it; then the image splits in two legs — slots that are published prefix entries become ordinary Host L2 entries, *pinned* for this request until its restore lands (and simultaneously visible as normal cache that later prompts may hit); everything else (unpublished state slots, replayable groups, the request's runtime slot-state blob — sampling state, speculative readiness) goes to a request-private **snapshot pool** in pinned host memory, never prefix-indexed, never evicted.
- Its Device pages are released, and the freed capacity is granted **to the specific blocked admission that triggered the retraction, retried in the same plan build** (retract → retry → retract until it fits or victims run out) — freed pages never sit idle waiting for next round's first asker.
- **Restore** copies the image back into fresh pages and resumes the request in the exact state it left — mid-prefill at its next chunk, or at its next decode step, with the first post-restore decode carrying its input token explicitly (the overlapped-decode capture belonged to the request-pool slot it was retracted from). One restore may start per round, ahead of fresh work.
- **Fallbacks are honest and bounded.** Imaging needs snapshot-pool room; if no offered victim's image fits, the scheduler *aborts* the newest resident instead (client-visible finish error 524) rather than waiting on a host budget. An explicit `--retraction-snapshot-ratio 0` runs with no pool at all: every capacity block aborts its victim. A no-progress detector (4,096 consecutive plans that ran nothing, fused role only) aborts a request that can never be funded rather than letting it wait forever. The snapshot pool is sized deliberately: by default 0.1× the Device KV capacity when there is no Host KVStore (whole images, kept cheap to pin), or enough image *tails* for `--retraction-snapshot-max-requests` requests (default derived to cover every resident request of the rank) when L2 exists.
- One exception in the other direction: the separate **sparse KV offloading** feature (§4.5) uses capacity *aborts* instead of snapshot recovery, disables the snapshot pool outright, and tells the client to resubmit — the design doc records this as a deliberate incompatibility, not an oversight.

### 3.6 Overlap scheduling

Like its peers, TokenSpeed overlaps CPU scheduling with GPU execution: the scheduler plans round N+1 while round N's forwards are in flight. The hybrid-cache design (§4.4) exposes what that costs in correctness machinery: a checkpoint may be *published* by the C++ side during overlap, but stream ordering guarantees no GPU consumer reads it before the snapshot write that produced it has completed, and a published slot is never reused as the next checkpoint destination. On the execution side, the Qwen3.5 engineering post describes the same war fought inside the decode loop: the whole forward (target, sampler, draft) is captured into a single CUDA graph, and the CPU work *between* graph replays — input preparation, index arithmetic, state-pointer updates — is treated as a first-class optimisation target: device-to-host round-trips replaced by precomputed bounds and GPU-side sentinel values, index arithmetic fused by `torch.compile` from 10–14 launches into one or two, pinned-memory non-blocking transfers throughout, polling instead of synchronisation. Their summary claim is near-zero CPU overhead in the decode loop (project-reported, on the Qwen3.5/B200 stack).

## 4. KV cache design

### 4.1 Vocabulary: three group kinds, one flat pool

TokenSpeed's cache is organised by **cache groups** — one per attention family in the model — each classified into exactly one of three kinds, on which every scheduler decision switches:

- **`full_history`** — per-token KV rows that stay resident for the request's whole life; prefix-closed and shareable. (Standard and MLA latent attention.)
- **`sliding_window`** — per-token rows of which only the trailing window (plus optional sink tokens) stays resident; the middle expires. Some sliding groups are *replayable*: their slid-out content can be regenerated, which changes their reserve and reuse arithmetic.
- **`state`** — recurrent/convolutional state (GDN, KDA, Mamba-family layers). One block holds the state after some token count; it summarises everything before it, never slides, and a request holds **exactly two blocks** per state group whatever the prompt length (§4.4).

Underneath, physical storage is **CacheBlocks** aggregated into LCM (least-common-multiple) blocks: one physical page pool whose parents pack child blocks from every group, so bytes are fungible across groups. The Kimi K3 post gives the concrete shape: one flat pool where a page holds *either* 1,536 tokens of MLA latent history *or* one KDA recurrent snapshot, organised into 24 physical slabs, with a single global page ID indexing the corresponding page across all slabs — prefix caching, copy-on-write snapshots and CUDA-graph decode all operate on the same pool. There is no separate "KV budget" and "state budget" to strand against each other; the capacity model (§5.1) accounts per group, but the storage is shared.

### 4.2 Prefix matching: chain hashes, published boundaries, and tails

The logical layer (C++ side) is a prefix index over chain hashes, described in the cache-concepts doc and the Qwen3.5 post (which calls the structure a radix tree; the current design docs speak of a prefix index with tree links — ancestors, subtrees, root walks — so "radix-tree-structured prefix index" is the accurate summary of both):

- **Identity.** One chain hash per page of `prefix_granularity` tokens: a page's hash covers its own tokens chained on its parent's hash, so a hash identifies an entire prefix, not a page in isolation — the same construction as vLLM's hash chain, but the reuse boundary is *not* restricted to full pages.
- **Published boundaries and tails.** A reuse boundary is any token count at which some request *published* its state: every page multiple it completed, **plus a tail** wherever it stopped writing — its prompt end, a junction cut, its finish, its retraction — hashed as `hash@T` over the partial page's first tokens. Two requests share cache below the longest published boundary that is a prefix of both. This is finer than block-aligned-only caching (vLLM) and close in spirit to SGLang's exact-token matching, achieved with hashes and explicit publication points rather than edge-splitting alone.
- **The probe.** Before a first chunk, admission probes the index for the prompt's leading pages and for a published tail inside the following page. The hit boundary T is a token count carried as-is. The probe is bounded: the final prompt token is always recomputed (to produce logits) — the *replay tail* — and a per-request bound exists for prompt-logprob requests, which must recompute every position they report logprobs for. Only a freshly submitted prompt is probed; a retracted request is never re-probed, it returns by image restore (§3.5), so no position whose logits were produced is ever matched against another request's pages.
- **Copy-on-write tails.** A hit that ends mid-page cannot simply share the page — the hitter will write past the boundary. The tail's blocks are copied out of the shared entries (which stay pinned as sources until the copies land) into private blocks the request owns — the *copy-in* reserve the capacity model charges for. Published blocks are never written again; a request continuing past a published checkpoint rotates it to read-only input and writes into a fresh block (§4.4).
- **Eviction.** The index orders entries by access epoch, then location; eviction takes available (unpinned) entries in that LRU-style order, with planners that first check indexed free counts and only enumerate victims under pressure, using shadow occupancy for the parents they tentatively evict. Entries pinned by any owner — an admission's acquired hit, a transfer, a retraction image — are set aside and skipped until released. A separate duplicate-reclamation pass removes Host copies whose content is fully resident on Device again.

### 4.3 The tiers: Device (L1), Host KVStore (L2), Mooncake Store (L3)

- **L1 — Device.** The GPU page pool of §4.1.
- **L2 — Host KVStore.** A pinned-host-memory pool with the same block/bucket geometry discipline as Device (mirrored ranks must agree on packing before allocation, or startup refuses). Two write policies: **write-through** (a copy streams to Host at publication; the two tiers then largely mirror each other) and **write-back** (nothing streams at publication; what an admission *evicts* from Device leaves by whole segments, written back in the same plan — so the two tiers together hold distinct content up to roughly the sum of their capacities). Eviction write-back has a subtle admission interaction the scheduler doc spells out: if an in-flight write-back segment could extend a waiting prompt's hit, that prompt's first admission *waits for the copy ACK and probes again* rather than admitting against a half-true picture — the request holds no pages or slot while waiting, so it blocks nobody.
- **L3 — Mooncake Store.** A distributed/object tier behind the same index, **namespaced by weight version** (`--weight-version`, default `default`): pages published under one set of weights are never served as hits under another — the stale-KV-after-weight-update hazard, handled as a naming rule. L3 is **fetched before admission, never by it**: a request waiting on an L3 query/GET sits in a `Prefetching` state, holding no Device pages and no request-pool slot, owned by a transfer manager with bounded queues and a soft deadline after which the request simply recomputes. Failed rows never publish; a partially successful GET publishes its successful rows and ordinary group matching decides the reusable boundary.
- **The snapshot pool** (§3.5) is a fourth host structure but not a cache tier: request-private, unindexed, unevictable.

### 4.4 Hybrid / recurrent state: two slots and natural checkpoints

For GDN/KDA/Mamba-style layers the cache problem is the known hard one: a recurrent state summarises its whole prefix and is updated in place, so it cannot be sliced — only checkpointed. TokenSpeed's answer (Qwen3.5 post + scheduler doc §1.2):

- **Two slots per request.** Slot 0 is the input checkpoint a forward reads; slot 1 is the output it writes. A prefill chunk rotates (slot 1 becomes slot 0, a fresh block is acquired for slot 1); ordinary decode steps write slot 1 in place and acquire nothing, so decode consumes no state capacity. Because a request holds its pair from first admission, a pool sized at two blocks per live request back-pressures at admission instead of wedging at the first decode.
- **Natural checkpoints.** A state is published only where its owner stops writing it: a prompt end, a junction (§3.2), a finish, a retraction — never at an ordinary chunk end or decode step. The checkpoint's key is the key of the exact token count it summarises, shared with the KV groups, so one key names a request's progress across every group kind. A published state block is never written again.
- **Copy-on-write reuse.** A later request matching the prefix copies the cached checkpoint into its private working slot (`mamba_cow_src_index` in the Qwen3.5 account) and continues from the copy; the tree's slot is never mutated. Newly allocated slots are guaranteed clean in exactly two ways: they receive a copy-on-write copy from a known-clean checkpoint, or Python explicitly zeroes them — the allocator itself hands out IDs without clearing GPU memory, so the cleanliness invariant is a runtime rule, stated as such.
- **Checkpoint granularity restrictions.** Some state families may only publish prefill-produced checkpoints, at a configured granularity G (multiples of the prefix page size); decode-produced states then stay private (saved only for the request's own retraction restore). An opt-in **in-forward checkpoint** (`--enable-state-checkpoint-in-forward`, off by default) makes the prefill forward that spans the last page boundary before a long prompt's replay tail also snapshot the state *there* — serving exactly the multi-turn pattern where the next turn re-renders the end of the previous prompt plus its reply, which can resume at neither the old prompt end nor its finish (those become **dead checkpoints** and are deliberately kept out of the cache in this mode). A conversation's earlier checkpoint (two turns back) is evicted early once a newer one is published past it, unless another request resumed from it — multi-turn traffic keeps more *live* prefixes cached by discarding the ones the conversation has moved past.

### 4.5 Sparse KV offloading (a separate, narrower feature)

Distinct from the L2 tier: `--kv-offload-config` names specific attention layers whose KV is managed as a fixed *hot window* on device (a power-of-two `hot_tokens` count) with the rest offloaded to a budgeted host pool (`host_gb`), with optional cross-layer prefetch overlap. It is model-recipe-validated, uses capacity aborts rather than snapshot recovery (§3.5), and should be read as a long-context pressure valve for specific models, not as the general memory story.

### 4.6 What "session" means here

There is **no engine-level session object** in the material read. Prefix/session handling is entirely content-keyed: a conversation's next turn reuses whatever its re-rendered prefix matches, across Device, Host and L3, for as long as eviction leaves it resident — plus the multi-turn-specific machinery of §4.4 (in-forward checkpoints, dead-checkpoint suppression, early eviction of superseded turn checkpoints). Conversation *history storage* (chat-history backends — PostgreSQL/Redis — and the Responses/Conversations APIs for agents) lives one layer up in SMG, the gateway, not in the engine. **[Interpretation]:** TokenSpeed's position is that the engine should not know what a session is; it should make re-deriving a session's state cheap enough that nobody needs to tell it. That is the same position SGLang's runtime takes for API clients, pushed further — SGLang's 2026 unified cache grew an explicit session-aware eviction; TokenSpeed instead shapes *which checkpoints exist* so that ordinary LRU keeps the right ones.

## 5. Memory management

### 5.1 Sizing: one fraction, one capacity model

- `--gpu-memory-utilization` is the fraction of GPU memory used for model weights and KV cache (the docs do not state a default value in the pages read — **unverified**, §10). `--max-total-tokens` can override the computed token-pool size directly.
- Device-graph (CUDA graph) memory is charged honestly: with the graph memory reserve on, graph buffers and startup residue (the docs give a worked example: sampled-token buffers over a 129K vocabulary ≈ 330 MB) come *out of the KV-cache budget*; disabling the reserve sizes KV from free memory instead. With the memory-saver feature enabled, startup skips the disposable graph probe, captures once, and the operator is told to leave headroom in the utilisation fraction.
- **The capacity model is config-only and shared.** A single C++ `CapacityModel` reads only pre-allocation config and computes, per group, the pages a live request can demand: protected decode tokens (decode width × overlap depth), the speculative draft window, two slots per state group, sliding-window resident pages plus one in-flight chunk behind the lookback, tail-handover and copy-in blocks while prefix caching is on. Python recipes call the same model to size a pool *before* the arena exists; the scheduler then bounds requests against the pool that was sized. An invariant the model's tests sweep: a pool sized for the configured concurrency admits every request the per-request bound accepts. Pools sized too small *reject* oversized requests at startup/admission rather than accepting requests that can never produce a forward.
- **Compaction.** A lone request's blocks in a packed group can be gathered into fewer LCM parents (`CompactLoneRequest`) so emptied parents return to the shared pool — the one case where an allocated block moves. A restore that failed for capacity seals competing admissions, and compaction interacts with retraction ranking (a request whose blocks a compaction plan is still filling is not offered as a victim).

### 5.2 Fragmentation stance

Structural, as with all paged designs, with two TokenSpeed-specific twists: (1) LCM packing means a parent LCM block can hold children from *different* groups, so a pool does not strand capacity per group — the fungibility of §4.1 is the anti-fragmentation mechanism; (2) the per-step residency gauge is O(1) bookkeeping (empty parents from the pool, active parents counted by the block tables' own references), so the system always knows its true free capacity without scanning. Residual waste is the familiar tail-page rounding, softened by tail publication (§4.2): a partial page is still a *matchable* cache entry even though its storage is a full block.

### 5.3 Weight memory: RL-shaped extras

Two features reveal a second target workload beside agent serving — RL rollout fleets:

- **Weight memory policies.** `--weight-memory-policy cpu_backup` copies weight regions to host on release and restores them on wake; `discard` releases weight pages with no copy, valid only for models that opt into a contract (immutable layout, no quantised weights, no online expert rebalancing) and receive a complete new version through the Model Updater SDK.
- **Mooncake weight updates.** Weights can be updated in place from a distributed source, bracketed as a session so each model derives its post-load state once; KV-cache scales other than 1.0 in an update are rejected (see §6.1); the engine does **not** roll back a failed update and may serve mixed weights until a successful retry or restart — documented plainly. Under L3, a successful update advances the weight version, which re-namespaces the cache (§4.3).
- A **bitwise-determinism numerics contract** (`--numerics rl-bitwise`) folds a dozen switches (batch-invariant collectives, per-request sampling streams, fixed reduction orders) so a teacher-forced pass reproduces a trainer's logprobs exactly — again, RL infrastructure, recorded here because it explains several otherwise-odd defaults.

None of this is relevant to a single-user chat fork except as a warning about scope: a meaningful slice of TokenSpeed's complexity budget is spent on a workload (RL weight churn) that is not even agent serving.

## 6. Quantisation & kernels

### 6.1 Supported quantisation

Weight quantisation, KV-cache quantisation and recurrent-state dtype are independent knobs, as in vLLM/SGLang:

- **Weights (`--quantization`):** `fp8`, `nvfp4`, `w8a8_fp8`, `compressed-tensors` named in the server-parameter docs; recipes add AMD Quark **MXFP4** checkpoints (routed experts quantised, first/last layers in BF16), FP8 checkpoints generally, and an **online FP8 attention-projection** option (`--enable-fp8-attn-proj`, off by default) that converts floating QKV/O (and GDN QKVZ) projections of Qwen3.5-class targets at load with 128×128 block scales and dynamic per-row activation quantisation, with DeepGEMM packed-scale paths on SM100/SM103.
- **KV cache (`--kv-cache-dtype`, `--kv-cache-quant-method`):** FP8 is the production shape in recipes (e.g., Kimi launches pair NVFP4 weights with FP8 KV). One striking restriction: **TokenSpeed's KV caches run unscaled** — under an FP8 KV cache, a `--quantization-param-path` file is accepted only if every factor is 1.0, and a checkpoint carrying KV scales other than 1.0 is rejected at load, as is a weight update carrying them. Calibration freedom is traded for a simpler, faster cache path; operators coming from vLLM's scaled-FP8-KV world should note the incompatibility.
- **Recurrent state (`--mamba-ssm-dtype`):** `float32` (default) or `bfloat16` storage for GDN/KDA state; scans still accumulate in FP32. BF16 halves state memory — for hybrid models, state is per-request fixed-size, so this is a concurrency knob, not a context knob.
- **GGUF:** no mention in any primary source read (docs, recipes, kernel posts). **Unverified** — recorded as "not found", not asserted as "unsupported" (§10).

### 6.2 The kernel layer: registry, traits, plugins

TokenSpeed-kernel is a standalone subsystem with its own PyTorch-blog deep dive (June 2026), usable without the engine. Its design:

- **Portable public APIs** for the operations that dominate inference — attention (`mha_prefill`, `mha_decode_with_kvcache`, …), MoE, GEMM, communication — that describe the *problem* (tensors, formats, model traits, constraints), never the backend.
- **A central registry.** Implementations register with metadata: operator family and mode, solution name, platform capability requirements, supported tensor signatures, feature traits, and priority. The selector filters by capability/signature/traits, ranks the survivors, caches the resolved callable per (model, platform, dtype, traits), and can be forced to a named solution for debugging/benchmarking.
- **Plugins.** Out-of-tree kernels register through the same decorator and participate in normal selection — the mechanism by which hardware vendors ship specialised kernels without forking the engine.
- **Backend families behind the API:** portable Triton everywhere; **Gluon** (Triton's low-level AMD dialect) for CDNA parts — the GPT-OSS post reports its Gluon attention fastest on 14 of 15 measured MI355X prefill shapes, 1.4–2.3× over the Triton baseline and 1.1–1.3× over AITER's path (project-reported, commit-pinned, ROCm 7.2.1); **CuTe DSL** for NVIDIA fast paths; vendor wrappers (FlashInfer, TensorRT-LLM kernels via FlashInfer, DeepGEMM, DeepEP, AITER) where they are the right tool. Attention backends are also directly nameable (`--attention-backend`: `mha`, `fa3`, `fa4`, `triton`, `flashinfer`, `trtllm_mla`, `tokenspeed_mla`, …), with a separate `--drafter-attention-backend` for the speculative drafter. FlashAttention 4 support for head_dim=256 was contributed upstream; native FA4 for Qwen3.5 was still in development in the May post.
- **Kernel ergonomics as a feature:** reference implementations as correctness targets, standalone benchmark/profiling harnesses reusing the same registry metadata, numerics checks, and deliberately lean dependencies — the kernel post frames the tight try/verify/benchmark/register loop as what makes kernel development (including by AI agents) tractable.

### 6.3 Speculative decoding

Speculation is a first-class, heavily used feature — unsurprising, since the agentic objective (§1) rewards per-user speed directly:

- **Methods:** EAGLE family (including **EAGLE-4**, served with TorchSpec-trained drafters since October 2026, with dynamic trees from the EAGLE-Harness cost model), **MTP** (the target checkpoint's own multi-token-prediction head as drafter — the common recipe shape: `--speculative-algorithm MTP --speculative-num-steps 3 --speculative-eagle-topk 1 --speculative-num-draft-tokens 4`), **DFLASH / DFlash2** block drafters, and **DSpark** (present in the Kimi K3 recipes).
- **Chains vs trees:** EAGLE3/MTP drafts are chains by default (draft tokens = steps + 1); `--speculative-eagle-topk > 1` drafts a tree (topk ≤ 16, steps ≤ 10, ≤ 64 nodes), which requires the TRT-LLM-family attention backends (`trtllm_mla` / `tokenspeed_mla` for MLA mode).
- **Sampling correctness:** `--enable-speculative-sampling` verifies by rejection sampling so sampled requests keep the target's distribution; EAGLE-4's sampled trees at temperature > 0 are supported on the same basis.
- **Numbers, as reported:** the EAGLE-4 post (LightSeek, October 2026) serves Qwen3.8-27B in BF16 on 4× B300, TP4: single request at temperature 1 decodes at **750 tok/s — 2.85× no-speculation, 1.28× the model's own MTP**; greedy reaches 985 tok/s (3.56× / 1.37×); on an agentic coding workload with sampling, EAGLE-4 gives ~3.0× over no speculation for a single user. The Qwen3.5 post reports MTP adding +100–159% decode throughput at batch 1 on the 397B NVFP4/B200 stack, decaying to near-zero or slightly negative at batch 64 with short outputs — the standard speculation shape (a latency tool whose value peaks at low concurrency), stated by the project itself.
- **The hybrid-state trick worth stealing** (§9.5): speculative verify on recurrent layers traditionally snapshots every step's state and copies the accepted one back — an O(layers × state) copy per decode step. TokenSpeed instead gives each request private *draft rows* in an extended state buffer, lets the kernel write each step's output directly to its row, and records which row is canonical in an index table; accepting is then an O(1) integer write. Move pointers, not data.

### 6.4 The MLA kernel in depth

**What MLA is.** Multi-head latent attention (the DeepSeek-lineage attention used by DeepSeek V3/V4, Kimi K2/K3, LongCat and others) replaces per-head key/value caches with a single shared **low-rank latent vector per token**: instead of caching K and V for every head, the cache stores one compressed latent from which each head's K and V are projected on the fly. The cache shrinks by roughly the head count, and decode — which at long context is dominated by reading the KV cache from HBM every step — reads far fewer bytes. The price is extra projection compute and an awkward kernel shape: the "keys" are latent, the per-head expansion is fused into the attention computation, and in absorbed form the score computation becomes a batched matmul (BMM1) whose M dimension is (query tokens × heads).

**Why agentic workloads make that shape hard.** In ordinary decode there is 1 query token; in speculative/agentic decode there are a handful (a draft chain or tree to verify — batch 4/8/16 with a few query tokens each in the launch benchmarks). Some MLA models also present a small effective head count to the kernel. Either way the BMM1 M tile is badly under-filled: Tensor Cores sit idle because there are not enough query rows to fill the tile, while the kernel is simultaneously streaming an enormous resident prefix (the long cached context that defines agentic traffic). That is precisely the regime TokenSpeed optimised for.

**MLA 1 (Blackwell, May 2026) — what it does.**

- *Decode:* **fold the query-sequence axis into the head axis** — group `q_seqlen` and `num_heads` together so the combined row count fills the BMM1 M tile, restoring Tensor Core utilisation in exactly the small-q, small-head cases above.
- *Prefill:* a **binary-version prefill kernel with a fine-tuned softmax** (the launch blog says it uses NVIDIA-internal knobs to tune the softmax implementation). Prefill here means the agentic prefill shape — a short new chunk attending over a long resident prefix cache — and LightSeek reports it beating TensorRT-LLM's MLA on all five typical prefill workloads of that shape.
- *Combined result, as reported:* with the rest of the engine's optimisations, MLA decode latency is **nearly halved versus TensorRT-LLM** on typical speculative-decoding workloads at batch sizes 4, 8 and 16 with long prefix KV cache (LightSeek's own benchmark, B200; §7 collects the end-to-end figures).

**Adoption by vLLM — the evidence.** LightSeek's launch blog and README state TokenSpeed MLA "has been adopted by vLLM", linking to vLLM. Independent corroboration found in this pass: the **vLLM v0.33.0rc3 release notes** (November 2026, via a release-notes index) list **"TokenSpeed MLA 2.0.3" among vLLM's pinned dependencies** (PRs #61125, #61689) — i.e., vLLM ships the `tokenspeed-mla` package as a dependency, which is adoption in the concrete, package form. The `tokenspeed-mla` package itself is published standalone on PyPI for SM100/SM103/SM107 (Blackwell-family) parts, compiling its CuTe DSL / Triton kernels at runtime; LightSeek reports it passed **2 million monthly downloads** by October 2026 (their figure, sourced to PyPI stats). **[Unverified]:** which vLLM version *first* integrated it, and whether it is vLLM's default MLA backend or an opt-in on any given hardware — not established from primary sources in this pass (§10). A secondary deployment guide's claims of a `VLLM_USE_TOKENSPEED_RUNNER=1` runner mode and a special vLLM image tag were **not** found in any primary source and are treated as unverified.

**MLA 2 (Vera Rubin, October 2026).** The successor kernel retargets the same ideas at NVIDIA Vera Rubin and at Kimi K3's shape (96 query heads, 4 or 8 query tokens):

- Built on a FlashInfer-derived pipeline, restructured from MLA 1's single alternating CTA pair (M128 tiles, QK and PV alternating, K=32-byte MMA) into **two CTA pairs with QK+softmax separated from PV** so the stages overlap across tiles, M256 tiles reusing KV across 256 query-head rows, K=64-byte FP8 MMA, queries resident in tensor memory, probabilities passed between pairs through distributed shared memory.
- **Native query-row packing:** instead of padding Kimi K3's 96 heads to 128 and splitting Q8 into two Q4 requests (the adapted-FlashInfer baseline: 4 tiles at 75% useful rows), MLA 2 packs each token's 96 heads consecutively — Q8 fits 768 useful rows into 3 fully occupied tiles. Plus tuned KV-split selection (splits cost pipeline/reduction overhead; full grids are left unsplit) and a tuned reducer.
- *Results, as reported, kernel latency only:* on the same Vera Rubin GPU, geometric-mean speedup **1.142× over recompiled MLA 1** (1.271× at Q8, 1.027× at Q4 — Q4's final tile is only 75% occupied) and **1.327× over the adapted FlashInfer baseline**; the headline **up-to-3.44× over MLA 1 on B200 / 2.84× over GB200** figures compare *across hardware generations* and confound hardware and software, as the post itself cautions. Small-batch gains are limited by pipeline fill/drain, split reduction and fixed launch costs — again, stated by the project.

**Why vLLM adopted it, in one sentence:** MLA is the attention of the current frontier-model generation, decode over long latent caches is the bottleneck of serving those models to agents, and TokenSpeed's kernel was — by its authors' benchmarks, unrebutted in any source read — the fastest available open implementation for exactly that shape on Blackwell, packaged so another engine could take it as a dependency without taking the engine.

## 8. Strengths / weaknesses

### Strengths

- **The objective function is the contribution.** Naming per-user TPS as a floor and TPM/GPU as the maximand reorganises every downstream decision — scheduler policies protect decodes, kernels optimise the few-query-tokens-over-huge-prefix shape, speculation is a headline feature rather than an add-on. Engines that "also serve agents" optimise a chat-shaped objective and inherit agent-shaped disappointments.
- **Correctness engineered into the scheduler's types.** The C++ FSM with ownership semantics makes whole classes of cache bugs unrepresentable, and the design docs reason about failure interleavings (transfers in flight, write-back ACKs landing plans later, compaction racing retraction) at a level of rigour no other engine in this corpus publishes. The docs themselves — scheduler, cache concepts, numerics, event loop — are public, current, and written as specifications.
- **Retraction done right.** Suspend-by-image with exact restore (§3.5) is strictly more humane than recompute under pressure, and the grant-to-the-blocked-admission retry loop shows the same care at the mechanism level. The abort fallbacks are bounded, named, and client-visible rather than silent.
- **The cache thinks in turns.** Published tails, junction cuts, in-forward checkpoints, dead-checkpoint suppression, superseded-turn eviction (§4.2, §4.4) — a set of small, precise mechanisms aimed at exactly how multi-turn traffic actually re-renders prompts. This is the deepest multi-turn cache engineering in the corpus alongside SGLang's unified tree, and it is more *surgical*: SGLang generalised the tree; TokenSpeed optimised which boundaries exist.
- **Kernels as a separable, adoptable product.** The registry/plugin layer (§6.2) plus standalone packaging is why the MLA kernel could be adopted by vLLM at all — the project's influence already exceeds its own deployment footprint, by design.
- **Day-0 frontier breadth across two vendors.** Kimi/Qwen/DeepSeek/GLM-class MoE and hybrid models on NVIDIA and AMD flagship parts, on the models' own launch days, with quality-parity claims the Kimi K3 post states explicitly (scores matching reference within noise on both platforms).

### Weaknesses

- **Altitude.** Everything assumes datacentre GPUs — Blackwell first (the flagship MLA kernel is SM100-family only; Hopper falls back to other MLA backends with BF16 KV), Hopper and AMD CDNA as supported seconds, RDNA4 only as a portable-Triton dense-BF16 path. There is no CPU path, no Apple path, and no small-model story in any source read; the one sub-1B appearance (Qwen3-0.6B) is a smoke-test recipe for RDNA4 bring-up. The runner container demands 32 GB of shared memory and privileged host networking in the getting-started guide — a fleet appliance, not an application.
- **Youth and churn.** Six months old at access time; nightly-first versioning (0.1.x), separately versioned components (kernel 0.1.4rc, MLA 2.0.3, scheduler on its own release pipeline), biweekly stables, and design docs that describe behaviour at a granularity the code must be moving under constantly. The May "preview" label may be stale, but nothing found replaces it with a stability commitment.
- **Complexity density.** The scheduler design doc alone runs to four-figure line counts of edge-case law (victim ranking under in-flight forwards, write-back segment settlement, PD pin states). This is the honest cost of the correctness programme in §3 — and it means the system's behaviour under pressure is effectively unknowable without reading the spec, and unimplementable without re-deriving it.
- **Unscaled FP8 KV is a real restriction** (§6.1): checkpoints and pipelines built around calibrated KV scales are rejected, not adapted.
- **The gateway is a second system.** SMG owns the chat template, history storage, routing and much of the API surface; operating TokenSpeed means operating (or trusting) LightSeek's gateway too. Dynamo support softens this on NVIDIA stacks only.
- **Benchmarks are single-source** (§7), and the two most-quoted (launch Pareto, 580 TPS) are launch-window artefacts on hardware (B200) almost nobody reading this dossier has.
- **RL-serving scope bleed** (§5.3): weight-update sessions, bitwise trainer-parity numerics and discard policies are fleet-training infrastructure riding in a serving engine — more surface, more config, more ways to misconfigure a plain deployment.

### Fit / misfit for a 6 GB single-user Go runner

**As software: a total misfit, more complete even than SGLang's.** TokenSpeed needs a datacentre NVIDIA or AMD GPU, a containerised privileged deployment, a Rust gateway, and a frontier MoE checkpoint to be about anything at all. Its smallest verified recipes are single-GPU bring-up tests; its design centre is 8×B200. On a 6 GB card there is no configuration in which it boots meaningfully, and its model zoo (GGUF absent from all sources) does not intersect the local ecosystem.

**As a design catalogue: unusually relevant, because the workload shape matches.** A long persona chat *is* an agentic workload at fleet size one: a huge stable prefix (character, lore, history), small appended increments per turn, tool-like side calls, long idle gaps (the user thinking, the user away), and a hard per-user latency floor — there is no aggregate throughput to trade latency against, so TokenSpeed's inverted objective is literally our objective. §9 grades the individual ideas.

## 9. IDEAS TO STEAL

Graded for one case only: long single-user persona chat on ~6 GB of GPU memory, in a Go runner, with GGUF-class GQA models. Each idea states the transfer, the expected gain, and the honest cost or non-transfer.

### 9.1 The objective, stated as a constraint — steal verbatim

**The steal.** Write the fork's scheduling objective the way TokenSpeed writes its own: *maximise useful work per GPU-minute subject to a per-user latency floor* — for us, a floor on streaming smoothness (inter-token latency) and time-to-first-token for the one user, treated as a constraint that other optimisations may not violate, rather than as a metric to glance at. Concretely this changes small decisions everywhere: sidecar generations (summaries, memory extraction) yield to the visible reply the way TokenSpeed's prefills yield to decodes; cache eviction protects the live conversation the way its policies protect in-flight work; "throughput" features (batching sidecars together) are adopted only when they do not tax the floor.

**Expected gain.** Not a speedup — a *priority discipline* that prevents the classic single-user failure of fleet-derived designs: optimising an aggregate nobody experiences while the one user's stream stutters. It costs nothing to adopt and is the cheapest item in this dossier.

### 9.2 FSM ownership for KV resources — steal the discipline, in Go types

**The steal.** TokenSpeed's deepest idea is not C++ — it is that cache-resource ownership is a *state machine with types*, so illegal reuse cannot be expressed. A Go runner can carry the same discipline in one language: model every KV block/page and every recurrent-state slot as a value with an explicit state (free / owned-by-request / published-in-cache / pinned-by-transfer-or-image / in-flight), allow transitions only through named operations, and make publication, copy-on-write and release the only ways states change. The PD-pin lesson generalises: any "must not free while X" flag should be *derived from state*, never stored beside it.

**Expected gain.** The bugs this prevents are the worst class in a persistent-cache runner (§9.3's tree makes them possible): silent output corruption from stale or double-owned KV, which users experience as a character "going weird" and which no test catches reliably. The cost is design effort up front and some ceremony in the allocator — modest in Go, where the state machine can be a small, heavily tested core. **[Assessment]:** of everything in TokenSpeed, this is the piece most likely to still matter to the fork in five years.

### 9.3 Suspend-by-image retraction — steal; it is the 6 GB pressure valve

**The steal.** When GPU KV space runs out mid-conversation, TokenSpeed images the victim's blocks to pinned host memory byte-for-byte and restores them exactly, publishing the frontier first so the suspended work doubles as cache. Translate directly: when the 6 GB pool fills (a second chat opened, a long context spike, a sidecar generation), **spill the coldest conversation's KV pages to host RAM as an image and restore them on return**, instead of discarding and re-prefilling. The refinements worth copying with it: (a) publish-before-image, so a suspended conversation's prefix is matchable by its own next turn even while suspended; (b) the snapshot area is request-private, bounded, and sized as a deliberate fraction of the GPU pool (their default 0.1× for whole images is a sane starting ratio); (c) if the image cannot fit, fail *visibly* (their abort) rather than silently recomputing — the user should learn "this chat was closed to free memory", not experience a mysterious minute-long pause; (d) grant freed pages to the specific request that was blocked, in the same scheduling pass.

**Expected gain.** On 6 GB, this is the difference between "switching chats costs a full re-prefill of tens of thousands of tokens" and "switching chats costs a PCIe copy". Host RAM is the one resource a small machine has in relative abundance. It is also the graceful-degradation tier vLLM V1 deliberately deleted and SGLang only reaches via fleet storage — for a single user it is simpler than both: one machine, one spill target, no network.

**Cost / risk.** The image must capture *everything* needed for exact resume (their blob carries sampling state and speculative readiness, not just KV — a chat resume needs sampler/RNG state and any recurrent-state slots too), and restore must be atomic with respect to model/template changes: an image taken under different weights or a different template is stale KV and must be invalidated, the way their L3 is namespaced by weight version. Budget a version stamp on every image.

### 9.4 Turn-shaped cache boundaries — steal selectively

**The steal.** Three of TokenSpeed's small mechanisms translate one-for-one to a radix/paged persona cache (assuming the fork has one, per the SGLang/vLLM dossiers):

- **Published tails:** let a cache entry end at the exact token where a turn ended, not only at page boundaries — the next turn's hit then covers the whole previous turn, not all-but-15-tokens of it.
- **Next-turn checkpoint placement (their in-forward checkpoint, miniaturised):** when finishing a turn, deliberately leave a reusable checkpoint at the boundary the *next* turn will actually resume from — which, because chat UIs re-render (system prompt + history + reply), is typically the end of the re-rendered history, not the raw generation end. Know your client's re-render shape and checkpoint for it.
- **Superseded-turn eviction:** when a conversation advances, its two-turns-back checkpoint is usually dead weight; evicting it early keeps live prefixes resident longer in a tiny pool. Their rule (evict the earlier checkpoint once a newer one is published past it, unless someone else resumed from it) is directly implementable as an eviction hint.

**Expected gain.** Each mechanism is worth a few percent of hit rate individually; together they attack the specific misses a naive page-aligned cache suffers on *every turn boundary* — which, in a chat, is every interaction. **Cost:** tail entries complicate the allocator (copy-on-write for the shared tail page — steal theirs: copy the tail out, keep the source pinned until the copy lands). The checkpoint-placement piece requires the runner to know the client's re-render behaviour, which couples engine to app — acceptable in a fork that ships both.

### 9.5 Move pointers, not data — steal the pattern

**The steal.** TokenSpeed's speculative-state trick (§6.3) — write each candidate state to its own row, record the canonical row in an index, accept by updating the index — is a general pattern: wherever the fork copies a large state to commit a small decision (accepting a draft token, forking a swipe, checkpointing a recurrent state, snapshotting for §9.3), first ask whether an indirection table can make the commit O(1). Swipe branching in particular: a fork should share pages and record divergence in the block table, never copy the trunk.

**Expected gain.** Small per operation, but these operations sit on the per-token and per-turn paths; on a memory-bandwidth-starved 6 GB card, avoided copies are avoided latency. **Cost:** indirection complicates every consumer of the state; apply it where a profile shows the copy, not everywhere.

### 9.6 The capacity model as a pre-flight check — steal, cheaply

**The steal.** One config-only function that answers "what is the worst-case memory of N live requests of length L on this model?" — used both to size the pool at startup and to admit/reject work, with a swept invariant that the two uses agree. For the fork: a startup report that states, for the loaded model on this GPU, the maximum conversation length and branch count the pool can guarantee — and admission that refuses (visibly) beyond it instead of thrashing. Persona-chat users plan around honest limits far better than around mid-chat degradation.

### 9.7 What does NOT transfer — stated plainly

- **The MLA kernel.** Our models are GQA/MHA GGUF models; there is no latent cache, no Blackwell Tensor-Core tile to fill, and at batch 1 with a handful of query tokens the entire problem the kernel solves does not exist. Its adoption by vLLM is a fact about the frontier-serving world, not an opportunity for the fork. The only transferable residue is the *shape of the thinking*: find the axis along which your kernel's tiles are under-filled (for us: small-batch GEMV behaviour in GGUF decode) and fold axes until they fill.
- **The SPMD/collective compiler, split TP/EP/KVP/DCP, PD/EPD disaggregation, Mooncake L3, SMG.** All are multi-GPU or multi-node machinery. A single 6 GB GPU has no collectives to generate and no peer to disaggregate to. KVP's *idea* (shard the history, not just the weights) has a single-device echo — shard history across GPU and host RAM, which is §9.3 — but the mechanism itself does not transfer.
- **FP8/NVFP4 frontier quantisation and unscaled FP8 KV.** GGUF's K-quants are the fork's ecosystem; TokenSpeed's quantisation world (calibrated FP8, NVFP4 MoE checkpoints, Quark MXFP4) does not intersect it, and its unscaled-KV restriction is a warning about a trade we are not being offered.
- **EAGLE-4 / TorchSpec speculation.** The supply-chain problem from the SGLang dossier applies unchanged: drafters are trained per target model by a separate project. MTP heads, where a local model happens to ship one, remain the only speculation with a plausible local path — and that is a property of the model, not of TokenSpeed.
- **The TPS-floor numbers.** 70–200 TPS/user is a datacentre agent figure. Our floor is human reading speed and streaming smoothness; importing their numbers as targets would be exactly the vendor-claim adoption this dossier is forbidden from making.
