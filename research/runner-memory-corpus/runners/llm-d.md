## Essence

llm-d is not an inference engine either. It is the **Kubernetes-native orchestration layer above inference engines** — but where Dynamo (§9) builds its own frontend, discovery and event planes as a vendor platform, llm-d deliberately builds almost nothing it can borrow from Kubernetes: a standard Gateway API proxy (Envoy-family) owns the data plane, a Go **Endpoint Picker (EPP)** owns only the placement decision, Kubernetes custom resources (`InferencePool`, `LeaderWorkerSet`) own discovery and topology, KEDA/HPA own scaling actuation, and the engines (vLLM first, SGLang second) own everything about actually running a model. Its founding moves are the same family as Dynamo's — **route by KV-cache locality**, **disaggregate prefill from decode**, **tier the KV cache** off the accelerator, **scale against inference signals rather than CPU** — expressed as composable Kubernetes pieces under multi-vendor, foundation governance instead of as one company's integrated system. The price of admission is stated in its first sentence everywhere it describes itself: this is a stack *for production deployments on Kubernetes*. No cluster, no llm-d — a fact §7 and §8 take seriously.

## 2. Architecture in our own words

The architecture documentation organises llm-d into seven functional areas — Router, Model Servers, Disaggregation, KV Cache Management, Model Server Orchestration, Autoscaling, and Batch/Async Serving. The model underneath them:

### 2.1 The Router: a borrowed proxy plus a decision service

The llm-d Router has two parts, and the split is the project's signature act of restraint:

- **The Proxy** is *not* llm-d code. Any L7 proxy conformant with the Gateway API Inference Extension (GAIE) does the data-plane work — connection handling, TLS, forwarding. Documented options span self-managed Envoy-family gateways (Istio, agentgateway, Envoy AI Gateway) and cloud-managed services (Google's Application Load Balancer / GKE Inference Gateway). llm-d supplies tooling to install one, but the proxy is a commodity it plugs into.
- **The Endpoint Picker (EPP)** is llm-d's own Go service and the only place routing intelligence lives. For every request, the proxy *parks* the request and consults the EPP over Envoy's external-processing protocol (`ext-proc`, a gRPC callback); the EPP evaluates the request against the current pool state and returns the chosen pod's address; the proxy then forwards the original request there. The EPP itself contains the request handler (parsers for OpenAI-style and vLLM gRPC request formats), the flow-control layer (§3.4), the request scheduler (§3.1), and an asynchronous data layer that watches the Kubernetes API for pool/pod state, scrapes model-server metrics, and maintains the prefix-cache structures §4 describes.
- **InferencePool** is the Kubernetes custom resource that binds the two together: a label selector defines which model-server pods are candidates, target ports define where they listen, and a reference to the EPP tells the Gateway controller where to attach the `ext-proc` callout. One pool ≈ one logical model deployment, namespace-scoped.

Two deployment shapes follow: **Gateway Mode**, where an existing Gateway API gateway is the entry point (the GKE Inference Gateway is this, managed), and a standalone mode where the project deploys the proxy itself. Either way the EPP contract is identical.

### 2.2 The GAIE relationship, as documented

The Kubernetes Gateway API Inference Extension (kubernetes-sigs) is the upstream standards project: it owns the `InferencePool` API, the endpoint-picking protocol between proxy and picker, and the conformance tests. llm-d describes itself — in the CNCF announcement's words, in substance — as **a primary implementation of GAIE**: its EPP is the production picker, where GAIE's own bundled lightweight picker is explicitly a conformance/reference implementation not recommended for production. The traffic also flows the other way: the scheduler repo's stated working rule is that general-purpose scheduling capabilities go *upstream to GAIE first* where applicable, with llm-d's own repos holding the pieces that need deep integration with the wider llm-d stack or are still experimental. In 2026 the GAIE project's own notice records the EPP and its associated APIs *moving out* of the GAIE repository into `llm-d/llm-d-router` — the standard's reference implementation and the project's picker have effectively merged homes, with GAIE retaining the API and conformance suite. Net: GAIE is the contract, llm-d is the implementation that matters, and neither is much use alone — the contract without the picker routes nothing intelligently; the picker without the contract is a proprietary sidecar.

### 2.3 Disaggregated serving and large-model topologies

- **Prefill/decode disaggregation.** Prefill-role and decode-role pods form separate pools. The EPP runs two scheduling profiles for one request (§3.5), returns the *decode* pod as the proxy's destination, and injects the chosen *prefill* pod into the request as a header; a sidecar beside the decode worker reads that header and coordinates the remote prefill, after which the KV blocks move prefill→decode over **NIXL** on RDMA fabric (the same NVIDIA transfer library Dynamo uses — infrastructure escaping its maker, as in the Dynamo dossier §2.1). The 0.9 line adds encode as a third role for multimodal (E/P/D, with SGLang), and revision-aware routing so a rolling update never pairs a prefill pod and a decode pod running different checkpoints.
- **Wide expert parallelism.** For MoE models too large or too sparse for one node: data-parallel attention combined with expert-parallel MLP layers across multi-node slices, with rank-aware routing in the EPP.
- **Orchestration objects.** Multi-node pod groups are deployed via **LeaderWorkerSet (LWS)**, the Kubernetes SIG controller for leader/worker accelerator groups with gang scheduling; llm-d's own **DisaggregatedSet** controller manages prefill/decode topologies as synchronised, versioned units so the pools roll and scale as one logical deployment (1.0's lockstep upgrades; it requires a current LWS, per the 1.0 release notes as reported).

### 2.4 The well-lit paths: opinionated shapes as a product surface

Instead of shipping a toolkit and a tuning manual, llm-d ships **well-lit paths**: benchmarked, tested deployment recipes (Helm charts + guides) for the shapes the project actually recommends, with published results inspectable in its **Prism** benchmark dashboard. The flagship is the **Optimized Baseline** — one homogeneous pool of model servers behind the Router with prefix- and load-aware scoring — which the README names as where most users should start and the quickstart deploys. Around it, composable paths add one capability each: **Precise Prefix-Cache Routing** (§4.2), **Tiered Prefix Cache** (§4.3), **Prefill/Decode Disaggregation**, **Wide Expert Parallelism**, **Predicted-Latency Routing**, **Flow Control**, **Autoscaling** (§3.6), **P2P KV-Cache Sharing**, **Fast Model Actuation** (peer-to-peer weight loading to cut replica cold start, added in the 0.9 line), and batch/async serving. The well-lit path is itself an architectural position: the project's answer to "distributed inference has fifty knobs" is a small set of pre-tuned, end-to-end-tested configurations whose benchmark contexts are published — the same institutional habit as Dynamo shipping its measuring instruments (Dynamo dossier §5.2), expressed as recipes rather than tools.

## 3. Scheduling & routing

### 3.1 The pipeline: producers → filter → score → pick

Every request passes through the EPP's scheduling cycle, organised as configured **profiles**, each profile being a pipeline:

1. **Data producers** prepare per-request, per-endpoint facts before scoring: a token producer that tokenises the prompt (exactly, via a vLLM render endpoint, or approximately), prefix-cache producers that compute each candidate's prefix-match information (§3.2), session-state producers, and the data layer's continuously scraped endpoint metrics (queue depth, running requests, KV-cache utilisation).
2. **Filters** remove candidates that cannot or should not serve the request: role filters (prefill / decode / encode), label-selector filters, an SLO-headroom-tier filter, and a prefix-cache-affinity filter that can narrow the field to cache-sticky endpoints — with a documented escape: a TTFT load gate that breaks stickiness when the sticky endpoints are enough slower than the rest.
3. **Scorers** each assign every surviving endpoint a normalised score in [0.0, 1.0]; the profile combines them as a **weighted sum** (the documentation's own worked example: scores 0.8 at weight 2.0 and 0.5 at weight 1.0 combine to 2.1).
4. **Pickers** choose from the scored list: `max-score-picker` (the default; highest score wins), `random-picker`, and `weighted-random-picker` (scores as lottery probabilities — the same anti-stampede idea as Dynamo's router temperature, Dynamo dossier §3.1).

A **profile handler** decides which profiles run and merges their results: `single-profile-handler` for ordinary pools, `disagg-profile-handler` for §3.5. Plugins carry a formal maturity lifecycle (Alpha/Beta/Stable, with experimental plugins gated behind an explicit opt-in flag in the 0.9 line) — the pipeline is a public extension surface, and the project treats it as one.

### 3.2 The scorer catalogue (as documented)

- **`prefix-cache-scorer`** — the signature scorer: scores by the length of the request's prefix already resident on the endpoint, fed by either the approximate or the precise producer (§3.3). In the tiered-cache configuration a *second* instance of it scores the CPU tier separately, so "prefix resident in host RAM" counts, at its own weight.
- **`queue-scorer`** — prefers shorter request queues. **`kv-cache-utilization-scorer`** — prefers lower KV-cache utilisation (headroom, and less eviction pressure). **`token-load-scorer`** — prefers lower queued/in-flight token load. **`running-requests-size-scorer`** — prefers fewer active requests.
- **`latency-scorer`** — scores by predicted-latency headroom against the request's SLO, fed by the Router's **latency predictor**: a sidecar that trains online regression models on completed requests to predict per-endpoint TTFT and per-token latency. Predicted-latency scheduling graduated from experimental during 2026 (the v0.7 notes list it as GA).
- **`session-affinity-scorer`** — maximum score to the endpoint that served this session's earlier turns, minimum to all others; the blunt instrument version of prefix affinity, for state the prefix index cannot see.
- **`lora-affinity-scorer`** — prefers endpoints already running the requested LoRA adapter or with capacity to load it.
- **`no-hit-lru-scorer`** — for requests with *zero* cache hits anywhere, prefers endpoints that have never taken a cold request, then least-recently-used ones, so expensive cold prefills spread across the fleet instead of piling onto whoever the other scorers favoured; inert when hits exist.
- GPU-utilisation scoring joined in the 0.9 line (scoring on measured accelerator utilisation via DCGM telemetry rather than inferring load from queue signals alone).

The **Optimized Baseline's** default combination, per Red Hat's developer documentation of the current line, is the prefix-cache scorer plus the queue scorer with **prefix weighted higher**, with a load-aware scorer added when balance matters more than reuse; the 0.9 release then made **sticky-until-saturated** the default strategy across the guides — stick to the best prefix match until that endpoint crosses a saturation threshold, then spill to the next-best. The direction of travel across versions is consistent: cache affinity is the primary signal, load is the constraint that keeps affinity honest.

### 3.3 Prefix-cache awareness: two ways of knowing

The EPP's central problem is epistemic: *what KV lives where?* llm-d ships two answers, and the contrast between them is the cleanest statement of the design's honesty about its own knowledge:

- **Approximate (the baseline default).** The EPP remembers *its own routing history*: it splits the incoming prompt into fixed-size blocks (64 tokens by default, estimated from characters — no tokeniser involved), builds a rolling hash chain over them, and keeps an in-memory LRU index of which prefix hashes it has previously sent to which pods. After each decision it updates the index on the assumption the chosen pod now holds that prefix. Cost: almost nothing — no tokeniser, no connection to the model servers. Failure mode, documented plainly: the index *diverges from reality* whenever a pod evicts a prefix under memory pressure, because nothing ever tells the EPP.
- **Precise (the advanced well-lit path).** The EPP stops guessing and subscribes to the truth (§4.2): the engines emit KV-cache events on every block creation/eviction, an indexer inside the Router maintains the fleet-wide block→pod map, a token producer obtains exact token IDs (via a vLLM render endpoint, typically a GPU-less render sidecar), and the scorer works from the longest *consecutive* prefix each pod verifiably holds. Cost: the render endpoint, the event connectivity, and the indexer's resources. The project's own benchmark of the difference is §6's most dramatic entry — under its (prefix-heavy, saturating) test workload the approximate mode was not a slightly worse precise mode; it collapsed, because at that scale its assumptions stopped being true.

### 3.4 Flow control: admission before placement

Scheduling decides *where*; flow control decides *whether and when*. The EPP can hold requests in an in-memory queue when the pool is saturated (a pluggable saturation detector, in the documented default based on per-endpoint in-flight concurrency), ordered by **priority bands** (latency-sensitive traffic ahead of batch), with fairness policies distributing dispatch opportunities among flows inside a band so one tenant cannot monopolise the pool. The 1.0 line graduates this into the headline multi-tenant QoS feature: priority- and fairness-aware flow control with controlled load shedding (a probabilistic admitter under overload; an exhausted band answers 429, an empty pool 503 — backpressure semantics a client can act on). Dynamo's Planner solves the overload problem by *changing capacity*; llm-d's flow control solves it by *ordering and refusing demand* — and §3.6's autoscaling then changes capacity on a slower clock. The two systems' emphases differ here in a way §9 uses.

### 3.5 Disaggregated scheduling

In a P/D deployment the disagg profile handler runs a prefill profile and a decode profile for the same request — each with role filters and its own scorer mix (prefix affinity and token load weigh naturally on the prefill side) — then merges: decode endpoint as the destination, prefill endpoint as the injected header (§2.3). The handler can also decide a request needs *decode only* (its KV is already transferred/resident) — the decision is counted in the EPP's disaggregation metrics by type (decode-only, prefill-decode, and the encode-including variants).

### 3.6 Autoscaling signals

llm-d's autoscaling doctrine, stated in its architecture docs in substance: **accelerator utilisation is an unreliable load signal** (a GPU sits near 100% during ordinary batching, saturated or not), so scaling must run on inference-native signals **exported by the EPP itself** — queue depth, running concurrency, pool saturation ratio, token backlog (seconds of queued prefill work plus KV occupancy), or estimated latency against an SLO. The recommended mechanism is deliberately unoriginal: **KEDA** reads those EPP metrics through Prometheus and owns an ordinary HPA that scales the model-server deployments; scale-to-zero is supported for intermittent workloads. The SLO-aware variant closes the loop through the latency predictor: scale on *predicted headroom* against the latency target rather than on a utilisation threshold already breached.

The project's own earlier answer is a cautionary exhibit: the **Workload Variant Autoscaler (WVA)** — a global optimiser that placed model variants across heterogeneous accelerators cost-optimally — was introduced experimentally in v0.4, iterated through v0.5 (saturation-based scaling, scale-to/from-zero with an activator), and is **deprecated** in the current docs in favour of KEDA + EPP, with its one un-replaced capability (cost-aware placement *across* variants) honestly listed as having no equivalent. Even a project this fond of building its own pieces retired its bespoke autoscaler for the ecosystem's standard one when the standard one could read good signals — the same lesson Dynamo's KVBM retirement teaches (Dynamo dossier §4.2), in a second organisation.

## 4. KV & memory design

### 4.1 The stance: KV state as a routing signal first, a capacity problem second

llm-d's KV design has three documented pillars plus a sharing layer, and their *order* is the design: **indexing** (know what lives where) feeds **routing** (send work to the state), while **offloading** (grow the state beyond HBM) and **P2P sharing** (move state between peers) enlarge what the first two can exploit. The cache is not managed for its own sake; it is managed so the scheduler's view of it stays true and large.

### 4.2 The indexer: how the EPP learns what KV lives where

The precise mode's indexer (the `llm-d-kv-cache` Go library, running inside the Router) works as follows, as documented:

- **Events.** Model servers (vLLM and SGLang today; the docs name TensorRT-LLM as also publishing) emit **KV events** over ZeroMQ whenever their cache state changes, in three types: a *stored* event (blocks with given content hashes created on a specific memory tier — payload carries the chained parent hash, the token chunk, any LoRA identity, and any multimodal extra keys), a *removed* event (blocks evicted from a tier/attention group), and an *all-cleared* event (the pod dropped its whole cache; the indexer drops every entry for that pod).
- **Delivery.** Two topologies: centralised (every pod publishes to one endpoint the EPP subscribes) for single-replica EPP, or **pod discovery** (each pod binds its own socket; every EPP replica discovers pods by label selector and subscribes to *every* pod independently, so replicas converge to the same index without coordination) for active-active EPP.
- **The index.** A map from **block key → set of pods** (with tier), where block keys are chained hashes over the token blocks — a block's key commits to its whole prefix, which is what makes the scorer's rule below well-defined. Documented backends: an **in-memory two-level LRU** by default (outer cache keyed by block hash, inner by pods per block; the docs give a default sizing on the order of 100M keys × 10 pod entries), a cost-aware cache variant budgeted in bytes for variable-size entries (multimodal/LoRA metadata), and an external Redis/Valkey option for deployments wanting a shared, persistent index — at a network hop per lookup, and noted as rarely necessary.
- **Scoring against the index.** For a request, the precise producer derives the block-key chain from the exact tokenisation and the scorer finds, per pod, the **longest consecutive prefix** present: because block *i* is only reusable with blocks *0..i−1* in hand, a pod holding blocks 3–4 but not 0–2 scores zero for them. Matches are weighted by tier (documented defaults: GPU 1.0, CPU 0.8; the maximum across tiers when a block lives in several), then normalised to [0,1] for the pipeline of §3.1. Multimodal content hashes and LoRA identity are folded into the key chain, so same-text/different-image prompts and different-adapter prompts index independently. Hybrid-attention models (per-layer-group caches that evict independently) are documented as a work-in-progress scoring problem, stated as such rather than solved on paper.
- **Speculative indexing.** Events confirming a routing decision arrive *after* it. With speculative indexing enabled, the producer inserts short-lived predicted entries for the chosen pod immediately after the pick (documented default TTL 2 s), so a back-to-back follow-up turn sees the affinity before the confirming event lands; entries expire if the event never confirms them. A small mechanism, and the one that most plainly shows the designers thinking about the index as a *belief system* with a freshness budget rather than a database.

The project's own scale note for the index (from the precise-routing blog's appendix): the index stores hashes, not tensors — on its worked example (a 365 GB fleet KV pool in 128-token blocks of ~8.6 MB), the block metadata is on the order of hundreds of KB, a data-to-metadata ratio it puts above a million to one. Indexing the fleet's cache is cheap; *not* indexing it is what costs (§6).

### 4.3 Offloading: tiers llm-d orchestrates but mostly does not implement

Here the Dynamo dossier's discipline — *integration vs implementation kept separate* — matters most, because llm-d's offloading story is deliberately mostly other people's code:

- **What is llm-d's own:** the indexer above (including its awareness of offloaded tiers — a CPU-tier block is indexable and scoreable, §3.2's second prefix scorer); an **llm-d filesystem backend** for vLLM's offloading connector (storing blocks on shared/local storage, shipped in the v0.5 line) with a Kubernetes-side PVC evictor utility; and the well-lit path configurations that wire tiers together (the Tiered Prefix Cache guide: HBM → CPU RAM by default, optionally → shared filesystem, filled lowest-latency-first).
- **What is the engine's:** the actual tiering machinery in the default path is **vLLM's native OffloadingConnector** — CPU RAM as primary tier (asynchronous DMA-staged transfers), with a multi-tier spec staging secondary tiers (filesystem, object store, peers) through the CPU tier; **SGLang's HiCache** plays the same role on that engine.
- **What is out-of-tree ecosystem:** connectors that plug into the engines' KV-connector APIs and own their own indexing/storage — the offloading documentation names **LMCache**, **Mooncake** and NVIDIA's KVBM as the examples. Google's 1.0 post says the same in production language: when accelerator memory fills, llm-d deployments move KV to host memory and then to SSD/shared storage *using* vLLM's OffloadingConnector, Mooncake, or SGLang's HiCache.
- **P2P sharing** composes the pillars: the index knows a peer holds the prefix, the Router marks the request with that source, and the model server pulls the blocks directly from the peer's **CPU tier over NIXL** — the source pod's GPU is never touched, and a lookup miss or partial match degrades to ordinary recompute rather than failing the request.

So the accurate sentence is: *llm-d implements the fleet's knowledge of the KV cache (indexing) and its exploitation (routing); the cache's tiered storage itself is implemented by the engines and the connector ecosystem, and llm-d's job is to make their state visible and their capacity addressable.* That is a different division of labour from Mooncake — which built the store itself for its own fleet (`papers/mooncake.md`) — and llm-d's relationship to Mooncake/LMCache is therefore **integration and lineage, not descent**: the LMCache project's home lab was a launch supporter, Mooncake's store/transfer machinery is a named backend option in the same connector ecosystem llm-d orchestrates, and no source read for this dossier claims llm-d implements, ports or forks either.

## 5. Engine relationship

### 5.1 vLLM-first, as documented

Every layer of the project's self-description puts vLLM first: the CNCF project summary describes llm-d as built on vLLM and GAIE; the launch material calls it vLLM-based distributed inference; the architecture docs name vLLM the **default engine** (PagedAttention, native tiered offloading, NIXL connector for disaggregation, wide expert parallelism); the quickstart and flagship guides deploy vLLM (the 1.0 quickstart's reference example is a two-replica Qwen3-32B vLLM deployment); the precise-routing machinery consumes vLLM's KV events and its render endpoints for tokenisation. **SGLang** is the documented second engine — RadixAttention, HiCache tiering, Mooncake/NIXL transfer backends, and the E/P/D heterogeneous topologies — and the 1.0 architecture docs also list **TensorRT-LLM** (`trtllm-serve`) among model servers. Support depth is not uniform across the three, and the docs do not pretend otherwise: the guides, event machinery and offloading paths are vLLM-centred, SGLang-complete in the areas named, and thinner beyond that.

### 5.2 What llm-d is not

llm-d contains no inference engine: no attention kernels, no GEMMs, no sampler, no quantisation formats, no model implementations, no weight loading of its own (Fast Model Actuation moves *other* pods' loaded weights peer-to-peer; the loading is still the engine's). A deployment's per-token speed, model coverage and hardware floor are its chosen engine's. Nor is it the neighbouring layers it touches: it is not a general API gateway (it borrows GAIE proxies and explicitly leaves auth/rate-limit/API management to them or to fronting gateways), and it is not a high-level serving control plane like KServe — the CNCF announcement positions it as *bridging* between such control planes above and engines below. What llm-d owns is exactly the middle: placement, cache knowledge, phase topology, admission, and the signals scaling runs on.

**Precise prefix-cache scheduling (project blog, 2025-09-24) — the best-contextualised claim in the set:**

- **57× faster response** (p90 TTFT 0.542 s for precise scheduling vs 31.083 s for the approximate scheduler; over 170× vs random scheduling) and **~2× the throughput** of the cache-blind configurations (8,730 output tok/s vs 4,428.7 for load-only and random; +25% over approximate), on **identical hardware**: 8 vLLM pods on **16× NVIDIA H100**, Qwen-32B (appendix: Qwen/Qwen-32B), workload simulating 150 enterprise customers with 6,000-token shared contexts, 5 concurrent users each submitting 1,200-token queries, load ramping 3–60 QPS, total KV demand ≈73% of cluster cache capacity. Read the ratios correctly: they measure *scheduler choice under saturation on a prefix-dominated workload* — the baselines' queues explode (mean wait queue 27–29 requests vs 0.1) — not an engine speedup, and the blog says the workload was chosen to be exactly the regime where scheduling decides.

**README "Performance and Adoption Highlights" (read 2026-11-15; mixed dates, each attributed by the README to a named partner):**

- **3× higher output throughput, 2× faster TTFT** — prefix-cache-aware routing vs round-robin, Llama 3.1 70B, **4× AMD MI300X** (Tesla / Red Hat).
- **40% reduction in TTFT and ITL** — predicted-latency scheduling vs heuristics, NVIDIA GPUs (Google).
- **Up to 70% higher tokens/sec** — prefill/decode disaggregation vs standard vLLM, GPT-OSS on **NVIDIA B200** (AWS).
- **10–30% throughput improvement** — disaggregated serving *on identical infrastructure*, GPT-OSS-120B and Llama 3.3 70B, AMD MI300X (Oracle). The most modestly framed claim in the table, and the one whose framing (same hardware both sides) this corpus wishes were universal.
- **50k tokens/sec cluster throughput** — wide expert parallelism on 16×16 NVIDIA B200 (~3.1k tok/s per GPU).
- **13.9× throughput improvement** — hierarchical KV offloading at 250 concurrent users vs GPU-only serving, **4× NVIDIA H100**.

**CNCF / v0.5 era (March 2026):**

- The CNCF announcement charts llm-d inference scheduling holding near-zero TTFT and scaling to **~120k tok/s** while a baseline Kubernetes Service degrades, on Qwen3-32B, 8 vLLM pods, **16× NVIDIA H100** (the v0.5 release's multi-tenant SaaS scenario — the same hardware family and workload shape as the precise-scheduling benchmark above).

**1.0 era (October 2026, founder-reported production and benchmark results):**

- **Google Cloud (1.0 blog, 2026-10-20):** on an agentic coding workload on **Ironwood TPU (TPU 7x)**, prefix-aware routing plus host-memory offload cut median TTFT by **>85%** and raised throughput **2.4×** vs a plain Kubernetes Service. From Google's production Vertex/Gemini platform via GKE Inference Gateway: prefix-cache hit rate **doubled, 35% → 70%**, TTFT cut **>35%** for coding agents and p95 TTFT **>50%** under bursty chat. A published multi-region benchmark (17,000-node GKE deployment, MoE model) reports **2.9×** throughput scaling across three clusters at 99.9% success with <1% routing overhead.
- **IBM Research (1.0 announcements, October 2026):** self-hosted frontier open models for agent workloads at a **~98% prefix-cache hit rate** and a blended serving cost of **~$0.11 per million tokens**, presented as **~11.5× lower cost than an all-proprietary configuration** for a quantum-error-correction-hardware research workload; and a large-MoE agentic demonstration (GLM-5.2) peaking above **6.6M output tokens/minute** serving up to **3,000 concurrent coding agents** with zero preemptions, at a stated 5–10× per-token cost advantage *versus commercial API pricing*. Both are cost comparisons against proprietary API stacks, not serving-system-vs-serving-system measurements, and are labelled as such here.

**The honest summary of §6:** on fixed hardware, llm-d's mechanisms show their worth exactly where its design says they should — prefix-heavy, multi-turn, saturating traffic, where placement and cache knowledge are the difference between reuse and recompute (the 2×-class throughput effects and the large TTFT effects under load). The order-of-magnitude ratios (57×, 13.9×, 11.5×) each arise against a baseline that is collapsing, cache-starved or commercially priced — true in context, and unusable out of it. The project's own open-benchmarking apparatus (Prism, published well-lit-path configurations) is a genuine mitigant: the configurations behind the headline numbers are inspectable, which is more than most vendors offer.

## 7. Strengths / weaknesses

### Strengths

- **Standards-native, upstream-first.** Building the picker as GAIE's primary implementation — and routing general improvements upstream to the SIG project — means llm-d's core contract (InferencePool, the picking protocol) is a Kubernetes standard other gateways implement, not a proprietary sidecar protocol. The 2026 consolidation of the production EPP into the llm-d organisation under CNCF governance makes the standard and its reference implementation hard to fork apart.
- **Restraint as architecture.** Borrowing the proxy, the autoscaler (KEDA/HPA), the gang scheduler (LWS) and the engines, and building only the decision layer, the indexer and the topology controllers, keeps llm-d's own surface small for what it does — and each borrowed piece is one its operators already run. WVA's deprecation (§3.6) shows the project applying the rule to itself.
- **The two-tier epistemics of §3.3.** Shipping an approximate mode that costs nothing and a precise mode that costs infrastructure — with the failure mode of the cheap one documented in its own docs — is honest systems design. Most routers silently pick one point on that trade-off.
- **Vendor neutrality with receipts.** Five founders across hyperscaler, OEM, neocloud and silicon; documented paths on NVIDIA, AMD, Intel XPU and Google TPU; CNCF governance. Whatever "any accelerator" is worth as a slogan, the well-lit-path matrix is broader than any single-vendor stack's in this corpus.
- **Day-2 maturity arrived on schedule.** The 1.0 line's headlines are unglamorous and correct: stable v1 config API, router HA, lockstep P/D rollouts, flow-control defaults, plugin lifecycle gating. The project spent its second year on operability rather than new multipliers.

### Weaknesses

- **Kubernetes is the price of admission — the whole design presumes it.** Every mechanism is a Kubernetes mechanism: discovery is pod watching, the pool is a CRD, the proxy attachment is a Gateway controller's `ext-proc` configuration, scaling is an HPA, topology is LWS, signals are Prometheus metrics. There is no llm-d outside a cluster — no single-node mode, no bare-metal mode, no degraded local form. An organisation (or a person) without a running, GPU-equipped Kubernetes platform buys the entire platform before the first routing decision improves. This is a legitimate design choice for its target users; it is also a hard wall, and §8's negative lesson hangs on it.
- **The sum of borrowed parts is still a sum.** A precise-routing production deployment is: a GAIE-conformant gateway, EPP replicas (with their data layer and index), a vLLM render endpoint for exact tokenisation, ZMQ connectivity from every model-server pod, KEDA + Prometheus for scaling, LWS (+ DisaggregatedSet) for disaggregated topologies, and engines configured to emit KV events. Each piece is standard; the integrated whole is a platform team's ongoing responsibility, and several failure modes live in the seams (a stale index routes on belief; an unresponsive EPP falls back per the pool's configured failure mode — open or closed, both operator choices with teeth).
- **Precision is conditional on the engines' observability.** Precise routing needs engines that publish complete, timely KV events and a render path that tokenises exactly as the engine does. Where that support is thin or the workload is multimodal/hybrid-attention (documented work-in-progress), the system falls back toward the approximate mode whose divergence under eviction pressure its own benchmark dramatised.
- **Youth and churn.** Eighteen months from launch to 1.0: a renamed scheduler repository, APIs moved between projects, a deprecated autoscaler, a config API that only stabilised in October 2026, plugin surfaces still graduating. Pinning versions and reading release notes is survival hygiene, as with Dynamo — with the difference that llm-d's 1.0 is younger than Dynamo's was at its dossier date.
- **Claims discipline is uneven.** §6 spans the corpus's best-contextualised scheduler benchmark and a launch headline with no configuration attached, plus cost ratios against proprietary API pricing presented beside serving measurements. The open-benchmark tooling mitigates; it does not eliminate the need to read every number's two sides.
- **Disaggregation inherits the fabric economics.** P/D separation pays the KV-transfer cost on every request; llm-d's transfer path is RDMA/NIXL, and the Mooncake break-even logic (`papers/mooncake.md` §2) governs whether reuse beats recompute on a given fabric. On Ethernet-only clusters the flagship topology is the wrong shape — the well-lit paths' accelerator guides assume the fast interconnects the claims were measured on.

## 8. What our Ollama work should steal as IDEAS

Graded for the corpus's target — a single-machine personal runner (Ollama-class, one GPU, one user), with Dynamo dossier §8.5's four-condition rule applied, not re-derived (§8.4). llm-d's export to us is narrower than Dynamo's in one way and sharper in another: narrower because everything is Kubernetes-shaped; sharper because **the one component worth studying is written in Go, as a plugin pipeline, for exactly the decision our runner also makes** — where should this request's work go, given where its state already is?

### 8.1 The scorer-pipeline shape — the Go design pattern worth stealing

The EPP's scheduling cycle is a small, legible architecture: **producers** attach typed facts to the request (tokenisation, per-candidate match info, live metrics) → **filters** remove impossible candidates → **scorers**, each returning a normalised [0,1] judgement about one concern, are combined by declared **weights** → a **picker** applies the final selection rule → a **profile handler** composes pipelines for different request classes. Every element is a small Go interface behind a registry, assembled from configuration, with per-plugin latency metrics.

Collapsed to one machine, the candidates stop being pods and become the placement decisions a personal runner actually faces: *which resident session's context serves this turn; which model (chat / summariser / embedder) takes this piece of work given where its context lives; which session is demoted when the GPU fills; does this background request run now or after the interactive turn?* Those decisions exist in every runner — they usually accrete as conditionals scattered through the serve path, each new heuristic editing the last one's behaviour invisibly. The steal is the **shape**: one named pipeline through which every placement decision passes, scorers that each own exactly one signal (prefix-resident fraction, queue/concurrency, KV pressure, session affinity, predicted latency headroom), weights that are configuration rather than code, and a picker whose rule is stated in one place. In Go this costs a handful of interfaces and a registry — the same idiom the EPP itself uses, at 1/1000th of its scale. **Grade: the pattern transfers whole; it is the single most portable idea in either orchestration dossier, precisely because it is a code-organisation pattern and not a distributed system. No EPP, no ext-proc, no proxy is imported — the pipeline runs in-process, in the request path, as a function call.**

### 8.2 The indexer, collapsed to one process — ledger #5's data structure, confirmed

The precise indexer's data structure is: **chained block-hash keys → the set of locations holding each block, maintained by create/evict events, queried as longest-consecutive-prefix per location, with matches weighted by tier.** Remove the fleet and that sentence *is* IDEA-LEDGER **#5** (hash-chained/radix prefix cache) with its locations renamed: pod+GPU/CPU tier becomes VRAM/RAM/SSD tier, the engines' ZMQ event stream becomes the runner's own block allocator emitting stored/removed notifications in-process, and the index becomes the structure the session-placement scorers of §8.1 read. llm-d contributes three refinements worth banking in its words: (1) the **longest-consecutive-prefix rule** as the scoring primitive — partial scattered hits are worth zero, only the unbroken chain counts, which is the correct semantics for causal attention and easy to get subtly wrong with a naive hit-count; (2) **tier-weighted matches** (its documented defaults price a CPU-tier block at 0.8 of a GPU-tier block) — the local version prices a RAM-resident block against a VRAM-resident one by measured restore cost, per the Mooncake break-even discipline; (3) **speculative indexing** — after choosing a placement, tentatively record the prefix as resident under a short TTL so the next turn's decision doesn't race the bookkeeping, expiring if unconfirmed. Locally the "eventual consistency" being papered over is a session still being restored or a prefill still running; the mechanism is a few lines and the failure it prevents (two back-to-back turns both routed as cold) is real in agent loops. **Grade: data structure already banked as #5; the three refinements are genuine, small, and stated here in transferable form. The ZMQ mesh, the multi-replica convergence, and the Redis backend are fleet organs — not imported.**

### 8.3 Smaller steals, briefly

- **Sticky-until-saturated as a named policy.** The guides' default — hold a session on its cache-warm placement until a saturation signal fires, then spill — is the local session policy in one line: a session stays resident while KV pressure is below threshold; the *first* response to pressure is demotion of the coldest state, not eviction of the active session (compare Dynamo §8.2's demote-don't-delete sharpening; the two dossiers converge on the same local rule from different fleets, which raises confidence in it).
- **Approximate first, precise when it pays.** llm-d's two epistemic tiers miniaturise cleanly: a personal runner can score placements from its own recent routing/restore history (free, occasionally wrong) and only consult exact allocator state when the decision is expensive — a model swap, a large restore. Knowing which tier of knowledge a decision used is itself worth recording in the bench output (#44's measurement law).
- **Flow control collapses to admission posture.** Priority bands and fairness queues presume tenants; one user has none. What survives is the *ordering* instinct — interactive turns ahead of background summarisation/batch, with an honest fast refusal (or deferral) at saturation instead of collective degradation — which is IDEA-LEDGER **#31**'s admission half, already banked from Mooncake. llm-d adds only the vocabulary of bands; **[speculation, marked]** a two-band local version (interactive / background) is plausibly all a personal runner ever needs, and this dossier takes no position on building it.
- **The latency predictor, honestly miniaturised.** An online regression over completed requests predicting TTFT per placement is the fleet form of a local profile table (measured TTFT by model × context-length on *this* card). The table is the honest scale for one machine; the predictor's *interface* — a scorer that asks "predicted headroom against the target?" — fits §8.1's pipeline unchanged when the table is all that feeds it. **[Speculation, marked.]**

### 8.4 The negative lesson — the four-condition rule, applied

Dynamo dossier §8.5 states the rule: an orchestration layer earns its keep when (1) multiple interchangeable workers differ in ways worth routing between, (2) capacity is variable so planning has actuators, (3) state is large, shared and mobile enough that tracking/moving beats recomputing, at fabric speeds, and (4) the layer's cost is small against the GPU-hours it optimises. **Applied to llm-d on a single machine, it fails on all four, identically** — one worker, fixed capacity, state one PCIe hop from its only consumer, and a "layer" whose minimum deployment (a Kubernetes cluster, a gateway, an EPP, an event mesh) costs more to run than the GPU it would optimise. The Gateway/K8s machinery itself therefore earns **nothing** locally: no InferencePool, no ext-proc, no KEDA, no ZMQ, no Helm chart survives the collapse, and importing any of it would be theatre of exactly the kind the rule exists to prevent. What survives is what survived Dynamo, plus llm-d's one extra: the *accounting* (scores, indexes, saturation signals) — and, uniquely here, the **code shape** the accounting is organised in (§8.1), because llm-d happens to organise it the way a Go program should. Steal the pipeline and the index; leave the platform.

## 9. Dynamo comparison

Same problem — placement, capacity and cache state above engines that already work — opposite centres of gravity. **Dynamo** is a single vendor's integrated platform: NVIDIA builds the frontend, router, planner, transfer library and operator as one system in Rust + Python, optimised around its own silicon and fabric, and governs it as a product. **llm-d** is a community's composable stack: a Go decision service and indexer slotted into Kubernetes standards (GAIE, Gateway API, KEDA, LWS) under CNCF governance, deliberately borrowing every layer it can — proxy, autoscaler, gang scheduling — and optimising for neutrality across vendors, accelerators and clouds. Their mechanisms converge almost point for point (KV-aware routing, disaggregation, tiered KV, inference-signal scaling) because both are productising the same research generation (DistServe → Mooncake); their remaining differences are about *who owns the seams* — Dynamo internalises them for coherence and speed of iteration, llm-d externalises them into standards for adoptability, and pays for it in integration surface. For this corpus the practical difference is the one §8 is built on: Dynamo exports accounting discipline, llm-d exports that *plus* a Go plugin-pipeline shape our own runner can legitimately imitate.
