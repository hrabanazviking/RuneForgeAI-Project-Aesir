## Essence

Dynamo is not an inference engine. It is the **orchestration layer above inference engines**: a Rust frontend and KV-aware router, a fleet of worker processes that wrap vLLM, SGLang or TensorRT-LLM, a planner that resizes prefill and decode pools against latency targets, a transfer library (NIXL) that moves KV cache between workers and memory tiers, and the discovery/event plumbing (etcd, NATS) that lets all of those parts find each other and agree on where every KV block in the fleet currently lives. Its four founding moves, all present in the March 2025 launch material, are: **disaggregate** prefill from decode into independently scaled GPU pools; **route by KV overlap** so a request goes to the worker that already holds its prefix instead of recomputing it; **tier the KV cache** off GPU memory into host RAM, SSD and networked storage so reuse survives beyond HBM capacity; and **plan capacity continuously** against TTFT/ITL service-level objectives instead of provisioning statically. Every one of those moves presumes a fleet: many GPUs, a fast fabric, many concurrent users, and traffic mixed enough that placement and capacity decisions actually have something to decide. Dynamo's own README says the quiet part plainly, in its "when to use" section: if you are running a single model on a single GPU, your inference engine alone is probably sufficient. This dossier takes that sentence as seriously as the headline multipliers in §6.

## 2. Architecture in our own words

NVIDIA's current architecture documentation describes Dynamo as three cooperating concerns — a fast **request path**, a responsive **control path**, and a resilient **state path** — realised as planes. The component model below follows that documented shape.

### 2.1 The request plane (the data path)

- **Frontend.** The client-facing entry point: an OpenAI-compatible HTTP service (chat/completions surface; the 1.x line also exposes an Anthropic-style messages endpoint, per release notes) that accepts, validates and preprocesses requests — tokenisation and request normalisation live here, not on the workers — and streams tokens back. In the Kubernetes Gateway-API topology (§2.4) the frontend can also run in a reduced "direct" mode as a per-worker sidecar.
- **Router.** Sits behind the frontend and chooses the worker(s) for each request. In its KV mode it is the Smart Router of the launch material: it scores workers by KV-cache overlap and load (§3.1). Simpler modes exist (load/round-robin-style selection, and an approximate KV mode that predicts cache state instead of consuming live events), and in disaggregated mode the router makes *two* choices per request — a prefill worker, then a decode worker.
- **Workers.** One worker wraps one backend engine instance (vLLM, SGLang, or TensorRT-LLM's PyTorch backend) and advertises a role: **prefill** (compute the prompt's KV, hand it off), **decode** (generate tokens), or **aggregated** (both, the traditional shape). The documented default connection is *integrated* — the Dynamo worker and the engine live in the same process, so Dynamo sees the engine's KV events and scheduler state directly. An experimental *sidecar* mode runs a stock engine server beside a CPU-only Dynamo sidecar and talks to the engine's native API; the docs are explicit that it does not yet match the integrated backends' feature coverage.
- **NIXL (NVIDIA Inference Transfer Library).** The point-to-point data-movement layer underneath the request plane: one API for moving inference data — above all KV blocks for the prefill→decode handoff — between HBM, host DRAM, local SSD and networked storage, over NVLink/NVSwitch, InfiniBand/RoCE (UCX/GPUDirect RDMA) or, as a fallback, TCP/Ethernet and object storage. NIXL is a separate open-source NVIDIA library that has escaped Dynamo in the usual way infrastructure does: the 1.0 blog notes its adoption by llm-d, TensorRT-LLM, SGLang and vLLM for KV transfer (compare Mooncake's Transfer Engine escaping into vLLM/SGLang in `papers/mooncake.md` §3 — the same pattern, §4.3).

### 2.2 The control plane (adaptation and orchestration)

- **Planner.** The autoscaler (§3.3): consumes live metrics and forward-pass records, computes how many prefill and decode workers the current traffic needs to hold its TTFT/ITL targets, and emits scaling targets.
- **Dynamo Operator + CRDs (Kubernetes realisation).** In the recommended production deployment, desired state is declarative: a `DynamoGraphDeployment` describes the serving graph (frontend, router, worker pools), and the operator reconciles Kubernetes resources to match the Planner's targets. A higher-level `DynamoGraphDeploymentRequest` (DGDR, beta in 1.0) lets an operator state only model + hardware + SLA and have the profiling/planning tooling propose and apply a topology.
- **Grove.** The topology-aware gang-scheduling layer for multinode Kubernetes: worker groups are modelled as grouped cliques with their own scaling groups for prefill and decode, so a rack-scale deployment (NVL72-class) is placed with awareness of racks, hosts, NVLink domains and NUMA nodes rather than pod-by-pod.
- **ModelExpress.** The cold-start accelerator: a new replica normally repeats the whole startup pipeline (download checkpoint, load weights, optimise, compile kernels, capture CUDA graphs). ModelExpress does the expensive parts once — streaming model weights GPU-to-GPU over NIXL/NVLink from a live worker instead of re-downloading them, and restoring a captured ready-to-serve checkpoint state for new replicas (§6 for the claimed effect).

### 2.3 The storage & events plane (the state path)

This is the plane that makes KV-aware routing possible, and the one a reader most often underestimates: the router can only route by cache contents if something continuously tells it what every worker holds.

- **Discovery.** Components register themselves and find each other through a discovery backend. The runtime's global default is an etcd-backed key/value store (`kv_store` mode: endpoints registered under a lease, so a dead worker's registration expires with its lease). Kubernetes deployments can instead use native discovery (worker-metadata CRDs + EndpointSlices; the operator sets this explicitly, and no etcd is then required). Local and single-node runs can use file-based or in-memory discovery — the quick-start commands in the current README run the frontend and a worker with a file discovery backend and no external services at all.
- **KV events.** Workers publish KV-cache lifecycle events — blocks created, reused, evicted — and the router consumes them to maintain its fleet-wide view of which prefixes live where. The documented transport for this event plane is **NATS**: Core pub/sub for live events, JetStream where durable delivery, replay and router-replica synchronisation are wanted. The request plane itself is a separate choice (direct TCP by default; HTTP or NATS as alternatives), which is why "Dynamo needs etcd and NATS" is only conditionally true: etcd is the default discovery store, NATS is required for *accurate, event-fed* KV routing, and both can be shed in reduced local modes at the price of approximate routing (`--no-kv-events` / `--no-router-kv-events` style flags) or no KV routing at all.
- **Offloading connectors.** The same plane carries the tiering machinery of §4: connectors that move reusable KV blocks between GPU, host and storage tiers (Dynamo's own KVBM historically; engine-native LMCache, SGLang HiCache and FlexKV in the current line).

### 2.4 Two routing topologies

The current docs describe two ways to expose the same system, sharing control and event planes: **Dynamo-native routing** (client → Frontend → Router → workers; Dynamo owns the entry point end to end) and **Gateway API routing with GAIE**, where a Kubernetes Gateway API Inference Extension gateway calls Dynamo's Endpoint Picker Plugin to choose a worker, then forwards to that worker's frontend sidecar in direct mode. The second topology exists so that gateway-level policy — auth, rate limiting, observability — can sit at the cluster edge in platforms that standardise on it.

### 2.5 Fault tolerance, as documented

Failures are treated as routine operating events, in layers: canary health checks on workers; graceful shutdown that drains in-flight work; discovery-lease expiry removing stale endpoints so traffic reroutes; **in-flight request migration** and cancellation at the request layer (the README's summary: workers fail, user requests don't); and load shedding / request rejection at the system layer to stop overload cascading. §8 returns to the migration item — it is Llumnix's primitive, arriving in product form.

## 3. Scheduling & routing

### 3.1 KV-aware routing: overlap priced against load

The router's core decision, as documented in the Router Guide / Router Design pages:

1. The incoming prompt is hashed into blocks, and the router looks the block sequence up in its index of fleet cache state — maintained as a **radix tree** over the block hashes reported by worker KV events — yielding, per worker, an **overlap score**: how much of this prompt's prefix that worker already holds.
2. For each candidate worker it estimates two costs: the **prefill cost** — the blocks it would still have to compute, i.e. input blocks minus overlapped blocks — and the **decode cost** — the worker's current active-block load from in-flight sequences.
3. It combines them in one documented cost expression, in words: *cost = (overlap weight × potential prefill blocks) + potential active blocks*, with the overlap weight defaulting to 1.0. The lowest-cost worker wins; an optional non-zero router "temperature" turns the choice into softmax sampling over the costs, deliberately injecting some randomness so that cache-greedy choices do not stampede one worker.
4. The weight is the tuning dial, and the docs state its trade honestly: raise it and routing favours cache reuse (better time-to-first-token, at the risk of piling onto the cache-rich worker and hurting inter-token latency); lower it toward load balancing; set it to 0 and prefix matching is switched off entirely — pure load balancing, no indexer created.

Two 1.0-era additions matter for §8: the router can consume **per-request hints** (priority, expected output length, latency sensitivity, cache-control/pinning intent) passed from agent frameworks through the frontend, using expected output length to make its load estimates less naive; and the router's scoring surface is itself churning — the deprecations ledger records the individual scoring/selection flags as deprecated in the 1.5 line in favour of a single policy-configuration flag, slated for removal in v1.7.0. Anyone building on the 0.x/1.0 flag surface should expect it to move.

### 3.2 Disaggregation mechanics

In disaggregated mode a request's life is the architecture doc's nine-step narrative, compressed here: frontend → router picks a **prefill worker** (by the same overlap logic — ideally one already holding much of the prompt) → the prefill worker computes the prompt's KV and returns transfer metadata → router picks a **decode worker** → the KV moves to the decode worker over NIXL → the decode worker generates and streams tokens back through the frontend → KV events update the fleet's cache view for the next routing decision, and offloading connectors may demote or recall blocks behind the scenes.

Design points worth recording:

- **The pools scale and parallelise independently.** Prefill is compute-bound and wants parallelism choices that minimise communication overhead; decode is memory-bandwidth-bound and wants the opposite trade in several regimes. Each pool gets its own tensor/pipeline/expert-parallel layout and its own replica count, and the Planner (§3.3) can also *move GPUs between pools* or collapse back to aggregated serving when the traffic mix makes disaggregation the wrong answer — the launch blog is explicit that disaggregation is not always optimal per-request (a surge of long-input/short-output summarisation can starve decode while prefill drowns, and the correct response may be aggregated workers or a rebalanced split).
- **The handoff is the price, and the fabric pays it or nobody does.** KV transfer cost is a first-class term in the planner's disaggregated-vs-aggregated decision. NVIDIA's own installation guide warns that without RDMA, disaggregated serving falls back to TCP with a severe, quantified degradation (its figures: TTFT in the ~98 s range versus ~200–500 ms with RDMA, in the documented test context). Disaggregation is therefore a *fabric feature* before it is a software feature — the same break-even logic Mooncake formalised (`papers/mooncake.md` §2), here as an operational warning.
- **Encode is a third pool for multimodal.** The 1.0 line generalises the split to encode/prefill/decode (E/P/D) for image-heavy workloads, with a CPU-backed LRU **embedding cache** so repeated images skip encoding entirely, and multimodal KV routing that counts image-bearing blocks in the overlap score.

### 3.3 The Planner: GPU-driven, SLA-first autoscaling

The Planner is an autoscaler built for the specific way LLM serving breaks generic autoscalers: the resource that saturates is KV capacity and queueing in *tokens*, and the objectives are TTFT and ITL, not CPU percentage. As documented in the current Planner pages, it works in two coupled loops:

- **Load-based (reactive) scaling** — the fast loop (default adjustment interval ~5 s in the current docs). It consumes **Forward Pass Metrics** — per-iteration records streamed from workers over the event plane describing batch composition, queue depth, token counts and forward-pass duration — plus queue/KV-utilisation signals, and steps prefill or decode replica counts up or down against thresholds. The early (0.3-era) documented form of this loop is the clearest statement of the signals: scale decode/aggregated workers on **average KV-cache utilisation** (documented default thresholds: up at 0.9, down at 0.5), scale prefill workers on **prefill queue size**, change by at most one worker per interval to avoid oscillation, and observe a grace period after adding a decode worker (its cache is cold; scaling something else down against it immediately would misread the fleet). The current docs keep the same signal family under named optimisation targets — `throughput` (default; queue-depth + KV-utilisation thresholds), `latency` (the same, more aggressive), and `load` (operator-set thresholds).
- **Throughput-based (predictive) scaling** — the slow loop (default ~180 s), available under the `sla` target. It forecasts traffic (the documented predictor family: ARIMA, Prophet, Kalman, constant), then asks a performance model how many prefill and decode replicas the forecast load needs to meet stated TTFT/ITL targets. The performance model is bootstrapped from profiling data — interpolation over measured (input/output length → TTFT/ITL) behaviour — and continuously corrected by the live Forward Pass Metrics. This is where the profiling tooling of §5.2 plugs in.

The Planner's outputs are replica targets per pool, applied through the operator/Kubernetes path (or a local process supervisor in non-Kubernetes mode); new workers are picked up by discovery and join the router's view automatically, and scale-down is deliberately gentle — a prefill worker is signalled to stop, a decode worker's discovery lease is revoked so it leaves rotation before it dies (0.3-era documented mechanics; the principle — *leave the routing view before you leave the world* — is the durable part).

## 4. KV & memory design

### 4.1 The stance: KV as a managed, tiered, transferable asset

Dynamo's memory design is the Mooncake thesis restated as product architecture (the lineage is handled carefully in §4.3): the KV cache is not a private by-product of whichever engine computed it. It is a **fleet asset** with its own lifecycle — created by prefill workers, indexed by the router, transferred by NIXL, demoted through storage tiers by offloading connectors, recalled on a later request's behalf, and evicted by policy — and the system's main scheduling decisions are made *about* it. Concretely:

- **Addressed by prefix.** Blocks are identified by their position in a hash/radix structure over the prompt's token blocks, so "where does the KV for this prefix live?" is a lookup, not a search — the precondition for §3.1's routing and for cross-request reuse.
- **Visible fleet-wide.** The KV event plane (§2.3) exists to keep that address book current. Routing quality is therefore bounded by event freshness: the documented approximate mode (no events, prediction only) is the honest admission that stale cache knowledge routes worse.
- **Tiered by temperature.** Hot blocks stay in GPU HBM; colder blocks demote to host DRAM, then to local SSD, then to networked/object storage (the 1.0 line adds S3/Azure-blob-class backends and global KV events for cluster-wide visibility of the colder tiers). The launch material's framing is economic: offloading lets an operator hold vastly more reusable KV than HBM alone — NVIDIA's launch text reaches for "up to petabytes" of KV in cheap tiers — at lookup/transfer costs the router's cost function is supposed to price in.
- **Transferable between workers and roles.** The same block set is the prefill→decode handoff (§3.2), the substrate for request migration under failure (§2.5), and the thing a newly scaled decode worker conspicuously lacks — hence the Planner's cold-cache grace period (§3.3). KV mobility is assumed everywhere; nothing in the design treats a block as nailed to the GPU that computed it.

### 4.2 KVBM — Dynamo's own block manager, and its deprecation

Through the 0.x and early 1.x lines, Dynamo's built-in tiering component was the **KV Block Manager (KVBM)**: a runtime layer that manages allocation and remote sharing of KV blocks across heterogeneous, distributed environments, presenting itself to the engine as a unified memory layer / write-through cache. As documented in the KVBM Guide, it tiers blocks across GPU memory (the G1 tier), host memory (G2) and disk/remote storage (G3), can run standalone as well as inside the full stack, registers its leader/workers through etcd, and supports both aggregated and disaggregated serving (including a replicated mode for MLA-class models where one rank loads from the lower tiers and broadcasts). Per the current README's feature matrix, KVBM support stands at: vLLM ✅, TensorRT-LLM ✅ (its PyTorch backend only), SGLang 🚧 (in progress) — a matrix that itself shifted between doc versions during 2026, which is characteristic of this project's pace.

**The current-status fact a reader most needs:** the deprecations ledger records **KVBM as deprecated in v1.5.0 (September 2026), with removal targeted for v1.7.0**. NVIDIA's stated migration path is to use the *engines' native* KV offloading for host/disk tiering — in practice the pluggable connector ecosystem Dynamo also orchestrates: **LMCache** (vLLM; host + persistent tiers), **SGLang HiCache** (host + optional external storage, with Dynamo adding tier-aware routing on top of its events), and **FlexKV** — while cross-node KV *sharing* is named as the scope of a separate, explicitly early-stage KV Cache Runner (KVCR) project that, per the ledger, does not replace KVBM. So the tiered-KV *design* (§4.1) is intact and central; Dynamo's *own implementation* of the tier manager is being retired in favour of orchestrating the engines' and ecosystem's implementations. A dossier written a year earlier would have presented KVBM as the centre of §4; as of 2026-11-15 that would be stale, and the correction is recorded here rather than smoothed over.

### 4.3 The Mooncake lineage — stated carefully

This dossier separates three kinds of connection that are easy to blur, because the corpus's measurement law applies to genealogy as much as to benchmarks:

1. **Documented inspiration (NVIDIA's own words, in substance).** Dynamo's current architecture documentation closes with an acknowledgements list of prior open-source work Dynamo is *informed by*: vLLM, SGLang, DistServe, **Mooncake**, AIBrix and BentoML. That is the strongest lineage statement NVIDIA itself makes, and it is a statement about *ideas*, made alongside five other projects — not a claim of descent from Mooncake specifically.
2. **Documented integration (verifiable in the docs and release notes).** Mooncake software enters Dynamo deployments as a component, the way any ecosystem part does: Mooncake is a named storage backend option for the tiered-cache integrations (SGLang HiCache workers can share an external pool *such as Mooncake*, with the router doing tier-aware selection over it; LMCache's backend list likewise includes Mooncake); the 1.0 blog credits "Mooncake and Alibaba" with extending Dynamo's AIConfigurator with SGLang support; and the v1.6.2 release notes raise the bundled Mooncake transfer-engine version floor in the SGLang/vLLM runtime images (the TensorRT-LLM image does not ship it). Integration is not ancestry — vLLM and SGLang are integrated far more deeply, and nobody calls Dynamo a vLLM descendant.
3. **Architectural kinship (this corpus's analysis, labelled as such).** The resemblance is real and deep: Mooncake's Conductor placing requests by where their KV lives is Dynamo's KV-aware router; Mooncake's disaggregated Store pooling KV across CPU/DRAM/SSD/NIC capacity is Dynamo's tiered-KV plane; Mooncake's phase pools are Dynamo's prefill/decode pools. Dynamo is what the KV-centric disaggregated architecture looks like when a GPU vendor rebuilds it as a general orchestration product over *other people's engines*, for arbitrary models and customers, on Kubernetes — where Mooncake was one operator's serving platform for its own chatbot, with its own engine underneath. **What is not supported by any source read for this dossier:** that Dynamo implements, ports, forks or descends in code from Mooncake, or that NVIDIA presents it as Mooncake's successor. The accurate sentence is: *Dynamo is the productised, vendor-built member of the architectural family Mooncake's paper defined — documented by NVIDIA as informed by Mooncake among others, integrating Mooncake components as options, and independently implementing the family's ideas (KV-centric placement, phase disaggregation, tiered pooled KV) as an orchestration layer.* The brief's shorthand "productised descendant" survives only in that qualified, ideas-level sense.

A parallel note for Llumnix (`papers/llumnix.md`): Dynamo's documented fault-tolerance layer includes in-flight **request migration** — Llumnix's defining primitive, in product form, used there for failure/draining rather than continuous rebalancing. No source read claims Llumnix lineage for it; the corpus records the convergence, not a descent.

## 5. Engine relationship

### 5.1 What Dynamo does NOT do

Dynamo contains no inference engine. It has no attention kernels, no GEMMs, no sampler, no quantisation formats, no model implementations. All of that lives in the backends — vLLM, SGLang, TensorRT-LLM (and, at the framework level in the launch material, PyTorch) — and a Dynamo deployment's per-token speed, model coverage, quantisation support and hardware floor are exactly its chosen backend's. What Dynamo owns is everything *between* engines: the frontend and tokenisation boundary, routing, phase disaggregation, KV visibility/transfer/tiering, capacity planning, discovery, and failure handling. The practical consequences:

- **Backend parity is a matrix, not a promise.** The README maintains a per-backend feature matrix (disaggregated serving, KV-aware routing and the SLA Planner across all three backends; KVBM asymmetric per §4.2; multimodal, tool calling, LoRA, speculative decoding and request migration varying by backend and version). Choosing a backend is choosing which subset of Dynamo you actually get.
- **Backend events are a dependency.** KV-aware routing is only as good as the backend's willingness to publish KV events and forward-pass metrics; the docs note per-backend switches and unevenness here (e.g. SGLang and TensorRT-LLM needing explicit event-publication configuration, vLLM's auto-configuration of events being deprecated in favour of explicit config). The orchestration layer's intelligence is capped by the engines' observability — a general law this corpus has met before, worth stating once in this form.
- **The successor framing needs one clarification.** NVIDIA's launch release calls Dynamo "the successor to NVIDIA Triton Inference Server". In the 1.x-era product landscape the general-purpose Triton line itself continues under the Dynamo brand umbrella (Dynamo-Triton) as a sibling; the `ai-dynamo/dynamo` project dossiered here is the distributed-LLM-serving framework, not a re-release of Triton's multi-framework server. Readers should not import Triton's properties (any-framework, any-processor serving) into this project.

### 5.2 Planner / profiling tooling around the engines

Dynamo ships a tooling belt whose job is to answer "how should this fleet be shaped?" *before* and *while* it runs — the part of the system most foreign to single-engine thinking:

- **AIConfigurator / AISimulate.** An offline performance-modelling and configuration-search tool: given a model, hardware and SLA targets, it estimates serving behaviour (from bundled/interpolated performance data) and searches deployment configurations — pool splits, parallelism layouts, replica counts — *without bringing up a GPU cluster*. It feeds the Planner's `sla` mode (§3.3) as its forward-pass performance model, and the DGDR zero-config flow (§2.2) as its recommender. (Naming in the sources drifts between AIConfigurator and AISimulate across versions; the 1.0 blog uses the former, current Planner docs describe the `aisimulate` package providing the compatibility API. Recorded as drift, not resolved into a false precision.)
- **SLA profiling.** The on-cluster counterpart: profile a real engine deployment across input/output-length regimes to produce the interpolation data the Planner consumes, so its capacity arithmetic is anchored in measured behaviour of *this* model on *this* hardware rather than a generic model.
- **AIPerf.** NVIDIA's benchmarking tool for generative-AI serving (the successor-in-spirit to TRT-LLM's bench tooling in the sibling dossier's §9.4 sense): load generation, trace replay and SLA-oriented measurement against SGLang/TensorRT-LLM/vLLM backends, used both by operators and in NVIDIA's own published Dynamo evaluations.
- **Planner "gym".** The repository ships a planner simulation environment (`gyms/planner-gym`) — the autoscaler itself is treated as something to be exercised against simulated traffic before it is trusted with a fleet. Noted because it is the same institutional habit as AIPerf: the vendor ships the measuring instruments with the system.

## 6. Reported performance claims — as reported by NVIDIA

**Every figure below is a vendor claim (or a vendor-cited third-party result), labelled with its date, hardware and model context, per this corpus's measurement law. None was reproduced for this dossier; none is a single-machine or consumer-hardware number; several compare against different hardware or radically different configurations, and say so.**

**Launch claims — GTC, 18 March 2025 (technical blog + newsroom release):**

- **Up to 30× more requests served** running DeepSeek-R1 on a **GB200 NVL72** (Blackwell rack-scale) with disaggregated serving. The blog's own figure caption supplies the confounds: TensorRT-LLM, FP4, input/output lengths 32K/8K; the non-Dynamo baseline ran in-flight batching at one parallelism layout (TEP16/PP4/DP4) against Dynamo's disaggregated layout (context EP4/DP16, generation EP64/DP3) — i.e. the comparison bundles disaggregation *and* a different parallelism strategy *and* is footnoted "projected performance subject to change". The newsroom version of the claim says tokens generated per GPU boosted "over 30×" on a large GB200 NVL72 cluster.
- **More than 2× throughput** serving **Llama 70B on Hopper** GPUs with the same number of GPUs (newsroom: Dynamo "doubles the performance and revenue" of Llama-serving AI factories on Hopper). Blog figure context: vLLM, FP8, ISL/OSL 3K/50, baseline TP8/DP2 in-flight batching vs disaggregated context TP2/DP4 + generation TP8.
- **Smart Router effect, as charted at launch:** the architecture documentation's version of this experiment reports **~3× faster TTFT and ~2× lower average request latency versus random routing**, on 100K real DeepSeek-R1 requests, R1-Distill-Llama-70B FP8, two HGX H100 nodes, average ISL/OSL 4K/800. (The launch blog's router figure uses the same workload description; the README's current "key results" table separately cites a **2× faster TTFT** figure for KV-aware routing from a **Baseten** benchmark on Qwen3-Coder 480B — a third-party production case, vendor-cited.)

**1.0 claims — GTC, 16 March 2026 (1.0 technical blog + press release):**

- **Up to 7× more requests served on NVIDIA Blackwell**, per the **SemiAnalysis InferenceX** benchmark as cited by NVIDIA (updated 3 March 2026): DeepSeek R1-0528, FP4, 1K/1K input/output, ~50 tokens/sec/user interactivity point, on GB200 NVL72 with wide expert parallelism. - The 1.0 blog also lists production adopters by name (cloud providers and AI-serving companies) — recorded in §7 as an adoption claim by the vendor, not independently audited for this dossier.

**Standing README "key results" table (read 2026-11-15; mixed dates):** 7× throughput per GPU (InferenceX, as above); 7× faster model startup (ModelExpress, DeepSeek-V3 on H200); 2× faster TTFT (KV-aware routing, Baseten/Qwen3-Coder 480B); **80% fewer SLA breaches at 5% lower TCO** from Planner autoscaling (cited to an Alibaba APSARA 2025 presentation); and a **750× higher throughput** line for DeepSeek-R1 on GB300 NVL72 via InferenceXv2 — the table's own context makes clear this is a cross-generation system comparison (new rack-scale hardware + new software vs an older baseline), and it is quoted here only as an example of how far headline ratios travel from anything an operator should expect Dynamo alone to deliver on fixed hardware.

**The honest summary of §6:** on *fixed* hardware with a *fixed* backend, the launch-era evidence supports Dynamo's mechanisms being worth roughly **2×-class** improvements in favourable regimes (Llama/Hopper disaggregation; router TTFT effects) — substantial, and consistent with what DistServe/Mooncake-class designs predict. The order-of-magnitude figures (7×, 30×, 750×) each bundle at least one of: new silicon, a new parallelism layout, a precision change, or a cross-generation baseline. That is not an accusation of falsity; it is the measurement law doing its job — a ratio without its two sides is marketing, and NVIDIA's own captions usually supply the sides for a reader who looks.

## 7. Strengths / weaknesses

### Strengths

- **It productises the research frontier, whole.** Disaggregation (DistServe/Splitwise), KV-centric placement and pooled tiered KV (Mooncake), request migration (Llumnix) — the 2023–2025 serving literature's main results appear here as one supported, documented, Kubernetes-native product within a year of announcement, with the engines the field already uses as its backends. Whatever its flaws, Dynamo is the shortest path from those papers to a running fleet.
- **The layering is right.** Refusing to be an engine — owning routing, capacity, cache visibility and failure handling while delegating kernels and sampling — lets Dynamo ride each backend's improvements and lets backends (via NIXL and the event contracts) improve without it. The vLLM dossier's "one core, several front doors" observation inverts here: one orchestrator, several engines.
- **Routing that prices the real cost.** The overlap-vs-load cost function (§3.1) is small, legible and tunable, and the docs state its trade-off in the open. It is the first production router whose primary signal is *where the state already is* — Mooncake's Conductor rule, generalised.
- **Capacity as a control problem, with instruments.** The Planner's two-loop design (fast reactive, slow predictive-with-profiling), the offline configurator, and shipping the benchmark tool (AIPerf) and a planner simulator alongside the system, together treat "how many GPUs, in which pools?" as a question with a measurable answer. Most serving stacks still leave it to folklore.
- **Failure and cold-start are designed, not patched.** Lease-based discovery, drain-before-death scale-down, request migration, and ModelExpress's attack on replica startup cost all address the unglamorous half of fleet operation that determines whether autoscaling is usable at all (a scaler whose new replicas take ten minutes to boot is a scaler that cannot follow traffic).
- **Open development, Apache-2.0, real adoption signals.** Public repo, public deprecations ledger, versioned docs, design proposals; the 1.0-era adopter list and the ecosystem integrations (llm-d adopting NIXL, LMCache/HiCache plugging in, LangChain passing router hints) are consistent with a platform others are building on — as vendor-reported, per §6's caveat.

### Weaknesses

- **The complexity cost is the product.** A production Dynamo deployment is: frontend(s), router(s), two or three worker pools across up to three backend stacks, etcd (or Kubernetes discovery machinery), a NATS cluster (with JetStream where durability is wanted), the operator + CRDs, Grove for multinode placement, Prometheus for the Planner's SLA mode, RDMA fabric configuration without which disaggregation collapses (§3.2), and per-backend event/connector configuration. Each part is documented; the *sum* is a platform team. This is datacenter infrastructure with datacenter moving parts, and its operational weight is only rational where GPU-hours are expensive enough to pay people to save them.
- **Churn at platform speed.** 0.x to 1.0 to 1.6 in twenty months; KVBM — a headline component of the launch architecture — deprecated in 1.5 and slated for removal in 1.7; router scoring flags deprecated in the same line; backend feature matrices shifting between doc versions; naming drift in the tooling (AIConfigurator/AISimulate). Pinning versions and reading the deprecations ledger is survival hygiene, exactly as with TensorRT-LLM (`runners/tensorrt-llm.md` §8) — but Dynamo asks it of an entire distributed system, not one runtime.
- **Its intelligence is borrowed.** Routing and planning quality cap out at what backends publish (KV events, forward-pass metrics) and what the fabric provides (RDMA or a ~two-orders-of-magnitude TTFT penalty in NVIDIA's own documented fallback warning). Dynamo on a backend with poor event support, or on Ethernet-only nodes, is a much duller system than the brochure version, through no fault of its algorithms.
- **Fleet assumptions all the way down.** Every mechanism needs slack to work with: routing needs multiple workers holding different caches; disaggregation needs spare GPUs to form pools; the Planner needs replicas it is allowed to create and destroy; migration needs somewhere to migrate *to*. At small scale the machinery does not degrade to a simpler version of itself — it mostly switches off, leaving the backend engine doing the work it always did, plus overhead. NVIDIA's own single-GPU guidance (§1, Essence) concedes the point.
- **Vendor gravity.** The design centre is NVIDIA's newest datacentre silicon (GB200/GB300 NVL72 rack-scale systems dominate the claims and recipes), NVIDIA's fabric (NVLink/NIXL), and NVIDIA's platform story. Backends include AMD-capable engines in principle, but nothing in the sources read presents Dynamo as hardware-neutral in practice; an operator on mixed or non-NVIDIA fleets is outside the tested centre.
- **Claims discipline required.** §6's bundling problem (ratios spanning silicon, precision and parallelism changes) is a property of how the product is marketed, and an adopter who budgets from headlines will be disappointed by the honest 2×-class same-hardware effects — which are genuinely valuable and did not need the inflation.

## 8. What our Ollama work should steal as IDEAS

Graded honestly for the corpus's target — a single-machine personal runner (Ollama-class, one GPU, one user; Project Aesir's single-machine serve in view). The through-line, stated first because everything below is its corollary: **Dynamo is a fleet answer, and almost none of its machinery survives the collapse to one machine — but its *accounting* does.** Dynamo's real export is a set of questions asked in the right units: where does the KV for this prefix live, what would recomputing it cost, what is this pool's capacity against a latency target. A single-machine runner that asks those questions in its own units already owns most of what Dynamo knows.

### 8.1 KV-aware routing → prefix-aware session placement (already ledger #5 territory)

Dynamo routes a *request* to the *worker* holding its prefix. A single-machine runner has one worker — but it still makes placement decisions of exactly this shape, one level down: which session's KV stays resident in VRAM, which is demoted to RAM/SSD, which prefix the next turn should be scheduled against, and (in a multi-model personal setup: chat model + summariser/embedding sidecar) which *model* a piece of work should go to given where its context already lives. The transferable item is the **cost function, not the router**: score a placement by *(new prefill the placement forces) weighted against (load/eviction it imposes)*, with an explicit weight the operator can tune — Dynamo's one-line formula is the fleet form of the rule IDEA-LEDGER **#5** (hash-chained/radix prefix cache) already implies and **#9/#11** (eviction scoring; spill idle, never running) implement piecemeal. Steal the explicitness: one named score, one named weight, instead of accreted heuristics. **Grade: principle already banked; the formula's shape is a small, real refinement. No router, no radix-tree-over-a-fleet, no event plane is imported.**

### 8.2 The tiered-KV manager → restates #43/#10 (with one sharpening)

Dynamo's GPU→CPU→SSD→remote tiering, demote-by-temperature, recall-on-demand, is the corpus's tiered-KV design (`memory/kv-cache-design.md`; IDEA-LEDGER **#10** session persistence, **#43** tier-boundary transit codec) at fleet scale — corroboration, not a new idea, and §4.2 adds a cautionary data point: NVIDIA itself is retiring its *own* tier manager in favour of the engines' native offloading. Even the vendor with every incentive to own this layer concluded the tier manager belongs with the engine that owns the blocks. For our Go runner that reads as: build tiering inside the runner's own block allocator (#4/#10), do not build a separate KV-management subsystem with its own registration/discovery life. **One sharpening does transfer:** Dynamo's 1.0-era *cache pinning with demote-instead-of-delete* (pinned agent prefixes resist eviction; on pressure they move to host memory rather than being dropped) is a clean local policy for the persona trunk — the anchor prefix (#5/#7) under memory pressure should be *demoted a tier*, never evicted into recompute, because its re-use is certain. That is a one-line policy in #10's store, worth banking in those words. **Grade: restatement + one policy line. KVBM itself: do not import, in any form — its own vendor is removing it.**

### 8.3 The Planner → a budget check, honestly labelled (the #31 pattern again)

SLA-driven autoscaling has no replicas to scale on one machine. What survives is the Planner's *input discipline*: decisions from measured per-iteration records (its Forward Pass Metrics) and from a profiled performance model, against explicit latency targets — miniaturised, this is the corpus's profiling-at-load habit (`runners/tensorrt-llm.md` §9.1/§9.2) plus IDEA-LEDGER **#31**'s admission half (Mooncake's lesson, already banked): a personal runner's "planner" is a budget check at admission — *will this request, at this context, alongside the resident session, hold the interactivity target on this card?* — answered from a small local profile, with an honest fast refusal or a demotion when the answer is no. The predictive loop, the traffic forecasters, and the replica arithmetic are fleet organs; importing them would be theatre. **Grade: discipline yes, machinery no. [Speculation, marked]:** if the personal runner ever grows a *second* machine on the home network (the fleet's smallest possible fleet — say a desktop plus a laptop), a two-node Dynamo-shaped split is the first scale at which any of §3 becomes real; the corpus takes no position on building that, and this dossier flags it only as the boundary case where the negative lesson of §8.5 expires.

### 8.4 Smaller steals, briefly

- **Drain-before-death, everywhere.** The Planner's scale-down etiquette (leave the routing view first, then stop) miniaturises to model/session lifecycle: a session being unloaded should finish or checkpoint its state (#10) before its blocks are freed; a model swap should be a visible, ordered transition, never a mid-generation disappearance. Cheap, and it is the local form of a fleet rule Dynamo documents well.
- **Cold-start as a measured cost.** ModelExpress exists because replica startup (download → load → compile → capture) dominated scaling responsiveness. The personal runner's analogue is model-load time on model switch — worth *measuring and budgeting* as a first-class number (and worth the cheap half of ModelExpress's idea: keep the ready state of the *other* model warm/restorable rather than rebuilding it per switch, which is #11's model/session lifetime decoupling stated from the startup side).
- **Ship the instruments.** AIPerf and the planner gym repeat TensorRT-LLM's lesson (`runners/tensorrt-llm.md` §9.4): benchmarking and simulation as shipped features of the system, not afterthoughts. For our runner: a built-in bench mode with hardware/precision context printed beside every number (IDEA-LEDGER **#44**, the measurement law as a build requirement) — Dynamo's §6 headlines are the standing exhibit of why the context line matters.
- **Hints at the boundary.** The 1.0 agentic-hints channel (priority, expected output length, cache intent travelling with the request) is a small API idea with local value: a personal runner's internal callers (UI chat, background summariser, agent tools) could declare *expected length* and *latency sensitivity* at admission, letting #31's budget check and #5's retention policy act on stated intent instead of guesses. **Grade: plausible, unpriced — an API-design note, not a build item. [Speculation, marked as such.]**

### 8.5 The negative lesson — where the line is

Dynamo is the corpus's clearest specimen of an orchestration layer, and studying it prices the species. An orchestration layer earns its keep when **all** of the following hold: (1) there are *multiple interchangeable workers* whose differences (cache contents, load, phase fitness) are worth routing between; (2) *capacity itself is variable* — replicas can be created and destroyed, so planning has actuators; (3) *state is large, shared and mobile enough* that tracking and moving it beats recomputing it, at fabric speeds; and (4) the *cost of the layer* (its own services, its operators, its failure modes) is small against the GPU-hours it optimises. A single-machine personal runner satisfies **none** of the four: one worker, fixed capacity, state that lives one PCIe hop from its only consumer, and an operator who is also the user. Below that line, every Dynamo mechanism degenerates — routing becomes a lookup in one's own cache (which is just #5), planning becomes a budget check (§8.3), tiering becomes the runner's own allocator policy (§8.2), and the event plane becomes a function call. **The line, stated as a rule for our work: build the accounting (scores, budgets, profiles, validity envelopes) at any scale; build orchestration machinery only when there is something to orchestrate.** Dynamo also validates the corpus's oldest structural instinct from the far side: NVIDIA, with unlimited resources, still put the intelligence in *placement, capacity and cache policy* and left token generation to the engines — the same division of labour as Ollama-over-llama.cpp, at the opposite end of the scale axis. The engines were never the interesting layer. The state was.
