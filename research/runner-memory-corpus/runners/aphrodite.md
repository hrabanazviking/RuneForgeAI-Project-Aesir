> **Licence discipline (binding on this dossier).** Aphrodite Engine is AGPL-3.0. This dossier was produced from **public documentation and observable behaviour only** — README text (as mirrored on PyPI and quoted by secondary sources), the public docs site, release notes, and public deployment guides. **No Aphrodite source code was read for implementation detail.** Everything below is behaviour, feature surface, and ideas, restated in our own words. Where a claim rests only on a secondary guide rather than the project's own documentation, that is said explicitly. Speculation is marked as speculation.

**Essence.** Aphrodite is what happens when a datacentre serving engine is forked by the people who actually run a character-chat platform. PygmalionAI took vLLM — continuous batching, paged KV cache, OpenAI-compatible serving — and re-aimed it at the roleplay/personal-use market: it loads the community's quantized checkpoints (above all GGUF, the llama.cpp world's format, inside a vLLM-lineage server), it exposes the RP sampler canon (DRY, XTC, Mirostat, min-p) that upstream vLLM never shipped, and it speaks the KoboldAI API so SillyTavern and friends can drive it without translation. It is the mirror image of KoboldCpp (covered in the companion dossier): KoboldCpp starts from llama.cpp and reaches *up* toward serving features; Aphrodite starts from vLLM and reaches *down* toward the personal/RP user. The two meet in the middle — and Aphrodite's existence is the strongest public proof that the meeting point is a real product category, not a thought experiment.

---

## 1. Identity and lineage, as documented

- The Aphrodite-era README (readable at tag v0.10.0, quoted in §10 sources) describes the engine as: an inference engine that "optimizes the serving of HuggingFace-compatible models at scale. Built on vLLM's Paged Attention technology, it delivers high-performance model inference for multiple concurrent users."
- The same README states it was "Developed through a collaboration between PygmalionAI and Ruliad" and serves "as the backend engine powering both organizations' chat platforms and API infrastructure." In other words, by its own account the project *began* as roleplay-platform infrastructure, not as a general serving product later adopted by RPers.
- Older PyPI descriptions (v0.4.x era) call it "the official backend engine for PygmalionAI," designed "to serve as the inference endpoint for the PygmalionAI website," crediting "FasterTransformer and vLLM" for its speed. Acknowledgements across eras credit vLLM (CacheFlow), FasterTransformer, xFormers, AutoAWQ, AutoGPTQ, SqueezeLLM, and ExLlama/ExLlamaV2.
- The fork relationship is *maintained*, not one-off: the project's own commit/release history contains periodic upstream-sync commits (titles of the form "chore(sync): sync to upstream …" / "[sync] … Upstream-vLLM: …"), as catalogued by the verification pass in §10. Aphrodite is therefore best understood as a **long-lived downstream fork with a recurring merge tax**, not a snapshot (see §7–§8).

## 2. Why fork vLLM for roleplay — the documented motivations

No single "why we forked" manifesto was found in the public material read; the motivations below are the ones the project's own feature choices and descriptions, plus reputable deployment guides, document in behaviour. They separate cleanly into three:

**2.1 The platform operator's need.** PygmalionAI runs a hosted character-chat service. It needed vLLM-class throughput (many concurrent users, batched decoding) for its own Pygmalion/MythoMax-class models — that is the stated original purpose (§1). A single-user engine (llama.cpp and family) does not serve a website; upstream vLLM does, but on upstream's terms.

**2.2 Quantization breadth for the community's checkpoints.** The RP community's model library does not live in BF16. It lives in quantized community releases on Hugging Face — GPTQ and AWQ builds, GGUF files, and other community formats. Upstream vLLM's roadmap prioritised mainstream production formats and recent datacentre hardware. Aphrodite's documented feature lists (§5) are dramatically wider, explicitly including GGUF and a long tail of community quant methods. Deployment guides summarise the resulting rule of thumb: pick Aphrodite over vLLM when your checkpoints are GGUF/GPTQ-class community quants (Spheron guide, §10). The consumer-hardware consequence is direct: a 4-bit checkpoint is what makes a 13B–70B model fit a single 24–48 GB card at all.

**2.3 The RP feature surface upstream would not ship.** Two things upstream vLLM did not offer, which the RP ecosystem treats as table stakes:
- **RP-grade samplers** — DRY, XTC, Mirostat and kin (§4). For long-form character chat, repetition collapse and bland top-probability continuations are *the* quality failure modes; the samplers that fight them were born in the Kobold/llama.cpp world, not the serving world.
- **A KoboldAI-compatible API** (§3), because the dominant RP frontend (SillyTavern) and its ecosystem grew up speaking Kobold. An OpenAI-only server is a foreign country to that tooling.

## 3. Serving behaviour, as documented

*Behaviour level only, per the header discipline. The engine core is inherited; what follows is what the documentation says it does, not how it is built.*

- **Core (inherited from vLLM):** continuous batching and paged KV-cache management (PagedAttention) — stated identically in both the Aphrodite-era and current READMEs. Requests are batched dynamically as they arrive and complete, rather than in fixed lock-step batches; KV cache is managed in paged blocks rather than one contiguous reservation per sequence. This is the datacentre half of the product, taken over wholesale.
- **Prefix caching** is listed among the engine's headline features, enabled by default in the current (Sonar-era) README's feature list; chunked prefill and an FP8 KV-cache option appear in the Aphrodite-era release notes (v0.6.1 notes cite "FP8 KV Cache + Chunked Prefill," initially limited to Ada Lovelace and Hopper GPUs).
- **Parallelism:** tensor, pipeline, data, and (in the current feature list) expert parallelism; multi-GPU and multi-node serving are documented features. The current parallelism guidance is conservative and worth quoting in spirit: start with one GPU; add parallelism only when one GPU cannot meet the memory or throughput requirement; keep tensor parallelism inside one high-bandwidth (NVLink-class) domain. *(Guidance text is from the current Sonar docs; the parallelism modes themselves are long-standing Aphrodite features.)*
- **Speculative decoding** is a documented, supported mode across eras: draft-model speculation, n-gram prompt-lookup decoding (documented on the Aphrodite docs site: candidates are gathered from the input text itself, no draft model needed), and — per a sample configuration file mirrored publicly — Medusa and MLP-speculator variants, with quantization applicable to the draft model (v0.6.1 notes: `--speculative-model-quantization`).
- **LoRA serving:** multi-LoRA support is a headline feature; v0.6.1 release notes document RSLoRA adapters, LoRA under pipeline parallelism, and **runtime load/unload endpoints** (`/v1/lora/load`, `/v1/lora/unload`) — i.e. adapters can be hot-swapped per deployment without a restart, and (per secondary guides) selected per request via the request's model field, including on quantized base models. For a character platform this is the "many personas, one base model" primitive.
- **Memory posture:** by design the engine claims ~**92% of GPU VRAM** by default (README, both eras; `--gpu-memory-utilization` lowers it). This is a server's posture — the card belongs to the engine — and it is the single clearest behavioural tell that Aphrodite is a *serving* engine even when a hobbyist runs it at home.
- **Observability:** Prometheus metrics on `/metrics`, inherited from vLLM (metric names largely compatible with vLLM dashboards, per the RunPod guide), plus per-LoRA request counters.
- **Model scope:** Hugging Face-compatible language models first; multimodal inputs, encoder–decoder serving (BART via the OpenAI server, v0.6.1), and Mamba support all appear in Aphrodite-era notes — the fork tracked upstream's widening model zoo rather than narrowing to chat models.

**API surfaces (documented):**
- **OpenAI-compatible API** — the default server, on port **2242** (not vLLM's 8000; the port itself is a Kobold-ecosystem heirloom). Completions and chat-completions endpoints; optional API keys.
- **KoboldAI-compatible API** — in early versions a separately launched endpoint module; in current form enabled alongside the OpenAI server with `--launch-kobold-api`, exposing `/api/v1/generate` on the same port 2242. This is the ecosystem bridge: SillyTavern, Kobold Lite and similar clients connect natively.
- **text-generation-webui (oobabooga)-compatible endpoint** — documented in early PyPI versions (an `api_server_ooba` entry point on port 8000), from the era when SillyTavern reached Aphrodite by selecting API Type "Aphrodite" under its TextGen WebUI menu. SillyTavern today carries Aphrodite as a **first-class Text Completion API type** in its own right, with its own default sampler ordering (see §4).
- The current (Sonar-era) README widens the front-end list further (adding e.g. Anthropic-compatible, pooling/scoring/reranking, transcription surfaces alongside OpenAI and Kobold). Those additions post-date the Aphrodite name and are recorded here only to show the trajectory: *more* API dialects over time, never fewer.

## 4. Sampler & generation surface, as documented

This is the section where Aphrodite most visibly diverges from its parent. Upstream vLLM's documented sampler set is the serving standard: temperature, top-p, top-k, repetition/frequency/presence penalties. Aphrodite's own feature lists add, verbatim in the current PyPI/README line: **"Support for modern samplers such as DRY, XTC, Mirostat, and more."** Older PyPI descriptions name **Mirostat, Locally Typical Sampling, and Tail-Free Sampling**. Behaviour of the headline additions, as publicly described:

- **DRY (Don't Repeat Yourself)** — penalises *repeated sequences*, not individual tokens: the longer a token sequence that already occurred in the context is being repeated, the stronger the penalty (documented request parameters include a multiplier, an exponential base, and a minimum match length). It attacks the RP failure mode of whole phrases and sentence shapes looping, which plain repetition penalty handles badly.
- **XTC (eXclude Top Choices)** — with a configurable probability, removes the highest-probability tokens above a threshold from the sampling pool for that step, forcing the model off its most generic continuation. Documented parameters: `xtc_probability`, `xtc_threshold`.
- **Mirostat** — entropy-targeting dynamic sampling: adjusts the effective truncation each step to hold the output's surprise near a target level (`mirostat_mode` and related parameters). Long documented in the project (named already in the earliest PyPI feature lists).
- **min-p** — keeps tokens whose probability is at least a fixed fraction of the *top* token's probability, so the candidate pool tightens when the model is confident and widens when it is not. Widely documented for Aphrodite in secondary guides and in SillyTavern's Aphrodite sampler handling; the project's own one-line feature lists fold it into "and more," so its presence is certain but its headline billing is via the ecosystem rather than the README.
- **Also documented in the surrounding surface:** eta-cutoff (named in secondary comparison tables), top-a, typical-p, tail-free sampling, epsilon-cutoff (the standard SillyTavern text-completion sampler panel, which SillyTavern maps onto Aphrodite), plus the inherited penalty family and `no_repeat_ngram`.

**Per-request control & ordering.** All of these are *request* parameters, not launch flags — each generation call carries its own sampler configuration alongside the standard fields (secondary guides show DRY/XTC/min-p passed as extra JSON fields in an otherwise OpenAI-shaped request). Sampler *order* is treated as meaningful: SillyTavern defines a dedicated default execution order for Aphrodite (DRY first, then penalties and no-repeat-ngram, then temperature-family steps), distinct from its orders for KoboldCpp and others. The lesson embedded here is that in the RP world a sampler stack is an *ordered pipeline*, and presets (whole named sampler configurations) are a user-facing artefact users share — the engine is expected to honour the full stack per request.

## 5. Quantization & models, as documented

The Aphrodite-era README at v0.10.0 lists, in one feature bullet: **AQLM, AutoRound, AWQ, BitNet, BitsAndBytes, EETQ, GGUF, GPTQ, QuIP#, SqueezeLLM, Marlin, FP2–FP12 formats, NVIDIA ModelOpt, TorchAO, VPTQ, compressed-tensors, MXFP4, "and more."** The current (Sonar) docs replace the bullet with a generated quantization matrix (AWQ/AutoAWQ, GPTQ and GPTQ-Marlin, AWQ-Marlin, FP8 variants, EXL3, BitsAndBytes, compressed-tensors, ModelOpt family, MXFP4, TorchAO, …), each method annotated with a minimum GPU compute capability, noting that NVIDIA CUDA accepts all registered methods. Three observations matter for our purposes:

- **GGUF in a vLLM fork is the architecturally notable act.** GGUF is llama.cpp's single-file, CPU-born format; the entire RP community's download library is GGUF files. Aphrodite documents loading them (`--quantization gguf`, pointing at a .gguf file or a GGUF Hugging Face repo, with a separate tokenizer source where needed) inside a paged-attention, continuously-batched server. Behaviourally, that means the community's existing model shelf becomes servable at datacentre concurrency *without re-quantizing or converting anything* — the fork absorbed the other ecosystem's artefact format rather than demanding the ecosystem change. Secondary guides add a caveat worth recording: GGUF coverage is described as solid for the standard K-quants (Q4_K_M, Q5_K_M, Q8_0) but less complete than native llama.cpp for exotic variants — for a GGUF-only workload, a native llama.cpp-family server remains the reference. *(Caveat is from the Spheron guide, §10, not the project's own docs.)*
- **Marlin fast paths are auto-detected.** GPTQ/AWQ checkpoints that are Marlin-compatible are documented (in secondary guides, consistent with the format matrix listing `gptq_marlin`/`awq_marlin` as first-class methods) to activate the Marlin kernels automatically — the user names the checkpoint; the engine picks the fast kernel. No re-quantization step.
- **The EXL2 question — flagged honestly.** 2026 deployment guides (Spheron, RunPod) repeatedly describe Aphrodite as serving **EXL2** checkpoints via bundled ExLlamaV2 kernels, and ExLlamaV2 is credited in the project's acknowledgements in every era. However, the independent README-level verification (§10) found **no Aphrodite/Sonar feature list that actually names EXL2 as a quantization method**, and the current generated matrix lists **EXL3**, not EXL2. This dossier therefore records EXL2 support as **widely claimed by secondary sources but not verified against the project's own feature documentation**. (EXL2 the *engine/format* is covered by its own dossier in this corpus; the point here is only what Aphrodite documents about itself.)

**Models.** Any Hugging Face-compatible model the underlying vLLM lineage supports is in scope, plus the fork's additions over time (Mamba, encoder–decoder, multimodal — §3). The practical RP consequence: fine-tuned character models published only as community quants — the Pygmalion/MythoMax lineage and its successors — are first-class citizens here, whereas on upstream they are edge cases.

## 6. Hardware, as documented

*Aphrodite era (to v0.10.x and the v0.22.0 requirements, which still carried the Aphrodite lineage directly):*
- **NVIDIA CUDA is the centre of gravity.** Requirements at v0.22.0: Linux, or Windows via WSL2 (no native Windows); Python 3.10–3.13; CUDA 12+. Early PyPI text adds a compute-capability floor: **CC 7.5+ required for AWQ**, with GPTQ as the fallback for older cards. Secondary guides describe Pascal-and-newer (GTX 1080 / P100 class) as the supported floor overall — a deliberately wider net than datacentre-only engines, matching the "whatever card the community owns" mission. Treat the Pascal claim as secondary-source, the CC-7.5-for-AWQ claim as project-documented.
- **AMD / other platforms in the Aphrodite era:** the Aphrodite-era material read for this dossier does not headline ROCm support; the engine inherits whatever platform story its vLLM base had at each sync point, and its own documentation led with CUDA. **Any stronger AMD claim for the Aphrodite era is unverified here.**
- *Current (Sonar) state, for contrast:* the present installer documents Linux x86-64 with NVIDIA CUDA, **AMD ROCm, or CPU**, plus Arm64 and Apple-silicon macOS (Metal), and the full install guide adds Intel XPU and Google TPU paths. That breadth is real but post-dates the rename; it shows where the lineage is heading, and must not be back-projected onto Aphrodite-era releases.
- **The VRAM posture (§3) is the operative hardware fact for personal users:** the engine takes ~92% of the card by default. On a 24 GB consumer card running a quantized 13B, that is a feature (maximum KV-cache room for long RP contexts and concurrent sessions). On a shared desktop card, it is a commitment — you lower `--gpu-memory-utilization` deliberately, or the engine owns the GPU.

## 7. Project health, as public fact

- **Cadence:** long-lived and active across the whole period. PyPI shows a steady release train from the 0.3.x/0.4.x era (2023–24) through **v0.10.0** under the Aphrodite name; release notes at v0.6.1 already speak of getting "back on track again with quicker releases," i.e. cadence discipline was a stated concern early. Development continued under the same repository through v0.24.1 (September 2026, last `aphrodite_engine`-named wheels).
- **The rename (post-dossier-scope event, recorded for accuracy):** on **2026-11-07** a breaking commit renamed Aphrodite Engine to **Sonar**; **v0.25.0 (2026-11-08)** is the first `sonar`-wheeled release, under the dphnAI organisation, still serving PygmalionAI workloads among others. The project's migration notes are blunt: install the new package in a fresh environment; imports, CLI names, and `APHRODITE_*` environment variables change with no fallback; the old PyPI package does not install the renamed release. The repository was still being pushed to as of 2026-11-09. Readers meeting "Sonar" in the wild should know it *is* this engine, renamed in place — same repository id, same lineage.
- **Fork drift is a documented, structural reality.** The sync-commit pattern (§1) means Aphrodite's vLLM base is a *moving negotiation*, not a pin: each upstream release must be merged, and fork-specific surface (quant methods, samplers, Kobold API) re-validated against it. The observable consequence, noted by third-party trackers, is that the fork **lags upstream on brand-new model architectures** while leading it on community formats and samplers. That is the fork's bargain, struck openly.
- **Community position:** Aphrodite is the Pygmalion ecosystem's engine — the backend behind PygmalionAI's own chat platform — and a named, first-class backend in **SillyTavern** (its own Text Completion API type, its own sampler-order preset), which is the RP world's dominant frontend. In the ecosystem's mental map it occupies the "serious serving, RP-native" slot: heavier to run than KoboldCpp, chosen when concurrency, HF-native models, or the full sampler/quant matrix justify it.

## 8. Strengths / weaknesses

**Strengths**
- **The complete RP serving stack in one process:** paged KV + continuous batching + community quants (incl. GGUF) + RP samplers + Kobold API + multi-LoRA. No competitor in this corpus combines all six; each rival lacks at least one leg.
- **Format hospitality:** the widest documented quantization matrix in the runner field (§5). The user's existing model shelf — however it was quantized, by whomever — probably loads.
- **Sampler depth as a quality feature:** DRY/XTC/Mirostat/min-p are not garnish; for long-form character chat they are the difference between a persona that stays in voice for 200 turns and one that loops by turn 30.
- **Ecosystem fit:** SillyTavern first-class support and a Kobold dialect mean zero frontend friction for its target users.
- **Proven at platform scale:** it runs (by its own account) real hosted chat platforms, not only hobby installs.

**Weaknesses**
- **AGPL-3.0 consequences (the big one).** AGPL's network clause means anyone who modifies Aphrodite and offers it as a network service must offer that service's users the corresponding source. For personal and internal use this is a non-issue; for a commercial hosted product it is a legal design constraint that upstream vLLM (Apache-2.0) does not impose — and it is the reason several guides lead with the licence before the features. For *our* corpus the consequence is methodological as much as legal: Aphrodite is a **study source, never a code source** — hence this dossier's behaviour-only discipline.
- **Fork-drift maintenance cost:** the sync treadmill (§7) is permanent. Features can lag upstream; upstream refactors can break fork surface; the project's history shows the team paying this tax continuously. Any long-lived fork inherits this — including, prospectively, ours if we ever fork rather than build.
- **Server posture on personal hardware:** ~92% VRAM claim, Linux/WSL2-only in its era, Python/CUDA environment weight. Next to KoboldCpp's single-file double-click experience, Aphrodite asks its personal users to meet it on datacentre terms.
- **GGUF is a guest, not a native:** documented GGUF support is real but (per secondary guides) narrower than llama.cpp's own — the format's home engine remains the reference implementation.
- **Identity discontinuity:** the 2026 rename to Sonar, with breaking package/CLI/env-var changes and no compatibility fallback, strands Aphrodite-named documentation, tutorials, and muscle memory. (Observation, stated neutrally: the project chose a clean break over aliases.)

## 9. Ideas to steal — licence-clean, ideas only

*Each idea below is a behaviour/product idea observed in public documentation, restated for independent implementation in our own Go engine. No Aphrodite code, text, or expression is carried over; AGPL material is inspiration at the level of "this product shape works," nothing more.*

1. **Ship the two halves together: datacentre machinery × persona feature canon.** Aphrodite's whole existence demonstrates that RP users do not want a *choice* between paged-KV/batched serving and the RP sampler/preset culture — they want both, in one binary, and will accept a heavier engine to get it. *Gain:* this is precisely Volmarr's commission (an improved Ollama for personal character chat); Aphrodite is the market proof that the merged product is wanted. *Cost/risk:* scope — batching + paged KV is the hardest machinery in the field; the steal is the *product shape*, sequenced honestly, not a promise to match throughput on day one.
2. **KoboldAI-API compatibility as an ecosystem bridge.** One extra API dialect bought Aphrodite instant citizenship in the SillyTavern world — every frontend, preset, and tutorial in that ecosystem worked unmodified. *Gain:* for a Go Ollama-successor, a Kobold-compatible endpoint (alongside the Ollama and OpenAI dialects) is a disproportionately cheap adoption multiplier in exactly our target community. *Cost/risk:* dialect surface must be maintained as the ecosystem's expectations evolve; keep it a thin translation layer over the native API, never a second engine.
3. **Load the other ecosystem's artefact format (the GGUF lesson).** Aphrodite, a vLLM fork, went and learned GGUF rather than telling RP users to convert their libraries. *Gain:* meeting users' existing model shelves where they lie removes the single largest switching cost; for our engine this validates GGUF-first as the home format *and* argues for never demanding conversion as the price of admission. *Cost/risk:* every foreign format is a permanent compatibility surface with edge cases (the exotic-K-quant caveat in §5 is the honest price tag).
4. **Samplers as an ordered, per-request, preset-shareable pipeline.** Aphrodite + SillyTavern together show the mature shape: sampler stacks are ordered (order changes output), configured per request, and exchanged between users as named presets. *Gain:* implementing DRY/XTC/min-p/Mirostat-class samplers as composable, orderable stages — with preset import/export — gives a personal engine the RP quality ceiling without any serving machinery at all; this is the cheapest high-value steal in the dossier. *Cost/risk:* sampler interactions are subtle and order-sensitive; needs a conformance-test habit (fixed seed, fixed prompt, recorded distributions) or the surface rots silently.
5. **Auto-detect the fast path (Marlin lesson).** The user names a checkpoint; the engine notices it is Marlin-compatible and uses the fast kernel, unasked. *Gain:* performance as a default behaviour rather than a flag the user must already understand — directly aligned with the "it should just work on the user's card" goal for a personal engine. *Cost/risk:* silent kernel selection must be *loud in the logs* (the guides note checking startup logs to confirm Marlin engaged); invisible magic that cannot be inspected becomes a support burden.
6. **Multi-LoRA as the persona primitive.** Hot-loadable adapters, selectable per request, on quantized bases: one base model, many characters, swapped in milliseconds. *Gain:* for character chat this maps perfectly — personas/skills as adapters over one resident base is cheaper in VRAM than one full model per character, and Aphrodite proves the pattern in production RP service. *Cost/risk:* adapter-on-quantized-base quality and compatibility vary; treat as an accelerator for compatible bases, not a universal guarantee.
7. **Speculative decoding without a draft model (n-gram prompt lookup).** RP prompts are long and self-similar (character cards, lore, repeated phrasing); a documented speculation mode that mines the *prompt itself* for continuations fits this workload unusually well. *Gain:* latency wins for long-context chat with zero extra model to host. *Cost/risk:* gains are workload-dependent (marked as expectation, not measurement — no benchmark for it was read in the project's own docs during this pass).
8. **State your VRAM posture as a product decision.** Aphrodite documents its 92% claim openly, with the knob to lower it beside the claim. *Gain:* for our engine, the equivalent honesty — a stated default memory posture for personal machines (where the GPU is shared with a desktop) plus one obvious knob — prevents the entire class of "your engine ate my card" failures. *Cost/risk:* none beyond the discipline of writing it down; the steal is the explicitness, and the *value* (92%) is a server value we should consciously not copy for a desktop-resident engine.
