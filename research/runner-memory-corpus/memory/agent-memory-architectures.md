# OR-6 Dossier A5: Agent Memory Architectures — What Persists Between Sessions, How It Is Retrieved, and How It Is Corrected

> Research Forge campaign — commissioned by Volmarr, 2026-11-15.
> Domain: OR-6 (memory), dossier A5 in the memory field map (`00-MEMORY-FIELD-MAP.md`).
> Clean-room note: this dossier is written in our own words. No source text is reproduced beyond short factual labels (function names, benchmark names, scores as published). Every factual claim about an external system is cited to a public source listed in §8, accessed 2026-11-15.
> Scope boundary: the runner dossiers in this corpus cover *in-context* memory — KV cache, prefix reuse, residency. This dossier covers the layer above them: the store that survives the end of a session, the machinery that decides what enters the next session's context, and the editor that is supposed to keep that store true. Where the two layers meet, this dossier says so explicitly.

## 1. Header + essence: the two-layer truth

**Essence.** A deployed language model has two completely different things that are both called "memory," and confusing them is the root of most bad design in this area:

1. **In-context memory is a cache.** The context window, and the KV cache that implements it, hold a working set for the current computation. It is fast, exact, and volatile: when the session ends, the runner unloads, or the window overflows, it is gone. Its correctness problem is *capacity* — what to keep resident — and the runner corpus (PagedAttention, prefix caching, KV compression) is the literature of that problem.
2. **Agent memory is a database with an editor.** Between sessions, something must persist on disk: facts about the user, a record of what happened, skills that worked, the persona that must not drift. That store is written by an *extraction* step (usually another model call), read by a *retrieval* step (usually embedding search plus ranking), and maintained — or not maintained — by an *update* step. Its correctness problem is not capacity. It is *truth over time*: facts change, extractions hallucinate, retrievals return the stale copy instead of the current one, and nothing in a plain vector store notices.

The two-layer truth, stated as a law for this corpus: **in-context memory is a cache; agent memory is a database with an editor, and most failures live in the editor.** A system can have a perfect KV cache and still lie to its user every morning, because the lie was written into the persistent store three weeks ago, was never superseded, and is retrieved faithfully. Conversely, a system with a modest window and an honest store — versioned facts, visible provenance, a user who can inspect and delete — will feel more trustworthy than a million-token window fed by a rotting store, because the window only amplifies what the store gives it.

Three consequences follow, and they organise the rest of this dossier:

- **Writes matter more than reads.** The literature markets retrieval (embeddings, rerankers, graphs). The failures users report — "it remembered something I never said," "it still thinks I live in my old city," "it merged two different people" — are almost all write-side or update-side failures: a bad extraction, a missing supersession, a consolidation that invented a detail. Retrieval faithfully surfaced a corrupt record.
- **Every persistent memory system is therefore an editorial system.** Someone or something decides what is worth keeping, in what words, under what key, and what happens when a newer statement contradicts an older one. In MemGPT/Letta that editor is the agent itself, via function calls (§3). In ChatGPT-style products it is a background extraction pipeline the user does not control turn-by-turn (§5). In Zep/Graphiti it is a temporal graph builder that invalidates rather than deletes (§6). The designs differ mainly in *who edits, when, and whether the edit is visible*.
- **Append-only memory plus retrieval guarantees eventual contradiction.** If the store only ever adds and never supersedes, then for any fact that ever changes, the store eventually contains both the old and the new value, and retrieval — which ranks by similarity and recency, not by truth — will sometimes serve the old one. This is not a tuning problem. It is a structural property, proved in §6 and measured, in effect, by the knowledge-update slice of LongMemEval (§6.5).

Why this matters to Volmarr's commission specifically: the Ollama work is driven by character memory — a persona that must not be lost, facts that must not silently rot, and memory that must not hallucinate. Those are precisely the three failure classes of the editor layer: *loss* (the anchor falls out of context or out of the store), *rot* (a superseded fact keeps being served as current), and *invention* (an extraction or reflection writes something that was never said). The runner can solve none of them. This dossier is about the layer that must.

## 2. The taxonomy: working / episodic / semantic / procedural

The agent literature borrowed its memory vocabulary from cognitive science, and — unusually for borrowed vocabulary — mostly kept the meanings. Two survey treatments anchor the usage in this dossier, both verified:

- **CoALA — Cognitive Architectures for Language Agents** (Sumers, Yao, Narasimhan & Griffiths, arXiv:2309.02427, published in *Transactions on Machine Learning Research*, 2024). CoALA organises a language agent along three axes — memory, action space, decision loop — and divides memory into *working* memory for the current decision cycle plus three long-term stores: *episodic*, *semantic*, and *procedural*. It is a descriptive framework, not an implementation, and it is the cleanest source for the four-way split.
- **Zhang et al., "A Survey on the Memory Mechanism of Large Language Model based Agents"** (arXiv:2404.13501, 2024; later published in *ACM Transactions on Information Systems*). Zhang et al. survey memory *mechanisms* — how memory is written, managed, and read — and distinguish memory by source, form, and operation, including the write–manage–read loop that later surveys formalised. Read together, CoALA supplies the *types* and Zhang et al. supply the *operations* performed on each type.

A later survey, Du (2026), "Memory for Autonomous LLM Agents" (arXiv:2603.07670), restates the same four temporal types and adds a useful emphasis on the *transition policy* between them — when an episodic record graduates to semantic status — as the under-specified step in most systems. This dossier cites Du only for that framing; the taxonomy itself needs no source newer than CoALA and Zhang et al.

### 2.1 The four types, mapped to concrete mechanisms

| Type | What it holds (agent-literature usage) | Concrete mechanism in deployed systems | Typical lifetime | Characteristic failure |
| --- | --- | --- | --- | --- |
| **Working** | The active state for the current decision cycle: current goal, recent turns, retrieved items, scratch reasoning | The context window itself, plus any structured state the harness re-injects each turn (system prompt, core blocks, tool results) | One turn to one session | Overflow eviction; silent truncation (see the Ollama dossier in this corpus: two truncation layers, neither reported to the caller) |
| **Episodic** | Records of concrete experiences, anchored in time: "this happened, then, in this session" | Conversation logs / recall stores; Generative Agents' memory stream (§4); Zep/Graphiti *episodes* kept verbatim as provenance | Months to indefinite; usually the largest store | Retrieval miss (the episode exists but is never surfaced); volume growth making ranking, not storage, the bottleneck |
| **Semantic** | De-contextualised knowledge abstracted from episodes: facts and preferences stated without their occasion ("the user prefers metric units"; "the user lives in Berlin *now*") | Extracted fact stores; vector-indexed memory items (Mem0-style); profile summaries (ChatGPT-style); entity–relation edges (Graphiti-style) | Until superseded — which is exactly the hard part (§6) | Staleness and contradiction: two values for one slot, both retrievable, no rule for which is current |
| **Procedural** | How to do things: reusable skills, plans, tool-use patterns, standing instructions | Voyager's skill library of verified executable code (§2.2); system prompts and standing instruction files; tool traces distilled into reusable procedures; in CoALA, also the model's own weights as *implicit* procedural memory | Long; changes by addition more than by correction | A stale procedure that still executes (the skill works, but the world it assumed has changed); untested self-written procedures promoted without verification |

Two distinctions the table makes visible, and that product marketing routinely blurs:

**Episodic is not semantic, and the step between them is lossy by design.** An episode says what was said. A semantic fact says what is *so*. Getting from the first to the second requires an inference — extraction, summarisation, or reflection — and every such inference can drop a qualifier ("might move to Berlin" → "lives in Berlin"), merge two entities, or invent a connective detail. Systems that keep the raw episode alongside the derived fact (Graphiti's design, §6.3) can audit the derivation. Systems that keep only the derived fact cannot: when the fact is wrong, there is nothing to check it against. *Provenance retention is therefore not a logging nicety; it is the precondition for correction.*

**Procedural memory in agents is mostly not in the weights.** CoALA counts model weights as implicit procedural memory, which is correct for capabilities ("how to write a sonnet") but misleading for deployments: the procedural memory a *deployment* can actually govern — standing instructions, skill libraries, tool policies — lives outside the model, in text and code the operator can version. Voyager (§2.2) is the canonical demonstration that this external, explicit form compounds: skills accumulate without overwriting each other, precisely because they are stored artefacts rather than weight updates.

### 2.2 Worked anchors for each type

- **Working:** any chat client's rendered prompt. In this corpus's terms, working memory is what the runner's KV cache caches — the two dossiers meet exactly here.
- **Episodic:** Generative Agents' memory stream (§4) is the purest published form: an append-only, timestamped, natural-language log of observations, with reflections and plans stored in the same stream. Letta's *recall* store (the searchable conversation history, §3) is the production descendant of the same idea.
- **Semantic:** ChatGPT's saved memories (§5) and Mem0's extracted facts (§5.3) are the two most-deployed forms: short natural-language statements, extracted from episodes, injected into future prompts. Graphiti's entity–relation edges are the structured form of the same type.
- **Procedural:** Voyager (Wang et al., 2023, arXiv:2305.16291) — a Minecraft agent whose skill library stores every *verified* JavaScript skill, indexed by an embedding of its description, retrievable and composable for later tasks. The verification gate is the point: a skill enters procedural memory only after execution confirms it worked. Most conversational systems have no equivalent gate for semantic memory — a fact enters the store because an extractor produced it, not because anything checked it. That asymmetry explains a large share of memory hallucination in production (§5.4, §6).

### 2.3 The operations: write – manage – read

Types alone do not describe a system. Zhang et al.'s mechanism view, and the later write–manage–read formalisation, add the operations every store must implement, explicitly or by accident:

1. **Write (extraction / encoding).** Decide what, from a raw episode, becomes a persistent record, and in what form. Choices: verbatim episode retention; extracted atomic facts; rolling summary; self-authored notes (Letta); reflection products (Generative Agents). *Every honesty failure in §6 can be traced to a write that was wrong, over-confident, or unprovenanced.*
2. **Manage (consolidation / update / forgetting).** Deduplicate, merge, supersede, expire, summarise, promote episodic → semantic, demote or archive the cold. This is the least implemented operation in shipped systems and the most important one for honesty. Letta's sleep-time compute (§3.4) and ChatGPT's later automatic memory management (§5.2) are both, in essence, attempts to staff this shift.
3. **Read (retrieval / injection).** Select, rank, budget, and place records into working memory for the current turn. Ranking signals in use: embedding similarity (relevance), recency/decay, importance, graph distance, lexical match — usually fused. The read step also owns the *injection budget*: how many tokens of memory the turn can afford, and in what order they are placed (§5.3).

A useful diagnostic for any memory product, used throughout §5–§6: **name its write, its manage, and its read. If it cannot name its manage step, it does not have one — it has accumulation.**

## 3. MemGPT / Letta deep: the OS metaphor made precise

### 3.1 The paper

Packer, Wooders, Lin, Fang, Patil, Stoica & Gonzalez, "MemGPT: Towards LLMs as Operating Systems" (arXiv:2310.08560, submitted October 2023, revised February 2024, UC Berkeley). The proposal is *virtual context management*: treat the context window the way an operating system treats physical RAM — as the fast, small tier of a hierarchy — and give the model the equivalent of system calls to page information between that tier and larger, slower, external tiers. The model itself decides what to page in, what to write out before it is evicted, and when to search its own history. Control flow borrows a second OS idea: *interrupts* — events (a user message, a timer, a memory-pressure warning) that hand control to the agent loop between generations.

The paper evaluates two settings where a fixed window is the binding constraint: document analysis far beyond the window, and multi-session chat. On its Deep Memory Retrieval (DMR) evaluation over multi-session conversation histories, the reported lift over a fixed-context baseline is large — for GPT-4, from 32.1% to 92.5% accuracy in the figures as reported by the paper and its subsequent summaries. Read that number with the discipline this corpus applies elsewhere: DMR is the MemGPT team's own benchmark, the questions are over a specific multi-session dataset family, and scoring involves model-based judgement. The number establishes that *managed* context beats *unmanaged* context on the authors' test by a wide margin. It does not establish a universal recall figure for any successor product, and later vendor comparisons that quote DMR scores from different pipelines are not commensurable (see §6.5 on benchmark hygiene).

### 3.2 The tiers, precisely

MemGPT as published distinguishes *main context* (what is in the prompt) from *external context* (everything pageable). Letta — the production framework the same team built from the project, renamed from MemGPT in September 2024 — refines external context into two named stores, giving the three-tier model now standard in descriptions of the lineage:

| Tier | OS analogue | Holds | How it is accessed | Visibility |
| --- | --- | --- | --- | --- |
| **Core memory** (main context) | RAM / pinned working set | A small set of labelled, editable *memory blocks*: by convention a `persona` block (who the agent is) and a `human` block (who the user is), plus task/project blocks as needed | Always in the prompt; edited in place by the agent via memory tools | Every turn, unconditionally |
| **Recall memory** | Disk cache / log | The conversation history — messages as they occurred | Searched on demand (keyword / conversation search tools) | Only when the agent asks |
| **Archival memory** | Cold storage | Long-term facts, documents, and material the agent chose to file for later | Inserted and searched via tools, typically over a vector index | Only when the agent asks |

The mechanics that make this an OS rather than a metaphor:

- **Function calls as system calls.** The model is given a bounded tool set for memory: append to / replace within a core block, insert into archival memory, search archival memory, search conversation history. A memory operation is therefore an ordinary tool call inside the agent loop: the model emits it, the runtime executes it against the store, and the result is spliced back as an observation before generation continues.
- **Pressure signals as interrupts.** When token usage crosses a warning threshold (the paper's worked example uses ~70% of the window), the runtime inserts a system warning telling the model to move what matters into persistent storage. At the flush threshold, the oldest portion of the queue is evicted and replaced by a recursive summary of what was evicted. Eviction is thus *announced and summarisable*, not silent — contrast the Ollama truncation behaviour documented in this corpus, where the equivalent loss is, at the compatibility API layer, not reported to the caller at all.
- **Heartbeat / scheduling.** The original design includes heartbeat-style continuation: the agent can request to be woken again (to finish a multi-step memory operation, or to act on a schedule) rather than ending its turn. Later Letta versions reworked the loop around native reasoning channels, but the architectural point survives: *memory management takes multiple steps, so the loop must let the agent spend steps on memory without confusing that with failing to answer.*

### 3.3 Self-editing blocks — and the direct line to the character-anchor law

The load-bearing primitive is the **memory block**: a labelled, size-bounded, persistent string that lives in core memory and that the agent edits with tools of the form *append to block* and *replace substring in block*. The bound matters as much as the editability: a block capped at hundreds to a few thousand characters forces curation. The agent cannot hoard; to add a new standing fact it must eventually compress, merge, or drop an old one — inside the block, in the open, where the edit is a recorded tool call.

The two conventional blocks deserve to be named plainly, because they are the point of contact with Volmarr's own law:

- The **`persona` block** holds the agent's self-description: identity, voice, standing behavioural commitments. It is in *every* prompt, at a *stable position*, under a *token budget the block itself enforces*.
- The **`human` block** holds the distilled facts about the user that the agent has decided must never need retrieving — the facts whose absence would break the relationship if forgotten for one turn.

That is, in agent-layer form, exactly the **character-anchor pattern** this programme already enforces at the prompt layer in its Voxta work: the character prompt sits at the end of memory in an unpushable anchor, resident context is not reprocessed each turn, and the persona is never left to compete with retrieved material for a place in the window. Letta's core blocks are the same engineering judgement, generalised: *the small set of things that define who is speaking and who is being spoken to must be pinned, budgeted, and edited deliberately — never retrieved probabilistically.* Retrieval is for the episodic and the archival. Identity is not a retrieval problem.

The converse also holds, and Letta's design makes it visible: anything *not* promoted into a core block is, by construction, allowed to be absent on any given turn. A deployment therefore has to decide, explicitly, which facts are anchor-class (always present, block-budgeted, human-auditable) and which are retrieval-class (present when relevant). Most consumer memory products make this decision implicitly and opaquely (§5); Letta at least makes it a visible artefact — a block with contents you can print.

### 3.4 What Letta added in production: sleep-time compute

Letta's later addition, **sleep-time compute**, moves the *manage* operation (§2.3) off the critical path: a second, background agent shares the same memory blocks and, while the primary agent is idle between turns or sessions, re-reads recent transcripts, consolidates blocks that are near their limit, files material into archival storage, and — in the stronger descriptions of the pattern — invalidates archival records that newer material contradicts. The primary agent then starts its next turn from cleaned memory instead of paying consolidation latency (and tokens) inside the user's turn.

The idea generalises beyond Letta and should be recognised wherever it appears: ChatGPT's automatic memory updating (§5.2) is a closed version of the same move, and Generative Agents' reflection (§4) is the research version. *Consolidation is batch work. Systems that try to do it inline, in the answering turn, either skip it or make the user pay for it; systems that never do it at all accumulate.* Sleep-time consolidation is the first design in this lineage that staffs the manage shift without taxing the read path.

Letta also, in its coding-agent line, versions memory as files under version control (a git-backed memory directory), so that every self-edit leaves a diff. That detail matters for §6: a self-editing agent whose edits are diffs can be audited and rolled back; a self-editing agent whose edits silently overwrite a database row cannot.

### 3.5 What the design costs — stated honestly

- **Model calls spent on memory management.** Every page-in, search, edit, and consolidation is model reasoning and, in the sleep-time design, whole extra model invocations. MemGPT-style agents are measurably slower and more token-hungry per user turn than a stateless chat call. The cost is the price of the capability, but it must be budgeted as such: on a local, Ollama-class deployment, the memory manager competes for the same GPU and the same KV budget as the conversation itself (§7).
- **The editor is the model, with the model's failure modes.** Self-editing means the agent decides what is important. It can fail to write what mattered, write what did not happen, replace the wrong substring, or — under concurrent triggers — race its own edits. Published engineering commentary on Letta-style deployments notes the sharp edges plainly: exact-substring replace fails when the text has drifted, concurrent turns can conflict on the same block, and there is no built-in transactional lock on blocks. Self-editing buys autonomy at the price of audit burden.
- **Function-calling competence is a dependency.** The original paper's weaker results with a smaller model were attributed in large part to weaker function calling. A memory architecture that requires the model to operate its own memory inherits a floor on model capability — directly relevant to small local models (§7).
- **Forgetting is not automatic.** In Letta-style blocks, nothing fades on its own; a memory leaves only if an agent edits it out or a sleep-time pass removes it. That is safer than silent decay for anchor-class material and worse than decay for trivia. The design has no native answer to "this was true, low-stakes, and is now clutter" except editorial labour — human or model.

**Verdict on the lineage.** MemGPT's contribution was not "a bigger context." It was the reframing of context as a *managed hierarchy with an accountable editor*, plus the demonstration that a model can operate that hierarchy through tools. Letta's contribution was to make the editor's workplace concrete — bounded blocks, named tiers, background consolidation, versioned edits. Every serious system since, including the closed consumer products in §5, is a variation on how much of that editor the user is allowed to see.

## 4. Generative Agents: memory stream, reflection, and the retrieval score

### 4.1 The paper and the setup

Park, O'Brien, Cai, Morris, Liang & Bernstein, "Generative Agents: Interactive Simulacra of Human Behavior" (UIST 2023; arXiv:2304.03442). Twenty-five agents inhabit a small sandbox town ("Smallville"). Each agent is an LLM (gpt-3.5-turbo in the paper) wrapped in an architecture with three components — a memory stream, reflection, and planning — seeded with a single paragraph of identity description. The research question was believability of simulated social behaviour over simulated days, not production memory correctness. That framing must be kept: Generative Agents is evidence about *what a memory architecture makes possible*, evaluated by human judgements of believability, not evidence about factual memory accuracy at production scale.

### 4.2 The three components

**Memory stream.** An append-only list of memory objects, each a natural-language description with a creation timestamp and a last-accessed timestamp. The base objects are *observations* — events the agent perceived, including its own actions. Reflections and plans are written into the same stream and retrieved by the same machinery; there is one store, typed by content rather than split into databases. In the taxonomy of §2, the stream is episodic memory that also carries its own derived semantic products (reflections) — an elegant unification, and a provenance hazard, since a reflection sits in the stream with the same standing as an observation unless the reader checks its type and its cited evidence.

**Retrieval score.** Because the stream quickly exceeds any prompt, each decision retrieves a small set scored on three normalised components, combined as a weighted sum (equal weights in the implementation as described):

- **Recency** — an exponential decay over time since the memory was last *accessed* (decay factor 0.995 per simulated hour in the paper's implementation). Note the subtlety: retrieval refreshes recency, so a memory that keeps being retrieved stays young — a rich-get-richer dynamic that is plausible for human-like salience and dangerous for stale facts (§6).
- **Importance** — an integer score (1–10) the model itself assigns when the memory is created, rating how significant the event is. Mundane observations score low; life events score high. Importance is therefore a *model judgement made at write time*, with all the calibration risk that implies.
- **Relevance** — embedding cosine similarity between the memory and the current situation/query.

The top-scoring memories are placed in context. Retrieval is *ranked, not filtered*: there is no truth gate, no supersession check, no source check. The score decides what the agent thinks with; nothing in the score knows whether a memory is still true.

**Reflection.** Raw observations do not generalise, so periodically — when the summed importance of recently perceived events crosses a threshold (150 in the implementation, firing roughly two to three times per simulated day) — the agent reflects: it takes its recent memories, generates salient high-level questions about them, retrieves memories relevant to each question, and writes inferences that cite the memories they were drawn from. Those inferences re-enter the stream, forming a *reflection tree*: observations at the leaves, increasingly abstract conclusions above them, themselves retrievable and reflectable-upon. Reflection is episodic → semantic consolidation (§2.3, manage) performed by the model, on a schedule, with citations — the most explicit published design for the consolidation step in the whole literature this dossier covers.

**Planning.** Retrieved memories and reflections feed a recursive planner (day plan → hour plan → minute-level actions), with reactions that can revise the plan when a new observation warrants it. Planning is included here only to complete the architecture; its memory relevance is that plans are *written back* as memories, so an intention formed on Monday is retrievable as context on Tuesday — procedural/episodic crossover, in §2's terms.

### 4.3 What the evaluation showed — and what it did not

The paper's ablation study interviewed agents under five conditions (full architecture; no reflection; no reflection or planning; observation-only variants; and a human crowdworker baseline writing behaviour by hand) and ranked believability with human raters, summarised with TrueSkill. The full architecture scored highest (μ ≈ 29.89), ahead of no-reflection (≈ 26.88), no-reflection-or-planning (≈ 25.64), the crowdworker baseline (≈ 22.95), and the full ablation (≈ 21.21). The two-day open simulation produced the famous emergent results — information about a party spreading from a seeded 4% of agents to 52%, relationship-network density rising, invited agents actually attending — from one agent seeded with the intention to host it.

What this establishes: each of observation, reflection, and planning contributes measurably to *perceived believability*, and a scored memory stream is sufficient machinery to sustain coherent simulated persons over days. What it does **not** establish: factual precision of recall (believability raters reward plausible coherence, and a confidently wrong memory can be highly believable), behaviour at thousands of agents or months of stream growth, or cost viability — the authors themselves report token costs in the thousands of dollars and multi-day wall-clock runs for 25 agents over two simulated days.

### 4.4 Known limits, including the honesty limits

- **Toy scale, by design.** Twenty-five agents, one town, two days. Nothing in the result speaks to retrieval quality when the stream holds a year of a real user's life.
- **Retrieval still misses.** The authors document agents failing to recall something they had perceived, or recalling a detail without its event — the ranking function is a heuristic, and its failures are silent.
- **Reflection can fabricate.** Reflections are model inferences; the paper and subsequent readings note invented or embellished conclusions entering the stream, after which they are retrieved with the same authority as observations. This is the Generative Agents form of the editor problem (§1): *the consolidation step is a hallucination surface.* The citation requirement (a reflection must point at its evidence memories) is the paper's mitigation, and it only helps a reader who follows the citations — the acting agent, mid-retrieval, generally does not.
- **Append-only, ranked-not-filtered.** Corrections are new entries competing with old entries under a score that rewards recent access. A superseded observation is never invalidated. §6 returns to this as the general theorem; Generative Agents is its cleanest early exhibit, excused only by the fact that in a two-day simulation, few facts have time to change.

**Why the paper still anchors this dossier.** Generative Agents isolated the three mechanisms every later system reuses — a timestamped episodic stream, scored retrieval over recency/importance/relevance, and scheduled model-written consolidation — and it did so in a form simple enough to reason about. MemGPT asked "who manages the window?"; Generative Agents asked "what makes a stream into a self?" Production systems (§5) are, architecturally, answers that combine both questions under cost and safety constraints neither paper had to meet.

## 5. Production patterns: what shipped systems actually do

Research architectures meet production under three pressures the papers did not face: the user did not consent to be an experiment, the memory store is a privacy liability, and the extraction pipeline must run at consumer scale and cost. This section describes behaviour-level patterns from public documentation — what the systems are documented to do, not how their internals are rumoured to work. The reference product is ChatGPT memory (OpenAI Help Center documentation, accessed 2026-11-15), with Mem0 as the open, published-architecture counterpoint.

### 5.1 The saved-memories store: explicit items, separate from history

The first production pattern, shipped by OpenAI from 2024 and retained as the "legacy" experience in the current documentation, has three separable stores that users routinely conflate and the documentation is careful to distinguish:

- **Saved memories** — discrete, short statements ("details you have explicitly asked ChatGPT to remember, or that it saves as useful context"). They are stored *separately from chat history*, are carried into future conversations as context, and persist until deleted. Deleting the chat a memory came from does **not** delete the memory; deleting the memory does not edit the chat. Full removal requires both — a documented behaviour that surprises users and that any honest design must surface, not hide.
- **Reference chat history** — a looser mechanism by which past conversations themselves inform future answers, without a discrete item the user can point at. It can be toggled separately from saved memories (with the documented asymmetry that turning off saved-memory referencing also turns off chat-history referencing, but not vice versa).
- **Custom instructions** — user-authored standing text, controlled word-for-word by the user. Not memory in this dossier's sense (no extraction, no editor), but the control case that shows what memory is *not*: memory is precisely the part the system writes itself.

Controls documented at behaviour level: memory on/off globally; per-item view, delete, and clear-all in Settings → Personalization → Memory; Temporary Chat as a session that neither uses nor updates memory; and a retention note that deleted saved memories may be kept in logs for up to 30 days for safety and debugging. That last line is worth pausing on: *deletion in the product sense means "no longer used for personalisation," with a bounded back-end retention the documentation discloses.* An honest local system can do strictly better — deletion that is actually deletion — and should say so as a feature (§7).

### 5.2 Profile extraction and the move to automatic management

The second pattern is the *editorial* evolution OpenAI's own documentation narrates, and it is the most instructive production honesty story available in public:

1. **Manual era.** Saved memories accumulated as a user-managed list. The documentation's retrospective verdict, in substance: the list *went stale and contradicted itself*, and keeping it current relied on users manually managing updates — which, at scale, they did not do.
2. **Automatic management era.** The system began managing saved memories itself: updating, combining, prioritising, and backgrounding less relevant items without waiting for the user.
3. **Summary era ("improved memory").** The current documented experience replaces (or offers alongside) the discrete list with a *continually updated broader summary* of relevant context — a memory summary the user can review, with a last-updated time, and with per-response source attribution (which memories / past chats / instructions influenced an answer) appearing in the product. The legacy discrete list remains selectable for users who prefer inspectable items over a rolling summary.

Read architecturally, this is the §2.3 manage operation being staffed, in public, in three steps — and a trade being made at each step: *inspectability is exchanged for currency.* A discrete list rots but can be audited line by line. A rolling summary stays current but cannot be audited line by line, because the unit of memory is no longer a line. Which side of that trade a character-memory system should take is not close (§6.4): a persona's facts must remain discrete, attributable, and individually deletable, even at the cost of more editorial labour. Summaries are for preferences; anchors are for identity.

**Profile extraction** is the write-side mechanism underneath all three eras: after (or during) conversations, a pipeline decides which user statements are durable facts/preferences worth persisting, normalises them into short statements, and writes them to the store. Public documentation describes the *behaviour* (ChatGPT "may save those details as a memory without you needing to ask"; memory is "intended for high-level preferences and details" and should not be relied on for verbatim text) but not the extractor's model, prompts, thresholds, or deduplication logic. This dossier therefore treats extraction quality in closed products as **not publicly verifiable** — a boundary stated again in §8. What *is* verifiable is the failure surface users experience, §5.4, which follows from the architecture regardless of extractor quality.

### 5.3 The open counterpoint: Mem0, and the injection budget

Mem0 (Chhikara et al., "Mem0: Building Production-Ready AI Agents with Scalable Long-Term Memory," arXiv:2504.19413, 2025, ECAI 2025) is the most useful open production pattern because its paper describes the full loop: an *extraction* phase that distils salient facts from a conversation, a *consolidation/update* phase that compares new facts against retrieved existing ones and applies add / update / delete / no-op decisions, and a *retrieval* phase that returns a bounded set of memories for injection. A graph variant stores relations between entities alongside the flat facts. On the LoCoMo benchmark (§6.5) the paper reports its base system at 66.9% (LLM-judged) against a full-context baseline at 72.9% — *lower* accuracy, bought with ~91% lower p95 latency and >90% token savings (figures as reported in the paper, from the authors' own runs; treat cross-system orderings from a vendor's paper as one vendor's measurement, §6.5). Later platform figures published by Mem0 for a revised algorithm (LoCoMo ~92.5, LongMemEval ~94.4 at ~6.9K tokens per query) are **vendor self-reports for a managed platform including proprietary optimisations, not peer-reviewed results**, and this dossier does not rely on them beyond noting that the gap between the 2025 paper numbers and the 2026 platform numbers is itself a lesson in benchmark non-comparability.

The transferable design content of Mem0 is not its scores. It is:

- **Memory as middleware.** Mem0 is a *layer beside* the agent, not an agent runtime (Letta) and not a chat product feature (ChatGPT). The host application calls extract / search / add explicitly. That boundary — memory as a service with an API — is the boundary §7 recommends for the Ollama build.
- **An explicit update decision.** Whatever its accuracy, the consolidation phase *names* the four outcomes for a new fact against an old store: add, update, delete, no-op. That is the minimal honest vocabulary for supersession (§6.2). A store whose write path has only "add" has opted out of honesty by construction.
- **A bounded injection.** Retrieved memories enter the prompt as a bounded block (thousands, not hundreds of thousands, of tokens). 

That last point connects directly to this corpus's Aesir work: **HS-7's stable-order budgeted injection** — the Aesir-side discipline of injecting a fixed, stably ordered, token-budgeted set of resident materials into context — is the *same shape at a different layer*. HS-7 governs what resident context the engine assembles; a memory service governs what persistent facts the client assembles. Both exist because unbounded, unstably ordered injection destroys the two things a character workload needs: prefix-cache reuse (order changes invalidate the cached prefix — see the Ollama dossier §4.4 in this corpus) and reproducibility (the same question must meet the same memories, or behaviour drifts for reasons no one can reconstruct). The rule that transfers across layers: **memory injection must be budgeted, stably ordered, and logged — the set injected on a turn is part of that turn's provenance.** If you cannot list what was injected, you cannot debug what was answered.

### 5.4 Failure modes users actually report

Collected from the documented behaviours above and the benchmark evidence in §6.5, the production failure catalogue — stated as failure *classes*, each traceable to a §2.3 operation:

1. **Stale facts resurfacing (manage failure).** A superseded value (old address, former employer, abandoned preference) is served as current because the old record was never invalidated and retrieval ranked it first. The single most reported class, and the one OpenAI's automatic-management redesign explicitly cites as its motivation.
2. **Memories the user never approved (write failure).** An extraction fires on a hypothetical, a joke, a quoted third party, or a one-off ("help me write a story about a vegetarian chef" → "user is vegetarian"). Because extraction is automatic and the write is silent, the user discovers the memory only when it distorts a later answer — if they discover it at all. Approval-free writing is the price of zero-effort memory; visible writing (§6.4) is how a local system declines to pay it in the same coin.
3. **Qualifier loss (write failure).** "Thinking of moving to Berlin" stored as "lives in Berlin"; "allergic to peanuts, maybe" stored as a firm allergy — or the reverse, a firm fact hedged into uselessness. Extraction compresses; compression drops modality.
4. **Entity conflation (write/manage failure).** Facts about two people with similar names, or about the user and a character the user role-plays, merge into one profile. For character-driven workloads this is the catastrophic case: the persona's facts and the user's facts cross-contaminating each other's stores.
5. **Deletion that does not delete (governance failure).** The chat is deleted but the memory persists (documented ChatGPT behaviour, §5.1); or the memory is deleted but derived summaries retain its content; or back-end retention outlives the user's expectation. Each is defensible in isolation; together they teach users that "forget" is a fiction — the fastest way to destroy trust in a memory system.
6. **Summary drift (manage failure, summary-era systems).** Each re-summarisation slightly rewords the profile; over many cycles the summary asserts things no single conversation ever said — reflection fabrication (§4.4) at production scale, with no citations to check.
7. **Injection surprise (read failure).** A memory from an unrelated context fires in a sensitive one (a health fact surfacing in a work draft) because relevance is topical similarity, not appropriateness. No major public system documents an appropriateness gate on retrieval; the absence is itself a finding.

### 5.5 What production teaches the research designs

Production did not refute MemGPT or Generative Agents; it *repriced* them. Self-editing by the answering model (Letta) is powerful but spends the user's turn on housekeeping, so production moved editing into background pipelines and sleep-time passes. Reflection (Generative Agents) works but fabricates, so production kept the consolidation and added — unevenly — user-visible stores and source attribution as the compensating control. Scored retrieval survived everywhere, because nothing cheaper ranks as well. And the discrete, inspectable memory list — the least glamorous artefact in this whole dossier — turned out to be the trust mechanism users actually use, which is why its replacement by an opaque summary is the production trend this dossier most cautions against for our own builds (§6.4, §7).

## 6. Honesty & supersession — how memory stays true

*This is the section Volmarr's commission turns on. It separates, explicitly, what is **published practice** (a named system or paper does it, cited) from **engineering synthesis** (this dossier's recommendation, labelled as such). Nothing in the synthesis is presented as industry standard; where the literature is silent, the synthesis says what we would build and why.*

### 6.1 The problem, stated exactly

A fact in a user's life is not a constant; it is a function of time. "Lives in X," "works at Y," "prefers Z," "is called W" — each has a validity interval, a source, and a successor. A memory store that records the *statement* without the *interval, source, and succession rule* has not stored the fact; it has stored a sentence that was once uttered near the fact. Supersession is the operation that keeps the store's *current view* aligned with the latest truth while preserving the history that explains how it got there. Without it, §1's theorem applies:

> **Append-only + retrieval ⇒ eventual contradiction.** *Argument:* let any slot (address, employer, preference) change value at least once. Append-only writing stores both values. Retrieval ranks by similarity/recency/importance — none of which is a truth predicate — so for some future query, the older value ranks in the injected set, possibly alone (if the newer statement was phrased dissimilarly), possibly beside its successor (inviting the model to average, pick arbitrarily, or assert both). As the number of changed slots and the store's age grow, the probability that a given turn is contaminated approaches certainty. No embedding model, reranker, or larger injection budget fixes this, because the defect is in the store's semantics, not the ranking. The only fixes are at write/manage time: supersede, invalidate, or version — §6.2.

LongMemEval (§6.5) operationalises exactly this as its *knowledge-update* question type, and its headline result — strong systems dropping ~30% on sustained-interaction memory versus oracle-context reading — is the measured cost of getting extraction, update, and retrieval jointly right being hard even for well-resourced systems.

### 6.2 Published practice: the supersession mechanisms that exist

Four mechanisms appear in the verified literature and documentation. They are not equivalent; they make different promises.

**(a) Model-decided update operations (Mem0 pattern — published).** At consolidation time, a model compares each new extracted fact against retrieved neighbours and chooses add / update / delete / no-op (§5.3). *Promise:* the current view usually wins. *Limits:* the decision is a model judgement with no transactional guarantee; a missed comparison (the old fact was not among the retrieved neighbours) leaves both alive; the deleted/updated history is not, in the base design, a queryable audit trail. This is supersession as *housekeeping*, not as *semantics*.

**(b) In-place self-edit (Letta pattern — published).** The agent replaces the stale substring inside a bounded core block (§3.3). *Promise:* for anchor-class facts, there is literally one place the fact lives in context, and editing it edits every future turn. The block bound forces the edit to be considered. *Limits:* archival/recall copies are not automatically reconciled with the block edit — the same fact can be current in core and stale in archival, and a later archival search can re-import the stale version (a *resurrection* path §6.3 names). Versioned-file memory (Letta's git-backed line) mitigates audit, not resurrection.

**(c) Bi-temporal invalidation (Zep / Graphiti pattern — published).** Rasmussen et al., "Zep: A Temporal Knowledge Graph Architecture for Agent Memory" (arXiv:2501.13956, 2025). Facts are edges between entity nodes in a temporal knowledge graph built by Graphiti. Each edge carries *two* timelines: **valid time** (when the fact was true in the world: `valid_at` → `invalid_at`) and **transaction time** (when the system learned it and when it stopped believing it). Raw inputs are preserved as *episodes*, and every derived edge names its source episodes. When new information contradicts an existing edge, the system does **not** delete it: it closes the old edge's validity (`invalid_at` set to the new fact's start) and inserts the new edge. *Promise:* the graph can answer both "what is true now?" and "what was true in March, and what did we believe in March?" — current view and history are both first-class, and invalidation-not-deletion makes supersession *non-destructive and auditable*. The paper reports 94.8% vs MemGPT's 93.4% on DMR and LongMemEval gains with far smaller injected context than full-history baselines (authors' runs; §6.5 hygiene applies). *Limits:* extraction into entities/edges is still model work with model error; the machinery (a graph database, entity resolution, edge extraction per episode) is the heaviest in this dossier; and bi-temporality answers "when was it true" beautifully while leaving "should the user have approved this write" untouched.

**(d) Automatic summary management (ChatGPT pattern — published behaviour).** The rolling summary is rewritten by the system as context changes (§5.2). *Promise:* no user labour; staleness is attacked continuously. *Limits:* the summary is not versioned for the user, individual supersessions are not attributable, and drift (§5.4.6) is uncheckable because prior versions and source episodes are not exposed. Supersession exists, but it is *unwitnessed*.

**Comparison, in one line each:** Mem0 supersedes by *decision*, Letta by *edit*, Graphiti by *semantics*, ChatGPT by *rewrite*. Only Graphiti's version makes the superseded fact remain queryable *as* superseded — which is why, of the four, it is the only one that fully satisfies the standard Volmarr's own campaign already states for memory work in the field map (A5): *never silently drop; superseded/absorbed states* are first-class, preserved states — not deletions wearing a friendlier name.

### 6.3 Contradiction detection, resurrection, and abstention

**Contradiction detection is retrieval-shaped, and that is its weakness.** Every published pipeline detects a contradiction by first *retrieving* candidate conflicting records (Mem0's neighbour comparison; Graphiti's related-edge check) and then judging the pair. If retrieval misses the conflicting record — different wording, different entity spelling, fact stored as summary prose rather than an item — no judgement ever runs, and both facts live. *[Synthesis:]* a robust store therefore cannot rely on similarity search alone for conflict detection. Slot-typed facts (a fact *about* an entity, *in* a named slot: residence, employer, preferred-name) can be checked *by key*, exhaustively and cheaply, at write time: a new residence value for a known entity *must* meet the old residence value, whatever their embeddings say. Free-text facts keep the similarity path; slotted facts get a guarantee. Most real-world staleness lives in a small set of slots — which is good news: the guarantee is affordable exactly where it matters.

**Resurrection is the under-discussed failure.** Even with correct supersession in the semantic store, stale copies survive in: the episodic log (correctly — episodes are history), old summaries not yet rewritten, archival inserts made before the correction, and the model's own paraphrases in later episodes ("as a Berlin resident, you…" — an episode that now *re-evidences* the stale fact for a future extractor). *[Synthesis:]* the defence is directional provenance: derived facts may cite episodes, but an extractor must weight *explicit user statements about the present* above *incidental presuppositions in old assistant prose*, and a superseded fact's tombstone (§6.4) must be consulted at *read* time as a filter, not only at write time as a hope. No system surveyed in this dossier documents a read-time tombstone filter; we flag that as an open gap, not a solved problem.

**Abstention is a memory virtue, and it is benchmarked.** LongMemEval includes abstention questions — the answer is *not in the history*, and the correct behaviour is to say so. A memory system that always retrieves *something* and always answers fluently will hallucinate precisely where its store is empty. *[Published practice:]* the benchmark treats abstention as a first-class ability alongside extraction and update. *[Synthesis:]* injection should carry an explicit "no relevant memory found" state into the prompt, distinct from an empty injection, so the answering model can distinguish "we know nothing about this" from "memory was not consulted." Conflating the two is how empty stores produce confident inventions.

### 6.4 The honest store: versioned facts, tombstones, provenance, user visibility

*[This subsection is engineering synthesis, assembled from the published mechanisms above and from Volmarr's standing laws for his own systems. It is labelled synthesis throughout and claims no external authority.]*

A memory store fit for a persona that must not be lost and facts that must not rot needs, at minimum:

1. **Versioned facts, not mutable rows.** Each fact is an immutable record: `(subject, slot-or-text, value, valid_from, valid_to, recorded_at, superseded_by, source_episode_id, writer, confidence)`. "Update" means: close the old version's `valid_to`, insert the new version pointing back at it. This is Graphiti's bi-temporal discipline (published, §6.2c) restated as a storage rule any backend — SQLite included — can implement. Current-view queries filter `valid_to IS NULL`; history queries do not. Nothing is ever overwritten, so every answer the system ever gave can, in principle, be explained.
2. **Tombstones for deletion.** A user deletion writes a tombstone (the fact's id, deletion time, deleter) and removes the value from all serving views, rather than pretending the record never existed — *except* that the tombstone itself must not retain the deleted content, and a user-demanded hard purge must be able to destroy tombstone and provenance together. The distinction matters: tombstones exist to stop resurrection (§6.3) — a deleted fact whose episode still lives will be re-extracted next consolidation unless something remembers that it was *deliberately forgotten*. Forgetting, in an honest system, is itself a remembered decision with the content removed.
3. **Provenance on every record.** Source episode, writer (user-stated / extractor / reflection / sleep-time pass), and the exact injected set per turn (§5.3). A fact that cannot name its source is downgraded: retrievable, but flagged unverified, and never promoted into an anchor block.
4. **User-visible memory as a right, not a settings page.** Inspect (list every current fact, with source and date), edit (correct the value — which is a supersession, witnessed), delete (tombstone, §6.4.2), and export (the whole store in a portable, plain format the user owns). ChatGPT's documented controls (view/delete/clear, §5.1) are the floor, not the ceiling: they expose the *current view* only, with no history, no provenance, and no per-fact source. A local-first system has no excuse for doing less than the full four operations — the data is on the user's disk, under the user's law.
5. **Anchor separation.** Persona/identity facts live in a distinct, bounded, always-injected store (the Letta core-block pattern, §3.3) with stricter write rules than the general store: writes require either an explicit user statement or user approval; extractors and reflections may *propose* anchor changes but may not commit them silently. This is Volmarr's character-anchor law expressed as a write policy: *what must never be lost must never be silently rewritten either.* Loss and corruption are the same failure wearing two coats; the anchor defends against both by being small, pinned, witnessed, and versioned.
6. **Approval tiers for writes.** *[Synthesis, extending §5.4.2:]* user-stated "remember this" → commit immediately. Extractor-inferred durable fact → commit to the general store, visibly, in a reviewable queue. Extractor-inferred *sensitive or identity* fact → propose only. Reflection product → commit as a *derived* record, typed as such, citing its evidence, never silently promoted to user-stated standing. The tiers cost some zero-effort magic; they buy the property that the store's contents are never a surprise to the person the store is about.

### 6.5 Benchmarks: what is verified, what is claimed, what cannot be trusted as quoted

Memory correctness finally has public benchmarks. Two are verified in this dossier against their papers; the surrounding vendor numbers require active distrust.

**LoCoMo** — Maharana et al., "Evaluating Very Long-Term Conversational Memory of LLM Agents" (ACL 2024; arXiv:2402.17753). Ten very long, machine-generated, persona-grounded conversations in the public release (~300 turns and ~9K tokens on average per conversation in the paper's corpus description, up to 35 sessions), with 1,986 QA pairs in the public set, of which the 1,540 non-adversarial questions (single-hop, multi-hop, temporal, open-domain) are the conventionally reported subset; the fifth category is adversarial/abstention. The paper's own finding stands: long-context and RAG systems improved over base models yet lagged humans substantially, worst on temporal reasoning. *Caveats, verified from secondary audits and stated plainly:* the conversations fit inside a modern large context window, so LoCoMo no longer cleanly separates "has a memory system" from "has a big window"; independent auditing has reported a non-trivial rate of answer-key errors (~6% in one 2026 audit — a single-team, non-peer-reviewed figure, quoted here as a warning, not a constant); and scores are LLM-judge-dependent, so two vendors' LoCoMo numbers from different judges, subsets, and token budgets are not a leaderboard. Mem0's paper-run 66.9% and later platform claims above 90% are both "LoCoMo scores" and are not in contradiction — they are different pipelines wearing one name.

**LongMemEval** — Wu et al., "LongMemEval: Benchmarking Chat Assistants on Long-Term Interactive Memory" (ICLR 2025; arXiv:2410.10813). 500 questions, each embedded in its own long, scalable multi-session chat history (the S variant: ~115K tokens, ~40–60 sessions per question), testing five abilities: information extraction, multi-session reasoning, temporal reasoning, **knowledge updates**, and **abstention** (30 of the 500 are abstention items). Headline finding, from the paper: commercial assistants and long-context models drop ~30% in accuracy when memory must be sustained across interactions versus reading the evidence directly. For this dossier, LongMemEval is the more important benchmark, because it is the only widely used one that *directly scores supersession and abstention* — the honesty operations of §6.2–§6.3 — rather than recall alone. Its per-ability breakdown, not its headline number, is the honest way to read any system evaluated on it.

**Deep Memory Retrieval (DMR)** — the MemGPT team's benchmark, used by both the MemGPT paper (GPT-4: 92.5% with MemGPT) and the Zep paper (94.8% vs 93.4%). Verified as *existing and as reported by those papers*; not an independent community standard, and small differences on it (94.8 vs 93.4) should be read as "comparable under the authors' pipelines," not as a ranking of the underlying ideas.

**Explicitly not relied upon:** vendor blog leaderboards quoting LoCoMo/LongMemEval scores without judge, subset, and token-budget disclosure (several were encountered during research, with mutually inconsistent figures for the same systems); the BEAM benchmark (encountered only via secondary/vendor summaries during this research pass — its arXiv record was **not independently verified** for this dossier, so no BEAM claim is made); and any "state of AI agent memory" survey-of-vendors published by a memory vendor, which is marketing literature even when its bibliography is real. The rule this dossier applied, and recommends: *a memory score is a claim until it names its answer model, its judge, its question subset, and its injected-token budget.*

### 6.6 Why "append-only + retrieval" fails — the section in one paragraph

Because truth has a time dimension and similarity does not. An append-only store treats "lived in X (2023)" and "lives in Y (2026)" as two equally real sentences; a retriever treats them as two equally eligible passages; an answering model, handed both or handed the wrong one, has no principled way to know that one *replaced* the other — replacement was never recorded anywhere. Every component did its job. The system lied anyway. That is why honesty in agent memory is a *storage-semantics* property (versioning, invalidation, tombstones, provenance — §6.4), purchased at write and manage time, and why no improvement to embeddings, rerankers, or window size can substitute for it. The editor is the product. Everything else is plumbing.

## 7. Applicability

### 7.1 The Ollama build: a boundary argument — runner vs client vs memory service

*[Synthesis, applying §§2–6 to this corpus's Ollama fork work.]*

The Ollama dossier in this corpus establishes that stock Ollama is deliberately stateless: no server-side conversation object, history resent by the client every turn, continuity simulated by prefix reuse inside a slot. The memory question for the fork is therefore not "how does the runner remember?" but "**which layer owns the store?**" Three candidate owners, argued in turn:

**Not the runner.** The runner (llama-server / MLX subprocess in the current Ollama design) owns tensors: weights, KV, sampling. Its lifetime is a keep-alive timer; its identity includes load-time options, so it is unloaded and respawned precisely when configuration changes. Putting the persistent store inside it would couple the most durable artefact in the system (the user's memory, measured in years) to the most ephemeral process in the system (a runner, measured in minutes), and would fork the store per model — the same user chatting with two models would grow two divergent memories. The runner's correct memory responsibilities are exactly the in-context half: KV management, prefix reuse, honest overflow behaviour (loud failure or reported truncation, per the Ollama dossier's §9 recommendations). *The runner is the cache. Caches do not own databases.*

**Not (only) the client.** A client-owned store (the chat app keeps a local file, injects excerpts) is the right *prototype* — it is how every Ollama front-end that "has memory" today actually works — and the wrong *end state* for Volmarr's use: multiple clients (desktop app, phone, Voxta-style front-ends) would each hold a partial store; extraction quality would vary per client; and the store's format would be whatever one app's author chose, unportable and unauditable across tools. Client-owned memory also repeats the ChatGPT deletion trap in miniature: delete the conversation in the app, keep the memory in the file, notice neither.

**A memory service beside the runner — the recommended boundary.** A small, local, model-agnostic service, owning exactly the §2.3 loop:

- **Store:** versioned facts + episodic log + anchor blocks, in a plain local database (SQLite is sufficient at personal scale), implementing §6.4 semantics: bi-temporal versioning, tombstones, provenance, inspect/edit/delete/export as API operations, not afterthoughts.
- **Write path:** an extraction step that runs *after* a turn (or in a sleep-time pass, §3.4), using whatever model is resident — with the honesty caveat that a small local extractor is a weaker editor than a frontier model, so approval tiers (§6.4.6) matter *more* locally, not less. User-stated "remember this" bypasses extraction entirely and commits verbatim.
- **Read path:** a retrieval call the client makes before each turn, returning a *budgeted, stably ordered, logged* injection set (§5.3) — anchor blocks first (always, pinned, in a fixed position for prefix-cache friendliness), then current-view semantic facts, then episodic excerpts — with an explicit empty state (§6.3).
- **Interface:** a narrow local HTTP API beside Ollama's own (extract / search / add / supersede / forget / export), so any client — the fork's UI, Rúnmál, a script — shares one store, one editor policy, and one audit trail. This is Mem0's middleware boundary (§5.3) with Graphiti's storage semantics (§6.2c) and Letta's anchor blocks (§3.3), assembled at personal scale. None of the three source systems is adopted wholesale; each contributes the part it proved.

Two Ollama-specific interactions the fork must handle, both visible from this corpus's own findings: (1) *injection stability vs prefix reuse* — the injected set must be placed so that its stable prefix (anchor + standing facts) preserves the runner's per-slot prefix reuse across turns; volatile retrieved excerpts belong after the stable prefix, never interleaved into it. (2) *Window budgeting is joint* — on a 4,096-token default window (the sub-24 GiB tier), a generous memory injection and a long conversation cannot both fit; the memory service's budget and the runner's `num_ctx` must be set with knowledge of each other, or layer-1/layer-2 truncation (Ollama dossier §4.3) will silently eat whichever the template places worst — historically, the persona. Budgeted injection is not an optimisation here; on small-window local hardware it is the difference between memory that works and memory that evicts the character it was built to protect.

### 7.2 Aesir: the in-context half is built; the other half is a store, an editor, and a contract

Aesir's session and residency work — resident character context held in an unpushable anchor, prefix memory, sessions that persist their engine state — is, in this dossier's taxonomy, an unusually strong implementation of the *working-memory* tier plus the *anchor* discipline: what must be in context is pinned, ordered, and not reprocessed. That is the in-context half of agent memory, done at engine level, and it is the half most systems do badly.

The other half — the half Aesir does not yet have, stated as requirements rather than as a design — is:

1. **A persistent store outside the engine process**, with §6.4 semantics (versioned, tombstoned, provenanced), owned by the serving layer rather than by any single session, so that a character's memory survives engine restarts, model swaps, and quantisation changes. Engine residency must remain a *cache of* that store's current view, never the store itself — the same cache/database separation as §7.1, one level down.
2. **An editor with Aesir-appropriate staffing.** Aesir serves interactively on constrained hardware; inline self-editing (Letta pattern) would spend scarce decode budget on housekeeping. The fitting pattern is the sleep-time one (§3.4): extraction and consolidation as background work between sessions, against the resident model or a small dedicated pass, writing *proposals* into the store under the approval tiers of §6.4.6 — with anchor-class changes never auto-committed.
3. **A contract between the halves.** The engine's HS-7-style stable-order budgeted injection is the natural seam: the store's read path *is* an HS-7 supplier. What the contract must add to HS-7's existing discipline is *provenance carriage*: each injected item arrives with its fact-id and version, and the session log records the injected set, so that any later "why did she say that?" can be answered from records rather than vibes. Aesir's honesty story, if it adopts this, becomes end-to-end: the engine can prove what was in context, and the store can prove why it was selected and whether it was still true.

What Aesir should *not* do: grow memory features inside the inference engine itself (per §7.1's runner argument, which applies to Aesir exactly as to Ollama's runner), or adopt a rolling-summary profile as a character's long-term self-knowledge (§5.2's inspectability trade — a character's facts must stay discrete). Aesir's compression-school work — teaching the engine to write the packed forms it reads — has a memory-layer analogue worth one sentence: a store that can *compact* its episodic log into semantic facts, lossily but with the episodes retained, is doing consolidation; a store that compacts *and discards* the episodes is doing summarisation-as-forgetting, and the difference is whether correction remains possible (§2.1).

### 7.3 MimirAlloc: one honest line

No real connection was found: MimirAlloc is a general-purpose allocator whose proven results concern allocation behaviour, not agent-memory semantics, and nothing in the verified agent-memory literature depends on allocator choice at the level this dossier operates — the honest line is that agent memory's problems are editorial, not allocational, and MimirAlloc enters only as the substrate any local memory service's database will unremarkably run on.
