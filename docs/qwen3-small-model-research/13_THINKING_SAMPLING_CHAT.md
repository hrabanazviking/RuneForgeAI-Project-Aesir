# 13 - Thinking Mode, Sampling, Chat Templates, and Token Discipline

**Research snapshot:** 2026-11-02

Qwen3's unified thinking/non-thinking behavior is one of the family features Aesir can exploit most directly. Correct support requires more than displaying `<think>` tags: template rendering, history policy, sampling, output separation, and task routing all matter.

---

# 1. Two modes in one model

Qwen3 post-trained models can operate in:

- **thinking mode** for deeper reasoning;
- **non-thinking mode** for faster ordinary responses.

Official Transformers templates expose `enable_thinking=True/False`. When thinking is enabled, user/system text can also use `/think` and `/no_think` as soft switches.

Aesir should expose this semantically rather than requiring applications to manually modify text.

Suggested request field:

```text
reasoning_mode = auto | thinking | non_thinking
```

---

# 2. Official sampler recommendations

Qwen's model-card guidance:

## Thinking

```text
temperature = 0.6
top_p       = 0.95
top_k       = 20
min_p       = 0
```

Qwen explicitly advises against greedy decoding in thinking mode because it can degrade performance and cause endless repetition.

## Non-thinking

```text
temperature = 0.7
top_p       = 0.8
top_k       = 20
min_p       = 0
```

These are upstream defaults, not immutable Aesir laws. Task-specific structured generation may need different settings, but deviations should be deliberate.

---

# 3. Repetition handling

Qwen notes that `presence_penalty` can reduce endless repetition and gives 1.5 as a useful value in guidance for problematic quantized behavior.

Aesir policy should be adaptive:

- default near zero unless repetition appears;
- raise penalty for detected loops;
- cap it because high values can cause language mixing or quality loss;
- record sampler state in reproducibility logs.

Potential loop detector:

- repeated n-gram ratio;
- near-identical sentence recurrence;
- repeated special/control token sequence.

---

# 4. Chat-template correctness

Aesir's Qwen3 support must render exact tokens for:

- system message;
- user message;
- assistant message;
- multi-turn history;
- thinking enabled/disabled;
- tool definitions;
- tool call;
- tool result;
- continuation.

Do not infer prompt format from visible text alone.

Regression files should store exact token ID arrays generated by a pinned official/reference tokenizer revision.

---

# 5. BOS semantics

HF configs expose a `bos_token_id`, but Qwen's chat protocol is not equivalent to 'prepend a conventional BOS token to every prompt.' Aesir's own model-wave work already established the correct no-BOS family behavior for Qwen3 execution.

Rule:

> The chat template/tokenizer owns prompt control-token placement. Loader metadata alone does not authorize injecting an extra token.

---

# 6. Thinking-content separation

Applications need two logical outputs:

```text
reasoning_content
final_content
```

Even if a low-level backend emits one textual stream, Aesir's protocol layer can parse the Qwen3 markers and expose the pieces separately.

Benefits:

- UIs can hide/show reasoning according to application design;
- agents can avoid feeding old reasoning back into history;
- metrics can count reasoning tokens separately;
- tool parsing can operate only on the correct output channel.

---

# 7. History policy

Qwen's best practices recommend not preserving prior thinking content in multi-turn history, retaining final answers instead.

Aesir/application strategy:

```text
store user turns
store final assistant answers
store structured tool calls/results as needed
discard previous hidden reasoning from next prompt
```

Benefits:

- fewer input tokens;
- smaller KV cache;
- less accidental reasoning contamination;
- lower prefill cost.

---

# 8. Thinking budget

Aesir should add a runtime reasoning budget even if the model itself does not enforce a perfect hard budget internally.

Possible controls:

```text
max_reasoning_tokens
max_total_output_tokens
time budget
```

If a model exceeds budget, policy options include:

- request final answer now through template/application protocol;
- stop and return partial result only if application permits;
- escalate model size on retry;
- switch task strategy.

Do not silently cut in the middle of a tool-call payload.

---

# 9. Auto reasoning router

A small classifier can choose whether a request deserves thinking.

Signals that favor thinking:

- math;
- multi-step coding/debugging;
- planning dependencies;
- contradiction resolution;
- complex tool orchestration;
- explicit user request for reasoning.

Signals favoring non-thinking:

- rewrite;
- translation;
- extraction;
- simple classification;
- casual chat;
- known single-tool lookup;
- formatting.

The router itself can be Qwen3-0.6B or deterministic application logic.

---

# 10. Model-size escalation versus more thinking

Aesir should compare two ways of spending compute:

```text
small model + long reasoning
larger model + shorter/non-thinking response
```

Sometimes 1.7B thinking beats 4B non-thinking. Sometimes 8B non-thinking beats a tiny model wandering for thousands of tokens.

A routing benchmark should optimize actual task success per latency/energy, not ideological preference for 'reasoning.'

---

# 11. Structured generation

For JSON/extraction/tool arguments:

- non-thinking often reduces extraneous prose;
- temperature may be lower than chat defaults;
- grammar/schema constraints are useful if Aesir supports them;
- greedy may still be appropriate for some non-thinking deterministic tasks, but thinking-mode warning remains important;
- validation and retry are mandatory for agents.

Aesir should keep sampler presets by workload:

```text
chat_thinking
chat_fast
json_strict
creative
code
```

Presets remain visible and overridable.

---

# 12. Token accounting

For every generation report:

```text
input_tokens
reasoning_tokens
final_output_tokens
cached_prefix_tokens
new_prefill_tokens
```

This helps explain why a 'short answer' may still be slow when thinking mode produced a long internal trajectory.

---

# 13. Streaming

Thinking-aware streaming must correctly handle state transitions:

```text
start reasoning
reasoning token stream
end reasoning
final answer token stream
```

Do not expose partial tool-call JSON to execution before the call is complete and validated.

A client may display reasoning or suppress it while still receiving final tokens promptly.

---

# 14. Stop conditions

Use token-aware stop conditions from the actual template/protocol. Avoid plain substring checks against decoded text when a special token exists.

Reasons:

- byte/BPE boundary ambiguity;
- stop text may appear inside reasoning or quoted content;
- decoded text normalization can differ;
- tools require structured boundaries.

---

# 15. Benchmark matrix

For every size and quant, test:

```text
thinking official sampler
non-thinking official sampler
greedy reference trajectory (correctness only, not thinking quality default)
low-temp structured preset
```

Record:

- task score;
- output/reasoning token count;
- repetition rate;
- latency;
- tool-call validity;
- language-mixing events.
