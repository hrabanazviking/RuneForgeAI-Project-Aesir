## What the battery pins

The per-slice suites (A-100/A-102/A-103/A-104/A-105) assert
properties of their own decisions. This battery pins the
COMPLETE rendered decision for every standard case, so any
future decision change — device, backend, reason text,
measured estimate, fallback, totals, digest — fails loudly
until a numbers-backed slice re-pins it deliberately.

Six cases, all in the full tier via `run_all`:

| Case | Pins |
|---|---|
| `battery.planner_standard_fixtures` | All 12 A-100 standard fixtures: full `PlannerDecision.line()` (device, backend, reason, measured est, A-099 fallback), on top of the A-100 device/backend expectations |
| `battery.planner_context_variants` | The same 12 fixtures under the GPU-absent registry (spillover/FIT/crossover decisions) and under the unproven context (no NPU placement at all — A-017 honesty gate) |
| `battery.spillover_standard_plans` | 6 A-102 plans (all-fit, capacity spill, atomic MEM-003 refusal, spill-cap refusal, assist unproven, assist proven): full placement log text + FNV-1a digest + refusal reason |
| `battery.replan_standard_scenarios` | A-103: the 6-step mixed generation plan; GPU loss (moved=2, audit + new decision lines), NPU loss (moved=2, all survivors on GPU/Vulkan), CPU loss (FAILED_CLOSED, reason pinned), seeded drill 4242 (tokens match control exactly, tokens + audit pinned) |
| `battery.big_model_standard_splits` | A-104: 6 named Llama-3.1-8B splits (half, zero, embed-only, full, small-pool, exact-edge) + the 6-rung budget ladder, full `line()` accounting each |
| `battery.fairness_standard_scripts` | A-105: 5 demand scripts (equal, weighted 2:1, adversarial trickle, idle-then-return, single-model): `summary_line()` + log digest each |

## How the pins were made

Pins were generated by a probe
(`hidden_files/a107_probe_out.txt`, 123 pinned values) that
ran the banked decision code on the standard fake
registries (the A-100/A-103 pattern: Vulkan first-class,
HIP probe-only, A-095 proven context) — no live hardware
probing, no live memory figures, so the battery is a pure
function of the decision code and its embedded measured
tables. Every pin was reviewed against the per-slice
tests' asserted expectations before being written into the
battery (e.g. re-plan moved counts 2/2, drill tokens match
control, half split 16/16 with KV 268435456 per side,
equal-share Jain 1000).

One transcription error was caught by the battery itself
on its first run (unproven-context below-band pin carried
an estimate suffix the banked decision does not emit) and
corrected to the probed value; the battery then passed.

## Re-pinning rule (the acceptance teeth)

A red battery case means a placement decision changed.
Do not edit a pin to make it pass. Land the numbers-backed
slice that justifies the new decision, regenerate the
pins from the new code, review the diff pin by pin, and
file the numbers in that slice's ledger.
