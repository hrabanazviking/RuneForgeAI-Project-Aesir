## 2. Inspection — what a block-halves split is, and how it differs from J-043 (PROVEN from the tree)

| Piece | Shape, as filed in the code / record |
|---|---|
| **J-043 co-work (`core/cowork_passes.mojo`)** | Divides a prompt batch **by rows inside one matrix product**: side A computes rows [0, first_rows), side B the rest. Every output element is computed whole by exactly one side with the serial reduction order, so the sides are **independent** and the join is a **gather** of the two output blocks. What crosses: each side's input slice + a full replicated copy of the shared matrix out, its output rows back. Its survival rule (J-040's margin+separation on measured joined times, against both parents) and its accounting discipline (join stated, never dropped) are what this slice reuses. |
| **J-056 block-halves split (this slice)** | Divides the layer stack **by blocks**: GPU runs blocks [0, ⌈L/2⌉), CPU runs blocks [⌈L/2⌉, L). Block k+1 consumes block k's hidden state, so per token/chunk the halves are **sequentially dependent** — there is no row-style independence inside a chunk. The only concurrency the shape admits is **pipelining across chunks** (GPU starts chunk i+1's first half while CPU finishes chunk i's second half). What crosses is exactly one thing: the **hidden state at the split boundary, once per chunk** (chunk_width × hidden × elem bytes). No matrix is replicated; no output is gathered. KV never crosses — each side writes the KV of the blocks it owns, on its own side. |
| **The host prefill path (`aesir.mojo` `_run_generation` / `_forward_batch`, J-053 §2)** | The whole-CPU parent: chunked batched passes (cap 256) over the **full** stack per chunk; pure-prefill chunks return before the head. It has no block-range form: `forward_pass_batched` (`core/inference.mojo`) always runs every block — a CPU **second-half** executor does not exist (S3, §3). |
| **The CUDA sessions (`core/llama3_cuda.mojo`, `core/gemma4_cuda.mojo`)** | The whole-GPU parent (J-055: whole-layer at width 1 exists and is proven; block width is M1/M2/M5-gated). Both run the **full** stack per token; neither has a block-range form, and neither exposes a hidden-state download — their device→host traffic is the logits path only (S2/S3, §3). |
| **The spill partition (`core/dense_residency.mojo`, J-021)** | Front layers GPU-resident, tail on CPU, token-identity PROVEN on the Stheno file. Geometrically this **is** a block split — at an unequal fraction chosen by fit, executed in the proven width-1 sequential form. J-056's balanced halves are the same geometry proposed as a *speed* candidate at block width; §5 grades that proposal, and only that proposal. The spill's residency verdict is untouched by it. |

## 3. Missing pieces — what a block-halves split needs that does not exist

Bound to J-054's M-list where it gates, plus the three pieces this slice names:

- **M1 + M2 + M5 gate the GPU half at block width** (general-width quantized GEMM; batched layout/admission above width 4; chunk-level session loop), exactly as they gate J-054's block prefill and J-055's block whole-layer. At width 1 the GPU half needs no M item — the proven sessions' shape — but §6 shows width 1 is also the split's worst accounted shape (a boundary transfer per token). **M4** sets the block halves' launch floor; **M6** is the same build for the Gemma 4 session; **M3** (batched attention) gates neither half's placement (attention is already device-resident per row on the GPU side, host-batched per row on the CPU side) — it gates the long-context ceiling, as in J-055 §3. **M7** gates quoting any per-phase wall, hence §7 times from outside.
- **S1 — A cross-device pipeline loop (NEW, named here).** No loop in the tree overlaps one device's chunk i+1 with the other's chunk i: both CUDA sessions and the host chunk loop are strictly sequential per chunk. The split's only concurrency mechanism (§2) is therefore unbuilt, host-side, and is the piece §7's live leg actually measures.
- **S2 — A chunk-granularity device→host hidden-state transfer road (NEW, named here).** The tree's upload road (`core/cuda_upload.mojo`, 64 MiB synchronised staging) is host→device, at open. The sessions' device→host traffic is logits-sized. A synchronised download of a chunk's hidden block (width × hidden × 4 B — 4,194,304 B at width 256 on the 8B shape, §6) at the split boundary has no existing road; §4 prices its bytes and crossings, §7's leg builds or borrows it explicitly.
- **S3 — Partial-stack (block-range) executors (NEW, named here).** Neither side can run blocks [a, b) today: the host batched forward and both CUDA sessions run the full stack (§2). A split executor needs a first-half form (embedding + blocks [0, h), ending by exporting the hidden state) and a second-half form (importing a hidden state + blocks [h, L) + final norm/head) on each device it may land on. The head belongs to the second half, paid once per prompt under the host discipline (J-053) — the split does not change the head count.

**What is NOT missing:** the fit decision that decides whether the whole-GPU parent exists (J-055, built); the per-side weight residency and its open upload (J-021/J-031 roads); the accounting (§4); the survival discipline (J-043's, reused).

## 5. The survival rule (pre-registered, accounting form)

Stated in `core/split_prompt.mojo`'s header and here **before** the §6 shapes were run through it. No wall exists on this slice, and no exchange rate between bytes, crossings and MACs is invented to fake one — so the only honest accounted form of the roadmap's "kept only where it wins" is **dominance**:

> A split SURVIVES on accounting alone only if it dominates **both** parents: less-or-equal on every accounted axis (total MACs; weight-read bytes; synchronised crossings; join bytes) and strictly less on at least one, against **each** parent separately, parents taken at the same prompt and chunk width. A split dominated by either parent (parent ≤ on all axes, < on at least one) is **ACCOUNTED-AND-REJECTED**. Where the whole-GPU parent does not exist (`whole_gpu_fits` false, J-055), the rule grades **nothing**: the shape is recorded **PARENT-ABSENT** — the residency fallback's geometry, neither a win nor a rejection.

Two honesty clauses ride with the rule. (a) **The verdict grades accounting, not time.** Pipelining (S1) could in principle make a dominated-accounting split win in wall time — the bottleneck side carries roughly half the MACs — exactly as J-025's and J-027's byte verdicts left their latency cases NOT PROVEN. Reopening requires §7's measured walls under the J-040/J-043 margin+separation discipline (split's joined median beats each parent's by more than 10% of the split's median, with round separation, against each parent separately); an accounted argument alone never reopens it. (b) **The axes are the whole claim.** A later citation may not quote the bottleneck halving without the crossings and join figures beside it, nor quote this rejection as a wall measurement.

## 6. The accounting (exact arithmetic on stated inputs; no run, no wall)

Stated inputs: J-053 §5's filed figures — Llama 3 8B (32 layers, hidden 4,096, projection MACs 6,979,321,856/token, attention MACs 8,623,489,024 at 256 tokens); Gemma 4 E2B (35 layers, projection MACs 1,238,630,400/token, dense part only); Stheno's tensor-byte total 4,912,898,048 B (J-021 §3) for the parent-absent row. Hidden-state element bytes 4 (the sessions' f32 state). Per-side weight bytes are caller-stated directory figures; the synthetic rows state equal halves so the traffic comparison is legible, and the Stheno row states the floor half of its filed total — none of these is a measured per-half directory figure, and the verdict does not rest on the halves' ratio (the split's total weight traffic equals the parents' for *any* split of the same stack).

- **Why the MAC and traffic axes can never rescue a split on accounting:** both are *conservation* axes. A block split redistributes the same products and the same per-chunk stack re-reads between two devices; it creates no fewer of either. The only axes a split can ever move are the ones it worsens (crossings, join) and the one no accounting axis captures (concurrent wall time, §5 clause (a)). That is the structural reason the accounted verdict is a rejection at every width and every filed shape — not a tuned outcome.
- **The join, priced plainly:** at width 256 on the 8B shape the boundary carries 4,194,304 B per chunk — small beside the per-chunk weight re-reads it accompanies, and it is *not* the join bytes that dominate the split; it is the **3× crossings** and the sequential dependence itself (§2). A citation that blames the join bytes alone misreads this account.
