## 2. Inspection — the MoE prefill path as it is (PROVEN from the tree)

**The session.** `MoEStreamSession` (`core/moe_session.mojo`, read in full this slice) admits only arch `olmoe` (any other arch refused by name), holds its resident set through the `GGUFSeer` mmap, and serves routed experts only through `ExpertCache` (fsketch default) + `StreamReader` pread. Its **only** forward entry is `step(token)` (line 552): embed → 16 × `_layer_forward` → final norm → output projection → a full vocab-wide argmax scan, returning the greedy next token. **There is no pure-prefill form** — no `step_prefill`, no `need_logits` flag, no chunk loop — so a prompt of N tokens is N `step()` calls and the head is paid N times (J-053 F1, re-verified here from the code, not from J-053's prose). Per layer, `_layer_forward` runs host primitives only (`gemm_f16`, whose own docstring states it executes no CUDA): attention projections + full-width Q/K RMSNorm + NeoX RoPE + flash attention, then the FFN half — norm, router GEMM ([64 × 2048] F32), softmax, top-8 selection with **raw** (non-renormalised) probability weights (the J-022 B1 discipline), J-019 willneed advice for every chosen expert's slabs, then `_expert_ffn` per chosen expert (cache access; admitted misses read the three slabs from disk; bypassed experts compute from scratch and are discarded). The module docstring's J-031 paragraph stands unchanged: the session computes on the host; the GPU division is planned in `core/moe_gpu_plan.mojo`; nothing in the module may claim GPU execution until that leg lands.

**The division machinery (J-031, re-read this slice).** `core/moe_gpu_plan.mojo` provides `plan_moe_gpu_division` (resident first, then KV/activation/reserve allowances, remainder as a whole-expert device cache; CPU_ONLY stated in-plan when resident + allowances exceed the budget), `plan_moe_gpu_token_transfers` (exact per-token H2D/D2H bytes + synchronised crossings per division; disagreeing miss facts refused), and `moe_gpu_upload_chunks` (the existing 64 MiB synchronised staging bound: OLMoE resident → 5 chunks, body → 59 chunks). It is **decode-shaped**: its transfer account is per token, its FULL division refuses per-token expert traffic, and it has no chunk width, no pass plan, and no head account. ## 5. The survival rule (pre-registered)

Stated in `core/moe_gpu_prefill.mojo`'s header and here **before** the §6 shapes were run through it. The GPU chunk form **SURVIVES ACCOUNTING** for a stated division and prompt only if all hold: **(a)** the division places the resident set on the device (CPU_ONLY → **NOT_APPLICABLE**); **(b)** the division is not the resident-only split (**REJECTED_RESIDENT_ONLY**, carried from J-031); **(c)** the GPU form's expert upload bytes do not exceed the CPU form's streamed bytes for the same routing (**REJECTED_EXPERT_BYTES** otherwise — the cache division ties this axis by construction, the full division pays zero); **(d)** the head is paid exactly once; **(e)** the resident weight-read saving reaches the road's standing margin — `saving_bp ≥ 1000` (10%, the J-040/J-043 discipline) — else **HEAD_ONLY**: the head collapse stands, the chunk economy does not.

Two honesty clauses ride with the rule, as in J-057. (a) **The rule grades counts and bytes, never time.** No byte/MAC-to-time exchange rate is stated or implied anywhere in this slice; the one measured CPU wall in §6 is an anchor for scale, not a term in any verdict. Only §7's measured walls can promote an accounted survival into a speed claim — or overturn it. (b) **Per-division, per-shape verdicts stay put.** The FULL survival on the J-022 model is a statement about that model on that card; the cache division's operative class (models that outgrow the device, J-032's) is unmeasured here and its survival is an accounting grade on the J-022 shapes, not a claim about that class.
