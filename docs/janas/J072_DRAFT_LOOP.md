**The loop (pre-registered shape, following J-071 §3's host contract steps 1–6).** One round:

1. **Snapshot** the committed state: target KV length, context-token count, RNG state word (one UInt64, J-071 §2), and the proposer's own KV length where its shape carries one.
2. **Plan k** (`plan_round_k`): the requested depth is checked against the floor (1), the band (k+1 ≤ 16), and the proposer's cap — violations refuse. The KV-capacity bound then applies *before* proposing: the deepest fitting k is `capacity − kv_before − 1`; a deeper request is **shortened explicitly** — the plan records requested vs planned and the shortening flag, so the host proposes the planned depth and no pass is ever silently truncated. Where not even k=1 fits, the plan refuses: the host ends or waits; it does not speculate past the cache. (`plan_verify`'s capacity refusal remains the backstop.)
3. **Dispatch** the proposer by slot (`dispatch_proposer`): SLOT_HEAD takes the MTP head or the assistant model, SLOT_CROSS_MODEL the cross-model drafter, SLOT_CONVERSATION the conversation proposer; a kind filed under the wrong slot is refused, never re-filed.
4. **Verify in one pass**: the host runs one draft-check pass of width k+1 and records the target's greedy choice at every position; the round derives entirely through `plan_verify` — acceptance is the longest true prefix, emission is the prefix plus exactly one further **target** choice (correction or bonus), built from the target's list only.
5. **Roll back exactly**: the pass tentatively advanced k+1 rows; the round discards k − accepted, and the committed lengths are **asserted** against the snapshot — KV and context land at snapshot + accepted + 1, the proposer's own KV at snapshot + accepted (0 for a zero-accepted round: fully rolled back), and the **RNG word is asserted equal to the snapshot's** (a greedy round draws nothing; `plan_verify` already refuses a reported draw). A disagreement raises inside the loop rather than committing a state the account does not describe. Any refusal from `plan_verify` propagates **before** any state is touched, so a refused round leaves the state exactly at its snapshot (tested, §5).
6. **Emit and file**: the account's emitted tokens are appended to the loop state's emission, and the round's account is the evidence J-073/J-075 read.

**Adaptive bounds (stated, per the roadmap text).** k lives in [1, cap]: cap 15 for model proposers (band-bound), 8 for the conversation proposer (J-071's stated cap); a session starts at **k_initial = 4**; the capacity fit bound can only shorten, explicitly. The adaptation rule's **shape** (`suggest_next_k`, a pure function of the last round's account): deepen by one after a fully accepted round, halve (floor 1) after a round that accepted nothing, hold otherwise — always clamped to [1, cap]. Nothing here measures whether the shape pays; that measurement, and any live tuning, is J-079.

## 3. Design — the loop

**`aesir_engine/core/speculative_loop.mojo`** (new, pure arithmetic in the J-066..J-071 pattern: it executes no forward, times nothing, opens no device, and contains no speed and no acceptance statistic):

- **`dispatch_proposer(slot, kind)`** — J-071's `plan_proposer` shape, checked against the requested slot (J-014 A3's three slots); wrong-slot and unknown kinds refused.
- **`plan_round_k(kind, requested_k, kv_before, kv_capacity) → KPlan`** — §1 step 2: floor/band/cap refusals, then the capacity fit bound with the shortening **recorded on the plan** (`requested_k`, `planned_k`, `cap_k`, `fit_k`, `shortened_for_capacity`); no-fit (not even k=1) refused.
- **`suggest_next_k(kind, current_k, accepted_count)`** — §1's adaptation shape, bounds enforced on both its input and its result; unmeasured by design (J-079).
- **`LoopState` / `LoopSnapshot`** — the session-side state (KV capacity, committed KV length, context count, RNG word, proposer KV length, accumulated emission) and its per-round snapshot.
- **`run_loop_round(mut state, slot, kind, drafts, target_greedy, rng_draws)`** — §1 steps 1–6 over `plan_verify`, with the rollback assertions against the snapshot as internal errors; refusals leave the state untouched.
- **`run_loop(initial, slot, kind, drafts_flat, round_ks, plain_target) → LoopResult`** — the multi-round driver over a flat draft encoding and a stated plain-greedy continuation (each round's target list is the continuation's next k+1 tokens — the account-level premise J-071 §5 stated; in a live host those lists come from the verify passes). It refuses a flat encoding that runs out mid-round and a drive that ends short of the continuation, and asserts the concatenated emission identical to the continuation under J-071's checker before filing a result.

**Legacy bound reconciliation (decided, implemented).** The verify pass is a draft-check pass, so the band governs every draft count that can ever reach one. Decision: **align the legacy module to the band** — `core/speculative.mojo`'s `evaluate_acceptance` hard limit changes 64 → **15** (its error text with it), because its per-call proposal count is a verify width in waiting (the sampled form's rounds, J-082, will run through verify passes of the same width); and **retain the default 4 as the loop's initial k** (`LOOP_K_INITIAL`), the depth a session starts at before any adaptation. Consequences checked: every in-tree construction uses 4 (its own tests, `test_multi_engine`), so nothing in the tree could legally hold a count the new limit refuses; the pre-existing suite re-passes at 2/2 (§5), and the loop's tests pin the reconciliation in code (15 admitted, 16 and the old 64 refused). The alternative — leaving 64 and merely documenting the difference — was rejected: J-071 named the discrepancy precisely so a later slice quoting the 64 as a verify width would be quoting a live number, and a bound that exists only in prose is not reconciled.

**Host contract** (in the module header, binding on the first live host): (1) build one `LoopState` at generation start from the session's committed lengths, RNG word, KV capacity, and the proposer's KV length; (2) per round, plan k with `plan_round_k` and propose exactly the planned depth from the dispatched slot's proposer; (3) run **one** draft-check pass of width k+1 and record the target's greedy choices; (4) call `run_loop_round` and emit exactly the state's appended tokens; (5) file every round's account with the run's evidence; (6) adapt k only through `suggest_next_k`'s stated bounds until J-079 measures the tuning.

**Registration in `tests/run_all.mojo` is not done**, for J-031 §10's stated reason (the branch line's counted-run pin cannot be re-accounted without the counted run, which belongs to an on-box leg) — the same standing practice as J-066..J-071.
