## 3. The inventory design

New module **`aesir_engine/core/device_inventory.mojo`** (~540 lines), standalone in the road's established pattern (cf. `placement_options.mojo`, `moe_gpu_plan.mojo`): pure parsers over machine-source text + one live `observe_device_inventory()`, tests at **`aesir_engine/tests/test_device_inventory.mojo`** as a standalone lightest-target suite. The module is not registered in `tests/run_all.mojo` (the J-031/J-036 precedent: registration rides with a counted run this VM's memory gate does not permit).

**Per-kind truth:**

- **CPU (`parse_cpuinfo`)** — logical processors = `processor` entries; physical cores = distinct (`physical id`, `core id`) pairs; packages = distinct physical ids; model = first `model name`/`Hardware`. Missing topology stays unknown (-1) and the line says so ("physical core count not reported by cpuinfo") — a count is never derived from the model name or the logical count. Threads-per-core is stated only when physical > 0 divides logical exactly.
- **Hybrid split (`apply_hybrid_split`)** — the ONLY road by which a performance/efficiency split enters the facts: both Intel hybrid sysfs cpulists (`/sys/devices/cpu_core/cpulist`, `/sys/devices/cpu_atom/cpulist`) present and non-empty, counted verbatim (`count_cpulist`, ranges refused when backwards). Otherwise the line states "performance/efficiency split not reported by this machine". On an AMD/VM source the split is therefore never guessed — group 3 of the tests pins all three shapes (both lists / neither / one).
- **GPU (`_probe_gpu`)** — live probe order: (1) `CUDA_VISIBLE_DEVICES` set empty or to `NoDevFiles` → absent, reason names the hiding; (2) `nvidia-smi --query-gpu=name,memory.total,memory.free --format=csv,noheader,nounits` via `run_checked_argv` → `parse_nvidia_smi_csv` (MiB → bytes, overflow-guarded; malformed/empty output refused and the refusal becomes the reason); (3) probe failure → absent with the probe's own error in the reason, cross-checked by listing `/sys/class/drm` (`parse_drm_listing`: an exact `card<digits>` entry counts, connector entries do not) — a card the NVIDIA probe cannot speak for is named as *unclaimed*, never silently dropped and never claimed as a CUDA GPU.
- **NPU (`npu_entry`)** — from Aesir's ledgers only, three states (parked / not present / not probed). On this road the live observer returns **parked** unconditionally: the Hailo's finish-line gate is closed, so the entry reads "reported from the ledger, not probed, never run by this road". There is no code path in the module that opens a device node, a driver, or a Hailo session. (Host-side shell evidence agrees the VM has no `/dev/hailo*` or `/dev/accel` node — recorded as corroboration in §4, not as the module's method: the module does not look, by law.)

**The line.** `DeviceInventory.device_line()` renders `devices: cpu … | gpu … | npu …` — each entry either `present — <facts>` or `absent — <reason>`. `describe()` is the same truth one entry per line. Completeness is a tested invariant (group 8): both the full and the all-absent inventories carry all three kinds on the line. `require_device_present(inv, kind)` raises for an absent kind carrying the entry's own reason — the exact feed point J-047's generalised refusal consumes; this slice itself refuses no placement (refusal-at-open is J-047's named work, meeting this inventory there).

**Probe honesty.** `observe_device_inventory()` never raises: each kind's failure becomes that kind's absent-with-reason entry, because at open the honest output is the line itself, reasons included. No present-GPU result is faked anywhere: the present path is proven only on injected probe output (groups 4/8), and the live group asserts this VM's real absent state.

## 6. Answered-locally records (clean-room)

- **Q: Which GPU probe — the tree's `CUDAGate` MAX discovery or an nvidia-smi-class probe?** The census does not speak to Aesir's internals. Answered locally (§2): the inventory uses the nvidia-smi-class probe so the truth line exists on the lightest surfaces (this VM: ~0.9 GB free; the MAX graph is the heavyweight road), and `CUDAGate.discover_physical_devices()` remains the session/doctor probe. Both answer name + VRAM; neither is a copy of the other, and the `GpuFacts` shape is the seam if a heavy surface later prefers the MAX probe.
- **Q: Should the CPU count come from `par_cpu_count()` (sysconf shim)?** Answered locally: no — the shim needs its staged `.so`; procfs states the same fact with no staging, and `native_hardware.mojo` already sets the procfs precedent. The shim remains the thread layer's source for its own purpose.
- **Q: What is the NPU's inventory state on a machine whose Hailo was never the question?** Answered locally from the campaign's own law: the ledger states are parked / not present / not probed, all three are representable, and the live observer on this road returns parked because the one NPU in Aesir's ledgers is the parked Hailo. No Intel-NPU live state is claimed — the tree has no such enumeration (§2), and Janas's Intel-NPU documentation (census J-004) describes Janas's machine, not Aesir's.
- **Q: Does the line report memory?** The census's bench report carries more than devices, but J-037's roadmap text names CPU topology, GPU + VRAM, NPU presence — and host memory already has its own proven observer (`observe_host_memory`, used at admission). Answered locally: memory stays out of the device line; adding it here would duplicate a working surface.
