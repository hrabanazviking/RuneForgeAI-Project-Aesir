## 2. Definitions and verdict rules (pre-registered)

Stated in `core/kv_drafts.mojo`'s header and committed (@ `8f6cedf6`) before the tests or harness were built or run.

- **Rollback in this tree** is *length restore*: a speculative round (J-071's account, J-072's loop) tentatively writes k+1 KV rows, commits accepted+1, and rolls back k−accepted by returning the committed length to snapshot + accepted + 1; rows past it are dead. Neither the host `KVCache` (`core/mimir_well.mojo` — appends by explicit position, reads bounded by the active length) nor J-088's `Int8KVStore` (identical geometry: separate K/V buffers, [layer][position][kv_width], append by explicit position, `attention_int8_head` reads only positions < seq_len) clears bytes on rollback. Rollback exactness is therefore a statement about the **stored state**, graded in three parts: **(R-A) committed preservation** — tentative appends at positions ≥ the snapshot length change zero stored scalars at positions < it; **(R-B) never-drafted equality** — after rollback and the next appends overwriting the rolled-back positions with the plain continuation's rows, the final store equals the never-drafted store **bit-exact at the precision's own representation** (f16 elements at f16; int8 codes *and* their f32 scales at int8) at every position < the final committed length; **(R-C) dead-row irrelevance** — attention over the committed length is unchanged by tentative rows past it.
- **Rollback extra error** is the difference between the rolled-back state and the never-drafted state **at the same precision**: exact iff that difference is exactly zero. The quantization error an int8 row carries against its f16 source (J-088's bound: ≤ half its row scale) is **not** rollback error — it is present identically in the never-drafted int8 state, and this slice never charges it to rollback. **Verdict rule:** a precision's rollback is EXACT iff (R-A) diff == 0, (R-B) diff == 0 and (R-C) holds in the exercised form; any nonzero diff grades NOT_EXACT and the diff count is filed, never rounded away.
- **Acceptance** is J-071's `accepted_count` (the longest draft prefix equal to the target's own greedy list); totals are J-075's ledger (accepted / drafted per row). Acceptance is a function of the draft list and the **target list** only — no Part V account, loop, or ledger function takes a KV precision input — so at the account level, given the same target lists, acceptance at int8 is unchanged from f16 by construction. Precision can change acceptance **only** by changing the target lists themselves (a model's greedy choices are a function of its logits, which read the KV): that is a live question, NOT PROVEN here (§1, §7). **Verdict rule:** account-level acceptance grades UNCHANGED iff a replay of the filed J-075 fixture accounts reproduces J-075's filed totals **exactly** (the validation gate) and the f16-labelled and int8-labelled replays differ by exactly (0 rounds, 0 drafted, 0 accepted); a changed-target control replay must grade DIFFERS by the exact amount its target change implies.
- **Byte price of a round**, per precision, through the precision's own accounting (`core/kv_account` for f16, `core/kv_int8` for int8): the verify pass tentatively writes k+1 rows, commits accepted+1 and discards k−accepted; each part is priced per token of context. By-construction write shapes in J-091's sense — a discarded row was written and then made dead; nothing here claims a device byte count.

## 3. Inspection — the surfaces, as filed (PROVEN from the tree)

- **The two caches share one rollback geometry.** The host well and the int8 store both append by explicit position into [layer][position][kv_width] buffers and bound every read by the active length; neither clears bytes on rollback. Length restore is therefore the whole rollback mechanism on both, and R-A/R-B/R-C are the complete exactness question: if tentative writes never touch committed positions, if overwriting appends restore the rolled-back positions exactly, and if reads never see past the length, nothing else can leak.
- **The Part V machinery is precision-free — mechanically.** `core/speculative_verify.mojo`, `core/speculative_loop.mojo` and `core/speculative_acceptance.mojo` contain no precision input at all (the word does not appear in any of the three files; this slice's inspect asserts it over their text). The committed-length arithmetic, the RNG rollback and the acceptance count are therefore literally the same functions at f16 and at int8; what precision changes is only the stored representation of the rows (graded in §5) and, live, the target lists a model produces (deferred, §7).
- **No live session integrates the int8 store.** J-088 §7 deferred the integration (host path, then dense CUDA, then Gemma 4 CUDA, each behind `--kv-precision` with f16 default); J-091's ladder graded every int8 cell INTEGRATION_BLOCKED on both lines, and that verdict is inherited unchanged here. Nothing in this slice wires `core/kv_drafts` into any session (the inspect asserts the no-wiring fact); the module executes no forward and times nothing.

## 5. Rollback exactness (the Q1 grade)

### 5.1 The int8 store exercise (deterministic, through the store's own surface)

The drafted store appends plain rows 0–5 (the committed prefix), tentative rows 6–10 (6–8 plain — the accepted prefix and the correction position; 9–10 the rejected drafts' rows, wrong salts), then — after the length-restore rollback — the plain continuation's rows at 9–10. The never-drafted store appends plain rows 0–10.

| Grade | Surface | Filed result |
|---|---|---|
| R-A committed preservation | code + scale diffs, drafted vs prefix store, positions < 6 | **0 codes, 0 scales** |
| R-C at the prefix | attention over length 6, drafted vs prefix store, every layer/head | **identical** |
| Control (before the overwriting appends) | state diff, drafted vs never-drafted, positions < 11 | **256 codes, 0 scales** — the rejected rows were really written (every stored code of the 2 rejected positions, × 2 layers × K/V, differs); their per-slice scales coincide because the synthetic rows' maxabs coincide — the codes carry the difference |
| R-B never-drafted equality | code + scale diffs after rollback + overwrite, positions < 11 | **0 codes, 0 scales, state diff 0** |
| R-B in value terms | max dequantized difference over the same positions | **0.0** |
| R-C at the final length | attention over length 11, drafted vs never-drafted | **identical** at every layer/head |
| **Verdict (pre-registered rule)** | | **EXACT** |

Tamper controls (the grading surface can see a difference when one exists): one flipped code in a copy of the plain store is seen as exactly **1** code diff and grades NOT_EXACT; one shifted scale (+0.5) is seen as exactly **1** scale diff with codes clean.

### 5.2 Quantization is not rollback error (filed so the two are never conflated)

A crafted row (maxabs 1.0, carrying 0.5) round-trips with error exactly **0.003937006** — J-088's bound, half its row scale (1/127) — and that error is real (> 0.0039, asserted). It is present **identically** in the drafted and never-drafted int8 states, so the rollback extra difference of §5.1 is 0 while the quantization error is not: the rollback is exact *at the precision's own representation*, which is the only exactness a rollback can owe. Any future filing that charges J-088's quantization error to rollback, or claims rollback exactness *against f16 values*, misstates this slice.

### 5.3 The f16 grade and the loop level

The store-level exercise is filed at int8 because int8 is the representation whose rollback the roadmap questions (its codes + scales are the state that could silently diverge). At f16 the same length-restore account holds on the host well's identical geometry (§3), and at the loop level the grade is precision-free by construction: this slice's validation gate B reproduces J-072's filed multi-round scenario **exactly** through `run_loop` (6 rounds, 24 tokens, accepted 18, rollback rows 6, KV 67 → 91, proposer KV 85, RNG word unchanged, emission identical to the plain continuation) — and that loop takes no precision input, so the account it proves is the rollback at both precisions. **Verdict: EXACT at f16 (account/loop level, on the host geometry of §3) and EXACT at int8 (account level and store level).** A store-level f16 diff exercise is not separately filed — f16 rows are stored verbatim, so the int8 exercise is the strictly stronger one; the live store grade on a real session is §7's leg, at both precisions.
