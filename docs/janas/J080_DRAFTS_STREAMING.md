## 1. The question, the mechanism, and the verdict rule — all stated before measuring

**The question.** Sequential decode touches one token's routed experts at a time, in token-major order (token, then its 16 layers). A speculative round verifies k+1 positions in **one** pass, and that changes the expert demand over the Part II stream in two distinct ways:

1. **Batching (reorder + sharing).** A verify pass is layer-major: for each layer, all k+1 positions are processed together. The same (layer, expert) pair routed by several positions in the batch is touched several times within a short window instead of being spread 128 accesses apart across separate token steps — during which the sequential stream's intervening demand can evict it. Batching therefore *could* raise the useful hit rate. It also reorders every admission/eviction decision the cache makes.
2. **Rejected-suffix waste.** The pass touches every verified position's routed experts **before** the rejection point is known. Positions past the accepted prefix (plus its one correction/bonus token) are computed and discarded: their misses stream real bytes, their admissions evict real residents, and that work buys nothing.

What does the sum of (1) and (2) do to the expert cache — the shipping **fsketch** policy (J-024) — hit rates, streamed bytes, evictions, and wasted fetches, versus plain sequential decode, on the J-022 model and its real demand?

**Field.** The J-022 model is OLMoE Q4_K_M (pin sha256 `8c310f1435a1222338fd2d3d974975be9cd908180b644bab0c2a94da1ac32f3f`, the J-015 pin). Its real demand is the J-016 trace (`j016_trace_olmoe.jsonl`, sha256 re-verified this run `85e1d2413cbfcd43516a03d8463c7266d486cf0f0d0a6ed3104d09111facf99a`; 577 tokens in 7 contiguous file-order segments — six prompts plus prose's 4 generation tokens filed last — 9,232 token-layers, 73,856 accesses). One model, one quant, prompt-phase demand with 4 generated tokens — the same scope limit J-017 §1 binds on every citation of this trace, and it binds this slice's verdict too (§5, honesty ledger). Budgets are built exactly as J-016/J-018/J-024 built them: pairs × mean scaled pair size (3,720; sizes simulated scaled ÷1024, exact for both OLMoE layer classes). Operating budgets **128 / 512 pairs** (≈0.49 / 1.95 GB).

**Rounds.** A round starting at trace position s of one segment verifies width w = k+1 positions s..s+k (clipped at the segment end; rounds never cross a segment boundary, and the cache carries across segments in file order exactly as the J-024 global session carries across prompts). Acceptance A ∈ [0, k] is the accepted draft prefix length; the round commits A+1 tokens (J-071: the prefix plus exactly one target token) and the next round starts at s+A+1. Every run emits the whole trace (577 tokens), which is what makes per-emitted-token normalisation honest. Fixed k ∈ {2, 4, 8} (J-079's baselines; 4 is J-072's initial depth).

**Acceptance — the stated, honest source.** No live pair is admitted on any filed fact (the J-078/J-079 record stands: only SIMULATED fixtures have ever been admitted), so acceptance is **modelled**, and every number that depends on it is labelled **SIMULATED on the MEASURED trace**. The model is the road's own filed fixture set, reused verbatim for continuity: per-round would-be prefix lengths L cycle deterministically through J-079 §4's regimes, themselves shaped from J-075's filed fixture shapes — **hot** [8,6,9,7,8,6,9,5] (English-prose/code-like), **cold** [1,0,2,1,1,0,1,2] (Italian-prose-like collapse), **mixed** [3,1,4,0,2,5,1,3] (structured-like spread); A = min(k, L), the cycle advancing one step per round globally across segments. **PERFECT** (A = k always) is filed beside them as the zero-waste ceiling, never as a candidate. A wasted position's routed set is **proxied** by the true continuation's set at the same offset — the trace records no draft's own routing, and the proxy keeps the access count and the measured locality real while inventing no routing; the limitation is stated wherever the waste numbers are read (§5).

**Disciplines (candidates, stated before measuring).**

- **SEQ** — token-major sequential decode; the base every delta is against.
- **BATCH-ALL** — layer-major verify pass over all w positions, waste charged in full. This is the buildable shape: a batched forward cannot know the rejection point before it runs.
- **BATCH-PREFIX** — layer-major verify pass over the useful positions only. **Not buildable as stated** (it needs the rejection point in advance); it is the decomposition bound that separates the two effects of §1's question: BATCH-PREFIX − SEQ is the batching (reorder + sharing) effect alone, BATCH-ALL − BATCH-PREFIX is the rejected-suffix waste cost alone.

**Cost accounting.** Every access goes through the J-024 tournament's `FSketchCache`, demand path unchanged. A miss streams its full pair size whether admitted or bypassed (the simulator's accounting, identical to J-024/J-025). Streamed bytes are normalised **per emitted token** (577 for every run), never per access, so waste cannot hide inside a larger denominator. Waste fetches are the misses among wasted accesses; their streamed bytes are totalled separately; evictions and admissions are attributed to the access class (useful / wasted) that triggered them. Batch sharing is counted per round as distinct (layer, expert) pairs over the verified positions versus the w×128 pair-slots issued.

**Verdict rule (pre-registered).** At each operating budget (128 and 512 pairs):

- Speculation is **CACHE-NEUTRAL-OR-BETTER** in a (regime, k) cell iff BATCH-ALL streamed bytes per emitted token ≤ SEQ there.
- If no buildable cell is neutral-or-better but BATCH-PREFIX beats SEQ somewhere, the verdict is **MIXED**: batching itself pays, rejected-suffix waste more than eats it — both halves quantified, neither hidden.
- If BATCH-PREFIX also never beats SEQ, the verdict is **TAX**: speculation imposes a streamed-bytes tax on this trace, quantified per regime / k / budget, to be weighed against tok/s at the J-086 gate. No speed is measured in this slice; a latency or speed case is **NOT PROVEN either way**, exactly as J-025 §7(a) binds its own bytes verdict.
- The PERFECT rows are read with the modelled rows: if even PERFECT BATCH-ALL costs bytes, the tax sits in the batching itself, not in acceptance.

| Regime | k=2 @128 / @512 | k=4 @128 / @512 | k=8 @128 / @512 |

**No buildable cell is cache-neutral at either budget.** The cheapest cells in the whole table (hot k=2 @128, +0.21 %; hot k=4 @512, +0.28 %) are zero-waste cells: the filed hot fixture's L values (all ≥ 5) accept every draft at k ≤ 4, so hot at k ≤ 4 *is* the perfect row — the table's floor is what speculation costs when acceptance never fails. The moment acceptance is imperfect, the tax is immediate: mixed at the shallowest depth already costs +19.48 % / +17.69 %, and cold at k=2 costs +47.10 % / +38.50 %.

(GB = 10⁹ B over the whole 577-token session.) Waste does not only stream: at cold k=8 @128, **76 % of all evictions are triggered by wasted accesses** — the rejected suffix churns the residents the useful stream chose, on top of paying its own fetches.

### 3.2 BATCH-PREFIX — the batching effect alone (net vs SEQ)

BATCH-PREFIX is positive (a cost) in **every cell but one**: hot +0.21…+1.71 %, cold +0.13 % @128 / +1.11 % @512 (identical across k by construction — cold's L ≤ 2 fixes A for every k ≥ 2, so the useful stream is the same), mixed +0.36…+0.73 %. The single negative cell is **mixed / k=2 @512: −0.33 %** (hit 0.770 vs SEQ 0.769; evictions 1,663 vs 1,668). Batch sharing is real — between 24 % (hot k=2) and 53 % (hot k=8) of a batch's pair-slots repeat a pair already issued in the same batch — but a shared pair the sequential stream would also have hit saves no bytes, and the layer-major reorder otherwise perturbs fsketch's admission/eviction choices slightly *against* the useful stream (PERFECT-ALL evictions @128 rise 1,050 → 1,122 / 1,187 / 1,330 at k=2/4/8 with zero waste anywhere). Even a perfect drafter pays the batching tax at k=8 (+2.09 % @128).

### 3.3 The hit-rate paradox — recorded so it cannot be misquoted

BATCH-ALL *hit rates rise* in the cold and mixed regimes (cold k=8: 0.390 @128, 0.844 @512, against SEQ 0.351 / 0.769) while streamed bytes per emitted token explode. Two reasons, both artefacts of the accounting, neither a benefit: (i) the denominator grows with wasted accesses, most of which re-touch pairs the batch itself just fetched; (ii) under §1's proxy, a wasted position's routed set *is* the true continuation's set at that offset, so waste warms exactly the residents the same tokens need when they are later committed usefully — a real draft's wrong tokens would route to *their own* experts and warm the wrong residents instead. **Consequence, stated plainly: the proxy biases BATCH-ALL favourably, so the byte taxes in §3.1 are, if anything, understated, and no hit-rate figure from a speculation-inflated denominator may be quoted as a speculation benefit.** Per-emitted-token bytes — the pre-registered currency — is the only honest headline, and the J-086 gate's tables must normalise the same way.

## 4. Verdict

**MIXED — by the pre-registered rule of §1, triggered by exactly one cell.** BATCH-PREFIX beats SEQ in one cell only (mixed / k=2 @512, −0.33 %), so the rule's MIXED branch fires: batching *can* pay, in a narrow shallow-depth / large-budget / mid-acceptance corner, and rejected-suffix waste eats it everywhere — at that very cell, BATCH-ALL costs +17.69 %. The substantive findings, which are the slice's real result and must be quoted with the label:

1. **On streamed bytes, speculation over the Part II expert stream does not pay for itself on this trace — it taxes, at every depth, in every acceptance regime, at both operating budgets.** The floor tax (perfect acceptance) is +0.2…+2.1 %; realistic acceptance multiplies it: roughly +18…+49 % at J-072's initial depth k=4 in mixed text, +104…+136 % in cold text, and +193…+307 % for cold text at k=8.
2. **The tax's dominant term is rejected-suffix waste, and it is multiplicative in (k − A).** This prices J-079's adaptive depth in bytes for the first time: in cold conditions, shallowing 8 → 2 cuts the tax from +307 % to +47 % @128 — adaptive depth is the difference between a heavy tax and a catastrophic one, and fixed deep k in cold text is the worst configuration measured on this road's cache.
3. **This verdict grades streamed bytes only** — the currency Part II's slices share. Speculation's actual case is wall-clock (one wide verify pass instead of k+1 narrow steps), which no offline replay can measure: any speed case is **NOT PROVEN either way** by this slice, exactly as J-025 §7(a) binds its own verdict. What this slice settles is the cache side of the J-086 ledger: a live net-tok/s claim for a (regime, k, budget) cell must first repay the byte tax tabled in §3.1 for that cell.
4. **Reopen conditions (named):** a decode-heavy trace (J-033's soak shape), where generated-token demand may share differently across a batch; a second model's trace; or a verify implementation that can skip suffix experts layer-wise once a layer's position is known dead — its bound is BATCH-PREFIX, which this slice shows still starts ~0.1…+2 % underwater on bytes, so even that design must win on wall, not on bytes. The Janas headline the roadmap quotes ("drafts are where MoE speculation pays most") is **not confirmed on the cache axis** by Aesir's own measured demand: on bytes, drafts are where MoE speculation *costs* most, because MoE verification multiplies expert demand per position in a way dense verification does not. Whether it pays on the wall axis is §6's live leg, and only that leg can say so.
