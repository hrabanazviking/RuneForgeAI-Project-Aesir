**The split, in Aesir's own terms.** A prompt pass is a batched matrix product. A two-device split divides the batch **by rows**: side A computes rows [0, first_rows), side B the rest. Row division needs no cross-device reduction inside the product — every output element is computed whole by exactly one side, in the serial path's fixed per-element reduction order, so a correct split's output is bit-identical to the unsplit output (the analogue asserts exactly this, §6). Candidate fractions are 1/4, 1/2, and 3/4 of the batch to the first side, de-duplicated by row count. Per split the planner states exactly: per-side work (rows_side × k × n × reps multiply-adds), crossing bytes (each side receives its input slice rows_side × k × 4 B and a full copy of the shared matrix k × n × 4 B, replicated to both sides; each side returns its output rows rows_side × n × 4 B), and the join (a gather of the full output, rows × n elements / rows × n × 4 B, in row order). For the filed workload shape every candidate split totals 4,194,304 multiply-adds and 1,097,728 crossing bytes — fraction-independent totals, unit-pinned (§5, group 1).

**Refusals, before any measurement.** The planner refuses: the same device twice (J-036's grammar, re-stated at plan time); any pair naming the NPU (the parked Hailo ledger — a parked device cannot take half a prompt pass); and a split with an empty side (first_rows 0 or rows — a one-sided split is a single-device pass wearing a plus sign).

## 3. The survival rule — pre-registered

**This rule was written into the module header before any J-043 live number was measured; `evaluate_split` is its pure form, unit-tested on injected measurement sets (§5, groups 4–8).** It inherits J-040's margin+separation discipline, applied against **each parent separately**:

- **(a) Margin:** (parent_median − split_median) exceeds **10%** of the split's median; and
- **(b) Separation:** the split's slowest counted round (its max) is still below the parent's median.

A split survives as an option **only** when both hurdles clear against **both** parents. A split that fails either hurdle against either parent is **MEASURED-AND-REJECTED**: recorded with its numbers and the failed hurdle per parent, and never kept — beating one parent only, or beating both inside the noise band, is a rejection, not a partial success. A split or parent that did not measure (excluded / unmeasurable-with-reason / bound-stopped / refused) produces **no survival verdict at all**: the record carries that state — an unmeasured split is neither kept nor rejected on numbers it does not have. Bound-stopped candidates are never ranked.

**Joined time.** A split's joined time is stated in one of two forms, always with the form named: concurrent sides join at max(side_a, side_b) + join; sequential sides at side_a + side_b + join. The join is in both forms — a split timing without its join is not a split timing. (True device pairs, when executors exist, will use the concurrent form; the analogue below measures the sequential form and says so every time.)

**Manual supremacy, untouched.** An explicit co-work prompt option names its pair and the planner evaluates exactly that pair — never substituting another pair, a single device, or the analogue. An explicit single or race option names no co-work pair: the planner records that and evaluates nothing. Open-time refusal of a hand placement remains J-047's work.

## 8. Answered-locally records (clean-room)

- **Q: Why row splits, not column/layer splits?** Answered from Aesir's own arithmetic: the prompt pass is a batched product in which each output element is a whole row-wise dot product; dividing by rows keeps every element whole on one side with the serial reduction order, so split output is bit-identical to unsplit output and the join is a pure gather. A column split would need a cross-device reduction inside every element — different arithmetic, a different join, and no executor in the tree to measure it through.
- **Q: Why is the analogue sequential when real co-work is concurrent?** Answered locally from the tree's proven patterns: the analogue runs one threaded executor at a time (J-039's shape); a concurrent form would need two executors running truly in parallel, which this harness does not provide. The sequential form (side_a + side_b + join) is the conservative bound, is named on every record, and can only *understate* a split — a split that cannot survive even the accounting test in sequential form earns no promotion, and one that someday survives it still earns no device claim.
- **Q: Why does the survival rule apply per parent instead of against the better parent only?** The roadmap's own sentence: "only splits that beat both parents survive as options." Beating only the weaker parent is exactly the partial success the rule exists to reject (§5, group 5 pins it).
- **Q: Why 1/4, 1/2, 3/4 fractions?** Answered locally: the two sides are not equally fast in general, so asymmetric fractions are the candidates that could match asymmetric speeds; the set is small, stated once in the planner, and de-duplicated by row count. Which fraction wins, if any, is the survival rule's question, not the planner's.
- **Q: Why are the pair records' plans built from the pure accounting function rather than `plan_device_split`?** Answered from the record's purpose (and stated in the code): `plan_device_split`'s plan-time refusals would raise and erase exactly the refused/excluded pairs the record exists to carry. The refusals themselves are not lost — they are `validate_device_pair`'s and `classify_pair`'s, both on the record and unit-pinned (§5, groups 2 and 9).
