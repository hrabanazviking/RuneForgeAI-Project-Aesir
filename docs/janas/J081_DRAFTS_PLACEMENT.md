## 1. Verdict — and the rule, pre-registered before any combination was priced

**J-081 closes CLOSED-WITH-DEFERRED-LEG:** the draft-check placement layer Part III's engine was missing is built and proven — a pure module that prices every draft/check placement combination for a stated (proposer/target pair, device set, round shape) in the road's own currencies, refuses combinations whose required pieces do not exist in-tree **by name**, and keeps exactly one combination per shape under the pre-registered rule below. The kept combinations are recorded placement **policy** — the placements the engine will use when the passes exist. The live placed round (GPU check of CPU drafts and the reverse, run and timed) is **DEFERRED-WITH-REASON** (§6): two global blockers stand in front of every combination, so no combination here is an executable or measured claim, and **no speed, wall, or tok/s is stated or implied anywhere in this slice** — "the fastest honest combination" is kept in the only honest currency available today, synchronised crossings and crossing bytes, and the doc says so wherever the word *kept* appears.

**The verdict rule (pre-registered; the module header is its normative text, written before any combination below was priced):**

- **Global blockers cap every combination at PLAN class:** (G-PROPOSER) no proposer implementation exists in-tree for any kind on any device, and (G-EXECUTOR) no verify-pass executor exists in-tree — `require_draft_check_use()` (J-036) still raises and the facade's `speculative_generate` still raises not-implemented (both asserted by the inspection recount, §5). A combination may be KEPT as the recorded placement policy, never as measured speed. This is also why J-042's draft-check chooser is untouched: it files NO-MEASURED-FALLBACK because no draft-check pass exists to measure, and a pricing layer does not change that — there is still nothing measured to fall back from.
- **Combination-specific refusals, checked in this order, first applicable name wins:** (1) a device the combination needs is absent from the stated device set; (2) a conversation proposer placed off the host CPU — it has no model to place (J-071: copied text, no KV); (3) any pass on an integrated GPU — no iGPU backend exists (J-066 DEFER; J-067 teaches its shape, builds no executor); (4) an MoE model placed on a discrete GPU — no MoE device admission/profile, no device expert payload store, no OLMoE device block maths (J-031's named missing pieces); (5) a GPU check pass whose width w = k+1 is not the one proven tile shape — width 4, and then only on the tile-admitted profile (J-054: widths 1 and 4 are the proven shapes; width 4 is admitted only for the exercised Llama 3.2 3B profile). A refused combination is still **priced** as a plan — its byte/crossing account is stated — so the cost of building it stays visible.
- **Keep eligibility + ranking.** Among combinations that are not refused: the check pass is the target model's pass, the expensive pass of the round, so accelerator-first (the Aesir standing law: NPU, then GPU, then CPU spill only) binds it first — keep-eligible combinations are exactly those whose check device is the highest-ranked check device among the non-refused combinations (discrete GPU above iGPU above CPU). Among the eligible, the kept combination is the one with (a) fewest synchronised crossings per round, then (b) fewest total device-crossing bytes per round (H2D + D2H), then (c) fewest contended bytes, then (d) the lowest combination code (deterministic order: draft CPU, then GPU, then iGPU). Exactly one combination is kept per (pair, device set, round shape).

**Pricing, in the road's own currencies (all per round):** token ids cross at 4 bytes each (J-031's token account); a width-1 pass on a discrete GPU synchronises once per token (J-053/J-054 decode discipline), a batched GPU check pays 1 for the pass plus 1 per inter-device transfer batch plus, for an MoE check, 1 per miss layer (J-031: uploads batch per miss layer); coupled proposers (MTP head, assistant model — J-071: they share the target's forward state / read its KV) split away from the check device cross the target hidden vector once per draft step; the verify batch's expert stream is J-080's `batch_streamed_bytes` account — a CPU check streams it on the host, a discrete-GPU check **re-pays exactly those bytes as an H2D upload** (J-031: GPU assistance relocates compute, it does not shrink byte traffic), an iGPU check pays them as contended bytes, never copy bytes (J-067); iGPU weight traffic is contended bytes (draft k times, check once), copy bytes always zero. Open-time residency is not a per-round cost and is not charged.

## 4. What this settles, and what it does not

- The roadmap's two named directions are both answered **as placement policy**: GPU check of CPU drafts is the kept combination for independent dense drafts at the one proven GPU width; the reverse (GPU draft, CPU check) is priced and is never kept while a non-refused GPU check exists, because accelerator-first binds the expensive pass — and for coupled drafts the reverse question does not arise, since the draft follows the target. That is the fastest honest combination in the currencies that exist today (crossings, then bytes); whether it is fastest in wall-clock is §6's leg, and only that leg can say so.
- J-080's byte tax and this slice compose, and the composition is stated so it cannot be misquoted at the gate: a GPU check does not shrink the expert stream — it re-pays it as upload — so a live GPU-check tok/s claim must first repay both J-080's per-cell byte tax and this slice's per-round crossing account for the kept combination.
- Nothing here admits a live pair, lifts the J-036 gate, or changes J-042's NO-MEASURED-FALLBACK: the chooser that files fallbacks and the planner that prices combinations answer different questions, and both records stand.
