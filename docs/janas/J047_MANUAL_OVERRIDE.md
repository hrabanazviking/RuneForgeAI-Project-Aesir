## 1. Question and ground

**Question.** Part III built every layer of choosing — J-036's options, J-037's inventory, J-038–J-043's measurement and choosers, J-044's learned defaults, J-045's re-trials, J-046's tolerance proof — and each layer states the same promise in its own words: a hand choice is fixed as MANUAL-FIXED and never ranked (J-040–J-042), learned values are defaults only under an explicit option (J-044), manual kinds are never re-trialled (J-045), a manual option has no auto choice to grade (J-046). What is the one layer that states, per pass kind, whose choice governs — hand, preset, learned, or auto — and refuses, at open, any governing choice that names a device this machine does not have?

**Ground, and only that ground.** The preset family's existence and its one documented semantic are the J-003 census rows (filed from Janas's public documentation): `--mode auto|eco|max`; "eco never uses the GPU for speed alone"; "A hand choice holds over `--mode` presets." The inventory truth and its entry types are J-037's (`DeviceInventory` / `DeviceEntry`, built by `cpu_entry` / `gpu_entry` / `gpu_absent_entry` / `npu_entry`; the NPU entry is the parked Hailo ledger on this road). The learned contract is J-044 §4 (defaults only; hosts consult learned entries only for kinds left on auto) and its record shape (`LearnedPassChoice`: option provenance, placement label, device, threads, decision). The re-trial exclusion is J-045's (`kind_retriable`: present and not MANUAL-FIXED). **Why the resolver runs no chooser.** The resolver decides *who governs*; running a measurement is the governing layer's own act (a chooser call under MANUAL-AUTO / PRESET-MEASURE / AUTO, a fixed choice under the FIXED layers, a seed under LEARNED). Folding chooser runs into the resolver would couple the supremacy logic to harness timing and make the stack untestable as pure logic — every prior Part III rule (the J-040 decision rule, the J-045 cadence, the J-046 tolerance rule) is a pure function for exactly this reason, and this slice follows it.

## 3. The precedence rule — stated before results

Per pass kind (prompt / drafts / reply), independently. The inputs are the kind's resolved J-036 option (choice + source + was-set), the resolved mode (§4), the kind's J-044 learned choice (ABSENT when no entry applies), and the kill-shrunk auto field text (J-036's `effective_auto_devices`).

- **(a) HAND — a set option governs absolutely.** Single / co-work forms govern as **MANUAL-FIXED**: the choice stands verbatim; it is never measured against, never ranked, and never re-trialled. A race form governs as **MANUAL-RACE**: measurement is restricted to exactly the named members; preset and learned are skipped — no layer widens or narrows the field the hand chose. An **explicit `auto`** (written by hand, source cli/env) governs as **MANUAL-AUTO**: it is a hand statement directing fresh measurement over the full auto field, so preset and learned are skipped for the kind — the measurement the user asked for is the one that runs. An *unset* auto (source default) is silence, not a statement, and falls through. (§8 records the explicit-auto decision and its ground.)
- **(b) PRESET — only where the hand is silent.** Eco governs as **PRESET-FIXED**, max as **PRESET-MEASURE** (§4). Mode auto governs nothing.
- **(c) LEARNED — only where the hand is silent AND no preset governs.** A present learned choice applies as the session default (**LEARNED**), provenance = its decision + originating option. A learned choice whose decision is MANUAL-FIXED is a *persisted hand choice*: it applies with that provenance stated, and `retrial_applies` is False for it (J-045's exclusion, carried through). An absent kind supplies nothing.
- **(d) AUTO — the remainder.** Nothing governs: the kind's chooser measures (J-040/J-041/J-042).

Every `KindResolution` reports its governing layer, its provenance in words, the fixed placement or the measurement field, whether a re-trial could ever apply to the outcome (True only for LEARNED-measured and AUTO outcomes — hand and preset outcomes are standing user instructions, not measurements, and there is nothing to re-trial), and the reason the layer governs. Drafts resolutions carry the standing addendum: choosing is not using — any *use* of a drafts placement still fails closed through J-036's `require_draft_check_use()` (gap G1) until Part V.

## 4. The preset surface — BUILT

**Verdict: built**, on the census ground (J-003 rows), in J-036's exact shape:

- **Grammar:** `--mode auto|eco|max`, exact lower-case spellings; `--mode value` and `--mode=value` argv forms; env equivalent **`AESIR_MODE`** (named by Aesir's own `AESIR_` rule — the census names the flag form only; §8). Refusals, all with reasons and all unit-tested: unknown value (`ultra`), wrong case (`ECO`), empty value, duplicate `--mode` ("state it once"), missing value, and any unrecognised spelling inside the surface's namespace (`--modee`). The namespace deliberately excludes `--model` (another surface's flag — a shared argv scan must never refuse the model picker's own flag; §8).
- **Precedence:** cli > env > default, the supplying source recorded on `ModeOption`, exactly as J-036 resolves placement values. An unset mode is auto with source default (silence); an explicit `--mode auto` is recorded with its source and still governs nothing — auto is the absence of a preset intent, stated.
- **What eco means** (per kind): a FIXED intent — `cpu threads=1`. The device half is the census's one documented eco rule ("eco never uses the GPU for speed alone") at its strongest honest reading: in eco the GPU is not in the field at all. The thread half is J-040's session default, the minimal-resource rung *by construction* (one thread, CPU only). Eco claims nothing about speed — no eco timing exists or is implied; it is an economy intent.
- **What max means** (per kind): a MEASURE intent — no fixed placement; the kind is measured over the full auto field (widest J-039 ladder, every device the inventory and kill switches leave eligible) and **the learned default is bypassed**, so the widest honest look is taken fresh. Max claims no device is fast: GPU/NPU candidates still carry no executor today and ride the chooser records as excluded / unmeasurable-with-reason exactly as under plain auto (J-040). (Answered-locally — the census documents no max semantics beyond the name; §8.)
- **Fail-closed where a preset would need what does not exist:** a drafts preset intent resolves and reports, but its note carries the G1 gate verbatim, and nothing in this module calls a drafts use into being. A preset never names a device the mode grammar cannot support: eco names only the CPU (which no kill switch can kill, J-036), max names no device at all.

## 5. Invalid-device refusal at open — generalised

`validate_open_choices(options, mode, learned, has_learned, inventory)` checks, in a stated order, **hand choices first** (prompt, drafts, reply — every device a *set* option names), **then the governing preset/learned devices** (via `resolve_precedence`'s own verdicts: a PRESET-FIXED kind's device, a LEARNED kind's chosen device). The first refusal raises with its reason; a return means every governing named device is present.

- **Whole, in every form.** `validate_choice_at_open` walks *every* device a value names: the single device, both members of an `a+b` co-work pair, every member of a comma race list. One absent member refuses the *entire* choice. No device is dropped from a list, substituted with auto/cpu, or trimmed so the rest can proceed — J-036's NPU-for-reply parse refusal, generalised to open time and to every source of a choice.
- **The reason names the device, the kind, and the inventory fact**, in the inventory entry's own rendered words. Filed examples (from the suite's fixture runs, §6):
  - `ManualOverride: --reply-on (hand choice) 'gpu' names gpu for a reply pass, but this machine's inventory says: gpu absent — no GPU probe answered: fixture states no gpu -- the choice is refused whole at open; no device is dropped from it, substituted, or trimmed so the rest can proceed (J-047 generalised refusal)`
  - The live VM form of the same refusal carries the real probe failure (`nvidia-smi failed (subprocess failed: nvidia-smi (wait status 32512)); /sys/class/drm lists no card device`) — see `j047_test_output.txt`.
  - Parked NPU (any form, prompt kind): `... names npu for a prompt pass, but this machine's inventory says: npu absent — Hailo NPU is parked by Aesir's campaign law (finish-line gate closed); reported from the ledger, not probed, never run by this road -- ...` The NPU needs no special case in the code: its inventory entry *is* absent-by-ledger on this road, so naming it as an execution device refuses through the uniform path, with the parked reason on the refusal's face. (J-036 still refuses NPU for drafts/reply earlier, at parse; the open refusal is what a prompt NPU — parse-legal as a stored value — meets when a session would actually execute on this road.)
- **The CPU is checked like any device.** An inventory whose cpu entry is absent refuses even a `cpu` choice, with its reason — the check is over J-037's real entries, not a hard-coded assumption that the CPU exists.
- **Only governing choices are refused.** A learned device shadowed by a hand choice or a governing preset is never applied, so it is never refused: refusing a stale default *under* a valid hand choice would let the shadowed layer argue with the hand — the exact supremacy violation this slice exists to prevent (§8). The hand layer itself is always checked in full, because the hand's devices are the ones the user just named.

## 8. Answered-locally records (clean-room)

- **Q: What does an explicit hand-written `auto` mean against presets and learned defaults?** The census does not say; J-036 stores an explicit auto with its supplying source (cli/env) precisely so the distinction is representable, and J-044's contract says hosts consult learned entries "only for kinds the user left on auto" without splitting written from unwritten auto. Answered locally (§3): a written auto is a hand statement — it directs fresh measurement, so preset and learned are skipped (MANUAL-AUTO); an unset auto is silence and falls through. The alternative (written auto = silence) would let a learned default silently replace the measurement the user explicitly just asked for — the silent-ignore shape Part III refuses everywhere.
- **Q: What does `--mode max` mean?** The census (J-003) documents the spelling and eco's one rule; it documents no max semantics. Answered locally from Aesir's own facts (§4): max = measure over the full field with the learned default bypassed. It deliberately does **not** mean "widest thread rung fixed" — J-039 measured that more threads can be slower, so fixing the widest rung would be a preset that argues with measurement; and it does not mean "GPU on" — no GPU executor exists to honour that (J-040), and inventing one in a preset would fake a device claim.
- **Q: What thread intent does eco carry beyond the census's GPU rule?** Answered locally: the serial rung, because it is J-040's session default and minimal by construction — an economy claim about *resources*, which is true by definition of the rung, not a speed claim, which would need measurement eco does not do.
- **Q: The env name for `--mode`?** The census names Janas's placement env equivalents but no mode env name in the rows this road filed. Answered locally by Aesir's naming rule (`AESIR_` + the flag's name, J-036 §9's precedent): `AESIR_MODE`.
- **Q: Should a learned/preset device shadowed by a higher layer be refused at open when its device is absent?** Answered locally: no (§5). Refusal exists to stop a choice that would *govern* from executing on a device the machine lacks. A shadowed choice governs nothing; refusing it would block a valid hand choice because of a stale default underneath it — a supremacy violation. The hand layer is always checked in full regardless of shadowing, because the hand's statement is the user's current word.
- **Q: Is `--model` inside the mode surface's namespace?** Answered locally: no. The scan owns `--mode` and its misspellings, but `--model` is another surface's flag in a shared argv; refusing it would break every combined command line. The boundary is coded in `_looks_like_mode_flag` and pinned by the scan test (a `--model` flag passes the scan untouched).
