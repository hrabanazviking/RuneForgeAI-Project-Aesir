## 1. Question and ground

**Question.** Part III built placement as a session-open discipline for a CLI-shaped surface: J-036's options, J-037's inventory, J-040–J-043's choosers, J-044's learned defaults, J-047's supremacy stack and open refusal, J-048's contention rule. Aesir also serves: what does it mean for *the same options* to be honoured by the server surface — which of them are session defaults, which may a single request override, and what happens when a request asks for a placement the running session cannot give?

**Ground, and only that ground — the server surface as this tree actually has it, read first-hand for this slice:**

- **The live service** is `cli/native_serve.mojo`: `serve_loaded()` runs **one resident session** (`Llama3CUDASession` or `Gemma4CUDASession`), concurrency 1, and `dispatch_native_serve()` fixes the execution state at startup — `--accel` must be `cuda` ("Native service requires a supported CUDA profile; no CPU fallback"), and `--device`, `--profile`, `--context`, the token/timeout limits, the sampling defaults, and the system default are all resolved once, before the first request (sampling/system through `resolve_native_settings`: CLI > config > built-in default). The startup banner states the truth it serves under: `backend=cuda; profile=…; concurrency=1; context=…`. Per request the loop calls `session.reset()`, `session.configure_sampling(request.sampling)`, `session.configure_control(...)` (plus `configure_output()` / `configure_tool()` on the OpenAI routes), then `session.begin_turn(...)`. **There is no configure-placement on any session, and no placement field in any request parser** (verified by text search of `server/` and `cli/native_serve.mojo`: no `prompt_on`, no placement import).
- **The three generation request shapes**, all bounded and fail-closed on unknown fields: native `POST /v1/generate` (`GenerateRequest` in `native_serve.mojo` — flat fields parsed through `FlatJSON.fields()`); Ollama `POST /api/generate` + `POST /api/chat` (`OllamaRequest` in `server/ollama.mojo` — its `options` object consumes **numbers only**, via `parser.number()`); OpenAI `POST /v1/chat/completions` + `POST /v1/completions` (`OpenAIRequest` in `server/openai.mojo` — flat fields). Non-generation routes (`/api/show`, `/api/tags`, `/api/ps`, `/v1/models`, `/health*`) execute no pass; `OllamaShowRequest` already refuses every control field ("Only model identity is meaningful for /api/show; reject ignored controls").
- **The two per-request precedents the tree itself sets.** *Cheap state:* sampling — every parser seeds from the session defaults and a per-request value overrides through `with_sampling_option()`, because `configure_sampling()` exists per request. *Allocation-bound state:* the context — `server/local_protocol.mojo`'s `require_loaded_context(requested, loaded)` refuses any per-request `num_ctx` that differs from the loaded context ("The allocated session cannot apply a per-request context resize"); `0` is the omission sentinel, equality is accepted. Token limits sit between: per-request, bounded by the session ceiling (`resolve_request_token_limit`).
- **Not a parity target:** `server/api.mojo`'s `BifrostGate` — a disconnected scaffold whose own dispatch returns HTTP 501 for every model-backed route ("no model-backed service loop is attached"). Parity with a surface that executes nothing would be fiction.
- **The startup half of the gap:** `dispatch_native_serve()` refuses any flag it does not know as an "Unsupported service option", and neither J-036's nor J-047's flags are in its list — today the placement options cannot even be *stated* on the serve command line, let alone resolved as session defaults.
- The placement ground itself: J-036's grammar/sources/kills/quality family, J-037's inventory entries, J-044's record shape, J-047's stack (`resolve_precedence`, `validate_open_choices`) and its §9 deferral of exactly this slice. ## 2. The parity rule — DECIDED, stated before results

Placement is **allocation-bound state, like the context, not cheap state, like sampling**: a resident session's passes execute where the session was opened (its device allocation, buffers, and KV are open-time facts), and no per-request reconfiguration for placement exists on any session in the tree. The rule therefore has four parts:

1. **Session defaults govern.** At serve open the host resolves the J-036 options + the J-047 mode from the serve command line and environment exactly as a CLI surface does, validates every governing named device against the inventory at open (J-047), applies the quality use gate (J-036), resolves the per-kind precedence **once** (J-047), and checks every **fixed** outcome against the resident placement the session will actually execute (defaults conformance, §6): a session default its own resident session cannot execute refuses the open.
2. **Per-request override exists exactly where the API allows.** The three generation request shapes may each carry `prompt_on` / `drafts_on` / `reply_on` (J-036 grammar, string values) and `mode` (J-047 grammar) — §4 states the exact field placement per shape. Non-generation routes carry no placement fields: a control a route cannot use is refused there as an unsupported field (the `OllamaShowRequest` discipline, generalised).
3. **A request value is a hand statement for that one request** (the requester is the hand for their request). Per kind: **request hand > request mode preset > the session's resolved outcome** — J-047's stack with the request layer on top. Request values inherit every J-036/J-047 refusal (grammar, pass-kind legality, session kill switches, whole-choice inventory refusal): a request can never resurrect a killed device, name an absent one, or drop a member of a list. Request outcomes never mutate the session defaults and never feed the learned file.
4. **Conformance is `require_loaded_context`'s shape, applied to placement.** A request-governed **fixed** placement for the prompt or reply kind must **equal** the resident session's executed placement for that kind, or the request is refused with the reason — never silently ignored, never silently honoured, never executed by re-placing the session. A request-governed **measurement demand** (a race list, an explicit `auto`, `mode max`) is refused with its reason: measurement is an open-time act (the choosers' choices are session-kept, J-040–J-042) and no per-request measurement exists. A request that states nothing for a kind is served under the session default for that kind — that is what session defaults mean.

Drafts follows the whole road's discipline (§5): a request drafts value resolves and validates exactly like the others, but no generation route executes a draft-check pass, so drafts outcomes face no resident conformance; any future route that *would* execute one must call J-036's `require_draft_check_use()` first, which refuses until Part V.

## 3. Where the code lives

The Part III pattern — a small dedicated standalone module in `core/` plus a standalone lightest-target test suite, host contract in the module, a comment block in `aesir_engine/aesir.mojo`:

- **New module `aesir_engine/core/server_placement.mojo`** (~700 lines): the field surface (`is_server_placement_field`, `apply_server_placement_field`, `ServerPlacementRequest` — raw values + was-set flags, J-036's raw-layer shape); the session defaults (`resolve_server_defaults` → `ServerPlacementDefaults`: J-047 open validation, then J-036's quality gate, then the one `resolve_precedence`); the resident statement (`ResidentPlacement`, `resident_single`); the two conformance gates (`require_server_defaults_conformance` at open, `require_server_request_conformance` per request); and the per-request resolver (`resolve_server_request_placement` → `ServerRequestPlacement` with per-kind `ServerKindPlacement` carrying governing layer **and** provenance surface, rendered by `report()`).
- **Tests at `aesir_engine/tests/test_server_placement.mojo`** (17 groups, §7).
- **A comment block in `aesir_engine/aesir.mojo`** beside J-048's, recording the rule and the consumption gap. The module is not registered in `tests/run_all.mojo` (the J-031/J-036–J-048 precedent: registration rides with a counted run the VM's memory gate does not permit; the standalone suite is the filed evidence).

**Why the module is JSON-free.** The three parsers do not share one field machinery (the native shape walks `FlatJSON.fields()`; the Ollama/OpenAI shapes walk their own field loops), and `core/` does not import `server/` anywhere in the tree. The surface therefore claims fields by **(name, value)** pair — `apply_server_placement_field()` returns True for the four names and stores the raw value, False for anything else so the host parser keeps its own fields and its own standing unknown-field refusal. One claim function serves all three shapes without bending any parser's layering.

**Why the resolver reuses J-047's session resolution instead of re-running the stack.** The session's precedence is resolved **once at open** and kept (the choosers' session-keeping discipline, applied to the resolution itself): the per-request resolver only has to state, per kind, whether the request hand, the request preset, or that kept session outcome governs. Re-resolving the session stack per request would redo open-time work per request and could drift from the open-time verdict the defaults conformance already checked.

## 4. The field surface — per API shape

| Shape | Placement fields | Placement |
|---|---|---|
| Native `POST /v1/generate` | `prompt_on`, `drafts_on`, `reply_on`, `mode` — string values | Flat, beside `prompt` / `system` / `stream` (`fields()` already carries string-kind fields) |
| Ollama `POST /api/generate`, `POST /api/chat` | the same four names — string values | **Top-level**, beside `model` / `prompt` / `system` / `stream` — **never** inside `options{}`, whose parser consumes numbers only (§8) |
| OpenAI `POST /v1/chat/completions`, `POST /v1/completions` | the same four names — string values | Flat, beside `model` / `max_tokens` / `temperature` |
| Show / tags / ps / models / health routes | **none** | A placement field there is an unsupported field and is refused by the route's standing discipline |

Field discipline, all unit-tested: values are stored **raw** at claim time and parsed at resolve (the raw-layer shape every Part III surface uses); a placement field stated twice on one request is refused ("state it once") — never silently overridden; a name outside the four is not this surface's (the parser's own handling applies); an empty value counts as stated and is refused by the J-036 parser with its reason, not silently treated as absent.

Naming (§8): the wire names are the CLI flag names with `-` → `_` (`--prompt-on` → `prompt_on`), matching the surfaces' own snake_case field style (`num_ctx`, `num_predict`, `max_tokens`, `top_p`).

## 5. Resolution semantics — per kind, per request

`resolve_server_request_placement(defaults, request, inventory)` validates before it resolves, in a stated order, and the first refusal stops the request with its reason (no partial resolution is ever served):

1. **Parse** each stated value (J-036 grammar + pass-kind legality: an NPU named for drafts or reply refuses whole at parse, in every form) and the request mode (J-047 grammar).
2. **Kill check** against the *session's* kill switches (`validate_against_kills`): a request naming a device the session killed is refused with the placement and the switch both named. `auto` is never refused here — its field shrinks, exactly J-036.
3. **Inventory check, whole** (`validate_choice_at_open`, J-047's generalised refusal at the request layer): every device a stated choice names — single, both co-work members, every race member — must be present, or the whole choice refuses with the device, the kind, and the inventory fact in the reason. A request-mode eco that would govern a hand-silent kind is likewise checked for its fixed CPU.
4. **Resolve** per kind: **(a)** a stated kind governs as the request's hand — single/co-work as MANUAL-FIXED (verbatim, for this request), race as MANUAL-RACE (the field is exactly the hand's list), explicit `auto` as MANUAL-AUTO (a hand statement directing fresh measurement); **(b)** else a stated request mode governs its preset shape — eco as PRESET-FIXED (`cpu threads=1`), max as PRESET-MEASURE (full field), auto governs nothing and falls through; **(c)** else the session's kept outcome governs verbatim, with its own governing layer and reason carried onto the request outcome. Every outcome records its **provenance surface** (`session` / `request`) beside its governing layer, and `retrial_applies` is False on every request outcome: a request is spent with its request, so nothing about it is ever re-trialled or learned.

Two consequences are pinned by tests: a request's hand beats *its own* request preset for the stated kind while the preset still governs the kinds the hand left silent; and the session defaults are **byte-identical after any request** (a second, silent request resolves to exactly the session outcomes — the defaults are taken by value and never mutated).

**Drafts.** A request `drafts_on` resolves through the same stack and its outcome carries the G1 addendum verbatim ("choosing is not using — no generation route executes a draft-check pass, and any use still fails closed (J-036 gap G1) until Part V"). It faces no resident conformance (§6) because there is no resident drafts execution for it to conform to — the honest statement is the gate, not a comparison against nothing.

**Quality fields are not per-request fields on this surface** (§8): the quality family is session state on the server exactly as its use gate already forces — resolved with the session's J-036 options at open and gated by `require_quality_use()` inside `resolve_server_defaults()`.

## 6. Conformance — the two gates

**At open** — `require_server_defaults_conformance(defaults, resident)`: the host states the resident placement (for the CUDA service: `resident_single(DEVICE_GPU)` — prompt and reply both execute on the opened CUDA device, the `backend=cuda` its own banner/health/readiness already state; a co-work resident would be stated as the pair). Every **fixed** prompt/reply outcome in the session resolution must equal the resident set for its kind: a manual-fixed outcome compares by its whole choice (single or co-work text), a preset-fixed or learned outcome by its one device (eco's CPU; a J-044 choice's device — learned choices are single-device by record shape). A mismatch refuses the open, naming the default, its layer, and the resident truth. Measurement outcomes fix nothing and are not checked: the resident statement is by host contract the kept choice any open-time measurement produced, so they agree by construction. An **unstated** resident refuses the check itself (fail closed — conformance against an unknown truth would be a guess).

**Per request** — `require_server_request_conformance(placement, resident)`: only **request-governed** outcomes are checked (session-governed kinds were conformed at open). For prompt and reply: a request-governed fixed placement must equal the resident set, else the request is refused ("…never silently ignored and never honoured by re-placing the session; state the placement in the session defaults at open, or open the session on the requested devices"); a request-governed measurement demand (MANUAL-RACE / MANUAL-AUTO / PRESET-MEASURE) is refused ("measurement is an open-time act: the choosers' choices are session-kept and no per-request measurement exists"). If any prompt/reply kind is request-governed and the resident is unstated, the check fails closed. Filed refusal examples (from the suite, §7):

- `ServerPlacement: request placement for a prompt pass is fixed at 'cpu', but the resident session executes prompt passes on 'gpu' -- the request is refused, never silently ignored and never honoured by re-placing the session; state the placement in the session defaults at open, or open the session on the requested devices`
- `ServerPlacement: request placement for a reply pass asks for measurement (MANUAL-RACE, field [cpu,gpu]), but measurement is an open-time act: …`

The passing cases matter as much as the refusals, and are pinned: a request whose fixed placement **equals** the resident (e.g. `reply_on: "gpu"` against the CUDA resident) is honoured — the parity surface is not a blanket refusal of request placement; a request `mode: "eco"` passes against a CPU resident and refuses against a GPU resident; a silent request needs no per-request conformance at all.

## 8. Answered-locally records (clean-room)

- **Q: Per-request override, or session defaults only?** The roadmap's own sentence answers the shape ("per-request override where the API allows, session defaults otherwise"); the tree answers *where the API allows*: the API's own division is by cost of change — sampling (cheap, `configure_sampling` exists) is per-request; context (allocation-bound, no per-request resize exists) is equality-or-refusal. Placement has no per-request configure on any session and its execution state is the resident allocation, so it stands with the context: per-request values are *accepted, resolved, and validated* on every generation shape, and honoured exactly when they conform to the resident execution (§2/§6) — refused with the reason otherwise. The alternative shapes were rejected for cause: silently ignoring a stated placement (the silent-drop shape Part III refuses everywhere), and re-placing a resident session per request (no mechanics exist; claiming them would fake an integration).
- **Q: Where do Ollama's placement fields live — inside `options{}`?** Answered locally: top-level. The `options` parser consumes JSON numbers only (`parser.number()` for every value); placement values are strings in J-036's grammar. Bending the options parser to admit strings would widen a bounded parser for one family; Ollama's own shape already carries its string controls (`model`, `prompt`, `system`) top-level, so placement stands with them. The native and OpenAI shapes are flat throughout, so one claim rule (§3) serves all three.
- **Q: Does a request carry the kill switches or the quality family?** Answered locally: no to both, for different reasons. Kills are machine/session policy (J-036: a kill from any source holds for every option, not under precedence) — a requester narrowing a session's device field per request is a session-policy act, so kills stay at open; a session's kills *bind* requests (§5 step 2). Quality: its levers are unbuilt and its only honest per-request behaviour today would be refusal at use (J-036's `require_quality_use`, J-091's ladder owns the evidence), so a per-request quality field could carry no parity — quality rides the session's J-036 resolution at open, where the gate already applies, and per-request quality is roaded to J-091 rather than built as a field whose sole behaviour is refusal.
- **Q: Should a session-governed kind be re-conformed per request?** Answered locally: no. Defaults conformance is an open-time check over open-time facts (the resolution and the resident statement both exist only at open); re-checking per request would re-refuse, mid-service, a state the open already admitted — and the one case it could catch (a resident statement that was false) is a host-contract breach, not a request property. Per-request conformance therefore covers exactly what the request itself changed (§6).
- **Q: Is an explicit request `auto` a demand, or a deferral to the session?** Answered locally: a demand, following J-047's settled reading (a written auto is a hand statement directing fresh measurement; an *unset* auto is silence). A deferral reading would make `reply_on: "auto"` indistinguishable from omitting the field — except that the user wrote it — and would silently substitute the session's kept choice for the measurement the requester just asked for. As a demand it is refused with its reason (§6), which tells the requester exactly where measurement lives (the session defaults at open).
- **Q: Does `server/api.mojo`'s BifrostGate get parity too?** Answered locally: no (§1). It executes nothing and its dispatch is an honest 501 scaffold; there is no session, no request execution, and no defaults for parity to attach to. If a future slice attaches a real loop to it, it consumes this module's contract like any other host.
