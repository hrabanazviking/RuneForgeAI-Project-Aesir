## 2. Inspection — where prompt reads happen, and what progress exists today (PROVEN from the tree)

**The four read loops.** (a) **Host engine, chunked:** `AesirEngine._run_generation` (`aesir_engine/aesir.mojo`) encodes the whole prompt, prints `Prompt tokens: <N> context_length: <C>`, then loops `_forward_batch` in chunks of `_prefill_batch_cap()` (`AESIR_PREFILL_BATCH`, default **256**, workspace-clamped) — every chunk but the last pure prefill — or, at cap ≤ 1, loops `_forward_position` per token. **Inside either loop it prints nothing and records nothing**: the next output is the first generated token's print in the decode loop. (b) **Llama 3 CUDA session:** `begin_turn` (`core/llama3_cuda.mojo:496`) tokenises the whole turn, sets `prompt_tokens` **before** its loop, then loops per token (per tile-4 inside `prefill_four` where admitted), polling `control.stop_reason()` per iteration and synchronising per token/tile. It emits nothing; its only per-token state a host can read afterwards is the totals in `status()`. (c) **Gemma 4 CUDA session:** `begin_turn` (`core/gemma4_cuda.mojo:287`), the same shape at width 1 only. (d) **Streamed MoE session:** `MoEStreamSession.step` (`core/moe_session.mojo:552`) is one token per call; the harness driving the calls owns any count, and no harness in the tree counts for progress.

**What progress information exists today — the full census.** A text search of the whole engine tree for progress reporting finds **none**: the only `progress` hits are staged-write guards ("staged … write made no progress" in storage/learned-file code — file-copy loops, unrelated), and there is **no progress callback, hook, sink, or record type anywhere** (the only callbacks in the tree are FFI range callbacks for the parallel GEMM ranges and the thread pool). The one timing split that exists is the native serve route's after-the-fact total: `cli/native_serve.mojo` wraps `session.begin_turn(...)` in `monotonic_milliseconds()` and files `timings_ms: {prefill, decode}` in the **final** response object (native `/v1/generate` only; the Ollama and OpenAI routes do not even split — they carry one whole-request `elapsed`). That is J-053's F3 exactly, re-verified here from the code: a post-hoc total on one route, not watching.

**The server's structural silence (the finding this slice's wiring turns on).** On **every** streaming route in `native_serve.mojo`, the order is the same: `session.begin_turn(...)` runs to completion **first**, and only then is the stream head sent (`send_stream_head` / `send_native_stream_head`) and the decode loop entered. `begin_turn` is a blocking call with no sink, so there is no moment at which a route *could* send a progress event today even if a session produced one: during the whole read the client's connection has received nothing at all — not even headers. Progress on the server surface is therefore not a formatting task; it needs the sink in §3, and the route order (head → progress events → decode chunks) is part of that same wiring.

**What the loops already hold, per boundary — why the account needs no executor change to be *true*.** Every loop knows its total before it starts (host: `len(tokens)`; CUDA: `prompt_tokens` set pre-loop; MoE harness: its prompt list) and its own width (host cap; 1 or 4; 1), and each boundary's completion is a real program point (the chunk call returns; the token/tile commits; the step returns). The account in §4 is therefore a faithful description of quantities every loop already has — the gap is purely that nothing carries them to a surface (§3).

## 5. The reporting discipline (pre-registered)

Stated in `core/prompt_progress.mojo`'s header and here **before** the §6 shapes were run through it. A prompt read earns and emits progress records under exactly these rules:

- **R1 — Earned.** A read is **WATCHED** iff total prompt tokens ≥ **1,024** (the first of J-053's baseline lengths at which a read is long by the road's own table) **and** chunk count ≥ **4**. Below either bound the read is **SILENT**: no record is ever emitted for it, on any surface. A short prompt that finishes before a person can read a progress line must not be dressed in progress spam to look instrumented; a single-chunk read has no "how far" to report however long it is.
- **R2 — Boundary-only.** Records exist only at chunk boundaries — after chunk *k* completes, never inside a chunk, never per token. `tokens_done` is therefore exactly what the executor has actually read at that boundary: a record never reports a token not yet read.
- **R3 — Step throttle.** Even at boundaries, a record is emitted only when the read crosses its next **10% step**: emit at boundary *k* iff ⌊bp(k)/1000⌋ > ⌊bp(k−1)/1000⌋, bp the floored basis-point fraction — plus the final boundary, always (R4). A watched read therefore emits **at most 10 records however fine its chunks are**: the step, not the chunk width, is the throttle, so no surface can spam by being narrow.
- **R4 — Final exactly once.** The boundary that completes the read emits the one final record (done == total, fraction exactly 10,000 bp, `is_final`). No earlier boundary can carry those values, and no record exists after it.
- **R5 — Monotonic.** Tokens done strictly increases and emitted fractions strictly increase across a read, by construction: boundaries are ordered and done is min(k × width, total).

One honesty clause rides with the discipline, as in J-057/J-058: **it grades counts, never time or usefulness.** It says when a surface may speak and what the record must contain. Whether the resulting lines actually keep a user oriented on a real long read — and whether they cost anything — is §7's measured question, and no §6 count may be cited as evidence for either.
