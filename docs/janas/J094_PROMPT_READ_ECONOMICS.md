## 1. The question — and the honest shape, stated up front

**Question.** What does it cost Aesir to *read* a 32k prompt — and what does Part IV's prefill work (J-053's anatomy, J-054's block prefill, J-055's whole-layer placement, J-056's split prompt) do to that cost?

**The shape this slice can honestly take, decided from evidence before building.** A 32k read *time* needs a live run of the 7B witness at 32k context. This tick neither machine can run one: the VM is far below its inference gate and purplelongship is unreachable. The standing Part VI pattern (J-091 §1, J-092 §1, J-093 §1) therefore governs: **price the read exactly in the currencies the tree's own modules define, inherit the ladder's verdicts unchanged, and file every wall as NOT PROVEN / DEFERRED-WITH-REASON to the J-098 gate with an exact recipe (§7).** No rate is fitted and no accounted quantity is converted into a claimed time anywhere in this slice: the record's only Coder walls sit under different placements at their two contexts (whole-GPU @4096, spilled @16384), so any rate fitted through them would attribute placement cost to the read — the refusal J-092 §3 filed for the time split, standing here for the whole wall.

**The findings, in one paragraph.** The 32k read of the ladder witness (Qwen2.5-Coder-7B Q4_K_M, sha256 `8053aeda222ba79e865a6eddd268332fd4e4dbe406371318d6df1f9beae9502b`, 4,683,074,688 B) is accounted at **321,576,079,720,448 MACs of work** (attention 107,755,427,856,384 + projection 213,820,651,864,064; a mean of 9,813,723,136 MACs per token), leaves **1,879,048,192 B of KV** behind at f16, and touches — as by-construction shapes — **30,787,265,101,824 B of KV reads**, plus weight-pass bytes that depend entirely on the surface's pass count: **599,433,560,064 B on the host's batched plan (128 passes)** against **153,454,991,376,384 B on the GPU line's width-1 plan (32,768 passes)**, for total touch shapes of 31,388,577,710,080 B (host form) and 184,244,135,526,400 B (GPU form). **Only one line can run this read as constructed today: the GPU line at f16, ACCOUNTED, with placement SPILL_REQUIRED** (admission 6,567,534,208 B against the filed usable 5,368,709,120 B). The CPU read is **CAP_REFUSED** (the host's 16,000-token cap), and every int8 read cell is **INTEGRATION_BLOCKED**. Part IV's priced effects (§6): host chunking is the one existing choice that moves the account — it removes exactly 152,855,557,816,320 B of weight-pass shape against the per-token fallback and changes no work or KV quantity; J-054's block prefill would move the GPU line's weight shape and syncs by the same chunk factor but is UNBUILT, so its effect today is zero; J-055's whole-layer placement changes **no** accounted read quantity at all; J-056's split is not kept (its own rule grades it rejected where a parent exists and parent-absent at the 32k rung); and 8-bit KV would cut the KV-written bytes by 910,163,968 and the KV-read shape by 14,912,581,533,696 at 32k while changing no work quantity — behind an integration that does not exist yet.

## 2. Definitions and verdict rules (pre-registered)

Stated in `core/prompt_read.mojo`'s header and committed (@ `635bc62c`) before the harness was built or run. The witness is J-091's (above): 28 layers, hidden 3,584, ffn 18,944, 28 query heads, 4 kv heads, head_dim 128, vocab 152,064, profile context cap 32,768.

- **Prompt read** at rung L = the prefill pass over a raw prompt of exactly L tokens, cold, no prefix reuse, ending when the KV of position L−1 is written. It is J-091's READ leg, so its session context is **L itself** (caps and admission judged at L, never L+128 — the write leg's session, J-091/J-093).
- **Work** = prefill attention MACs + prefill projection MACs, defined through `core/kv_ladder` over `core/prefill_anatomy` (J-053). **The one LM-head pass (544,997,376 MACs) is not part of the read**: on every dense surface it is paid by the first *generated* token (J-053 §3.7; J-091's prefill projection column excludes it). It is priced separately as the first-token hand-off, so it is never lost and never double-charged. (Consequence, filed to prevent miscitation: this slice's attention share of read work at 32k is 335,085 ppm; J-092's prompt-average share is 335,084 ppm — the same totals, differing only because J-092's rest includes that head pass.)
- **KV written** = `ladder_kv_total` at L per precision (f16 57,344 B/token via J-087; per-row int8 29,568 via J-088). **KV read shape** = per-token KV price × causal pairs, through `core/attention_share` (J-092's prefill traffic form). **Weight-pass bytes** = passes × the file's bytes, passes from the surface's own plan in `core/prefill_anatomy` (J-053). **Total touch shape** = KV read shape + weight-pass bytes + KV written, per surface and precision. All three byte quantities are by-construction *touch shapes* in J-091/J-092's sense — caches sit between every shape and any device; none is a measured byte count.
- **Surfaces filed:** the host batched plan (chunk cap 256, the tree's default) and the width-1 plans (host per-token fallback; the GPU line's Coder prefill). **No tile-4 Coder account is filed**: the tile is admitted only for the exercised Llama 3.2 3B profile (J-091 §3) — pricing one for Coder would invent a surface.
- **Sync crossings:** the GPU width-1 line pays one device synchronisation per token (J-053 §3.8, J-055); the host surfaces pay none.
- **Verdicts:** J-091's `ladder_cell_verdict` at LADDER_READ, inherited unchanged (integration judged before caps): ACCOUNTED / CAP_REFUSED (host cap 16,000 on the CPU line; profile cap 32,768 on the GPU line) / INTEGRATION_BLOCKED (int8 integrated on neither line). **GPU read placement:** `ladder_gpu_required_bytes` at context L against the filed usable VRAM 5,368,709,120 B (J-031) → WHOLE_GPU / SPILL_REQUIRED. The int8 columns are counterfactuals (CF) wherever they appear.
- **Part IV effect forms** (pre-registered in the module header): each Part IV choice is priced as an exact delta on this account, or stated as changing no accounted quantity — host chunking (exists), J-054 block prefill (UNBUILT counterfactual through its own planner's constants), J-055 whole-layer (the width-1 identity), J-056 split (through its own plan + survival rule), KV precision (J-088's store, integration deferred). No other Part IV slice defines a prefill quantity for this witness, and no delta is invented for one (§3).

## 6. What Part IV's prefill does to the number

Each choice priced exactly on §5's account, or stated plainly as moving nothing. Deltas are @32,768 unless a rung is named; all are ACCOUNTED arithmetic, none is a time.

**(a) Host chunking (J-053) — exists today; the one surface choice that moves the account.** Cap 256 vs the per-token fallback: passes 128 vs 32,768, weight-pass bytes 599,433,560,064 vs 153,454,991,376,384 — a delta of exactly **152,855,557,816,320 B** (32,640 fewer passes × the file's bytes; at 1,024 the same delta is 4,776,736,181,760). Work delta: **zero** (the touch-shape difference between the two host surfaces equals the weight delta exactly at every rung — the tests assert it — so chunking's work and KV deltas are zero by construction, J-053 §3.3). The one measured wall effect of chunking in the record (S-033, a different model, walls −9–14% for chunk 32→256, re-cited in J-053 §6) is MEASURED-INDICATIVE prior evidence and is **not** converted into a ladder wall here.

**(b) GPU block prefill (J-054) — UNBUILT; counterfactual only; effect today exactly zero.** Its own plan at width 256 for the 32k read (cross-checked field-by-field against `plan_gpu_block_prefill`, §8): 128 chunks, 128 sync crossings (vs 32,768 width-1), 25,088 batched GEMM calls (128 × 28 layers × 7 projections), **2,752,512 per-row attention calls — unchanged** (attention does not batch, J-053 F2: the plan counts them, it does not hide them), weight-read bytes 599,433,560,064 (the host-batched figure — the chunk factor is the same arithmetic on either device), admission **UNBUILT**. Work and KV deltas of the plan: **zero**. So if M1+M2+M5 land, the GPU read's *traffic character* flips from §5.2's weight-streaming shape to the host's KV-shaped one, and its sync count falls 256-fold; until they land, Aesir's GPU read account is the width-1 account in §5, and this counterfactual changes no filed number.

**(c) Whole-layer dense on GPU (J-055) — changes no accounted read quantity; said plainly.** At width 1 the whole-layer account *is* the GPU line's account in §5 (passes == syncs == L at every rung — pinned in the tests as the identity it is). There is no delta to file: whole-layer placement is a residency verdict (it decides, with J-091/J-093's admission arithmetic, *whether* the GPU line can hold a model at a context), not a read-cost lever. Its block form is (b)'s counterfactual under another name.

**(d) Split prompt (J-056) — not kept; effect today zero; its own rule grades the witness's rungs.** Priced through `plan_split_prompt` + `evaluate_split_accounting` with per-side weights stated as the file's floor half / remainder (J-056's synthetic-halves precedent; the verdict does not rest on the ratio) and the whole-GPU-parent flag taken from §5.3's f16 read placement: at the rungs where the parent exists (1,024 / 4,096 / 8,192) the split is **ACCOUNTED-AND-REJECTED** — total MACs and weight bytes conserve exactly against the read account (the split's total at 8,192 *is* §5.1's 60,190,493,769,728), while crossings worsen (96 vs the GPU parent's 32 and the host parent's 0 at 8,192) and join bytes are added (117,440,512 at 8,192; **469,762,048 at 32,768**, = L × hidden × 4). At 16,384 / 32,768 the parent does not exist (spill rungs), so the rule grades **PARENT-ABSENT**: the shape there is J-021's proven spill geometry, neither a win nor a rejection. The executor (S1–S3) does not exist in any case.

**(e) KV precision (J-088's 8-bit store; integration deferred) — moves bytes exactly, work not at all.** f16 → int8 at 32,768: KV written **−910,163,968 B** (27,776 B/token × 32,768), KV read shape **−14,912,581,533,696 B** (27,776 × pairs) — roughly halving both KV terms (ratio 0.5156 with scales). Work delta: **exactly zero** — MAC counts are precision-invariant (J-092 §3; the module's work functions take no precision, so the zero is by construction, not by measurement). Admission delta: the 16k read would hold whole-GPU (§5.3 CF column); the 32k read still spills. And every int8 cell is INTEGRATION_BLOCKED today: these deltas price a store that exists as a component behind a session integration (J-088 §7) that has not landed.

**The Janas comparison, shape/form only.** Janas's published figure names a *time* (15 minutes for its laptop to read a 32k prompt). Aesir's answer in this slice is an *account* (the §5 tables) with its time explicitly NOT PROVEN (§7). The two are not the same currency and no conversion is filed: Aesir's 32k read time will be whatever the §7 legs measure on Aesir's hardware, filed beside this account, and until then the honest Aesir number for the roadmap's question is the account itself — 3.22×10¹⁴ MACs, 1.88 GB of KV written, a 30.79 TB KV-read shape, and a pass count that Part IV's chunking discipline sets at 128 (host) while its unfinished block work leaves at 32,768 (GPU).

## 7. Deferred legs — the live read (DEFERRED-WITH-REASON; recipe for the J-098 gate to re-cite)

**Why deferred:** the VM stayed far below the 5,500 MB inference gate all tick (MemAvailable ~0.58–1.87 GB) and purplelongship is unreachable and 204-owned when it returns — no read wall could run on any box. The int8 legs are additionally blocked on J-088 §7's integration, and the CPU 16k/32k read cells are CAP_REFUSED as constructed (step 4 handles them explicitly; nothing here waives a cap silently).

**The recipe, in dependency order:**

1. **Window and machine discipline:** purplelongship in a guarded idle gap (204 state heartbeat checked first; yield to a live 204 run) for the GPU line and the primary CPU line; the VM behind MemAvailable > 5,500 MB is an acceptable CPU-line substitute only. One heavy run at a time; per run file load, MemAvailable/VRAM, Tctl, and `nvidia-smi` state. Median of 3 runs per cell is the filed wall; a single run files as MEASURED-INDICATIVE.
2. **Re-pin before running:** sha256 of the Coder Q4_K_M file on the box must equal `8053aeda222ba79e865a6eddd268332fd4e4dbe406371318d6df1f9beae9502b` (4,683,074,688 B) before any leg; a file that does not verify does not run.
3. **Read legs (f16 first; int8 only after step 6):** per ACCOUNTED read cell of §5.3, one raw prompt of exactly L tokens from the road's prompt corpus (token count verified on the run; no chat template, no BOS manipulation). CPU line: host batched path with the chunk cap stated (default 256) and a per-token (cap-1-named-as-such) leg beside it, so §6(a)'s accounted weight delta gets its measured counterpart. GPU line: dense CUDA session at context L, placement per §5.3 (whole through 8,192; spilled from 16,384 with `exec_layers` recorded), width-1 passes as the Coder profile admits; if J-054's M1+M2+M5 have landed by gate time, a block-width leg at 256 runs beside the width-1 leg and files as the §6(b) counterfactual's measurement, labelled with its width. File the prompt-fill wall and tok/s = L / wall; where the serve path cannot separate tokenize+admit from fill, file the serve wall and say so (J-053 §3's census stands: no phase timer exists — a timer added before the gate may split it, filed as its own instrument). First-token latency (fill + the §2 head pass + sampler) is filed separately, never folded into the fill wall.
4. **Cap-refused CPU cells:** the 16k/32k CPU reads stay CAP_REFUSED in the closed table unless the gate first lands an explicit cap decision — lift `MAX_RUNTIME_CONTEXT` for the leg, or drive the leg through an explicitly-sized cache — recorded as a decision with its own slice (J-091 §7 step 4's rule, applied to reads).
5. **Comparator (llama-bench-class, conditions stated where they cannot be identical):** on the same box and file, `llama-bench` pp at each rung (pp32768 at the top), default f16 KV. The conditions that cannot be made identical, stated in advance (J-091 §7 step 5, inherited): llama-bench drives synthetic token ids through its own batching (its `-b`/`-ub` stated in the filing) with no tokenizer or template, while Aesir drives tokenized raw text through its own paths (batched host / width-1 or block CUDA); per-token work shapes are this slice's pinned counts on both sides, but token content and batching differ, so the comparison files as pp-class numbers side by side, never as faithfulness evidence. 6. **Int8 legs:** only after J-088 §7's integration lands per line (host path for CPU, dense CUDA for GPU), each behind `--kv-precision` with f16 default, and each path's J-089 §7 paired grade (step 7) passed at the ladder's lengths before its walls are filed as read cells; until then int8 read cells keep this slice's INTEGRATION_BLOCKED verdict in any gate table.
7. **Faithfulness of every Aesir row:** ids-first, then teacher-forcing rank + logit gap against the ggml CPU comparator on the raw prompt (CPU engine vs CPU comparator only; **never `llama-cli --single-turn`**), per J-089 §7 steps 4–6; a reference that fails files COMPARATOR_ARTIFACT with its kind named and is re-run, not debated.
8. **Registration:** with the counted live run, register `test_prompt_read` in `tests/run_all.mojo` and re-account the pin (J-031 §10's rule).
