## 1. Question and ground

**Question.** Part III built placement as eleven separate pieces, each with its own report in its own vocabulary: J-036's options, J-037's inventory, J-038/J-039's measured candidates, J-040–J-042's choosers, J-043's co-work planner, J-044's learned file, J-045's re-trials, J-046's tolerance proof, J-047's precedence stack, J-048's contention rule, J-049's server parity. When a user (or a developer debugging a surprising placement) asks the single question *"why is this pass running there?"*, no one surface answers it whole: the chooser record knows the numbers but not the learned state; the precedence resolution knows the governing layer but not the candidates; the learned report knows the stored choice but not this session's measurement. J-045's module header already pointed at this slice by name ("J-050's explainability surface will cite both"). What is the one report that answers the question, per pass kind, from exactly the pieces that already exist — and what does it honestly say for the parts that were never measured?

**Ground, and only that ground — the pieces as this tree actually has them, read first-hand for this slice:**

- **The chooser records are the candidate truth.** `PromptChoiceRecord` / `ReplyChoiceRecord` / `DraftChoiceRecord` each carry, in identical shapes: the resolved option text/form/source, the decision code + text, `has_choice` + the chosen label/device/threads, the best and runner-up labels + medians, the margin percent and separation flag, and the whole `measurements` list — each measurement a label, device, thread count, a status in the shared vocabulary (measured 0 / excluded 1 / unmeasurable 2 / bound-stopped 3 — the codes coincide across the three choosers, as J-046's module already records), a verbatim reason when it did not measure, and a `TimingSummary` (count / median / min / max / spread, ns) when it did. Each measurement renders itself (`render()`), and each record renders itself (`report()`).
- **Precedence is J-047's kept resolution.** `OverrideResolution.for_kind()` gives, per kind, the governing layer code, the provenance in words, the fixed text or the measurement field, whether a re-trial could apply, and the reason the layer governs. `governing_name()` names the layer.
- **The learned state is J-044's load + lookup.** `LearnedLoad` (status MISSING / LOADED / REFUSED with reason and path, entries whole) and `LookupResult` (APPLIED with the entry, or a named mismatch — NO-ENTRY / MACHINE-MISMATCH / MODEL-MISMATCH / BOTH-MISMATCH / NOT-LOADED — with its reason). An applied `LearnedEntry` renders its own key (machine + model shape), its measured-at stamp, and each kind's stored choice via `LearnedPassChoice.render()` (present with placement/device/threads/decision/option provenance, or absent).
- **Re-trial state is J-045's plan.** `RetrialPlan` (state KEEP / DUE / MANUAL-ONLY / KEY-DRIFT, trigger, age + opens, per-kind due flags, reason) is a pure function of the entry, an injected clock, an injected opens counter, and the current key.
- **The standing context pieces.** J-037's `DeviceInventory.device_line()` (the bench-style device line: what exists or why not); J-043's `CoworkRecord` (per-pair plans + verdicts, `survived_count()`, the outcome line); J-046's `ToleranceProof` (per-shape, per-kind `RepetitionGrade`s with verdicts BEATEN / MET / MISSED / NOT PROVEN against the pre-registered targets); J-048's `PlacementPressurePlan.describe()` (one contention decision in full); J-049's `ServerRequestPlacement` (per-kind `ServerKindPlacement` with governing layer, session/request provenance, fixed choice or measurement field, and reason).
- **The gap every Part III slice records stands:** no live session in the tree consumes a placement plan yet, and no surface prints any of these reports in a live path. The explainability surface therefore inherits the same honest shape: a host contract, not a wiring.
- No Janas source was opened; none was needed — the subject is Aesir's own debugging surface. Questions the ground does not answer are answered locally in §6.

## 2. The report — DECIDED, stated before results

The report shape was pre-registered in the new module's header before any J-050 result existed, and `report()` implements exactly it:

1. **Header** naming the surface and the honesty rule (assembled from J-036–J-049 and nothing else; a fact no supplied piece carries is stated as its absence).
2. **The inventory line** (J-037's device line, verbatim).
3. **The options line** (J-036's resolved `describe()` + the J-047 mode name).
4. **The learned-file state in full**: the load state line (status, path, entry count or refusal reason), the lookup line (status + reason), and — when an entry applies — the entry's own rendering (key, measured-at, per-kind stored choices).
5. **Per pass kind, in prompt / drafts / reply order, one block** with exactly these lines: `option`, `governing` (layer + provenance + fixed/measure + reason), `decision` + `choice` (or `choice: NONE` on a chooser refusal), `best:` (best + runner-up medians, margin, separation — when the record carries them), `candidates (N considered, M measured):` with one line per candidate in the chooser's own rendering, `learned:` (the kind's stored choice inside the applied entry, or the named reason none applies), `re-trial:` (the plan's state for the kind, or its stated absence), and the kind's extra lines where supplied (prompt co-work, tolerance summary, device-sweep / axes notes verbatim).
6. **Context lines**: the J-048 pressure plan when supplied (else its stated absence), and the J-049 server note when per-request outcomes were supplied.
7. **Closing honesty lines**: candidate numbers are the supplying choosers' own harness numbers on the machine that measured them, in that window — not model pass timings; no placement verdict for any model is made; a kind with no chooser record was never measured here and says so; the NPU stands as the inventory states it (parked, never probed, never run).

**The two honesty rules the shape enforces.** *Never-measured is a statement, not a blank:* a kind with no chooser record renders `choice: NOT STATED -- no chooser record was supplied for the <kind> kind, so this kind was never measured in this explanation and no candidate numbers exist to show` and `candidates: none recorded (never measured)` — the report distinguishes "measured and excluded (GPU absent, NPU parked)" from "never measured at all" on its face. *Assembly invents nothing:* `assemble_placement_explanation` is pure assembly — it measures nothing, resolves nothing, and looks nothing up; every number and reason in the report is a supplied piece's own, carried verbatim (candidates through the choosers' own `render()` lines, converted — not re-derived — by `explain_candidate_from_prompt/reply/draft`).

**The flag.** `--explain-placement` is a bare boolean reporting flag (`scan_explain_placement_args`): it asks for the report and changes no placement, takes no value (a `--explain-placement=<anything>` form is refused as mistyped), and stating it twice is refused — the argv discipline of the surfaces it joins. It is not an option in J-036's grammar and enters no precedence.

## 3. Where the code lives

The Part III pattern — a small dedicated standalone module in `core/` plus a standalone lightest-target test suite, host contract in the module, a comment block in `aesir_engine/aesir.mojo`:

- **New module `aesir_engine/core/placement_explain.mojo`** (~640 lines): the flag (`EXPLAIN_FLAG`, `is_explain_placement_flag`, `scan_explain_placement_args`); the candidate conversion (`ExplainCandidate` + the three `explain_candidate_from_*` builders, carrying label / status / median / min / max / spread / rounds + the chooser's verbatim line); the learned state (`LearnedExplainState` + `learned_state_from(load, lookup)`); the per-kind block (`KindExplanation` with its candidate counts and rendering); the inputs bundle (`PlacementExplainInputs` — every predecessor piece optional-by-flag); the assembler (`assemble_placement_explanation` → `PlacementExplanation.report()`); and the small restated name tables (candidate statuses, chooser decisions, tolerance verdicts — restated, as J-046 restates the PM_* codes, so this module imports no name two predecessors both export).
- **Tests at `aesir_engine/tests/test_placement_explain.mojo`** (13 groups, §5).
- **A comment block in `aesir_engine/aesir.mojo`** beside J-049's, recording the surface and the consumption gap. The module is not registered in `tests/run_all.mojo` (the J-031/J-036–J-049 precedent: registration rides with a counted run the VM's memory gate does not permit; the standalone suite is the filed evidence).

**Why an inputs bundle, not a live builder.** Every predecessor piece is produced at a different moment by a different owner (the choosers at open, the learned load + lookup at open, the re-trial plan on demand, the pressure plan where contention is decided, the tolerance proof only when the J-046 proof is run, the server outcomes per request). A builder that reached for them itself would have to own all those moments — it would be a session, which is exactly the wiring this road has not built. The bundle states the contract instead: a surface hands the assembler exactly what it kept, flags what it did not, and the report's absences are therefore truthful statements about that surface's open, auditable from the report alone.

**Why the governing line prefers J-049's outcome when supplied.** Where a server request governed a kind, the truthful answer to "why this placement, for this request?" is the request layer's outcome (its governing layer, its session/request provenance, its reason) — the session resolution it rode on is still in the report (the options line and, for silent kinds, the outcome itself carries the session resolution verbatim). Where no server outcomes are supplied, the governing line is J-047's resolution verbatim. Either way the layer and its provenance are named on the kind's own block; there is no kind whose governing layer the report leaves implicit.

## 4. What each kind's block states — semantics

**Candidates.** Every measurement on the supplied chooser record, in record order, in the chooser's own words: a measured candidate shows `median / min / max / spread / rounds` (the harness's numbers, converted field-for-field and pinned by the conversion tests); an excluded candidate shows `EXCLUDED -- <reason>` (e.g. a GPU the inventory states absent); an unmeasurable candidate shows `UNMEASURABLE -- <reason>` (the parked NPU; every draft-check candidate, J-035 gap G1); a bound-stopped candidate shows its partial counted rounds, marked not ranked — exactly the choosers' own rendering discipline. The block header counts considered vs measured so a field of exclusions cannot masquerade as a measured field.

**Choice.** The chooser's decision name + text and its chosen label, or `NONE` when the record is a refusal (a refusal is not a choice — J-044's discipline, kept). The best/runner-up line carries the numbers the decision stood on (medians, margin %, separation) when the record carries them; a sole-measured record carries no runner-up line and none is invented.

**Governing.** §3's rule. A hand-fixed kind names MANUAL-FIXED and its fixed text; a learned kind names LEARNED and the stored choice it applied; a silent kind names AUTO and its measurement field (the kill-shrunk auto field, as J-047 computed it). The reason is the governing piece's own reason text, verbatim.

**Learned.** Inside an applied entry: the stored choice in full (`placement (device, threads, decision, from option; entry measured-at)`) or `absent in the applied entry` for a kind nothing was learned for. Without an applied entry: the named state — the lookup's status and reason (MISSING file, REFUSED file, MODEL-MISMATCH, …) — so "no learned choice" always says *which* no it is. Without any supplied load: `NOT STATED`, a different sentence from every one of those, because an unsupplied load is the explanation's gap, not the file's state.

**Re-trial.** The supplied plan's state for the kind: `DUE for this kind (trigger …)` or `not due for this kind`, with the plan's age/opens and its reason — including MANUAL-ONLY (a hand choice is never re-trialled) and KEY-DRIFT, which the plan states as not-a-re-trial at all. No plan supplied renders the cadence's absence, never a guessed due state: the cadence's inputs (clock, opens counter) are the host's, and an explanation that invented them would be fiction.

**Extras.** The prompt kind carries the J-043 line (pairs planned, pairs survived, outcome text) or its absence. Every kind carries its J-046 tolerance summary when grades were supplied (per-kind repetition verdict counts against the pre-registered targets; drafts renders the standing `NOT PROVEN` G1 line). Chooser sweep/axes notes ride verbatim. The pressure plan is report-global (it is one pool decision, not a per-kind one) and renders in the context lines with its full `describe()` numbers.

## 6. Answered-locally records (clean-room)

- **Q: Does the explanation re-run any measurement, resolution, or lookup itself?** Answered locally: no — pure assembly (§2). Re-running would make the report a second, divergent source of the very truths it exists to explain (a re-measured field could disagree with the session's kept choice and the report would then explain a choice that was never made). The pieces a surface kept at open are the explanation's ground; what it did not keep, the report states as absent.
- **Q: Where does `--explain-placement` live in the option grammar — is it a J-036 option?** Answered locally: no. It changes no placement, takes no value, and has no env equivalent and no precedence; it is a reporting flag scanned beside the option scans (J-036's / J-047's scan pattern), exactly as a `--help`-class flag stands beside a grammar without joining it. Giving it a value form or a precedence would let a debugging surface argue with the placement it reports.
- **Q: Should the report grade the choice (was it a good choice)?** Answered locally: no. Grading is J-046's proof, with its pre-registered repetitions and targets; the explanation *cites* its verdict counts where grades are supplied and otherwise stays a record. A per-open report that re-graded on one sweep would contradict J-039/J-041's proven sweep instability and J-046's whole design.
- **Q: One global learned section, or the learned state per kind as well?** Answered locally: both, deliberately. The load/lookup/key facts are entry-global and are stated once in full (§2 step 4); the stored choice and re-trial due state are per-kind facts and stand in each kind's block, so a reader of one block never has to cross-reference another section to answer for that kind. The duplication is of *citation*, not of truth: both renderings come from the same supplied entry.
- **Q: Does the drafts kind get a thinner block?** Answered locally: no — the same lines, with the same honesty. Its chooser record (J-042) is a real record whose candidates are unmeasurable-with-reason and whose outcome is a fallback/refusal shape; rendering it thinner would hide exactly the G1 state a debugging user most needs to see stated plainly.
