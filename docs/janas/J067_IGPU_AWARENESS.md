## 1. The iGPU's real shape — and the verdict rule, stated before building

**The shape.** An integrated GPU differs from a discrete GPU in kind, not in degree:

1. **No VRAM of its own.** The bytes a probe or vendor tool calls an iGPU's "device memory" are the same system RAM the CPU, the Part II expert cache, and the OS share. Its pool identity is the **system pool** — the one contested pool of J-048's rule — never a second pool beside it.
2. **Its usable budget is an allowance, not a pool.** It is drawn from the system pool and charged in J-048's order: placement fixed bytes first and in full, the expert cache elastic after them, the cache floor (one token's full routed demand, J-028) held. A discrete division (J-031: resident + KV/activation/reserve charged against a stated *usable device budget*, the remainder a device cache) applied naively to an iGPU makes two errors at once: it charges the iGPU's bytes against a pool that does not exist separately, so the machine's total becomes *system pool + claimed VRAM* — the same bytes counted twice, the J-026-class over-commit error (two consumers each sizing against the full snapshot) in device dress — and it treats the device as isolated when every byte it touches contends with the CPU side.
3. **There are no transfers to tax as copies.** J-031's per-token account prices H2D/D2H bytes and synchronised crossings because a discrete card sits across a bus. An iGPU sits on the shared memory fabric: the data is already where both processors can read it. The honest tax is **bandwidth contention** — every byte a prefill pass touches (weights + activations + KV) competes for the shared fabric with every byte the CPU side touches in the same window. The tax is therefore priced in **bytes contended**, never in copy bytes (zero, by construction) and never in time (no iGPU bandwidth figure exists in this tree's record, and none is invented here).

**The verdict rule (pre-registered; mechanical in `core/igpu_account.mojo`, `evaluate_igpu_claim`).** Which placements the account permits an iGPU to win on accounting alone, and which it refuses to decide without a live measurement:

- **PERMITTED by accounting alone:** admitting an iGPU *prefill* placement as a candidate, and choosing it as the placement of record, when its fixed bytes fit the shared allowance and the expert cache keeps its floor after them — with no speed claim attached. Accounting also **REFUSES outright**, with no measurement able to cure it: a placement whose fixed bytes do not fit the shared pool, or that would leave the required cache below its floor, or whose budget was derived additively.
- **REQUIRES a live measurement (the account refuses to decide):** any claim that iGPU prefill is *faster* than the same machine's CPU prefill (or slower, or equal — all three are measurements); any *reply*-pass win for an iGPU (the J-041 question: single tokens, the smallest work per pass, where per-token fixed costs meet the bandwidth tax — never decided by accounting); any co-work split ratio; any bandwidth, wall, or tok/s figure whatsoever. A speed claim backed by a live measurement that actually measured faster than the same machine's CPU line is permitted — by the measurement, not by the account.

## 4. What was built — the iGPU shape in the placement layer

**`aesir_engine/core/igpu_account.mojo`** (new, a sibling account module in the J-066 grain — the placement/inventory modules' grain is pure per-slice account modules consumed by hosts, cf. `moe_gpu_plan.mojo`, `placement_pressure.mojo`, `vulkan_port_surface.mojo`; extending those modules in place would have mixed the discrete and shared shapes into one planner and risked the filed discrete proofs). It executes nothing, opens no device, and contains no speed:

- **Device kind distinct from discrete:** `GPU_KIND_NONE / GPU_KIND_DISCRETE / GPU_KIND_INTEGRATED`, with `pool_for_gpu_kind` (integrated → `POOL_SHARED_SYSTEM`; discrete → `POOL_SEPARATE_DEVICE`), `shares_system_pool`, and `has_own_vram` (discrete only). Unknown kind codes are refused.
- **Shared-pool budget derivation:** `plan_igpu_budget(system_pool, placement_fixed, reserve, cache_open, cache_floor, expert_body)` — J-048's order in the one system pool: fixed bytes (J-031's charging order: resident + KV + activation/scratch, plus reserve) first and in full; the cache last, elastic, capped at its open-time budget and at the expert body where stated. The plan states its **allowance** (`pool − floor`: the most fixed bytes the pool can carry while the cache keeps its floor), its decision (`FULL` / `SHRUNK` / `REFUSE`), and `total_charged_bytes`, which **never exceeds the system pool**. Below the floor, and for fixed-over-pool, the plan is REFUSE with the numbers stated — no consumer is cannibalised. `correct_total_bytes` vs `naive_additive_total` name the double-count and its size: the correct total for an iGPU machine is the pool, once.
- **Prefill-placement bandwidth-tax account:** `plan_igpu_prefill_tax(weights, activations, KV, cpu_co_load, claimed_copy_bytes)` returns `copy_bytes_charged = 0` by construction, `contended_bytes = weights + activations + KV`, and `shared_traffic_bytes = contended + cpu_co_load`. **What is charged:** the bytes the pass touches on the shared fabric, plus the CPU side's concurrent bytes the caller states. **What is not charged:** copies (none exist), time (none is known), and any per-token launch cost (a live-measurement quantity). A caller stating nonzero copy bytes for an integrated device is **refused**, not silently zeroed — that statement is the discrete shape leaking back in, and the caller must restate the pass in the iGPU's shape.
- **The claim verdict:** `evaluate_igpu_claim(fits, floor_holds, is_prefill, claims_speed_win, live_measured, measured_faster)` — §1's rule in pure form (§5 pins every branch).

**Host contract** (in the module docstring, binding): classify kind from inventory truth (integrated only when the machine's own sources say its memory is shared; never assume shared, never assume separate without a probe); for an integrated device use this account against the one system pool — never `plan_moe_gpu_division` with a claimed VRAM figure; price claims through the tax + verdict before stating them; run §7's recipe on the first iGPU machine before quoting any number. This slice wires the module into **no live session path**: no session can execute on an iGPU today (J-066 DEFER), and claiming integration would fake it.

## 6. Worked shape — what changes on an iGPU machine (accounting only)

On a hypothetical 32 GiB shared-pool machine (an illustration of the arithmetic, **not** a machine in hand and not a measurement): a discrete treatment would state 32 GiB system + a claimed "8 GiB VRAM" = 40 GiB of placeable memory; the account states 32 GiB, once. A prefill placement with 6 GiB fixed bytes and a 512 MiB cache floor is charged 6 GiB against the pool, the cache takes up to its open budget from the remaining 26 GiB, and the floor holds — or the plan refuses, with numbers, if a larger placement would break the floor. The same pass's tax is its touched bytes (weights + activations + KV) plus whatever the CPU side touches concurrently — and whether that placement *beats* the CPU line on that machine remains, in full, a §7 measurement.

2. **Budget legs:** run `plan_igpu_budget` on the machine's real pool + a named model's directory-true fixed bytes, and verify on the live machine (resident measurements at open) that charged + headroom closes on the pool and the expert cache's floor holds under a co-runner taking RAM (J-028/J-048 discipline). 3. **Prefill placement legs:** the same sha-pinned model + prompt set, prefill placed (a) CPU-only, (b) iGPU under the account — via whatever backend exists then (J-066's reopen decides the road; this leg does not presume it). Median-of-3 walls per leg, machine state per run (loadavg, thermals, MemAvailable); cells under contention/thermal distress are MEASURED-INDICATIVE.
4. **Shared-bandwidth tax measured under CPU co-load:** leg (b) repeated with a bounded CPU co-runner (J-023 shape) doing stated memory traffic; the degradation vs leg (b) idle is the first measured tax figure, filed against the account's contended/shared-traffic bytes for the same passes — the account is graded, not just quoted.
5. **Reply leg (the J-041 question):** single-token placement measured under the same discipline; an iGPU reply win is claimed only if it clears J-041's hurdles on measurement.
6. **Faithfulness:** any session leg graded ids-first vs the same surface's CPU ids, then teacher-forcing rank + logit gap vs the ggml CPU comparator on the raw prompt — never `llama-cli --single-turn`; near-tie band and step-0 class as standing.
