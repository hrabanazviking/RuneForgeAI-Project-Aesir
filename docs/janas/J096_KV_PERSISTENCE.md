## 1. The question — and the honest shape, stated up front

**Question.** Should a session's KV be saved to a file at session end and restored at the next open, so the long prompt is read once instead of every time? The roadmap's three sub-questions, in its own order: is the benefit real (measured), what privacy/storage shape does the saved data demand (decided on evidence), and — only if it pays — what gets built?

**The shape this slice can honestly take, decided from evidence before building.** A live restart benefit (a wall, a tok/s) needs a session that can consume a restored KV, and none exists: J-088 §7 deferred the int8 session integration and J-091 graded every int8 cell INTEGRATION_BLOCKED; the host f16 cache likewise has no save/restore surface. This tick neither machine can run a live session anyway (the VM far below its inference gate; purplelongship unreachable). The slice therefore grades the benefit in the account's own filed units (J-094's read work and touch shapes — the honesty rule of every Part VI slice: no wall is measured on this VM, so no wall is filed), decides the privacy shape on the record, and builds exactly the part that is buildable and provable today if the pre-registered rule passes: the serialise/restore mechanism at the int8 store level, graded bit-exact in J-095's R-B form. Session wiring is not built at either precision. The live legs are **NOT PROVEN** and are filed as DEFERRED-WITH-REASON to the J-098 gate with an exact recipe (§7).

**The findings, in one paragraph.** The benefit at the account level is not close: a FULL restore at the 32k rung avoids **321,576,079,720,448 MACs** of re-read work (J-094's filed total) for a persistence traffic of 3,758,096,528 B at f16 / 1,937,768,592 B at int8 — **85,568 / 165,951 MACs of avoided work per traffic byte**, against a pre-registered bar of 1,000 — and the traffic is 0.012% of the re-read touch shape it replaces. The worst cell on the ladder (f16 @1,024) still clears the bar 57-fold (**57,792** MACs per traffic byte). The storage burden holds at every rung (the largest save file, f16 @32,768, is 40.12% of the model file it serves). The pre-registered verdict is therefore **PAYS at every rung × both precisions**, exactness is proven (§6.1), and an acceptable privacy shape exists (§6.2) — so under the slice's own rule the minimal mechanism **is built**: `serialize_int8_store` / `deserialize_int8_store` over J-088's real store, with binding, corruption refusal and dead rows never stored. Why this is not J-027's rejected question is stated in §6.3. The **live** benefit — any wall for a restart that restores instead of re-reading — remains **NOT PROVEN** (§7, §10).

## 2. Definitions and verdict rules (pre-registered)

Stated in `core/kv_persistence.mojo`'s header and committed (@ `351838dd`) before the tests or harness were built or run. The witness is the ladder's (J-091/J-094): Qwen2.5-Coder-7B Q4_K_M, sha256 `8053aeda222ba79e865a6eddd268332fd4e4dbe406371318d6df1f9beae9502b`, 4,683,074,688 B; 28 layers, hidden 3,584, ffn 18,944, 28 query heads, 4 kv heads, head_dim 128, profile context cap 32,768; rungs 1,024 / 4,096 / 8,192 / 16,384 / 32,768.

- **Candidate shapes.** FULL — every committed position's KV saved, per precision (f16 through J-087, per-row int8 through J-088). PREFIX — only the first P positions saved (the shared-prefix case); a prompt of L > P restores P rows and reads only the suffix. No other shape is priced: per-layer/per-head partial saves break attention's need for every layer's rows at a position, and saving rows past the committed length saves dead state (J-095) by definition.
- **Benefit, in filed units.** For a FULL save/restore at length L, per precision: WORK AVOIDED = J-094's read work at L (prefill attention + projection MACs, through `core/prompt_read`). Restoring avoids the read's work and nothing else — the model still loads, and the first generated token still pays its head pass (J-094 §2; never charged to the read, never claimed as saved here). FILE BYTES = 72 B of format overhead (64 header + 8 trailer, §4) + the KV total at L at the precision. TRAFFIC = 2 × FILE BYTES (one write at save, one read at restore — both directions charged). RE-READ TOUCH = J-094's host-batched touch shape at L at the same precision (the conservative surface comparator: the host-batched shape is the smallest surface shape J-094 files at either precision). WORK PER TRAFFIC BYTE = WORK AVOIDED // TRAFFIC, floored. For a PREFIX save of P at L: WORK AVOIDED = the read work at P exactly; the remaining work is W(L) − W(P) by the causal-pair account (suffix projections are per-token constant; suffix attention pairs are the total pairs minus the prefix pairs — conservation asserted in the tests). STORAGE BURDEN = FILE BYTES as floored ppm of the model file's bytes; a file larger than the model it serves is a burden failure at that rung whatever the work says.
- **Benefit verdict rule.** A cell grades PAYS iff TRAFFIC < RE-READ TOUCH **and** WORK AVOIDED ≥ TRAFFIC × 1,000 (three orders of magnitude of work per byte moved, stated before measuring). Any other outcome grades DOES_NOT_PAY with its numbers filed.
- **Privacy/storage decision rule.** A saved KV file is **PROMPT-EQUIVALENT** data: its rows are a deterministic function of the prompt's tokens and the model's weights (J-087's layout, J-088's quantizer), and a restored store continues the prompt exactly — that is the feature. It must be handled as the prompt's plaintext is handled. A persistence shape is the tuple (opt-in per save · owner-only access · bound to the model + shape + length it came from, mismatch refused · explicitly deletable in one operation · confined to the engine's cache home). **A shape is ACCEPTED iff all five properties hold; any one missing REJECTS the shape whatever its benefit.** (Owner-only by platform default alone does not count — the shape must state it.)
- **Worth-building verdict rule — built only if it pays.** The minimal mechanism (§4) is built iff ALL of: (1) every ladder cell (5 rungs × 2 precisions, FULL shape) grades PAYS and the storage burden holds at every rung; (2) exactness is provable at the store level in J-095's R-B form (the format is lossless by construction; any round-trip diff withdraws the mechanism, it is not filed); (3) an ACCEPTED privacy shape exists under the rule above. A measured REJECTION (nothing built) is a complete closure on this road (J-025 / J-027 / J-090 precedents); the verdict is whatever the filed numbers say. Two bounds hold whatever the rule returns: the **f16 mechanism is not built** (no List-backed f16 store exists to serialise — the host cache is the well's RuneTensor storage, J-087 §3.1 — so f16 persistence is priced here and its mechanism deferred to §7 with the host integration), and **no session is wired** at either precision (int8 session integration is INTEGRATION_BLOCKED, J-091).

## 6. Exactness, the privacy decision, and the J-027 distinction

### 6.1 Round-trip exactness (the mechanism's proof, R-B form)

The exercise store (J-095's shape: 2 layers × 2 kv-heads × head_dim 16, capacity 24, plain rows 0–10, fingerprint 424242) serialises to **1,832 B** (= 72 + 11 × 160) and restores **bit-exact**: 0 differing codes, 0 differing scales, dequantized max difference 0.0, attention identical at every layer and head — verdict **EXACT** under §2's rule, graded through `core/kv_drafts`' own diff functions (§8). Two controls keep the proof honest: rows appended *past* the saved length change no stored byte (dead rows are never stored — the serialised bytes are identical with and without them), and single-byte tampering — one payload code byte, one scale byte — is refused by the checksum on restore, as are bad magic, truncation, a trailing byte, a fingerprint mismatch, a sub-header file and an inconsistent kv_width header (6/6 refusals, §8). The inspect script additionally rebuilds the entire file in Python under the header's byte format from the stated synth rule and J-088's quantizer, and its checksum must equal the Mojo harness's filed checksum — byte-level cross-implementation agreement, so the format is specified tightly enough for a second implementation to reproduce it (§8).

### 6.2 The privacy/storage decision (on the record)

Graded mechanically by `kvp_privacy_verdict` over §2's five properties:

| Shape | Opt-in | Owner-only | Bound | Deletable | Confined | Verdict |
|---|---|---|---|---|---|---|
| OPT-IN (explicit save, cache home, bound, one-operation delete) | ✓ | ✓ | ✓ | ✓ | ✓ | **ACCEPTED** |
| SILENT (default-on, unbound) | ✗ | ✓ | ✗ | ✓ | ✓ | **REJECTED** |
| SHARED (world-readable / synced, unconfined) | ✓ | ✗ | ✓ | ✓ | ✗ | **REJECTED** |

Each property is individually disqualifying (the tests exercise all five single-missing cases). **The decision: persistence ships, when §7 wires it, only in the OPT-IN shape** — an explicit per-save opt-in; the file owner-only in the engine's cache home; restore bound by the header's fingerprint + shape + saved_len, mismatch refused and filed (never silently fallen back past — a caller may re-read after a refusal, but the refusal is on the record); deletion a single explicit operation. The mechanism built in this slice enforces the *binding* property at the store level (fingerprint + shape + checksum, §4); location, permissions, opt-in surface and deletion are host duties, specified in the module's host contract and in §7 step 2, because no session is wired here. A saved file's sensitivity follows from its definition: it is PROMPT-EQUIVALENT — whoever holds the file and the model holds a working continuation of the prompt — so backups, sync tools and shared caches that sweep the cache home would copy prompt-equivalent data, and the OPT-IN shape's confinement exists precisely to keep that decision with the user, per save.

### 6.3 Why this is not J-027's question

J-027 rejected persisting an expert *map* on a proven conservation: a prefetch fetch costs exactly the demand miss it replaces, so the oracle ceiling netted exactly zero. That conservation does not hold here, and §5 is the measurement of its failure to hold: recomputing one token costs its full projections plus attention over every prior pair (321,576,079,720,448 MACs over the 32k prompt), while restoring its KV costs its stored bytes once (traffic 3,758,096,528 B f16, both directions charged). The two persistence-adjacent questions of this road therefore close in opposite directions on their own evidence — the map is rejected, the KV pays — and neither verdict borrows the other's.

### 6.4 The worth-building verdict

Rule §2, applied to the filed numbers: (1) PAYS at all 10 FULL cells, burden holds at every rung (§5.1); (2) round-trip EXACT (§6.1); (3) the OPT-IN shape is ACCEPTED (§6.2). **All three clauses pass, so the mechanism stands as built** (§4) — at the store level only, int8 only, with no session wiring, exactly the bound the rule pre-registered. What the verdict does *not* say: that a restart is faster. That is a wall, and it is NOT PROVEN (§7, §10).

6. **Registration:** with the counted live runs, register `test_kv_persistence` in `tests/run_all.mojo` and re-account the pin (J-031 §10's rule).
