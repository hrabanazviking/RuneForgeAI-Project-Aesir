## 1. The verdict rule — stated before the verdict

**What evidence would have justified BUILD NOW.** Building a second GPU backend is justified only when all five of these hold at once, each as a filed artefact, not an assertion:

1. **Hardware in hand** — a non-NVIDIA GPU machine is physically available to this campaign (not ordered, not planned, not a spec sheet).
2. **A named consumer** — a specific model + session that must run GPU-accelerated on that hardware, named in advance.
3. **A spike measured** — the single prefill kernel of §7 (the width-1 Q4_K block matvec) actually built as a Vulkan compute shader and run on that hardware, beside the same kernel on the proven road.
4. **The spike faithful** — the Vulkan kernel's outputs match the scalar reference's reduction discipline (§7), and any session built on it would be graded ids-first, then teacher-forcing rank + logit gap against the ggml CPU comparator on the raw prompt (never `llama-cli --single-turn`).
5. **The spike competitive** — on that hardware, the Vulkan kernel beats the fallback Aesir would otherwise use there (the proven CPU line), median-of-3 walls with machine state filed. A faithful port that is slower than the CPU path it replaces buys nothing.

**The rest of the rule:** a measured spike that is *unfaithful*, or faithful but *uncompetitive* on the target hardware, is a **REFUSE** for that shape — the evidence will have answered the question the other way. Anything short of the full conjunction, with no measured counter-evidence, is **DEFER**: the question stays open, the reopen conditions (§7) stay filed, and no code is committed on a hunch — the roadmap's own closing words for this slice. The rule is mechanical in `core/vulkan_port_surface.mojo` (`evaluate_vulkan_verdict`); the suite pins every branch (§5).

## 2. Verdict

**DEFER — do not build a Vulkan compute path now; reopen only on §7's conditions.** Tonight's record against §1's rule: hardware in hand **no** (no non-NVIDIA GPU exists in the fleet in hand — §6), named consumer **no** (no model/session is waiting on a non-NVIDIA GPU), spike measured **no** (impossible tonight, §7), faithful/competitive **unmeasured**. The account evaluates exactly this record to DEFER (test group 4). Nothing measured tonight points the other way either: this is not a REFUSE — no spike has ever run and failed — and it is not within reach of BUILD NOW.

The grounds, in one paragraph: what Vulkan would buy is *GPU acceleration* on non-NVIDIA hardware — not Aesir itself, which already runs everywhere via its proven CPU line (J-030). The only named future case, the ROG Flow Z13's AMD iGPU, **has not landed**; every GPU machine in hand is NVIDIA and already on the proven CUDA road. What Vulkan would cost is a second full backend: **40 kernel families + 2 session surfaces + 8 infrastructure items = 50 work items** (§4), maintained in duplicate forever, graded per backend under J-060's battery, and exposed to per-driver shader variance of exactly the kind Janas's own public documents record having to self-check around. Paying that cost today buys acceleration for hardware the campaign does not have, for a consumer nobody has named. When the hardware lands, §7's spike — one kernel, both ways, on that hardware — is a small, bounded experiment that converts this verdict from inspection to measurement before any port is committed.

**No Vulkan code, shader, or backend stub is committed by this slice** — the roadmap forbids a rewrite on a hunch, and a fail-closed `VulkanGate` stub in the AMDGate pattern was considered and rejected for the same reason: a stub would be quoted as a started port, and tonight's honest state is *not started, deliberately* (§8).

## 4. The port surface — what building it would cost (the account)

`core/vulkan_port_surface.mojo` (§5) pins the surface as inspected; the counts are exact, the items are named, and **no effort estimate in hours is offered** — the campaign does not convert item counts into schedules it cannot measure.

- **40 kernel families:** packed matvec forms 2 + Llama device functions 15 + Gemma kernels 12 + CUDA-compute kernels 7 + session kernel 1 + fused/matrix kernels 3. Each is a SPIR-V shader (or shader family) to write, grade, and maintain *in addition to* its CUDA original — Mojo GPU kernels do not re-emit as SPIR-V through any in-tree path (§3), so none of the 40 is a recompile; all 40 are rewrites in a second kernel language.
- **2 session surfaces** to re-host (`Llama3CUDASession`, `Gemma4CUDASession`): open/admission, buffer layout, per-token and tile loops, sampling, and their existing contracts — or a new backend-neutral session layer, which is itself a build the tree does not currently have (§3's missing seam) and which would have to be proven not to disturb the CUDA sessions' filed proofs.
- **8 infrastructure items:** **I1** device discovery + capability/extension cache (Vulkan capability is extension-driven; vs `CUDAGate`); **I2** buffer allocation + memory-type selection across Vulkan's explicit heaps (vs `CUDADeviceResources`); **I3** an upload-staging replacement with the 64 MiB bounded discipline (vs `cuda_upload.mojo`); **I4** command-buffer submission + the cross-once synchronisation discipline (vs `context.synchronize()` / `enqueue_function`); **I5** a shader build pipeline — GLSL→SPIR-V compilation at build time (Janas's public INSTALL names glslang ≥15.2 and a build that proceeds without GPU support when unmet) **plus a per-driver self-check** that excludes shaders a driver computes wrongly (Janas's public docs file this as a real, shipped necessity — the RADV `fma()` case — so driver variance is a *measured cost of this road in the census record*, not a rhetorical one); **I6** the two session surfaces above, counted once here as the integration item if a seam is built instead; **I7** inventory + CLI truth for Vulkan devices (J-037's probe and `hardware.mojo:44` both change); **I8** a full J-060 battery re-grade of the new backend, per arch — a second backend doubles every future faithfulness cell, permanently.
- **Total: 50 work items**, before the first wall is measured. And the maintenance shape matters more than the count: every future kernel fix, quant kind, and arch lands twice or the backends drift — on a road whose CUDA side is *still* missing its own prefill GEMM (J-054 M1) and its MoE device pieces (J-058 G1–G5). A Vulkan port started today would be a second unfinished GPU road beside the first.

## 6. What Vulkan would buy — priced against the fleet as it stands

- **The benefit is real but narrow:** one compute API spanning NVIDIA, AMD, and Intel GPUs. For this campaign the benefit reduces to exactly one case — *GPU acceleration on a non-NVIDIA GPU* — because Aesir already runs on every machine it has via the CPU line (J-030, PROVEN) and on every NVIDIA GPU via CUDA (the wave record; ledger cross-check). Vulkan buys **no new machine the ability to run Aesir**; it buys a future AMD machine a faster prefill/decode than its CPU.
- **The fleet tonight:** purplelongship — NVIDIA (RTX 2060 class, the ledger's sm_75 record), served by CUDA, and the campaign's only GPU box; this VM — no GPU at all; Mimir — no GPU road in this campaign (its accelerator is the parked Hailo, untouched by this slice and not a Vulkan target). **Non-NVIDIA GPU machines in hand: zero.**
- **The named future case:** the ROG Flow Z13 *when it lands* is AMD (roadmap text; an order placed 2026-10-29 per the campaign's wider record, delivery not yet known — it has not landed). Its iGPU is also a *shared-memory* device (the design corpus's own example: an AMD Vulkan device shares system memory), which cuts both ways and must be measured, not assumed: no discrete VRAM tier, no upload wall of the discrete shape — and a memory-bandwidth profile much closer to the CPU it would replace than to a discrete card. Whether Vulkan prefill beats that machine's CPU line is precisely §7's spike question; the census's Janas numbers (e.g. its Qwen3-4B prompt at 220 vs 85 tok/s) are **Janas's, on Janas's hardware, and are not evidence about Aesir on a Z13** — they show the road can pay somewhere, not that it pays here.
- **The timing asymmetry decides it:** the cost (§4) is payable in full *today*; the benefit is payable only *after* hardware that has not landed arrives, and is then decidable by a one-kernel spike in days, not by a 50-item port in advance. Building now would also freeze the port against a CUDA surface that is still moving (J-054 M1, J-058 G-items unbuilt) — every one of those landings would have to be mirrored into a backend with no hardware to grade it on.

## 7. The spike that could not run tonight — and the exact reopen recipe

**Why no spike ran (environment evidence, from `j066_inspect_output.txt`, this VM):** `vulkaninfo`, `glslangValidator`, `glslc`, `nvcc`, and `nvidia-smi` are all **absent**; `/dev/dri` and `/dev/nvidia0` are **absent**; `/usr/share/vulkan/icd.d` is **absent** and `/etc/vulkan/icd.d` is **empty** — `libvulkan.so.1` exists as a loader library with **no installable client driver behind it**, so no Vulkan device can be enumerated, let alone run a shader; `libcuda.so.1` is **absent**, so the CUDA side of "both ways" cannot run here either. A kernel that cannot execute on either API cannot be graded, and writing an unrun shader to file would be exactly the hunch-commit the roadmap forbids. purplelongship could have supplied the CUDA side, but it is unreachable tonight, NVIDIA-only (it cannot supply the Vulkan-on-AMD evidence the question turns on), and yielded to the 204 road in any case.

**Reopen conditions — all of §1's items, as a recipe** (a device-capable worker, on the landed hardware):

1. **Trigger:** a non-NVIDIA GPU machine is in hand (the ROG Flow Z13 landed, or any AMD/Intel GPU box joins the fleet) **and** a named consumer is filed (model + session that must be GPU-accelerated there). Either alone does not reopen: hardware without a consumer is a benchmark toy; a consumer without hardware is this slice again.
2. **State the road choice first:** Vulkan vs the HIP road `AMDGate` gestures at — one paragraph, filed, against that hardware's actual driver state. The spike below is the Vulkan leg of that choice; a HIP spike, if chosen instead, is a different slice and does not discharge this one.
3. **The spike kernel (one prefill kernel, both ways):** `block_matvec_kernel` kind 12 (Q4_K), width 1, over device-resident bytes, at a J-054 filed projection shape (columns divisible by 256; e.g. the Llama 3.2 3B profile's Q/K/V slab shapes) — (a) as-is on the proven CUDA road (purplelongship, guarded idle window, 204 heartbeat checked first, machine state recorded), and (b) as a GLSL/SPIR-V compute shader on the target AMD/Intel device, built with the build-time compiler the census names (glslang ≥15.2 class), with the driver + version filed. Same input bytes, sha-pinned, both ways.
4. **Faithfulness grading (kernel level):** Vulkan outputs vs the scalar CPU reference, in the matvec kernels' own reduction discipline — bit-exact, or the exact divergence filed with its size and cause (driver `fma()` behaviour is the census's named suspect; a float64 once-rounded workaround, if needed, is part of the spike's result, not an embarrassment to hide). Then, if a session is ever built on it, the full road discipline: ids first vs the same surface's CPU ids, teacher-forcing rank + logit gap vs the ggml CPU comparator on the raw prompt, never `llama-cli --single-turn`, near-tie band and step-0 class as standing.
5. **Competitive grading:** median-of-3 walls per kernel call on the target hardware, machine state per run (loadavg, thermals, memory), against **the same machine's CPU matvec** — the fallback the port would replace there. Cells under sustained load or thermal distress are MEASURED-INDICATIVE and do not close the grade.
6. **Verdict by the account:** file the five booleans into `evaluate_vulkan_verdict`'s terms in the reopening slice's doc. BUILD_NOW authorises scoping the §4 port (in dependency order: I5+I1 → spike kernel generalised to J-054 M1's width-M form → I2/I3/I4 → I6/I7 → per-arch sessions → I8 battery). REFUSE closes the Vulkan question for that hardware/shape with the measured reason. Anything else stays DEFER and says which item is still missing.
