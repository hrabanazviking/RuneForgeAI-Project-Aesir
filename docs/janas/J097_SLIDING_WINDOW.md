## 1. The service — and the honest shape, stated up front

**The service.** An editor holds one document across many small edits. Without a window service, every edit costs a full re-read of the new version — J-094's read account at the new length. The sliding-window service retains the current version's token sequence and the KV rows of its committed positions (the WINDOW, the retained segment [0, L), bounded by the witness profile's 32,768 context cap). On an edit it computes the FIRST DIVERGENCE between the old and new token sequences by exact token comparison — the same comparison `core/prompt_prefix` performs — and keeps exactly the rows before it: a position p < C holds the same token at the same position with the same causal ancestry, so its KV rows stay valid. Every position p ≥ C is recomputed by the ordinary prefill: an edited token changes the causal ancestry of every later position, an inserted or deleted line slides every later position, and a moved line's own rows are **not** reusable at its new position (position and ancestry both changed). "Re-reads a moved line cheaply" means exactly this and no more: the re-read of a moved line costs the suffix from the **earlier** of its two endpoints, never the whole document unless the earlier endpoint is position 0.

**What this service is not.** It is not the architecture's sliding-window *attention* (the Gemma local layers in `core/compute.mojo`) — that is a model property; this is a context-retention service over versions of one document. Documents longer than the cap are not claimed: retaining only a trailing part would change attention semantics and is a different, unbuilt service (§2, §10).

**The shape this slice can honestly take.** No editor or completion session exists to wire today — Part VII's completion (J-111) is not built, and int8 session integration is INTEGRATION_BLOCKED (J-091) — and neither machine can run a live session this tick anyway (the VM far below its inference gate; purplelongship offline). The slice therefore builds the account and the divergence mechanism as a pure module, exercises the divergence computation on concretely edited token sequences for every stated edit shape, grades the service under its pre-registered rule in J-094's filed units, and defers every live quantity to the J-098 gate (§7). The findings, in one paragraph: the divergence exercise is **exact on all nine shapes**; the window is never worse than the naive re-read on any shape and strictly cheaper wherever any prefix survives; the stated editor mix saves **450,780 ppm** of the naive re-read work (**244,430,291,861,504** of **542,238,528,634,880** MACs) against a pre-registered bar of 250,000 ppm — so under its own rule the service is **KEPT**. The one shape that saves nothing is named plainly: a first-line edit (C = 0) has no prefix to keep and only ties. Every live quantity — any wall, any editor latency, whether a live session's kept rows are bit-identical in practice — is **NOT PROVEN** (§7, §10).

## 2. Definitions and verdict rules (pre-registered)

Stated in `core/kv_window.mojo`'s header and committed (@ `e2806e40`) before the tests or harness were built or run. The witness is the ladder's (J-091/J-094): Qwen2.5-Coder-7B Q4_K_M, sha256 `8053aeda222ba79e865a6eddd268332fd4e4dbe406371318d6df1f9beae9502b`, 4,683,074,688 B; 28 layers, hidden 3,584, ffn 18,944, 28 query heads, 4 kv heads, head_dim 128, profile context cap 32,768.

- **Workload model (editor-style, deterministic).** The document is 128 lines × 64 tokens = **8,192 tokens** (a ladder rung). Nine edit shapes, one occurrence each, stated before measuring: EDIT_LATE (edit in place, line 96, C = 6,144), EDIT_EARLY (line 8, C = 512), EDIT_FIRST (line 0, C = 0), MOVE_LATE (line 100 moved to the end, C = 6,400), MOVE_EARLY (line 8 moved to line 96, C = 512), INSERT_MID (a new 64-token line at line 32, C = 2,048, new length 8,256), DELETE_MID (line 32 deleted, C = 2,048, new length 8,128), APPEND (a new line appended, C = 8,192, new length 8,256), NO_CHANGE (the same document re-presented, C = 8,192). The MIX is the unweighted sum over these nine shapes. Token comparison itself is host integer work over at most min(old, new) positions — no model work, charged to no MAC account, and bounded by the document length; it is stated so it is never smuggled into, or out of, the account.
- **Cost definition (filed units only; no wall is measured on this VM in this slice).** Through `core/prompt_read` (J-094) over `core/kv_ladder` (J-091): W(L) is the accounted read work of a prompt of L tokens (attention + projection MACs; the head pass is the first generated token's, never the read's). REUSE is the number of leading positions whose KV the service keeps: the first divergence capped by the tree's FINAL-TOKEN rule — `core/prompt_prefix` never reuses the final prompt token (it always recomputes activations/logits) — so REUSE = min(C, new_length − 1), and also never more than the old length holds. Per shape: NAIVE COST = W(new_length); AVOIDED = W(REUSE) exactly (J-096's prefix conservation: the kept prefix's work is the read work at REUSE; suffix projections are per-token constant and suffix attention pairs are the total pairs minus the prefix pairs); WINDOW COST = NAIVE − AVOIDED; KV REWRITTEN = (new_length − REUSE) × the per-token KV price at the precision (f16 through J-087, per-row int8 through J-088, both through `core/kv_persistence`'s pricing so this account cannot drift from J-096's); SAVED PPM = AVOIDED as floored ppm of NAIVE, computed by `kw_saved_ppm` (§9's overflow-safe form — the value is the floored ppm either way).
- **Correctness rule.** The windowed result must equal the full re-read's result, stated in two parts, never blurred: positions p < REUSE are BIT-EXACT BY CONSTRUCTION against the full re-read at the same precision — same token, same position, same causal ancestry at every layer (by induction on layers: a position's layer-l KV depends only on tokens at positions ≤ p through layers < l), so a deterministic forward recomputes the identical rows the window kept; and positions p ≥ REUSE are RECOMPUTED by the ordinary prefill, not approximated — no row is reused across a divergence, a position shift, or a move. The divergence computation is exercised on real token lists for every shape in the tests (the predicted C must equal the computed first divergence of the concretely edited sequences). Whether a live session's kept rows are bit-identical in practice is a live question: NOT PROVEN here, deferred to the J-098 gate recipe (§7), and the first consumer (J-111, Part VII code completion) inherits that deferral by name.
- **Verdict rule — KEPT only if it pays.** The service is KEPT iff ALL of: (1) EXACTNESS: the divergence exercise passes for every shape — a mispredicted divergence withdraws the service, it is not filed; (2) NEVER WORSE: every shape's WINDOW COST ≤ its NAIVE COST, and every shape with REUSE > 0 is strictly cheaper than its naive re-read (the C = 0 shape may only tie: a first-line edit has no prefix to keep, and the service must say so rather than hide it); (3) THE MIX PAYS: the mix's SAVED PPM ≥ 250,000 ppm — a quarter of the naive re-read work over the stated editor mix, stated before measuring. Any other outcome grades NOT_KEPT with its numbers filed (J-025 / J-027 / J-090 precedents: a measured rejection is a complete closure). Two bounds hold whatever the rule returns: **no session is wired** (no editor or completion session consumes this service today; int8 session integration is INTEGRATION_BLOCKED, J-091, and the host prefix surface this service's reuse cap follows is wired only into the CUDA Llama session, not into any editor surface) — the inspect asserts the no-wiring fact; and every live quantity (any wall, any editor latency, J-111's published-class comparison) is NOT PROVEN in this slice and is filed as DEFERRED-WITH-REASON to the J-098 gate.
- **What is not built.** No eviction or trailing-window retention for over-cap documents, no per-line KV relocation (a moved line's rows are recomputed — a relocation that re-based positions would need a position-remapping proof this slice does not claim), no session or editor wiring, and no live measurement. The built surface is the account + the divergence mechanism of the module, exercised deterministically.

Readings, no more than the arithmetic says:

- **The moved line is the roadmap's case, and it is priced honestly.** MOVE_LATE — line 100 moved to the end of an 8,192-token document — re-reads only the suffix from position 6,400 (the earlier endpoint): 14,317,587,529,728 MACs instead of 60,190,493,769,728, a 762,128 ppm saving. The cheapness does **not** come from reusing the moved line: its tokens sit verbatim at positions 8,128–8,192 in the new version and not one of its rows is reused (the tests pin this) — position and causal ancestry changed, so its rows are recomputed as part of the suffix. What is avoided is the untouched prefix's work, and only that.
- **Where the edit sits is the whole story.** Attention's quadratic term makes late edits cheap to serve and early edits dear: EDIT_LATE saves 729,021 ppm while EDIT_EARLY — the same one-line edit at line 8 — saves only 55,944 ppm, and EDIT_FIRST saves exactly 0 (NO_SAVE, filed as such, not hidden). An editor whose edits cluster at the end of the document is this service's best case; a first-line-heavy workload would grade far worse under the same rule, and the mix verdict (§6) belongs to the stated mix, not to editors in general.
- **NO_CHANGE pays the final-token tax in the open.** Re-presenting the identical document still recomputes one token (reuse 8,191 of 8,192; KV rewritten exactly one token at each precision) because the tree's prefix law never reuses the final prompt token. The service inherits the law rather than quietly exempting itself.
- **Insert/delete symmetry, priced.** INSERT_MID and DELETE_MID diverge at the same position and keep the same prefix; their naive costs differ only because the new lengths differ (8,256 vs 8,128), and their saved ppm differ accordingly (227,047 vs 231,026). Nothing about a slide is charged or credited beyond the suffix recompute — the slide itself is free in this account because it *is* the suffix recompute.

## 6. Exactness and the verdict

### 6.1 The divergence exercise (the mechanism's proof)

For every shape the tests and harness build the concretely edited token sequence (an edited line's tokens replaced, a moved line's tokens relocated, a line inserted/deleted/appended) and compute the first divergence by exact token comparison over the actual sequences: **predicted == computed on all nine shapes**, with prefix controls exact (one sequence a prefix of the other diverges at the shorter length; identical sequences diverge at their length; a mid-sequence difference diverges at its position). The reuse cap is pinned on all nine shapes and on a synthetic pair (identical length-11 sequences reuse 10, never 11). Conservation (avoided + window cost == naive) and never-worse hold on all nine shapes, and the KV rewrite bytes are exact at both precisions on all nine.

### 6.2 The verdict, under the pre-registered rule

Rule §2, applied to the filed numbers: (1) EXACTNESS — the divergence exercise passes for every shape (§6.1); (2) NEVER WORSE — every shape's window cost ≤ its naive cost, strictly cheaper wherever reuse > 0, the C = 0 shape tying exactly as the rule allows; (3) THE MIX PAYS — **450,780 ppm ≥ 250,000 ppm**. **All three clauses pass, so the service is KEPT** — as an accounted, exercised mechanism with no session wired, exactly the bound the rule pre-registered. The rule can fail and is exercised failing on each clause in the tests (a worse shape rejects, an inexact divergence rejects, a mix under the bar rejects, and exactly 250,000 ppm keeps — the boundary is inclusive as stated). What the verdict does *not* say: that any edit is faster in wall time. That is a live quantity, and it is NOT PROVEN (§7, §10).

## 9. Defects found

- **No defect found in prior work.** Every gate this slice grades against reproduced exactly: J-094's read-work totals at all five rungs (the validation gate), J-087's/J-088's per-token prices through J-096's pricing path, J-096's prefix conservation holding as the identity AVOIDED == W(REUSE) at every shape, and all five neighbour suites rebuilt from this tree pass unchanged.
- **Two defects in this slice's own design files, found on first build and fixed in-slice (@ `6d0cc1aa`); no filed number rested on either, and no pre-registered definition changed:**
  1. **The tests as committed did not compile.** Mojo 1.0's `List[Int]` is not `ImplicitlyCopyable`, so every `var r = rows[i]` row access in `test_kv_window.mojo` is a compile error ("value of type 'List[Int]' cannot be implicitly copied … consider you can copy it explicitly with '.copy()'") — reproduced in the completion run by rebuilding the committed form, which fails at the first row access. Fixed by the explicit `.copy()` the compiler itself prescribes, at all seven row-access sites. The design commit's tests therefore never ran as committed; every PASS in §8 is from the fixed files.
  2. **The saved-ppm formula as committed overflows.** The design commit computed SAVED PPM as `avoided * 1000000 // naive` in the module, the mix pin in the tests, and the harness's MIX line. At this slice's work totals the scaling overflows a 64-bit integer: avoided × 1,000,000 reaches 60,190,493,769,728,000,000 (APPEND) against an Int64 maximum of 9,223,372,036,854,775,807 — **6 of the 9 shapes and the mix overflow** (verified independently in Python big integers, and asserted mechanically by the inspect). In Mojo the product would wrap and the ppm — including the mix ppm the verdict rule grades — would be garbage. Fixed by `kw_saved_ppm(avoided, naive)`: the floored ppm computed in two scaling steps (×1000, then ×1000 on the remainder), which is exact — avoided·1000 = q·naive + r gives ppm = q·1000 + ⌊r·1000/naive⌋ identically — and cannot overflow (each intermediate stays below naive × 1000 ≈ 5.4×10¹⁷). Applied in the module (account + service verdict), the tests and the harness; the inspect asserts no single-step form remains anywhere and that the two-step form equals the direct big-integer ppm on every shape and the mix (450,780).
- **A note on the harness's earlier partial run:** the design worker's first builds (before the stall) already contained both fixes in the working tree and produced harness runs byte-identical to the completion run's filed runs (same sha256) — the completion run rebuilt everything from the banked tree state and re-ran every suite itself; no number in this doc rests on the earlier partial run.
