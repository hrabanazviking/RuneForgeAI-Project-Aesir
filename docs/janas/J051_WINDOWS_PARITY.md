## 3. What the tree DOES carry for Windows — the WSL bridge (filed record; not re-run by this slice)

## 5. The Part III portability audit — every item graded

Grades: **portable-by-construction** (no OS assumption in the item; it would behave as written on any hosted build), **windows-risk-with-reason** (a named Linux/POSIX assumption; the reason and the failure mode are stated), **not-applicable** (the item makes no OS contact to grade). Evidence is the filed audit output plus the passages read verbatim for this doc.

### Portable-by-construction

- **P-1 — Option grammar, values, precedence, kills** (`placement_options`, `manual_override`, `server_placement`'s field claiming): pure string logic over argv text and env text — grammars, refusal tables, the hand > preset > learned > auto stack. No path, file, or OS call in the logic. The one FFI touch is reading env values through `getenv` (`placement_options.mojo:1017`, and the same shape restated in `device_inventory`/`learned_file`/`manual_override`/`parallel`): `getenv` is present in every hosted C runtime including MSVC's, and the `AESIR_*` names are valid environment names on Windows.
- **P-2 — The decision core**: the three choosers' decision rules and records (`prompt_placement`, `reply_placement`, `draft_placement`), `within_tolerance`'s grading, `placement_pressure`'s planner, `placement_explain`'s assembly, `cowork_passes`' split planner/join accounting, `moe_gpu_plan`'s division accounting, `expert_cache`'s policy arithmetic. Pure arithmetic and string assembly over supplied records and facts; they consume the probed/measured pieces but touch no OS surface themselves. Their *inputs* are graded at W-1…W-6; the rules are not the port's work.
- **P-3 — Device-inventory parsers** (`parse_cpuinfo`, `apply_hybrid_split`, the nvidia-smi row parser, the DRM listing parser): pure functions over injected text, unit-proven since J-037 on fixtures including GPU-present rows. A port reuses them unchanged behind a Windows-shaped probe (W-1).
- **P-4 — The learned-file FORMAT** (J-044): a fixed-order line block of `\n`-terminated lines with an FNV-1a checksum over the body, parsed by exact offsets. Bytes are written and read as bytes; the format carries no OS fact. The line-ending consequence is fail-closed by design, read first-hand in the parser: the loader splits on `"\n"`, rebuilds the body line-by-line, and verifies the checksum over the rebuilt bytes — a CRLF-mangled copy (the classic Windows-editor/checkout accident) changes those bytes, fails the checksum, and is **REFUSED whole with the reason**, never partially applied, never a crash (the same refusal J-044's corrupt/bit-flipped groups already prove for byte changes). The tree's `.gitattributes` eol discipline (§3) is the same instinct applied to its fixtures.
- **P-5 — The retrial log's path**: `learned path + ".retrials.log"` — a suffix append, separator-free, exactly as portable as the learned path it rides on (its append *mechanism* is W-5).
- **P-6 — Server parity layer** (`server_placement`): pure resolution/conformance over request fields and the session's stated resident placement. The resident server it describes (`native_serve`, CUDA + POSIX) is the engine's Linux surface and is graded under Delta W1, not as a Part III assumption.

### Windows-risk-with-reason

- **W-1 — Device inventory's LIVE probe** (`device_inventory.mojo:534,559,565,567`): reads `/proc/cpuinfo` and the `/sys/devices/cpu_core|cpu_atom` cpulists, cross-checks the GPU via `ls /sys/class/drm`, and probes `nvidia-smi` argv-only through `posix_process`. `/proc` and `/sys` do not exist on Windows-native; `ls` is not a Windows command. **Failure mode is honest degradation, not a crash — PROVEN by the code's own structure**: `observe_device_inventory` never raises; each probe failure becomes that kind's absent-with-reason entry (the hybrid-split read is separately try-wrapped), the same shape J-037's live VM line demonstrates. `nvidia-smi` itself exists on Windows, so the GPU row parser (P-3) has a real Windows input; the procfs/sysfs reads are the probe's port points.
- **W-2 — Thread topology's live facts** (`thread_topology.mojo:293,299,301`): duplicates W-1's `/proc` + `/sys` reads to build the ladder's facts. Same class, same failure shape (facts absent → the ladder cannot be derived live); the ladder derivation from supplied facts is P-2/P-3-grade pure.
- **W-3 — The threaded executor's vehicle** (`core/parallel.mojo` → `aesir_engine/thread_par.c`, `libaesir_par.so`, linked `-lpthread` in CI and by `scripts/launch.py`): POSIX threads and a `.so` shim are the tree's only threading vehicle, and Part III's threaded trials (J-039) and co-work analogue (J-043) ride it. The shim's contract degrades any *shim* failure to the serial call — never a crash, never a hang — but a Windows-native build today has no shim to link at all: a Win32-thread port of this one C file is Delta W1 work. The serial path every trial compares against is in-process and portable.
- **W-4 — The harness clock** (`placement_harness.mojo:128–135`): `monotonic_ns` is one FFI function over `clock_gettime(CLOCK_MONOTONIC)`. POSIX-named; the settle/median/bound accounting it feeds (`account_rounds`) is pure and portable. A port replaces this one function (a performance-counter equivalent), nothing else in the harness.
- **W-5 — The learned file's persistence FFI** (`learned_file.mojo:1337,1353,1376,1392,1401,1444` and companions): the tree's persisted-record discipline in full — two-argument `mkdir(path, 448)`, `mkstemp`, `open64`, `pwrite`, `fsync` (including on a parent-directory fd), `rename`, `unlink`, `__errno_location`. Every one is a glibc/POSIX name or signature; `__errno_location` is glibc-specific even among POSIX systems, and MSVC's `rename` additionally refuses to replace an existing target, which would break the stage→rename atomic-replace pattern specifically even where the name exists. `retrial.mojo`'s log append shares the class (`pwrite` + `fsync`, `:808,822`) and adds no new assumption. **This is tree-uniform discipline, not a Part III idiosyncrasy**: `state_vault.mojo` carries the identical pwrite/fsync/rename pattern (`:85,109,125,134`) — the port point is the tree's persistence style itself, named once here for the whole style.
- **W-6 — The learned file's path construction** (`learned_file.mojo:1264,1266,1315,1325`, `learned_file_path:1252–1276`): joins with `"/"`, derives parents by scanning for byte 47 only, and roots the default chain in `$HOME` (`$HOME/.cache/aesir/…`). Three distinct Windows facts: (a) Win32/CRT file APIs do accept `"/"` as a separator — stated as platform knowledge, **NOT PROVEN on this tree**, and irrelevant until the FFI of W-5 exists to carry a path at all; (b) `HOME` is not a Windows-native variable (the native root is `USERPROFILE`), so the default chain silently falls through to `.aesir-cache/` in the working directory — a behavioural difference, in the safe direction (a local cache, not a wrong one), but a difference a port must decide on purpose; (c) a user-supplied `AESIR_CACHE_HOME`/`AESIR_LEARNED_FILE` value written with `"\"` separators would defeat `_learned_parent`/`_ensure_parent_dirs`, which see no `"/"` in it. The explicit overrides themselves are separator-agnostic in intent (a full path supplied by the user wins as written).
- **W-7 — `setenv`/`unsetenv` FFI** (`thread_topology.mojo:313–339`): the trials' env-staging helper uses the POSIX names; MSVC's CRT offers the `_putenv` family instead. Confined to staging `AESIR_THREADS`-class variables for trials and tests; the `getenv` reads of P-1 are unaffected.

### Not-applicable

- **N-1 — GPU/NPU placement semantics**: no GPU executor exists on any platform yet (J-038's standing fact), so there is no Windows GPU behaviour to diverge; the NPU entry is a campaign ledger state (parked), not an OS fact. Both are graded where they actually live — W-1's probe and Delta W1.
- **N-2 — Report text**: every Part III report is a `"\n"`-joined string the host prints. No Part III module opens a console, a file, or a codepage; rendering is the host surface's business, not a placement assumption.

## 6. What placement means for a Windows user today — the WSL reading (reasoned; NOT PROVEN by any run in this slice)

Because the only Windows route is the bridge, the placement behaviour a Windows user actually gets today is Part III's Linux behaviour inside their WSL distro. Read from the code (each point's grade is the reasoning's, not a measurement's):

- **The inventory describes the VM, honestly.** Under WSL2, `/proc/cpuinfo` reports the vCPUs WSL assigns the distro, not the host's silicon; the hybrid cpulists are absent, so the split is stated not-reported — J-037's machine-stated-only discipline makes the line truthful as far as it goes, but a choice measured there is chosen for the VM's resources, and a host with a large P/E topology behind a small WSL allocation is invisible to it.
- **The learned file lives in the distro.** `$HOME` under WSL is the distro user's home, so the default learned path sits on the distro filesystem with the POSIX semantics the format assumes (W-5/W-6 do not bite on this route). If a user instead points `AESIR_CACHE_HOME` at a DrvFS mount (`/mnt/…`), the tree's own launch doc warns that DrvFS applies its mounted Windows permission semantics (`docs/LOCAL_LAUNCH.md:46`; AES-FND-008's boundary says the same) — what that does to the learned file's fsync/rename discipline specifically is **NOT PROVEN**.
- **Key drift is the safe failure.** Changing WSL's resource allocation changes the J-037 facts, which changes the J-044 machine key, so learned entries miss *by name* (MACHINE-MISMATCH) rather than applying wrongly; J-045's re-trials own the recovery. The same holds if the checkout moves between distros.
- **The drafts/G1 and parked-NPU facts are unchanged by the OS route** — they are Aesir facts, and the bridge carries them verbatim.

None of §6 was exercised in this slice: no Windows host, no WSL, no PowerShell run. It is filed so the J-052 gate can label WSL claims correctly, and so a future attended WSL session has its checklist already written.
